XiHan.Framework.ObjectStorage.FileSystem ​

对象存储的默认实现：本地目录按容器与键存放内容与元数据，原子替换写入，ETag 是内容的 SHA-256，带总量与单对象配额。适用于开发、测试、单实例部署，以及挂了共享卷的小规模部署。

项内容
包 IDXiHan.Framework.ObjectStorage.FileSystem
环层Ring 3（实现）
能力提供 objectstorage.blob@1、objectstorage.multipart@1（role: default）；依赖 kernel.hosting@1
特性入口FileSystemObjectStorageFeature
配置节XiHan:ObjectStorage:FileSystem
依赖XiHan.Framework.ObjectStorage.Abstractions
AOT兼容
稳定性Stable

概述 ​

存储把每个容器放在根目录下的一个子目录里：

text
<RootPath>/<container>/data/<key>          内容
<RootPath>/<container>/meta/<key>.json     元数据（内容类型、ETag、修改时间、自定义元数据）
<RootPath>/<container>/uploads/<上传标识>/  未完成的分片上传

键的各段经编码后作为路径，大小写不敏感的文件系统上键仍区分大小写；容器目录按需创建。写入先落同目录的临时文件（名字含 ~xihan-tmp-，键的编码不会产出 ~，键里写什么都不会被当作临时文件），复制完成后原子替换，再写元数据。配额在进程内计量：启动时扫描目录得到已用量并清理残留的临时文件，之后每次写入与删除更新。

预签名不是文件系统的能力。需要限时地址时装 Hosting.AspNetCore 的 HostedBlobUrlFeature 并 MapXiHanBlobs()，由宿主代收发，见对象存储。

何时使用 ​

  • 开发与测试，或单实例部署：默认就用它，Profiles.Full 已装配。
  • 多实例部署、对象量大、需要客户端直连存储：用 ObjectStorage.S3。多个进程共享同一目录时本包的配额只是近似。

安装与启用 ​

bash
dotnet add package XiHan.Framework.ObjectStorage.FileSystem --prerelease

当前是预览版，安装要带 --prerelease；从源码或本地包源引用见快速上手。

csharp
builder.AddXiHan(xihan => xihan.UseFeature<FileSystemObjectStorageFeature>());

配置 ​

键类型缺省说明
RootPathstring<AppContext.BaseDirectory>/blobs根目录；相对路径按当前目录解析，结尾的目录分隔符去掉
MaxTotalBytes正整数1073741824（1 GiB）全部对象的总字节上限
MaxBlobBytes正整数268435456（256 MiB）单个对象的字节上限，分片与拼接后的对象同样受它约束
MultipartExpiryHours正数168（7 天）未完成的分片上传保留多久；过期即拒绝再传分片与完成，启动时与运行期间清掉
MaxMultipartUploads正整数1000未完成的分片上传数上限
json
{
  "XiHan": {
    "ObjectStorage": {
      "FileSystem": { "RootPath": "/var/lib/app/blobs", "MaxTotalBytes": 1073741824, "MaxBlobBytes": 268435456 }
    }
  }
}

非 root 运行的容器镜像里应用目录可能不可写，KubernetesApp 示例在生产配置里把 RootPath 设到 /tmp/xihan-blobs；要持久保存的数据挂卷并把 RootPath 指过去。

命名实例（Provider 名 filesystem）的设置用同样的四个键，RootPath 必填：

json
{ "XiHan": { "ObjectStorage": { "Stores": { "archive": { "Provider": "filesystem", "RootPath": "/var/lib/app/archive" } } } } }

主要类型 ​

类型说明
FileSystemObjectStorageFeature特性入口（IHostedFeature、IShadowAwareFeature）；启动时扫描目录；被 S3 等存储顶替（或没被选为对象存储、分片上传只是兜底选出）时只登记命名实例 Provider；常量 HealthName = objectstorage.filesystem.capacity
FileSystemBlobStore实现 IBlobStore 与 IBlobMultipartStore；RootPath、UsedBytes；不经宿主使用时用 CreateAsync 创建（建目录并扫描已用量后才交出，构造不公开）
FileSystemObjectStorageOptions选项；FromConfiguration、FromSettings（命名实例的设置，未知键抛出）
FileSystemBlobStoreProvider命名实例的 Provider，ProviderName = filesystem

使用示例 ​

不经宿主直接使用（测试、命令行工具）：

csharp
using XiHan.Framework.ObjectStorage.Abstractions.Blobs;
using XiHan.Framework.ObjectStorage.FileSystem;

var store = await FileSystemBlobStore.CreateAsync(new FileSystemObjectStorageOptions { RootPath = "./data/blobs", MaxTotalBytes = 64L << 20 }, TimeProvider.System, NullLoggerFactory.Instance, CancellationToken.None);
// 扫描已用量、清理残留的临时文件与过期的分片上传

var put = await store.PutAsync(new ContainerName("reports"), new BlobKey("2026/10/summary.txt"), "hello"u8.ToArray(), BlobPutOptions.Default, CancellationToken.None);
Console.WriteLine($"{put.ValueOrThrow().ETag}, used {store.UsedBytes} bytes");

行为与限制 ​

  • 原子性：读取方要么看到旧对象，要么看到完整的新对象。不覆盖的写入（含分片上传的完成）由文件系统原子判定谁先占住内容路径：Linux 与 macOS 上先以独占创建的空文件占位、再把内容原子替换上去，Windows 上不替换地改名；内容文件已存在即 OBJECTSTORAGE_CONFLICT_001，并发的不覆盖写入（含共享目录的多个进程）只有一个成功（ADR-0089、ADR-0168、ADR-0172）。
  • 配额：复制过程中逐段检查并预留额度，超过 MaxBlobBytes 或 MaxTotalBytes（已用量加正在写入的全部预留）的项返回 OBJECTSTORAGE_UNAVAILABLE_002，不留下内容；并发写入合计也超不过总配额。覆盖写入期间新旧内容同时在盘上，要有新内容全长的余量，旧对象的字节在替换后才释放（ADR-0183）。单进程计量正确，多进程共享目录时只是近似。
  • 列举：遍历容器目录、按序数排序、按前缀过滤，续页标记是上一页最后一个键；外部直接放进 data/ 目录、没有元数据的文件按文件信息补一份元数据；文件名还原出的键不符合键文法的（含保留前缀 .xihan 下的，ADR-0090）跳过。
  • 范围读取：打开内容文件后定位到起点，只交出该段。
  • 分片上传：每次上传一个目录，manifest.json 记键与写入选项，分片文件名带编号与内容的 SHA-256，同一编号重传先落新文件再删旧的；完成时按清单拼接成同目录临时文件再原子替换，计入配额后删掉上传目录。暂存的分片计入总配额，未完成的上传最多 MaxMultipartUploads 个，过期的上传拒绝再传分片与完成（ADR-0184）。上传标识只认本实现发出的 32 位小写十六进制。
  • 健康项 objectstorage.filesystem.capacity 由存储同步计算：已用量达到 MaxTotalBytes 即 Degraded（OBJECTSTORAGE_UNAVAILABLE_002），否则 Ready。命名实例的探测用同一口径。
  • 命名实例建出时即建目录并扫描用量，预签名用宿主签名器的 ForStore(name)。本包被别的存储顶替时仍登记 filesystem Provider，命名实例照常可用。
  • 与 S3 混装、以本包为缺省实例时，指定 objectstorage.blob = xihan.objectstorage.filesystem 即可，S3 只登记命名实例；要缺省的分片上传再把 objectstorage.multipart 指定给本包，要缺省的预签名装 HostedBlobUrlFeature 并把 objectstorage.presign 指定给 xihan.hosting.blob-urls。有特性依赖分片上传或预签名却没指定时，那项能力解析到 S3 且是被要求的，OBJECTSTORAGE_VALIDATION_004 启动失败（见对象存储）。
  • 通过 ObjectStorage.Conformance 的 BlobStoreConformance 与 BlobStoreProviderConformance。
错误码含义
OBJECTSTORAGE_NOTFOUND_001对象不存在
OBJECTSTORAGE_NOTFOUND_002分片上传不存在或已结束
OBJECTSTORAGE_VALIDATION_001读取范围的起点不在对象内
OBJECTSTORAGE_VALIDATION_002分片清单不合法
OBJECTSTORAGE_CONFLICT_001对象已存在且不允许覆盖
OBJECTSTORAGE_UNAVAILABLE_001IO 失败，reason 只写异常类型的全名，完整异常进日志（ADR-0115）：IO 异常的消息常带服务器上的完整路径
OBJECTSTORAGE_UNAVAILABLE_002配额或单对象大小超限
