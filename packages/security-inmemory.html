XiHan.Framework.Security.InMemory ​

安全的默认实现：从配置装载 API Key 主体与权限授予，提供 security.authentication@1（ApiKey 方案）与 security.authorization@1（RBAC 授予存储）。只用于开发、原型与测试。

项内容
包 IDXiHan.Framework.Security.InMemory
环层Ring 3（实现）
能力提供 security.authentication@1、security.authorization@1；依赖 kernel.hosting@1
特性入口InMemorySecurityFeature（清单 xihan.security.inmemory，role: default）
配置节XiHan:Security（含 InMemory 子节）
依赖XiHan.Framework.Security.Abstractions
AOT兼容
稳定性Stable；InMemoryPermissionGrantStore 实现 Preview 的授予管理接口，与 InMemorySecurityHealthContributor 同为 Preview

概述 ​

特性只为解析器选中自己的能力注册服务与中间件：

能力被本包提供时注册
security.authentication@1InMemoryPrincipalStore、ApiKeyAuthenticationHandler、Authenticate 阶段的 AuthenticationMiddleware
security.authorization@1InMemoryPermissionGrantStore 与 IPermissionGrantStore、PermissionChecker、authenticated 策略、PolicyCatalog、Authorize 阶段的 AuthorizationMiddleware；启动时核对操作契约引用的策略（SECURITY_VALIDATION_004，ADR-0080）

清单角色是 default：装配 Security.Jwt 或 Security.OpenIdConnect 后本包让出认证、只提供授权；装配 Security.Database 后让出授权、只提供认证；两边都被顶替时本包不装配。健康项 security.inmemory.capacity 只看本包仍在提供的那部分存储。

何时使用 ​

  • 本地开发、演示、自动化测试，主体与授予随配置提交：用本包。Profiles.Standard 已包含它。
  • 生产环境：认证换 Security.Jwt 或 Security.OpenIdConnect，授予换 Security.Database。

安装与启用 ​

bash
dotnet add package XiHan.Framework.Security.InMemory --prerelease

当前是预览版，安装要带 --prerelease；从源码或本地包源引用见快速上手。单独装配时：

csharp
using XiHan.Framework.Hosting.AspNetCore;
using XiHan.Framework.Security.InMemory;

var builder = WebApplication.CreateBuilder(args);
builder.AddXiHan(xihan => xihan.UseFeature<InMemorySecurityFeature>());

var app = builder.Build();
app.UseXiHan();
app.Run();

配置 ​

键（XiHan:Security:InMemory）类型缺省说明
Principals:<id>:ApiKeystring必填API Key，至少 8 个字符；节名 <id> 是主体 ID
Principals:<id>:DisplayNamestring无显示名
Principals:<id>:Rolesstring无逗号分隔的角色
Principals:<id>:Tenantstring无所属租户，写成 tenant 声明
Principals:<id>:Claims:<type>string无附加声明
Grants:role:<role>string无授予角色的权限码，逗号分隔，* 为全部
Grants:user:<id>string无授予用户的权限码，逗号分隔
MaxPrincipalsint1000主体上限
MaxGrantsint10000授予上限，按（主体，权限码，租户）计数

XiHan:Security:RequireAuthentication 与 XiHan:Security:RoleClaim 见 Security.Abstractions。

json
{
  "XiHan": {
    "Security": {
      "InMemory": {
        "Principals": {
          "alice": { "ApiKey": "dev-alice-key", "DisplayName": "Alice", "Roles": "admin,editor", "Tenant": "acme", "Claims": { "email": "alice@example.com" } },
          "bob": { "ApiKey": "dev-bob-key", "DisplayName": "Bob", "Roles": "viewer", "Tenant": "acme" }
        },
        "Grants": {
          "role": { "admin": "*", "editor": "orders.read,orders.write", "viewer": "orders.read" },
          "user": { "alice": "reports.read" }
        }
      }
    }
  }
}

配置里的授予都是全局的（对任何租户生效）；租户专属授予只能在运行时经授予管理 IPermissionGrantAdministration.GrantAsync 添加。

主要类型 ​

类型说明
InMemorySecurityFeature特性入口；HealthName = security.inmemory.capacity
InMemorySecurityOptionsMaxPrincipals、MaxGrants、TenantClaim、Principals、Grants；FromConfiguration 读取上面的配置，TenantClaim 读 XiHan:MultiTenancy:TenantClaim（缺省 tenant）
PrincipalRecord配置里的一个主体：Id、ApiKey、DisplayName、Roles、Tenant、Claims
InMemoryPrincipalStore主体存储：FindByApiKey（常量时间比较）、Set、Remove、Capacity、Count
ApiKeyAuthenticationHandlerApiKey 方案的处理器；SchemeName = ApiKey
InMemoryPermissionGrantStore授予存储，同时是 IPermissionGrantAdministration：GetManyAsync、GrantAsync、RevokeAsync（各一次加锁处理整批）、ListAsync、Capacity、Count
InMemorySecurityHealthContributor健康项的贡献者

使用示例 ​

带 API Key 调用 framework/samples/SimpleApp：

bash
curl -H "Authorization: ApiKey dev-alice-key" http://localhost:5000/whoami

运行时添加租户专属授予：

csharp
using XiHan.Framework.Primitives;
using XiHan.Framework.Security.Abstractions.Permissions;

public sealed class TrialGrants(IPermissionGrantAdministration grants)
{
    // 只在 acme 租户里给 bob 导出权限；配置文件里写不了租户专属授予
    public ValueTask<Result> GrantExportAsync(CancellationToken cancellationToken)
        => grants.GrantAsync(new PermissionGrant(GrantSubject.ForUser("bob"), "reports.export", "acme"), cancellationToken);

    // 不存在时是 SECURITY_NOTFOUND_002
    public ValueTask<Result> RevokeExportAsync(CancellationToken cancellationToken)
        => grants.RevokeAsync(new PermissionGrant(GrantSubject.ForUser("bob"), "reports.export", "acme"), cancellationToken);
}

行为与限制 ​

  • 被选为授权能力时，特性在 Configure 里登记启动核对 PolicyCatalog.EnforceOn，核对操作契约按名引用的策略：内核在容器建好之后、任何特性启动之前执行它，不存在（含 permission:<code> 的权限码未登记）即抛出 SECURITY_VALIDATION_004、宿主启动失败，不论失败策略（IsolateFeature 也一样，不包成 KERNEL_HOSTING_002）；之后登记的操作（插件握手之后）在登记时核对（ADR-0080、ADR-0085）。特性本身不实现 IHostedFeature。
  • 认证成功的主体按顺序带上：每个角色一条类型为 XiHan:Security:RoleClaim 的声明、一条租户声明（有 Tenant 时）、附加声明。租户声明的类型取 XiHan:MultiTenancy:TenantClaim（缺省 tenant），与多租户的 ClaimTenantResolver 读同一个配置键，改了它 ApiKey 主体的租户照样被认出。
  • API Key 逐条做常量时间比较；找不到返回 SECURITY_DENIED_003。
  • 容量：新增主体超过 MaxPrincipals、新增授予超过 MaxGrants 时返回 SECURITY_UNAVAILABLE_002；替换已有主体、重复授予不占容量。配置里的条目超过上限时，构造存储即抛出 FrameworkException。
  • 授予存储按（主体，租户）分组保存：被容量拒绝的授予不留下任何条目，撤销某个主体在某个租户下的最后一条授予时连同这一组一起移除，授予与撤销反复进行也不会让存储增长。
  • 健康项 security.inmemory.capacity：主体存储或授予存储任一达到上限即 Degraded（SECURITY_UNAVAILABLE_002，两者都满时报主体存储），否则 Ready。
  • 数据只在进程内存里：运行时的增删不跨实例同步，重启后恢复为配置内容。
  • 通过 Security.Conformance 的 PermissionGrantStoreConformance。

API Key 明文写在配置里

主体与 API Key 随配置文件分发，任何能读配置的人都能冒用这些主体。本包只用于开发与测试，示例值用 dev-…-key 这类明显的开发值。
