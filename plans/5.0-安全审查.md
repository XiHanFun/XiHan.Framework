> 日期：2026-11-12。
>
> 方法：五组并行只读审查。
> - 认证、授权与 WebAuthn
> - 租户隔离
> - 入站协议与宿主
> - 出站、反序列化与资源上限
> - 文件路径、插件、密钥与加密
>
> 每条标注复核状态：
> - 「复核确认」：对照代码逐行核过。
> - 「审查确认」：审查时读代码确认，未再复核。
> - 「推断」：未完全核实。

## 一、高危

- **S-01 端点上的授权要求会替换操作契约的权限**（复核确认；两组独立发现，一组在运行时复现）**已修：ADR-0174**
  - 位置：`Security.Abstractions/Authorization/AuthorizationMiddleware.cs:27-32`。只要有显式要求，就不再按契约推导；`UseXiHan()` 也只取端点上的最后一个要求（`Hosting.AspNetCore/ApplicationBuilderExtensions.cs:74-77`）。
  - 场景：宿主写 `app.MapXiHanOperations().RequireXiHanAuthentication()`，本意是「API 要登录」。结果任何没有授予的已登录用户都能调用每个 HTTP 操作，各操作声明的权限全部失效。`MapXiHanOperations()` 的 XML 文档恰好建议在这里加授权约定（ADR-0144）。gRPC 与 MCP 仍按契约检查，只测这两种协议发现不了。
  - 修法：端点上的全部要求与契约要求一起判定，全部通过才放行。补 HTTP 层测试。
- **S-02 插件经清单拿到宿主任意配置节与绑定，含密钥**（复核确认）**已修：ADR-0177**
  - 位置：`Plugins.Wasm/Runtime/WasmPluginRuntime.cs:1104-1121`、`Plugins.OutOfProcess/Runtime/PluginRuntime.cs:947-967`。`Configure` 把清单 `contributes.config.section` 指向的整节和清单列出的每个绑定原样交给插件，不检查归属，也不经授予。
  - 场景：一个零权限的 Wasm 插件（README 写明适合不受信任的插件）在清单里写 `XiHan:Security:Jwt`，就能拿到 JWT 密钥并伪造任意主体，预签名密钥、数据库连接串、AI 与 S3 密钥同理。进程外插件的环境变量白名单因此也失效了。
  - 修法：配置节限定在 `XiHan:Plugins:<清单 ID>` 之下，或者要求运营方显式授予 `config:<节>` 与 `binding:<名>`，未授予的在发现插件时就拒绝。同步改 `spec/plugin/lifecycle.md`。
- **S-03 S3 命名实例没给密钥时使用宿主的 AWS 凭据**（复核确认）**已修：ADR-0178**
  - 位置：`ObjectStorage.S3/S3ObjectStorageFeature.cs:226-228`。`AccessKey` 或 `SecretKey` 为空时走 `new AmazonS3Client(config)`，即 SDK 的默认凭据链（环境变量、配置文件、实例角色）。命名实例的设置可以由租户填写（ADR-0117）。
  - 场景：能登记存储实例的租户管理员只填 Region、不填密钥，就能以宿主的身份列举、读写宿主角色能访问的任何桶；`EnsureBuckets` 还能在宿主账号里建桶。
  - 修法：命名实例必须给出两项密钥，只给一项也拒绝。用环境凭据只能由运营方在 Provider 选项里打开，不能经实例设置打开。

## 二、中危

- **S-04 WebAuthn 认证不核对凭据归属**（复核确认）**已修：ADR-0179**
  - 位置：`Security.WebAuthn/WebAuthnCeremonies.cs:255-259`。只有存储的凭据和响应两边都带用户句柄时才比对。`VerifyAuthentication` 没有「期望用户」入参，`WebAuthnRegisteredCredential` 也不交回句柄，应用很容易存成空。
  - 场景：知道受害者口令的攻击者，用自己账号下的通行密钥签受害者的挑战并省略句柄，校验就会通过。文档的示例按 `response.Id` 查凭据，也不核对归属。
  - 修法：加 `expectedUserHandle`；响应带了句柄而存储没有时拒绝；改文档示例；注册时提示「凭据 ID 不得已登记」。
- **S-05 OIDC 不配 `Audience` 时不校验受众**（复核确认）**已修：ADR-0180**
  - 位置：`Security.OpenIdConnect/OpenIdConnectAuthenticationHandler.cs:126-127`。
  - 场景：多个应用共用一个身份提供方（Entra、Google、Auth0，或同一 Keycloak realm 下的多个客户端）时，发给别的应用的令牌也会被接受。
  - JWT 同样不强制受众，但用的是应用自己的对称密钥，风险低得多。
  - 算法白名单只算加固：Microsoft.IdentityModel 不会把 RSA 公钥当 HMAC 密钥用。
  - 修法：OIDC 必须配置 `Audience`，否则启动失败，除非显式声明不校验。可选加 `ValidTypes`，防止把 ID 令牌当访问令牌用。
- **S-06 绕过管道的端点上的授权要求不执行，启动检查却照样通过**（复核确认）**已修：ADR-0175**
  - 位置：`ApplicationBuilderExtensions.cs:60-64` 遇到绕过元数据直接放行，不读要求；`EndpointRequirementCheck.cs:47-49` 对这些端点照样校验通过。
  - 场景：`MapXiHanOpenApi().RequireXiHanPermission(…)`、`MapXiHanGrpc()`、`MapXiHanProto()` 或 Hub 上的要求不生效，匿名调用方照样拿到文档或调用操作。`UseXiHan()` 写在 `UseRouting()` 之前时，普通端点同样失效。
  - 修法：带要求的绕过端点在启动时失败；端点带要求但没经过 `UseXiHan()` 判定时，拒绝请求。
- **S-07 HTTP 操作的请求体在认证与限流之前整体缓冲**（复核确认）**已修：ADR-0176**
  - 位置：`ApplicationBuilderExtensions.cs:85-95` 在进管道前绑定载荷；`OperationRequestBinder.cs:224-241` 复制一次、解析成 `JsonDocument` 再改写。框架不设上限，只有 Kestrel 默认的 30 MB；也不检查 Content-Type。
  - 场景：匿名调用方对需要权限的 POST 操作发送接近 30 MB 的 JSON，一个请求就占用数百 MB 内存，并发几十个就能耗尽内存，而且绕过 Resilience 阶段的限流。
  - 修法：载荷绑定挪到 Authorize 之后；加框架级请求体上限（缺省 1～4 MB）并直接从流解析；要求 `application/json`，否则 415。MCP 与 CloudEvents 同样处理。
- **S-08 工作流 Http 活动整读响应，超时没有上限**（审查确认）**已修：ADR-0181**
  - 位置：`Workflow.Abstractions/Activities/WorkflowHttpClient.cs:48,60-62`、`HttpActivity.cs:136-138,283-285`。按 `ResponseContentRead` 读取，缓冲上限是缺省的约 2 GiB，读完才截断到 4 MiB；`TimeoutSeconds` 只检查大于 0。
  - 场景：能发布流程定义的租户用户，把地址指向自己的服务器，返回超大响应或一点点慢慢吐，就能耗尽进程内存，或者长期占着事务、实例锁和数据库连接。
  - 修法：用 `ResponseHeadersRead`，读到 `MaxBodyBytes + 1` 就停；引擎选项设 HTTP 超时上限，校验器与活动两处都检查。
- **S-09 工作流的扇出与变量大小没有上限**（审查确认）**已修：ADR-0182**
  - 位置：`ForEachActivity.cs:95,128`、`WorkflowEngine.cs:948,976-978`、`SetVariableActivity.cs:48`、`ExpressionCompiler.cs:552-556`。
  - 问题：
    - 并行 ForEach 的子实例数不受限，可以嵌套 16 层，每完成一个子实例就把结果数组整个复制一遍。
    - 级联取消只覆盖最近 1000 个子实例。
    - 字符串用 `+` 自我倍增几十次就超过 1 GB。
  - 修法：引擎选项加 ForEach 项数上限、单个变量序列化后的大小上限；`+` 的结果长度设上限；级联取消分页处理全部子实例；结果原地追加。
- **S-10 全局授予无法限定为「仅平台」，角色与用户主体不带租户**（审查确认；两组）**已修：ADR-0197**（授予的范围拆成平台、每个租户与租户专属）
  - 位置：`Security.Database/Grants/GrantRows.cs:26-39`、`PermissionChecker.cs:146-148`。
  - 场景：平台把 `*` 全局授给 `role:admin`。如果某个租户管理员的令牌里也有 `role=admin`，或者用户 ID 与平台用户相同（分库后自增 ID 重复），他就能通过平台操作的权限检查。
  - 修法：把「仅平台」与「所有租户」拆成两个作用域；或者让操作契约声明只限平台，由 Authorize 阶段在有租户时拒绝。
- **S-11 租户 ID 区分大小写，过滤却交给数据库排序规则**（审查确认；两组；数据库行为未实测）**已修：ADR-0196**（租户 ID 只用小写、整串匹配）
  - 位置：EF `EntityFrameworkCoreRepositoryOfT.cs:704`、SqlSugar `SqlSugarRepositoryOfT.cs:791`、`GrantRows.cs:38`。
  - 场景：RFC-0007 规定 `Acme` 与 `acme` 是两个租户，而 SQL Server、MySQL 的默认排序规则不区分大小写。SqlSugar 下 `ACME` 的用户能读写 `acme` 的行；EF Core 的读取会泄露；授予也会串到另一个租户。
  - 修法：建租户时拒绝只有大小写不同的 ID；读回后按序数再筛一遍；文档约定租户列使用区分大小写的排序规则。
- **S-12 MCP 的 HTTP 端点不校验 `Origin`，也接受任意 Content-Type**（审查确认）**已修：ADR-0199**（`AllowedOrigins`、内容类型与请求体上限）
  - 位置：`Protocols.Mcp/McpEndpointRouteBuilderExtensions.cs:37,46-74`。MCP 规范要求服务端校验 `Origin`。
  - 场景：开发者在本机跑着 MCP 服务时访问一个网页，网页用 `text/plain` 发出的简单请求就能调用匿名工具，借助 DNS 重绑定还能读到结果。
  - 修法：按白名单校验 `Origin`，并要求 `application/json`。
- **S-13 CloudEvents 入站未映射的事件类型直接当主题**（审查确认；规范如此，属于设计）**已修：ADR-0200**（未映射的类型缺省拒绝，`AcceptUnmappedTypes` 显式打开）
  - 位置：`CloudEventsProtocolOptions.cs:145-153`。
  - 场景：只被允许投递某一种 webhook 的发送方，能投递到任意有订阅的主题，包括插件订阅的主题，租户与主体也由它自报（ADR-0121 已接受的风险由一个主题扩大到全部主题）。
  - 修法：加「只接受已映射类型」的选项，或者按类型分别授权。
- **S-14 数据库授予缓存在撤销提交之前就清空**（审查确认，未复现）**已修：ADR-0194**（复现确认；租户目录同一做法）
  - 位置：`Security.Database/Grants/PermissionGrantRecordStore.cs:355-356`、`DatabasePermissionGrantStore.cs:105-127`。
  - 场景：被撤销的人在撤销提交之前持续发起调用，可以把旧授予重新写进缓存，保留到 TTL 结束；`CacheTimeToLiveSeconds=0` 时永久保留。
  - 修法：提交之后再清缓存，用代数计数丢弃清缓存之前开始的读取；考虑拒绝 TTL 为 0。
- **S-15 文件系统存储的配额只检查、不预留**（审查确认）**已修：ADR-0183**
  - 位置：`ObjectStorage.FileSystem/FileSystemBlobStore.cs:411-449,528-531`。
  - 问题：并发写入能超额最多 N×`MaxBlobBytes`；对同一个键并发覆盖或删除会少记用量，之后可以一直写到重启。
  - 修法：在锁内预留额度、失败回滚，提交时按磁盘上的实际旧长度计算差值。
- **S-16 文件系统分片暂存没有上限**（审查确认）**已修：ADR-0184**
  - 位置：`FileSystemMultipartUploads.cs:19,329-382`。
  - 问题：暂存不计入配额（ADR-0049 的设计，但违反默认实现要有容量上限的规则）；过期清理只在启动时跑；过期的上传仍能继续传分片。
  - 修法：设暂存字节上限或并发上传数上限，周期清理，拒绝过期的上传。
- **S-17 Kubernetes Lease 客户端的 TLS 校验忽略主机名与 EKU**（审查确认）**已修：ADR-0201**（按集群 CA 校验并核对主机名与 serverAuth）
  - 位置：`Scheduling.Kubernetes/Leases/KubernetesLeaseClient.cs:64-76`。
  - 场景：持有任意一张集群 CA 签发证书的中间人能冒充 API Server，窃取 ServiceAccount 令牌，并伪造租约造成双主。
  - 修法：改用 `CertificateChainPolicy` 的自定义根信任，保留主机名校验。
- **S-18 宿主调用插件时不带认证，回调套接字放在共享临时目录**（审查确认）**已修：ADR-0202**（宿主调插件带会话令牌，回调套接字放进私有目录；Go SDK 侧核对令牌待跟进）
  - 位置：`Plugins.Protocol/Handshake/PluginMetadata.cs`、`PluginCallbackServer.cs:49`。
  - 场景：本机其他用户或同一 Pod 的边车容器直接连插件端口，冒充任意主体和租户调用插件。
  - 规范不符：`handshake.md` §4 要求目录 0700、文件 0600。
  - 修法：宿主每次调用都带令牌，由 SDK 校验；套接字放进私有目录。
- **S-19 Wasm 沙箱的资源限制不完整**（部分推断，修复时逐项复现确认）**已修：ADR-0186**
  - 位置：`WasmPluginRuntime.cs:827`、`WasmInstance.cs:78`。
  - 问题：宿主侧没有超时，epoch 中断不了 WASI 宿主函数；`table.grow` 不受内存上限约束；输出文件与单条日志都没有上限。
  - 修法：宿主侧加超时并弃用超时的实例，设置表元素上限，输出设上限。

## 五、检查后没有问题的

- **认证与授权**：
  - 匿名的判定、缺策略与存储故障时拒绝、`*` 只做精确匹配；ADR-0121 的修法仍然成立。
  - JWT 要求签名与 `exp`，密钥至少 32 字节；OIDC 强制 HTTPS 与签发者，未知 `kid` 的刷新有限频。
  - ApiKey 用常量时间比较；401 质询只列已注册的方案。
  - WebAuthn 按 RFC 顺序核对，挑战常量时间比较，CBOR 用严格模式且有深度上限。
- **租户**：
  - 租户解析先校验文法再查存储，存储不可达不当作不存在。
  - 无租户的调用看不到多租户行；写入沿用存储里的 TenantId。
  - 访问器是作用域服务；幂等键与授予缓存按租户划分；工作流分区检查齐全。
- **入站**：
  - Expose 过滤在各协议都生效。
  - `traceparent` 与 Baggage 键白名单；错误响应不带堆栈与异常文本；JSON 深度 64。
  - 代收发端点的 HMAC 常量时间比较，`BlobKey` 拒绝 `..`。
- **出站与反序列化**：
  - 地址策略在连接时按已解析的地址判定，没有 DNS 重绑定窗口，重定向也覆盖；嵌入的 IPv4 按内层地址判定。
  - 没有自动解压与多态反序列化；正则都带超时或是线性的。
  - 各缓存与队列都有上限。
- **文件、插件与加密**：
  - 路径编码覆盖大写、非 ASCII、`%`、`:`、`\` 与结尾的点，`Within` 兜底。
  - 进程外插件启动时清空环境变量再按白名单继承，会话令牌是安全随机数。
  - Wasm 的指针越界检查正确；密钥类型的 `ToString` 打码。
  - 全库不用 `System.Random`。
