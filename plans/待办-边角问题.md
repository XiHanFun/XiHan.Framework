# XiHan.Framework 边角问题待办

> 来源：第十一轮各路改动与六个 SDK 交回的「要提给用户」；第十轮的条目已在第十一轮做掉或决定不做并删掉，剩下的两条（输出上限用例的根因、只能在 CI 上验证的）挪到「测试与工具」

这份清单记各轮改动顺带发现、没有列成选项的边角问题，每条写问题、位置、可能的修法或待定的取舍与出处。拿它挑下一批要做的；它不是承诺，列在这里不等于要做。做掉或决定不做的条目直接删掉，理由写进提交说明或 ADR。

## 测试与工具

- **性能门禁的相对比较量的多半是当前代码（重要）**：`ci.yml` 把对照提交建在 `$RUNNER_TEMP/base-src`，`framework/scripts/Test-Benchmarks.ps1` 的 `Invoke-Program` 却以仓库根为工作目录运行两边的基准程序；BenchmarkDotNet 的缺省工具链按当前目录找 csproj 重新生成并构建，对照那一轮实际构建、量的是当前提交（kern11 本机实测：生成项目的 ProjectReference 指向当前工作区，删掉的类让对照的生成项目编译失败）。冷启动与内存两项是绝对上限，不受影响。可能的修法：跑对照时工作目录设到对照工作区的根，或改用 in-process 工具链；修好后要核对 ADR-0338 的交替复测（ADR-0341，第十一轮）
- **门禁不覆盖 XGI 调用器的路径**：`PipelineBenchmarks` 只有直通中间件，XGI 一次调用的分配（第十一轮 8424 → 8080 B）是用没提交的临时基准量的；待定：要不要固化进基准（ADR-0341，第十一轮）
- **输出上限用例的根因仍待查**：重试用尽时会记下占句柄的进程，下次偶发时据此查（ADR-0327、0338）
- **只能在 CI 上验证的**：Oracle 夹具的清池再试、探测用例的新超时、性能门禁的交替复测，都只在出事时走到（ADR-0338）

## 内核与协议

- **Observe 之后的中间件仍看到编码之前的结果**：审计（`AuditMiddleware` 在 Observe 阶段 `End`）与熔断，对写不出响应的 XGI 调用照旧记成功（ADR-0341，第十一轮）
- **ASP.NET Core 的幂等回放在管道之后编码**：`UseXiHan()`（`ApplicationBuilderExtensions`）编码回放的响应不在 try 里，写不出不走 Problem Details；回放的响应来自首次写得出的记录，几乎走不到（ADR-0341，第十一轮）
- **只生成快速路径的上下文遇到要回退的深度抛 `InvalidOperationException`**：64 层、最里层是可空值或更深时给不出元数据，不是 `ArgumentException`，XGI 入口照旧 `KERNEL_UNEXPECTED_001`；已写进 remarks（ADR-0342，第十一轮）

## 标识与调度

- **`KubernetesSchedulingOptions.Namespace` 不核对 DNS 标签文法**：孤立的代理项经 `Uri.EscapeDataString` 变成 `%EF%BF%BD`（实测），只会让请求失败，不会让不同节点撞成同一个标识（ADR-0348，第十一轮）

## 对象存储

- **首尾有空格的 ASCII 值在 Amazon S3 上可能丢空白**：Provider 编码写出，Amazon S3 若照文档先解码、存下原值再原样返回，HTTP 会去掉首尾空白；RustFS 不受影响；待定：要不要像 `OBJECTSTORAGE_VALIDATION_009` 那样也拒收（ADR-0343，第十一轮，已写进规范的缺口）
- **纯 ASCII 值里的制表符照旧原样交出**：交出的值含控制字符；拍板是「纯 ASCII 的值不变」（ADR-0343，第十一轮）
- **原样字节的读法依赖 HTTP 客户端按 Latin-1 交出头**：应用自己注册按别的编码读头的 `IAmazonS3` 时，非 ASCII 的原样值报不合规的应答（ADR-0343，第十一轮）
- **009 的代价**：RustFS 原样存取解得开的 encoded-word（如 `=?UTF-8?B?YQ==?=`），以前在 RustFS 上能往返的这类值现在写不进去（ADR-0343，第十一轮）

## 消息

- **代理死信没有重投工具**：升级前写进的空 `subject` 消息进了 `.dlq` 之后只能由运维改正后自行重新发布；待定：要不要提供工具（ADR-0332，第十一轮）
- **空 `subject` 的清理语句只验证了两种数据库**：SQL Server、MySQL、Oracle 的语句按方言文档写好了（scratchpad `round11-followups.md`），没在真实库上跑，文档站只放了 SQLite 与 PostgreSQL；可在 CI 的库上补一个门控用例验证后再写进文档（ADR-0332，第十一轮）

## 插件

- **`error-text-writing.json` 要不要也进 `host` 档**：宿主写错误时同样经这条规则（`PluginErrorMapper.ToProto`），.NET 已经回放；这次只进了 `plugin` 档（ADR-0346，第十一轮）
- **`wasm.md` §6「失败即关闭」只写了 `PLUGINS_UNAVAILABLE_001`**：钩子应答读不出时实际是 `PLUGINS_UNEXPECTED_001`，§2 照实测写了，§6 没改（ADR-0345，第十一轮）
- **ADR-0345 的级别**：照 ADR-0312 的先例定为 MINOR；它拒收以前照收的重复成员与超过 64 层，若算收窄输入应为 MAJOR（`v1.0.0` 之前允许），规范 `CHANGELOG.md` 的级别要跟着改（ADR-0345，第十一轮）
- **`plugin-messages.json` 的「phase 一律小写」**：`plugins.process.failed` 的 `when` 这样写，宿主一侧的 `phase` 可能是操作 ID 或中间件名（以前就有）

## SDK

- **Go 的错误文案替换有两份实现**：SDK 的 `scrubText` 与一致性模块新增的 `rules.WriteErrorText`，向量对两份都独立验证；待定：SDK 是否改用 `rules` 的那份，`framework-sdk-go`（ADR-0349，第十一轮）
- **Go 已关闭之后的 `Unavailable` 都报成已关闭**：宿主恰在同一刻真的回 `Unavailable` 的也算，其他状态码照常映射，`framework-sdk-go`（ADR-0349，第十一轮）
- **Rust 的 `Host` 没有关闭操作**：`invocation.md` §5「已关闭」一项在 Rust 里不出现，运行时收尾之后再回调会怎样没查，`framework-sdk-rust`（ADR-0349，第十一轮）
- **几个 Baggage 键都写不成 UTF-8 时点名哪一个各家不同**：Go、TypeScript 按键名排序取第一个，Java、Python、PHP 取迭代遇到的第一个；规范不作规定（ADR-0347、0349，第十一轮）
