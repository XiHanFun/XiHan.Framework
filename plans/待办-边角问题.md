# XiHan.Framework 边角问题待办

> 日期：2026-11-26 · 基线：`dev` @ `4f0b85259`
> 来源：第四～八轮各路改动交回的「要提给用户」，去重后删掉了已经处理与已经决定的
> 路径前缀省略 `framework/src/XiHan.Framework.`；SDK 的位置写仓库名

这份清单记各轮改动顺带发现、没有列成选项的边角问题，每条写问题、位置、可能的修法或待定的取舍与出处。拿它挑下一批要做的；它不是承诺，列在这里不等于要做。做掉或决定不做的条目直接删掉，理由写进提交说明或 ADR。

## 内核

- **原样写出的 `�` 被当成写不出**：`EncodeResponse` 发现文本里有 `�` 转义时换宽松的编码器再写一遍分辨，不经编码器写出的这个转义（转换器 `WriteRawValue` 原样写的文本、预先编码的 `JsonEncodedText`、缺省编码器下名字里有 U+FFFD 的属性名）第二遍仍在，按写不出结束；框架自己的响应类型没有这样的写法，`Kernel/Operations/OperationDescriptorOfT.cs`（ADR-0318「修订」，第八轮）
- **写出深度与解析器的两处边角**：序列化上下文的 `MaxDepth` 比 64 小时写出照它，比规范严（与读请求的层数相同）；只认原选项的自定义解析器给不出副本选项的元数据，第一次写出即失败，`Kernel/Operations/OperationDescriptor.cs`（ADR-0318「修订」、ADR-0319，第八轮）
- **`EncodeResponse` 抛两种异常**：超过写出的深度上限时是 System.Text.Json 的 `JsonException`，其余写不出是 `ArgumentException`，XGI 入口一样处理，直接调这个 `Stable` 方法的代码要接两种（ADR-0318「修订」，第八轮）
- **Schema 校验编出的请求写成 U+FFFD**：Validate 阶段为 Schema 校验把类型化请求编成 JSON 时照缺省把孤立代理项写成 U+FFFD，不在 RFC-0001「写出与转交」之内，`Kernel/Validation/ValidationMiddleware.cs`（ADR-0318，第七轮）

## 对象存储

- **文件系统里以空格结尾的内容类型写不回**：ADR-0295 之后、ADR-0308 之前写进文件系统存储的这类内容类型照旧读出，原样写回（复制对象时 `new BlobPutOptions { ContentType = head.ContentType }`）抛 `ArgumentException`，`ObjectStorage.FileSystem/FileSystemBlobStore.cs`。可选：读出时去掉结尾的空格、给一次性迁移，或维持现在的升级须知（ADR-0308，第五轮）
- **S3 缺长度照旧兜底**：读取与 `Head` 的应答缺 `Content-Length`、列举的对象缺 `<Size>` 时取 SDK 的值或 0（`entry.Size ?? 0`），`ObjectStorage.S3/S3BlobStore.cs`。修法：照 ADR-0313 当不合规的应答返回 `OBJECTSTORAGE_UNAVAILABLE_001`（ADR-0313，第六轮）
- **S3 列出分片不查重复编号**：10000 片之内应答重复交出同一编号时照收，只有累计超过 10000 片才失败，`S3BlobStore` 列出分片的分页。修法：同一编号出现两次即不合规的应答（ADR-0313，第六轮）
- **S3 条件写入探测拿空 ETag 去完成**：探测里上传分片的应答缺 `ETag` 时照样以空 ETag 发 `CompleteMultipartUpload`，`ObjectStorage.S3/S3ConditionalWriteProbe.cs`。修法：与发起缺上传标识一样按尚未确认处理（ADR-0313，第六轮）
- **写入结果的修改时间是本机时钟**：S3 的 `PutObject` 应答没有修改时间，`BlobMetadata.LastModified` 取本机时钟；如实表示「没有」要把这个 `Stable` 的 `required DateTimeOffset` 改成可空，是 Stable 的破坏，`ObjectStorage.Abstractions/Blobs/BlobMetadata.cs`（ADR-0313，第六轮）
- **S3 解组时头写错原样抛出**：`Last-Modified`、`Content-Length`、`x-amz-mp-parts-count` 写错时 `GetObject`、`HeadObject` 等原样抛 SDK 解组的 `FormatException` / `OverflowException`，不是对象存储的错误，`ObjectStorage.S3/S3BlobStore.cs`。修法：当不合规的应答返回 `OBJECTSTORAGE_UNAVAILABLE_001`（ADR-0317，第七轮）
- **S3 整读的 ETag 不是内容的 MD5**：兼容服务给的 `ETag` 是十六进制却不是内容的 MD5（又没有 SSE 的应答头）时，整读交出的流读到末尾抛 SDK 的 `AmazonClientException`，调用方拿到的不是对象存储的错误，`ObjectStorage.S3/S3BlobStore.cs`（ADR-0317，第七轮）
- **整读认 ETag 解码失败靠调用栈文本**：`IsUndecodableETag` 在 `Exception.StackTrace` 里找 `AmazonS3ResponseHandler.ProcessResponseHandlers(` 一帧，AOT 发布关掉栈追踪支持时认不出，回到原样抛出 SDK 的异常（不比 ADR-0317 之前差），`ObjectStorage.S3/S3BlobStore.cs`（ADR-0317，第七轮）
- **探测留下的上传计数不全**：条件写入探测的发起超时或断连而服务其实建了上传时，同样留下放弃不了的上传、不计入 10 次；次数按实例的生命计，重启应用或重建命名实例后至多再留 10 个，`ObjectStorage.S3/S3ConditionalWriteProbe.cs`（ADR-0317，第七轮）
- **ADR-0313 背景对写入的说法不准**：ADR-0313「背景」说整读与写入时 SDK 都把 `ETag` 当 MD5 核对，ADR-0317 实测 SDK 4.0 写入不核对（只在整读包 `MD5Stream`），ADR-0313 正文没有更正（ADR-0317，第七轮）
- **元数据的值宽松存取**：`BlobPutOptions` 的元数据只拒控制字符，有孤立代理项的值在文件系统的旁路文件与 S3 的 `x-amz-meta-*` 里存成 U+FFFD，读回与写入不同，`ObjectStorage.Abstractions`。修法：与键一样拒收孤立代理项（ADR-0316，第七轮）

## 消息

- **框架事件设不了 `dataschema`**：领域事件、调度与工作流的框架事件发布时都不带 `dataschema`，要的只能自己构造 `MessageEnvelope`。修法：发布选项或事件元数据里给出模式（ADR-0305，第四轮）
- **`dataschema` 的空值两种读法不对称**：结构化 JSON 里 `dataschema` 为空串不合法，binary 的空 `ce-dataschema` 头等于没有（沿用两边原有的读法），RFC-0009「信封」、`protocol/cloudevents.md`、`Protocols.CloudEvents/Inbound/CloudEventsHttpBinding.cs`。待定：统一成哪一种（ADR-0305，第四轮）
- **binary 的数据体不过 JSON 文本检查**：CloudEvents binary 模式的数据原样作请求体，声明为 JSON 的数据有重复成员或超过 64 层照发，structured 会拒绝，`Protocols.CloudEvents/Inbound/CloudEventsHttpBinding.cs`。待定：要不要照 `Encode` 核对（ADR-0318 备选 5，第七轮）
- **binary 入站宽松读百分号序列**：`DecodeHeaderValue` 用 `Uri.UnescapeDataString`，非法的 UTF-8 百分号序列（`%ED%A0%80`、截断的 `%C3`）原样留成百分号文本、不报不合法，`Protocols.CloudEvents/Inbound/CloudEventsHttpBinding.cs`。待定：读成信封不合法还是照旧（ADR-0318，第七轮）

## 插件与协议

- **protobuf 字符串字段宽松编解码**：进程外插件 gRPC 上的 protobuf `string` 字段（如 `Error.details`）由 Google.Protobuf C# 宽松编解码，孤立代理项不报错，`Plugins.OutOfProcess`、`Plugins.Protocol`。不换字符串字段的编解码修不了，代价大（ADR-0312，第五轮）
- **错误细节与 `Result` 的写出不严格**：`PluginJson.SerializeDetails`、`ResultJson.Write` 照 System.Text.Json 的缺省把孤立代理项写成 U+FFFD，不在 RFC-0001「写出与转交」列出的范围内，`Plugins.Protocol/Mapping/PluginJson.cs`、`Kernel/Json/ResultJson.cs`。待定：并不并进「写出与转交」、失败语义（ADR-0315，第六轮）
- **Wasm 下发绑定的孤立代理项没验证**：`Binding.value` 与属性有孤立代理项时 Google.Protobuf 的 JSON 写出器抛 `ArgumentException`，Wasm 运行时的配置步骤接不接得住没验证，`Plugins.Wasm`。修法：补用例，确认按配置失败、退避重试处理（ADR-0315，第六轮）
- **会话令牌按字典查找**：`PluginSessions` 用字典查会话令牌，不是定时比较；令牌高熵，风险低，`Plugins.OutOfProcess/Callbacks/PluginSessions.cs`。可选：按令牌的哈希查找再定时比较（第六轮 misc6）

## SDK

- **Rust 只用 `SystemTime`**：Windows 上表示不了 1601 年之前的时刻，两个平台写出的精度不同，`framework-sdk-rust` 的 `plugin::Envelope.time`。待定：引入 `time` / `chrono`，或公开内部的 `UtcTime`（ADR-0306，第四轮）

- **SDK 没有 `CHANGELOG.md`**：六个 SDK 仓库都没有，变更只记在文档站 `docs/sdks/*` 的「破坏性改动与迁移」。待定：要不要各自补（第四轮 SDK）

- **Java 读文本宽松**：`OperationResponse.payloadText()`、`Envelope.dataText()` 把孤立代理项读成 U+FFFD（展示用），`framework-sdk-java`（第五、六轮）
- **Java 本地目录缺消息键**：`messaging.envelope.invalid` 不在 `PluginMessages` 的本地目录（只收 `plugin-messages.json` 的键），`PluginMessages.catalog()` 渲染不出；交给宿主按键翻译不受影响，`framework-sdk-java`（ADR-0315，第六轮）
- **Python 没有收 `str` 的 `invoke`**：`Host.invoke` 的载荷只收 `bytes`。待定：要不要新增收 `str` 的接口，随之要严格编码（ADR-0312，第五轮）
- **手写的信封时间用例与向量重叠**：第五轮第二批的三个 SDK 原来手写的 `time` 用例与 `plugin/sdk-envelope-times.json` 重叠，都保留着。待定：要不要精简（ADR-0310，第五轮）
- **Go 查不出 `MarshalJSON` 自己换的 U+FFFD**：`encodeResponse` 在 `encoding/json` 写完之后照它的规则再走一遍要写出的字符串，`MarshalJSON` 内部换成 U+FFFD 的看不出，`MarshalText` 与 `IsZero` 被再调一次，`primitives.ID` / `Maybe` 靠未导出的钩子；json/v2 还要 `GOEXPERIMENT=jsonv2`，暂时换不了，`framework-sdk-go` 的 `operation`（ADR-0318，第七轮）
- **Go 缺嵌入层数叠加的单独用例**：没有「`MarshalJSON` 交出 60 层、套在 10 层里」的用例，整段文本的检查已经覆盖，可补，`framework-sdk-go` 的 `operation`（ADR-0319，第八轮）
- **TS 无类型的写出不查深度与重复成员**：错误细节等无类型的线上写出仍用 `writeJson` 的缺省，不查 64 层与重复成员，不在 ADR-0319 的规则内，`framework-sdk-typescript`。待定：要不要跟（ADR-0319，第八轮）
- **Python 整数按 `str()` 写**：`_json._write` 对整数用 `str(value)`，`int` 子类覆写 `__str__` 会写出数字以外的文本（现在由写完之后的检查拦下、本地失败），按值模型应改用 `int.__repr__`，`framework-sdk-python`（ADR-0319，第八轮）
- **Python dataclass 的同名字段静默覆盖**：两个字段的 `json_field` 同名时后者覆盖前者（.NET 建元数据时抛出），写出之后的检查看不到，`framework-sdk-python` 的 `_codec.encode`（ADR-0319，第八轮）

- **临时文件被占用的偶发失败**：全量测试偶发 `%TEMP%` 文件被占用的 `IOException`（`PluginOutputLimitTests.OverlongOutputLine…`、`SqlSugarDataSourceConformanceTests.GetOrAdd…`），重跑通过。修法：查没释放的句柄，用例各用独立的临时目录（第五轮 objstore5）
- **测试项目的识别规则**：`TestProjectNamingTests` 按行首的 `[Fact]` / `[Theory]` 与派生自一致性套件认「含测试」，`_libraries` 只有 `Testing.Workspace`；将来有自定义的测试特性要扩充规则，`framework/test/XiHan.Framework.Architecture.Tests/TestProjectNamingTests.cs`（ADR-0307，第四轮）
- **自定义编码器的分支没有仓库用例**：`EncodeResponse` 遇自定义的 `JavaScriptEncoder` 总再写一遍的分支只在临时目录里用 unsafe 的探针验证过；派生编码器要 unsafe，架构测试 `Sources_DoNotWriteUnsafeCode` 又不许测试写 unsafe，`Kernel/Operations/OperationDescriptorOfT.cs`（ADR-0318「修订」，第八轮）

## 性能

- **.NET 响应写出慢了约 3 倍**：XGI 入口写完之后过 `JsonText.FindProblem`，小响应 0.31 → 0.90 µs（分配 176 → 952 B），约 1 MB 2.2 → 5.3 ms（分配约 2.1 MB），带 U+FFFD 的约 1 MB 6.7 ms；主要花在 `FindProblem` 本身，再降要改成不分配成员名字符串的比较，代码变大、与程序集预算冲突，`Kernel/Operations/OperationDescriptorOfT.cs`（ADR-0318「修订」、ADR-0319，第八轮）
- **程序集预算只剩 512 B**：内核 408064 B 加原语 103424 B 共 511488 B，性能门禁的上限是 512000 B，内核下次增长就会撞线。待定：调预算还是先给内核减体积（ADR-0318「修订」，第八轮）
- **Python 写出慢约 2.3 倍**：`_encode_response` 写完之后再 `parse` 一遍整段文本，`framework-sdk-python`（ADR-0319，第八轮）
- **PHP 大响应慢约 4.5 倍**：`Codec::encode` 写完之后完整过 `JsonText::check`，78 KB 约 3.0 ms；只查深度（`json_decode($text, true, 65)`）约 0.47 ms，代价是误用内部的 `RawJson::checked` 带进来的重复成员拦不住，`framework-sdk-php`（ADR-0319，第八轮）
