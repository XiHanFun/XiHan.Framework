# XiHan.Framework 边角问题待办

> 日期：2026-11-27 · 基线：`dev` @ `dd1644940`
> 来源：第九轮各路改动交回的「要提给用户」，以及第九轮还在进行的 SDK 跟进；第四～八轮的条目已在第九轮做掉或决定维持并删掉
> 路径前缀省略 `framework/src/XiHan.Framework.`；SDK 的位置写仓库名

这份清单记各轮改动顺带发现、没有列成选项的边角问题，每条写问题、位置、可能的修法或待定的取舍与出处。拿它挑下一批要做的；它不是承诺，列在这里不等于要做。做掉或决定不做的条目直接删掉，理由写进提交说明或 ADR。

## 内核与协议

- **类型化请求与原始调用还有两处不对称**：浮点成员是 NaN 时，类型化请求在 Validate 阶段按未处理的异常结束（500），原始调用里同样内容是 `KERNEL_VALIDATION_001`；64 层、最里层有值时，类型化请求同样是 500，原始调用读得进，`Kernel/Validation/ValidationMiddleware.cs`（ADR-0320 备选 13、15，第九轮）
- **写不出响应时不记日志**：XGI 入口与幂等记录写不出响应都只在 Span 与指标里记失败，没有日志，排查只能靠错误码；要日志得另定一条（XGI 入口在内核，体积紧）（ADR-0324，第九轮）
- **MCP 的一行不设长度上限**：stdio 按字节分行，一行的长度照旧不设上限，`Protocols.Mcp/Transports/McpStdioTransport.cs`（ADR-0320，第九轮）
- **MCP 的 Streamable HTTP 入口没有核对**：正文不过 JSON 文本的共同检查，有非法 UTF-8 时怎样处理没有实测，`Protocols.Mcp`（ADR-0320，第九轮）

## 标识

- **同类的标识还没拒收孤立代理项**：插件元数据里的幂等键（经 protobuf 宽松写出）、工作流的 `StarterId`、`Workflow.Database` 的 `HolderId`、OTel 的 `ServiceName`；`SetAuditAction` 只拒空白；`ResourceName` 的 ID 段仍收控制字符；ADR-0316 的 `BlobKey` / `CacheKey` 私有判定没有换成 `UnicodeText`（ADR-0321，第九轮）
- **代码登记的作业有孤立代理项时同步卡住**：每个周期记日志并重试，排在后面的代码作业也一直同步不进去。待定：改成启动即失败，`Scheduling`（ADR-0321，第九轮）

## 对象存储

- **.NET 的 S3 写不出非 ASCII 的元数据值**：`SocketsHttpHandler` 缺省拒收非 ASCII 的请求头，写入以 `HttpRequestException` 失败、返回 `OBJECTSTORAGE_UNAVAILABLE_001`；规范与向量把 `2026 年度报告` 这类值算合法，文件系统存储也照收。SDK 的开关 `AWSConfigsS3.EnableUnicodeEncodingForObjectMetadata` 是进程级的全局设置，又按 UTF-16 码元编码、会拆坏成对的代理项。待定：修不修、怎么修（例如 Provider 自己按 RFC 2047 编码），`ObjectStorage.S3`（ADR-0322，第九轮实测）
- **批量删除的逐项报错在真实 SDK 上走不到**：`DeleteObjects` 的应答有错误项时 SDK 抛 `DeleteObjectsException`（静默模式也一样），Provider 把整批报成存储故障；ADR-0313 按 `DeleteErrors` 逐项报告的分支只有内存替身走得到，`ObjectStorage.S3/S3BlobStore.cs`（ADR-0322，第九轮实测）
- **写坏的 XML 原样抛出**：`ListObjectsV2`、`ListParts`、`DeleteObjects` 等的响应体不是良构 XML 时 SDK 抛 `XmlException`，不是对象存储的错误，`S3BlobStore`（ADR-0322，第九轮实测）
- **列出分片的编号不比起点大**：交出的编号不比请求的起点大、但也不重复时没有判定，`S3BlobStore` 列出分片的分页（ADR-0322，第九轮）
- **读够长度后释放也抛出**：调用方读够长度、没读到末尾就释放时，SDK 在释放时才核对 `ETag`，这时也抛携带 `OBJECTSTORAGE_UNAVAILABLE_001` 的 `FrameworkException`；只认 `IOException` 的调用方接不住。待定：释放时吞掉还是照抛，`ObjectStorage.S3`（ADR-0322，第九轮）
- **两处成功应答没接解析失败**：`AbortMultipartUpload` 与 `PutBucket` 的成功应答现在没有 SDK 按类型读的值，没加解析失败的捕获；SDK 升级后若加了，`FormatException` 会再漏出来（ADR-0322，第九轮）

## 消息

- **出站头值不编空格与双引号**：`EncodeHeaderValue` 不百分号编码空格与双引号，CloudEvents 1.0.2 §3.1.3.2 要求这两个也编码；现有测试锁定了「空格原样」，`Protocols.CloudEvents`（ADR-0323，第九轮）
- **入站不解开双引号括起的头值**：CloudEvents 要求接收方支持，`Protocols.CloudEvents/Inbound/CloudEventsHttpBinding.cs`（ADR-0323，第九轮）
- **`ce-subject` 与 `ce-time` 的空头**：binary 的空头仍等于没有；structured 里 `"subject": ""` 读成空串、`"time": ""` 不合法，读法不对称（ADR-0323，第九轮）
- **数据模式只能在代码里登记**：`AddMessageDataSchema` 不从配置读（`type` 带点号，写不进环境变量的配置键）（ADR-0323，第九轮）

## 工作流

- **锁超时的文案写成实例**：`workflow.lock.timeout` 写「工作流实例 '{id}'」，锁键早就也是定义 ID 与重用策略的派生键，现在目录也用。修法：10 个区域改成不限于实例的说法（ADR-0326，第九轮）
- **容器之间比较还取两遍文本**：两个容器 `==` 深比较、`contains` 的元素与要找的值都是容器时，里面的字符串仍取两遍文本，`Workflow.Abstractions` 的表达式求值（ADR-0326，第九轮）

## 插件

- **Wasm 启动阶段的失败不退避重试**：Wasm 宿主启动阶段的失败（含配置失败）不在后台重试，下一次调用时按需再试（ADR-0260 第 4 条）；进程外插件按退避重试，只有 Wasm 运行期崩溃之后的重建按退避。待定：统一成退避（改法小：`WasmPluginRuntime` 加 `ScheduleRestart`，`AttachAsync` / `LoadAsync` 启动失败后调用，`plugin/wasm.md` §5 写明）；发现阶段的握手失败也不重试（ADR-0067），可一并定（ADR-0325，第九轮）

## SDK

- **SDK 没有 `CHANGELOG.md`**：六个 SDK 仓库都没有，变更只记在文档站 `docs/sdks/*` 的「破坏性改动与迁移」。待定：要不要各自补（第四轮 SDK）
- **TS 已关闭客户端的先后**：`Host.invoke` 把客户端已关闭的核对挪到载荷编码之后；`Host.publish` 已关闭时编不成的那项仍报编码错误，全部编不成时报编码错误；`plugin/invocation.md` §5 没写这几种先后，`framework-sdk-typescript` 的 `Host`。待定：写进规范还是对齐别的 SDK（ADR-0312、ADR-0315，第五、六轮）
- **Java 本地目录缺消息键**：`messaging.envelope.invalid` 不在 `PluginMessages` 的本地目录（只收 `plugin-messages.json` 的键），`PluginMessages.catalog()` 渲染不出；交给宿主按键翻译不受影响，`framework-sdk-java`（ADR-0315，第六轮）
- **Python 没有收 `str` 的 `invoke`**：`Host.invoke` 的载荷只收 `bytes`。待定：要不要新增收 `str` 的接口，随之要严格编码（ADR-0312，第五轮）
- **手写的信封时间用例与向量重叠**：第五轮第二批的三个 SDK 原来手写的 `time` 用例与 `plugin/sdk-envelope-times.json` 重叠，都保留着。待定：要不要精简（ADR-0310，第五轮）
- **Go 缺嵌入层数叠加的单独用例**：没有「`MarshalJSON` 交出 60 层、套在 10 层里」的用例，整段文本的检查已经覆盖，可补，`framework-sdk-go` 的 `operation`（ADR-0319，第八轮）
- **TS 无类型的写出不查深度与重复成员**：错误细节等无类型的线上写出仍用 `writeJson` 的缺省，不查 64 层与重复成员，不在 ADR-0319 的规则内，`framework-sdk-typescript`。待定：要不要跟（ADR-0319，第八轮）
- **Python 整数按 `str()` 写**：`_json._write` 对整数用 `str(value)`，`int` 子类覆写 `__str__` 会写出数字以外的文本（现在由写完之后的检查拦下、本地失败），按值模型应改用 `int.__repr__`，`framework-sdk-python`（ADR-0319，第八轮）
- **Python dataclass 的同名字段静默覆盖**：两个字段的 `json_field` 同名时后者覆盖前者（.NET 建元数据时抛出），写出之后的检查看不到，`framework-sdk-python` 的 `_codec.encode`（ADR-0319，第八轮）

## 测试与工具

- **输出上限用例的根因是推断**：`PluginOutputLimitTests` 删临时目录时改成有界重试，根因（进程树里别的进程异步终止、还占着句柄）是推断的，本机没复现；若仍偶发，要在失败时记下占着句柄的进程再查（ADR-0327，第九轮）
- **新增的门控用例第一次上 CI**：S3（RustFS）28 条本机实测过；`Workflow.Database.Tests` 新增的 161 条（SQL Server、MySQL、Oracle 各 53 条）本机没跑过，Oracle 拆成三份的时长按每条约 33 秒推算，`test-shard` 的 `filter` / `part` 输入第一次用（ADR-0326、ADR-0327，第九轮）

## 性能

- **程序集预算几乎用尽**：内核 408064 B 加原语 103424 B 共 511488 B（上限 512000 B）；内核 `.text` 只剩约 32 B、原语约 88 B 余量，内核再长就撞线。注意在工作区里量会更大（PDB 路径写进 `.text`），以主检出或 CI（`ContinuousIntegrationBuild` 映射路径）为准（ADR-0318「修订」，第八、九轮）
