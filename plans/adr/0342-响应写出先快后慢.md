# ADR-0342 响应写出先快后慢

## 状态

已采纳（只改内核：`OperationDescriptor` 新增 internal 的 `Write`，`OperationDescriptor<TOperation, TRequest, TResponse>.EncodeResponse` 与 `ValidationMiddleware` 为 Schema 校验编码请求都经它；新增基准 `OperationBenchmarks.EncodeResponse`。规范、公开 API、错误码、消息键、配置键与向量不变）。

## 日期

2026-11-27

## 背景

ADR-0329 为让 64 层、最里层是可空值的响应照写，写出用的元数据向序列化上下文的解析器为改了深度上限的选项副本（`OperationDescriptor.WriteOptions`）重新取，副本设了缺省的编码器，不走源生成的快速路径（ADR-0329 决策 2 与备选 8）；「只在快速路径失败时换按元数据的写法再写一遍」当时否决（ADR-0329 备选 9：多一条重试路径，接住的异常里分不清是深度还是转换器自己抛出的）。留下两件事：

- 代价没量。
- 只生成快速路径（`GenerationMode = Serialization`）的上下文给不出按元数据的写法，第一次写出即失败（`InvalidOperationException`：解析器没有给出属性元数据），以前能写；为 Schema 校验编码类型化请求同样如此。

仓库所有者拍板「先快后慢」：先走快速路径（原选项、原 `JsonTypeInfo`），快速路径写不出（它抛出的那几种异常，以实测为准）时再按元数据写一遍；只生成快速路径的上下文恢复能写；改前改后各量一次写进 ADR。

### 快速路径在哪些输入上写不出（实测）

六种上下文（选项与生成时一致的源生成上下文；同一上下文把 `MaxDepth` 设成 8、设成 128；只生成元数据；设了 `UnsafeRelaxedJsonEscaping` 编码器；只生成快速路径），每种 18 个输入（一般的响应、NaN、孤立代理项、本来就是 U+FFFD 的字符，与从根算起 2 层到 201 层之间 14 种层数的对象链，最里层是 `int?`），各按原选项写一遍、按 ADR-0329 的副本写一遍：

| 输入（层数从响应的根算起） | 原选项（快速路径） | 按副本（元数据） |
| --- | --- | --- |
| 64 层、最里层是可空值 | `JsonException`（里面再调序列化器时按原选项的上限 64，消息是「A possible object cycle was detected」，`StrictJson` 包成 `ArgumentException`） | 照写 |
| 65 层及更深 | `InvalidOperationException`（写出器：「CurrentDepth (64) is equal to or larger than the maximum allowed depth of 64」） | `ArgumentException`，`InnerException` 是 `JsonException` |
| `MaxDepth = 8`：8 层、最里层是可空值 / 9 层及更深 | `JsonException` / `InvalidOperationException` | 照写 / `ArgumentException`（`JsonException`） |
| `MaxDepth = 128`：65 层到上限（实测 65～101 层） | 照写，再由文本检查以 `ArgumentException` 拒绝，没有 `InnerException` | `ArgumentException`，`InnerException` 是 `JsonException` |
| 只生成元数据、自定义编码器：64 层、最里层是可空值 / 更深 | `JsonException` / `JsonException` | 照写 / `ArgumentException`（`JsonException`） |
| NaN、孤立代理项、文本检查不过 | 与按副本相同的 `ArgumentException` | 同左 |
| 其余（写得出的） | 写出的字节与按副本相同 | — |
| 只生成快速路径的上下文 | 与上面第一种上下文相同 | 一律 `InvalidOperationException`（给不出元数据） |

深度上限不超过 64 的上下文里，原选项那一遍写得出的，按副本也写得出、字节相同；写不出而按副本写得出、或两边抛的异常不同的，只有上表第一、二、三、五行，原选项那一遍抛的都是 `JsonException`（包成 `ArgumentException`）或 `InvalidOperationException`。深度上限大于 64 的（第四行）原选项那一遍更宽，结果的 `InnerException` 与按副本的不同。

## 备选

1. **先照原选项的元数据写，只在 `InvalidOperationException` 与内层是 `JsonException` 的 `ArgumentException` 上按副本再写一遍，结果以这一遍为准**：采纳。
   - `ArgumentException { InnerException: JsonException }` 是 `StrictJson.Serialize` 包过的序列化器的 `JsonException`；没有内层的 `ArgumentException`（NaN、被换成 U+FFFD 的字符、文本检查不过）两遍结果相同，不再写一遍。
   - 转换器自己抛出的这两种异常在第二遍里照样抛出，结果不变，多执行一次转换器；ADR-0329 备选 9 担心的「分不清」因此不影响结果。`NotSupportedException`、框架异常这类编程错误不回退。
   - 实测上面 5 种不是只生成快速路径的上下文、各 18 个输入共 90 种组合，改后的结果（写出的字节，或异常的类型、内层的类型与消息）与 ADR-0329 的写法逐一相同。
2. **原选项的深度上限大于 64 时直接按副本写，不先走快速路径**：采纳。照原选项会写到它的上限才由文本检查拒绝，`InnerException` 由 `JsonException` 变成没有（上表第四行）；直接按副本写与 ADR-0329 相同。这样的上下文本来少见。
3. **只在 `JsonException` 上回退**：否决。65 层以上快速路径抛 `InvalidOperationException`，`EncodeResponse`「写不出只抛 `ArgumentException`」（ADR-0320）就不成立了。
4. **按异常消息分辨深度**：否决。消息随运行时版本与区域变化。
5. **任何异常都回退**：否决。`NotSupportedException`（不支持的类型）与框架异常是编程错误（ADR-0320 备选 23），再写一遍只是多做一次。
6. **把写出器的深度上限放大，让快速路径不抛 `InvalidOperationException`**：否决。快速路径不核对深度，会把再深的文本写完才由文本检查拒绝，`InnerException` 跟着变，深的输入多写很多。
7. **只生成快速路径的上下文要再写一遍时把异常换成 `ArgumentException`**：不做。给不出元数据是上下文的生成方式不支持（`InvalidOperationException`，ADR-0320 备选 23 的「编程错误」），经 XGI 入口的结果照旧是 `KERNEL_UNEXPECTED_001`；记进 `EncodeResponse` 的 XML 文档。
8. **为 Schema 校验编码类型化请求也先快后慢**：采纳。与写出响应共用同一份写出用的选项（ADR-0329 备选 10），同一个只生成快速路径的问题；`Validate` 阶段编不成只接 `ArgumentException`，照旧。
9. **缓存副本的 `JsonTypeInfo`（以前的 `_writeInfo`）**：删掉。只在回退时用，副本选项自己缓存 `GetTypeInfo` 的结果。

## 决策

1. `OperationDescriptor.Write(value, info, checkText)`（internal）：原选项的 `MaxDepth` 大于 64 时按 `WriteOptions` 的副本写；否则先 `StrictJson.Serialize(value, info, checkText)`，接住 `InvalidOperationException` 与 `ArgumentException { InnerException: JsonException }` 时按副本再写一遍。
2. `EncodeResponse` 用 `Write(response, ResponseInfo, checkText: true)`，删掉 `_writeInfo`；`ValidationMiddleware` 用 `Write(request, RequestInfo, checkText: false)`。
3. `EncodeResponse` 与 `WriteOptions` 的 XML 文档、内核 README 同步；规范没写到快速路径，不改。
4. 基准：`framework/benchmarks` 里没有写响应的基准，新增 `OperationBenchmarks.EncodeResponse`（选项与生成时一致的源生成上下文，响应有文本、金额、可空值与三个元素的列表），不进 `budgets.json`，性能门禁照相对回退比较它。

## 理由

- 写出的结果与 ADR-0329 相同，只是先走快的那条：多数应用的上下文选项与生成时一致，正常的响应不必为极少见的 64 层付出按元数据写的代价。
- 只生成快速路径的上下文是 System.Text.Json 只为写出的生成方式，普通的响应恢复能写；只在那几种深度上给不出。
- 回退只认实测到的两种异常，其余写不出照旧只写一遍。

## 影响

- **公开 API**：不变。
- **对已有部署与代码的行为变化**：
  - 只生成快速路径（`GenerationMode = Serialization`）的上下文用作响应或带 Schema 的请求时照常写出；ADR-0329 之后第一次写出即失败（`InvalidOperationException`，经 XGI 入口是 `KERNEL_UNEXPECTED_001`）。要再写一遍的输入（64 层、最里层是可空值，或超过上下文的深度上限）仍给不出元数据，抛 `InvalidOperationException`。
  - 只认原选项的自定义解析器只在要再写一遍时才给不出元数据（ADR-0329 之后第一次写出即失败）。
  - 其余写出的字节、写不出时的异常（类型、`InnerException`）与读请求的层数不变。
- **性能**（本机，BenchmarkDotNet 缺省作业，`OperationBenchmarks.EncodeResponse`；三份代码各在自己的工作区里构建、按「改前、改后、0329 之前、0329 之前、改后、改前」交替跑，第 3 次时机器忙、波动大）：

  | 代码 | 每次分配 | 平均耗时（两次） |
  | --- | --- | --- |
  | ADR-0329 之前（dev @ f487ad494，副本没设编码器、走快速路径） | 936 B | 820.0 ns（标准差 215 ns）/ 526.6 ns |
  | 改前（ADR-0329，dev @ 42c8f0ae1，按元数据写） | 1248 B | 614.5 / 590.2 ns |
  | 改后 | 936 B | 578.9 / 502.0 ns |

  分配是确定的：按元数据写比快速路径多 312 B（同一进程里只量 `JsonSerializer.SerializeToUtf8Bytes`：快速路径 176 B、按元数据 488 B），其余 760 B 是写完之后过 `JsonText.FindProblem` 的。耗时受同一台机器上别的构建影响，成对比较改后比改前快约一成，与 ADR-0329 之前相当；机器空一些时改后另量过三次，482.6～497.7 ns，改前一次 544.1 ns。
  经 XGI 入口一次调用的分配见 ADR-0341（8424 → 8080 B）。
- **体积**：本 ADR 与 ADR-0341 合计（工作区 Release 构建）：Primitives 103424 → 103424 字节；Kernel 364544 → 365056 字节（`.text` 361792 → 362464 字节，多 672 字节，按 512 字节一档多一档），合计多 512 字节。主检出与工作区的基线相同（364544），折成主检出口径合计 467968 → 468480 字节，距预算 43520 字节。
- **测试**：
  - `ResponseTextCheckTests`：只生成快速路径的上下文写出的字节与 System.Text.Json 写出的相同，孤立代理项、NaN 只抛 `ArgumentException`，64 层、最里层是可空值与 100 层抛 `InvalidOperationException`（改之前第一条断言就失败）；`MaxDepth = 8`、走快速路径的上下文 8 层照写、9 层只抛 `ArgumentException`（`InnerException` 是 `JsonException`）。既有的 64 层、65 层、100 层、字节相同、`MaxDepth` 128 与 8 的用例照过。
  - `ValidationMiddlewareTests`：只生成快速路径的请求上下文，带 Schema 的类型化调用照常执行，NaN 是 `KERNEL_VALIDATION_001`、`reason` 为 `$`（改之前按未处理的异常结束）。既有的 NaN、64 / 65 层用例照过。
