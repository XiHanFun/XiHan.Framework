# ADR-0163 分片句柄的覆盖标志必填，文件系统存储只经异步工厂创建

## 状态

已采纳（RFC-0012）。

## 日期

2026-11-11

## 背景

API 审查第三节「对象存储」一组：

- **分片句柄缺省覆盖**：`BlobMultipartUpload(container, key, uploadId, bool overwrite = true)`。
  - 应用常把上传标识存下来，完成时重建句柄；S3 实现在完成时按句柄上的值决定是否条件写入（`If-None-Match: *`）。
  - 重建时漏传第四个参数，以 `Overwrite = false` 开始的上传就静默变成覆盖，可能盖掉别人刚写入的对象。
  - 框架自己的托管上传端点重建句柄时也没传，文档示例也一样。
- **文件系统存储能构造出半初始化的对象**：
  - `FileSystemBlobStore` 的构造是公开的，配额已用量要另调 `InitializeAsync` 扫描目录才得到。
  - 不调用时已用量从零算起，超额的写入照样放过，过期的分片上传也不清理。
  - 一致性套件的宿主就是这样直接构造的。

## 决策

1. **覆盖标志必填**：
   - `BlobMultipartUpload` 的构造只收身份（容器、键、上传标识），`Overwrite` 改为 `required` 初始化成员，漏写就编译不过。
   - 两个 Provider 开始上传时按 `BlobPutOptions.Overwrite` 填写。
   - 托管端点上传分片时写明 `Overwrite = false`：分片不看这个标志，只在完成时生效。
2. **文件系统存储只经异步工厂创建**：
   - 构造与 `InitializeAsync` 改为 `internal`。
   - 新增 `FileSystemBlobStore.CreateAsync(options, clock, loggerFactory, ct)`：建根目录、扫描已用量、清掉过期的分片上传后才交出。
   - 特性与 Provider 在包内构造后紧接着初始化，行为不变。
3. **一致性套件的被测存储异步创建**：`BlobStoreConformance.CreateStore()` 改为 `CreateStoreAsync()`，返回 `ValueTask<IBlobStore>`，宿主可以先初始化再交出。

## 影响

- 源码迁移：
  - `new BlobMultipartUpload(container, key, uploadId)` → `new BlobMultipartUpload(container, key, uploadId) { Overwrite = … }`，值与开始上传时一致；原来传了第四个参数的改成初始化器。
  - `new FileSystemBlobStore(options, clock, loggers)` 加 `InitializeAsync` → `await FileSystemBlobStore.CreateAsync(options, clock, loggers, ct)`。
  - 继承 `BlobStoreConformance` 的 Provider 测试把 `CreateStore()` 改成 `CreateStoreAsync()`。
- 改动的类型都是 `Preview`；GA 前修改，不需要登记豁免（ADR-0131）。
