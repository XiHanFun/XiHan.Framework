# ADR-0326 表达式只取一次文本与目录改写定义取锁

## 状态

已采纳（规范 RFC-0021「目录」「锁」「默认实现与 Provider」的查询列回填、「一致性」与状态行已改；本仓库 `Workflow.Abstractions`、`Workflow.Database` 与 `Workflow.Conformance` 实现；错误码、消息键与配置键不变）。

## 日期

2026-11-27

## 背景

待办「边角问题」里工作流的四条，仓库所有者已拍板：

1. **表达式还有两处取两遍文本**（第六轮 misc6）。`7eed229d0` 让读字符串的运算把量长度时取出的文本接着交给运算，还剩两处：
   - 数组与对象作文本实参（`toString`、`upper` / `lower` / `trim`、拼接、`contains` / `startsWith` / `endsWith` 的非数组实参、模板占位）：`ExpressionRun.ReadText` 先 `Read` 量规模，再 `WorkflowValueText.Of` 写文本，容器里每个字符串的文本各取一遍。
   - `contains(数组, x)`：`Read(array)` 量元素时取一遍，`AreEqual` 比较时 `TryDecimal` 与 `AsString` 又各取一遍。实测从 JSON 文本读来的一个 1048576 码元的元素，一次 `contains` 分配 6291848 字节，是解码一次的三倍。
   - 由 JSON 文本读来的字符串每取一次文本都要解码全文、分配一个新的字符串。
2. **回填与定义编辑之间有窗口**（ADR-0304 备选 12）。目录在调用方的事务里整行写定义、不取锁；`DatabaseWorkflowBackfill` 在一个短事务里重读定义行再写。调用方写了定义、还没提交时，回填读到的是提交之前的旧行，算出查询列后写回：PostgreSQL、SQL Server、MySQL 与 Oracle 上它的写入等调用方的行锁，调用方提交后照写，把编辑过的文档换回旧的（停用了的定义又成了已发布，而它的定时启动书签已经删了）；SQLite 上它等单写者，忙等超时后整个分区失败。规范与文档只能写「宜在没有人编辑定义时运行」。
3. **引擎与任务套件只在 PostgreSQL 上有门控类**（第五轮 workflow4）。存储与回填四种库都有，引擎（42 条）与任务（9 条）一致性套件在 SQL Server、MySQL 与 Oracle 上没有。
4. **`Workflow.Database` 没有架构版本**（ADR-0304）：所有者定了不引入。

## 备选

表达式（第 1 条）：

1. **数组与对象边写文本边记读取量，一遍走完**：采纳。`WorkflowValueText` 写容器时把每个值、成员名、字符串（写进文本的那一份）与数字逐个交给 `IValueTextTally`，求值的 `ExpressionRun` 实现它、每一笔照 RFC-0021「长度与上限」记；累计超过上限即在那里抛出，写到一半停下。写文本的只有 `WorkflowValueText` 一处，量的规则只在 `ExpressionRun` 一处。
2. **先写文本，再从文本推读取量**：否决。读取量是每个值 64 加上字符串、数字写法与成员名的长度，写出的文本有转义、规范化的数字与排过序的成员，推不回去；几十万个值的容器也要先写完才知道超没超。
3. **在 `ExpressionRun` 里另写一份容器的遍历**：否决。容器的写法（成员按序数排序、超过 64 层写 `null`、字符串转义）就有了两份，迟早不一致。
4. **`contains` 量元素时交回比较用的元素**（`ReadItems`）：采纳。是字符串的元素取出文本、量长度，再照 `7eed229d0` 的 `Materialize` 换成已取出的文本交给比较，读取量与 `Read` 相同。代价是一个与数组等长的引用数组。
5. **比较与量元素放在同一遍**：否决。读取量的次序是先读数组、再按元素个数读要找的值，都在比较之前记；同一遍比较就要先取出要找的值的文本，读与记的次序拆开。
6. **由自定义转换器构造的字符串也换成取出的文本**：否决，理由同 `7eed229d0`：换成字符串之后 `TryDecimal` 把它当数字文本读，比较的结果会变；这类值文本很短。
7. **两个容器深比较时里面的字符串**（`==` 两侧都是容器、`contains` 的元素与要找的值都是容器）：不在这次范围。深比较按结构走，先比个数，量的时候不知道会比哪些成员。

目录与回填（第 2 条）：

8. **目录改写已有的定义时经执行范围取定义 ID 的锁，持有到作用域结束**：采纳。锁就是引擎用的那把（`IWorkflowInstanceLock`，定时启动本来就以定义 ID 为键），执行范围（`WorkflowScope`）把它持有到调用方事务提交或回滚之后，与实例锁的「锁与事务的先后」相同。回填拿到锁时读到的是已经提交的定义；定义级定时书签的恢复也与目录互斥，停用与恢复不再交错。内存实现同样取锁，规则在抽象包里。
9. **在 `Workflow.Database` 的定义存储里取锁**：否决。存储在调用方的工作单元里写，锁要持有到提交之后才关得上窗口，只有执行范围知道作用域什么时候结束；存储自己再持有一份锁，与执行范围持有的同一个键（定义级定时书签的恢复）在同一个作用域里互不认得，不可重入的锁会等自己到超时。
10. **定义行加并发戳**：否决。存储契约是「不做乐观并发（实例锁串行化写入）」；加列要改应用管理的表结构，回填正是为这类升级而设。
11. **先取锁再读**：否决。调用方给的 ID 可能看不到（不存在、在别的分区、空白或超过锁键的 128 个字符），为它们取锁要么抛出、要么等到超时，结果从「不存在」变成「等锁超时」。采纳的做法是先读一次，只为看得到的定义取锁，再在锁内重读、按重读的结果核对与写回。
12. **批量操作按 ID 的序数次序逐个取，同一 ID 只取一次**：采纳。两个批量操作不会交叉等对方；拿不到的那一项以取锁的错误失败（等待超时是 `WORKFLOW_TIMEOUT_001`），别的项照常，与批量的逐项结果一致。
13. **`CreateAsync` 与 `NewVersionAsync` 也取锁**：否决。它们写的是新 ID，提交之前别人看不到。
14. **回填的定义行与定义级定时书签各取各的**：否决。两者归属同一个定义 ID，合成一个键在一把锁、一个事务里重读再改写（与实例行和它的书签相同），拿不到计入 `Busy`。
15. **改 `workflow.lock.timeout` 的文案**（现在写「工作流实例」）：不在这次范围。定时启动的定义 ID 与重用策略的派生键早就用这条消息。

门控类与架构版本（第 3、4 条）：

16. **照 PostgreSQL 的写法给 SQL Server、MySQL 与 Oracle 补引擎与任务的门控类**：采纳。夹具（建库、建表、清理、Oracle 的 180 秒启动期限）都在已有的 `IGatedDatabase` 实现里，门控类只换夹具；Oracle 的两个类进 `OracleGroup`，不与别的用例并行。
17. **Oracle 一个类复用一个用户、用例之间清表**：不做。要重写夹具，本机没有 Oracle 验证不了；时长的估算见「影响」。
18. **引入架构版本与迁移**：否决，照所有者的决定，理由同 ADR-0304 备选 2。

规范的档位：

19. **MAJOR（`v1.0.0` 之前允许）**：采纳。RFC-0021 已经写明定义的写入不加锁、回填「宜在没有人编辑定义时运行」，现在改成取锁；目录的五个操作多了一种逐项失败（等锁超时）。引擎套件新增一条用例。

## 决策

1. **表达式**（`Workflow.Abstractions`，RFC-0021 不变）：
   - 新增内部接口 `Values/IValueTextTally`（`Value`、`Name`、`Text`、`Number`）；`WorkflowValueText` 新增 `Json<TTally>(node, tally)`，`Of` 以不记的结构体调同一份写法，文本不变。
   - `ExpressionRun` 实现 `IValueTextTally`（每一笔 `Add`），`ReadText` 的容器分支改成 `WorkflowValueText.Json(node, this)`；新增 `ReadItems(array)`，`contains(数组, x)` 用它交回的元素比较。
   - 结果与工作量都不变：`expression-limits.json` 的 50 条读取量向量照旧通过。超过上限时报告的工作量可能比以前少一步（64）：以前记上成员名之后要再记上那个成员的一步才比较，现在每记一笔就比较；向量与 RFC 只要求超过上限。
2. **目录**（`WorkflowDefinitionCatalog`）：`UpdateAsync`、`PublishAsync`、`DisableAsync`、`ArchiveAsync`、`DeleteAsync` 先读出调用方分区里看得到的定义，按 ID 的序数次序逐个经执行范围取锁（同一 ID 一次），在锁内重读，按重读的结果核对、写回；拿不到锁的项以取锁的错误失败，看不到的项照旧 `WORKFLOW_NOTFOUND_001`。锁持有到作用域结束，同一作用域里之后的操作复用。
3. **回填**（`PartitionBackfill`）：去掉不加锁的定义改写；定义的批扫描出的过时定义与定义级定时书签的归属合成键，逐个在定义 ID 的锁内（与实例相同的 `RewriteOwnersAsync`）重读再改写定义行与它的书签，拿不到计入 `Busy`。`DatabaseWorkflowBackfill`、`DatabaseWorkflowBackfillReport` 的 XML 文档与包 README 不再要求没有人编辑定义时运行。
4. **规范**：RFC-0021「目录」写明改写已有定义的操作取定义 ID 的锁、持有到作用域结束、拿不到的项与看不到的项各怎样；「锁」的锁键与持有者加上目录；查询列回填的「与引擎互斥」改成定义行同样在锁内改写、可以在有人编辑定义时运行；「一致性」加一条引擎用例；状态行与对应 ADR。
5. **测试**：
   - `ExpressionBudgetTests`：容器作文本实参时每个字符串只取一次文本（以自定义转换器构造、每写一次 JSON 记一次数的值核对，九种运算与模板占位）；`contains` 在从 JSON 读来的数组里找时一个百万码元的元素只解码一次（按当前线程分配的字节核对）；从 JSON 读来与进程内构造的容器作文本实参，结果与工作量相同。先红后绿。
   - 引擎套件用例 43（`Transaction_CatalogEdits_HoldTheDefinitionLockUntilTheInvocationEnds_AndReleaseOnRollback`）：调用里改草稿，别的调用在它结束之前发布不了（`WORKFLOW_TIMEOUT_001`），同一调用里再改复用锁，回滚后照常发布；内存、SQLite（SqlSugar 与 EF Core，含发件箱与调度的宿主）与四种门控库都跑。
   - `InMemoryWorkflowTests`：别人持有定义的锁时，改写、发布、删除与归档的那一项等锁超时，同一批里别的项与看不到的 ID 照旧。
   - `DatabaseWorkflowBackfillTests`（SQLite）：持有一个定义的锁时它跳过、`Busy` 是 1，释放后补上；回填与同时进行的定义编辑：编辑的调用提交之前回填跳过这份定义，提交之后它仍是编辑后的样子（`BackfillScenario.EditWhileBackfillingAsync`，`ServerWorkflowBackfillTests` 在四种门控库上跑同一份）。先红后绿：以前前者改写了这份定义、`Busy` 是 0，后者在 SQLite 上忙等 5 秒后分区以 `WORKFLOW_UNAVAILABLE_001` 失败。
   - 门控类：`SqlServerWorkflowEngineConformanceTests`、`SqlServerWorkflowTaskConformanceTests`、`MySqlWorkflowEngineConformanceTests`、`MySqlWorkflowTaskConformanceTests`、`OracleWorkflowEngineConformanceTests`、`OracleWorkflowTaskConformanceTests`（Oracle 两个在 `OracleGroup`）。
6. **架构版本**：不引入。现有的 README、文档站、RFC-0021 与 ADR-0304 都写的是「没有架构版本与自动迁移」，没有将来引入的承诺。

## 影响

- **公开 API**：`Workflow.Conformance` 的 `WorkflowEngineConformance` 新增用例方法 `Transaction_CatalogEdits_HoldTheDefinitionLockUntilTheInvocationEnds_AndReleaseOnRollback`（Preview）。没有新的配置键、错误码与消息键，特性清单不变。
- **行为**：
  - 目录改写已有的定义会等别人持有的同一份定义的锁，最多 `XiHan:Workflow:LockTimeoutSeconds`，超时那一项以 `WORKFLOW_TIMEOUT_001` 失败；同时改同一份定义的两次调用由此串行，后提交的不再悄悄覆盖先提交的。每次改写多读一次定义；数据库实现每个改写的定义多一行租约（随作用域结束删除，持有期间续约）。
  - 回填可以在有人编辑定义、引擎照常运行时调用；`Busy` 也计入锁被占用的定义。
  - 表达式的结果与工作量不变，容器作文本实参与 `contains` 在数组里找时少解码一到两遍。
- **规范**（规范工作区已提交）：RFC-0021「目录」「锁」「默认实现与 Provider」「一致性」与状态行，MAJOR（`v1.0.0` 之前允许）。向量不变。
- **CI**：`Workflow.Database.Tests` 多出 161 条门控用例：SQL Server、MySQL 与 Oracle 各 53 条（引擎 43、任务 9、回填与定义编辑 1），PostgreSQL 2 条（引擎用例 43、回填与定义编辑）。database 分片里 SQL Server 与 MySQL 的类与已有的门控类并行。oracle 分片的 53 条与已有的 17 条 Oracle 用例一样串行、每条新建用户与全部表：照 2026-11-26 dev 的 CI（run 45854971994）推算，那里 `Workflow.Database.Tests` 用了 11 分 24 秒，其中不连 Oracle 的部分约 2 分钟，17 条 Oracle 用例约 9.5 分钟、每条约 33 秒；多出的 53 条约 29 分钟，这一步要 40 分钟上下，作业约 43 分钟，超过 `test-oracle` 现在的 30 分钟期限。database 分片的三个库建库快、类之间并行，估计多 1 到 2 分钟，在 20 分钟期限以内。
- **六个 SDK**：不受影响。

## 理由

- 写文本的地方只有一处、量的规则只有一处，两者走同一遍，字符串只取一次文本，也不会出现「量的」与「写的」两套遍历。
- 定义的锁与实例的锁同一把、同一个持有者：持有到提交之后才放，窗口就关上了，不必再要求运维挑时候跑回填；放在执行范围而不是存储里，同一作用域里的重入与复用照旧由它判断。
- 只为看得到的定义取锁，看不到的 ID 结果不变；批量按序数取锁，与引擎「一次调用先后持有几把锁」的做法一样有界，交叉等锁时一方超时。

## 修订（2026-11-27）

推送后 CI 的 Oracle 分片里，引擎套件 `DelayedStart_AndReusePolicy` 偶发等不到延迟启动：用例的 `ManualClock` 以带 100 纳秒的时刻起步，Oracle 把 `timestamp(6)` 的写入四舍五入到微秒，存下的启动时刻可能比推进后的时钟晚不到一微秒，手动时钟又不会自己走，轮询永远看不到到期。PostgreSQL 与 MySQL 截断、SQL Server 的 `datetime2(7)` 不丢精度，所以只在 Oracle 上出现，约一半的概率。

修法：`Workflow.Conformance` 内部的 `ManualClock` 把起点截到整微秒，与存储套件第六轮的做法（时刻一律对齐到微秒）一致；引擎与任务套件里四处用它起步的用例一起受益，公开面不变。
