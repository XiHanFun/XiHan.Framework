# ADR-0319 类型化应答写出的文本过 JSON 文本的共同检查

## 状态

已采纳（规范 RFC-0011 规则 2 的「载荷的文本」与规则 10 的「编码」、RFC-0001「写出与转交」的类型化响应一条、`plugin/invocation.md` §1「插件一侧写出应答」，以及 RFC-0001、RFC-0011、RFC-0017 的状态行已改；框架代码不变，.NET 的缺口记在「影响」，怎么补由仓库所有者另定；六个 SDK 的改动由 SDK 一侧跟进；向量、错误码、消息键与配置键不变）。

## 日期

2026-11-26

## 背景

ADR-0318 把「写不成合法的 JSON 文本」定为类型化响应写不出，但规范正文只列了字符串：以 UTF-16 存放字符串的语言与 Python 的 `str` 里孤立的代理项，以字节存放字符串的语言（Go、PHP）里不合法的 UTF-8。RFC-0001「JSON 文本」的共同检查还有两条：嵌套不超过 64 层，任何一层都没有重复的成员名。六个 SDK 写出类型化应答时核对的范围因此不一样：

1. **Go**：`operation.encodeResponse` 在 `encoding/json` 写出之后，对整段文本做共同检查（`jsontext.Check`），再按 `encoding/json` 的规则核对字符串。嵌套超过 64 层、`MarshalJSON` 原文里有重复成员，都在本地失败。
2. **Java**：`OperationJson.encode` 在 Jackson 写出之后过 `JsonText.check`，范围与 Go 相同。
3. **.NET**：System.Text.Json 写出时的深度上限缺省是 64；孤立的代理项由 ADR-0318 的 `StrictJsonEncoder` 拦下；重复成员不核对（实测见「影响」）。
4. **TypeScript**：`encodeResponse` 用 `writeJson(…, { loneSurrogates: 'reject' })`，只拒孤立的代理项，不查深度，也不查重复成员。
5. **Python**：`_encode_response` 的 `dumps(…, strict=True)` 只拒代理项码点。它把成对的两个代理项码点也算写不出，这与 ADR-0301 的读取规则一致，但规范只写了「孤立的代理项」，在以码点存放的 `str` 里成对的两个算不算孤立，没有写明。
6. **Rust**：`String` 总是合法的 UTF-8。但 `serde_json::value::RawValue::from_string` 只核对语法，`"\ud800"` 这类转义照收、照样写出；重复成员与深度也不查。
7. **PHP**（这次实测，本机 `php:8.4-cli`）：SDK 的 `Json::encode` 与 `json_encode` 的缺省深度都是 512，65 层的数组照常写出；`RawJson` 各自过得了检查，嵌进去之后层数叠加，60 层的 `RawJson` 套在 10 层数组里写出 70 层。重复成员写不出：数组、`JsonObject` 与 `stdClass` 的键唯一，`RawJson::of` 拒收重复成员。

结果是超过 64 层或有重复成员的应答，Go 与 Java 在插件一侧以 `KERNEL_UNEXPECTED_001` 失败，TypeScript、Python、Rust 与 PHP 照常交回，再由宿主按 `plugin/invocation.md` §1 以 `PLUGINS_UNEXPECTED_001` 拒绝：同一个处理器在不同语言里是两种结果，正是 ADR-0318 统一过的那种分歧。

仓库所有者已拍板：统一成「写出的文本要过 RFC-0001 的共同检查」，TypeScript、Python、Rust 补上；Python 的 `str` 里出现任何代理项码点都算写不出。

## 备选

1. **写出的整段文本过 RFC-0001「JSON 文本」的共同检查，没过即写不出**：采纳。
   - 共同检查是读的一方早已用的那一份（宿主读插件交回的应答，ADR-0315；SDK 读载荷，ADR-0236），写的一方用同一份，写得出的就读得进。
   - 序列化器按类型写出时自己的限制拦不全：自定义的写法（转换器、`MarshalJSON`、`toJSON`）、原样嵌进去的 JSON 文本（`json.RawMessage`、`RawValue`、`JsonElement`、`RawJson`）、成员名的命名策略与扩展数据都能写出超过 64 层或有重复成员的文本。核对写出的结果，就不用逐种列举。
   - 写完之后核对整段文本，或者边写边核对，结果相同；规范只规定结果。
2. **只补深度，不管重复成员**：否决。宿主照样拒绝重复成员，不补就仍是两种结果。
3. **SDK 不查，交给宿主拒绝**（TypeScript、Python、Rust、PHP 的现状）：否决，理由同 ADR-0318 备选 8：宿主报的是 `PLUGINS_UNEXPECTED_001`，把处理器写不出的应答归成插件写坏了协议内容；同一个处理器在 Go 或 Java 里又是另一个结果。
4. **结果照现行规则：`KERNEL_UNEXPECTED_001` + `kernel.invocation.unhandled_exception`，没有参数，不带 `inner`，没有载荷**：采纳。
   - RFC-0011 规则 10 的「编码」已经写明写不出就是这个结果，ADR-0318 写明写不成合法的 JSON 文本不带 `inner`；深度与重复成员是同一件事。
   - 写的过程中处理器自己的代码（`toJSON`、`MarshalJSON`、转换器）抛出框架异常时照旧放进 `inner`，这一条只管核对没过的情形。
5. **层数从响应的根算起**：采纳。原样嵌进去的文本各自过得了检查，嵌进去之后可能超过 64 层；按整段文本算，与读的一方相同。
6. **Python 的 `str` 里任何代理项码点（U+D800–U+DFFF）都写不出，成对出现的两个也一样**：采纳，照所有者的决定。
   - 理由是与 ADR-0301 的读取一致。RFC-0001「JSON 文本」第一条：以字符串交来的文本先严格编码成 UTF-8 再检查。Python 的 `str` 以码点存放，`chr(0xD83D) + chr(0xDE00)` 是两个码点，不是 U+1F600，严格编码成 UTF-8 时编码不成（`UnicodeEncodeError`），Python SDK 读取时（`_json.parse`）也按语法错误拒收。读的一方不收的 `str`，写的一方也不写。
   - 以 UTF-16 存放字符串的语言里，高代理项紧跟低代理项是一个字符，照常写出；Python 里没有这种「成对」，两个码点就是两个码点。
7. **Python 把成对的两个代理项码点合成一个字符写出**（SDK 非严格的 `quote` 现在这样写）：否决。写出的是 U+1F600，读回来是另一个字符串，等于悄悄改了值，与 ADR-0318 不写成 U+FFFD 同一个理由。
8. **Python 把它们写成 `\ud83d\ude00` 这样的一对转义**：否决。转义的一对在 JSON 里同样表示 U+1F600，结果同上。
9. **处理器以字符串或字节交回的应答也由 SDK 过共同检查**：不在这次范围。那是处理器交来的文本，不是 SDK 写出的：以字符串交回的照 ADR-0315 严格编码，以字节交回的由宿主核对、没过归给插件（`plugin/invocation.md` §1），都照旧。
10. **加向量**：否决，理由同 ADR-0312 备选 13：要写出的是各语言自己构造的响应对象，向量要先被各语言的 JSON 读取器读进来，超过 64 层、重复成员与成对的代理项码点读进来就各不相同（System.Text.Json 缺省拒收超过 64 层，Go 与 Python 的标准库遇重复成员取最后一个，转义的一对代理项读成一个字符），由各实现的单元测试核对。
11. **规范的档位是 MINOR（写明）**：采纳。
    - 以前不作规定：ADR-0318 的「写不成合法的 JSON 文本」在正文里只列了字符串，深度与重复成员在写出一侧没有规定；Python 成对的代理项码点算不算孤立也没写。
    - 宿主一侧的行为不变：宿主读插件交回的应答照旧按共同检查核对，没过照旧是 `PLUGINS_UNEXPECTED_001`（ADR-0315）。
    - 两个方向的互通都不失败（RFC-0024「版本」第 3 条）：较早 MINOR 的 SDK 交回超过 64 层或有重复成员的应答，新的宿主与较早的宿主一样拒绝；新 MINOR 的 SDK 在本地失败，按 §3 报 `KERNEL_UNEXPECTED_001`，较早 MINOR 的宿主照常读入。读取一侧没有新的拒收，用不着「照收，否则算 MAJOR」那一条。
    - 宿主自己的 XGI 入口同受这一条约束：.NET 以前把有重复成员的响应经 HTTP、MCP 等写给调用方，补上之后是 `KERNEL_UNEXPECTED_001`。这是写给协议调用方的内容，XiHan 读 JSON 的一方本来就不收这样的文本；经 `Host.Invoke` 交给插件的应答有重复成员时，SDK 的读取早已拒收（ADR-0236），不是新的互通失败。
    - 不是 MAJOR：没有改已经写明的行为。ADR-0318 的字符串规则原样保留，Python 那一条只是把「孤立」在以码点存放的 `str` 里怎么算写死，Python SDK 本来就这样做。
12. **.NET 这次不改代码**：采纳，照所有者的决定。内核的写出另有改动在做，避免冲突；缺口写在「影响」，怎么补由所有者另定。

## 决策

1. **类型化应答写出的文本**（RFC-0011 规则 10 的「编码」与规则 2 的「载荷的文本」，RFC-0001「写出与转交」，`plugin/invocation.md` §1）：XGI 入口（宿主与 SDK）把类型化的响应写成载荷时，写出的整段文本要过 RFC-0001「JSON 文本」的共同检查，含嵌套不超过 64 层（从响应的根算起）与任何一层没有重复的成员名；没过即响应写不出，`KERNEL_UNEXPECTED_001` + `kernel.invocation.unhandled_exception`，没有参数、不带 `inner`、没有载荷，插件一侧照这一条报给宿主。写完之后核对，或者边写边核对，都可以。
2. **Python**：`str` 里任何代理项码点（U+D800–U+DFFF）都写不出，成对出现的两个也一样，不合成一个字符，也不写成一对转义；理由是与 ADR-0301 的读取一致。
3. **不加向量**；规范的档位是 MINOR。
4. **对 ADR-0318 的扩展**：扩展的是它的决策 2（类型化应答）与备选 6（「写不成合法的 JSON 文本即写不出」）。ADR-0318 只把字符串列为写不成的情形，这里扩到 RFC-0001 共同检查的全部条目，并写明 Python 成对的代理项码点。ADR-0318 的其余部分不变：字符串不写成 U+FFFD、不写成转义（备选 6），结果不带 `inner`（备选 7），范围只是成功响应编成载荷的那一处（备选 12），.NET 用 `StrictJsonEncoder` 核对字符串（备选 10）。ADR-0318「影响」里各 SDK 的条目照下面「影响」改写：Go 与 Java 已经满足，TypeScript、Python、Rust 与 PHP 要补。

## 理由

- 与 ADR-0318 同一个理由：处理器写不出的应答在写的那一方本地失败，宿主与各 SDK 结果相同，不让宿主替它背「插件不合规」。只拦字符串，超过 64 层与重复成员仍是两种结果。
- 读与写用同一把尺子：写出的文本过得了读的一方的检查，才不会出现「写得出、读不进」；按写出的结果核对，比逐种列举序列化器的漏洞可靠。
- Python 成对的代理项码点：读的一方按严格的 UTF-8 拒收，写的一方合成一个字符写出，写出去的就是另一个字符串。

## 影响

- **公开 API**：无。框架的实现随后在同一天补上（见最后一条）。
- **对已有部署与代码的行为变化**：.NET 补上缺口之后（见最后一条），响应写出有重复成员或超过 64 层时，经 XGI 入口的调用以 `KERNEL_UNEXPECTED_001` 失败、没有载荷，HTTP 是 500；以前照常写出。
- **规范**（规范工作区已提交）：RFC-0011 规则 2 与规则 10、RFC-0001「写出与转交」、`plugin/invocation.md` §1 与三个状态行，写明（MINOR）。
- **Go 一致性模块**：不变。
- **六个 SDK**（规则在 RFC-0011 规则 10 的「编码」与 `plugin/invocation.md` §1；每家都补一条 64 层照常写出的测试，防止差一层）：
  - Go：已满足，不用改。`encodeResponse` 写出之后过 `jsontext.Check`，`TestResponsesThatAreNotJSONTextAreNotWritten` 已有 65 层、`MarshalJSON` 交出的重复成员与 64 层照常写出。
  - Java：已满足，补测试。`OperationJson.encode` 写出之后过 `JsonText.check`；补 65 层、自定义 `JsonSerializer` 写两次同一个字段名、`@JsonRawValue` 交出的重复成员，以及 64 层照常写出。
  - TypeScript：`encodeResponse` 写出之后过共同检查（`readJsonText`），或者 `writeJson` 加深度与重复成员的核对。`JsonMembers` 的成员名只在文档里说不重复，构造时不核对，`writeJson` 照写重复的成员。
  - Python：`_encode_response` 写出之后过共同检查（`_json.parse`），或者 `_write` 加深度与重复成员的核对。实测 65 层的列表、`to_json_value` 交出的有重复键的 `Mapping` 都照常写出；成对的代理项码点已经拒收，补测试。
  - Rust：`encode` 之后跑 `json::check`，没过即 `unhandled()`。
  - PHP：核对的结果见「背景」第 7 条：写不出重复成员，超过 64 层照写。`Codec::encode` 写出之后过 `JsonText::check`，没过即 `unhandledException`、不带 `inner`。
- **.NET 的核对**（这次不改代码；用 `OperationDescriptor<…>.EncodeResponse` 写出、`JsonText.FindProblem` 核对，实测）：
  - 深度：
    - 太严：64 层、最里面一层有非 `null` 的值（64 层数组里的 `0`，64 层对象最里面的 `int` 成员）写不出，抛出 `JsonException`。System.Text.Json 写每个值之前核对写出器的当前深度是否已到上限，第 64 层里的值也算超。同一份 64 层的文本 `DecodeRequest` 读得进，同一个对象作为响应却写不出；Go、Java、Python、TypeScript 都写得出。只有空容器或 `null` 的 64 层照常写出。
    - 太松：序列化上下文把 `MaxDepth` 设得比 64 大时（如 128），100 层照写，写出的文本过不了共同检查。设得比 64 小时（如 32）按它的上限更早写不出。
    - 转换器 `WriteRawValue` 写进去的层数不计入写出器的深度，`[` 加 64 层的原文写出 65 层。成员里的 `JsonElement`、`JsonNode` 与转换器自己写的容器计入，从响应的根算起超过 64 层即抛出。
  - 重复成员：不核对，下面几种都照常写出：`[JsonExtensionData]` 的键与声明的属性同名，`DictionaryKeyPolicy` 把两个键映射成同一个名字，成员里的 `JsonElement` 或 `JsonNode.Parse` 读来的节点带重复成员（两者缺省都收重复成员），自定义转换器写两次同一个名字，`WriteRawValue`。属性之间的名字冲突（命名策略、`[JsonPropertyName]`）System.Text.Json 在建元数据时抛出 `InvalidOperationException`，按写不出结束，不是缺口。
  - 孤立的代理项：`WriteRawValue` 写进去的 `"\ud800"` 转义绕过 `StrictJsonEncoder`，写出的文本过不了共同检查，这是 ADR-0318 的做法漏掉的一种。`JsonElement` 与 `JsonNode` 里转义出的孤立代理项写出时先解转义，照样被拦下。
- **测试**：框架新增 `ResponseTextCheckTests`（见最后一条）。
- **文档**：文档站的各 SDK 页、`plugins/out-of-process`、`plugins/wasm`、`packages/kernel` 与 `appendix/spec` 待改。
- **待定（已解决，见下一条）**：.NET 怎么补（写完之后过 `JsonText.FindProblem` 能补上太松、`WriteRawValue` 与重复成员三处，太严的一处要动序列化器的深度上限）。
- **.NET 怎么满足**（内核 `OperationDescriptor<…>.EncodeResponse`，细节见 ADR-0318「修订（2026-11-26）」第 4 条）：写完之后整段文本过 `JsonText.FindProblem`，没过即抛出 `ArgumentException`，XGI 入口按未处理的异常结束（`KERNEL_UNEXPECTED_001`，不带 `inner`）。写出的深度上限放到序列化上下文的上限与 64 取小再加 1：按响应类型的选项建一份只改 `MaxDepth` 的副本（`new JsonSerializerOptions(options)`，按原选项缓存在 `ConditionalWeakTable`），再向同一个解析器 `GetTypeInfo(typeof(TResponse))` 重新取元数据；源生成的上下文也一样，不经反射，第一次写出时才取。64 层、最里层有值的响应照常写出，第 65 层由检查或 System.Text.Json 的深度上限拦下。原样嵌进去的文本、转换器写两次的成员、扩展数据与声明成员同名、字典的键按命名策略撞名、带重复成员的 `JsonElement` / `JsonNode`、原样嵌进去的 `\ud800` 转义都是写不出。`JsonText.FindProblem` 改为按层复用状态，结果不变。测试 `ResponseTextCheckTests`，改之前 13 条里 11 条失败。代价：约 1 MB 的响应 2.27 → 5.34 ms，小响应 0.36 → 0.90 µs。
