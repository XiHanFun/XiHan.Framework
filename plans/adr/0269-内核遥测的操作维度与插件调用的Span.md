# ADR-0269 内核遥测的操作维度与插件调用的 Span

## 状态

已采纳（内核的 `ObserveMiddleware` 与 `FrameworkDiagnostics`、`Plugins.Protocol` 的 `PluginTracing` 已改，公开面不变；规范 RFC-0023 新增的「内核的遥测」一节与 `plugin/invocation.md` §6 的修订已补）。

## 日期

2026-11-24

## 背景

- 内核的遥测只有一条 Span 与两个指标，都由 Observe 阶段的 `ObserveMiddleware` 发出，经 `FrameworkDiagnostics` 的 ActivitySource 与 Meter（名字都是 `XiHan.Framework`）：
  - Span `xihan.invoke`（`Internal`），标签 `xihan.outcome`，失败时状态为 Error、说明是错误码。
  - 计数器 `xihan.invocations`（`{invocation}`）与直方图 `xihan.invocation.duration`（`ms`），标签 `xihan.outcome`（`success` / `failure` / `unset`）。
- 三者都分不出是哪个操作：看板上只有全应用的总量与总耗时，哪个操作慢、哪个操作在失败，要回到日志里按 trace-id 找。链路里每条 `xihan.invoke` 长得一样，采样器也没法按操作取舍（比如不采健康检查）。
- `plugin/invocation.md` §6 写明宿主为每次 `Invoke` / `InvokeStream` / `HandleEvent` 记录 `xihan.invoke` 的子 Span `xihan.plugin.invoke`，标签 `xihan.plugin.id`、`xihan.operation`。实现里没有这条 Span：链路上看不出调用进了哪个插件、在插件一侧花了多久；写给插件的 `trace_parent` 取的是 `xihan.invoke` 的 span-id，插件自己的 Span 直接挂在它下面。
- 规范只给了插件那条 Span 的名字与两个标签名。内核的 Span 与指标有哪些标签、标签在什么时候不带，RFC-0023 没有写。

## 备选

操作维度：

1. **标签名用 `xihan.operation`**：采纳。`invocation.md` §6 已经用这个名字指操作 ID，内核的 Span 与指标用同一个，三处是同一个维度。
2. **不是操作调用时写一个固定的占位值（照 OpenTelemetry 对未知 HTTP 方法的做法写 `_other`）**：否决。占位值是在说「这是一个叫 `_other` 的操作」，而这些调用（消息处理器、作业、直接交给 `App.InvokeAsync` 的处理器、没有匹配到操作端点的 HTTP 请求）根本不是操作调用。不带标签时，后端按「有没有这个属性」就能把两类分开；Prometheus 上缺的标签等同空值，按 `xihan_operation` 分组时它们自成一组。
3. **不是操作调用时拿调用来源的请求目标（主题、作业名、请求路径）顶上**：否决。这些文本的取值不受登记表约束，请求路径更是调用方给的；进了指标标签就是无界的基数。
4. **调用结束时再读操作描述**：否决。处理器在同一个上下文上再发起调用时，调用器把里层的描述放进同一个上下文，外层结束时读到的是里层的操作。改在进入时读。
5. **Span 开启之后再 `SetTag`**：否决。采样器只看得到创建时给出的标签；创建时带上，才能按操作采样。代价是有监听器时每条 Span 多建一个一项的数组。
6. **每次调用拿登记表核对上下文里的描述确实登记过**：不做。描述由调用器与宿主在管道开始前从登记表取出放进上下文；`SetOperation` 是公开的，应用自己放一个手建的描述是代码行为，不是请求数据，为它每次调用多查一次登记表不值得。

插件调用的 Span：

7. **另开一个 ActivitySource（`XiHan.Framework.Plugins`）**：否决。规范说它是内核 `xihan.invoke` 的子 Span；缺省的导出只订阅 `XiHan.Framework` 一个源，另开一个就得让每个导出方多订一个。
8. **在两个运行时的调用与投递里各开一次（四处）**：否决。宿主调用插件操作只有一个入口（`ProxyOperationDescriptor.ExecuteAsync`），投递也只有一个（`PluginRoster.DeliverAsync`），都在 `Plugins.Protocol` 里、两个宿主共用。
9. **只包住发给插件的那一次 RPC**：否决。等插件可用（懒激活、Wasm 的排队）也是「调用这个插件」花的时间，插件不可用时更该有一条状态为 Error 的 Span。
10. **种类用 `Internal`**：否决。它有进程外（或沙箱里）的子 Span，是一次对外的调用；`Client` 是这种 Span 的种类。
11. **直接 `StartActivity`、以当前 Activity 为父级**：否决。应用关掉内置中间件时管道里没有 `xihan.invoke`，当前 Activity 可能不在这次调用的链路里（或者根本没有），Span 会另起一条链路。改为与 `xihan.invoke` 共用 RFC-0003 规则 7 的取法。
12. **投递的 Span 也带 `xihan.operation`（写主题，或写一个固定值）**：否决，理由同备选 2、3。投递不是操作调用。要不要另加一个主题标签，记为待定。
13. **把异常记成 Span 事件（`AddException`）**：否决。事件带异常消息与调用栈，消息里可能有路径与地址；状态的说明只写异常类型。

不在这次范围里的：

14. **改已有的名字、单位与标签**（直方图的单位由 `ms` 改 `s`、加 `error.type`、Span 的显示名带上操作 ID）：不做，见「影响」的待定。
15. **给插件调用加指标**：不做。操作调用已经计在 `xihan.invocations` 里（带代理操作的 ID）；按插件分的指标要先定维度。
16. **把标签名与「在调用的链路里开 Span」做成公开 API**：不做。先以 internal 给内核与插件宿主用，公开要先进规范。

## 决策

1. **`xihan.operation` 维度。** Observe 阶段在进入时读上下文里的操作描述，有描述时：
   - Span `xihan.invoke` 在创建时带标签 `xihan.operation`（操作 ID），采样器看得到。
   - `xihan.invocations` 与 `xihan.invocation.duration` 的每次记录带 `xihan.operation` 与 `xihan.outcome` 两个标签。
   - 取值只有操作描述的 ID：调用器按请求里的 ID 在登记表里找到描述才进管道（找不到直接返回 `KERNEL_NOTFOUND_001`，不进管道，也就没有 Span 与指标），HTTP 宿主取匹配到的操作端点上的描述。登记表有容量上限（缺省 10 000），维度的取值随之有上限。
2. **不是操作调用时不带这个标签**：消息处理器、作业、直接交给 `App.InvokeAsync` 的处理器、没有匹配到操作端点的请求。Span 与指标上只有 `xihan.outcome`，不写占位值，也不拿主题、作业名、请求路径顶替。
3. **没有监听器时不付代价。** 没有 Span 监听器时不建标签数组、不开 Span；两个仪表都没人订阅时不算耗时、不调仪表；标签以值类型传给仪表，不装箱、不建数组。读操作描述是一次字典查找，不分配。
4. **`xihan.plugin.invoke`**（`Plugins.Protocol` 的 `PluginTracing`，两个宿主共用）：
   - 宿主调用插件的操作（`Invoke`）与向插件投递事件（`HandleEvent`）各记一条；宿主没有实现 `InvokeStream` 的调用，将来实现时走同一处。
   - 经内核的 ActivitySource 创建，种类 `Client`。
   - 父级按 RFC-0003 规则 7（`FrameworkDiagnostics.StartActivity`，与 `xihan.invoke` 同一处实现）：管道里有 `xihan.invoke` 时是它的子 Span；没有时以上下文的上游为远端父级，或作为这条链路的根，总在调用的链路里。上游「不采样」时不开。
   - 标签：`xihan.plugin.id`（插件的清单 ID）；操作调用另带 `xihan.operation`（代理操作的 ID）；投递不带。两个标签都在创建时给出。
   - 状态：宿主一侧拿到失败结果（插件报的业务失败、插件不可用、传输失败）时为 Error，说明是错误码，与 `xihan.invoke` 一致；调用抛出（取消、载体的故障）时为 Error，说明只写异常类型的全名；成功时留空。
   - 范围：从进入载体的调用到它返回，含等插件可用的时间。
   - 与上下文传播的关系：载体在这条 Span 之内组装 `InvocationMetadata`，`trace_parent` 按 RFC-0003 规则 7「写出」取当前 Activity，也就是这条 Span 的 span-id 与采样位；插件一侧的 Span、插件原样带回来的回调，都挂在它下面。
   - 没有监听器时直接转调载体，不进异步状态机、不分配。
5. **实现的位置。** 规则 7 选父级的逻辑从 `ObserveMiddleware` 挪到 `FrameworkDiagnostics.StartActivity`（internal），标签名收在内核的 `DiagnosticTags`（internal）；`Plugins.Protocol` 本来就以确切版本引用内核的 internal（ADR-0134）。公开面没有变化。

## 理由

- 操作 ID 是这个框架里唯一一个既能回答「是哪个接口」、取值又天然有上限的名字：它来自登记表，不来自请求。
- 维度宁可缺、不可假。没有操作的调用带一个占位值，看板上就多出一个并不存在的操作；带上请求里的文本，指标的基数就交给了调用方。
- 采样与导出都发生在内核之外。内核能做的是把后端需要的信息在对的时机给出去：采样要的标签在创建时给，没人听时什么都不做。
- 插件调用是链路上最值得单独看的一段：它跨进程或跨沙箱，慢了、断了都要能一眼看出是哪个插件。让插件的 Span 挂在这一段下面，宿主等待与插件处理的时间才分得开。

## 影响

- **公开 API**：没有变化（`PublicAPI.Unshipped.txt` 不变）。
- **新增与变化的遥测**：

  | 信号 | 名字 | 变化 |
  | --- | --- | --- |
  | Span | `xihan.invoke` | 操作调用新增标签 `xihan.operation`，创建时给出；名字、种类、`xihan.outcome`、状态与父级的规则不变 |
  | Span | `xihan.plugin.invoke` | 新增：种类 `Client`，标签 `xihan.plugin.id`、`xihan.operation`（只有操作调用），失败时状态为 Error |
  | 计数器 | `xihan.invocations` | 操作调用新增标签 `xihan.operation`；名字、单位与 `xihan.outcome` 不变 |
  | 直方图 | `xihan.invocation.duration` | 同上 |

- **对已有看板与告警的影响**：
  - 两个指标的时间序列按操作分开了。先聚合再比较的查询（`sum(...)`、`sum by (xihan_outcome)(...)`）结果不变；直接按 `{xihan_outcome="failure"}` 取单条序列的查询现在得到多条，要加 `sum`。
  - 序列数由「结果数」变成「操作数 × 结果数」（直方图再乘桶数）。操作多、后端按序列计费的部署可以在导出一侧用视图去掉这个维度。
  - 有 Span 监听器时，写给插件的 `trace_parent` 的 parent-id 由 `xihan.invoke` 换成 `xihan.plugin.invoke`：插件一侧的 Span 在链路里深了一层，trace-id 与采样位不变。没有监听器时与原先完全一样。
  - 代理操作的 ID 来自插件的握手声明：反复加载声明了不同操作的插件，`xihan.operation` 的历史取值会随之累积；任一时刻仍受登记表容量约束。
- **规范（已补，规范指针 `3d3a139`）**：
  - RFC-0023 新增「内核的遥测」一节：源与仪表的名字、两条 Span 与两个指标、三个标签的取值，以及「不是操作调用时不带 `xihan.operation`」「操作 ID 在创建 Span 时给出」「没有监听器时不创建、不记录」三条规则。
  - `plugin/invocation.md` §6 第 2 条：写明种类、父级的取法、`HandleEvent` 不带 `xihan.operation`、状态、范围，以及 `trace_parent` 以它为父级。
- **待定**：
  - 投递的 Span 要不要带主题（如 OpenTelemetry 消息约定的 `messaging.destination.name`）。主题来自订阅声明、不是请求数据，放在 Span 上没有基数问题；现在投递的 Span 只看得出是哪个插件。
  - 已有的名字与单位（都是破坏性改动，这次没有动）：`xihan.invocation.duration` 的单位是 `ms`，OpenTelemetry 的约定是 `s`；失败的调用可以加 `error.type`（错误码）维度；Span 的显示名可以带上操作 ID（`xihan.invoke orders.create`），名字本身保持低基数。
  - 标签名与 `StartActivity` 是否公开：子系统的 Provider 想在调用的链路里开自己的 Span 时用得上。
  - 测试里监听 Span 与指标的收集器现在在三个测试项目里各有一份；要不要像 `LogCapture`（ADR-0262）那样收进 `Testing`。
- **测试**：
  - 内核 `ObserveTelemetryTests`：操作调用的 Span 与两个仪表都带操作 ID、采样器在创建时看得到；失败与抛出记在同一个操作名下、Span 的状态是 Error；没有操作的调用不带标签；未知的操作 ID 不进管道，Span 与指标里都没有它；同一个上下文上的嵌套调用不改外层的维度；不采样时指标照记；没有监听器时不开 Span、仪表关着。原有的 `ObserveTracingTests`（父级与采样）不改断言，与新用例同进一个不并行的集合：监听器是进程级的，别的用例的监听器会替它的采样器作决定。
  - 共用的 `PluginTracingTests`（假运行时）：名字、种类、两个标签、是 `xihan.invoke` 的子 Span、调用期间它是当前 Activity、写出的 traceparent 取它；没有 `xihan.invoke` 时以上游为远端父级，上游不采样时不开；失败结果与抛出的状态；代理操作经它调用；投递给每个订阅了的插件各一条、互为兄弟、没有操作标签；没有监听器时交回的就是载体自己的任务。
  - 端到端：进程外用真实的 EchoPlugin 子进程、Wasm 用真实的 EchoWasm 模块，`echoes.relay` 把收到的元数据原样带回宿主，回调读到的上游正是 `xihan.plugin.invoke` 的 span-id；插件报业务失败时状态为 Error、说明是插件的错误码；事件投递的 Span 挂在投递那次调用的 `xihan.invoke` 下面。
  - 新用例先在旧实现上跑过：内核的 4 条（要操作维度的）与 Wasm 的 2 条失败，其余 3 条是回归守卫（没有操作的调用、未知操作、没有监听器）；`PluginTracingTests` 引用新的 internal 类型，在旧实现上不能编译。
- **文档**：内核、进程外与 Wasm 三个包的 README 已同步；文档站的 `common/observability`（遥测一览的表与 `xihan.outcome` 一段）、`packages/observability-opentelemetry`、`startup/pipeline`、`plugins/out-of-process`、`plugins/wasm`、`packages/plugins-outofprocess`、`packages/plugins-wasm` 与更新日志待改。
