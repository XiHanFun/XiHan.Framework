# ADR-0304 工作流数据库实现的查询列回填

## 状态

已采纳（规范 RFC-0021「默认实现与 Provider」写明，本仓库 `Workflow.Database` 实现）；2026-11-27 由 ADR-0326 修订：目录改写定义取锁，回填的定义行也在锁内改写（见文末「修订」）。

## 日期

2026-11-25

## 背景

`Workflow.Database` 的定义、实例与书签以 JSON 文档列存整份对象，另有一批由文档算出、只为把过滤与排序下推到 SQL 而存的**查询列**：

| 表 | 查询列 | 来历 |
| --- | --- | --- |
| 定义 | `StatusOrder`、`Category`、`SearchText`、`Title` | ADR-0096、ADR-0102、ADR-0103 |
| 实例 | `StatusOrder`、`SearchText`、`Title` | ADR-0099、ADR-0102、ADR-0103 |
| 书签 | `NodeId`、`DefinitionName`、`InstanceStatus`、`SearchTitle`、`SearchInstanceText` | ADR-0096、ADR-0099 |

它们是几轮里陆续加上的可空列，RFC-0021 每次都写「升级前写入的行要回填」，却从没给出做法；ADR-0296 把关键字的小写改成简单映射之后，含 `İ` 或平面以外大写字母的 `SearchText`、`SearchTitle`、`SearchInstanceText` 也要重新折叠。所有者要求按包里现有的迁移机制提供回填：分批、可以重复跑（已是新折叠的行不再改写）、可取消、批大小有上限，并有不靠真实数据库、能在本机跑的用例。

查下来包里**没有**架构版本与迁移机制：README 写的是「表结构由应用管理」，持久化的 `InitTables` / `EnsureCreated` 只建缺表、加缺列（开发与测试的便利），生产库的结构演进由应用的迁移脚本负责。可以照着的现有做法是两处：存储在工作单元里经仓储读写、写入行时由文档算出查询列；锁与发件箱这类不在调用里的步骤用 `UnitOfWorkScope` 在根提供者的新作用域里开自己的工作单元（ADR-0259），租户库先用 `TenantShardScope` 绑定分片（发件箱的 `OutboxDatabases`）。

## 备选

1. **SQL 迁移脚本**：否决。折叠是 Unicode 的简单小写映射，各数据库的 `LOWER()` 与它不同（PostgreSQL 按排序规则、SQL Server 按排序规则、SQLite 只认 ASCII）；书签的列还要取所属实例的行。只有存储自己的算法算得对。
2. **加一张架构版本表、启动时自动迁移**：否决。多节点同时启动要协调谁来跑；租户库要逐个绑定分片；回填可能要跑很久，挡在启动路径上会让应用迟迟不进入服务状态。表结构本来由应用管理，回填同样交给应用在升级之后调用。
3. **只回填三个关键字列**：收宽成全部查询列。这几列与关键字列是同一种东西、同一个缺口（「升级前写入的行要回填」），由同一份文档算出、在同一遍扫描里顺带比较；只做关键字，剩下的缺口还要再来一次。
4. **重新折叠存着的列**（不读文档）：否决。旧的列可能来自更早的规则（第八批把 `%`、`_` 换成全角，ADR-0099 第四节撤销）或干脆为空，从它推不出新值；文档是唯一的事实源。
5. **整行经存储的 `SaveAsync` 写回**：否决。它会把文档按当前的序列化重写一遍，回填的本意只是补查询列；而且同样需要下面的锁。
6. **按 ID 的大小做游标**（`Id > 上一批最后的 ID`）：否决。持久化的规约不保证字符串的大小比较能翻译（RFC-0005 没有写到，三种持久化上都没有验证过），内存实现与数据库的排序规则也可能不同。改用创建时间：实例表本来就有 `(TenantId, CreatedAt)` 索引，写入后不变；游标是创建时间的 `>=` 加上同刻已经读过的行数的偏移。
7. **按偏移分页整张表**：否决。每批都要跳过前面全部的行，大表上是平方的开销，书签不断被删时偏移还会成片漂移。偏移只留在同刻的行里（通常一两行）。
8. **书签单独按表扫描**：否决。书签表没有创建时间的索引；按所属实例的 ID 读（有索引）跟着实例的批走，定义级定时书签跟着定义的批走。
9. **不加锁直接改写**：否决。行没有并发戳（「存储契约」：实例锁串行化写入），扫描与写入之间引擎提交了这个实例，回填就会把旧文档写回去——丢的是流程状态。实例行与它的书签行在实例锁内重读再改写；锁的键是实例 ID 或定义 ID，与引擎写这些行时相同。
10. **一批里的锁一次全拿**：否决。引擎的一次调用可能先后持有几个实例的锁（父子流程），回填同时持有多个、再等下一个，就可能与它互相等到超时，让用户的调用以 `WORKFLOW_TIMEOUT_001` 失败。一次只持有一个；要改写的行很少（大多数行算出来与存着的相同），逐个加锁的开销只落在它们身上。
11. **锁拿不到就让分区失败**：否决。一个长时间运行的实例会挡住整个分区；跳过并计数（`Busy`），再跑一次补上。
12. **定义也加锁**：不做。目录写定义本来不加锁；回填在一个短事务里重读再写，只剩重读到写入之间的窗口，文档与 RFC 里写明宜在没有人编辑定义时运行。
13. **一个分区失败就整体失败**：否决。批量优先的逐项结果：一个租户库连不上不挡别的分区；已经提交的批留着，可以重跑。

## 决策

1. **规范**：RFC-0021「默认实现与 Provider」新增 `Workflow.Database` 的「查询列回填」：查询列的清单与它们由文档（书签另取所属实例的行）算出；`DatabaseWorkflowBackfill.RunAsync(partitions, batchSize)` 按分区（逐项结果、空集合不触存储、重复的分区再回填一次、不经管道绑定分片、不看租户是否启用）、分批（1 到 1000，创建时间加 ID 的次序，书签随所属的批按页读）、可以重复运行（与现有值相同的行不改写，文本列的空串与 `NULL` 当作相同）、与引擎互斥（实例锁内重读再改写，一次只持有一个，拿不到的计入 `Busy`；定义不加锁）、可取消（每批之前检查，已提交的批留着）；结果的四个计数。「关键字的小写」里「含这些字符的已有行要重新折叠回填」指向它。
2. **.NET**：
   - 新增公开的 `DatabaseWorkflowBackfill`（单例，由特性登记，构造函数是内部的）与 `DatabaseWorkflowBackfillReport`（`Scanned`、`Rewritten`、`Busy`、`Batches`），常量 `MaxBatchSize` = `EntityQuery.DefaultMaxTake`。
   - 存储的三个行类各新增内部的 `RefreshQueryColumns(row, 对象, …, apply)`：由对象算出查询列、返回是否与行里现有的值不同，`apply` 为真时写进行里；存储写入行（`ToRecord`）与回填都经它，回填才认得出已是新值的行。新增内部的 `QueryColumns.SameText`（空串与 `null` 相同，Oracle 的缘故）。
   - 新增内部的 `PartitionBackfill<TDefinition, TInstance, TNode, TBookmark>`：先定义、后实例，每批一个只读工作单元扫描（经 `UnitOfWorkScope` 的准备步骤绑定租户分片），要改写的定义在一个可写工作单元里重读再写，要改写的实例与书签逐个键在 `DatabaseWorkflowInstanceLock` 内开可写工作单元重读再写；抛出的异常回滚后记警告日志、归为 `WORKFLOW_UNAVAILABLE_001`，调用方的取消原样抛出。
3. **测试**：`DatabaseWorkflowBackfillTests`（本机，SQLite）——经存储写入三个定义、五个实例（两两同一个创建时刻，批的边界落在同刻的行中间）、五个用户任务与一个定义级定时书签，再把行改成升级前的样子（逐个码元的不变文化折叠、几列置空）；批大小 1、2、1000 都按预期的批数改写全部过时的行，关键字（`İZİN`、`İstanbul`、`imza`、平面以外的 `𐐨`）从一个也查不到变成全部查到，第二次运行改写零行；EF Core 在 SQLite 上同样；持有一个实例的锁时它与它的书签跳过、`Busy` 是 1，释放后再跑补上；平台、租户与重复的分区各一项结果、未写入的租户是零；批大小越界、空白的租户、空入参在动存储之前抛出；取消的令牌在进入存储之前抛出、行原样留着。`PostgresWorkflowBackfillTests`（门控 `XIHAN_TEST_POSTGRES`，CI 的数据库分片）在真实的 PostgreSQL 上跑同样的分批、重复与分区用例。
4. 包 README 新增「升级之后回填查询列」与主要类型一行。

## 影响

- 公开 API：新增 `DatabaseWorkflowBackfill`、`DatabaseWorkflowBackfillReport`（`Preview`）。没有新的配置键、错误码与消息键，特性清单不变。
- 行为：存储写入的行与以前完全相同（`ToRecord` 只是改成经同一个方法算出查询列）。回填只在应用调用时运行。
- 迁移（升级须知，与 ADR-0296 的那一条合并）：数据库实现的应用升级之后，为平台与每个租户调用一次 `DatabaseWorkflowBackfill.RunAsync`；`Busy` 不为零时再跑一次。没有过时行的库跑一遍只是读，改写零行。
- 规范：RFC-0021「默认实现与 Provider」一条、「关键字的小写」一句、状态行（写明以前没有给出做法的回填，MINOR）。
- 没有覆盖到的：SQL Server、MySQL 与 Oracle 上只有存储一致性套件跑在真实库上的现有门控，回填的门控用例只写了 PostgreSQL（与本包现有的门控夹具一致）；那三种库上游标的 `>=` 与 `IN` 走的是存储已经在用的翻译。
- 六个 SDK：不受影响。

## 理由

- 回填用存储写入行时同一份算法，「已是新值」就有了确定的含义：与存储此刻会写进去的值相同，重复运行自然收敛到零。
- 不改表结构的管理方式：表与列仍由应用管，回填是应用在升级之后调用的一步，不挡启动，也不需要多节点协调。
- 安全优先于速度：查询列错了只是查不到，文档被旧值覆盖却是流程状态的丢失，所以宁可逐个加锁、跳过忙的实例。

## 修订（2026-11-27）

ADR-0326 推翻了备选 12（「定义也加锁：不做」），其余不变：

1. **目录改写已有的定义时取定义 ID 的锁**：`UpdateAsync`、`PublishAsync`、`DisableAsync`、`ArchiveAsync`、`DeleteAsync` 经执行范围取锁、持有到作用域结束（调用方事务提交或回滚之后），与实例锁的「锁与事务的先后」相同。锁放在目录（抽象包）而不是定义存储里：存储在调用方的工作单元里写，只有执行范围知道作用域什么时候结束。
2. **回填的定义行也在锁内改写**：决策 1 的「定义不加锁」与决策 2 的「要改写的定义在一个可写工作单元里重读再写」改成：过时的定义与定义级定时书签的归属合成键，逐个在定义 ID 的锁内重读、再改写定义行与它的书签，拿不到计入 `Busy`。决策 1 的结果里 `Busy` 计入锁被占用的定义。
3. **不再要求没有人编辑定义时运行**：RFC-0021「默认实现与 Provider」、`DatabaseWorkflowBackfill` 与 `DatabaseWorkflowBackfillReport` 的 XML 文档、包 README 照改。
4. **测试**：决策 3 加两条本机用例（持有定义的锁时它跳过、释放后补上；回填与同时进行的定义编辑），后一条在四种门控库上也有（`ServerWorkflowBackfillTests`）。「影响」里「回填的门控用例只写了 PostgreSQL」已经过时：SQL Server、MySQL 与 Oracle 的回填门控类在 2026-11-26 补上了。
5. **架构版本**：备选 2 维持，所有者定了不引入。
