# ADR-0334 写给插件的幂等键与另几处标识拒收孤立的代理项

## 状态

已采纳。

- 规范：
  - `plugin/invocation.md` §2 写明宿主写 `baggage` 时的核对。
  - `conventions/baggage-keys.md` 的幂等键写出补上插件协议，`conventions/error-codes.md` 的 `PLUGINS_UNEXPECTED_001` 补上这一种。
  - RFC-0001「孤立的代理项」的表补上幂等键写给插件、发起人、持有者标识、服务名与审计的显式动作。
  - RFC-0021「实例与执行」的发起人与「默认实现与 Provider」的 `HolderId`、RFC-0023「导出」的服务名、RFC-0015「事件的产生」的显式动作已改。
  - RFC-0001、0015、0017、0021、0023 的状态行已改。
- 向量：不变。
- .NET：新增消息键 `workflow.instance.starter_invalid`（10 个区域）。错误码与配置键不变。

## 日期

2026-11-27

## 背景

ADR-0321「影响」里「同类而没改的」几处，仓库所有者已拍板全部拒收：

1. **插件元数据里的幂等键**。先查了它在调用链上在哪里被接受、在哪里核对：
   - 接受：载体入站、`App.CreateContext` 的选项、插件回调的元数据、Wasm 中间件改写的 Baggage 都按 ADR-0204 的例外留着它，丢了它重复的调用会执行两次。
   - 核对：只有 Idempotency 阶段按缓存键的文法拒绝（`CACHING_VALIDATION_001` + `caching.idempotency.invalid_key`，ADR-0316）。
   - 插件这一路绕过了这道核对：没有装配 `caching.distributed@1` 的宿主没有 Idempotency 阶段；Wasm 中间件可以排在它之前（Observe 等阶段）。
   - 宿主随后把它写进 `InvocationMetadata`（代理操作的调用、投递、中间件钩子）。实测：gRPC 载体的 protobuf 编码换成 U+FFFD，EchoPlugin 照常应答；Wasm 载体的 proto3 JSON 写出器抛出 `ArgumentException`，调用以 `KERNEL_UNEXPECTED_001` 结束。
   - 外部输入带不进来：HTTP 入站的百分号解码解不出孤立的代理项（ADR-0321 实测）；插件回调的 protobuf 字符串与 Wasm 消息里转义写出的孤立代理项都读不出（这次补了用例）；命令行宿主不收幂等键。能带进来的只有进程内的代码（`App.CreateContext` 的选项、`WithBaggage`）。
2. **工作流的发起人 `StarterId`**：没有文法。它写进实例、待办与事件的 `starterId`，是「我发起的」的查询条件，也是 `Starter` 指派规则解析出的处理人。
3. **`Workflow.Database` 的 `HolderId`**：只拒空白。它是租约行 `Holder` 的前缀（每次取锁另带随机后缀），经数据库参数宽松编码之后存下的是另一段文本，只差在孤立代理项上的两个节点在租约表里分不开。
4. **OpenTelemetry 的 `ServiceName`**：只拒空白。它是每个信号的资源属性 `service.name`，编成 UTF-8 发给后端。
5. **`SetAuditAction`**：只拒空白。动作进审计记录、日志与 `AuditQuery.Action`；换行能在日志里伪造一行。
6. **`BlobKey` / `CacheKey` 的私有判定**：ADR-0316 各写了一份，ADR-0321 新增原语 `UnicodeText.HasLoneSurrogate` 时这一轮另有代理在改对象存储，没换。

## 备选

幂等键：

1. **在插件这一路补上核对**：采纳。
   - 宿主把调用交给载体之前核对上下文里已登记的 Baggage，有孤立的代理项即这一次失败，不启动进程、不取实例。
   - 位置：代理操作在 `ProxyOperationDescriptor.CheckedInvoker`（两种载体的操作都经这里，与应答载荷的核对是同一处）；投递在 `PluginRoster.DeliverAsync`；Wasm 中间件在 `WasmMiddleware` 调 `before` 之前。判定是 `PluginMetadata.Check`，只有一份。
   - 错误照宿主组装插件请求失败的已有做法（ADR-0321 下发的绑定有孤立代理项）：`PLUGINS_UNEXPECTED_001` + `plugins.process.failed`，`id` 为清单 ID，`phase` 为操作 ID、`event` 或中间件名，`reason` 为 `baggage '<键>' has a lone surrogate and cannot be encoded as UTF-8`。
   - `PluginMetadata.FromContext` 写出时再核对一遍，遇到即抛出 `ArgumentException`，与 `HttpInvocation.FormatBaggage` 一致：调用方都先核对过，走到这里是编程错误，不交给载体宽松地编码。
2. **在建上下文的那一层拒收**：否决。ADR-0204 定了幂等键不按值的约束丢弃、不合法的留给 Idempotency 阶段以校验错误拒绝。建上下文时抛出或丢弃会改变所有宿主的语义，内核也没有体积余量。
3. **用 Idempotency 阶段的 `CACHING_VALIDATION_001`**：否决。插件包不依赖缓存，`caching.*` 的消息目录在没有缓存的宿主里也没有登记；错误码按领域分。
4. **新的错误码（`PLUGINS_VALIDATION_006` 一类）**：否决。所有者定了按该处已有的非法输入处理；宿主组装插件请求失败已有 `PLUGINS_UNEXPECTED_001` 加 `reason`。代价是 HTTP 500 而不是 400：能带进来的只有进程内的代码，是编程错误。
5. **丢掉这个成员**：否决，同 ADR-0321 备选 6，插件就没有幂等，是静默兜底。
6. **在写元数据的运行时里核对（`PluginRuntime`、`WasmPluginRuntime`）**：否决。这一轮另有代理在改 Wasm 插件运行时；放在载体外面的共用处，两种载体只有一份。
7. **中间件的 `after` 钩子再核对一次**：不做。`before` 改写进来的 Baggage 来自 proto3 JSON，转义写出的孤立代理项读入时就被拒绝（`PluginJsonCodecTests` 新增的用例）；钩子之后的代理操作照常经第 1 条核对。

其余几处：

8. **发起人**：启动与实例查询（`ListInstancesAsync`、`CountInstancesAsync`）返回 `WORKFLOW_VALIDATION_002` + 新消息键 `workflow.instance.starter_invalid`，没有参数，排在关联 ID 之后、找定义与进存储之前。采纳。
   - 子实例继承的发起人经 `StartAsync`，同一条。
   - 备选：并进 `workflow.instance.correlation_invalid`。否决：它说的是关联 ID。
9. **`HolderId`**：初始化器抛出 `ArgumentException`，从配置读取也经它，应用启动失败，照 ADR-0321 备选 13 的选项做法。采纳。
10. **`ServiceName`**：同上。采纳。
11. **`SetAuditAction`**：有控制字符（`char.IsControl`，与 Baggage 的值相同）或孤立的代理项时抛出 `ArgumentException`，与细节的键一样：动作是程序给的，不合法是编程错误。采纳。
12. **`BlobKey` / `CacheKey`**：换成 `UnicodeText.HasLoneSurrogate`，删掉两份私有判定。`BlobKey` 的那一份是 `internal`，`BlobPutOptions` 的元数据值、`BlobMultipartUpload` 的上传标识与 `BlobUrlRequest` 的文件名也在用，一并换。行为不变，已有用例照过。采纳。

向量与级别：

13. **向量不补**。采纳。
    - 宿主写元数据这一侧没有可回放的输入输出：`plugin` 档的向量由 SDK 认领。
    - 发起人、持有者标识与服务名没有向量文件。
    - 审计的 `event-selection.json` 里 `explicitAction` 是 JSON 字符串，写不出孤立的代理项；加 `utf16` 的写法要改 Go 一致性模块的读法，钉着旧版本的 SDK 会读不出整份文件（同 ADR-0321 备选 15）。
14. **MAJOR（`v1.0.0` 之前允许）**：发起人、持有者标识、服务名与审计的显式动作收窄了以前照收的输入；插件协议的写出由宽松编码变成失败。

## 决策

1. **规范**（MAJOR，`v1.0.0` 之前允许）：
   - `plugin/invocation.md` §2：宿主写 `baggage`（调用、投递与 Wasm 中间件的钩子）时已登记键的值有孤立的代理项，这一次不交给插件，`PLUGINS_UNEXPECTED_001` + `plugins.process.failed`，插件照常服务、不计入重启。
   - `conventions/baggage-keys.md`、`conventions/error-codes.md` 同步。
   - RFC-0001 的表与 RFC-0015、0021、0023 的文法与约束。
2. **.NET**：
   - `Plugins.Protocol`：`PluginMetadata.Check`（internal），`ProxyOperationDescriptor.CheckedInvoker`、`PluginRoster.DeliverAsync` 调它；`PluginMetadata.FromContext` 遇到即抛出。
   - `Plugins.Wasm`：`WasmMiddleware` 调 `before` 之前核对，失败即关闭调用。
   - `Workflow.Abstractions`：`WorkflowEngine` 的启动与实例查询，`WorkflowMessages.InstanceStarterInvalid`。
   - `Workflow.Database` 的 `DatabaseWorkflowOptions.HolderId`、`Observability.OpenTelemetry` 的 `OpenTelemetryOptions.ServiceName`、`Auditing.Abstractions` 的 `SetAuditAction`。
   - `ObjectStorage.Abstractions` 与 `Caching.Abstractions`：判定换成 `UnicodeText.HasLoneSurrogate`。

## 理由

- 与 ADR-0316、ADR-0321 同一个理由：孤立的代理项编不成 UTF-8，宽松的编码换成 U+FFFD 得到的仍是合法的文本，收的一方看不出来，不同的标识落到同一个条目、服务或人上。
- 幂等键的文法本来就在（缓存键的文法），插件这一路只是绕过了 Idempotency 阶段：补上这一路，不改建上下文的语义，也不改有 Idempotency 阶段的宿主看到的错误。
- 判定只有一份（原语的 `UnicodeText`），插件一侧的核对也只有一份（`PluginMetadata.Check`），放在两种载体的外面。

## 影响

- **公开 API**：
  - 新增 `WorkflowMessages.InstanceStarterInvalid`（Preview）。其余签名不变。
  - `Stable` 类型的行为变更：`OpenTelemetryOptions.ServiceName` 与 `AuditInvocationExtensions.SetAuditAction` 收窄了合法的输入（见下）。`CacheKey`、`BlobKey`（Stable）只换了判定的实现，行为不变。
- **程序集体积**：Primitives 103424 字节、Kernel 408576 字节（本工作区口径），都没有变。
- **对已有部署与代码的行为变化（升级须知）**：
  - 插件：上下文的幂等键有孤立的代理项时，调用进程外与 Wasm 插件的代理操作、投递给插件与经过 Wasm 中间件以 `PLUGINS_UNEXPECTED_001` 结束，`reason` 写明键名；以前 gRPC 载体写成 U+FFFD 照常调用，Wasm 载体以 `KERNEL_UNEXPECTED_001` 结束。有 Idempotency 阶段的宿主照旧在那里以 `CACHING_VALIDATION_001` 拒绝（Wasm 中间件排在它之前时先遇到这一条）。
  - 工作流：启动与实例查询的发起人有孤立的代理项时返回 `WORKFLOW_VALIDATION_002`（`workflow.instance.starter_invalid`）。
  - 选项：`XiHan:Workflow:Database:HolderId` 与 `XiHan:Observability:OpenTelemetry:ServiceName` 有孤立的代理项时，构造或从配置读取抛出 `ArgumentException`，应用启动失败。
  - 审计：`SetAuditAction` 的动作有控制字符或孤立的代理项时抛出 `ArgumentException`。
  - 迁移：从外部输入拼这些值的代码先用 `UnicodeText.HasLoneSurrogate` 判断（审计动作另去掉控制字符），配置里的这两项去掉孤立的代理项。
- **规范**（规范工作区已提交）：RFC-0001、0015、0017、0021、0023，`plugin/invocation.md`、`conventions/baggage-keys.md`、`conventions/error-codes.md`。
- **六个 SDK**：宿主写给插件的元数据从此总是合法的 UTF-8，SDK 读的一侧不用改。反方向（插件回调宿主时 SDK 写的元数据，幂等键在 SDK 里同样按例外留着）各语言的写出器怎样处理孤立的代理项这次没有核对，规范也没有写，留给所有者定（报告另列）。
- **同类而没改的**（报告另列）：调度选项的 `NodeId`（`XiHan:Scheduling:NodeId`）同是租约的持有者标识，只拒空白。
- **测试**：
  - `PluginBaggageSurrogateTests`（进程外）与 `WasmBaggageSurrogateTests`（操作与中间件钩子）：三种孤立的代理项都失败、错误的 `id` / `phase` / `reason`、成对的代理项照常、插件仍在服务且没有重启。
  - `PluginMetadataTests`：`Check` 的错误、`FromContext` 抛出、未登记的键不核对；`PluginJsonCodecTests`：转义写出的孤立代理项读不出。
  - `WorkflowStarterTests`：启动与查询被拒、不写实例、关联 ID 先于发起人、成对的代理项照常查到。
  - `DatabaseWorkflowTests`、`OpenTelemetryObservabilityTests`、`AuditMiddlewareTests` 各一条。
  - 改实现之前这些用例都失败（成对代理项与未登记键的那几条除外）。`BlobKey` / `CacheKey` 的已有用例照过。
- **文档**：Plugins.OutOfProcess、Plugins.Wasm、Workflow.Abstractions、Workflow.Database、Observability.OpenTelemetry、Auditing.Abstractions 的 README 已同步；文档站与更新日志待改。
