# ADR-0225 删除租户留墓碑

## 状态

已采纳（RFC-0007「租户存储」两条修订，`conventions/error-codes.md` 登记 `MULTITENANCY_CONFLICT_001`）。

## 日期

2026-11-13

## 背景

5.0 安全审查「加固建议」（`plans/5.0-安全审查.md` 第四节）。

- 租户的数据按租户 ID 归属：实体行的 `TenantId`、授予的租户范围、缓存与幂等键里的租户段、对象存储里按租户分的容器与键。
- `ITenantAdministration.RemoveAsync` 只删租户目录里的那一项，不清理这些数据：框架不知道应用把哪些数据放在哪里。
- 删了之后再用同一个 ID 新建，新租户就接手了旧租户留下的全部数据。ID 往往取自客户的名字或域名，被别的客户再次使用并不罕见。

复现：一致性用例 `TenantAdministrationConformance.Remove_RetiresTheId_SoItCannotBeRecreated`，内存与数据库实现都失败：删除之后同一 ID 照常新建。

## 备选

1. **删除租户时清理全部数据**：否决。框架看不到应用的全部存储，清不干净就是假安全。
2. **只在文档里提醒**：否决。管理界面上的「删除、重建」看起来完全正常。
3. **墓碑**：采纳。

## 决策

1. 删除留墓碑：删除的 ID 读不到（`Find` 为无值、`List` 不列出、分片解析不到），再删一次是不存在。
2. 再用 `UpsertAsync` 新建这个 ID，那一项为 `MULTITENANCY_CONFLICT_001`（消息键 `multitenancy.tenant.id_retired`，参数 `tenantId`），同一批里别的项照常。
3. 内存实现：墓碑记在锁里的集合，计入 `MaxTenants`，删了再建不能绕过上限。配置里装载的租户与此无关；进程重启后墓碑随内存数据一起消失。
4. 数据库实现：`TenantRecord` 实现 `ISoftDeletable`（`IsDeleted`、`DeletedAt` 两列），删除是软删除；新建前对读不到的 ID 带 `IncludeDeleted` 再查一次，找到的是墓碑。
5. 确实要释放一个 ID：先清理它的数据，再由运维直接删掉墓碑行。框架不提供释放接口：调用方说不清数据已经清干净。

## 影响

- 破坏性变更：
  - 删了再建同一个租户 ID 的流程会失败，要换一个 ID。
  - `TenantRecord` 多两列，已有的表要加上（SqlSugar 的 `InitTables` 会补列，EF Core 用迁移）。
  - 内存实现的容量：墓碑也占位。
- 公开 API：`MultiTenancyErrors.IdRetired`、`MultiTenancyMessages.TenantIdRetired`、`TenantRecord.IsDeleted`、`TenantRecord.DeletedAt`、一致性用例 3。
