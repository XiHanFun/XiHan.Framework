# ADR-0230 审计记录的资源列收到 512

## 状态

已采纳（`spec/rfcs/0015-auditing.md` 随之修订）。修订 ADR-0036「资源 1024」一项。

## 日期

2026-11-16

## 背景

`Auditing.Database` 的 `AuditRecord.Resource` 声明为 `[StringLength(1024)]`，同时在（`Resource`，`Sequence`）上建索引，用于按资源名精确查询（ADR-0159）。

BasicApp 在 MySQL 与 SQL Server 上建表时，这条索引建不出来：

- MySQL（InnoDB，utf8mb4）一个索引键最长 3072 字节，`varchar(1024)` 按每字符 4 字节算是 4096 字节，建表即 "Specified key was too long"，`audit_record` 整张表建不出来。
- SQL Server 非聚集索引键最长 1700 字节，`nvarchar(1024)` 是 2048 字节，建索引只给警告，之后写入超过 1700 字节的行即失败。

PostgreSQL 与 SQLite 没有这个限制，一致性套件发现不了。

## 备选

1. 资源列收到 512：MySQL 2048 + 8 字节、SQL Server 1024 + 8 字节，都在上限内。
2. 保留 1024，只对资源名的前缀建索引：MySQL 有前缀索引，SQL Server、PostgreSQL 没有同样的写法，各库的索引定义要分开，`EntityIndex` 也表达不了。
3. 另存资源名的哈希并索引哈希：精确查询改为先比哈希，记录多一列，查询与写入都要多算一步。

## 决策

采用备选 1：`AuditRecord.Resource` 改为 `[StringLength(512)]`，索引不变。

资源名 `xrn:<partition>:<service>:<tenant>:<type>/<id>` 没有长度上限（RFC-0008），实际的资源名是前四段加类型与标识，通常不到 100 个字符，512 留了足够的余量。

## 理由

- 一个长度能让同一个记录在 PostgreSQL、MySQL、SQL Server、Oracle、SQLite 上用同一份索引定义，不需要按库分开写。
- 备选 3 为了一个不会出现的长度多加一列、改查询路径，不划算。

## 影响

- 建表变化：新建的 `audit_record` 的 `resource` 是 `varchar(512)`（SQL Server `nvarchar(512)`）。已经按 1024 建好的库（只可能是 PostgreSQL 与 SQLite）照旧可用，不需要迁移。
- 资源名超过 512 个字符的事件写入失败，与以前超过 1024 一样。
- 公开 API、错误码、消息键、配置键不变。
