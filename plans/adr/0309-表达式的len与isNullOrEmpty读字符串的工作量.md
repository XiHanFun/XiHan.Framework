# ADR-0309 工作流表达式的 `len` 与 `isNullOrEmpty` 读字符串的工作量

## 状态

已采纳（RFC-0021「长度与上限」的表里 `len` 读是字符串或数字的实参，`isNullOrEmpty` 只读到能判定为止；`expression-limits.json` 的 `budgets` 改 5 条、补 9 条；.NET 的 `ExpressionRun` 与编译器跟上；Go 一致性模块的回放补两条核对）。

## 日期

2026-11-26

## 背景

ADR-0296 的读取量表把 `len`、`isNullOrEmpty` 放在「不读」里，ADR-0303 改成只读数字，理由是「字符串的文本就是它自己」。上一轮报告在 Release 构建上实测：变量 `s` 是从 JSON 读来的 4194304 个码元的字符串，`len(s)` 在长度以内连写 571 次约 1.3 秒，工作量只有 118995（全是步数）；`isNullOrEmpty(s)` 连写 201 次约 0.4 秒，工作量同样只有步数。

开销在把字符串取出来：.NET 里从 JSON 读来的值是 `JsonElement` 后面的一段 UTF-8，`GetString()` 每次都要解码一遍、分配一个新的字符串（四百万个码元约两毫秒），`len` 拿它数长度，`isNullOrEmpty` 拿它看长度是不是零。两者的情形不同：

- `len` 的结果是 UTF-16 码元数，要走完全文才数得出：JSON 文本里的转义（`\uXXXX`、`\n`）与多字节的 UTF-8 都要逐个看；字符串按 UTF-8 存的语言（Go、Rust、PHP）与按码位存的（Python）同样要逐个码位换算。只有按 UTF-16 存、已经取出来的字符串（.NET、Java、JavaScript 的普通字符串）长度是现成的。
- `isNullOrEmpty` 只要知道有没有第一个码元。各语言取出来的字符串都能在常数时间里判定；JSON 文本里空串只有 `""` 一种写法（转义至少写出一个码元），看原文的长度就够了。全文读取只是 .NET 实现的做法：先写出值的文本，再看长度。

## 备选

1. **`len` 维持不读字符串，只把 .NET 改成不取出全文**：否决。上面第一条：数 UTF-16 码元在多数语言里要扫描全文，.NET 从 `JsonElement` 也拿不到不解码的 UTF-16 长度。开销在每个码元上，与字符串的其他读取同一个单位，就该计入。
2. **`len` 读字符串，口径与算术相同**（「是字符串或数字的实参」）：采纳。字符串记长度，数字仍记它的写法的长度（ADR-0303），容器的长度是元素或成员的个数，不读。
3. **`isNullOrEmpty` 与 `len` 一样读全文**：否决。判定空串不需要全文，读全文的开销是实现造出来的，应当改实现，而不是让规则迁就它；否则「先判空再处理」这样正常的写法读一个百万码元的字符串就记一百万。仓库所有者给的方向是「只读到能判定为止」。
4. **`isNullOrEmpty` 读字符串记 0**：否决。照「只读到能判定为止」：空串看一眼就知道是空的（0），非空的要看到第一个码元才知道不是空的（1）。记 1 与它多长无关，上限之内照样随便用；向量也能分出三种做法——不读（128）、只读第一个码元（129）、读全文（`isNullOrEmpty(j)` 是 1044127）。
5. **`isNullOrEmpty` 读数字维持 ADR-0303 的全文**：否决。ADR-0303 的理由是「数字的文本要先从它的写法读出值再写出来」，这对要文本长度的 `len` 成立；`isNullOrEmpty` 不要文本——数字的文本至少一个字符，总不是空串，看类型就能判定。同一条「只读到能判定为止」下，非空的字符串记 1 而原文四百万位的数字记四百万说不通。布尔同理（以前也是 0）。
6. **原有的「读字符串」一对只改字面量的长度**：做不到。`len(upper(x))` 现在每个码元读两次（`upper` 一次、`len` 一次），工作量每多一个码元跳 2，奇偶与上限对不上：.NET 算出字面量 3402 个码元是 16777215、3403 个是 16777217。改成 `isNullOrEmpty(upper(…)) || …`：`upper` 照旧读全文，`isNullOrEmpty` 只记 1，`j` 与 15 个 `k` 原样保留，字面量 272 个码元正好到上限、273 个超过。「读数字」那一对 `g+g+g+g+len(upper('…'))` 的字面量同样每个码元读两次，奇偶正好对得上，从 506 个改成 253 个、507 个改成 254 个。
7. **另设 `len` 的上限、或按码位计**：否决。计量的单位与拼接、`upper` 相同才能放进同一份上限；按码位计各语言的结果不同（RFC-0021「长度与上限」：长度一律按 UTF-16 码元）。

## 决策

1. **规范**（RFC-0021「长度与上限」的表）：`len`、`isNullOrEmpty` 一行拆成两行——`len` 读是字符串或数字的实参，字符串记长度、数字记它的写法的长度，容器不读；`isNullOrEmpty` 只读到能判定为止：是非空字符串的实参记 1，空串记 0，`null`、布尔、数字与容器不读，并写明实现判定空串时不能取出全文。例子里 `len(k + k)` 由 2097408 改成 4194560（`len` 再读一遍拼出的 2097152 个码元），另加 `isNullOrEmpty(k)` 是 129。状态行、「对应 ADR」与「一致性」的向量表随之改写。改了已写明的行为，MAJOR（`v1.0.0` 之前允许）。
2. **向量**（`expression-limits.json` 的 `budgets`，由 41 条到 50 条，全部期望值由 .NET 算出）：
   - 改 5 条：「读字符串」的一对改成上面第 6 条的写法（272 / 273 个码元，名字改成「upper 读字符串、isNullOrEmpty 只读第一个码元」）；「拼到拼接的上限一次」由 9437696 改成 13632000（名字加上「len 再读一遍拼出的字符串」）；「读数字」的一对改成 253 / 254 个码元。「拼到拼接的上限两次」与「模板里占位的表达式超过」照旧超过，带出的文本不变。
   - 补 9 条：`len(s)` 131、`len(j)` 1044127；`isNullOrEmpty(j)` 129、`isNullOrEmpty('')` 128、`isNullOrEmpty(g)`（原文四百万位的数字）128、`isNullOrEmpty(z)`（1172 个元素的数组）128；`isNullOrEmpty(k)` 用 `||` 连写 201 次 38729（每次两步加 1，读全文的实现在这条上就超过上限）；`len(j)+len('a…')+len(k)×15` 的字面量 1150 个码元正好到上限、1151 个超过。
   - `$comment` 写明 `len` 与 `isNullOrEmpty` 的读法。
3. **.NET**：`ExpressionRun` 删去内部的 `ReadIfNumber`，新增内部的 `ReadEmptiness(JsonValue)`——判定是不是空串、非空的记 1；判定不取出全文：由 `JsonElement` 承载的看原文（`JsonMarshal.GetRawUtf8Value`，带两侧引号，空串正好两个字节），进程内的 CLR 字符串看长度，由 `Guid`、`DateTimeOffset` 等构造、写成 JSON 是字符串的值取它的文本（都很短）。编译器里 `len` 改用 `ReadScalar`；`isNullOrEmpty` 不再先写出值的文本：`null` 与容器看类型与个数，字符串经 `ReadEmptiness`，布尔与数字直接为假（结果与以前相同，放不下的 JSON 数字也是假）。
4. **Go 一致性模块**：这一条没有对应的类型或常量要跟。`rules/workflow_test.go` 的回放核对补两条：以 `len(` 开头、对很长的字符串变量求 `len` 的用例要有正好到上限的与超过的；要有对很长的字符串变量连写 `isNullOrEmpty`、工作量比那个字符串的长度还少的用例。

## 影响

- 公开 API：没有签名变化，没有新的消息键、错误码与配置键。
- 行为（升级须知）：对很长的字符串求 `len` 的表达式以前不计它的长度，现在可能以 `WORKFLOW_VALIDATION_003`（`budget_exceeded`）失败——一次求值里对百万码元的字符串求十几次、对四百万码元的求四次就到上限；正常的字符串每次多记它的长度，远在上限以内。`isNullOrEmpty` 读非空的字符串多记 1，读数字不再记它的写法的长度，结果都不变。迁移与 ADR-0296 相同：在活动里处理这样的数据，或只取需要的部分。
- 性能：同一台机器上，`isNullOrEmpty(s)` 连写 201 次由约 0.4 秒降到 0.06 毫秒；`len(s)` 连写 571 次读到第四次即以 `budget_exceeded` 停下，约 16 毫秒。
- 规范：RFC-0021「长度与上限」的表、例子、状态行与「一致性」；`expression-limits.json`；`conformance/README.md` 的向量表；`rules/workflow_test.go`、`vectors_subsystems.go` 的注释。
- 测试：`ExpressionLimitVectorTests` 回放全部 50 条并核对上面第 4 条的两种用例都在；`ExpressionBudgetTests` 的「`len` 与 `isNullOrEmpty` 读数字不读字符串」换成三条——`len` 对从 JSON 读来与进程内构造的字符串、数字记同样的读取量而不读容器，从 JSON 读来的四百万码元的字符串 `len` 连写 571 次读到第四次就超过，`isNullOrEmpty` 对十一种值（JSON 里的空串、带转义的、很长的，进程内的空串与很长的，`Guid`、原文四百万位的数字、布尔、空数组、对象、`null`）只读到能判定为止、连写 141 次的工作量是步数加 141。
- 六个 SDK：不受影响（不认领 `workflow` 档）。

## 理由

- `len` 与别的读字符串的运算同一口径：开销在每个码元上的，按码元记，不因为「文本就是它自己」而免掉数码元的那一遍。
- `isNullOrEmpty` 的计量照它真正需要读的记：规则描述运算本身要读什么，不描述某个实现碰巧读了什么；.NET 读多了，改的是 .NET。
