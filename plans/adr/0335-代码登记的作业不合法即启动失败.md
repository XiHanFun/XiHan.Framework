# ADR-0335 代码登记的作业不合法即启动失败

## 状态

已采纳。

- 规范：RFC-0013「作业类型登记」写明代码登记的作业不合法时在哪里失败，「调度器 `IJobScheduler`」里 ADR-0321 的那一句与「代码作业写入存储」一段随之改，状态行已改；RFC-0001「孤立的代理项」的表补上代码登记的作业，状态行已改。
- 向量：不变。
- .NET：`Scheduling.Abstractions`。公开签名、错误码、消息键与配置键不变。

## 日期

2026-11-27

## 背景

ADR-0321 让作业与触发器的说明与数据拒收孤立的代理项，代码登记的作业照「同步失败记日志、下一个周期重试」的已有做法处理。第九轮发现这样会卡住：

- 代码登记的作业不合法时，`AddJob` 照收。进入服务状态后首个周期把代码作业写进存储，每个周期都以 `SCHEDULING_VALIDATION_001` 失败、记一条 Warning、下个周期再试，定义不改就永远不会成功。
- 同步按名字逐个写、第一个失败即停，排在它后面的代码作业也一直写不进去，按计划不运行；`ScheduleAsync`、`RestoreAsync`、`UnscheduleAsync`、暂停与恢复都先同步，每一次也都再失败、再记一条日志。
- 不只孤立的代理项：触发器名重复与触发器引用的日历没有登记，代码作业也是这样。

仓库所有者已拍板：启动即失败。能在登记时判定的在登记时抛 `ArgumentException`，只能在宿主启动时判定的在启动时抛 `FrameworkException`，消息写明作业名与原因，不再周期重试；运行时经 `ScheduleAsync` 登记的照旧返回 `SCHEDULING_VALIDATION_001`。

## 备选

1. **按判定的时机分两处**：采纳。
   - 登记时（`AddJob` → `JobRegistry.Add`）：说明与数据有孤立的代理项、触发器名重复。抛出 `ArgumentException`（参数 `definition`），消息 `Job '<名>' is invalid: <原因>.`，与同名重复登记同一处、同一种异常，作业不进登记表。
   - 启动时（`JobSchedulerEngine.StartAsync`，两个实现包的特性启动时调它）：触发器引用的日历没有登记。日历由 `AddJobCalendar` 登记，可以写在 `AddJob` 之后，登记作业的那一刻判定不了。抛出 `FrameworkException`（`SCHEDULING_VALIDATION_001`），消息 `Code-defined job '<名>' is invalid: <原因>.`；内核把它包成特性启动失败（`KERNEL_HOSTING_002`，内层是这个异常），默认的失败策略下应用不启动。
   - 原因与运行时 `ScheduleAsync` 返回的 `reason` 是同一段文本。
2. **启动时把三种都再核对一遍**：采纳。`JobDefinition.Data` 是可变的 `JsonObject`，登记之后才改坏的在这里拦下，不留到同步。代价是每个代码作业多走一遍说明与数据，只在启动时一次。
3. **规则只有一份**：采纳。新增 internal 的 `JobDefinitionRules.FindProblem(definition, calendars)`：孤立的代理项，再按触发器的次序逐个核对名字重复与日历；不给日历时不核对日历。运行时的 `ScheduleOneLockedAsync`、登记与启动都用它，次序与原因与以前的 `ScheduleOneLockedAsync` 相同。
4. **只管孤立的代理项**：否决。触发器名重复与日历未登记卡住同步的方式一样，所有者定的规则是「代码登记的作业不合法即启动失败」。
5. **同步遇到不合法的定义跳过它、接着写后面的**：否决。仍是每个周期记日志的静默兜底，代码里写的作业不运行也没人知道。
6. **启动时连同存储一起写**：否决。写存储要等进入服务状态（RFC-0013：调度器在应用不在服务状态时不按计划运行），存储不可用是暂时的，照旧在周期里重试。
7. **同步里的写入失败（存储不可用）**：照旧记日志、下个周期再试。定义不合法的已在登记或启动时失败，不会走到这里。
8. **级别**：MAJOR（`v1.0.0` 之前允许）。以前照收、只在日志里报的代码作业，现在登记或启动失败。

## 决策

1. **规范**：RFC-0013「作业类型登记」写明两处的失败与消息；ADR-0321 那一句改成代码作业在 `AddJob` 时就按这一条失败；「代码作业写入存储」写明写入失败重试、定义不合法的不会走到这里。RFC-0001 的表同步。
2. **.NET**：
   - 新增 `Jobs/JobDefinitionRules`（internal），说明与数据的孤立代理项判定从 `JobSchedulerEngine` 移过来。
   - `JobRegistry.Add` 在同名检查之前调它（不核对日历）；`JobSchedulerEngine.StartAsync` 在开始轮询之前逐个核对代码作业（核对日历）；`ScheduleOneLockedAsync` 改调它。
   - `AddJob` 的 XML 文档与包 README 写明。

## 理由

- 代码里登记的作业是程序的一部分，不合法是编程错误：越早失败越好查，与同名重复登记、选项不合法一样在装配或启动时报出来。
- 判定的时机由信息什么时候齐决定：说明、数据与触发器名在登记时就齐了，日历要等装配完；两处共用一份规则，原因的文本与运行时相同。
- 存储不可用是暂时的，周期重试仍然合理；定义不合法重试多少次都不会好。

## 影响

- **公开 API**：签名不变。`SchedulingServiceCollectionExtensions.AddJob`（Stable）的行为收窄：不合法的定义抛出 `ArgumentException`（以前照收）。`JobSchedulerEngine.StartAsync`（Preview）可能抛出 `FrameworkException`。
- **程序集体积**：不涉及 Primitives 与 Kernel。
- **对已有部署与代码的行为变化（升级须知）**：
  - 代码登记的作业的说明与数据有孤立的代理项、触发器名重复时，`AddJob` 抛出 `ArgumentException`，应用装配失败；以前照收，启动后每个周期记一条 Warning（`Writing code-defined job '…' to the store failed with 'SCHEDULING_VALIDATION_001'; retrying next cycle.`），按名字排在它后面的代码作业也写不进存储。
  - 触发器引用了没有登记的日历时，调度的实现包特性启动失败（内层 `SCHEDULING_VALIDATION_001`），默认的失败策略下应用不启动。
  - 迁移：按异常消息里的作业名与原因改代码定义，或补上 `AddJobCalendar`。运行时 `ScheduleAsync` 的行为不变。
- **规范**（规范工作区已提交）：RFC-0013、RFC-0001。
- **六个 SDK**：没有调度，不受影响。
- **测试**：
  - `CodeJobValidationTests`（`Scheduling.InMemory.Tests`）：登记时四种不合法（说明、数据里数组中对象的成员名、触发器的数据、重复的触发器名）都抛出、消息与参数名、什么都没登记；日历未登记时启动失败，内外两层的错误码与消息；登记之后才改坏的数据在启动时失败；日历登记在作业之后照常启动、写进存储。
  - 去掉两处核对时前三条失败（实测），第四条照过。
  - 运行时的 `JobDefinitionSurrogateTests` 与一致性套件照过。
- **文档**：`Scheduling.Abstractions` 的 README 已同步；文档站与更新日志待改。
