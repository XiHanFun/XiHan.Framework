# ADR-0081 只读工作单元里的写入是 500 类缺陷；软删除实体的唯一索引改为部分唯一索引

## 状态

已采纳（`spec/rfcs/0005-persistence.md`、`spec/rfcs/0011-operations.md`、`spec/rfcs/0021-workflow.md` 与 `spec/conventions/error-codes.md` 随之修订）。修订 ADR-0073 第一节的错误码种类、ADR-0077 只读调用里的错误码、ADR-0072 软删除实体的唯一索引。

## 日期

2026-11-01

## 一、只读工作单元里的写入是 500 类缺陷

### 背景

- ADR-0073 让只读操作（动词 `get` / `list`，或 `ReadOnly = true`）开只读工作单元，写入以新码 `PERSISTENCE_DENIED_001` 拒绝（HTTP 403、gRPC `PermissionDenied`，熔断不计数）。三处产生它：三个 Provider 的仓储写入（返回结果并把工作单元记为失败）、EF Core 与 SqlSugar 工作单元的 `EnsureTransactionAsync`（抛出、由 Transaction 阶段转为结果）、工作流加入只读事务时的 `IWorkflowTransaction.EnsureWritable`（ADR-0077，取锁、执行活动之前）。
- 403 让客户端与网关把它当作"已认证但没有权限"：前端走无权限提示，网关可能按越权统计，运维的 5xx 告警看不到它。可它与权限无关，换一个有权限的用户照样失败——是只读操作的实现写了数据，属于代码缺陷。
- 用户决定（第三批第 9 条）：改成 500 类错误；同一作用域的嵌套调用维持拒绝（`PERSISTENCE_VALIDATION_002`，行为不变）。

### 备选

错误码：

1. 保留 `PERSISTENCE_DENIED_001` 的编号、只改含义——不成立：错误码的 KIND 段就是 HTTP / gRPC 映射的依据（`conventions/error-codes.md`、`protocol/http.md`），`DENIED` 段的码不可能映射成 500。
2. 新码 `PERSISTENCE_UNEXPECTED_001`，撤销 `PERSISTENCE_DENIED_001`。
3. 不转结果，让异常与拒绝都落到 Observe 阶段的 `KERNEL_UNEXPECTED_001`。

撤销的旧码：保留登记标为"已撤销"（双轨），或直接删除登记。

### 决策

- 新码 `PERSISTENCE_UNEXPECTED_001`，常量仍是 `PersistenceErrors.ReadOnly`（名字说的是"只读拒绝写入"，没变），值从 `PERSISTENCE_DENIED_001` 改为它。仓储写入、`EnsureTransactionAsync`、`EnsureWritable` 三处都用 `Error.Unexpected` 构造；中间件仍只捕获这一个码、回滚并转为同码结果。
- `PERSISTENCE_DENIED_001` 从错误码表删除，不保留兼容：尚未发布，编号规则"一经发布不复用"约束的是已发布的码，没有发布过就没有要保护的客户端，留一个"已撤销"的码只会让人以为两个都会出现。
- 消息键沿用 `persistence.unit_of_work.read_only`，十种语言的文案补一句"这是操作实现的缺陷"。
- 映射：HTTP 500、gRPC `Internal`、命令行按 UNEXPECTED 的退出码；熔断按操作 ID 计数（RFC-0004 计 UNAVAILABLE / TIMEOUT / UNEXPECTED）。
- 不变：同一服务作用域里再经管道的嵌套调用仍以 `PERSISTENCE_VALIDATION_002` 结束内层；只读工作单元不开事务、写入时拒绝、拒绝即把工作单元记为失败、处理器忽略也以同一错误结束；嵌套调用各开自己的工作单元、只读不传播。

### 理由

- 500 才是缺陷的位置：告警、错误率与 SLO 按 5xx 统计，只读操作写数据这种上线后必须修的问题应当出现在那里，而不是混进 403 的越权统计；客户端也不会把它当成权限不足去提示用户换账号。
- 转为同码结果而不是交给 Observe 阶段：状态码同为 500，但 `PERSISTENCE_UNEXPECTED_001` 与本地化文案直接说明是只读写入，`KERNEL_UNEXPECTED_001` 只能说"发生未处理异常"；而且仓储写入本来就是结果，三处产生同一个码，排查只认一个码。
- 计入熔断可以接受：熔断按操作 ID 各一份，有缺陷的只读操作每次都会失败，熔断只挡住它自己；没有为它配置熔断的操作不受影响。ADR-0073 当时以"熔断会把确定性缺陷当成下游故障"否决 UNEXPECTED，这条在按操作隔离的熔断下代价有限，由用户的决定取舍。

### 影响

- 行为（BasicApp 升锁要改的）：只读操作里的仓储写入、`EnsureTransactionAsync`、工作流写入，从 403 `PERSISTENCE_DENIED_001` 变为 500 `PERSISTENCE_UNEXPECTED_001`；gRPC 从 `PermissionDenied` 变为 `Internal`；配置了熔断的只读操作，这类失败计入熔断。管道外以 `UnitOfWorkOptions(IsReadOnly: true)` 开的工作单元里写入，同样返回新码。
- 排查：日志与响应里的 `code` 是 `PERSISTENCE_UNEXPECTED_001`、`type` 是 `urn:xihan:error:PERSISTENCE_UNEXPECTED_001`；找到响应对应的操作 ID，它是只读的（动词 `get` / `list` 或声明了 `ReadOnly = true`），在它的处理器（及它在同一作用域里调用的服务）里找新增、更新、删除、`EnsureTransactionAsync` 或工作流的发起 / 办理。改法与 ADR-0073 相同：去掉只读、换非只读的动词，或把写入放进新服务作用域里的另一次调用。客户端或网关里按 `PERSISTENCE_DENIED_001` / 403 判断的代码要删掉。
- 公开 API（都在 Unshipped）：`PersistenceErrors.ReadOnly` 的值变化，签名不变。
- 文档：RFC-0005「只读工作单元」与一致性一段、RFC-0011 只读一条、RFC-0021「只读的调用」、错误码表；各持久化包与工作流包的 README，docs 的工作单元、持久化、操作、工作流指南与相关包页面。

## 二、软删除实体的唯一索引改为部分唯一索引

### 背景

- ADR-0072 让软删除实体（`ISoftDeletable`）的唯一索引末尾自动带 `IsDeleted`：未删除的行之间唯一，但同一业务键最多一行已删除——删除、重建、再删除同一个键时，第二次删除撞上索引、返回 `PERSISTENCE_CONFLICT_003`。当时以"MySQL 与 SqlSugar 的建索引入口都不支持部分索引"否决了部分索引。
- BasicApp 自己的 `ActiveUniqueIndex` 已经是部分唯一索引（`ux_<表>_<列>… WHERE is_deleted = false`，建表之后以原生 SQL 补建，只支持 PostgreSQL 与 SQLite）。
- 用户决定（第三批第 11 条）：改成只约束未删除行的部分唯一索引；SqlSugar 与 EF Core 都做；不支持部分索引的数据库在启动时明确报不支持，不静默退化。

### 备选

1. 维持 ADR-0072（删除标记进列）。
2. 支持的数据库建部分唯一索引，其余数据库退化成删除标记进列——静默退化，同一份声明在不同数据库上语义不同。
3. 在 MySQL、Oracle 上用函数索引或生成列模拟（`UNIQUE (Code, (CASE WHEN IsDeleted = 0 THEN 0 ELSE Id END))` 之类）——各库写法不同、版本要求不同（MySQL 8.0.13+），本机验证不了，也绕开了 SqlSugar 的建表流程。
4. 支持的数据库建部分唯一索引，其余数据库启动失败；应用要在那些数据库上唯一约束，就在声明里显式写 `IsDeleted`（普通唯一索引）。

EF Core 写条件 SQL 要知道 Provider，而 `ModelBuilder` 不知道：给 `ApplyPersistenceConventions` 加 `DatabaseFacade` 参数；经 DbContext 选项扩展登记约定插件（`IConventionSetPlugin`），在模型定型时按 Provider 补条件；在索引上加注解、由别处翻译。

### 决策

取 4。

- 契约：`EntityIndex.ExcludesDeleted`（软删除实体的唯一索引、声明的列里没有 `IsDeleted` 时为真）；`Properties` 就是声明的列，不再自动追加 `IsDeleted`；名字规则不变（仍按声明的列推出，所以名字不变、定义变了）。声明里显式写了 `IsDeleted` 的是普通唯一索引，不加条件。
- 支持的数据库：PostgreSQL、SQLite、SQL Server。SqlSugar 支持的其余类型逐个核对：MySQL / MySqlConnector / TiDB / OceanBase / Doris / GoldenDB / TDSQL 是 MySQL 系，没有部分索引；Oracle / OceanBase Oracle 模式 / TDSQL Oracle / 达梦 是 Oracle 系，没有部分索引；ClickHouse、QuestDB、TDengine 没有唯一索引；DuckDB、Access、DB2、HANA、Xugu、GBase、神通没有部分索引或无从核对；人大金仓、openGauss、GaussDB、瀚高、Vastbase、PolarDB、TDSQL PG 源自 PostgreSQL、语法上可能支持，但没有验证环境；ODBC 与自定义方言不知道是什么库——这些一律按不支持处理。
- SqlSugar：部分唯一索引不交给 `SugarIndexAttribute`（它写不出条件，交给它就成了约束已删除行的普通唯一索引），`ConfigureIndexes` 跳过它们。新增公开的 `SqlSugarConventions.InitTables(client, params Type[] entityTypes)`：先核对数据库类型（不支持就在建任何表之前抛出），再分普通与分表实体建表，之后按方言补建部分唯一索引——PostgreSQL、SQLite `CREATE UNIQUE INDEX IF NOT EXISTS … WHERE "IsDeleted" = false / 0`（PostgreSQL 上名字转小写，与 SqlSugar 建出的其他索引一致），SQL Server 查 `sys.indexes`（名字加表）后 `CREATE UNIQUE NONCLUSTERED INDEX … WHERE [IsDeleted] = 0`，键含可空列时另加 `IS NOT NULL`；表名与列名用 SqlSugar 自己的转义（`InstanceFactory.GetSqlBuilderWithContext`）。特性开着 `InitTables` 时按落点逐个连接调用它；特性启动时不论是否建表，都核对已登记的软删除实体所落连接的数据库类型，不支持即以 `PERSISTENCE_UNAVAILABLE_008` 中断启动（一次列出全部）。唯一键重复的核对把部分唯一索引一并算上，只比较未删除的写入项与未删除的行。
- EF Core：`ApplyPersistenceConventions(this ModelBuilder, DatabaseFacade database)`，按 `database.ProviderName` 给部分唯一索引加 `HasFilter`——Npgsql `"IsDeleted" = false`、SQLite `"IsDeleted" = 0`、SQL Server `[IsDeleted] = 0`（键含可空列另加 `IS NOT NULL`），列名取调用时的映射；其余关系型 Provider 建模时抛出 `FrameworkException(PERSISTENCE_UNAVAILABLE_008)`，一次列出全部；非关系型 Provider 不加条件。特性启动时在独立作用域里取一次模型，建模错误在启动时失败。生成器的 `ApplyGeneratedEntities` 在引用了 `Persistence.EntityFrameworkCore` 时也多收一个 `DatabaseFacade database` 并转交。唯一键重复的核对按名字认出约定建的部分唯一索引，只比较未删除的行。
- `PERSISTENCE_CONFLICT_003` 的含义去掉"软删除撞上同一键已删除的行"（只在列里显式写了 `IsDeleted` 时还会发生）；`PERSISTENCE_UNAVAILABLE_008` 增加"数据库不支持部分唯一索引"一种情形。

### 理由

- 部分唯一索引正是想要的语义：唯一性只关心还在用的行，删除永远不该因为历史上删过同一个键而失败。BasicApp 的 `ActiveUniqueIndex` 已经这样做并在用。
- 启动失败而不是退化：退化会让同一份声明在 MySQL 上又回到"第二次删除失败"，或者干脆没有唯一约束——两种都是事后才发现的静默差异。显式写 `IsDeleted` 让应用自己在声明里选择普通唯一索引，选择看得见。
- 没验证过的 PostgreSQL 衍生库按不支持处理：语法相近不等于建索引、`IF NOT EXISTS`、布尔字面量与 SqlSugar 的转义都一致；验证之后放进支持名单只是改一处。
- `SqlSugarConventions.InitTables` 公开：框架之外建表的地方（租户独立库、迁移工具）同样需要部分唯一索引，只给特性内部用就会在租户库里悄悄缺一个唯一约束；只有一个入口，应用不必记两步。
- 启动时核对、而不只在建表时：生产库不开 `InitTables`，由迁移脚本建表；不在启动时核对，就要等写入出现重复数据才发现唯一约束根本建不出来。
- EF Core 取 `DatabaseFacade` 参数：约定插件只在经本特性建的 DbContext 上生效，设计期工具（`dotnet ef migrations`）建出的上下文没有它，迁移里就会悄悄少了条件；注解会进模型快照与迁移。参数显式、`OnModelCreating` 里总有 `Database` 可传，设计期与运行期一致。启动时取一次模型，让不开 `EnsureCreated` 的生产配置同样在启动时暴露建模错误。
- SQL Server 加 `IS NOT NULL`：它的唯一索引把 NULL 当作相等，显式写了条件后 EF Core 不再自动加可空列的过滤；补上后含 NULL 的键在各数据库上都不受约束，与唯一键重复的核对一致。

### 影响

- 行为：软删除实体的 `[EntityIndex(IsUnique = true)]`：同一业务键删除、重建、再删除不再返回 `PERSISTENCE_CONFLICT_003`；未删除的同键行照样冲突。
- 启动期新增失败：SqlSugar 已登记的软删除实体声明了唯一索引（列里没有 `IsDeleted`），而所落连接不是 PostgreSQL / SQLite / SQL Server 时启动失败（不论是否开着 `InitTables`），`SqlSugarConventions.InitTables` 在建表之前抛出；EF Core 用其余关系型 Provider 时建模即失败；EF Core 特性启动时会建一次模型，任何 `OnModelCreating` 里的错误从"第一次使用时"提前到启动时。
- 公开 API（都在 Unshipped）：新增 `EntityIndex.ExcludesDeleted`、`SqlSugarConventions.InitTables`；`ApplyPersistenceConventions(ModelBuilder)` → `ApplyPersistenceConventions(ModelBuilder, DatabaseFacade)`（调用写 `modelBuilder.ApplyPersistenceConventions(Database)`）；生成的 `ApplyGeneratedEntities(ModelBuilder)` → `ApplyGeneratedEntities(ModelBuilder, DatabaseFacade)`（引用了 `Persistence.EntityFrameworkCore` 时）。
- 表结构：框架自带的表（发件箱、审计、授予、翻译、调度、工作流、租户目录）没有软删除实体，索引名与定义都不变，BasicApp 的基线不因框架表重新生成。应用自己的软删除实体：索引名不变，定义从（列, `IsDeleted`）变为（列）`WHERE IsDeleted = false`；`InitTables` 按名字跳过已有索引，此前的预览建出的旧索引要手动删掉再建；EF Core 迁移会表现为删索引、重建带条件的索引。
- 测试：SqlSugar 在 SQLite、PostgreSQL、SQL Server 上验证部分唯一索引（已删除的同键任意多行、未删除的同键冲突、再建一次不重复建），仓储删除同一键三轮不冲突、未删除的同键返回 `PERSISTENCE_CONFLICT_003`（SQLite、PostgreSQL），MySQL 上 `InitTables` 与特性启动失败；EF Core 在 SQLite 上验证 `HasFilter` 与仓储行为，Npgsql / SQL Server 的条件文本与不支持的 Provider、特性启动失败经内部入口验证。SQL Server 的用例要 `XIHAN_TEST_SQLSERVER`，CI 不提供，跳过。

> 修订（2026-11-01）：CI 起了 SQL Server 服务容器，`XIHAN_TEST_SQLSERVER` 的用例在 CI 里真跑，见 ADR-0084 第五节。
