# ADR-0261 消息代理的投递尝试收成一处

## 状态

已采纳（`Messaging.Abstractions` 新增 `MessageDeliveryAttempt`、`MessageDeliveryOutcome` 与 `DeliveryDisposition`，`Preview`；内存、RabbitMQ、Kafka、Redis 四个代理改用它，这四个包的公开面不变；RFC-0009「投递」第 3、5 条补了细则）。

## 日期

2026-11-24

## 背景

- 四个代理（`Messaging.InMemory`、`Messaging.RabbitMQ`、`Messaging.Kafka`、`Messaging.Redis`）各写了一份「收到一条消息之后」的骨架：
  - 等应用进入服务状态（RFC-0009「投递」第 5 条）。
  - 把投递交给 `MessageDispatch` 一次，把结果归类：成功、返回失败、抛出异常、被停止取消。
  - 失败之后按尝试号、`MaxAttempts` 与订阅方式决定去向：重投、竞争订阅进死信、广播订阅丢弃。
  - 记死信或广播丢弃的日志。
- 各代理真正不同的只有与中间件相关的动作：内存代理重新入队，RabbitMQ 重新发布再确认，Kafka 原位重试、提交或回退位点，Redis 原位重试、`XCLAIM` 与 `XACK`。
- 四份里相同的部分：
  - 失败后的判定等价（尝试号小于 `MaxAttempts` 重投，否则竞争进死信、广播丢弃）。
  - 死信与广播丢弃两条日志的模板逐字相同。
  - 派发抛出的异常都转成 `MESSAGING_UNEXPECTED_001`，把异常消息写进 `reason`，异常本身不记日志。
- 副本之间已经分叉：
  - **停止期间的失败**：只有 Redis 不重试、不进死信（RFC-0009 的 Redis 一节写了）。另外三家只接住「令牌已取消时的取消异常」，而真实的派发经管道，`DeadlineMiddleware` 把处理器的取消写成 `KERNEL_CANCELLED_001` 的失败结果返回、不抛异常，这个分支在真实路径上到不了，被取消的处理器算成一次失败：
    - 内存代理以下一次尝试号重新入队；赶上最后一次尝试，竞争投递进死信列表、广播投递被丢弃。
    - Kafka 接着原位重试（令牌已取消，处理器立刻再失败），到上限把消息发布到死信主题并提交位点。这与「流」第 2 条「停止时未完成的消息不提交，重启后重新投递」相反。
    - RabbitMQ 的重新发布（重试与死信）在取发布锁时就因令牌已取消而中止，原消息没有被确认，后果只在日志：赶上最后一次尝试会先记一条「已进死信」或「广播已丢弃」的警告，而消息并没有进死信。广播投递到上限的那次确认同样带着已取消的令牌交给客户端；它发不发得出去都不改变结果，广播队列随连接删除。
  - **等服务状态的时机**：内存代理与 RabbitMQ 的每次尝试都是重新收到一遍，每次都等。Kafka 与 Redis 只在一条消息的第一次尝试之前等，原位重试不再等。特性按逆拓扑序逐个停止，应用进入排空（`Draining`）到消息特性收到停止信号之间有一段时间；这期间失败过一次的消息接着原位重试，管道以 `KERNEL_HOSTING_004` 拒绝调用，几次空转把尝试次数用完，消息进死信（Kafka 还提交了位点）。
  - **内存代理丢投递**：从队列取出、还在等服务状态的投递，停止时随取消异常离开循环，没有放回队列。
- 这些差异没有哪一处是有意为之。派发抛出的异常四家一致，但与别处的规则不一致：ADR-0115 与 ADR-0259 定下 `reason` 只写异常类型的全名、完整异常进日志。经管道的处理器异常由 `ObserveMiddleware` 记日志；到代理这里的是管道之外的异常（建作用域失败、应用不在服务状态），原先没有任何地方能看到它，只剩最后那条带错误码的死信日志。

## 备选

1. **留在各包，只把分叉修齐**：否决。四份骨架仍在，下一个代理 Provider 会带来第五份。
2. **基类或模板方法**（代理继承一个带消费循环的基类）：否决。四个消费循环的形状不同：内存代理每主题一条通道，RabbitMQ 是客户端回调，Kafka 是阻塞取消息的专用线程加位点回退，Redis 是轮询加回收。共同的只有「一次尝试」这一段。
3. **放进各包共享的内部文件，或给 Provider 开 `InternalsVisibleTo`**：否决。`src` 下没有链接文件的机制，友元要求确切版本引用（ADR-0134、ADR-0254 备选 1）。
4. **并进 `MessageDispatcher`**（加静态方法，或让派发直接返回了结方式）：否决。`MessageDispatcher` 是处理器一侧的入口，把投递变成一次内核调用；代理拿到的是 `MessageDispatch` 委托而不是它，测试与一致性套件都用委托打桩。了结方式是代理一侧的判定。改 `MessageDispatch` 的返回类型则是破坏 `Stable` 契约。
5. **只收归类与判定，等服务状态留在各代理**：否决。等的时机正是分叉点；收进来之后每次尝试都等，原位重试的代理不用各自记得。
6. **结论里只给错误码字符串**：否决。Redis 的死信条目与日志只要错误码，但内部错误与参数丢了就找不回来；结论带整个 `Error`。
7. **停止期间的失败只认 `KERNEL_CANCELLED_001`**：否决。处理器或中间件可以把取消换成别的错误，认错误码还会再漏。与 ADR-0259 一样只认令牌，代价见「影响」。
8. **被管道以 `KERNEL_HOSTING_004` 拒绝的派发也不算一次尝试**：这一批不做。四家一致、规范没写；只在「查看服务状态」与「管道自己的检查」之间状态刚好翻转时发生，代价是一次尝试。
9. **无法解码的消息也收进来**：这一批不做。它没有信封，不是一次投递；三家的日志按介质措辞不同（队列、主题、流），内存代理没有这条路径。
10. **日志记在共用类型自己的类别下**：否决。记在调用方传进来的 `ILogger` 上，类别仍是各代理自己的，按代理过滤日志的办法不变（同 ADR-0259 备选 7）。

## 决策

1. `XiHan.Framework.Messaging.Abstractions.Handlers` 新增三个类型（`Preview`）：
   - `DeliveryDisposition`：一次尝试之后怎么了结这条投递。`Abandon`（0）、`Complete`、`Retry`、`DeadLetter`、`Discard`。
   - `MessageDeliveryOutcome`：结论，带 `Disposition` 与失败的 `Error`。`default` 是 `Abandon`、没有错误：没有结论的投递不会被当成已处理而确认掉。
   - `MessageDeliveryAttempt`：静态类，两个方法。`RunAsync(dispatch, delivery, options, app, logger, cancellationToken)` 投递一次并给出结论；`Exhausted(delivery, error, logger)` 给出用完尝试次数时的结论。
2. `RunAsync` 的规则只有一份：
   - 每次尝试之前等应用进入服务状态：每 10 毫秒查看一次，直到进入或令牌取消。
   - 派发一次。返回成功即 `Complete`，令牌是否已取消不论：处理完的要确认，否则重启后再投一次。
   - 返回失败（含 `default` 结果）与抛出异常都是一次失败的尝试。抛出的异常转成 `MESSAGING_UNEXPECTED_001`：`reason` 只写异常类型的全名；`FrameworkException` 写它的错误码，它转成的错误留作内部错误。完整异常经 `logger` 记一条警告。
   - 失败之后尝试号小于 `MaxAttempts` 即 `Retry`，否则按 `Exhausted` 了结。尝试号由代理给出，已经超过上限（RabbitMQ 消息头里的数，调小了上限之后）同样按用完处理。
3. 取消只认令牌，结论是 `Abandon`，不算一次失败：
   - 令牌已请求取消时抛出的 `OperationCanceledException`（等服务状态时，或处理器里）。
   - 令牌已请求取消时返回的失败或抛出的其他异常。
   - 令牌没有取消时的 `OperationCanceledException`（处理器自己的超时）是一次失败。
4. `Exhausted`：竞争订阅是 `DeadLetter`，广播订阅是 `Discard`，各记一条警告；`error` 可以为空，日志里记 `?`。`RunAsync` 在最后一次尝试失败时调用它；代理不经派发就要了结时直接调用。
5. 日志三条，都记在调用方的 `logger` 上：
   - 死信与广播丢弃：模板与原先四份逐字相同。
   - 新增 `Dispatching message {MessageId} on topic {Topic} threw on attempt {Attempt}.`，带异常。
6. 四个代理只把结论翻译成自己的动作：

   | 结论 | 内存 | RabbitMQ | Kafka | Redis |
   | --- | --- | --- | --- | --- |
   | `Complete` | 计一次成功投递 | `basic.ack` | 竞争订阅提交位点，广播订阅不提交 | `XACK` |
   | `Retry` | 以下一次尝试号入队尾 | 以下一次尝试号定向发回所消费的队列，确认后 `basic.ack` | 原位进行下一次尝试 | `XCLAIM` 给自己后原位进行下一次尝试 |
   | `DeadLetter` | 进有界的死信列表 | 发布到死信队列，确认后 `basic.ack` | 发布到死信主题，落盘后提交位点 | `XADD` 到死信流（带 `attempt` 与 `error`），应答后 `XACK` |
   | `Discard` | 没有动作 | `basic.ack` | 没有动作，不提交 | `XACK` |
   | `Abandon` | 按原尝试号放回队列，消费循环结束 | 不确认 | 以取消异常抛出：不提交位点，消费循环退出；重放把取消交还调用方 | 不确认，条目留给回收 |

7. 保留的差异，都是有意为之：
   - 内存代理的重投入不了队（队列已满）时调用 `Exhausted` 了结：队列有界，等位置会卡住这个主题唯一的消费者。
   - Redis 回收来的条目投递次数已超过上限时不派发，直接调用 `Exhausted`（没有错误可带）：投递次数记在消费组的待确认列表里，认领一次加一，超过上限说明已经投过上限次。RabbitMQ 的尝试号只在重新发布时加一，消息头里的数就是这一次的尝试号，照常派发。
   - 被放弃的投递再到达时的尝试号由代理决定：内存代理与 RabbitMQ 仍是原来的；Kafka 的原位计数不落盘，重启后从 1 起；Redis 的回收让投递次数加一。
   - 无法解码的消息仍由 RabbitMQ、Kafka、Redis 各自处理（备选 9）。

## 理由

- 「什么算一次失败的尝试」放在一处，代理就没有机会再写出第二种过滤条件。三家「接住取消异常」的分支看着没错，只是真实的派发根本不抛这个异常；这种错靠逐份审查很难发现。
- 等服务状态与派发放进同一个方法，「每次尝试之前都等」对重新收到一遍的代理是原样，对原位重试的代理补上了缺口，不需要各自的循环知道这件事。
- `default` 的结论是不了结：任何漏掉赋值的路径最坏是多投一次，不会把没处理的消息确认掉。
- 异常消息是处理器或驱动写的，带什么不由框架决定。类型全名足够对上日志里的那一条，错误码是框架自己定的常量。

## 影响

- **停止时被取消的处理器不再算一次失败**：
  - 内存代理：原先以下一次尝试号重新入队，赶上最后一次尝试进死信列表或被丢弃；现在按原尝试号放回队列。
  - Kafka：原先接着原位重试到上限、把消息发布到死信主题并提交位点；现在不重试、不进死信、不提交，重启后重新投递。重放（`ReplayAsync`）里调用方取消时原先同样走到死信，现在抛出取消。
  - RabbitMQ：竞争投递原先也没有被了结（重新发布在取发布锁时中止），变化只在日志：最后一次尝试上不再记「已进死信」或「广播已丢弃」的警告。广播投递到上限时原先还会带着已取消的令牌调用一次确认，现在不调用。
  - Redis：不变，规则移到共用的一处。
- **停止期间真正的业务失败也不算**：只认令牌的代价。处理器在停止信号到来的同时返回了业务失败，这次不计，消息重新投递后再失败一次才计。投递本来就是至少一次。
- **应用排空期间不再原位重试**（Kafka、Redis）：原先尝试次数被空转掉、消息进死信；现在等在服务状态上，停止信号到来即放弃。
- **内存代理不再丢投递**：从队列取出、还在等服务状态的投递，停止时放回队列。消费循环在放弃一条投递后正常结束，原先以取消异常结束；`StopAsync` 两种都接得住。
- **Redis 回收来的已超上限的条目不再等服务状态**：原先先等应用进入服务状态再写死信流；现在直接写。不执行处理器，与应用的状态无关。
- **Redis 的消费循环在停止时**：还在等服务状态的条目原先以取消异常离开循环，现在与被取消的处理器一样返回、不确认。回收途中返回时循环会再取一批新条目才退出，这一批留在本消费者的待确认列表里由别的实例回收；被取消的处理器原先就是这条路径。
- **派发抛出的异常**：
  - `reason` 由异常消息变成类型全名或框架错误码。这个错误原先不出代理，只有它的错误码进日志与 Redis 的死信条目，错误码不变。
  - 每次抛出多一条警告，带完整异常，记在各代理的日志类别下。
- **公开面**：新增三个类型（`Preview`）。四个 Provider 包的 `PublicAPI` 文件不变。
- **自写 `IMessageBroker` 的 Provider**：把自己的「派发、归类、判定」换成 `MessageDeliveryAttempt.RunAsync`，按 `Disposition` 翻译；不改也能通过一致性套件，但停止与排空期间的行为要自己对齐。
- **测试**：共用的一处在 `Messaging.Abstractions.Tests` 覆盖；内存、Kafka、RabbitMQ 的翻译各有不需要中间件的用例（打桩的生产者、消费者与通道）；Redis 新增打桩数据库上的用例，覆盖新条目的投递，回收与投递次数仍只在真实 Redis 上验证。
- **规范**：RFC-0009「投递」第 3 条原先没有写停止期间的失败，第 5 条没有写「每次尝试之前」。已把 Redis 一节里「停止期间的失败不重试、不进死信」提到「投递」作为全部代理的规则，并写明取消只认令牌、抛出的异常怎么转成错误、Redis 回收到的已超上限条目不等服务状态。
