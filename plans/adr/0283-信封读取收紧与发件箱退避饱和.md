# ADR-0283 信封读取收紧与发件箱退避饱和

## 状态

已采纳（RFC-0009「信封」「发件箱」已修订，向量 `messaging/cloudevents-envelopes.json` 与 `messaging/outbox-backoff.json` 已补；`Messaging.Abstractions` 的 `CloudEventsFormat` 与 `OutboxOptions.RetryDelayAfter`、`Protocols.CloudEvents` 的 binary 模式已改；原语层新增 `TimestampText`，内核的 `JsonText` 公开）。

## 日期

2026-11-24

## 背景

ADR-0277 给 `messaging` 档补向量时，把正文与 .NET 对不上的地方列成了一张「待定」的表（它的「影响」里「正文与 .NET 的出入」），其中 RFC-0009 有四行。这四行都是「读得比规范宽」或「算得比规范窄」，各语言 SDK 没法照着 .NET 实现：

1. **`time` 用通用的日期解析**。`CloudEventsFormat.Decode` 用 `DateTimeOffset.TryParse`：
   - 空格代替 `T`、没有秒、只有日期、偏移不带冒号（`+0800`、`+08`）、首尾带空白、小数点写成逗号、超过九位的小数、HTTP 日期（RFC 1123）与 `01/02/2026 03:04:05` 都读得出。
   - 没有偏移的时间按**本机时区**读：同一份文档在 UTC 的机器上与在 `+08:00` 的机器上读出相差八小时的两个时刻。
   - 比 100 纳秒细的小数四舍五入，`9999-12-31T23:59:59.999999999Z` 进位后溢出、读不出；偏移超过 ±14:00 的（文法允许到 ±23:59）因为 `DateTimeOffset` 装不下而读不出。
   - 这与 ADR-0276 处理的 `xihan-deadline` 是同一类问题，那边已经定了一条文法（RFC-0003 规则 8）。
2. **`data_base64` 而没有 `datacontenttype`**。文档不写内容类型时缺省 `application/json`，数据却在 `data_base64` 里，读出来是「内容类型为 JSON 的非 JSON 字节」。这个信封读得出、写不回：`Encode` 以「声明为 JSON 的数据不是合法 JSON」抛出。RabbitMQ 的重投与死信要把读出的信封再写一遍，正好踩在这上面。
3. **`data` 与 `data_base64` 同时出现、扩展属性的非字符串值、重复的成员**规范没有写：
   - 两个数据成员都在时 .NET 读 `data`、不报错（CloudEvents 的 JSON 格式里两者互斥）。
   - 扩展属性的数字与布尔保留 JSON 原文，`null`、对象与数组读成空字符串。
   - 重复的成员取最后一个：信封不过 RFC-0001「JSON 文本」的共同检查，而 Result 与 Error 的线上编码、操作载荷与清单都过。`{"id":"a",…,"id":"b"}` 读成 `b`，孤立的代理项转义（`"\ud800"`）读成 U+FFFD。
4. **发件箱的退避把指数截在 30**。`OutboxOptions.RetryDelayAfter` 写的是 `RetryDelay × 2^min(次数 − 1, 30)`，用浮点数算。`MaxRetryDelay` 大于 `RetryDelay` 的 2 的 30 次方倍时（1 毫秒与 30 天），间隔停在 `RetryDelay × 2^30`，到不了上限；正文写的是「不超过 `MaxRetryDelay`」，没有指数的上限。Go 一致性模块的 `rules.OutboxRetryDelay` 一直照正文算，向量的用例都落在两者一致的范围里，所以没有暴露。

写出一侧有两处与新的读取规则冲突，是这次才看到的：

- 扩展属性名的文法（`^[a-z0-9]{1,20}$`）收得下 `id`、`source`、`type`、`time`、`subject`、`data`、`specversion`、`datacontenttype`。带着这样一个扩展的信封写出来是重复的成员，读回时扩展的值顶掉规范属性（`id` 变成扩展的值）。
- `Encode` 把 JSON 数据解析后原样嵌进文档，数据里重复的成员、孤立的代理项转义都照写；嵌套到 64 层的数据让文档成为 65 层，序列化器抛出的是 `JsonException`，不是契约说的 `FrameworkException`。

## 备选

1. **`time` 留一条回退**（先按文法读，读不出再交给通用解析）：否决。回退就是没改，「没有偏移按本机时区读」还在。
2. **读不出的 `time` 当作没有**（像 `xihan-deadline` 那样）：否决。截止时间是可选的提示，丢掉它调用照常；`time` 是事件的属性，悄悄丢掉会让处理器拿到一个没有发生时间的事件。CloudEvents 也要求属性值合法。按信封不合法处理，走已有的「无法解码」（竞争订阅进死信、广播订阅丢弃，ADR-0275）。
3. **读出的 `time` 保留文档里的偏移**（改动之前就是这样）：否决。文法允许的偏移到 ±23:59，`DateTimeOffset` 只装得下 ±14:00，保留就得再拒绝一段合文法的文本，或者一部分保留、一部分换算。一律换算成 UTC；`DateTimeOffset` 按时刻比较，写出时仍合文法。
4. **在 `Messaging.Abstractions` 里复制一份解析**：否决。同一条文法两份实现正是 ADR-0278 刚收掉的。
5. **直接调用 `DeadlineText.TryParse`**：否决。它的解析并不专属于截止时间，但名字、文档与规范出处（RFC-0003 规则 8「截止时间的文本」）都是；信封那边调用一个叫「截止时间」的方法读事件时间，读代码的人要多绕一步，哪天截止时间另加约束，信封会跟着变。把解析提成原语层的 `TimestampText`，`DeadlineText.TryParse` 转给它。
6. **`TimestampText` 一并给 `Format`**：不做。结构化 JSON 写出用 `O` 格式（带信封里那个时刻的偏移），binary 模式与插件协议先换算成 UTC 再写，都已经合文法；原语层只增不改，没有调用方的成员不加（ADR-0278 备选 11）。
7. **`TimestampText` 不公开**：做不到。它要给 `Messaging.Abstractions` 与 `Protocols.CloudEvents` 用，`src` 下不新增友元（ADR-0254 备选 1）。
8. **重复的成员用 System.Text.Json 的 `AllowDuplicateProperties = false`**：否决。它只查它反序列化到的层，查不到 `data` 内部（`JsonElement`），也不管孤立的代理项与 BOM；规范要的是与清单、载荷同一道检查。
9. **给内核加友元，让消息抽象包用 internal 的 `JsonText`**：否决。友元要求按确切版本引用内核（ADR-0134），消息抽象包是第三方 Provider 引用的契约包，不该钉死内核的版本；照 ADR-0254 的做法把共用的东西放成下层包的公开成员。
10. **重复的成员只查顶层**：否决。RFC-0001 写的是任何一层；`data` 内部重复的成员，各语言的解析器取第一个还是最后一个并不一致，处理器看到的数据因此不同。
11. **扩展属性的对象与数组照旧读成空字符串**：否决。发送方给了值、接收方读出空串，值丢了却没有任何信号。`null` 不同：JSON 里「成员为 `null`」与「没有这个成员」常被当作一回事，读成没有这个属性。
12. **扩展属性的数字与布尔归一化**（`1.50` 读成 `1.5`）：否决。归一化要定一套数字的写法，各语言的格式化不同；原文是确定的。代价见「影响」的 SDK 一条。
13. **`data_base64` 缺内容类型时信封不合法**：否决。CloudEvents 不要求写 `datacontenttype`，这样的文档别的实现会发出来；读成二进制数据不丢信息，也写得回去。
14. **写出一侧不查，信封读不回来由消费方处理**：否决。消费方的处理是进死信，离出错的地方很远：发布成功了，消息却到不了处理器。写出时过一遍读取一侧的检查，发布的调用方当场拿到异常。代价是每次编码多扫一遍文档。
15. **只针对两种已知情形查**（扩展名同规范属性重名、JSON 数据单独过检查）：否决。数据的深度要按「在文档里的层数」算，单独查数据会差一层；两处检查也比「写出的文档自己过一遍」容易漏。
16. **退避改用 `decimal` 或 `BigInteger`**：不需要。`RetryDelay × 2^n` 是否超过上限，等价于 `RetryDelay` 是否大于上限右移 `n` 位，64 位整数里就能判断，不会溢出。
17. **binary 模式的 `ce-time` 这次不动**：否决。它是同一个属性的另一个载体，同样用 `DateTimeOffset.TryParse`、同样把没有偏移的时间按本机时区读；`protocol/cloudevents.md` 本来就写着 RFC 3339。只收紧结构化 JSON 的话，同一个事件换一种内容模式就读得出。
18. **插件协议的 `Envelope.time` 一并收紧**：这次不做。它用的是「没有偏移当作 UTC」，没有本机时区的问题；收紧要先核对六个 SDK 写出的文本，属于插件协议的修订。

## 决策

1. **`time` 只有一条文法**（RFC-0009「信封」第 3 条）：与截止时间的文本相同，即 RFC-0003 规则 8 的读法——必须有 `T`（或 `t`）、秒与偏移（`Z`、`z` 或 `±HH:MM`），小数一到九位，按整串匹配、不裁剪空白，各段与换算成 UTC 之后的范围照规则 8。
   - 不合文法或越界即信封不合法（`MESSAGING_VALIDATION_002`，消息键 `messaging.envelope.invalid_time`），不换别的格式再试。
   - 读出的是 UTC 时刻（偏移为零），比 100 纳秒细的小数截断、不进位。
   - binary 模式的 `ce-time` 同一条文法。
2. **原语层新增 `TimestampText.TryParse(string?, out DateTimeOffset)`**（`XiHan.Framework.Primitives`，`Stable`，自 5.0）：`DeadlineText` 原来的解析原样搬过去，`DeadlineText.TryParse` 转给它，行为不变。只有解析，没有写出。
3. **文档带 `data_base64` 而不写 `datacontenttype`**：数据内容类型是 `application/octet-stream`。写了内容类型的照它；没有 `data_base64` 的照旧缺省 `application/json`。
4. **`data` 与 `data_base64` 同时出现**：信封不合法，消息键 `messaging.envelope.data_conflict`。两个成员都不是 `null` 才算同时出现，`data_base64` 为空串也算在内。
5. **扩展属性的值**：字符串照原样；数字与布尔保留 JSON 原文；`null` 视为没有这个属性；对象与数组即信封不合法，消息键 `messaging.envelope.invalid_extension_value`（参数 `name`）。
6. **信封文档先过 RFC-0001「JSON 文本」的共同检查**：
   - 没过即信封不合法，消息键仍是 `messaging.envelope.invalid_json`，参数 `reason` 是出错的路径：语法错误为 `$`，重复的成员为它的路径（`$.id`、`$.data.lines[0].sku`），与清单、操作载荷的写法相同。
   - 检查之后形状不对的（顶层不是对象、规范属性不是字符串）同样只给路径，不再带 System.Text.Json 的异常消息（它带着内部类型的全名）。
   - 内核的 `JsonText.Check` 与 `JsonTextProblem` 公开（`XiHan.Framework.Kernel.Json`，`Preview`），消息抽象包直接调用。
7. **写出的文档必须读得回来**：`CloudEventsFormat.Encode` 写完之后自己过一遍 `JsonText.Check`，过不了抛出携带 `MESSAGING_VALIDATION_002` 的 `FrameworkException`；序列化器因为深度抛出的 `JsonException` 也转成它。
8. **发件箱的退避饱和在上限**：`RetryDelayAfter` 按整数刻度算，对任何尝试次数、任何一对间隔与上限都是 `min(RetryDelay × 2^(次数 − 1), MaxRetryDelay)`。翻倍的次数达到 63，或 `RetryDelay` 大于 `MaxRetryDelay` 右移这么多位，即取上限；否则左移，不会溢出。

## 理由

- 取严不取宽与 ADR-0276 一致：.NET 以前照收的写法别的语言做不到同样宽松，没有偏移的时间按哪个时区读还取决于解析器所在的机器。信封跨进程、跨语言，读法必须只有一种。
- 读不出就是不合法，不是「当作没有」：信封已经有一条现成的出路（无法解码的消息进死信或丢弃，日志里有原因），不需要再发明一种半读出的状态。
- 一条文法一个解析器、一道检查一个入口。两处各写各的，是这次要修的分歧的来源；复用之后，规范改一个字符只改一处。
- 读得出就写得回、写得出就读得回，是代理重投与死信能工作的前提。前一半由决策 3 补上已知的缺口，后一半由决策 7 在写出时保证。
- 退避的公式正文一直是对的，错的是实现里一个为了防溢出而加的截断；饱和本身就防溢出。

## 影响

**公开 API**

- 新增 `XiHan.Framework.Primitives.TimestampText`（`TryParse`）。
- `XiHan.Framework.Kernel.Json.JsonText`（`Check`、`MaxDepth`）与 `JsonTextProblem` 由 internal 改为公开，`Preview`。
- `MessagingMessages` 新增两个消息键常量：`EnvelopeDataConflict`（`messaging.envelope.data_conflict`）、`EnvelopeInvalidExtensionValue`（`messaging.envelope.invalid_extension_value`，参数 `name`），10 种区域的文案都已补。
- `CloudEventsFormat`、`OutboxOptions`、`CloudEventsHttpBinding` 的签名不变。没有新错误码。

**行为变化：以前读得出、现在是信封不合法的文档**

`CloudEventsFormat.Decode` 的全部调用方同时生效：RabbitMQ、Kafka、Redis 三个代理的消费，发件箱的投递，`Protocols.CloudEvents` 的 structured 与 batch 入站；`time` 的一行另含 binary 入站的 `ce-time`。

| 类别 | 例子 | 以前读成 |
| --- | --- | --- |
| `time` 用空格代替 `T` | `2026-01-02 03:04:05Z` | 同一时刻 |
| `time` 没有偏移 | `2026-01-02T03:04:05`、`2026-01-02T03:04:05.5` | 按本机时区 |
| `time` 没有秒 | `2026-01-02T03:04Z` | 秒取 0 |
| `time` 只有日期 | `2026-01-02` | 本机时区当天的零点 |
| `time` 的偏移不是 `±HH:MM` | `+0800`、`+08` | 按该偏移 |
| `time` 首尾带空白 | 空格、制表符、换行 | 裁掉后读 |
| `time` 的小数超过九位，或小数点写成逗号 | `.1234567891Z`、`,5Z` | 四舍五入到 100 纳秒 |
| `time` 是别的日期写法 | `Fri, 02 Jan 2026 03:04:05 GMT`、`01/02/2026 03:04:05` | 同一时刻；没有偏移的按本机时区 |
| `data` 与 `data_base64` 同时出现 | `"data":{…},"data_base64":"…"` | 读 `data` |
| 扩展属性的值是对象或数组 | `"detail":{"a":1}`、`"tags":["a"]` | 空字符串 |
| 重复的成员，任何一层 | `"id":"a",…,"id":"b"`、`"data":{"a":1,"a":2}`、`"seq":…,"\u0073eq":…` | 取最后一个 |
| 字符串或成员名里孤立的代理项转义 | `"subject":"\ud800"` | U+FFFD |

**行为变化：读出的值不同了**

- `time` 一律是 UTC 时刻（`Offset` 为零）。以前保留文档里的偏移；按时刻比较的代码不受影响，取 `Offset`、`DateTime` 或 `LocalDateTime` 的会看到不同的值，再写出时偏移是 `+00:00`。
- `time` 里比 100 纳秒细的小数截断：`.123456789Z` 以前是 `.1234568`，现在是 `.1234567`。
- 文档带 `data_base64` 而不写 `datacontenttype`：`DataContentType` 由 `application/json` 变成 `application/octet-stream`，`IsJsonData` 由真变假；这样的信封现在写得回去。
- 扩展属性的值是 `null`：以前信封里有这个扩展、值是空字符串，现在没有这个扩展。
- 信封不合法时 `messaging.envelope.invalid_json` 的 `reason`：以前是 System.Text.Json 的异常消息，现在是路径（`$`、`$.id`）。无法解码的消息的日志与 `Protocols.CloudEvents` 的 400 应答里的文案随之变短。

**行为变化：以前读不出、现在读得出**

- `time` 的偏移在 ±14:00 之外（`+23:59`），与 `9999-12-31T23:59:59.999999999Z`。

**行为变化：`Encode` 现在抛出的信封**

都抛出携带 `MESSAGING_VALIDATION_002` 的 `FrameworkException`，发布的调用方当场得到：

| 信封 | 以前 |
| --- | --- |
| 扩展属性与规范属性同名（`id`、`source`、`type`、`time`、`subject`、`data`、`specversion`、`datacontenttype`） | 写出重复的成员，读回时扩展的值顶掉规范属性 |
| JSON 数据里有重复的成员名 | 照写 |
| JSON 数据的字符串里有孤立的代理项转义 | 照写，读回时成 U+FFFD |
| JSON 数据嵌套到 64 层以上（文档超过 64 层） | 抛出 `JsonException` |

内存代理不经线上编码，这些信封在它上面照旧能发；换成带线上编码的代理或接上发件箱时会在发布处抛出。

**发件箱的退避**

- `MaxRetryDelay` 不超过 `RetryDelay` 的 2 的 30 次方倍时（缺省的 5 秒与 5 分钟远在此内）没有变化。
- 超过时，第 32 次及以后的失败之后间隔继续翻倍直到上限；以前停在 `RetryDelay × 2^30`。1 毫秒与 30 天：第 32 次之后是 2147483648 毫秒，第 33 次起是 30 天，以前都是 1073741824 毫秒。
- 间隔按整数刻度算。以前经浮点数，刻度数超过 2^53 时有舍入误差。

**迁移**

- 自己写结构化 JSON 或 `ce-time` 头的发送方，`time` 写成带 `T`、秒与偏移的 RFC 3339 时刻。JavaScript 的 `Date.prototype.toISOString()`、Go 的 `time.RFC3339Nano`、Java 的 `Instant.toString()`、.NET 带偏移的 `ToString("O")` 写出的都合文法；不带时区的时间（.NET `Kind` 为 `Unspecified` 的 `DateTime`、Python 的朴素 `datetime.isoformat()`）与秒为零时省略秒的写法（Java 的 `OffsetDateTime.toString()`）读不出。
- 升级前已经在队列、流、主题或发件箱表里的消息：框架自己写出的 `time` 是 `O` 格式、扩展属性都是字符串，读得出。例外是两种本来就有问题的信封——带着与规范属性同名的扩展，或 JSON 数据里有重复的成员——它们以前读得出（读出的值是错的），升级后按无法解码处理：竞争订阅进死信，广播订阅丢弃，发件箱行进死信。升级前可以先排空。
- 给信封加了名为 `id`、`data` 这类扩展的代码要改名。
- 依赖 `Envelope.Time.Offset` 的处理器改为按时刻使用，或自己换算到需要的时区。
- 不再有「读出空字符串的扩展」来表示发送方写了 `null`；用 `Extension(name)` 的有无判断。

**测试**

- 原语层：`TimestampTextVectorTests` 以 `plugin/deadlines.json` 的 `valid` 与 `invalid` 回放 `TimestampText`，核对它与 `DeadlineText.TryParse` 逐条相同、没有偏移的文本读不出、±14:00 之外的偏移换算成 UTC。
- `Messaging.Abstractions.Tests`：向量回放补「读出的信封写出再读回」与「五条规则各有用例」两条；`MessageContractTests` 逐类核对消息键与 `reason`，以及 `Encode` 拒绝的四种信封；`OutboxBackoffVectorTests` 核对向量里确有越过 2 的 30 次方倍的用例。
- `Protocols.CloudEvents.Tests`：binary 模式的 `ce-time`。
- 向量：信封新增 8 条读得出的、31 条必须拒绝的；退避新增 10 条。Go 规则包的 `DecodeCloudEvent` 随之改（先过 `CheckJSONText`，`time` 用 `ParseDeadline`）；`OutboxRetryDelay` 本来就照正文算，不用改。

**规范**

- RFC-0009：「信封」的读取改成五条并补「写出」；「发件箱」写明退避对任何次数都饱和在上限；「一致性」里不作规定的写法去掉已经写明的四类，补上两类这次看到的（规范属性写成 `null`、内容类型是 JSON 而 `data_base64` 里不是 JSON）。
- `protocol/cloudevents.md`：`ce-time` 与信封不合法的情形指向 RFC-0009「信封」。
- RFC-0001、RFC-0003：「JSON 文本」的适用范围加上消息信封，.NET 映射补 `TimestampText` 与 `JsonText`；规则不变。

**没有解决的**

- 内容类型写明是 JSON、数据却在 `data_base64` 里且不是 JSON 的文档仍然读得出、写不回（`Encode` 抛出）。规范对这种不相称的写法不作规定。
- 只有空白的必填属性、写成 `null` 的规范属性、内容类型不是 JSON 而数据写在 `data` 里、Base64 文本里的空白，仍然不作规定。
- 扩展属性名的文法本身没有改：`MessageEnvelope` 仍然接受名为 `id` 的扩展，要到编码时才被拒绝。把这几个名字从文法里去掉要改 `EnvelopeExtensions.IsValidName`（`Stable`）与向量 `envelope-extensions.json`。
- 插件协议的 `Envelope.time`（`PluginEnvelopeMapper.FromProto`）仍用通用的日期解析，没有偏移当作 UTC（备选 18）。
- `Protocols.CloudEvents` 的 batch 入站把请求体整体交给 `JsonDocument`，数组这一层不过共同检查（每个事件各自过）；它的两处 `reason` 仍是异常消息与一句英文。
