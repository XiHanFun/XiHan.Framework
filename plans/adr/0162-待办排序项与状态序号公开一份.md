# ADR-0162 待办查询改用排序项列表，状态序号公开一份

## 状态

已采纳（RFC-0021「列表排序」）。

## 日期

2026-11-11

## 背景

API 审查第三节「工作流」一组：

- **待办查询的排序写法不同**：
  - 定义查询与实例查询用有序的排序项列表 `Sorts`，每项是 `(Field, Descending)`，有项数上限与逐项核对（ADR-0102、ADR-0104）。
  - 待办查询 `UserTaskQuery` 只有一个 `bool Descending`。
  - 以后要按截止时间或标题排序，就得在 GA 后另加成员。
- **状态序号写了两份**：内存实现与数据库实现各有一个内部的 `WorkflowStatusOrder`，内容一字不差。
  - 新增一个状态时，两份要同时改。
  - 第三方的存储实现只能再抄一份，否则遇到新状态就抛 `ArgumentOutOfRangeException`。
- 审查列出的「`ResumeAsync(bookmarkId)` 能直接消费用户任务书签、绕过任务服务」复核时未处理：恢复书签走引擎的通用路径，是否要拒绝用户任务书签牵涉操作者校验的位置，需要单独核对任务服务与引擎的边界，留作后续一项。

## 决策

1. **待办查询的排序项列表**：
   - `UserTaskQuery.Descending` 改为 `Sorts`（`IReadOnlyList<UserTaskSort>?`），新增排序项 `UserTaskSort(Field, Descending)` 与字段枚举 `UserTaskSortField`。
   - 字段目前只有 `CreatedAt`，`MaxSorts` 为 1；以后加字段只追加枚举值并放宽上限。
   - 缺省（空列表）仍是创建时间升序（先到先办），同刻按写入先后。
   - `IWorkflowTaskService.QueryAsync` 与定义、实例查询同一套核对，都返回 `WORKFLOW_VALIDATION_002`：
     - 项数超过上限，消息键 `workflow.task.query_sorts_too_many`。
     - 某项为空或字段未定义，消息键 `workflow.task.query_sort_invalid`。
   - 十个语言文件同步。
2. **状态序号公开一份**：
   - `WorkflowStatusOrder.Of(status)` 移到 `Workflow.Abstractions`（`Preview`），定义与实例状态各一个重载。
   - 内存与数据库实现删掉自己的副本，改用它。
   - 新增状态时只改这一处，已有 Provider 随之得到新序号。

## 影响

- 源码迁移：
  - `new UserTaskQuery { …, Descending = true }` → `new UserTaskQuery { …, Sorts = [new(UserTaskSortField.CreatedAt, Descending: true)] }`。
  - 不写排序的查询不用改。
- 实现 `IWorkflowBookmarkStore` 的 Provider 改读 `Sorts` 的第一项决定方向；自己维护状态序号的改用 `WorkflowStatusOrder.Of`。
- 改动的类型都是 `Preview`；GA 前修改，不需要登记豁免（ADR-0131）。
