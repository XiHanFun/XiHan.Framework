# ADR-0313 S3 的列举、批量删除与读写的应答缺必需的内容返回错误，写入结果的修改时间取本机时钟

## 状态

已采纳（规范 RFC-0012「契约」「S3 Provider」「S3 的条件写入探测」「范围读取、分片上传与预签名」与 `conventions/error-codes.md` 里 `OBJECTSTORAGE_UNAVAILABLE_001` 的说明已改；`ObjectStorage.S3` 的 `S3BlobStore` 在读取、`Head`、写入、列举、列出分片与批量删除遇到缺必需内容或分页不前进的应答时返回 `OBJECTSTORAGE_UNAVAILABLE_001`，`S3ConditionalWriteProbe` 在发起分片上传的应答没有可用的上传标识时以同一个码结束这次探测；公开面、错误码、消息键与向量不变）。

## 日期

2026-11-26

## 背景

ADR-0302 与 ADR-0308 把「服务回了成功，应答里却缺了必需的内容」定为服务端错误（`OBJECTSTORAGE_UNAVAILABLE_001`），改了分片上传的发起、上传分片与列出分片三处。ADR-0308 的「待定」列出 `S3BlobStore` 里还有几处同类问题，仓库所有者已拍板全部要改：

- **列出分片的分页不前进**：`ListPartsAsync` 在应答说截断了（`IsTruncated`）却不给 `NextPartNumberMarker` 时，下一次请求不带标记、从头再列；给的标记不比本次的起点大时原地再列。循环没有上界，每一轮都把这一页的分片加进列表，直到调用方取消。本 ADR 的用例先红后绿时实测：回环上的假对端每次都回同一份截断而没有标记的 XML，以前的实现在 10 秒的期限里不停请求，最后抛出 `OperationCanceledException`。
- **批量删除的错误项没有 `Key`**：`DeleteAsync` 以 `failed[error.Key] = …` 记下 `DeleteObjects` 的错误项，`Key` 为空时 `Dictionary` 抛 `ArgumentNullException`，而这时这一批的删除已经在服务端执行了。错误项带的键不在这一批里时，那一项被记到一个不相干的键上，这一批真正失败的那一项报告成功。
- **列举截断却没有续页标记**：`ListAsync` 把 `IsTruncated ? NextContinuationToken : null` 交出去，应答说截断了而没有标记时续页标记为空，调用方以为列完了。
- **条件写入探测拿到没有上传标识的发起应答**：`S3ConditionalWriteProbe` 不看发起的应答，接着以空的标识发 `UploadPart`。线上 SDK 照样发出不带 `uploadId` 的请求；内存替身回 `NoSuchUpload`，探测报成「`UploadPart` 那一步的服务端错误」，原因看不出是发起的应答不合规。
- **读取、`Head` 与写入的应答缺 `ETag` 或修改时间**：缺 `ETag` 时元数据的 `ETag` 是空串，缺修改时间时是 `DateTimeOffset.MinValue`，都是静默兜底。仓库所有者要求先逐个操作查清应答本来带不带这两项，再定怎么改。

### 逐个操作查清的结果

依据：Amazon S3 API Reference 的公开页面（`API_GetObject`、`API_HeadObject`、`API_PutObject`、`API_CompleteMultipartUpload`、`API_CopyObject`、`API_ListObjectsV2`、`API_ListParts`、`API_UploadPart`、`API_DeleteObjects`，2026-11-26 读取，看「Response Syntax」与「Response Elements」），以及本仓库钉的 AWS SDK for .NET（`AWSSDK.S3` 4.0.104.8）的模型与 XML 文档。SDK 的应答类型里修改时间是 `DateTime?`、`ETag` 是 `string?`，应答没有这一项时为 `null`；SDK 的 `PutObjectResponse` 与 `CompleteMultipartUploadResponse` 没有修改时间属性。

| 操作 | Provider 用在哪 | 应答带 `ETag` | 应答带修改时间 | 本 ADR 的处置 |
| --- | --- | --- | --- | --- |
| `GetObject` | `GetAsync` 整读与范围读取（206） | 是，`ETag` 头 | 是，`Last-Modified` 头 | 缺任一项 → `OBJECTSTORAGE_UNAVAILABLE_001` |
| `HeadObject` | `HeadAsync`；完成分片上传之后取元数据 | 是，`ETag` 头 | 是，`Last-Modified` 头 | 缺任一项 → `OBJECTSTORAGE_UNAVAILABLE_001` |
| `HeadObject` | 批量删除之前、不覆盖写入与分片上传的发起和完成之前判存在；范围起点越界时取总长 | 同上 | 同上 | 不用这两项，不因缺了它们失败 |
| `PutObject` | 写入 | 是，`ETag` 头 | **否**：应答头只有 `x-amz-expiration`、`ETag`、`x-amz-version-id`、`x-amz-object-size` 与校验和、加密相关的头 | 缺 `ETag` → `OBJECTSTORAGE_UNAVAILABLE_001`；修改时间本来没有，取本机时钟（照旧），契约写明可以与读出的不同 |
| `CompleteMultipartUpload` | 完成分片上传 | 是，响应体 `<ETag>` | **否** | Provider 不用这个应答的内容，完成之后再 `HeadObject`，按上面第二行 |
| `ListObjectsV2` | 列举 | 是，每个 `<Contents>` 的 `<ETag>` | 是，`<LastModified>` | 要交出的对象缺任一项 → 整页 `OBJECTSTORAGE_UNAVAILABLE_001` |
| `UploadPart` | 上传分片 | 是，`ETag` 头 | 否 | 缺 `ETag` 已由 ADR-0308 处理 |
| `ListParts` | 列出分片 | 是，`<Part><ETag>` | 是，`<Part><LastModified>` | 修改时间不用；编号、`ETag`、长度已由 ADR-0308 处理，分页见本 ADR |
| `CreateMultipartUpload` | 发起分片上传、条件写入探测 | 无（应答是 `UploadId`） | 无 | 上传标识已由 ADR-0302 处理，探测见本 ADR |
| `DeleteObjects` | 批量删除（静默模式） | 无 | 无 | 错误项的 `Key` 见本 ADR |
| `CopyObject` | 不用 | 是，`<CopyObjectResult><ETag>` | 是，`<CopyObjectResult><LastModified>` | — |
| `AbortMultipartUpload`、`CreateBucket`、`HeadBucket`、`ListBuckets` | 放弃、建桶、健康项 | 不看 | 不看 | — |

查的过程中另发现一处 SDK 自己的行为：整读（`GetObject` 不带范围）与写入时，SDK 把不带 `-` 的 `ETag` 当作内容的 MD5 去核对。`ETag` 不是十六进制（包括只有引号的 `""`）时，SDK 在交出应答之前就抛 `ArgumentOutOfRangeException`（本 ADR 的用例实测），这个异常不在 Provider 的「存储故障」之列，原样抛给调用方。见「影响」的待定。

## 备选

### 列出分片的分页

1. **按 S3 写明的语义核对标记**：采纳。S3 写明截断时 `NextPartNumberMarker` 是这一页的最后一片、下一页只列编号更大的分片，所以截断的应答里标记必须存在、比这一页请求的起点（`PartNumberMarker`，第一页为 0）大、且小于 10000——编号最大 10000，标记到了 10000 就不可能还有下一页。三条一起保证标记每页严格增大且落在 1–9999，一次列出至多请求 10000 页。
2. **只核对标记存在**：否决。标记存在而不前进（等于或小于起点）时照样原地循环。
3. **只限总页数**（如 10000 页）：否决。页数到上限之前已经发了上万个请求、收了重复的分片；标记的核对在第二页就能停下。
4. **总片数的上界**：采纳。一个上传最多 10000 片（S3 的上限，也是 `BlobMultipart.MaxPartNumber`）。标记的核对挡住了原地循环，挡不住每页都前进、却重复交出同一批分片的应答；累计超过 10000 片即失败，列表有界。片数不超而编号重复的情形没有另判（见「影响」的待定）。
5. **截断而没有标记时交出已列出的部分**：否决，理由同 ADR-0308 备选 13：续传按列出的结果跳过已传的分片，少了的分片会被重传或让完成清单缺一片。

### 批量删除的错误项认不出是哪一项

6. **整次调用都返回 `OBJECTSTORAGE_UNAVAILABLE_001`**：否决。`DeleteAsync` 的结果是逐项的（RFC-0012「契约」，`conventions/batch-first.md` 规则 4），没有「整次调用」的失败可返回；把所有项都报成失败，等于把已确认不存在的项、别的批里已经删成的项也报错，与「删除失败只影响本次负责删除的项」相悖。
7. **只给认不出的那一项报错、其余算成功**：否决。认不出就是不知道是哪一项，算哪一项都是猜；静默模式的应答不列删成的项，这一批里没有一项能确认删成了。
8. **这一批里本次负责删除的项各报一个错误**：采纳。这与这一批的 `DeleteObjects` 请求整个失败时的处置相同（批量优先规则 4 的「写入阶段的基础设施失败对这些项统一报告」），只是原因换成「应答里有认不出键的错误项」。已确认不存在的项（`Head` 404）、同一批里重复的项（第二次报告不存在）与别的批照旧：它们的结果不依赖这一批的应答。报错的项里可能有已经删掉的，删除是幂等的，调用方重试即可，已删的报告不存在——比把没删掉的报成删掉了安全。
9. **改用详细模式（`Quiet = false`）按删成的项排除**：否决。应答随键数增长（每个删成的键一项），还要处理删成的项缺键、重复、不在这一批里的情形，同样的问题多了一层；静默模式下按这一批整体处理就够了。
10. **错误项带的键不在这一批里**：与没有键同样处理。它同样认不出是这一批里的哪一项，以前会被记到一个不相干的键上。核对用这一批的键做成的集合，不在每个错误项上线性查找。

### 列举截断却无续页标记

11. **截断而没有可用的续页标记即失败**：采纳。S3 写明 `IsTruncated` 为真时发送 `NextContinuationToken`。「可用」是不为空，并且与本次请求带的标记不同：续页标记是不透明的，判不了「前进」，但原样交回本次的标记意味着调用方拿它再列只会回到原处，循环从 Provider 挪到了调用方。
12. **列出的对象缺 `ETag` 或修改时间**：查清的表里两项都本该有。要交出的对象缺任一项即整页失败，不跳过它，理由同备选 5；不符合键文法而本来就跳过的对象（目录占位、保留前缀下的）缺什么不影响这一页。对象的长度缺失仍按 0：本次只处理 `ETag` 与修改时间，见「影响」的待定。

### 条件写入探测的发起缺上传标识

13. **按服务端错误处理（尚未确认，照常启动、后台重试）**：采纳。探测现有的分类里，服务端错误（连不上、超时、其余服务端错误）都是 `OBJECTSTORAGE_UNAVAILABLE_001`、尚未确认；ADR-0302 把不合规的应答定为服务端错误，`S3BlobStore` 的发起遇到它同样返回 `OBJECTSTORAGE_UNAVAILABLE_001`。探测的其余不合规应答也走这一类：服务回 500、回认不出的错误码都是尚未确认。它不说明服务认不认条件写入（还没走到带条件的完成），所以不是「不认」（`OBJECTSTORAGE_UNAVAILABLE_003`）；也不是改凭据、建桶就能修好的配置错误（`OBJECTSTORAGE_DENIED_002`、`OBJECTSTORAGE_NOTFOUND_001`）。`reason` 写明是发起这一步的应答缺了上传标识：`CreateMultipartUpload of '.xihan/probe/conditional-write' returned no usable UploadId`。
14. **判为不认、启动失败**：否决。不认是终态，要换服务或关闭条件写入后重启；中间的代理偶尔截断响应体时，这会让一次偶发的不合规应答永久关掉不覆盖写入。
15. **拿不到标识就不再探分片、只靠单次写入的结论**：否决。分片上传的不覆盖保证要靠完成的条件头，不探就是没有确认。
16. **判定的口径**：与 `S3BlobStore` 的发起同一个函数（`S3BlobStore.IsUsableUploadId`，按 `BlobMultipartUpload` 构造的公开前置条件），探测里缺失、为空、带空白与当不了句柄的标识一样处理。拿不到标识就放弃不了这个上传，留给桶的生命周期规则清理，同 ADR-0302。

### 读取、`Head` 与写入的 `ETag` 与修改时间

17. **本该有却没有的返回 `OBJECTSTORAGE_UNAVAILABLE_001`**：采纳（拍板）。`GetObject`（含范围读取）与 `HeadObject` 缺 `ETag` 或修改时间、`PutObject` 缺 `ETag`。`ETag` 的「可用」与上传分片同一个判定：去掉两端的引号之后不为空、不只有空白（ADR-0308 备选 12）——`BlobMetadata.ETag` 要随内容变化，空串与空白做不到。修改时间只判缺失。`reason` 每种缺失一个固定文本，写明请求名与字段，不带应答里的值；Warning 与 ADR-0308 共用 `The S3 service answered {Operation} for bucket '{Bucket}' without the content the blob store needs: {Reason}.`。
18. **写入缺 `ETag` 时重发，或另发 `Head` 补 `ETag`**：否决。对象可能已经写进去了：重发可能又缺一次，覆盖写入还会再写一遍；`Head` 是另一个请求、另一个可能缺内容的应答，并发覆盖时还可能读到别人写的那一版。调用方可以 `Head`，或重写同一个键。
19. **`PutObject` 的修改时间另发 `Head` 取得**：否决。每次写入多一个请求（批量写入翻倍）；写入成功之后 `Head` 失败会把成功报成失败，不覆盖的写入重试时又得到 `OBJECTSTORAGE_CONFLICT_001`；并发覆盖时 `Head` 读到的可能是别人那一版。
20. **`PutObject` 的修改时间在契约里写明可以缺省**：要把 `BlobMetadata.LastModified` 改成可空，这是 Stable 公开契约的破坏，不在本次范围（见「影响」）。
21. **`PutObject` 的修改时间照旧取本机时钟，在契约里写明写入结果的修改时间可以与读出的不同**：采纳。这是契约本来就允许的：一致性套件比较写入结果与读出的元数据时本来就不比修改时间（`BlobStoreConformance` 用例 1），文件系统存储的写入结果用的也是它自己的时钟（存进元数据文件的就是它）。RFC-0012「契约」写明：写入结果里的最后修改时间是 Provider 记下的写入时刻，不要求与之后读出的相同；S3 取本机收到应答时的时钟，读取、`Head` 与列举交出服务记下的值。`BlobMetadata` 的类型与 XML 文档不改。
22. **完成分片上传**：应答里的 `ETag` 不用，完成之后的 `Head` 按 `HeadObject` 判定；缺内容时返回错误而对象已经拼成，与写入同理不重发。
23. **只判存在与否的 `Head` 也要求这两项**：否决。批量删除与不覆盖写入之前的 `Head` 只看应答的状态（200 或 404），范围起点越界时的 `Head` 只取总长，`ETag` 与修改时间都用不到；因为一个用不到的字段让删除、写入失败，是把判定放到了不相干的地方（同 ADR-0308 备选 12「按要构造的东西的前置条件判」）。这几处改用不组装元数据的 `HeadObjectAsync` / `HeadExistsAsync`。
24. **SDK 在整读与写入时自己做的 MD5 核对**：不改。它在应答交给 Provider 之前抛出，Provider 判不到；要接住就得把 `ArgumentOutOfRangeException` 之类的编程错误当存储故障，这一步不在本次拍板里（见「影响」的待定）。

## 决策

### 规范

1. RFC-0012「契约」写明（MINOR）：写入结果里的最后修改时间是 Provider 记下的写入时刻，不要求与之后读出的相同；文件系统存储存的就是它，S3 取本机收到写入应答时的时钟。
2. RFC-0012「S3 Provider」写明（MINOR）：
   - 批量删除的应答里有错误项没有键（缺失或为空）或带的键不在这一批里：这一批里本次负责删除的项各以 `OBJECTSTORAGE_UNAVAILABLE_001` 失败，已确认不存在的项、同一批里重复的项与别的批照旧，不抛出。
   - 列举截断却没有可用的续页标记（缺失、为空，或与本次请求带的相同），或要交出的对象没有可用的 `ETag`、没有修改时间：整页 `OBJECTSTORAGE_UNAVAILABLE_001`。
   - 新增「读取、`Head` 与写入的应答里的 `ETag` 与修改时间」一条：上面查清的结论、缺了的处置、写入不重发不回滚、`PutObject` 的修改时间取本机时钟、完成分片上传之后的 `Head`、只判存在与否的 `Head` 不用这两项、Provider 不用 `CopyObject`。
   - 映射里「服务应答成功却缺了必需的内容」的括注补上这几处。
3. RFC-0012「S3 的条件写入探测」写明（MINOR）：发起分片上传的应答没有可用的上传标识，与其余服务端错误同类（`OBJECTSTORAGE_UNAVAILABLE_001`，尚未确认），`reason` 写明这一步，不再发上传分片，也放弃不了这个上传；启动或建实例时照常启动、照常建出，在后台重试。
4. RFC-0012「范围读取、分片上传与预签名」写明（MINOR）：列出分片的应答截断了，续页标记却缺失、不比这一页请求的起点大，或不小于 10000，或累计列出的分片超过 10000 个，整个列出 `OBJECTSTORAGE_UNAVAILABLE_001`，不交出已列出的部分。
5. `conventions/error-codes.md` 的 `OBJECTSTORAGE_UNAVAILABLE_001` 补一句「服务的应答不合规同此」并指向这几节（PATCH，码不变）。

### 实现

6. `S3BlobStore`：
   - `GetAsync`（两个重载）与 `HeadAsync` 经 `DescribeObject` 组装元数据：`ETag` 去掉引号之后不为空、不只有空白，修改时间存在，否则按 `GetObject` / `HeadObject` 各自的固定原因返回。`ToTimestamp` 不再收可空的值，`DateTimeOffset.MinValue` 的兜底删掉。
   - `PutOneAsync` 在 `PutObject` 之后判 `ETag`，原因 `PutObject returned no usable ETag`；修改时间照旧取 `_clock`。
   - `ListAsync` 逐个判要交出的对象的 `ETag` 与修改时间，截断时判续页标记，原因 `ListObjectsV2 returned an object without a usable ETag`、`ListObjectsV2 returned an object without a LastModified`、`ListObjectsV2 was truncated without a usable NextContinuationToken`。
   - `ListPartsAsync` 的起点从 0 开始计，截断时判标记（存在、大于起点、小于 10000），每加一片之前判累计不超过 10000，原因 `ListParts was truncated without a usable NextPartNumberMarker`、`ListParts returned more than 10000 parts`。
   - `DeleteAsync` 以这一批的键做成集合，错误项没有键或键不在集合里时这一批的键都记为失败，原因 `DeleteObjects returned an error without a usable Key`，每一批只记一条 Warning。
   - 新增私有的 `HeadObjectAsync`（原样交出 `HeadObject` 的应答）与 `HeadExistsAsync`（只判存在与否），批量删除、不覆盖写入与分片上传的发起和完成之前的存在判定、范围起点越界时取总长都改用它们。
   - `IsUsablePartETag` 改名 `IsUsableETag`（对象与分片同用），`IsUsableUploadId` 由 `private` 改 `internal` 供探测使用。
7. `S3ConditionalWriteProbe.CompleteRefusedAsync` 改返回 `Result<bool>`：发起的应答没有可用的上传标识时返回 `OBJECTSTORAGE_UNAVAILABLE_001`，原因 `CreateMultipartUpload of '.xihan/probe/conditional-write' returned no usable UploadId`（常量 `UploadIdMissingReason`），不再发后面的请求。`S3ConditionalWriteGate` 的分类不改：它按错误码分类，这个结果落在尚未确认；类型与 `StartAsync` 的文档注释补上「含服务的应答不合规」。

## 理由

- 规范与 SDK 都写明了应答里有什么：照写明的去判，缺了就是服务一侧的问题，调用方拿到与其余服务端错误同一个码，而不是一个看上去合法的空串、最小时刻，或一个空键引发的异常。
- 分页与片数都有上界，Provider 不会因为一个不合规的应答无界地请求、无界地攒列表。
- 批量删除的逐项结果只在能确认时报成功；认不出就按这一批整体失败，与请求整个失败时一致，调用方重试是安全的。
- 判定放在用到它的地方：组装元数据时要 `ETag` 与修改时间，只判存在时不要。

## 影响

- **公开 API**：签名不变（`PublicAPI.Unshipped.txt` 无改动）。`BlobMetadata` 不改。
- **行为**（都是合规的服务不会遇到的应答）：
  - S3 的读取、`Head`、写入、列举、列出分片与批量删除遇到上面的应答返回 `OBJECTSTORAGE_UNAVAILABLE_001`，不再交出空的 `ETag`、最小的修改时间、空的续页标记，不再循环不止，不再抛 `ArgumentNullException`。
  - 写入缺 `ETag` 时对象可能已经写进去了；完成分片上传之后的 `Head` 缺内容时对象已经拼成。
  - 批量删除报错的项里可能有已经删掉的。
  - 条件写入探测遇到发起缺上传标识：照常启动、健康项 Degraded（`conditionalWrites` 为 `unconfirmed`），不覆盖写入返回 `OBJECTSTORAGE_UNAVAILABLE_004`（`reason` 为 `OBJECTSTORAGE_UNAVAILABLE_001`），后台按退避重试，应答恢复正常后自动确认。
- **规范**（规范仓库已改，指针待更新）：RFC-0012 四节（MINOR），`conventions/error-codes.md` 一处说明（PATCH）。不加向量：这些都是 S3 Provider 对服务应答的处置，只有 .NET 的 S3 Provider 实现，由它自己的测试核对（同 ADR-0302、ADR-0308）。
- **测试**（都不需要 S3 服务）：
  - 新增 `S3ObjectResponseTests`：回环假对端回缺 `ETag`、`ETag` 只有引号、缺 `Last-Modified` 的 `HEAD`、整读与范围读取，回缺 `ETag` 的 `PUT`；完整的应答照常；写入结果的修改时间是注入的时钟；替身上只判存在的 `HEAD`（不覆盖写入、分片上传的发起、批量删除）不需要这两项；完成之后的 `HEAD` 缺 `ETag` 返回错误而对象已在。
  - 新增 `S3ListingResponseTests`：截断而没有续页标记、续页标记与请求的相同、对象缺 `ETag`（缺失与只有引号）或修改时间都整页失败；新的续页标记照常交出；目录占位缺什么照样跳过。
  - 新增 `S3DeleteResponseTests`：错误项没有键、键为空、键不在这一批里时这一批要删的项都报错、不存在与重复的项照旧、只记一条 Warning；带着这一批的键的错误项只影响那一项；超过 1000 个键时认不出的错误项只影响它所在的那一批。
  - `S3MultipartPartResponseTests` 补：线上截断而没有标记只发一个请求；标记缺失、为 0、等于或小于起点时第二页即失败；标记为 10000 或更大时第一页即失败；每页都前进而重复交出 1000 片时第 11 页失败；正常的三页按标记依次请求、列全。
  - `S3ConditionalWriteTests` 补：发起的应答没有标识、为空或当不了句柄时，探测以 `OBJECTSTORAGE_UNAVAILABLE_001` 结束、`reason` 点名发起这一步、只发三个请求；`S3ConditionalWriteRetryTests` 补：启动照常、健康项降级、恢复正常的应答后后台确认。
  - `FakeS3Client` 加 `HeadAnswer`（换掉 `HEAD` 的应答，缺省带 `ETag` 与修改时间）、`DeleteErrors`（模拟 `DeleteObjects` 的错误项）与 `PartPages`（模拟列出分片的分页）。
  - 改实现之前，最终这组用例里有 32 条失败：断言不符、以前的实现抛出 `ArgumentNullException`，或在期限里循环到 `OperationCanceledException`。
  - 一致性套件与对真实服务的用例只在设了 `XIHAN_TEST_S3` 时执行，本机与 CI 都跳过。
- **文档**：包 README（S3）已改；文档站的 `object-storage/advanced`、`packages/objectstorage-s3`、`appendix/spec` 与更新日志待改。
- **待定**：
  - 整读与写入时 SDK 自己核对 MD5：`ETag` 不带 `-` 而又不是十六进制（含只有引号）时，SDK 抛 `ArgumentOutOfRangeException`，Provider 接不到，原样抛给调用方。要不要在这两处把 SDK 的这类异常也当作不合规的应答，留给仓库所有者定。
  - 读取与 `Head` 的应答缺 `Content-Length`、列举的对象缺 `<Size>` 时长度照旧按 SDK 给的值或 0，本次没有改。
  - 列出分片的应答在片数不超 10000 时重复交出同一编号、或交出不比请求起点大的编号，本次没有判。
  - 条件写入探测里上传分片的应答没有 `ETag` 时，探测照样拿空的 `ETag` 去完成，结果取决于服务先判条件还是先判分片。
  - 发起缺上传标识的服务若确实建了上传，探测每次重试都会留下一个放弃不了的上传（写入触发的就地探测至多每秒一次，后台至多每个健康探测间隔一次），靠桶的生命周期规则清理。
  - `BlobMetadata.LastModified` 改成可空、让 S3 的写入结果如实「没有」修改时间，是 Stable 契约的破坏，没有做。

## 更正（2026-11-27）

「背景」的「逐个操作查清的结果」之后写的「整读（`GetObject` 不带范围）与写入时，SDK 把不带 `-` 的 `ETag` 当作内容的 MD5 去核对」，对写入不成立。ADR-0317 反编译 `AWSSDK.S3` 4.0.104.8 并实测：`AmazonS3ResponseHandler.ProcessResponseHandlers` 只在 `PutObjectRequest.InputStream`（或 `UploadPartRequest.InputStream`）是 `MD5Stream` 时才拿 `ETag` 比较，而 SDK 4.0 不再把上传的流包成 `MD5Stream`（上传的完整性交给 `AWSSDK.Core` 的请求校验和），所以写入的 `ETag` 不是十六进制时照常交出，不抛出；只有整读把响应流包成 `MD5Stream`、先把 `ETag` 当 MD5 解码。据此，备选 24 与「影响」的待定里「整读与写入时 SDK 自己核对 MD5」一条应读作「整读时」；写入一侧没有要处理的事。整读一侧的处理见 ADR-0317（`ETag` 不是十六进制）与 ADR-0322（内容对不上 `ETag`、识别不靠调用栈）。本 ADR 的决策与实现不受影响。
