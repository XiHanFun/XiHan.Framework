# ADR-0287 工作流表达式小语言写进规范

## 状态

已采纳（framework-spec：RFC-0021「表达式」重写成十二个小节，`conformance/vectors/workflow/` 新增五个表达式向量文件并进了 `workflow` 档，Go 一致性模块登记了它们并核对结构；本仓库：`Workflow.Abstractions` 的求值器照正文修正，五个文件各有回放）。

## 日期

2026-11-24

## 背景

- RFC-0021「表达式」只用一段话列了运算符与函数的名字。文法、每个运算符对每种操作数怎么算、数字怎样舍入与写出、模板怎样找占位、错误带哪些参数，都只在 .NET 的 `ExpressionCompiler` 里。按规范另写一个实现的人写不出相同的结果。
- ADR-0277 给十一个子系统档补向量时把表达式留了下来（备选 5）：它是 `workflow` 档里最适合写成向量的部分——纯函数、输入输出确定——但正文没有逐条写出。
- 这次把 .NET 的行为逐项读出来之后，发现其中一批不是「规范没写」而是「写不进规范」：行为取决于 .NET 平台的类型或库，别的语言复现不了，有的连 .NET 自己在不同的时候结果都不一样。

  | 行为 | 问题 |
  | --- | --- |
  | 数字的文本照 `decimal` 内部记着的小数位数写：`1.50` 写 `1.50`，`1.5 + 1.5` 写 `3.0`，`2.50 * 2` 写 `5.00`，`min(1, 1.0)` 与 `min(1.0, 1)` 写出不同的文本 | 同一个数值因来历不同写出不同的文本；JavaScript、PHP 读 JSON 时拿不到这个位数；存储是否保留它也因库而异 |
  | `date()` 与比较里的时间交给 `DateTimeOffset.TryParse` | 月份名、斜线日期、不补零的月日、只有年月都读得出；只有时间的 `12:30` 补上**机器当天的日期**——同一段文本在不同的日子读出不同的时刻，`'9:30' < '10:45'`、`'1/2' < '1/10'` 这样两个字符串比大小的结果跟着变 |
  | `now()` 与 `date()` 返回进程内的 `DateTimeOffset` 值 | 它的文本带七位小数；写进变量、过一遍存储之后成了 `System.Text.Json` 写的不带多余小数位的字符串。同一个值前后文本不同，`x == now()` 在存储前后结果不同 |
  | 数组与对象的文本是 `JsonNode.ToJsonString()` | 非 ASCII 字符与 `<`、`>`、`&`、`'`、`+`、`"` 写成 `\uXXXX`（`{{ tags }}` 渲染出 `["\u8BF7\u5047"]` 这样的文本），数字照读入时的原文（`2.50`、`1e2`），成员照插入的顺序——都是这个库的缺省，别的语言的 JSON 库写不出同样的文本 |
  | `+`、`-`、`*`、`/` 的结果放不下、`round` 的小数位数不在 0 到 28、数组下标超出 32 位整数 | `OverflowException` / `ArgumentOutOfRangeException` 直接逃出返回 `Result` 的求值器 |
  | 字符串当数字用时交给 `decimal.TryParse(NumberStyles.Float)` | 结尾带 NUL 字符的字符串也读得出；位数与指数都上千时读出的不是数学值（解析器把指数截在一千） |
  | `/` 与 `%` 先求值右操作数、先看除数；`-`、`*` 核对完左操作数才求值右操作数；`round` 先求值第二个实参 | 两个操作数都有错时报哪一个，每个运算符各不相同，写不成一条规则 |
  | 模板渲染的结果没有上限 | 占位可以是整个变量的 JSON 文本（变量上限 8 MiB），一个几 KB 的模板重复一千次就渲染出几个 GB。`+` 拼接有 4194304 的上限（ADR-0182），渲染没有 |
  | 错误里带出的文本 | `not_date` 的 `value`、`not_boolean` 与 `unterminated_placeholder` 的 `expression` 不截断（模板本身没有长度上限）；截断处落在代理对中间时留下半个字符；`unexpected_character` 遇到基本多文种平面以外的字符只带出前一半 |
  | 成员名与变量名区不区分大小写取决于 `JsonObject` 是怎样造出来的 | 按 Web 缺省选项反序列化出来的不区分，写进存储再读回来的区分：`obj.B` 在存储之前读到成员 `b`，之后是 null。内存实现保存深拷贝（保留选项），数据库实现存 JSON 文本，两个 Provider 结果不同 |
  | 由 `double`、`float`、`short` 等构造、还没过存储的值 | `double` 经 `(decimal)` 转换（只留 15 位有效数字，`0.1 + 0.2` 成了 0.3），过了存储是 0.30000000000000004；`float`、`short` 等根本不算数字，过了存储又算 |

## 备选

1. **照 .NET 的现状逐条写进规范**：否决。上表的每一行写进去都等于要求别的语言模拟 .NET 的某个类型或库（`decimal` 的小数位数、`DateTimeOffset.TryParse`、`System.Text.Json` 的缺省转义），有几行连「同一输入同一结果」都做不到。ADR-0277 备选 2 否决过同样的做法。
2. **数字改成 IEEE 754 双精度**（与 RFC-0010 模板的值模型一致）：否决。金额与数量是流程条件里最常见的操作数，`0.1 + 0.2 == 0.3` 在现有流程里为真；`decimal` 的四则运算可以用大整数精确地说清楚（见决策 2），不必换。
3. **数字保留小数位数**（General Decimal Arithmetic 那样把数字看成整数与小数位数的一对）：否决。它要求实现从 JSON 里读出数字的写法（`1.50` 与 `1.5` 是两个值），JavaScript 的 `JSON.parse` 与 PHP 的 `json_decode` 做不到；存储会不会保留这个位数也因库而异。数字只看数值，文本只有一种写法。代价见「影响」的升级须知：`19.90` 不再渲染成 `19.90`。
4. **时间文本只收截止时间的文法**（RFC-0003 规则 8：必须写秒与偏移）：否决。`date('2026-01-02')` 是现有流程与文档里的写法，表单的日期时间控件给出的是 `2026-01-02T03:04`，数据库常见的是 `2026-01-02 03:04:05`。文法取它的超集：只有日期、不写秒、不写偏移（当作 UTC）、空格分隔都读得出，别的写法一概不认。
5. **时间仍交给平台解析，向量只收各语言都读得出的写法**：否决。比较运算在两边都读得成时间时按时刻比，读不读得成由平台决定的话，两个普通字符串比大小的结果也由平台决定。
6. **容器的文本照成员原来的顺序**：否决。JavaScript 的对象把整数样的键排到前面，Go 的 `map` 与 Rust 的 `serde_json` 缺省都不保序。照 RFC-0010 模板里容器的写法（ADR-0236）按名字的序数顺序，字符串的转义也用同一种写法，规范里只有一种紧凑 JSON。
7. **两个数字文本按文本比**（`'007' == '7'` 现在为真）：这次不改。这条规则与平台无关、说得清楚（数字或数字文本都当数字），改了会让现有流程里两个表单字段比大小（`'10' > '9'`）的结果翻转。它是不是想要的行为留给所有者定（见「没有解决的」）。
8. **下标带小数时报错**：不改。截去小数部分（`arr[1.9]` 是 `arr[1]`）与语言无关，照写。
9. **不认识的转义报错**（`'\q'` 现在是 `q`）：不改，照写。
10. **在 Go 一致性模块里实现一个求值器**：不做。五个文件的求值由参考实现 .NET 回放；Go 模块登记这五个文件，并核对不必求值就能判的部分（每个数字结果是规范文本、`syntax` 与消息键所在的组一致、长度按 UTF-16 码元计、带出的文本照截断规则、每个消息键与每个内置函数都有用例）。
11. **放不下另设错误码**：否决。表达式的错误都是 `WORKFLOW_VALIDATION_003`，区分靠消息键；加一个键 `workflow.expression.number_out_of_range`。
12. **`round` 的小数位数超过 28 时当作不变、负数时按零**：否决，那是静默兜底。不在 0 到 28 之间就是错误。
13. **渲染的上限做成配置**：否决。与 `+` 拼接用同一个常量 4194304：两处防的是同一件事。
14. **`WorkflowValues.AsString` 不动，求值器另用一套文本**：否决。同一个 JSON 标量在活动里与在表达式里写出两种文本，比改一个 Preview 的静态方法更糟。
15. **运算符的向量做成每个运算符 × 左右各七种操作数的全矩阵**（十三个运算符 637 条）：收窄。`-`、`*`、`/`、`%` 只认数字，每种操作数在左右各出现一次就够；`&&` 与 `||` 左边不是布尔时右边是什么都一样。`+`、`==`、`<` 保留全矩阵。

## 决策

1. **RFC-0021「表达式」重写**，分成：长度与上限、值（数字、数字文本、数字的文本、值的文本）、词法、文法（EBNF 与解析时的错误表）、求值（作用域与次序）、运算符、成员与索引、内置函数、时间、条件、模板、错误。另一种语言的实现者只读这一节（与它引用的 RFC-0001「空白字符」、RFC-0003 规则 8、RFC-0010 的 JSON 字符串写法）就能实现出相同的结果。
2. **数字**是 m × 10^(−s)，m 的绝对值不超过 2^96 − 1，s 在 0 到 28 之间，只看数值。运算的结果是精确值「放进数字」：取最大的 s 使它乘以 10^s 按一半取偶舍入之后放得下。这就是 `decimal` 四则运算在数值上的结果——用 40 万组随机操作数（偏向边界）把 `+`、`-`、`*`、`/`、`%`、`round` 与文本的读入同大整数算出的规则逐条对过，没有出入。所以 .NET 的算术不用改，改的是它的边缘：放不下时报 `number_out_of_range`，文本不带内部的小数位数。
3. **数字的文本**只有一种写法：不用指数，小数部分不带结尾的零，零写 `0`。`WorkflowValues.AsString` 照此写出。
4. **数字文本**（字符串当数字用）是一条文法加数学值：首尾的空白只认 U+0009–U+000D 与空格，可选的符号，ASCII 数字与可选的小数点，可选的指数。`.NET` 新增内部的 `WorkflowNumberText`：按文法扫一遍，改写成不带指数的写法再交给平台舍入（这种写法平台的舍入与规则一致，50 万组随机文本对过）。变量里的 JSON 数字按原文过同一条文法。
5. **值的文本**：`null` 是空串，标量是它自己的文本，数组与对象是紧凑的 JSON——成员按名字的序数顺序，数字写规范文本，字符串只转义 `"`、`\` 与 U+0000–U+001F，超过 64 层的容器写 `null`，与 RFC-0010 模板里的容器同一种写法。`.NET` 新增内部的 `WorkflowValueText`，拼接、`toString`、各字符串函数、对象的键与模板都经它。
6. **时间是字符串**。读法是 RFC-0003 规则 8 的超集（见备选 4），不裁剪首尾空白，比 100 纳秒更细的小数截断；写法与截止时间相同：UTC、七位小数、`+00:00`，定宽 33 个字符。`now()` 与 `date()` 返回这种文本；比较只在两边都是合文法的字符串时按时刻。`.NET` 新增内部的 `WorkflowTimeText`，读与写都落到原语 `DeadlineText` 上。
7. **求值的次序**统一成：二元运算符与函数先从左到右求值全部操作数，再从左到右核对类型，除法与取余最后看除数；`&&` 与 `||` 照旧短路；索引先求值被索引的值再求值下标。
8. **上限**：表达式 4000、嵌套 64 层、`+` 拼出的字符串 4194304 不变；模板渲染出的文本新增同一个 4194304 的上限，字面文本与每个占位的文本接上去之前按累计长度核对。长度与位置都按 UTF-16 码元计（以前写「字符」）。不另设求值步数的上限：没有循环与递归，运算次数不超过表达式的长度。
9. **错误**：新增消息键 `workflow.expression.number_out_of_range`（参数 `operator`：`+`、`-`、`*`、`/` 或 `round`），10 个区域文件都补了；数组下标放不进整数时是已有的 `index_out_of_range`。错误里带出的文本一律最多 200 个码元、不切开代理对；`unexpected_character` 的 `character` 是整个字符；渲染超过上限的错误也带 `expression`（模板）。
10. **成员名与变量名一律按序数比较**，不随 `JsonObject` 的大小写选项；对象的深比较同样。
11. **由 CLR 类型构造的值按它写成 JSON 之后的形式参与求值**（数字按 JSON 里的写法读，`DateTimeOffset`、`Guid` 等是它的 JSON 字符串），与过一遍存储之后相同。
12. **实现自定**，正文里标明、不进向量：放不下的 JSON 数字（如变量里的 `1e40`）在表达式里怎样表现；`upper` / `lower` 对 U+0130 与 U+0131 的转换（.NET 的不变文化不转换它们，Unicode 的简单映射转成 `i` 与 `I`）；实现所带的 Unicode 版本不同时，新近收录的字符算不算字母、有没有大小写映射。含孤立代理项的字符串不在规定之内。
13. **向量**五个文件，期望值全部由 .NET 的求值器算出（脚本在临时目录，不提交）：

    | 文件 | 用例 |
    | --- | --- |
    | `expression-syntax.json` | 116 条求值成功、96 条失败：字面量、空白、标识符、优先级与结合性、成员与索引与调用的写法，解析时的每一种错误与位置 |
    | `expression-operators.json` | 376 条成功、206 条失败：运算符与操作数种类的组合，数字的舍入与范围，数字文本，除以零与求值的先后，拼接，相等，比较，逻辑的短路，成员与索引 |
    | `expression-functions.json` | 195 条成功、75 条失败：16 个内置函数，数字文本与时间文本合法与不合法的写法 |
    | `expression-templates.json` | 40 条渲染、16 条渲染失败、7 条条件、9 条条件失败 |
    | `expression-limits.json` | 长度、嵌套、拼接与渲染的上限两侧，链不算嵌套，错误里带出的文本 |

    `workflow.expression.` 下的 25 个消息键每个至少有一条用例。
14. **规范的级别**（RFC-0024）：改了已经写明的行为（`+` 拼接里数字与容器的文本、`now()` 的结果等原先由 .NET 实测决定而正文一笔带过的地方）记 MAJOR（`v1.0.0` 之前允许）；新向量文件与新写明的规则是 MINOR。

## 理由

- 表达式是流程定义的一部分，定义是会被导出、迁移、由别的语言的引擎执行的数据。它的语义不能挂在某个平台的类型上。
- 修正的每一处都是「同一输入同一结果」做不到或别的语言做不到的地方；与平台无关、只是不太顺眼的规则（数字文本按数值比、下标截去小数、不认识的转义）都照原样写下，不借这次机会重新设计语言。
- 时间与截止时间用同一种写法、容器与消息模板用同一种写法：规范里同一件事只有一种写法，实现也只写一份。
- 定宽的时间文本按序数比较的先后就是时刻的先后，`date(a) == date(b)` 就是按时刻比相等——把时间做成字符串之后不必再给相等加一条特例。

## 影响

**公开 API**

- 新增常量 `WorkflowMessages.ExpressionNumberOutOfRange`。没有别的签名变化；`IWorkflowExpressionEvaluator`、`ExpressionScope`、`WorkflowValues` 的成员不增不减（都是 `Preview`）。
- 新增的 `WorkflowNumberText`、`WorkflowTimeText`、`WorkflowValueText` 与 `WorkflowValues.TryMember` 是 internal。没有新的配置键与错误码。

**行为变化（升级须知）**

| 原来 | 现在 | 迁移 |
| --- | --- | --- |
| 数字的文本带 `decimal` 内部的小数位数：`{{ price }}` 在 `price` 是 `19.90` 时渲染 `19.90`，`1.5 + 1.5` 写 `3.0` | 规范文本：`19.9`、`3`。`WorkflowValues.AsString`、模板、`+` 拼接、`toString`、`len`、对象的键都是 | 要固定小数位数的展示（金额）在流程之外格式化，或把格式化好的字符串放进变量；语言里目前没有格式化函数 |
| 数组与对象的文本是 `System.Text.Json` 的缺省写法：`["\u8BF7\u5047"]`、`2.50`、成员照原顺序 | 紧凑 JSON：非 ASCII 与 `<>&'+` 原样，数字写规范文本，成员按名字排序，超过 64 层写 `null` | 解析结果不变；按文本匹配容器的条件（`contains(obj, '"b":1')`）照新的文本写 |
| `now()` 与 `date()` 的结果是 `DateTimeOffset` 值 | 字符串 `2026-01-02T03:04:05.0000000+00:00` | 进程内读结果用 `WorkflowValues.TryConvert<DateTimeOffset>`，不用 `GetValue<DateTimeOffset>()`。写进变量的文本由 `…T03:04:05+00:00` 变成带七位小数的定宽写法，两种写法比较时都按时刻。`now() + 1` 以前报错，现在是拼接 |
| `date()` 与比较里的时间交给 `DateTimeOffset.TryParse` | 只认文法：`YYYY-MM-DD`，或加 `T` / 空格与 `HH:MM`，秒、一到九位小数与偏移可省 | `01/02/2026`、`Jan 2, 2026`、`2026-1-2`、`2026-01`、`12:30`、首尾带空白的都不再是时间：`date()` 报 `not_date`，比较时按文本。九位以内超过七位的小数由四舍五入改成截断 |
| 字符串当数字用时结尾可以带 NUL 字符 | 不合文法，不是数字 | 无 |
| 结果放不下、`round` 的位数越界、下标超出整数范围时抛出异常（经引擎成为 `WORKFLOW_UNEXPECTED_001`） | `WORKFLOW_VALIDATION_003`：`number_out_of_range` 或 `index_out_of_range` | 无 |
| `'x' / 0`、`nope / 0`、`'x' % 0` 报 `division_by_zero` | 先求值两边再核对：`operands_not_numeric`、`unknown_variable`、`operands_not_numeric` | 只影响同时有两处错的表达式报哪一个 |
| 模板渲染的结果不限长 | 超过 4194304 → `string_too_long` | 渲染结果超过 4 M 个字符的模板改为分段，或在活动里拼 |
| `not_date` 的 `value`、`not_boolean` 与 `unterminated_placeholder` 的 `expression` 不截断 | 最多 200 个码元再接 `…` | 无 |
| 成员名与变量名在不区分大小写的 `JsonObject` 上不区分大小写 | 一律区分 | 靠大小写不敏感取到成员的表达式改成准确的名字（这种表达式在实例过一遍存储之后本来就取不到） |
| `double` 构造的变量经 15 位有效数字的转换；`float`、`short` 等构造的不算数字 | 都按它的 JSON 写法 | 无（过了存储本来就是这样） |

**规范**

**没有解决的**

- 两个数字文本按数值比（`'007' == '7'`、`'0e1' == '0e2'` 为真，`'10' > '9'` 为真）是不是想要的行为。它与平台无关，已经照现状写进正文与向量；要改成「两边都是字符串时按文本」是语言的设计变更，会翻转现有流程的结果。
- 没有把数字格式化成固定小数位数的函数：数字的文本规范化之后，金额的展示要在流程之外做。
- 活动自己读时间的地方（`Delay.Until`、`UserTask.DueAt`）与 `WorkflowValues.TryConvert<DateTimeOffset>` 仍用平台的日期解析：它们不在表达式语言之内，这次没有动。`now()` 与 `date()` 写出的文本它们都读得出。
- 活动里把数组与对象写成文本的地方（`RenderProperty` 遇到非标量属性、`Http` 的请求头）仍用 `ToJsonString()`，与表达式里容器的文本不是同一种写法。
- 含孤立代理项的字符串进了变量时，读它的文本会抛出 `InvalidOperationException`（`System.Text.Json` 读不出这样的字符串）。操作载荷按 RFC-0001「JSON 文本」不会带进这样的字符串，进程内直接构造的没有拦。
- 实现自定的三处（决策 12）。
- 一次求值的时间没有单独的上限：长度以内可以写出两千次接近 4 M 的拼接，每次都要复制，合计是秒级的 CPU。
