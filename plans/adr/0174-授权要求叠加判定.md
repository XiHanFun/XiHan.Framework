# ADR-0174 授权要求叠加判定

## 状态

已采纳（RFC-0008「授权」第 1 条修订）。

## 日期

2026-11-12

## 背景

5.0 安全审查 S-01（`plans/5.0-安全审查.md`），高危。两组审查独立发现，其中一组在运行时复现。

- `AuthorizationMiddleware` 只要拿到宿主写入的要求，就不再按操作契约推导：两者是二选一，显式要求优先。
- `UseXiHan()` 只取端点上的最后一条 `AuthorizationRequirement`（`GetMetadata`）。
- ADR-0144 让 `MapXiHanOperations()` 返回约定构建器，它的 XML 文档建议在这里加授权约定。

后果：

- 宿主写 `app.MapXiHanOperations().RequireXiHanAuthentication()`，本意是「整个 API 要登录」，结果每个操作自己声明的权限都失效了，任何没有授予的已登录用户都能调用全部 HTTP 操作。
- 在组上加 `RequireXiHanPermission("api.access")` 也一样。
- 普通路由组也有同样的问题：组上要权限、端点上要登录，只剩登录这一条。ASP.NET Core 自己的授权要求是叠加（AND）的，这里的行为与使用者的预期相反。
- gRPC 与 MCP 不读端点元数据，仍按契约判定，只测这两种协议发现不了。

复现：`EndpointRequirementStackingTests`。没有任何授予的用户调用要 `orders.write` 的 `orders.create`，修正前返回 201；组上要 `orders.read`、端点上要登录的普通端点，修正前返回 200。

## 备选

1. **端点上的要求只在契约没有权限时生效**：否决。普通路由组上「组要权限、端点要登录」的情况仍然只剩一条，而且使用者没法给操作再加一道要求。
2. **启动时拒绝在操作端点上加授权约定**：否决。「API 都要登录」「整组操作再要一个 `api.access`」是合理的需求，应该支持。
3. **全部要求叠加**：采纳，与 ASP.NET Core 的语义一致。

## 决策

1. **要求叠加**：Authorize 阶段判定的是宿主写入上下文的全部要求，加上操作契约推导出的那一条。
   - 按顺序逐条判定，全部满足才放行；第一条不满足就以它的结果结束（拒绝的原因、存储不可达的失败照旧）。
   - 相同的要求只判定一次。
2. **上下文 API**（`Security.Abstractions`，`Stable`，GA 前修改）：
   - `RequireAuthorization(requirement)` 改为追加，可以调用多次；复制后追加，不原地改数组（ADR-0138 的并发约定）。
   - `FindAuthorizationRequirement()` 返回单个 `Maybe`，删除；改为 `GetAuthorizationRequirements()`，按写入顺序返回全部要求，没有时为空，不含契约推导的那一条（ADR-0153：`Get…` 必定交出值）。
3. **宿主**：`UseXiHan()` 以 `GetOrderedMetadata` 把端点上的全部要求写进上下文；启动核对（`EndpointRequirementCheck`）逐条核对每一条要求的策略。
4. RFC-0008「授权」第 1 条写明叠加语义；`MapXiHanOperations()` 与 `EndpointConventionBuilderExtensions` 的 XML 文档写明约定不顶替契约。

## 影响

- 行为：原先依赖「端点要求顶替契约权限」的宿主，现在两者都要满足。这正是修复的目的；有意放宽某个操作的权限，要改那个操作的契约。
- 源码迁移：`context.FindAuthorizationRequirement()` 改为 `context.GetAuthorizationRequirements()`；原来判断「有没有要求」的写法改成判断 `Count == 0`。
- OpenAPI 对普通端点仍只发布一条 `x-xihan-permission`（取最后一条要求），不影响判定。
- GA 前修改，不需要登记豁免（ADR-0131）。
