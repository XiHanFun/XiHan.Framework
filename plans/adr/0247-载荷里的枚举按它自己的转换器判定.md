# ADR-0247 载荷里的枚举按它自己的转换器判定

## 状态

已采纳（只改 .NET 参考实现，修正 ADR-0236 的 `JsonRequestShape`；规范不变）。

## 日期

2026-11-20

## 背景

- ADR-0236 在解码前加了内部的 `JsonRequestShape`，按序列化元数据以 RFC-0011 规则 2 的顺序先查一遍形状，它认不出的部分（自定义转换器、多态）交给反序列化。枚举一律按「缺省的转换器只读整数」判定，只在属性自己标了 `[JsonConverter]` 时跳过。
- 字符串枚举更常见的写法是在枚举类型上标 `JsonStringEnumConverter<T>`，或在源生成上下文里写 `UseStringEnumConverter = true`。这两种写法属性上都没有转换器，形状检查照样只收整数，载荷里的成员名一律以 `KERNEL_VALIDATION_001` 失败，`reason` 是这个成员的路径。RFC-0011 对这类枚举的 Schema 写的是 `type: string` + `enum`，同一份请求按 Schema 合法、解码却失败。
- 受影响的不只是应用：框架自己 Workflow 的状态与排序枚举都在类型上标了字符串转换器。一个应用在 5.0.0-rc.3 上 592 个集成用例里有 181 个因此失败。
- 缺省的转换器与字符串枚举转换器是 System.Text.Json 内部的同一个 `EnumConverter<T>`，只差构造时的选项，`JsonTypeInfo.Converter` 看不出读不读字符串。

复现：新增的 `EnumPayloadTests` 在修之前有 3 例确定失败：字符串上下文里的成员名、类型上标了转换器的枚举、数组里第二项不合法时报的位置。

## 备选

1. **枚举一律不查，交给反序列化**：否决。整数枚举收到字符串、后面又有类型不符时，会先报后面那一处，违反「按文本顺序报第一处」。
2. **字符串一律放过、整数照旧核对范围**：否决。整数枚举收到字符串时同样会打乱先后；`allowIntegerValues: false` 的字符串转换器收到整数时也会。
3. **用反射读转换器的私有选项**：否决。依赖 System.Text.Json 的内部字段，换版本就会失效，内核也不用反射。
4. **由枚举自己的转换器读这一个值**：采纳。读不读字符串、认不认整数、范围与未知成员名都由转换器自己判定，与随后的反序列化结果相同；只读这一处，报错的位置与先后不变。

## 决策

1. `JsonRequestShape` 遇到枚举（含 `Nullable<T>` 的底层枚举、数组项与字典值）时，用该枚举的 `JsonTypeInfo` 反序列化这一个值，抛出 `JsonException` 即报该值的路径，否则通过。
2. 其他类型的判定不变。

## 理由

- 判定与反序列化出自同一个转换器，形状检查不会比解码更严，也不会更松。
- 只在这一个值上调用，异常只在载荷不合法时出现，合法载荷的开销是一次枚举读取。

## 影响

- 线上行为：类型上或上下文里登记了字符串枚举转换器的请求，成员名重新能解码（5.0.0-rc.3 起被拒）；整数枚举收到字符串照旧报该成员的路径，先后与 rc.3 相同。
- 公开 API 不变，规范不变。
- 测试：内核新增 `EnumPayloadTests`，覆盖字符串上下文、类型上的转换器与缺省整数枚举三种写法下的解码与报错位置；`PayloadReasonVectorTests` 照旧通过。
