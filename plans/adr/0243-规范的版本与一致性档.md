# ADR-0243 规范的版本与一致性档

## 状态

已采纳（规范新增 RFC-0024 与 `conformance/profiles.json`，各 RFC 的状态行写明所属的档；`README`、`docs/appendix/spec.md` 与总体方案 §9.3 随之修订）。

## 日期

2026-11-19

## 背景

- 规范 README 承诺语义化版本标签与「`v1` 期间只增不改」，但规范仓库一个标签都没有。.NET 与六个 SDK 各自钉着裸提交，说不清实现的是哪一版。
- ADR-0233～0237 多次改写各 SDK 的可观察行为，每次都是「把不作规定写死」，却没有版本号记录。澄清与变更也从没区分过。
- 「规范性（各语言必须一致）」把协议映射、打包、迁移和各子系统 RFC 都算了进去，而六个 SDK 只实现核心与插件一侧。「Stable：通过全部向量」因此对 SDK 无从判定：WebAuthn、Wasm、远程 Provider 的向量本来就不归它们。ADR-0242 用各实现的豁免表暂时顶着，并约定分层定下后由它取代豁免表。
- 两份外部评审都把这两件事列为首要问题。

## 备选

用户逐项拍板，每项都选了推荐的一种。

1. **版本形态**：
   - 采纳：独立的 `v1.x.y`。
   - 否决：跟框架版本走 `v5.x.y`。规范会被 .NET 的发布节奏绑住，SDK 修 bug 不动规范，却要对着框架版本号说话。
   - 否决：先 `v0.x.y`。线上的原语层、协议与 Schema 已经都是 1，会出现 v0 的规范定义 v1 的协议这种错位。
2. **MINOR 的边界**：
   - 采纳：MINOR 可以写死以前不作规定的行为，已经写明的行为才不能改。
   - 否决：任何可观察的变化都进 MAJOR。每次补规定都要升大版本，协议版本也得跟着升，v1 会很快变成 v5、v6。
3. **分层粒度**：
   - 采纳：核心、角色档、子系统档三层。
   - 否决：只分 `core` 与 .NET 专属两档。以后别的语言做宿主或实现某个子系统时没有档可认领，又得再拆。
4. **何时钉标签**：
   - 采纳：只在发版时钉。
   - 否决：任何时候都必须指向标签。规范先改、实现后跟的流程会让标签很碎。

## 决策

1. **版本**（RFC-0024「版本」）：
   - 规范打 `vX.Y.Z`；Go 的一致性模块在同一提交另打 `conformance/vX.Y.Z`，因为它是子目录模块。
   - MAJOR 与线上的数字一致：`FrameworkInfo.SpecVersion`、清单 `primitives`、Schema `$id`。
   - PATCH 不改规范性内容。MINOR 只增，或写死以前不作规定的行为，但不能让按较早 MINOR 实现的对端互通失败。MAJOR 改已写明的行为、删除内容或线上不兼容。
   - 新协议版本与旧版本并存算 MINOR，去掉旧版本才算 MAJOR；同一协议版本里的写死不升协议版本，也不在握手里协商 MINOR。
   - 5.0 正式版之前打 `v1.0.0-rc.N`，正式版时打 `v1.0.0`。
   - 规范新增 `CHANGELOG.md`，每个改动规范性内容的提交在「未发布」一节记一条。
2. **钉规范**：
   - 日常分支可以指向规范 `main` 上的任意提交。
   - 发预发布或正式版时，submodule 必须正好在规范标签上，Go 的 `go.mod` 用标签版本；正式版只钉正式版标签。
   - 实现在 README 的状态一节写明钉的版本、认领的档与缺口。
3. **一致性档**（RFC-0024「一致性档」）：
   - 档表 `conformance/profiles.json` 是唯一事实源，档名有：`core`；角色档 `plugin` / `host` / `wasm`；子系统档 13 个，按术语表的能力 ID 前缀命名；`provider:caching.distributed@1`。
   - 每个规范文件与向量文件至少属于一个档，RFC 的状态行写明所属的档。
   - Go 经 `conformance.Profiles()` 与 `RequiredVectors` 读取。
   - 校验：conformance 模块的测试核对向量全被覆盖、档名合文法；`tools/speccheck` 核对规范文件全被覆盖、子系统档名来自术语表、RFC 状态行与档表一致。
4. **成熟度**：
   - Reference 是 .NET。
   - Stable：认领 `core`，认领的 `stable` 档没有缺口，运行器全部通过且没有名单外的跳过，并有钉在规范正式版标签上的发布版。
   - Experimental：有缺口，或还没有这样的发布版。
   - Community：在 XiHanFun 之外维护。
   - 现状写在规范 README：.NET 是 Reference，缺口是 `core` 的 `primitives/wire-encoding.json`（原语层没有 Result 与 Error 的 JSON 编解码）；六个 SDK 都没有缺口，但还没有钉在标签上的发布版，所以都是 Experimental。
5. **ADR 的位置**：ADR 仍在 XiHan.Framework 的 `plans/adr/`。规范性的要求必须写在规范正文或向量里，不能只写在 ADR 里。

## 理由

- 规范的版本号与线上数字一致，读到 `primitives: "1"` 就知道是哪条线。
- 「写死以前不作规定的行为算 MINOR」与这一个月的实际节奏吻合，加上互通约束，不会让已发布的插件在新宿主里失灵。
- 档把「规范性」从「所有语言都要做」改成「认领了就要做到」。Stable 因此可以判定，豁免表也有了取代它的结构：认领的档里没回放的向量才是缺口。
- 档名复用术语表的能力 ID 前缀，不另起一套词汇。

## 影响

- 可观察行为不变：没有修改任何期望值、Schema 或协议。
- 现在不做的有三件，作为后续工作：
  - 七个实现的向量全集测试改为按认领的档读档表，豁免表只剩缺口。
  - XiHan.Framework 与各 SDK 的发布工作流核对规范标签。
  - 打首个规范标签 `v1.0.0-rc.1`（与 `conformance/v1.0.0-rc.1`）。打标签属于外部状态变更，等用户明确要求。
- `.NET` 的缺口（Result 与 Error 的 JSON 编解码）是 Reference 实现自己的欠账，另行处理。
- 文档：规范 README 的规范性表、版本与生态三节，`docs/appendix/spec.md` 的规范性、成熟度、版本与 RFC 表，总体方案 §9.3。
