# ADR-0348 调度的租约持有者标识拒收孤立的代理项

## 状态

已采纳。

- 规范：
  - RFC-0013「领导选举」新增一条：从选项与配置来的持有者标识（节点 ID 与 Kubernetes 的持有者）不能有孤立的代理项；「Provider」的节点 ID 指向它；状态行与「对应 ADR」已改。
  - RFC-0001「孤立的代理项」的表补上调度的节点 ID 与 Kubernetes 的持有者标识，状态行已改。
- 向量：不变。
- .NET：错误码、消息键与配置键不变。

## 日期

2026-11-27

## 背景

ADR-0334 让 `Workflow.Database` 的 `HolderId` 拒收孤立的代理项，「同类而没改的」记下了调度选项的 `NodeId`（`XiHan:Scheduling:NodeId`）：它同是租约的持有者标识，只拒空白。仓库所有者已拍板同样拒收。这次顺带查了调度各个 Provider 里别的持有者与节点标识：

1. **`SchedulerOptions.NodeId`**（`Scheduling.Abstractions`，内存与数据库实现都从 `XiHan:Scheduling` 读它）：
   - 引擎拿它写节点行（`SchedulerNodeRecord.Id`）、运行记录（`JobRunRecord.NodeId`）与抢占的触发器（`AcquiredBy`），也是取消请求的查询条件；数据库实现的领导租约以它为持有者（`DatabaseLeaderElection`）。
   - 只拒空白。实测（SQLite，修之前）：节点 ID `node-\uD800` 的节点行存成 `node-�`。抢到的触发器读回来的 `AcquiredBy` 与节点 ID 不等，引擎认为不是自己抢到的：间隔 100 毫秒的作业 3 秒里一次也没运行，同一用例换成 `node-ok` 运行了 10 次。`node-\uD800` 与 `node-\uDC00` 两个节点在节点表里只剩一行。
2. **`KubernetesSchedulingOptions.Holder`**（`XiHan:Scheduling:Kubernetes:Holder`）：
   - 完全不核对。它写进 Lease 的 `spec.holderIdentity`。
   - JSON 写出器（System.Text.Json 缺省的编码器）把孤立的代理项写成 `�`，实测请求体是 `{"holderIdentity":"pod�"}`：Lease 上看到的不是配置的持有者，只差在孤立代理项上的两个 Pod 在 Lease 上分不开。
   - 争用与续约靠 `resourceVersion` 裁决、不比较持有者，选举本身不会出错。
3. **别的标识都已有文法**：
   - 租约的资源名 `LeaseResource` 是 `JobName`（`^[a-z0-9][a-z0-9._-]{0,127}$`），Kubernetes 的 `Lease` 是 DNS 标签。
   - 进程内的选举每次获取生成新值，不从配置来。
   - `DatabaseSchedulingOptions` 只有健康探测的间隔。

## 备选

1. **节点 ID 在初始化器里拒收**：采纳。照 ADR-0334 备选 9 的 `HolderId`。
   - 空白之后判定，`UnicodeText.HasLoneSurrogate`；不合时抛出 `ArgumentException`（`The node ID must not contain lone surrogates.`），从配置读取也经它，应用启动失败。
   - 配置里的空白照旧视为没有配置，用默认值。
2. **Kubernetes 的持有者同样在初始化器里拒收**：采纳。
   - `null`（没有配置）照收；空白照旧视为没有配置，由 `ResolveHolder` 按 Pod 的约定解析。只多拒孤立的代理项，消息 `The holder identity must not contain lone surrogates.`。
3. **按约定解析出的持有者也核对**（环境变量 `XIHAN_POD_NAME`、`HOSTNAME` 与机器名）：否决。
   - Pod 名由 Kubernetes 按 DNS 子域名校验，是 ASCII；Linux 上 .NET 按 UTF-8 解码环境变量，解不出的字节换成 U+FFFD，得不到孤立的代理项。
   - 要测它就得改进程的环境变量，影响同一进程里别的用例；这次只收选项与配置这两条路。
4. **在用到它的地方核对**（`DatabaseLeaderElection`、`KubernetesLeaderElection` 的构造）：否决。选项是唯一的入口，从配置读取时失败就是启动失败，不等到解析服务；与 ADR-0334 同一处。
5. **新的错误码或返回 `Result`**：否决。这是运营方的配置，照 ADR-0321 备选 13 的选项做法抛出参数异常。
6. **向量不补**：采纳。选项没有向量文件，调度只有 .NET 实现。
7. **MAJOR（`v1.0.0` 之前允许）**：两个键收窄了以前照收的输入。

## 决策

1. **规范**（MAJOR，`v1.0.0` 之前允许）：
   - RFC-0013「领导选举」：数据库实现的节点 ID 与 Kubernetes 实现配置的持有者不能有孤立的代理项，构造选项或从配置读取即抛出参数异常、应用启动失败；成对的代理项照常，配置里的空白仍视为未配置。「Provider」的节点 ID 指向这一条。
   - RFC-0001「孤立的代理项」的表：「运营方配置的前缀、后缀与名字」一行补上这两项。
2. **.NET**：
   - `Scheduling.Abstractions`：`SchedulerOptions.NodeId` 的初始化器。
   - `Scheduling.Kubernetes`：`KubernetesSchedulingOptions.Holder` 从自动属性改成带核对的初始化器。

## 理由

- 与 ADR-0316、0321、0334 同一个理由：孤立的代理项编不成 UTF-8，宽松的编码换成 U+FFFD 之后仍是合法的文本，收的一方看不出来，不同的节点落到同一个标识上。
- 节点 ID 这一处比 `HolderId` 更重：抢占的归属按字符串比较，读回的不是原值，数据库实现上作业根本不运行，而不只是排查时对不上。
- 判定只有一份（原语的 `UnicodeText`），放在选项上：配置与代码两条路都经过它。

## 影响

- **公开 API**：签名不变，`PublicAPI` 文件不变。`SchedulerOptions` 与 `KubernetesSchedulingOptions`（都是 Preview）收窄了合法的输入。
- **程序集体积**：Primitives 103424 字节、Kernel 364544 字节（本工作区口径），都没有变。
- **对已有部署与代码的行为变化（升级须知）**：
  - `XiHan:Scheduling:NodeId` 与 `XiHan:Scheduling:Kubernetes:Holder` 有孤立的代理项时，构造选项或从配置读取抛出 `ArgumentException`，应用启动失败。以前节点 ID 照收（数据库实现上作业不运行），Kubernetes 的持有者写成 U+FFFD。
  - 迁移：去掉配置里的孤立代理项；从外部输入拼这两个值的代码先用 `UnicodeText.HasLoneSurrogate` 判断。
- **规范**（规范工作区已提交）：RFC-0001、RFC-0013。
- **六个 SDK**：不用跟，调度只有 .NET 实现。
- **CLI 知识库**：`configuration.json` 里两个键的说明补上这一条。
- **测试**：
  - `InMemorySchedulingTests.NodeId_WithALoneSurrogate_IsRejected_AndAPairIsKept`：三种孤立的代理项在代码设置与配置节两条路上都抛出，成对的代理项照常。
  - `KubernetesLeaderElectionTests.Holder_WithALoneSurrogate_IsRejected_AndAPairIsKept`：同上，另有成对代理项的持有者照常写进 Lease、`null` 照收。
  - `DatabaseSchedulingTests.NodeId_WithALoneSurrogate_FailsStartup`：配置节里的节点 ID 让装配了数据库实现的宿主启动失败。
  - 改实现之前这三条都失败。
- **文档**：`Scheduling.Database`、`Scheduling.Kubernetes` 的 README 已同步；文档站与更新日志待改。
