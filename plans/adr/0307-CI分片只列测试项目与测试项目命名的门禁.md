# ADR-0307 CI 分片只列测试项目与测试项目命名的门禁

## 状态

已采纳（`New-TestShard.ps1` 从 `test/Directory.Build.props` 的条件里取后缀，只把名字以 `.Tests` 结尾的项目列进分片的筛选器，`core` 少了 `XiHan.Framework.Testing.Workspace`，测试项目一个不少；架构测试的 `Workspace.TestProjects` 改成同一口径，命名空间门禁改看 `test` 下的全部项目；架构测试新增 `TestProjectNamingTests`：含测试的项目名字以 `.Tests` 结尾、以 `.Tests` 结尾的项目都含测试、别的类库只能是名单里的；规范不变）。

## 日期

2026-11-25

## 背景

### 分片的筛选器把类库也列了进去

ADR-0253 的 `New-TestShard.ps1` 把 `test` 下有同名项目文件的目录都算作测试项目。ADR-0300 加了不发包的类库 `XiHan.Framework.Testing.Workspace` 之后，它也在里面：

- `core` 的筛选器列了 58 个项目，其中它不是测试项目。`test/Directory.Build.props` 只给名字以 `.Tests` 结尾的项目设 `IsTestProject` 与测试用的包，`dotnet test` 跳过它，结果不受影响；但筛选器说的是「这一片的测试项目」，列出的并不都是。它本来就由引用它的测试项目带进构建，不必列。
- 架构测试的 `Workspace.TestProjects` 用的是同一个口径：分片表把它列进某一片，`TestShardTests` 不报。
- ADR-0300 的「影响」记过这两处，当时认为不用改。仓库所有者已拍板：分片只列测试项目，判定口径与 `test/Directory.Build.props` 相同，不另起一套规则。

### 名字写错的测试项目悄悄不跑

`test/Directory.Build.props` 按 `$(MSBuildProjectName.EndsWith('.Tests'))` 设测试项目的属性、四个包（`Microsoft.NET.Test.Sdk`、`Microsoft.Testing.Extensions.CodeCoverage`、`xunit.v3`、`xunit.runner.visualstudio`）与 `using Xunit`。名字写成 `.Test`、`Tests`（少了点）的测试项目：

- 不是测试项目，`dotnet test` 不运行它，`New-TestShard.ps1` 也不把它列进任何一片。
- 并不总是编不过：13 个 `*.Conformance` 包都依赖 `xunit.v3.extensibility.core`，引用了一致性套件的项目自己写上 `using Xunit;` 就能编过 `[Fact]`。构建是绿的，用例一条也不跑。
- 反过来，名字以 `.Tests` 结尾的类库会被当成测试项目，加上测试 SDK 与 xUnit。
- 没有门禁拦这两种情形。仓库所有者已拍板：架构测试核对两个方向，不以 `.Tests` 结尾的类库写成门禁里的名单，加新的要改门禁。

### 仓库里测试的写法

改前的检出有 68 个测试项目和 1 个类库，「含测试」照这些事实来认：

- `test` 下的源码有 2605 处 `[Fact]`、268 处 `[Theory]`，都独占一行，没有参数、没有命名空间前缀、不与别的特性写在同一对方括号里；没有从 `FactAttribute` / `TheoryAttribute` 派生的特性。
- 一致性套件：`src` 下 13 个 `*.Conformance` 包里有 29 个抽象类声明了共 280 处 `[Fact]`，32 个测试项目里有类从它们派生、继承这些用例；`MessageStreamConformance` 从 `MessageBrokerConformance` 派生。
- `test` 下的项目文件都不写 xUnit 与测试 SDK 的引用，也不设 `IsTestProject`：这些全由 `test/Directory.Build.props` 按名字加。项目文件因此分不出谁含测试，要看源码。
- 68 个测试项目每个都有自己声明测试方法的源文件（最少的 9 个项目各 1 个）；`Testing.Workspace` 一个也没有。

## 备选

1. **分片脚本按「源码里有 `[Fact]`」或「引用 xUnit」判定**：否决。另起一套规则：脚本与 MSBuild 的看法分开时，筛选器里会有 `dotnet test` 不运行的项目，或漏掉它运行的项目。
2. **脚本里写死 `.Tests`**：否决。后缀成了两份，`test/Directory.Build.props` 改了，脚本不跟着改。从它的条件里取，取到的后缀不止一种时报错。
3. **脚本对每个项目求 MSBuild 的 `IsTestProject`**（`dotnet msbuild -getProperty:IsTestProject`）：否决。本机每次求值约 0.4 秒，69 个项目约半分钟，每个分片作业都要在还原之前付一遍；`test/Directory.Build.props` 只按名字判定（下面的门禁核对这一点），按名字取与求值的结果相同。
4. **「含测试」看项目文件里的 xUnit 引用**：否决。`test` 下的项目文件都不写，由 `test/Directory.Build.props` 按名字加，看不出来。项目文件自己引用这些包另作一条规则拦下（决策 7）。
5. **只认 `[Fact]` / `[Theory]` 的字面**：否决。只从一致性套件派生的测试项目（新 Provider 的测试常这样起步）会被判成不含测试。套件按「`src` 下声明测试方法的抽象类，及从它们派生的抽象类」现场找，不写死名单。
6. **识别从 `FactAttribute` 派生的自定义特性**：这次不做。仓库里没有这样的特性。认不出它只影响两种情形：以 `.Tests` 结尾、只用自定义特性的项目被报「不含测试」（失败，看得见）；名单里的类库用了它而没被认出（静默）。名单只有一个项目，加进名单要改门禁、经过评审，到有这样的特性时再扩识别。
7. **不列名单，非 `.Tests` 的项目只要不含测试就放行**：否决（仓库所有者拍板）。识别漏掉的写法会让含测试的类库静默通过；名单让每个新类库都要改一次门禁。
8. **名单放在 `test/Directory.Build.props` 或单独的 JSON 文件**：否决。名单只给门禁用，写在门禁里，加一个类库就是改一次架构测试。
9. **另核对 `test` 下的项目都在 `XiHan.Framework.slnx` 里**：这次不做。漏加的测试项目被 `New-TestShard.ps1` 列进筛选器后，`dotnet build` 以 MSB4025（筛选器里的项目不在解决方案里）失败，不是静默的。

## 决策

### 分片只列测试项目

1. `New-TestShard.ps1` 从 `test/Directory.Build.props` 里形如 `$(MSBuildProjectName.EndsWith('<后缀>'))` 的条件取后缀，要求只有一种（现在是 `.Tests`），否则报错；测试项目是 `test` 下名字以它结尾、有同名项目文件的目录。分片表列了不是测试项目的名字时，报错消息改说「不是测试项目」。
2. 改前改后各生成四个分片的筛选器对比：`core` 从 58 个项目到 57 个，只少了 `test/XiHan.Framework.Testing.Workspace/XiHan.Framework.Testing.Workspace.csproj`；`integration`（9 个）、`database`（2 个）、`oracle`（1 个）逐字相同；改后四片的并集正好是 68 个以 `.Tests` 结尾的项目，改前的并集多出的只有 `Testing.Workspace`。
3. 架构测试的 `Workspace` 新增常量 `TestProjectSuffix`、`IsTestProjectName`、`TestDirectoryProjects`（`test` 下的全部项目）与 `ProjectFiles`（任意深度的项目文件）；`TestProjects` 只含名字以 `.Tests` 结尾的，`TestShardTests` 因此也不认分片表里的类库，失败消息同样改说「不是测试项目」；命名空间的两条门禁（`AllProjects`）改用 `TestDirectoryProjects`，`Testing.Workspace` 照旧在内。

### 测试项目的命名门禁

4. 架构测试新增 `TestProjectNamingTests`，五条用例：
   - `DirectoryProps_MarksTestProjectsByTheNameSuffixAlone`：`test/Directory.Build.props` 判项目名的条件只有 `$(MSBuildProjectName.EndsWith('.Tests'))` 一种，`IsTestProject` 只在它下面设一次，它下面有包引用。脚本取后缀、门禁按名字认测试项目，都靠这一点成立。
   - `ProjectFiles_SitInADirectoryOfTheirName`：`test` 下任意深度的项目文件都在 `test/<名>/<名>.csproj`。脚本与架构测试只认这个位置，放在别处或文件名与目录不同的项目不进任何一片。
   - `ProjectsUnderTest_ContainTestsExactlyWhenNamedAsTestProjects`：以 `.Tests` 结尾的项目必须含测试、不在名单里；不以它结尾的项目不许含测试（先报这一条，即使它在名单里），且必须在名单 `_libraries` 里（现在只有 `XiHan.Framework.Testing.Workspace`）；名单里的项目必须存在。
   - `ProjectFiles_LeaveTestProjectSettingsToTheDirectoryProps`：项目文件不设 `IsTestProject`，不引用 `test/Directory.Build.props` 给测试项目加的包（从它读，包 ID 不分大小写）。否则 `dotnet test` 与分片对同一个项目的看法会分开：设成 `false` 的 `.Tests` 项目不运行，自己引用测试 SDK 的非 `.Tests` 项目在整个解决方案里运行、在 CI 的分片里不运行。
   - `Recognition_FollowsHowTheRepositoryWritesTests`：拿代码片段核对识别（下一条的七种写法认得出，注释、索引器、`[InlineData("a", Fact)]`、`[MemberData(nameof(Theory))]`、`[FactOfTheDay]`、`[Facts]` 不误认；从套件派生的三种写法认得出，名字里带套件名、成员类型是套件的不误认；只经派生的抽象类算套件，不是抽象类的不算），并核对 `src` 里找得到 `CacheStoreConformance`、泛型的 `IdGeneratorConformance` 与派生的 `MessageStreamConformance`。
5. 「含测试」的认法：项目自己的源码里有行首的 `[Fact]` / `[Theory]`（可带 `Xunit.` 或 `global::Xunit.` 前缀、`Attribute` 后缀与参数，可与别的特性写在同一对方括号里），或有类的基类列表里出现一致性套件。套件是 `src` 下声明测试方法的源文件里的抽象类（一个文件一个类型），加上从套件派生的抽象类，反复找到没有新的为止。
6. 门禁先红后绿，反例都是临时加的，验证后删掉，不在提交里：
   - 把 `Testing.Workspace.Tests` 复制成 `XiHan.Framework.Probe.Test`：报「含测试但名字不以 `.Tests` 结尾」，并列出声明测试方法的文件。
   - 在 `Testing.Workspace` 里加一个带 `[Fact]` 的文件与一个从 `CacheStoreConformance` 派生的类：报同一条，列出两处。
   - 只有项目文件的 `XiHan.Framework.Empty.Tests`，与只在注释里写着 `[Fact]` 的 `XiHan.Framework.Comment.Tests`：报「以 `.Tests` 结尾却不含测试」。只从 `MessageStreamConformance` 派生的 `XiHan.Framework.Suite.Tests` 通过。
   - 不在名单里、不含测试的 `XiHan.Framework.Testing.Fixtures`：报「不在名单里」。
   - 把 `Testing.Workspace` 改名为 `Testing.Workspaces`：报新名字不在名单里、名单里的 `Testing.Workspace` 不存在。
   - `test/XiHan.Framework.Empty.Tests/Nested/Other.Tests.csproj`：报位置不对。
   - `Primitives.Tests` 的项目文件加上 `<IsTestProject>false</IsTestProject>` 与 `XUnit.v3` 的引用：两条都报。
   - `test/Directory.Build.props` 里一处条件改成 `EndsWith('.Test')`：门禁报出这个条件，`New-TestShard.ps1` 报取到两种后缀。
   - 分片表把 `Testing.Workspace` 列进 `database`：`New-TestShard.ps1` 报它不是测试项目，`TestShardTests` 同样失败。

### 说明的同步

7. `test/Directory.Build.props` 的注释写明脚本从它取后缀、门禁核对它；技能的 `testing-and-release.md`（CI 的测试分片）与 `gates.md`（架构测试覆盖）补上这条门禁。

## 理由

- 测试项目只由名字决定：MSBuild、分片脚本与架构测试用的是 `test/Directory.Build.props` 里的同一个后缀，脚本从它取，门禁核对它只按这个后缀判定，三处不会各说各的。
- 名字写错的代价是用例悄悄不跑、CI 照样是绿的；这种错只能在跑用例之前，看文件系统查出来。
- 「含测试」照仓库实际的写法认，认法的边界写在门禁的说明里。认漏的写法在以 `.Tests` 结尾的项目上表现为失败；在类库上才会静默，而类库要先进名单，名单在门禁里。

## 影响

- CI：`core` 作业的筛选器少一个项目，构建与运行的用例不变（`Testing.Workspace` 照旧经项目引用构建）。
- 新加测试项目：名字以 `.Tests` 结尾、放在 `test/<名>/<名>.csproj`，不用登记。新加给测试项目引用的类库：名字不以 `.Tests` 结尾，加进 `TestProjectNamingTests` 的 `_libraries`。
- 以后要改测试项目的后缀：改 `test/Directory.Build.props` 的条件，脚本跟着取；架构测试的 `Workspace.TestProjectSuffix` 要一起改，测试项目都要改名。
- 用例数：`Architecture.Tests` 多 5 条（89 → 94），别的测试项目不变。
