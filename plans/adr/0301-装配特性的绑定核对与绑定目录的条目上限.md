# ADR-0301 装配特性的绑定核对与绑定目录的条目上限

## 状态

已采纳（规范 RFC-0016「资源绑定与配置节」第 6、8 条与新增的第 10 条、RFC-0002 的字段表与解析规则 4、RFC-0001「JSON 文本」、`plugin/lifecycle.md` §2、`conventions/error-codes.md` 的 `KERNEL_HOSTING_001` 与 `KERNEL_HOSTING_005`、清单 Schema 的 `bindings[].required` 说明已改，向量 `plugin/binding-properties.json` 的 `limits` 与 `plugin/plugin-messages.json` 的 `reasons` 已补；内核的 `AppBuilder` 改用 `PluginBindingRules` 核对特性的绑定，`BindingResolver` 新增 `MaxBindingFiles`、`MaxBindings`，`PluginContext` 新增 `ServiceBindingRoot`；`Plugins.InProcess` 的 `InProcessPluginHost` 构造时收根目录；`Plugins.Protocol` 的 `PluginJson.ParseDetails` 改用严格的 UTF-8 编码；Go 一致性模块加两个常量与对应的核对）。

## 日期

2026-11-25

## 背景

ADR-0292 收紧了插件宿主一侧的绑定，「待定」里留下三件事；另有一处 JSON 文本的编码与别处不一致。仓库所有者已拍板，四件都做，契约先进规范。

1. **内核装配特性时的核对与插件宿主不是一套规则。** `AppBuilder.Build` 只核对清单里 `Required` 的绑定：来源里有这个名字就算给出，只给了类型（`XiHan:Bindings:db:type`，或只有 `type` 文件的绑定目录）的必需绑定照常装配，特性拿到的 `BindingValue` 没有主值也没有属性，第一次连接时才失败；可选的绑定不核对类型，给错了类型照样交给特性。插件宿主（ADR-0292）对同一份清单、同一个字段的判断是：没有主值也没有属性就是没给，可选的也核对类型。框架 Provider 声明的绑定全是可选的（EF Core、SqlSugar 的 `db`，`Caching.Redis` 的 `cache`，三种消息 Provider 的 `queue` / `stream`，S3 的 `objectstorage`，Nacos 的 `nacos`），所以装配特性时框架自己的绑定一个也不核对类型：`db` 挂成一个 `queue` 类型的绑定，EF Core 拿着 AMQP 的地址去连关系库。
2. **绑定目录的条目数不限**（ADR-0292 备选 8）。ADR-0292 只限了字节数：一个文件 512 KiB、一个绑定合计 1 MiB。空文件不占字节的额度，一个绑定目录里放上几万个空文件，每个都读成一项属性进内存；根目录下的绑定个数也不限，`SERVICE_BINDING_ROOT` 指错到一棵大目录树（日志目录、家目录）时，每个子目录都当成一个绑定读，每个最多 1 MiB，总量没有上界。
3. **进程内插件只认环境变量的根目录**（ADR-0285 待定、ADR-0292 待定）。`InProcessPluginHost` 没有特性入口，构造时只收配置；加载前的核对用 `BindingResolver.Resolve(configuration)`，根目录取环境变量 `SERVICE_BINDING_ROOT`，插件自己读绑定也只能这样读。应用经 `UseServiceBindingRoot` 指定了别的目录时，内核与另两种插件宿主读那个目录，进程内宿主核对的、插件读到的却是环境变量指的目录：核对可能在一个与内核不同的目录上通过或失败。
4. **`PluginJson.ParseDetails` 用宽松的 UTF-8 编码。** 它把错误细节的文本经 `Encoding.UTF8.GetBytes` 变成字节再过共同检查，字符串里的孤立代理项被悄悄换成 U+FFFD，读出一份本不合法的细节；内核的 `ResultJson.Read(string)` 与 `ManifestReader.Read(string)` 用的是严格编码，同样的输入按不是 JSON 处理。核对现状：经 gRPC 二进制收到的字符串由 Google.Protobuf 按 UTF-8 解码（非法字节换成 U+FFFD），出不了孤立代理项；Wasm 载体的 proto3 JSON 解析器遇到转义出的孤立代理项即拒绝整条消息（`PluginJsonCodec.Decode` 返回空）。所以眼下从线上到不了这条路，宽松编码只在进程内的调用里起作用，但规则应当一致。

## 备选

装配特性时的核对：

1. **内核另写一份与 `PluginBindingRules` 相同的判断**：否决。两份规则迟早走样；仓库所有者要的是同一处。
2. **把规则挪到 `Kernel.Hosting` 并改名（如 `BindingRules`）**：否决。`PluginBindingRules` 就在内核程序集里、是公开的 `Preview` 类型，`AppBuilder` 直接用得到，能复用就不挪；改名要牵动三个插件宿主包、README、文档站与 SDK 文档里的引用，换来的只是名字。它的说明写明「内核装配特性用的是同一处，名字里的 Plugin 是最初的使用方」。
3. **只把「只有类型」并入「没给出」，可选的照旧不核对类型**：否决。框架 Provider 的绑定全是可选的，这样等于框架自己的绑定照旧一个也不核对类型；可选的绑定一旦给出，特性同样会拿它去连（ADR-0292 备选 17 的理由对特性一样成立）。
4. **可选的绑定类型不符时当作没有（`FindBinding` 返回无值）并记警告**：否决。理由同 ADR-0292 备选 18：悄悄少给一个运营方明明给了的绑定，比启动失败更难查。
5. **装配特性时对清单声明的每个绑定调用 `PluginBindingRules.FindViolation`，按清单的顺序报第一处，启动失败**：采纳。错误码照旧是 `KERNEL_HOSTING_001`，它的处置（补上或改正绑定）不变。被顶替的节点照旧不装配、不核对。
6. **为「只有类型」另登记一个错误码**：否决。处置与「没给」相同。
7. **异常消息保留以前的两种句式**（`Binding 'db' (connection:relational) required by feature '…' is not provided.` 与 `… must be of type …`）：否决。规则的文本只在一处，内核在外面包一层带特性 ID 的句子：`Feature '<清单 ID>' is not configured: <reason>.`，与进程内宿主的日志 `Plugin <ID> is not loaded: <reason>.` 同一个形状。「没给」的句子不再带清单声明的类型：类型不是没给的原因；类型不符时两个类型都在 `reason` 里。

条目数的上限：

8. **只限一个绑定目录的文件数**：否决。根目录下的绑定数同样无界，指错根目录是比放错文件更常见的事故。
9. **文件数取 64 或 65（下发给插件的属性上限，加 `type` 文件）**：否决。宿主进程里的特性读绑定不受下发的限制（ADR-0292 备选 2 同一理由），正好卡在下发上限上没有余量。
10. **一个绑定目录最多 128 个文件，根目录下最多 128 个绑定**：采纳。文件数是下发上限 64 的两倍：`type` 文件之外，下发得了的属性一定读得进来，读得进来而下发不了的绑定仍可以给宿主进程里的特性用，与 ADR-0292 两个字节上限都是下发上限两倍以上的关系相同；Go 一致性模块核对「文件数不小于 64 + 1」。绑定数取同一个数：框架 Provider 一共读七个绑定名，一个应用连同它的插件声明到上百个绑定是没见过的部署，解析全部绑定读进内存的内容由此有了上界（128 × 1 MiB，条目 128 × 128 个）；两个上限同一个数，运营方只记一个。
11. **以 `.` 开头的文件也计入文件数**：否决。与 ADR-0292 字节数的口径相同：它们不读、不进结果、不占内存；Kubernetes 挂载 Secret 时放的 `..data` 与带时间戳的目录是目录，本来也不在文件里。
12. **以 `.` 开头的子目录不算绑定**：这次不改。现在它们照样读成绑定（目录名就是绑定名），计数跟读的口径走，每个子目录都计入；要不要跳过是另一件事，记为待定。
13. **边读边数，读到第 129 项时失败**：否决。先数、后读：根目录先数子目录，每个绑定先数文件，多出一项时这一层一个字节也不读，报出来的是条目数，而不是碰巧先读到的某个超大文件；数的时候最多枚举到上限再多一项，不把整个目录列进内存。
14. **只解析点了名的绑定时（插件宿主）也数根目录下的绑定数**：否决。点名时只读那几个目录（ADR-0268：别的绑定读不出来不影响这个插件），根目录下有多少绑定与它无关；被点名的绑定照样核对文件数。
15. **错误码**：沿用 `KERNEL_HOSTING_005`，登记表与 `KernelErrors.BindingTooLarge` 的说明扩写为「绑定目录超过大小或条目数的上限」：采纳。处置相同（把不属于绑定的东西挪走、改正根目录），这个码是 ADR-0292 在同一个「未发布」里加的；另登记新码否决。
16. **消息与 `reason`**：内核的消息只带绑定名与上限，不带路径与文件名：`Binding '<绑定>' has more than 128 files.`、`The service binding root contains more than 128 bindings.`。插件宿主的固定 `reason` 为 `binding '<绑定名>' has more than 128 files`，与 `binding '<绑定名>' has more than 64 properties` 同一个句式，登记进 `plugin-messages.json`。
17. **内部类型**：`BindingTooLargeException` 的 `Total`（布尔）换成 `Limit`（internal 枚举 `BindingLimit`：`FileBytes`、`TotalBytes`、`FileCount`），`Plugins.Protocol` 按它写三种 `reason`。根目录的绑定数超限直接抛携带 `KERNEL_HOSTING_005` 的 `FrameworkException`：那时没有具体的绑定，插件宿主也碰不到它。

进程内插件的根目录：

18. **给 `Plugins.InProcess` 加特性入口，从 `FeatureContext.ServiceBindingRoot` 取根目录**：否决。进程内宿主是应用在构建之后自己创建、持有的对象（文档的推荐用法），加特性要定能力 ID、清单与生命周期，牵动面远大于一个参数。
19. **内核在构建之后公开根目录（`App.ServiceBindingRoot`，或登记进容器），进程内宿主从那里取**：否决。`App` 是 `Stable` 类型，为一个调用方加成员；进程内宿主不收 `IServiceProvider`；应用交给 `UseServiceBindingRoot` 的值它自己手里就有。
20. **构造函数加可选参数 `serviceBindingRoot`**（与 `OutOfProcessPluginHost`、`WasmPluginHost` 的同名参数同义，`null` 取环境变量），加载前的核对按它解析：采纳。
21. **插件一侧：`PluginContext` 加 `ServiceBindingRoot`**（与 `FeatureContext.ServiceBindingRoot` 同名同义），插件把它与 `Configuration` 交给 `BindingResolver.Resolve`：采纳。插件读到的与宿主核对的是同一套来源。
22. **`PluginContext` 加 `Bindings`（宿主核对过的那一份）**：否决。理由同 ADR-0285 备选 20：插件要的是与宿主同一个来源，根目录给了、读法就是公开的 `Resolve`；多一份字典是多一份不随挂载轮换更新的快照。
23. **`PluginContext` 的构造加可选参数，不另加重载**：采纳。PublicAPI 只有一行；没有包验证基线（ADR-0131），已有的五个参数的调用照样编译。

严格的 UTF-8：

24. **照 `ResultJson` 改用 `throwOnInvalidBytes` 的 `UTF8Encoding`，编码失败按这个方法现有的失败语义处理（当作没有细节，返回空）**：采纳。
25. **编码失败时把整个错误换成 `PLUGINS_UNEXPECTED_001`**：否决。`ParseDetails` 的失败语义一直是「当作没有细节」（`invocation.md` §3），通不过共同检查的细节就是这样处理的，错误本身照常读入。
26. **规范只在 `invocation.md` §3 写**：否决。规则属于 RFC-0001「JSON 文本」的「文本按 UTF-8 编码」，`ResultJson`、`ManifestReader` 早已照此严格；写在共同检查那里，各语言以字符串交来文本的地方同一口径（2026-11-25 写明）。
27. **加向量**：否决。向量文件要先被各语言的 JSON 读取器读进来：System.Text.Json 读到转义出的孤立代理项即抛，Go 换成 U+FFFD，Python 原样保留，同一条向量在各语言里得到的输入不同；由 .NET 的单元测试核对。

## 决策

1. **装配特性的绑定核对与插件宿主同一套规则**（RFC-0016「资源绑定与配置节」第 8 条、RFC-0002 字段表、`plugin/lifecycle.md` §2「`bindings` 的核对」）：`AppBuilder.Build` 对每个装配的节点，按清单的顺序对每个声明的绑定调用 `PluginBindingRules.FindViolation`，第一处不合即抛 `FrameworkException(KernelErrors.MissingBinding)`，消息 `Feature '<清单 ID>' is not configured: <reason>.`。不合的两种：必需的绑定没有内容（两种来源都没给，或只给了类型）；来源声明的类型与清单不同（必需与可选都核对，按序数比较）。可选的没有内容照常装配。被顶替的节点不核对。
2. **绑定目录的条目数上限**（RFC-0016「资源绑定与配置节」第 10 条）：
   - `BindingResolver.MaxBindingFiles` = 128：一个绑定目录里读的文件（以 `.` 开头的不计）多于 128 个即解析失败；`BindingResolver.MaxBindings` = 128：解析全部绑定时根目录下的子目录多于 128 个即解析失败。
   - 先数、后读，最多枚举到上限再多一项；点了名的解析只数被点名的绑定的文件，不数根目录下的绑定。
   - 超限抛携带 `KERNEL_HOSTING_005` 的 `FrameworkException`，装配时启动失败；插件宿主按配置这一步失败处理，`reason` 为 `binding '<绑定名>' has more than 128 files`。配置来源不受约束。
3. **进程内插件与应用用同一个绑定根目录**（`plugin/lifecycle.md` §2、RFC-0016 第 6 条）：`InProcessPluginHost(configuration, loggerFactory, serviceBindingRoot = null)`，加载前按 `BindingResolver.Resolve(configuration, serviceBindingRoot)` 核对；`PluginContext` 带上同一个值（`ServiceBindingRoot`）。应用经 `UseServiceBindingRoot` 指定了根目录时把同一个值交给构造函数。
4. **`PluginJson.ParseDetails` 严格编码**（RFC-0001「JSON 文本」）：先以 `throwOnInvalidBytes` 的 UTF-8 编码，编码不成（孤立的代理项）即当作没有细节，再过共同检查。

## 理由

- 同一份清单、同一个字段，在特性与插件上含义一样：只有类型的绑定对谁都没有用，给错了类型的绑定对谁都危险。规则只在 `PluginBindingRules` 一处，四个使用方（内核与三种插件宿主）的结论与文本都一样。
- 字节数的上限保护不了「很多个很小的条目」：条目数与字节数一起，才让一次解析读进内存的量有界。先数后读，让超限的报错稳定地指向条目数，而不取决于文件系统先列出哪个文件。
- 进程内插件拿的是整个宿主配置，信任边界与隔离运行的插件不同（ADR-0177），但「读哪个目录」与信任无关：内核、三种插件宿主与插件自己都应当读同一个目录，核对才有意义。
- 以字符串交来的 JSON 文本，按 UTF-8 编码时只有一种结果：要么是合法的 UTF-8，要么不合法；换成 U+FFFD 是替调用方改写了文本。

## 影响

- **公开 API**（`PublicAPI.Unshipped.txt` 已同步）：
  - `Kernel`：`BindingResolver.MaxBindingFiles`、`BindingResolver.MaxBindings`（都是 128）；`PluginContext` 的构造加可选参数 `string? serviceBindingRoot = null`，新属性 `PluginContext.ServiceBindingRoot`。`KernelErrors.MissingBinding`、`BindingTooLarge` 与 `PluginBindingRules` 的说明扩写。internal：新枚举 `BindingLimit`，`BindingTooLargeException.Total` 换成 `Limit`。
  - `Plugins.InProcess`：构造加可选参数 `string? serviceBindingRoot = null`。
  - `Plugins.Protocol`、`Plugins.OutOfProcess`、`Plugins.Wasm`：公开面不变。
  - 没有新的错误码与消息键；`KERNEL_HOSTING_001`、`KERNEL_HOSTING_005` 的含义扩写；`plugin-messages.json` 多一条固定 `reason`。
- **对已有部署与代码的行为变化（升级须知）**：
  - 特性声明的必需绑定只给了类型（`XiHan:Bindings:<名>:type`，或只有 `type` 文件的绑定目录）：应用启动失败（`KERNEL_HOSTING_001`）；以前照常装配。补上主值或属性，或去掉这个只有类型的绑定。
  - 特性声明的可选绑定给出了内容、来源声明的类型却与清单不同：应用启动失败；以前照常交给特性。框架 Provider 的绑定都是可选的，这一条对它们都生效：改正来源的 `type`，或去掉它（来源不声明类型时取清单的）。
  - `KERNEL_HOSTING_001` 的异常消息改为 `Feature '<清单 ID>' is not configured: <reason>.`：按消息文本匹配的脚本与测试跟着改（错误码不变）。
  - 一个绑定目录里多于 128 个文件（以 `.` 开头的不计），或根目录下多于 128 个子目录：应用启动失败（`KERNEL_HOSTING_005`）；插件声明的绑定多于 128 个文件时插件配置失败。把不属于绑定的文件或目录挪走，或改正 `SERVICE_BINDING_ROOT`。
  - 应用经 `UseServiceBindingRoot` 指定了根目录、又用进程内插件的：把同一个值交给 `InProcessPluginHost` 的构造函数；插件里读绑定的 `BindingResolver.Resolve(context.Configuration)` 改成 `BindingResolver.Resolve(context.Configuration, context.ServiceBindingRoot)`。不改的照旧读环境变量的目录。
  - 错误细节的文本里有孤立的代理项时当作没有细节（以前换成 U+FFFD 读出）。
- **规范（规范工作区已提交）**：RFC-0016 第 6、8 条与新增第 10 条、错误码一节与状态行；RFC-0002 字段表里 `bindings`、解析规则 4 与状态行；RFC-0001「JSON 文本」第一条与状态行；`plugin/lifecycle.md` §2（`bindings` 的解析里文件数超限的 `reason`，「与宿主进程里的特性的区别」改成相同，进程内插件的根目录）；`conventions/error-codes.md` 的 `KERNEL_HOSTING_001`、`KERNEL_HOSTING_005`；清单 Schema `bindings[].required` 的说明；`conformance/vectors/plugin/binding-properties.json` 的 `limits` 加 `maxBindingFiles`、`maxBindings` 与 `$comment`；`plugin-messages.json` 的 `reasons` 加一条、两条 `when` 补上内核的用法；`conformance/README.md` 的那一行。条目数的上限与装配特性的核对是规范的 MAJOR（`v1.0.0` 之前允许），进程内插件的根目录是 MAJOR（以前写明取环境变量），RFC-0001 那一句是写明（MINOR）。
- **Go 一致性模块**：`rules.MaxBindingDirectoryFiles`、`rules.MaxBindingDirectories`；`conformance.BindingPropertyLimits` 加 `MaxBindingFiles`、`MaxBindings`；测试核对它们与向量相同、文件数不小于下发的属性上限加一。
- **六个 SDK**：插件一侧的行为不变（核对都在宿主）。`plugin-messages.json` 多了一条宿主一侧的 `reason`，按「向量里的每一条都要在 SDK 里有对应」核对的测试要把它列进宿主一侧的名单。读错误细节时把字符串编码成 UTF-8 再检查的 SDK 改用严格编码（见报告；从 protobuf 线上收到的字符串出不了孤立代理项，属于口径一致）。
- **待定**：
  - 根目录下以 `.` 开头的子目录照旧读成绑定（备选 12）。
