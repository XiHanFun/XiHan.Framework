# ADR-0346 错误文案替换的共同向量

## 状态

已采纳（规范新增向量 `conformance/vectors/plugin/error-text-writing.json`，进 `plugin` 档；`plugin/invocation.md` §3「写出 `Error` 的文案」与 §7、RFC-0017 状态行、`conformance/README.md` 已改；一致性模块新增类型化入口 `conformance.ErrorTextWriting` 与规则函数 `rules.WriteErrorText`、`rules.WriteErrorTextUTF16`、`rules.WriteErrorTextCodePoints`；本仓库只加回放测试，代码不变）。

## 日期

2026-11-27

## 背景

ADR-0339 让写进插件协议的 `Error` 文案按 Unicode 的「最大子部分」换成 U+FFFD，分 UTF-16、Python 的 `str`、字节串三种写法写进 `invocation.md` §3；六个 SDK 各自写了用例，用例的个数与写法不同（Go 18 条字节串、Python 6 条 `str`、PHP 与 Java 各一组），规范没有向量，ADR-0339「影响」把加不加留给所有者。仓库所有者拍板：做向量，进 `plugin` 档，六个 SDK 同一轮回放；期望值由 .NET 算出。

## 备选

输入的写法（向量文件本身要过严格读取，孤立代理项的转义会被共同检查拒绝）：

1. **UTF-16 的输入写成码元的十六进制数组**（`"utf16": ["0061", "D800", "0062"]`）：采纳。与 `baggage-keys.json`、`cache-keys.json`、`blob-keys.json` 等已有的 `utf16` 写法相同（RFC-0012「一致性」的组法，一致性模块已有 `CodeUnits` 类型，.NET 已有 `SpecVectors.FromCodeUnits`），各 SDK 都已有组字符串的代码。
2. **UTF-16 的输入写成 JSON 字符串里的 `\uD800`**：否决。共同检查拒收孤立代理项的转义；各语言的 JSON 读取器读法不同（System.Text.Json 抛出，Go 换成 U+FFFD，Python 原样保留，ADR-0316）。
3. **字节的输入写成十六进制字符串**（`"hex": "61eda08062"`）：采纳，与 `json-text.json` 的 `hex` 相同。
4. **Python 的 `str` 另设一组码点**（`"codePoints": ["0061", "D83D", "DE00", "0062"]`）：采纳。ADR-0339 给 `str` 的规则是每个代理项码点一段、成对出现的两个也各是一段；按 RFC-0012 从码元组 `str` 时成对的代理项合成一个码位，写不出这种情形。码点按四到六位十六进制写，允许 U+D800–U+DFFF。
5. **期望值写成十六进制的 UTF-8 字节**：否决。替换之后总是合法的 Unicode，写成 JSON 字符串严格读取照常读得出，人也读得懂；ASCII 以外一律写成 `\uXXXX` 转义（平面以外的字符写成成对的两个转义），U+FFFD 在文件里看得见是 `�`。
6. **字节串的语言另按 WTF-8 回放 UTF-16 一组**：否决。编成 UTF-8 的孤立代理项在字节里是三段，换出三个 U+FFFD，与 UTF-16 一组的期望值（一个）不同；各语言只回放与自己存放字符串的方式相同的那一组，Python 另按 RFC-0012 的组法回放 UTF-16 一组（组出的 `str` 只在孤立的代理项上有代理项码点，结果与 UTF-16 相同）。

期望值与档：

7. **由 .NET 算出**：采纳。UTF-16 一组经 `Encoding.UTF8` 编码再解码（与 `PluginErrorMapper.ToProto` 写出的相同，ADR-0339），码点一组逐个码点照此（代理项码点以单个码元交给它），字节一组经 `Encoding.UTF8.GetString`；生成程序放在临时目录、不提交。另用 Python 的 `bytes.decode('utf-8', 'replace')` 与 `bytes.decode('utf-16-be', 'replace')` 核对字节与 UTF-16 两组，一致性模块的三个规则函数独立实现、回放同一份文件（Go 的 `utf16.Decode` 本来就把不成对的代理项换成一个 U+FFFD，字节一侧按 Unicode 标准表 3-7 自己写）。
8. **只进 `plugin` 档**：采纳（拍板）。宿主一侧同样经这条规则写出（.NET 的 `PluginErrorMapper.ToProto`），也可以进 `host` 档；这次照拍板只进 `plugin`，.NET 照样回放（`SpecVectorCoverageTests` 只要求认领的档都有回放，多回放不受限）。是否也进 `host` 档留给所有者（报告另列）。
9. **规则函数放进一致性模块**：采纳。向量文件都由规则包回放（`conformance` 技能），Go SDK 可以直接改用 `rules.WriteErrorText` 代替自己的 `scrubText`。

覆盖的情形：UTF-16 一组是 ADR-0339 用例里的八种（单独的高、低代理项，颠倒的一对，末尾的高代理项，开头的低代理项，连着的两个高代理项，成对之后多一个低代理项，多一个高代理项之后成对）加只有一个低代理项，合法的成对代理项、U+FFFD 本身与基本平面的多字节文本；码点一组是单独的、成对出现的、颠倒的代理项码点，平面以外的字符与 U+FFFD；字节一组是编成 UTF-8 的高、低代理项与分开编码的一对，截断的四、三、二字节序列（在 ASCII 之前与末尾），截断之后紧跟合法序列，`C0` `C1` 与三、四字节的过长编码，`F4 90` 起头的越界，`F5`–`FF`，单独的延续字节，Unicode 标准表 3-8 的连续几段非法，合法的四字节字符、U+FFFD 本身、代理项两侧的 U+D7FF 与 U+E000、U+10FFFF 与多字节文本。

## 决策

1. **规范**：
   - 新增 `conformance/vectors/plugin/error-text-writing.json`（`utf16` 12 条、`codePoints` 5 条、`bytes` 24 条），`$comment` 写明三组输入的写法、谁回放哪一组、期望值怎样算出与核对；进 `plugin` 档。
   - `plugin/invocation.md` §3「写出 `Error` 的文案」末尾加一条指向向量，§7 补上由实现的测试回放；RFC-0017 状态行同日再补充，对应 ADR 加 0346。
   - 一致性模块：`vectors.go` 的类型（`ErrorTextWritingVectors` 等）与入口 `ErrorTextWriting`，`rules/errortext.go` 的三个函数，`rules/plugin_test.go` 的回放（UTF-16 一组要盖住孤立代理项的四种写法与成对的代理项，码点一组要有成对出现的两个代理项码点，合法的原样、不合法的至少换出一个 U+FFFD），`vectors_test.go` 的非空核对，`conformance/README.md` 的向量表与规则表。
2. **.NET**：`Plugins.OutOfProcess.Tests` 新增 `PluginErrorTextVectorTests`：UTF-16 一组按 .NET 的输入形状经 `PluginErrorMapper.ToProto`（文案与内部错误的文案），码点一组逐个码点经它，字节一组以 `Encoding.UTF8.GetString` 对照。代码不变。

## 理由

- 同一条规则六个 SDK 各写一份用例，个数与情形各不相同，最容易出错的字节串一侧（截断的前缀、窄的第二字节范围）只有 Go 与 PHP 自己的几条；一份共同的向量让六家与宿主对同一组输入得出同一个结果。
- 三组输入照三种存放字符串的方式分，正好是 ADR-0339 写进规范的三种写法；各家只回放自己那一组，不需要模拟别的语言的字符串。
- 期望值由 .NET 的标准库算出，Python 的标准库与 Go 的独立实现核对，没有一项是手算或取自某个 SDK。

## 影响

- **规范**：新增向量文件进 `plugin` 档（MINOR）；`invocation.md` §3、§7 与 RFC-0017 状态行。
- **六个 SDK**：认领 `plugin` 档，覆盖测试在回放之前失败，需同一轮回放（逐家见报告）；Go SDK 还要把 `go.mod` 里的一致性模块升到含这份向量的提交（向量经模块内嵌）。
- **.NET**：只加测试；`SpecVectorCoverageTests` 不变（不认领 `plugin` 档，多回放不受限）。
