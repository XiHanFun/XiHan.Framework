# ADR-0223 工作单元的租户必须与绑定的分片一致

## 状态

已采纳（RFC-0007「分片」一条修订，`conventions/error-codes.md` 登记 `PERSISTENCE_VALIDATION_010`）。

## 日期

2026-11-13

## 背景

5.0 安全审查「加固建议」（`plans/5.0-安全审查.md` 第四节）。

- 管道外的代码用 `TenantShardScope` 给作用域绑定一个租户的分片，再自己开工作单元，租户写在 `UnitOfWorkOptions.TenantId` 里。RFC-0007 写的是两者「应一致」，但没有谁核对。
- 不一致时，工作单元按一个租户过滤与写入，连的却是另一个租户的库：
  - EF Core 整个 `DbContext` 连到分片库。
  - SqlSugar 的租户实体落分片连接。
  - 一个租户的行会写进别的租户的库，读也读不到自己的数据。
- 经管道的调用不会不一致：Tenant 阶段解析出的租户既决定分片，也是 Transaction 阶段工作单元的租户。

复现：EF Core 与 SqlSugar 的 `TenantShardingTests.UnitOfWork_OnAShard_MustBeForTheShardsTenant`。修正前，绑定 acme 的分片后以 beta（或不带租户）开工作单元照常成功。

## 决策

1. 客户端建在分片上时，开始工作单元即核对：工作单元的租户必须等于分片的租户（序数比较，不带租户也算不一致），否则抛出 `PERSISTENCE_VALIDATION_010`，工作单元保持未开始。
2. EF Core：取 `DbContext` 所在的分片绑定的 `tenant` 属性。DbContext 建在命名连接上时没有分片，不核对。
3. SqlSugar：特性建的客户端工厂在建出带分片连接的客户端时，把分片的租户记进作用域的 `SqlSugarShardTenant`，工作单元开始时读它。应用自己登记客户端时不核对。

## 影响

- 管道外绑定分片、却以别的租户或不带租户开工作单元的代码，从「静默写错库」变为抛出。迁移：工作单元的 `TenantId` 写绑定的那个租户。
- 公开 API：`PersistenceErrors.ShardTenantMismatch`。
