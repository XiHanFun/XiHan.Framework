# ADR-0183 文件系统存储的配额边写边预留

## 状态

已采纳（RFC-0012「Provider」修订 `ObjectStorage.FileSystem` 的配额一条）。

## 日期

2026-11-12

## 背景

5.0 安全审查 S-15（`plans/5.0-安全审查.md`），中危。

- `FileSystemBlobStore.PutOneAsync` 在复制时逐段调用 `FitsQuota(length - previousLength)`：只检查、不预留。N 个并发写入各自看到同一个已用量，都通过检查，提交后合计超额最多 N×`MaxBlobBytes`。
- `previousLength` 是开始写入时从元数据读到的旧长度，提交时照它算差值。对同一个键并发覆盖，两个写入方都按同一个旧长度扣减；覆盖期间有人删除，删除也扣一次。用量因此少记，甚至记成负数，之后的写入不受配额约束，直到重启重新扫描。
- 能写对象的调用方（租户用户的上传）就能触发；默认实现的容量上限因此失效。

复现：`FileSystemQuotaConcurrencyTests`。修正前：
- 8 个并发的 768 KiB 写入在 1 MiB 配额下全部成功，盘上 6 MiB。
- 两个并发覆盖与「覆盖时删除」都把用量记成 0，盘上实际 100 KiB。

## 备选

1. **整个写入持锁**：否决。复制是长时间的 IO，一个慢客户端就能让所有写入排队。
2. **预留只按与旧对象的差值**：否决。旧长度在提交前可能被并发的覆盖或删除改掉，按它算正是这次缺陷的来源；而且复制期间新旧内容确实同时在盘上。
3. **复制时逐段预留，提交、删除与记账在锁里按磁盘上的实际长度完成**：采纳。

## 决策

1. **预留**：存储新增进程内的预留量。写入每复制一段先预留这段的字节，已用量加全部预留超过 `MaxTotalBytes` 即停，返回 `OBJECTSTORAGE_UNAVAILABLE_002`，释放已预留的部分，不留下内容。分片上传的完成为拼出的全长预留。
2. **提交**：`CommitAsync` 接手调用方的预留。改名与记账在配额锁里一并完成：
   - 先量此刻磁盘上旧内容的实际长度，再换上新内容。
   - 已用量加上新长度、减去旧长度，预留扣掉新长度。
   - 不覆盖且已存在时只释放预留。
   - 写元数据在锁外。
3. **删除**：量长度、删文件与扣用量在同一把锁里，与提交互斥。
4. 锁里只有改名、删文件与量长度这几个元数据操作，复制与写元数据都在锁外。

## 影响

- 行为：覆盖写入期间要有新内容全长的余量。以前只要求差值，配额将满时覆盖一个大对象会被拒绝，先删再写或调大 `MaxTotalBytes`。这与磁盘的实际占用一致：替换之前临时文件与旧内容同时在盘上。
- 用量与磁盘在单进程内一致；多进程共享目录时仍只是近似，与以前相同。
- 公开 API 不变；内部的 `CommitAsync` 去掉 `previousLength` 参数，`FitsQuota` 换成 `TryReserve` / `Release`。
