# ADR-0351 性能门禁的两边基准各在自己的项目目录里运行，跑完核对构建的是哪个项目

## 状态

已采纳（只改性能门禁：`framework/scripts/Test-Benchmarks.ps1`、基准程序的入口 `framework/benchmarks/XiHan.Framework.Benchmarks/Program.cs`、`ci.yml` 里性能门禁作业的注释；框架的包、公开面、错误码、消息键、配置键、预算（`budgets.json`）与规范都不变）。更正 ADR-0173 与 ADR-0338：在这之前，相对回退里耗时与分配的比较两边量的都是当前提交。

## 日期

2026-11-28

## 背景

第十一轮记进 `plans/待办-边角问题.md` 的一条（重要）：`ci.yml` 把对照提交建在 `$RUNNER_TEMP/base-src`，`Test-Benchmarks.ps1` 却以仓库根为工作目录运行两边的基准程序；BenchmarkDotNet 的缺省工具链按当前目录找 csproj 重新生成并构建，对照那一轮实际构建、量的是当前提交。冷启动与内存两项是绝对上限，不受影响。

## 查明的事实

- **BenchmarkDotNet 怎样找要构建的项目**（0.15.8，缺省的 `CsProjCoreToolchain`）：
  - 它不直接运行给出的程序，而是在程序目录下生成一个项目（`<程序集名>-<作业>-<序号>/BenchmarkDotNet.Autogenerated.csproj`），以 `ProjectReference` 引用基准项目，再 `dotnet build`。基准项目连同它引用的框架源码都在这一步重新编译。
  - 基准项目按工作目录找：从工作目录往上找第一个含 `.sln` 或 `global.json` 的目录作根目录，在根目录下按「与程序集同名的 csproj」递归查找；找不到根目录时就在工作目录下找。
  - 仓库根有 `global.json`。以仓库根为工作目录时，根目录就是当前提交的检出，找到的是当前提交的基准项目，不管运行的是哪一边的程序。
- **复现**（本机，临时工作区放在 scratchpad，以 `dev` 的 `3176fcc19` 检出，规范用本地规范克隆的工作区）：
  - 在临时工作区里加一个只有它才有的基准 `BaseOnlyMarker`，构建之后以仓库根为工作目录运行临时工作区的程序：生成的代码编译失败（`CS0103`，当前名称中不存在 `BaseOnlyMarker`），即编译的是仓库根的源码。
  - 加 `--keepFiles` 留下生成的项目：`ProjectReference` 指向 `E:\Repository\XiHanFun\XiHan.Framework\framework\benchmarks\…\XiHan.Framework.Benchmarks.csproj`，不是临时工作区的。
  - 改以临时工作区的基准项目目录为工作目录：`BaseOnlyMarker` 编译、运行成功，`ProjectReference` 指向临时工作区。
- **影响的范围**：
  - 从 ADR-0173 接上门禁起，相对回退里**耗时与分配**两项比较的都是当前提交与它自己。CI 的对照工作区不在仓库根下，只要两边的基准集合相同，对照那一轮就构建得过，报告照常出数，看不出问题。
  - 第九轮记下的 `PipelineBenchmarks.FiveMiddleware` 首测与复测都慢了 5% 以上（ADR-0338 的背景），是同一份代码两轮之间的差：运行器的漂移确实够得着阈值。ADR-0338 在本机验证交替复测时也是拿同一份程序当两边，结论不受影响。
  - **冷启动与常驻内存**的相对比较不经 BenchmarkDotNet，直接运行各自的程序，一直量的是各自的提交；绝对预算与程序集大小只看当前提交，也不受影响。
- **没跑成的基准不报错**：生成的项目构建失败、基准运行出错时，BenchmarkDotNet 照样以退出码 0 结束，只在结果里记成 `NA`。脚本看退出码，看不出有基准没跑成；当前提交里没跑成的，只有列进 `budgets.json` 的四个会因「没有结果」失败。结果文件里没跑成的基准照样有一项，只是没有正式测量、每次分配为空：拿它比较，耗时之比是无穷大，分配成了「从 0 B 增加」。
- **生成目录同名覆盖**：同名的生成目录已经存在时（比如上一次中断留下的），BenchmarkDotNet 覆盖它，不另起一个序号。

## 备选

1. **每一边以自己的基准项目目录为工作目录运行**：采纳。从程序目录往上找与程序集同名的 csproj，就是这一边的项目；往上找根目录时落在这一边的检出里。改动只在脚本里。
2. **改用 in-process 工具链**：否决。不再重新构建，量的确实是给出的程序；但基准与 BenchmarkDotNet 宿主同在一个进程，测量的条件变了，`budgets.json` 的绝对预算是按独立进程量定的，预算不动的前提下不换口径。
3. **在基准程序里换一个固定项目路径的工具链**（继承 `CsProjGenerator` 改写找项目的方法，构建时把项目路径写进程序集）：否决。依赖 BenchmarkDotNet 的受保护成员，升级时更容易坏；方案 1 只靠工作目录就够了。
4. **只改工作目录，不核对**：否决。这个问题能藏这么久，是因为错了也照常出数；以后 BenchmarkDotNet 换了找项目的规则、或有人在 `global.json` 之外加了 `.sln`，同样会悄悄回到这一步。
5. **对照提交的基准没跑成也失败**：否决。对照提交构建不过时门禁本来就只跳过相对比较（ADR-0173 决策「对照提交还没有基准项目、构建失败或没有探针时，跳过对应的相对比较并在摘要里写明」）；对照那一轮没跑成同样处理，不让当前提交替对照提交的问题挡住。
6. **不改基准程序的退出码，在脚本里从结果文件判断没跑成的基准**：否决。结果文件只列跑成的；判断「应该有哪些」要另外列一遍基准，退出码是最直接的信号。

## 决策

1. `Test-Benchmarks.ps1` 运行一组基准时以这一边的基准项目目录为工作目录：
   - 新函数 `Get-BenchmarkProject` 从给出的程序目录往上找 `XiHan.Framework.Benchmarks.csproj`，找不到即抛出（程序目录必须是项目目录下的构建输出）。
   - `Invoke-Program` 与 `Invoke-Dotnet` 多一个 `-WorkingDirectory`，缺省仍是 PowerShell 的当前位置；冷启动与常驻内存的探针照旧。
   - 脚本开头把 `-Head`、`-Base`、`-Artifacts` 转成绝对路径，换了工作目录照样指向原处（CI 传的 `-Head` 是相对路径）。
2. 每一轮都带 `--keepFiles` 运行，跑完以 `Assert-GeneratedProjects` 核对：程序目录下每个 `BenchmarkDotNet.Autogenerated.csproj` 恰好引用一个项目，且就是这一边的基准项目；不是、或一个生成的项目都没有，即抛出。运行之前先删掉程序目录下已有的生成目录（同名的会被覆盖，删了之后剩下的就都是这一轮的），核对之后再删掉。
3. 基准程序有基准没跑成时以退出码 1 结束：`RunBenchmarks` 返回 `int`，任一 `Summary` 有致命的校验错误、或任一报告 `Success` 为假即返回 1。
4. 脚本按退出码区分两边：
   - 当前提交不为 0 即失败（照旧抛出 `Benchmark run '…' exited with code …`）。
   - 对照提交不为 0 只记下：报告末尾加「注意：对照提交的基准运行 … 有基准没跑成（退出码 …），没有结果的基准不比较」，在 GitHub Actions 里同时作为 `::warning::` 注解，照常比较跑成了的基准。首测与复测两轮的对照都这样处理。
   - 读结果时跳过没有正式测量的基准（没跑成的），当作没有结果：对照提交里没跑成的报成「对照提交没有这个基准」。
5. `ci.yml` 性能门禁作业的注释改正首测的次序（先当前、后对照，ADR-0338 已改脚本的说明，这里没跟上），并写明两边各在自己的项目目录里运行。

## 影响

- **门禁从此真的比较两个提交**：第一次推送时对照是 `3176fcc19`，两边的框架代码相同、只有门禁本身不同，耗时与分配应当持平；以后的推送里，代码真的变慢或多分配，首测会报出来、复测交替确认。同一份代码两轮之间够得着 5% 的漂移（第九轮实测）仍要靠 ADR-0338 的交替复测抵消。两个提交的程序集不同，代码布局的差异可能让没改过的基准差几个百分点；以前两边是同一份代码，碰不到这种情况，前几次推送要看（记进待办「只能在 CI 上验证的」）。
- **CI 时长**：每一轮多一次读写生成目录，可以忽略；重新构建的源码换了一份，构建时间不变。
- **验证**（本机 Windows；临时工作区里在 `OperationBenchmarks.EncodeResponse` 前埋 `Thread.SpinWait(20000)`，另加只有它才有的 `BaseOnlyMarker` 与一定抛出的 `Throwing`）：
  - 临时工作区当作当前提交、主检出当作对照：首测 `EncodeResponse` +80374.1%（p = 6.96E-07），交替复测 +81472.4%（p = 4.83E-11），门禁只以这一条失败（退出码 1）。其余基准 −3.6%～+0.6%、分配持平；`BaseOnlyMarker` 记为「对照提交没有这个基准」，即当前一边编译的是临时工作区的源码。冷启动 +2.2%，框架额外常驻内存 +0.1%。跑完两边的程序目录下都没有留下生成目录。
  - 两边对调（主检出当作当前提交，临时工作区当作对照，它的 `Throwing` 一定抛出）：门禁通过（退出码 0，用时 427 秒），报告末尾记下「注意：对照提交的基准运行 base 有基准没跑成（退出码 1），没有结果的基准不比较」；`EncodeResponse` −99.9%，其余 −6.5%～−0.8%。
  - 核对与失败的路径直接调脚本里的函数（按语法树取出，不另抄一份）：一个生成的项目都没有、引用的不是这一边的项目，都抛出；对照的基准没跑成时记下注意、结果里不含它；当前的没跑成时抛出；跑完不留生成目录。
  - 基准程序：生成的项目构建失败时退出码 1，正常时 0。
  - CI（run 46160646160，对照 `3176fcc19`）：核对通过，门禁通过。两边的框架代码相同，当前一边快 0.5%～13.3%（对照后跑，运行器变慢）；分配持平，启动的两项差 0.9% 以内。首测次序的这一偏差记进待办。

## 没有解决的

- 核对依赖 BenchmarkDotNet 生成的文件名 `BenchmarkDotNet.Autogenerated.csproj` 与 `ProjectReference` 的写法；升级 BenchmarkDotNet 时若这两样变了，门禁会以「没有生成的项目」或「构建的不是这一边的项目」失败，要跟着改脚本。
- 本机的主检出下若有 `.claude/worktrees` 之类含基准项目副本的目录，BenchmarkDotNet 在根目录下会找到不止一个同名项目而报错；以前就是这样，CI 不受影响。
