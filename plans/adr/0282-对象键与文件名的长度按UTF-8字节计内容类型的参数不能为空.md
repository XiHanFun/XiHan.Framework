# ADR-0282 对象键与文件名的长度按 UTF-8 字节计，内容类型的参数不能为空

## 状态

已采纳（`ObjectStorage.Abstractions` 的 `BlobKey`、`BlobQuery`、`BlobUrlRequest`、`BlobPutOptions` 已改，常量 `BlobKey.MaxLength` 改名 `MaxBytes`、`BlobUrlRequest.MaxDownloadFileNameLength` 改名 `MaxDownloadFileNameBytes`；规范 RFC-0012 的「标识」与预签名已写明，向量 `blob-keys.json`、`blob-content-types.json` 已补、新增 `download-file-names.json`，Go 一致性模块的规则已改）。

## 日期

2026-11-24

## 背景

ADR-0277 给 `objectstorage` 档补向量时，在「正文与 .NET 的出入」里记下两处没有动的地方：

- **对象键与保存的文件名的长度没有单位。** RFC-0012 写对象键「1 到 1024 个字符」、预签名下载保存的文件名「1 到 255 个字符」。
  - .NET 的 `BlobKey.IsValid` 判 `value.Length > MaxLength`，`BlobUrlRequest` 判 `fileName.Length`，数的都是 UTF-16 码元。
  - S3 的对象键上限是 1024 个 UTF-8 字节。1024 个汉字的键是 1024 个码元、3072 字节：`BlobKey` 收下，文件系统存储写得进，换成 S3 就被服务拒绝（落成 `OBJECTSTORAGE_UNAVAILABLE_001`，看上去像存储故障）。同一个应用换一个 Provider，合法的键变成写不进的键。
  - 查询前缀 `BlobQuery.Prefix` 用同一个上限（`BlobKey.IsValidPrefix`），正文里没有写它的文法。
  - 文件名进 `Content-Disposition` 头与 S3 的响应头覆盖参数，按 RFC 5987 百分号编码后每个字节 3 个字符；按码元计时 255 个汉字编出 2295 个字符。
  - 同一类问题缓存键已经改过（ADR-0274、ADR-0276 决策 1）。
- **内容类型的参数部分比正文宽。** 正文写「可跟 `;` 起头的参数」，.NET 的正则是 `(?: *;[\x20-\x7E]*)?`：
  - `;` 之后可以什么都没有（`text/plain;`、`text/plain; ` 能过），这样的值原样成为对象的内容类型，进 S3 的请求头与文件系统的元数据文件。
  - 媒体类型与 `;` 之间可以有空格（`text/plain ; charset=utf-8`），正文没有写。

依赖这两条的地方（全仓搜 `BlobKey.MaxLength`、`IsValid`、`IsValidPrefix`、`MaxDownloadFileNameLength`、`IsValidContentType`）：

- 键：`BlobKey` 的构造与显式转换；两个存储包列举时用 `IsValid` 跳过不合文法的对象；宿主代收发端点用它核对路径里的键。
- 前缀：`BlobQuery.Prefix`。
- 文件名：`BlobUrlRequest.ForDownload`，再到 `BlobContentDisposition.Attachment`、宿主签名器的规范串与 S3 的预签名。
- 内容类型：`BlobPutOptions.ContentType`、`BlobUrlRequest.ForUpload`、宿主代收的上传（签名没限定内容类型时取请求头，不合文法是 `OBJECTSTORAGE_VALIDATION_006`）。
- 文件系统存储把键的每段编码成文件名（`BlobPathEncoding`）：小写字母、数字与 `._-` 原样，其余按 UTF-8 字节写成 `%XX`。它不读长度上限，没有按上限分配的缓冲。

## 备选

1. **长度维持码元，或按码位（字符）计**：否决，理由同 ADR-0274 备选 1、2：后端的限制是字节，别的语言要先转码才数得出码元。
2. **两个上限都按 UTF-8 编码后的字节数计**：采纳。
3. **常量名留作 `MaxLength` / `MaxDownloadFileNameLength`**：否决，理由同 ADR-0274 备选 4：值没变、含义变了，`text.Length <= BlobKey.MaxLength` 这样的预检照常编译、结论却是错的。改名让它们编译失败。命名照 `CacheKey.MaxBytes`。
4. **留一个带 `[Obsolete]` 的旧名**：否决。两个类型都是 `Stable`，但 5.0.0 还没有发，正式版前的破坏直接改；留别名就是留一个结论错误的预检还能编译的口子。
5. **内容类型的上限也改成字节、常量改名 `MaxContentTypeBytes`**：否决。内容类型的文法只有 ASCII，字符数就是字节数，没有歧义可消；只在文档里写明这一点。
6. **查询前缀不进规范**：否决。它与键共用上限，单位改了它也得跟着改；正文不写，各实现又会各数各的。照 .NET 的现状写明：字符约束与字节上限同键，可以为空、可以以 `/` 结尾，对各段不作要求。
7. **文件名不单设向量文件，只在正文写明**：否决。没有向量盯住的规则迟早分歧（ADR-0276「理由」）；键的向量文件里塞不进文件名的规则。新增 `download-file-names.json`。
8. **内容类型的 `;` 两侧照 RFC 9110 的 OWS 把制表符也收下**：否决，只收空格。
   - 整个内容类型不含控制字符是 ADR-0214 定下的（值进请求头与元数据文件），制表符是控制字符；现有向量里 `text/plain;\tcharset=utf-8` 是必须拒绝的，收下它要翻一条已有的期望。
   - 取严不取宽（ADR-0276「理由」）：只收空格不拒绝任何现在合法的值。
9. **只拒绝「第一个 `;` 之后全是空白」**（正则里加一个非空格字符即可，结尾多出的 `;`、连续的 `;` 照收）：否决。决定是「`;` 之后为空的不合法」，结尾的 `;` 与连续的 `;` 都是一个后面为空的 `;`；只查第一个，`text/plain; charset=utf-8;` 这样带着尾巴的值还是会进存储。
10. **按 RFC 9110 把每个参数解析成 `name=value`，值可以是带引号的字符串**：否决。ADR-0214 定的是「参数部分不细分」；细分要处理引号与转义，拒绝的范围比决定大得多（`; flowed` 这类没有等号的也会被拒）。
    - 代价是引号不被解析：引号里的 `;` 同样算分隔，`boundary="a;b"` 是两段非空的参数（合法），`boundary=";;"` 中间一段为空（不合法）。这一点写进正文与向量。
11. **顺带把参数末尾的空格也禁掉**（`text/plain; charset=utf-8 ` 现在合法）：否决。不在决定之内，是又一类「原来能过、现在被拒」。
12. **不成对的代理项（编不成 UTF-8 的键与文件名）一并判为不合法**：不在本 ADR，同 ADR-0274 备选 7。这类字符按替换后的 3 个字节计，与实际编码的结果一致。

## 决策

1. **对象键 `BlobKey`**：文法不变，长度改为 UTF-8 编码后 1 到 1024 字节。
   - `BlobKey.MaxLength` 改名 `MaxBytes`，值仍是 1024。
   - 判定先查字符，码元数乘 3 不超过上限的不数字节，其余才调 `Encoding.UTF8.GetByteCount`（做法同 `CacheKey`）。
   - `Validate` 与构造的异常消息写「1 to 1024 bytes long in UTF-8」。
2. **查询前缀 `BlobQuery.Prefix`**：字符约束与字节上限同键（`BlobKey.IsValidPrefix`），可以为空、可以以 `/` 结尾，对各段不作要求，不受保留前缀限制。异常消息写明上限与单位。
3. **保存的文件名**：不为空、不全是空白、不含控制字符、UTF-8 编码后不超过 255 字节。
   - `BlobUrlRequest.MaxDownloadFileNameLength` 改名 `MaxDownloadFileNameBytes`，值仍是 255。
   - 「不全是空白」是 .NET 一向的行为，这次写进正文。
4. **内容类型**：媒体类型之后可跟若干个参数，文法按整串匹配：

   ```text
   ^<token>/<token>( *; *[\x21-\x3A\x3C-\x7E][\x20-\x3A\x3C-\x7E]*)*$
   ```

   - 每个 `;` 两侧可以有空格（RFC 9110 的 `OWS ";" OWS`，只取空格）。
   - 每个 `;` 之后必须有参数：不含 `;` 的可打印 ASCII 与空格，以非空格字符开头。
   - 参数内部不细分，不解析引号。
   - 整体仍是 1 到 255 个字符；`MaxContentTypeLength` 不改名。
5. **消息键与本地化文案不改**。写着长度的只有 `objectstorage.blob.content_type_invalid`（「不超过 {max} 个字符的媒体类型」），内容类型只有 ASCII，这句话仍然成立；键与文件名不合法是 `ArgumentException`（编程错误），没有消息键。
6. **规范与向量**：
   - RFC-0012「标识」写明键与前缀的单位、内容类型参数的写法；「范围读取、分片上传与预签名」写明文件名的规则。
   - `blob-keys.json`：`maxLength` 改名 `maxBytes`，每条加 `utf8Bytes`、`utf16Units`；键与新增的 `prefixes` 各有正好到上限、多 1 个字节、码元数不超而字节数超的用例。
   - 新增 `download-file-names.json`（档 `objectstorage`）。
   - `blob-content-types.json`：补 `;` 两侧的空格、多个参数、引号里的 `;`，以及 `;` 之后没有参数的各种写法。
   - Go 规则包：`IsBlobKey` 改按字节，新增 `IsBlobKeyPrefix`、`IsBlobDownloadFileName`，`MaxBlobKeyLength` 改名 `MaxBlobKeyBytes`，新增 `MaxBlobDownloadFileNameBytes`，内容类型的正则同上。

## 理由

- 键的上限唯一的用处是「写得进后端」。按字节计之后，`BlobKey` 收下的键在 S3 上一定不因长度被拒，换 Provider 不会让合法的键变成写不进的键。
- 取严不取宽：按字节计只会更严（码元数不超过字节数），纯 ASCII 的键与文件名没有任何变化；内容类型只拒绝 `;` 后面没有东西的写法，那样的值本来就不该进存储。
- 改名是为了让依赖旧含义的代码编译失败。

## 影响

- **公开 API 与迁移**（`PublicAPI.Unshipped.txt` 已同步；尚无基线，不需要 `CompatibilitySuppressions.xml`）：
  - `BlobKey.MaxLength` → `BlobKey.MaxBytes`；与它比较的 `text.Length` 换成 `Encoding.UTF8.GetByteCount(text)`。
  - `BlobUrlRequest.MaxDownloadFileNameLength` → `BlobUrlRequest.MaxDownloadFileNameBytes`，同上。
  - 其余签名不变。
- **原来能过、现在被拒的输入**（纯 ASCII 的键、前缀与文件名不受影响）：
  - 对象键：含非 ASCII 字符、UTF-16 码元数不超过 1024 而 UTF-8 超过 1024 字节的。全是 3 字节字符（汉字）的键原先最多 1024 个字，现在 341 个；全是 4 字节字符（表情，占 2 个码元）的原先 512 个，现在 256 个；全是 2 字节字符的原先 1024 个，现在 512 个。`new BlobKey(text)`、显式转换与 `Validate` 抛出 `ArgumentException`，`IsValid` 返回 `false`；宿主代收发端点上这样的键是 404（与其余不合文法的键相同）。
  - 查询前缀：同样的三类长度。`new BlobQuery { Prefix = … }` 抛出 `ArgumentException`。
  - 保存的文件名：含非 ASCII 字符、码元数不超过 255 而 UTF-8 超过 255 字节的。全是汉字的文件名原先最多 255 个字，现在 85 个。`BlobUrlRequest.ForDownload` 抛出 `ArgumentException`。
  - 内容类型：`;` 之后没有参数的——只有 `;`（`text/plain;`）、`;` 后面只有空格（`text/plain; `）、结尾多出的 `;`（`text/plain; charset=utf-8;`）、连续的 `;`（`text/plain;;charset=utf-8`、`text/plain; ;charset=utf-8`，含引号里连续的 `;`）。`BlobPutOptions.ContentType` 与 `BlobUrlRequest.ForUpload` 抛出 `ArgumentException`，`IsValidContentType` 返回 `false`；宿主代收的上传（签名没限定内容类型）带这样的 `Content-Type` 返回 `OBJECTSTORAGE_VALIDATION_006`（HTTP 400），不写入。
- **存储里已有的超长键**（旧版本经文件系统存储写入、UTF-8 超过 1024 字节的）：
  - `BlobKey` 构造不出来，读不到、删不掉；两个存储包的列举跳过它们（同其余不合文法的对象）。
  - 文件系统存储启动时扫描目录计已用量，它们的字节仍然计入总配额；要腾出配额，在存储的根目录下按路径删除（键的每段按 `BlobPathEncoding` 编码成目录与文件名，`data/` 与 `meta/` 下各一份）。
  - S3 上不会有这样的对象：服务本来就拒绝。
- **存储里已有的、内容类型带着空参数的对象**：读取不受影响。两个存储包读元数据时不重新校验内容类型，`BlobMetadata.ContentType` 照原样交出；只有把它原样写回 `BlobPutOptions`（复制对象之类）时才会抛出。
- **文件系统存储**（核对过，没有改代码）：
  - 路径编码不读长度上限。键的相对路径最长由「码元数的九倍」（1024 个汉字，9216 个字符）降到「字节数的三倍」（3072 个字符）；以前超出 Linux `PATH_MAX`（4096）的那些键现在构造不出来，没有新增的失败方式。
  - 单个文件名（一段）的系统上限照旧：一段里要转义的字节超过 85 个时编码后超过 255 个字符，写入返回 `OBJECTSTORAGE_UNAVAILABLE_001`；macOS 整条路径的上限是 1024 字节，接近上限的键在那里同样写不进。这些是原有的限制，这次没有动。
- **规范**（规范仓库已改，指针待更新）：RFC-0012 的两处写明是 MINOR，内容类型的收紧是 MAJOR（`v1.0.0` 之前允许）；`blob-keys.json` 的成员改名与新增的向量文件会让认领 `objectstorage` 档的实现的回放失败，目前只有 .NET 认领这个档。
- **测试**：
  - 回放：`BlobKeyVectorTests`（键、保留前缀、查询前缀；核对向量自己标的字节数与码元数属实，上限两侧与「码元数不超而字节数超」各有用例）、新增的 `DownloadFileNameVectorTests`（同样的核对，合法的文件名都写得成响应头）、`BlobContentTypeVectorTests`（另经 `BlobUrlRequest.ForUpload` 走一遍，核对收紧的几类写法都有用例）。架构测试 `SpecVectorCoverageTests` 按文件名认领新增的向量文件。
  - 文件系统：最长的键（ASCII、分段的汉字、表情）编码后不超过字节数的三倍并能解回；41 段、每段 8 个汉字、恰好 1024 字节的键写入、读取、列举、删除走一遍。
  - 文件名的字节上限、内容类型的参数各有手写用例；宿主代收的上传带 `Content-Type: text/plain;` 返回 400 且不写入。
  - S3 上恰好 1024 字节的多字节键没有用例：一致性套件对真实服务的用例只在 CI 设了 `XIHAN_TEST_S3` 时执行，这次没有给套件加这一条（见「待定」）。
- **文档**：文档站的 `object-storage/basics`、`object-storage/advanced`、`packages/objectstorage-abstractions`、`appendix/spec` 与更新日志待改。
- **待定**：
  - 一致性套件 `BlobStoreConformance` 是否加一条「恰好 1024 字节的多字节键完整往返」（缓存那边加了 `Keys_AtMaxUtf8Bytes_RoundTrip`）。键要拆成短段才能在文件系统上通过，S3 兼容服务对单段长度各有各的限制，加进套件之前要先在 RustFS 上实测。
  - 不成对的代理项算不算合法（备选 12），规范没有写；缓存键有同样的问题。
  - 文件系统存储里旧版本留下的超长键没有清理的途径（上面「存储里已有的超长键」），要不要给一个按路径清理的工具或在启动扫描时报告。
