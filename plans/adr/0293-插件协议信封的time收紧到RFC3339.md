# ADR-0293 插件协议信封的 time 收紧到 RFC 3339

## 状态

已采纳（规范 `plugin/invocation.md` §4 与 RFC-0017 已补，新增向量 `plugin/envelope-times.json`（档 `host`）；`Plugins.Protocol` 的 `PluginEnvelopeMapper.FromProto` 改用原语层的 `TimestampText`；Go 一致性模块新增 `rules.ReadEnvelopeTime`、`rules.FormatEnvelopeTime`）。

## 日期

2026-11-25

## 背景

- ADR-0283 把消息信封的 `time` 收紧为一条文法（RFC-0009「信封」第 3 条，即 RFC-0003 规则 8 的读法），结构化 JSON 与 binary 模式的 `ce-time` 都改用原语层的 `TimestampText.TryParse`。插件协议的 `Envelope.time` 留在了外面（ADR-0283 备选 18）：要先核对六个 SDK 写出的文本。
- `plugin.proto` 里 `Envelope.time` 是字符串（字段 7，注释「RFC 3339；可空」），不是 `google.protobuf.Timestamp`：宿主与插件之间传的是文本，进程外载体与 Wasm 载体（proto3 JSON）都一样。
- 宿主读插件写来的信封在 `PluginEnvelopeMapper.FromProto`（`Host.Publish` 与 Wasm 的 `publish` 导入共用，经 `PluginPublishBatches.Collect` 逐项转换）：`DateTimeOffset.TryParse(text, InvariantCulture, AdjustToUniversal | AssumeUniversal)`。没有本机时区的问题（没有偏移的按 UTC），但比文法宽得多：空格代替 `T`、没有秒、只有日期、偏移不带冒号、首尾空白、逗号小数、超过九位的小数、RFC 1123 的日期都读得出；读不出时的错误是 `messaging.envelope.invalid`，`reason` 是一句英文。
- 宿主写给插件的（`ToProto`）是 `ToUniversalTime().ToString("O")`：`2026-11-25T03:25:00.0000000+00:00`，七位小数、`+00:00`，已经合文法。
- 六个 SDK 的现状（只读核对，代码位置见下文「影响」）：没有一个 SDK 自己格式化、核对或解析 `Envelope.time`。作者给的是一个原样的字符串（Go `Envelope.Time string`、TypeScript `time?: string`、Rust `time: Option<String>`、Java `Builder.time(String)`、Python `time: str | None`、PHP `string $time`），发布时原样写进 `Envelope.time`；投递时宿主写的文本原样交给处理器。没有 SDK 有 Wasm 客体一侧的 `publish` 绑定。所以 SDK 自己写不出不合文法的文本，会不合文法的只有作者传进来的字符串。

## 备选

1. **留一条回退**（先按文法读，读不出再交给通用解析）：否决，理由同 ADR-0283 备选 1：回退就是没改，各语言做不到同样宽松的读法。
2. **读不出当作没有时间**：否决，理由同 ADR-0283 备选 2：`time` 是事件的属性，悄悄丢掉会让处理器拿到没有发生时间的事件。按「信封不合法」处理，那一项不发布。
3. **把字段改成 `google.protobuf.Timestamp`**：否决。字段类型的改变在线上不兼容，要新增协议版本，六个 SDK 与两种载体同时跟；Wasm 载体的 proto3 JSON 里 `Timestamp` 本来也写成 RFC 3339 文本，问题还在。
4. **错误沿用 `messaging.envelope.invalid` 加一句 `reason`**：否决。结构化 JSON 与 binary 模式对同一种情形用的是 `messaging.envelope.invalid_time`（参数 `time` 是原文，ADR-0283），插件发布的消息到了代理那边就是同一个信封，键应当相同；`reason` 是只有 .NET 写得出的英文句子。
5. **SDK 在本地核对作者给的 `time`**：否决。宿主逐项核对的先后是发布器、主题、`xihantenant`、信封能否转换（`invocation.md` §5）；本地先判 `time` 会改变错误的先后（宿主没有发布器时本该每一项都是 `plugins.callback.messaging_unavailable`），与 SDK 不在本地核对 `xihantenant` 同一个理由。SDK 另提供以时刻类型写入 `time` 的接口时，写出的文本必须合文法（规范写成「宜与宿主的写法相同」）。
6. **向量放进 `plugin` 档，要求 SDK 回放**：否决。SDK 一侧没有读写 `time` 的逻辑（原样传递），回放只能核对「原样」；向量放在 `host` 档，由宿主（.NET）回放。SDK 若加了时刻类型的写入接口，可以拿 `written` 与 `valid` 自测。
7. **宿主写出时改用 `Z`、去掉末尾的零**：不改。现在的 `O` 格式合文法，与截止时间的写法（`deadlines.json` 的 `written`）相同；改写法只会让已经按它写了测试的插件跟着改。

## 决策

1. **`Envelope.time` 的文法**（`plugin/invocation.md` §4）：空串表示没有这个属性；不是空串时与 RFC-0009「信封」第 3 条相同（RFC-0003 规则 8 的读法：必须有 `T` 或 `t`、秒与偏移 `Z` / `z` / `±HH:MM`，小数一到九位，按整串匹配、不裁剪空白，各段与换算成 UTC 之后的范围照规则 8），读成 UTC 时刻，比 100 纳秒更细的小数截断。
2. **宿主读插件写来的信封**：不合文法或越界时那一项不发布，结果是 `MESSAGING_VALIDATION_002` + `messaging.envelope.invalid_time`（参数 `time` 是原文），其余各项照常。`PluginEnvelopeMapper.FromProto` 改用 `TimestampText.TryParse`，在构造信封之前核对；其余属性不合法时照旧是 `messaging.envelope.invalid`。
3. **宿主写给插件的信封**：不变，换算成 UTC、七位小数、`+00:00`，没有时间写空串。规范写明它一律合文法、SDK 原样交给作者。
4. **SDK**：不在本地核对、原样写出作者给的文本；另提供时刻类型的写入接口时写出的文本必须合文法。
5. **向量** `plugin/envelope-times.json`（档 `host`）：`valid`（读得出的文本与 UTC 时刻，含空串、各语言常见的合文法写法与 ±23:59 的偏移）、`invalid`（各语言常见的不合文法写法与越界）、`error`（错误码与消息键）、`written`（宿主写出的文本）。期望值由 .NET 算出。

## 理由

- 信封跨进程、跨语言，读法只能有一种；插件发布的消息进了代理，之后由 RabbitMQ、Kafka、Redis 以结构化 JSON 再读一遍，那边已经只认这条文法。宿主在发布时就拒绝，比让消息进了代理再在消费方进死信近得多。
- 现有的 SDK 不会因此坏：它们不写自己的文本，只转交作者的字符串；作者用各语言最常见的 RFC 3339 写法（Go `RFC3339Nano`、JavaScript `toISOString`、Java `Instant.toString`、Python 带时区的 `isoformat`、PHP `DATE_ATOM`、chrono `to_rfc3339`）写出的都合文法（向量 `valid` 收了这几种）。

## 影响

- **公开 API**：没有变化（`PluginEnvelopeMapper` 是 internal）。没有新的错误码与消息键（`messaging.envelope.invalid_time` 是 ADR-0283 加的）。
- **行为变化（升级须知）**：插件发布的信封里，`time` 写成以下样子的那一项现在以 `MESSAGING_VALIDATION_002` + `messaging.envelope.invalid_time` 失败、不发布（以前读得出，没有偏移的按 UTC）：没有偏移（`2026-11-25T03:25:00`，Python 不带时区的 `datetime.isoformat()`）、空格代替 `T`（Go 的 `time.Time.String()`、Python 的 `str(datetime)`）、只到分钟（Java `OffsetDateTime.toString()` 在整分钟时、Python `isoformat(timespec='minutes')`）、偏移不带冒号（PHP `DATE_ISO8601`、`strftime('%z')`）、只有日期、RFC 1123、首尾空白、超过九位的小数、逗号小数。插件作者改用带偏移的 RFC 3339 写法。以前读不出的 `time` 的错误由 `messaging.envelope.invalid`（`reason` 是一句英文）变成 `messaging.envelope.invalid_time`（`time` 是原文）。偏移在 ±14:00 之外（到 ±23:59）的现在读得出。
- **SDK 写出的 `time`（核对结果）**：都是作者字符串的原样转交，SDK 自己不格式化：
  - Go：`plugin.Envelope.Time`（`plugin/options.go`），`ToProtoEnvelope`（`plugin/status.go`）原样写；投递 `FromProtoEnvelope` 原样交出。
  - TypeScript：`Envelope.time?: string`（`src/plugin/conversion.ts`），`toProtoEnvelope` 写 `envelope.time ?? ''`；非字符串（纯 JS 或 `as any` 传进来的 `Date`、数字）被 protobuf 的编码器 `String(value)` 成 `Wed Nov 25 2026 …` 或一串数字，现在会被拒绝。
  - Rust：`Envelope.time: Option<String>`（`src/plugin/types.rs`），`proto_envelope`（`src/plugin/convert.rs`）写 `unwrap_or_default()`。
  - Java：`Envelope.Builder.time(String)`（`Envelope.java`），`Wire.envelope` 原样写。
  - Python：`Envelope.time: str | None`（`_model.py`），`to_proto_envelope`（`_convert.py`）写 `envelope.time or ""`。
  - PHP：`Envelope::$time`（`src/Plugin/Envelope.php`），`Protocol::toProtoEnvelope` 原样写；非 `strict_types` 的调用方传入整数会被转成数字文本。
  - 六个 SDK 都没有 Wasm 客体一侧的 `publish` 绑定，都已经有同一条文法的严格读法（各自的截止时间解析），可以拿来做时刻类型的写入或可选的作者侧自检。
- **规范（规范工作区已提交）**：`plugin/invocation.md` §4 新增 `Envelope.time` 一条；RFC-0017 状态行与数据向量列表；新增 `conformance/vectors/plugin/envelope-times.json` 并进 `host` 档（`profiles.json`）、`conformance/README.md` 的向量表与规则列表。这是规范的 MAJOR（`v1.0.0` 之前允许）：以前读得出的文本现在被拒绝。
- **Go 一致性模块**：`rules.ReadEnvelopeTime`（空串为没有，其余经 `ParseDeadline`）、`rules.FormatEnvelopeTime`（同 `FormatDeadline`）、常量 `EnvelopeTimeErrorCode`、`EnvelopeTimeErrorKey`；`conformance.EnvelopeTimes()` 读向量，规则包回放全部用例。
- **测试**：`ProtocolVectorTests.EnvelopeTimes_FollowTheVectors` 经真实的 `FromProto` 回放 `valid` 与 `invalid`（错误码、消息键、参数 `time`），经 `ToProto` 回放 `written`；`EnvelopeTimes_ThatAreNotValid_FailOnlyTheirItemOfAPublish` 核对 `PluginPublishBatches.Collect` 只让不合文法的那一项失败、其余照常分组；`EnvelopeTimes_ThatTheEarlierHostRead_AreRejectedNow` 列出以前 `DateTimeOffset.TryParse` 读得出、现在被拒绝的写法。
- **文档**：进程外与 Wasm 两个包的 README 已同步；文档站的 `plugins/out-of-process`（发布消息一节）、`plugins/wasm`、`appendix/spec`（向量表）与更新日志待改；各 SDK 的文档在讲发布消息的地方写明 `time` 的写法。
