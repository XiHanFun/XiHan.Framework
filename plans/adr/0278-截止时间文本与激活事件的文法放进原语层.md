# ADR-0278 截止时间文本与激活事件的文法放进原语层

## 状态

已采纳（.NET 参考实现跟上 ADR-0276 的第 2、3、4 条：截止时间的文本、操作 ID 的上限、`onEvent:` 的下划线；`Primitives`、`Kernel`、`Hosting.AspNetCore`、`Plugins.Protocol` 已改，规范不动。ADR-0276 第 1 条的缓存键由 ADR-0274 跟进）。

## 日期

2026-11-24

## 背景

ADR-0276 把规范里没写死的几处写死之后，.NET 一侧有四件事要跟上：

1. **截止时间的文本有两个读取点，宽严不同**。插件协议一侧的 `PluginDeadlines.TryParse`（`Plugins.Protocol`，ADR-0237）按文法手写解析，回放 `plugin/deadlines.json`；HTTP 入口 `HttpInvocation.Create`（HTTP、gRPC、MCP 的 Streamable HTTP 与认证方案 `XiHan` 共用）用 `DateTimeOffset.TryParse`。拿 `plugin/deadlines.json` 的 `invalid` 逐条喂给后者，53 条里它读得出 30 条：空格代替 `T`、没有偏移（当作 UTC）、没有秒、只有日期或年月、只有时间（补上系统当天的日期）、`+0800` / `+08` / `+8`、偏移前带空格、十位小数、小数点写成逗号、首尾的空格、制表符、换行与 U+00A0、斜线分隔的日期、HTTP 日期与英文月份名。合法的文本里，九位小数它四舍五入（`.123456789` 读成 `.1234568`），`9999-12-31T23:59:59.999999999Z` 进位后溢出、读不出。
2. **严格的那一份宿主引用不到**。`PluginDeadlines` 是 `Plugins.Protocol`（Ring 5）的 internal 类型，`Hosting.AspNetCore` 在 Ring 4，依赖方向也不允许它引用插件包。
3. **激活事件的正则写了两份**。原语层 `Manifest.Activation` 的初始化校验与内核 `ManifestShape` 读清单时的形状检查各有一个一字不差的生成正则，规范改一个字符要改两处；全仓没有第三处（生成器、分析器、命令行工具与两个插件宿主都不解释激活事件，只看有没有 `onStartup`）。
4. **三个新向量文件没有回放**。架构测试 `SpecVectorCoverageTests` 按档表核对，`context/http-deadline.json`（档 `host`）、`primitives/operation-ids.json`（档 `core`）、`caching/cache-keys.json`（档 `caching`）都报缺。

## 备选

1. **把 `PluginDeadlines` 改成 public，宿主引用 `Plugins.Protocol`**：否决。Ring 4 引用 Ring 5 违反依赖方向，不装插件的应用也会带上 gRPC 与 protobuf。
2. **放进内核**：否决。内核放得下（宿主与插件协议都引用它），但同一类东西的先例在原语层：`TraceParent`（ADR-0235）是「载体里一段文本的文法」，规则 7 与规则 8 在同一个 RFC 的同一节。放在原语层，只引用原语层的抽象包（消息信封、远程 Provider）将来要读写这段文本时不必为此引用内核。解析是手写的，没有正则、没有反射、没有依赖，符合 Ring 0 的约束。
3. **做成值类型**（像 `TraceParent` 那样的 `readonly record struct`）：否决。`TraceParent` 把 trace-id、parent-id 与采样位三个分量绑在一起，值类型有意义；截止时间就是一个时刻，`InvocationContext.Deadline` 与 `InvocationContextOptions.Deadline` 已经是 `DateTimeOffset?`，再包一层只多一次转换。所以是静态类，形状取 `TraceParent` 的两个动作：`TryParse` 与写出。
4. **类型叫 `Deadline`**：否决。带 `Deadline` 属性的类型里（`InvocationContext`、`InvocationContextOptions` 以及各处的选项类），简单名 `Deadline` 先绑定到属性，`Deadline.TryParse(...)` 编译不过。取规范的说法「截止时间的文本」，叫 `DeadlineText`。
5. **解析改用生成正则加 `DateTimeOffset.ParseExact`**：否决。文法之外还有各段的取值范围、换算成 UTC 之后的范围与「截断不进位」三条，正则只表达得了前一半，`ParseExact` 的小数位数与进位又是另一套规则。已有的手写解析回放过全部向量，原样搬过去。
6. **HTTP 入口留一条回退**（先按文法读，读不出再交给 `DateTimeOffset.TryParse`）：否决。规则 8 明文写着「不换别的格式再试」，留回退等于没改。
7. **HTTP 入口读不出时答 400**：否决，ADR-0276 备选 3 已否决；规范写的是当作没有这个头。
8. **宿主自己裁剪首尾空白再匹配**：否决。`protocol/http.md` 写明宿主拿到的是 HTTP 解析器交来的值、不再裁剪；Kestrel 已按 RFC 9110 去掉可选空白，宿主再裁一次只会让不经解析器的入口（`TestServer`、手工构造的 `HttpContext`、改写过头的中间件）带进来的空白被照收，与向量「开头有空格」「结尾有空格」不符。
9. **头出现多次时取第一个值**：否决。规范写的是各个值以逗号并成一个文本、读不出；取第一个的结果会随中间代理合不合并重复的头而变。`StringValues.ToString()` 正是以逗号拼接，直接把它交给解析即可。
10. **激活事件的文法留两份，各改一个字符**：否决，下次再改还是两处。**只在内核留一份**：否决，`Manifest.Activation` 的初始化校验是原语层已有的行为，不能反过来依赖内核。所以放进原语层并公开，与 `ManifestId.IsValid`、`CapabilityId.IsValid`、`OperationId.IsValid` 同形——内核的形状检查本来就这样引用这三个。
11. **`ActivationEvent` 再给 `Validate`、种类枚举或模式匹配**：不做。宿主目前不解释模式（ADR-0276 备选 5），通配怎样匹配规范还没定；原语层只增不改，没有调用方的成员不加。
12. **`caching/cache-keys.json` 在这里一并回放**：不做。它要求缓存键按 UTF-8 字节计，`CacheKey` 的改动在 ADR-0274。覆盖测试有缺口表，按它已有的机制登记成过渡的缺口；缺口有了回放时测试会失败，提醒删掉登记。

## 决策

1. **原语层新增 `DeadlineText`**（`XiHan.Framework.Primitives`，`Stable`，自 5.0）：
   - `TryParse(string? text, out DateTimeOffset deadline)`：按规则 8 的文法整串匹配，年 `0001`–`9999`、月日按公历、时分秒与偏移各在范围内、不认闰秒，换算成 UTC 之后（不计小数）在 `0001-01-01T00:00:00` 到 `9999-12-31T23:59:59` 之间；小数一到九位，比 100 纳秒细的部分截断、不进位；读出的时刻偏移为零。`null`、空串、不合文法、越界都返回 `false`，`deadline` 为 `default`；首尾的空白不裁剪。
   - `Format(DateTimeOffset deadline)`：换算成 UTC 后写成七位小数加 `+00:00`（`O` 格式），写出的文本 `TryParse` 读得回同一时刻。
2. **HTTP 入口改用它**：`HttpInvocation.Create` 把 `xihan-deadline` 的各个值以逗号并成的文本（`StringValues.ToString()`）交给 `DeadlineText.TryParse`，不裁剪、不回退。读不出（不合文法、越界、空值、出现多次）当作没有这个头：不报错，请求照常处理，`grpc-timeout` 照常生效。`grpc-timeout` 的读法不变（1 到 8 位数字加单位，整串匹配，出现多次读不出），它的期望值本来就由 .NET 算出。
3. **插件协议改用它**：`PluginDeadlines` 去掉 `TryParse` 与 `Format`，只留插件协议自己的两件事（元数据与 gRPC 调用截止时间取较早者的 `Effective`、`ServerCallContext.Deadline` 的换算 `FromCall`）；`PluginMetadata.FromContext` 写出用 `DeadlineText.Format`。行为不变。
4. **原语层新增 `ActivationEvent.IsValid`**（`XiHan.Framework.Primitives.Manifests`，`Stable`，自 5.0）：文法 `^(onStartup|onOperation:[a-z0-9.*-]+|onEvent:[a-z0-9._*-]+)\z`，`Manifest.Activation` 的初始化校验与内核 `ManifestShape` 都引用它，两处的私有正则删除。`onEvent:` 的模式从此可以带下划线，`onOperation:` 不变。
5. **操作 ID 不改实现**：`OperationId.MaxLength = 128` 与 `IsValid` 本来就是向量的出处。回放 `primitives/operation-ids.json` 没有暴露不符。
6. **回放的归属**：
   - `plugin/deadlines.json` 的文法部分（`valid`、`invalid`、`written`）由原语层的测试对 `DeadlineText` 回放；插件宿主的测试改走协议自己的读写点（`PluginDeadlines.Effective` 与 `PluginMetadata.FromContext`），`effective` 仍在那里。ADR-0276 补的 16 条 `invalid` 两边都跑到。
   - `context/http-deadline.json`（37 条）由 `Hosting.AspNetCore` 的测试回放：按用例的请求头建 `HttpContext`，时钟停在向量的 `now`，经公开的 `HttpInvocation.CreateContext(httpContext, services)` 取截止时间。
   - `primitives/operation-ids.json`（34 条）由原语层的测试回放，并核对向量里确有正好 128 个字符的合法 ID 与只因 129 个字符而不合法的 ID。
   - `caching/cache-keys.json` 登记为过渡的缺口，理由指向 ADR-0274。

## 理由

- 一条文法只该有一个解析器。两个读取点各写各的，就是这次要修的分歧的来源；`TraceParent` 已经证明「载体文本的文法放原语层、各载体共用」行得通。
- 取严不取宽与 ADR-0276 一致：HTTP 入口以前照收的写法，别的语言的宿主做不到同样宽松，没有偏移的时间按哪个时区读、只有时间的补哪一天，都依赖解析器所在的机器。
- 读不出不报错是规范的决定：截止时间是可选的，带着旧写法的调用方请求仍然成功，只是不再有截止时间。代价见「影响」。

## 影响

**公开 API（只增）**

- 新增 `XiHan.Framework.Primitives.DeadlineText`：`TryParse(string?, out DateTimeOffset)`、`Format(DateTimeOffset)`。
- 新增 `XiHan.Framework.Primitives.Manifests.ActivationEvent`：`IsValid(string?)`。
- `HttpInvocation` 的签名与常量不变，变的是 `xihan-deadline` 的读法。`PluginDeadlines` 是 internal，不在公开面。

**行为变化：`xihan-deadline` 不再读得出的写法**

HTTP、gRPC 元数据、MCP 的 Streamable HTTP 与认证方案 `XiHan` 四处同时生效。下面这些以前读得出，现在当作没有这个头（以 `2026-11-18T03:25:00Z` 为例）：

| 写法 | 例子 | 以前读成 |
| --- | --- | --- |
| 空格代替 `T` | `2026-11-18 03:25:00Z`、`2026-11-18 03:25:00 +08:00` | 同一时刻 |
| 没有偏移 | `2026-11-18T03:25:00`、`2026-11-18T03:25:00.5`、`2026-11-18 03:25:00` | 当作 UTC |
| 没有秒 | `2026-11-18T03:25Z`、`2026-11-18T03:25` | 秒取 0 |
| 只有日期或年月 | `2026-11-18`、`2026-11` | 当天或当月 1 日的零点 |
| 只有时间 | `03:25:00`、`03:25` | 补上宿主当天的日期 |
| 偏移不是 `±HH:MM` | `+0800`、`+08`、`+8`、偏移前带空格 | 按该偏移 |
| 小数超过九位，或小数点写成逗号 | `.1234567890Z`、`,5Z` | 四舍五入到 100 纳秒 |
| 首尾带空白 | 空格、制表符、换行、U+00A0 | 裁掉后读 |
| 斜线分隔的日期 | `2026/11/18T03:25:00Z`、`11/18/2026 03:25:00`、`11/18/2026` | 同一时刻（月 / 日 / 年） |
| HTTP 日期与英文月份名 | `Wed, 18 Nov 2026 03:25:00 GMT`、`18 Nov 2026 03:25:00`、`November 18, 2026 03:25:00` | 同一时刻 |

合法文本读出的值有两处变了：

- 比 100 纳秒细的小数截断而不是四舍五入：`2026-11-18T03:25:00.123456789Z` 以前读成 `.1234568`，现在是 `.1234567`。
- `9999-12-31T23:59:59.999999999Z` 以前进位后溢出、读不出，现在读成能表示的最晚时刻。

没有变的：头出现多次与值为空，以前也读不出；读出的时刻已经过去仍以 `KERNEL_TIMEOUT_001`（504）结束；`grpc-timeout` 的读法。

**迁移**

- 调用方自己写 `xihan-deadline` 的，写成带 `T`、带秒、带偏移的 RFC 3339 时刻。.NET 用 `DeadlineText.Format(deadline)`（或 `ToString("O")` 写带偏移的 `DateTimeOffset`）；JavaScript 的 `Date.prototype.toISOString()`、Go 的 `time.RFC3339Nano`、Java 的 `Instant.toString()` 写出的都合文法。
- 容易踩到的两种：不带时区的时间（.NET 的 `DateTime` 且 `Kind` 为 `Unspecified` 时 `O` 格式没有偏移，Python 的朴素 `datetime.isoformat()`）以前被当作 UTC；秒为零时省略秒的写法（Java 的 `OffsetDateTime.toString()`）以前照收。两者现在都读不出。
- 这个变化是静默的：读不出不报错，调用照常执行，只是不再有截止时间。宿主没有为此记日志（见「没有解决的」）。
- 清单：`activation` 里带下划线的 `onEvent:` 以前在读取时以 `kernel.manifest.invalid` 被拒、构造 `Manifest` 时抛 `ArgumentException`，现在读得出；已有的清单都不受影响。
- 自己写了激活事件正则的代码可以改用 `ActivationEvent.IsValid`。

**测试**

- 新增 `DeadlineTextVectorTests`、`OperationIdVectorTests`、`ActivationEventTests`（原语层）与 `HttpDeadlineVectorTests`（宿主）；`WebHostTests` 补两个用例：宽松写法的已过期时刻不再让请求以 504 结束，头出现两次时没有截止时间。
- `SpecVectorCoverageTests` 的缺口表登记 `caching/cache-keys.json`。ADR-0274 的回放合进来之后要删掉这一项，否则测试以「缺口有了回放」失败；在那之前规范 README「都没有缺口」的说法对参考实现暂时不成立。

**文档**

- 包 README：`Primitives`（主要类型加 `TraceParent`、`DeadlineText` 与各字段的文法类型）、`Hosting.AspNetCore`（`xihan-deadline` 只认一种写法）。
- 文档站待改：`web/hosting.md` 的请求头表、`common/resilience.md` 与 `startup/invocation-context.md` 里「RFC 3339，UTC」的说法、`protocols/grpc.md` 与 `packages/protocols-grpc.md`（`xihan-deadline` 读不出时 `grpc-timeout` 生效）、`packages/hosting-aspnetcore.md`、`packages/primitives.md`（两个新类型）、`plugins/overview.md` 的 `activation` 一行（`onEvent:` 可以带下划线）、更新日志。

**没有解决的**

- 请求带了 `xihan-deadline` 却读不出时，宿主不记日志也不计数，调用方用旧写法的话只能从「截止时间没有生效」反推。要不要记、记在哪一级、带不带头的原文（它是调用方写的，原样进日志有伪造日志行的风险），没有定。
- `Manifest` 与 `ManifestShape` 里 SemVer 与插件权限两条正则同样各有一份，这次没有动：规范没有改它们，收拢要再加两个公开的原语成员。
- 六个 SDK 的激活事件文法与操作 ID 上限由各自的仓库跟进（ADR-0276「影响」）。
