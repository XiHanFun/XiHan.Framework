# ADR-0302 S3 的服务端点不带用户信息，发起分片缺上传标识返回错误，运营方开关进配置索引

## 状态

已采纳（`ObjectStorage.S3` 的 `S3ObjectStorageOptions` 拒收带用户信息的端点，`S3BlobStore.StartAsync` 对缺上传标识的应答返回 `OBJECTSTORAGE_UNAVAILABLE_001`；CLI 知识库的配置索引新增「由 Provider 读取」的键，收进 S3 的两个运营方开关；规范 RFC-0012「S3 Provider」「范围读取、分片上传与预签名」「一致性」已改）。

## 日期

2026-11-25

## 背景

ADR-0294 与 ADR-0295 的「待定」留下三处，仓库所有者已拍板都做：

- **合法的端点可以带用户信息**（ADR-0294 待定第二条）。`ServiceUrl` 只要求是绝对的 http 或 https 地址，`https://user:pass@host` 照样收下、原样保存，`S3ObjectStorageOptions` 打印时明文出现（`PrintMembers` 只遮蔽密钥、令牌与代理凭据）；AWS SDK 也不用这段用户信息，配了的人以为凭据随地址走，实际走的是两项密钥或默认凭据链。端点有三个来源：缺省实例的配置节、绑定 `objectstorage` 的主值（Service Binding 的 Secret 里的 `uri`）、命名实例的设置（可以由租户填写，ADR-0117）。
- **发起分片上传的应答没有上传标识时抛出**（ADR-0295 待定第二条）。`StartAsync` 把应答里的 `UploadId` 直接交给 `BlobMultipartUpload` 的构造。回环上的假对端回 `200` 而没有响应体时，SDK 照收、`UploadId` 为空，构造抛 `ArgumentNullException`；内存替身给出空串、空白、带控制字符或超过 1024 个字符的标识时，构造抛 `ArgumentException`（本 ADR 的用例先红后绿时实测）。合规的服务不会这样应答，兼容服务的缺陷或中间的代理改写了响应体时会。
- **两个运营方开关不在配置索引里**（ADR-0294 待定第一条）。`docs/packages/objectstorage-s3.md` 的「两个运营方开关」是 `XiHan:ObjectStorage:S3:NamedInstancesUseAmbientCredentials`（ADR-0178）与 `XiHan:ObjectStorage:S3:NamedInstancesAllowProxy`（ADR-0294），由 `S3BlobStoreProvider` 带 `IConfiguration` 的公开构造读取。配置索引 `Knowledge/configuration.json` 只收各 Options 类 `FromConfiguration` 读的键，`KnowledgeConfigurationTests` 对每个键核对「读到了」，收进去会被判为 indexed but never read；操作 `cli.config`（MCP tool `xihan_framework_config`）因此查不到这两个键。索引是人工整理的（ADR-0076），`Update-CliKnowledge.ps1` 只生成包与特性清单 `catalog.json`。

## 备选

### 端点的用户信息

1. **照收、打印时遮蔽用户信息**：否决。拍板是凭据只走密钥配置；留着一段 SDK 不用的凭据，只会让人以为配上了。
2. **把用户信息拆出来当 `AccessKey` / `SecretKey`**：否决。凭据多出一条路，要定它与配置节、绑定属性的优先级，要解百分号编码，还要与两项密钥成对（ADR-0294）的核对交织。
3. **只拒绝带口令的（`user:pass@`），`user@` 与空的 `@` 照收**：否决。`user@` 的用户名常是访问密钥 ID，是半套凭据；空的 `@` 没有用处。按 RFC 3986 的 `userinfo "@"` 出没出现一刀切，规则一句话说得清。
4. **以 `Uri.UserInfo` 是否为空判定**：否决。`http://@host` 的 `UserInfo` 是空串，看不出主机之前写过 `@`；取连同分隔符的 `UriComponents.UserInfo | UriComponents.KeepDelimiter`，非空即带了用户信息。路径、查询与片段里的 `@` 不在这一段里。
5. **与不合法的端点共用「must be an absolute http or https URL」**：否决。看不出错在哪；另写一句，指明凭据该写在哪几个键里，仍只报键名或绑定名，不带原值（ADR-0294）。
6. **新登记错误码**：否决。命名实例照旧是定义不合法 `OBJECTSTORAGE_VALIDATION_003`，缺省实例照成组设置的处置装配失败（`ArgumentException`）。

### 发起的应答缺上传标识

7. **错误码**：按 RFC-0012「S3 Provider」的现有映射，不存在的键与桶之外，「其余服务端错误」是 `OBJECTSTORAGE_UNAVAILABLE_001`；服务应答成功却缺了必需的内容是服务一侧的问题，归这一类。否决的有：
   - `OBJECTSTORAGE_VALIDATION_*`：调用方没有过错，校验类的码让人去查自己的输入。
   - 新登记「服务应答不合规」的码：调用方的处置与其余服务端错误相同（等运维换服务或修代理），`reason` 已说明是哪一步的应答，不值得单独一个码。
   - 抛 `FrameworkException`：仓库约定可恢复的失败返回 `Result`。
8. **`reason` 照 ADR-0115 写异常类型的全名**：不适用，这里没有异常。写固定文本 `InitiateMultipartUpload returned no usable UploadId`，与条件写入探测的 `reason` 写明哪一步是同一做法，不带应答里的值（可能很长，也可能带控制字符）。
9. **只判 `null`**（字面上的「没有 `UploadId`」）：否决。空串、空白、带控制字符、超过 1024 个字符的同样让句柄的构造抛 `ArgumentException`。先按句柄构造写明的公开前置条件（1 到 1024 个可见字符）判，哪一种都不抛。
10. **在 `ObjectStorage.Abstractions` 公开 `BlobMultipartUpload.IsValidUploadId`，S3 调它**：没有做。那是 Stable 类型的公开面增项，而上传标识的写法规范没有写（RFC-0012 只说「不透明」），要另走 RFC。S3 包按构造文档写明的前置条件判，边界由用例守住：1024 个字符收下、1025 个拒绝。
11. **用 `try`/`catch` 接住句柄构造的 `ArgumentException`**：否决。拿编程错误的异常做流程控制，也会吞掉别的参数错误。
12. **收到这样的应答后重发，或放弃那个上传**：否决。重发可能在服务端再留一个未完成的上传；没有标识放弃不了。留给桶的生命周期规则（未完成的分片上传过期即放弃）。

### 运营方开关进配置索引

13. **维持只收 Options 类读的键**：否决（拍板）。
14. **另起一个节条目，`options` 写 Provider 的类型**：否决。节与 Options 类一一对应，`EveryOptionsClassWithFromConfiguration_IsIndexed` 与 `ConfigurationSection` 常量的核对都按 Options 类；同一个节分成两条，按节查会得到两条。
15. **键上加一项可选的「读取它的类型」`readBy`**：采纳。模型多一个可选成员，JSON 里只在这两个键上出现，其余 305 个键不动。
16. **在代码里以特性标出 Provider 读的键，由脚本生成索引**：否决。配置索引一直是人工整理、测试核对（ADR-0076）；脚本照旧只生成 `catalog.json`。
17. **查询输出不带 `readBy`**：否决。`SectionView` 说的是「读取它的 Options 类」，不带上它，`cli.config` 就把这两个键说成 Options 类读的。`KeyView` 加一项可空的 `ReadBy`，为空不写，其余键的输出不变。
18. **测试怎么调 Provider 的构造**：取它恰好一个带 `IConfiguration` 参数的公开构造（宿主的容器里总有配置，按它建 Provider），配置之外的参数从一个只有宿主缺省服务的容器里取：内核 `AppBuilder` 总会补上的时钟、日志与出站地址策略。以后的 Provider 要别的服务时用例失败、写明缺哪个类型。不选 `ActivatorUtilities`：它在几个构造之间按容器里取得到什么挑一个，要核对的是带配置的那一个，直接取它更明确。

## 决策

### 端点不带用户信息

1. RFC-0012「S3 Provider」写明（MINOR，以前正文没有规定端点的写法）：`ServiceUrl` 与绑定 `objectstorage` 的主值是绝对的 http 或 https 地址，主机之前不能有用户信息——`user:pass@`、`user@`、`:@` 与空的 `@` 都算，路径、查询与片段里的 `@` 不算；S3 的凭据只走 `AccessKey`、`SecretKey`、`SessionToken` 与绑定的同名属性。带了用户信息是配置错误，处置同成组设置。
2. `S3ObjectStorageOptions` 的四处入口共用私有的 `RequireServiceUrl`：先判绝对的 http / https，再判连同分隔符的用户信息。消息只带主语与凭据该写的键：
   - 配置节：`'XiHan:ObjectStorage:S3:ServiceUrl' must not contain user information; set the credentials with 'XiHan:ObjectStorage:S3:AccessKey' and 'XiHan:ObjectStorage:S3:SecretKey'.`
   - 命名实例的设置：同上，键不带前缀；`S3BlobStoreProvider.CreateAsync` 照旧转成 `OBJECTSTORAGE_VALIDATION_003`，不建客户端。
   - 绑定的主值：`The value of binding 'objectstorage' must not contain user information; set the credentials with the binding properties 'accessKey' and 'secretKey'.`；绑定覆盖配置节，配置节里合法的端点救不了它。
   - 直接构造（`init`）：`The service URL must not contain user information; set the credentials with 'AccessKey' and 'SecretKey'.`
3. 合法端点的保存与打印不变：现在合法的端点里没有用户信息，`ToString()` 不必再遮蔽端点。

### 发起的应答缺上传标识

4. RFC-0012「范围读取、分片上传与预签名」的 S3 一条写明（MINOR，以前不作规定）：发起的应答成功却没有可用的上传标识（缺失、为空，或当不了句柄），是不合规的应答，同其余服务端错误返回 `OBJECTSTORAGE_UNAVAILABLE_001`，不抛出；`reason` 写明是发起的应答没有可用的上传标识，不带应答里的值；不重发。「S3 Provider」的错误映射补一句：服务应答成功却缺了必需的内容同样是服务端错误。错误码登记表不改。
5. `S3BlobStore.StartAsync` 拿到应答后先判 `IsUsableUploadId`（1 到 1024 个字符，不含空白与控制字符，同句柄构造的公开前置条件），不合即记一条 Warning（`The S3 service answered InitiateMultipartUpload for bucket '{Bucket}' without a usable upload ID.`，不带标识的值）并返回 `OBJECTSTORAGE_UNAVAILABLE_001`，`reason` 为 `InitiateMultipartUpload returned no usable UploadId`。不覆盖的发起照旧先 `Head`，之后的缺标识同样处理。

### 由 Provider 读取的键

6. `ConfigKeyEntry` 加可选成员 `ReadBy`（JSON `readBy`）：读取这个键的类型的完全限定名，与节的 Options 类同包，不是 Options 类时才写。为空即由 Options 类读取，行为同以前。
7. `configuration.json` 的 `XiHan:ObjectStorage:S3` 一节在末尾加两个键，`readBy` 都是 `XiHan.Framework.ObjectStorage.S3.S3BlobStoreProvider`：`NamedInstancesUseAmbientCredentials`、`NamedInstancesAllowProxy`，类型 `boolean`，缺省 `false`。
8. `KnowledgeConfigurationTests`：
   - `Section_MatchesWhatItsOptionsRead` 只拿 `readBy` 为空的键核对 Options 类；Options 类读到了标成 Provider 读取的键，同样报「read but not indexed」。「要有缺省值或示例」对两类键都查。
   - 新增 `ProviderKeys_MatchWhatTheirProviderReads`，按（节, 读取类型）逐个：以记录读取的配置调用那个构造（见备选 18），核对每个键都读到、构造在节内读到的路径都登记为它读的、必填键缺了就失败、上下限与枚举与布尔取值按索引接受或拒绝。Provider 不公开读到的值，「缺省值与不写等价」不在这里核对，由包自己的测试经带配置的公开构造核对：代理开关不写与 `false` 都不许是 `S3ConfigurationHardeningTests` 原有的，凭据开关的同一条以前只经内部构造核对，`S3NamedInstanceCredentialTests` 补上经配置的两条。
   - 读取委托由原来的 `MethodInfo` 改成 `Func<IConfiguration, object>`，两类核对共用 `Invoke`、`ExpectFailure`、`CheckRange` 与「节内读到却没登记」的判断。
9. 查询输出 `KeyView` 加 `ReadBy`（为空不写）；`appsettings` 片段照旧按缺省值写出，S3 一节多出两个 `false`。
10. `Update-CliKnowledge.ps1` 不改：`catalog.json` 不受影响，跑两遍都没有差异。

## 理由

- 凭据只有一条路，配置、日志与报错里都不会出现第二份；规则按 RFC 3986 的成分判定，不靠字符串里找 `@`。
- 服务给的东西不合规，是服务一侧的错误：调用方拿到的应当是与其余服务端错误同一个码，而不是一个看上去像自己传错了参数的异常。
- 配置索引的用处是让人与编码助手查到每个能写的键；读取它的是 Options 类还是 Provider，只是核对的入口不同，同一套「读到、登记、取值」的核对都能做。

## 影响

- **公开 API**：不变（`PublicAPI.Unshipped.txt` 无改动）。CLI 的 `ConfigKeyEntry`、`KeyView` 是内部类型；`cli.config`（MCP tool `xihan_framework_config`）的输出对这两个键多出 `readBy`。
- **升级须知（行为收紧）**：`ServiceUrl`（配置节或命名实例的设置）或绑定 `objectstorage` 的主值带用户信息的部署，升级后缺省实例启动失败、命名实例登记失败（`OBJECTSTORAGE_VALIDATION_003`）。迁移：地址去掉 `user:pass@`，凭据写进 `AccessKey` / `SecretKey`（绑定写属性 `accessKey` / `secretKey`）；以前这段用户信息本来就没有被 SDK 使用。
- **行为**：`StartAsync` 遇到缺上传标识的应答不再抛出，返回 `OBJECTSTORAGE_UNAVAILABLE_001`；一致性套件不变。
- **规范**（规范仓库已改，指针待更新）：RFC-0012 两处写明，都是 MINOR（以前不作规定；只影响 .NET 的 S3 Provider，线上与各 SDK 不变）；「一致性」的「向量不收的」写明 S3 Provider 的配置写法不收向量。没有新向量、新错误码。
- **测试**（都不需要 S3 服务）：
  - `S3ConfigurationHardeningTests`：七种带用户信息的写法在配置节、绑定的主值（配置节的端点合法时照样拒绝）、命名实例的设置与建实例、直接构造里都被拒，消息与日志里没有用户名与口令；缺省实例装配失败；路径、查询、片段里有 `@` 与 IPv6 字面量的端点照收。
  - 新增 `S3MultipartStartResponseTests`：回环假对端回 `200` 而没有响应体时（真实 SDK），返回 `OBJECTSTORAGE_UNAVAILABLE_001`、只有发起这一个请求、记一条带桶名的 Warning；内存替身给出空串、空白、带空格、带控制字符、1025 个字符的标识同样返回它，`reason` 写明 `InitiateMultipartUpload` 与 `UploadId`、不带标识的值；1024 个字符的标识收下；不覆盖的发起先 `Head` 再发起，缺标识照样返回它。改实现之前 7 条失败（`ArgumentNullException` / `ArgumentException`）。
  - `FakeS3Client` 加 `NextUploadId`，可以让发起的应答不带标识或带任意标识。
  - `S3NamedInstanceCredentialTests`：凭据开关经配置不写或写 `false` 时，没给密钥的定义被拒，原因写明要打开的键。
  - CLI：`ProviderKeys_MatchWhatTheirProviderReads` 一行（S3）；把一个开关的 `readBy` 去掉、把另一个的键名拼错时，两条核对分别报出（先红后绿时实测）；`KnowledgeQueriesTests` 新增按键路径查到开关、带 `ReadBy`，Options 类自己的键不带。
- **文档**：包 README 已补端点不带用户信息；文档站的 `packages/objectstorage-s3`（端点一段、运营方开关表注明已进配置索引）、`configuration/options`（绑定主值）、`object-storage/advanced`、命令行知识库的说明页与更新日志待改。
- **待定**：S3 其余应答缺了必需内容时仍会抛出，本 ADR 没有处理——`UploadPart` 的应答没有 `ETag` 时 `BlobPart` 的构造抛 `ArgumentException`；`ListParts` 的分片没有编号时按 0 交给 `ValidatePartNumber`，同样抛出。要不要按决策 4 一并返回 `OBJECTSTORAGE_UNAVAILABLE_001`，留给后续。
