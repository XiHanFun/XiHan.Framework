# ADR-0294 S3 命名实例配代理要运营方开关，配置报错不回显原值，缺省实例的半套密钥是配置错误

## 状态

已采纳（`ObjectStorage.S3` 的 `S3BlobStoreProvider`、`S3ObjectStorageOptions` 已改；`xihan pack` 的绑定 Secret 样板已补；规范 RFC-0012「S3 Provider」与「命名存储实例」、RFC-0016 的状态行、`packaging/app-manifest.md` 已改）。

## 日期

2026-11-25

## 背景

ADR-0281 把会话令牌、超时、尝试次数与代理做成设置之后，它的「待定」与复核留下四处：

- **命名实例的代理没有运营方开关**（ADR-0281 备选 6 与「待定」）。命名实例（`BlobStores` 按 `BlobStoreDefinition` 建的）的设置可以由租户填写（ADR-0117、ADR-0178）。配了代理时过出站地址策略的是代理的地址，目标归代理管：运营方若在策略里放行了一个内网正向代理，能填命名实例设置的人就能经它到达策略本来拒绝的地址（元数据服务、内网管理面）。同类的「借宿主的身份」在 ADR-0178 已经由运营方开关 `NamedInstancesUseAmbientCredentials` 管住。
- **`ServiceUrl` 报错回显原值。** `S3ObjectStorageOptions.ServiceUrl` 的 `init` 抛出 `The service URL '…' must be…`，写成带用户信息的地址（`http://user:pass@host`）又拼错了协议时，口令进了异常消息；缺省实例装配失败时它进启动日志，命名实例经 `OBJECTSTORAGE_VALIDATION_003` 的 `reason` 回到登记实例的调用方。ADR-0281 对 `ProxyHost` 已经是「报键名，不带原值」。
- **缺省实例的半套密钥悄悄走默认凭据链**（ADR-0281「待定」第三条）。只给 `AccessKey` 或 `SecretKey` 其中一项时，`CreateCredentials` 返回空、SDK 走环境变量与实例角色：配置的人以为用的是这把钥匙，实际是宿主的身份。命名实例早就拒绝（ADR-0178）；ADR-0281 新增的成组设置也都拒绝半套，只有这一处是原有行为。
- **`xihan pack` 的绑定样板没有 `sessionToken`。** ADR-0281 给绑定 `objectstorage` 加了属性 `sessionToken`，`bindings.example.yaml` 的 `blob` 段仍只以注释列出 `accessKey`、`secretKey`。

同一个包里其余配置报错带出原值的地方（逐条查过 `S3ObjectStorageOptions`、`S3BlobStoreProvider`、`S3ConditionalWriteProbe`、`S3ObjectStorageFeature`）：

| 位置 | 带出的 | 处理 |
| --- | --- | --- |
| `ParseBoolean`（`ForcePathStyle`、`EnsureBuckets`、`ConditionalWrites`、绑定的 `forcePathStyle`） | 原值 | 保留 |
| `ParseInt32`（`MaxAttempts`、`ProxyPort`）、`ParseSeconds`（`RequestTimeoutSeconds`）、`ConfigurationValues` 读的 `HealthProbeIntervalSeconds` 与两个运营方开关 | 原值 | 保留 |
| `RequestTimeout`、`MaxAttempts`、`ProxyPort`、`HealthProbeInterval` 的 `init`（`ArgumentOutOfRangeException.ActualValue`） | 原值 | 保留 |
| `FromSettings` 的未知设置键 | 键名 | 保留 |
| `Region`、`HealthBucket`、`ProxyHost` 与成组设置的报错 | 只有键名 | 不用改 |
| `ServiceUrl` 的 `init`，配置节、实例设置与绑定主值经它 | 原值 | 改 |

保留的判断依据：带出的只有数值、布尔值与键名，它们的取值空间里没有凭据，报原值能直接看出写错了什么；会写进凭据的只有字符串键——两项密钥、令牌、代理的四项，以及可以带用户信息的地址（`ServiceUrl`、绑定主值）——这些一律只报键名。`Region` 与桶名不是机密，但它们的报错本来就没有带值，不必为它们开例外。

## 备选

1. **命名实例一律不许配代理**：否决。运营方自己登记的多个实例（不经租户）走统一的出口代理是合理的部署，应该能显式打开，理由同 ADR-0178 备选 1。
2. **开关放在实例设置里**：否决，理由同 ADR-0178 备选 2：设置正是租户能填的部分。
3. **开关只管 `ProxyHost`，`ProxyUserName` 这类照收**：不需要。读取设置时已经核对成组（用户名与口令只能跟着代理给），有主机才算配了代理，判一项即可。
4. **先判开关、再判代理的写法与成组**（定义里出现任何 `Proxy…` 键就拒绝）：否决。空白的键按 ADR-0281 不算给出，要另写一套「算不算给出」的判断；先照常读设置，两种错误都是 `OBJECTSTORAGE_VALIDATION_003`，报错都不带值。
5. **键名 `NamedInstancesUseProxy`**：否决，读起来像「命名实例都走代理」。采纳 `NamedInstancesAllowProxy`：开关的含义是允许实例自己的设置配代理。
6. **`ServiceUrl` 报错遮蔽用户信息、保留其余部分**：否决。不合法的地址解析不出结构，遮蔽要自己找 `@`，写错的花样多（缺 `//`、协议拼错、多出空格），漏一种就泄露；只报键名最稳，排查时去看配置本身。
7. **合法的 `ServiceUrl` 也不许带用户信息**：不在本 ADR。决定只管报错；合法地址的打印另见「待定」。
8. **半套密钥的核对放在 `S3ObjectStorageFeature.Configure`，不进 `RequireComplete`**：否决。`RequireComplete` 是 ADR-0281 成组核对的一处：绑定覆盖之后读完即核对，手工构造的选项在建客户端时核对，命名实例读设置时核对。放进去三条路一致。命名实例原先在 `RequireCredentials` 里的「只给一项」分支因此走不到，删掉。
9. **半套密钥保留旧行为、只记一条警告**：否决，是静默兜底（ADR-0281 备选 9）。
10. **为命名实例的开关另登记错误码**：否决。它与密钥开关一样是定义不合法，沿用 `OBJECTSTORAGE_VALIDATION_003`。

## 决策

1. **运营方开关 `XiHan:ObjectStorage:S3:NamedInstancesAllowProxy`**：
   - 常量 `S3BlobStoreProvider.AllowProxyKey`；缺省 `false`；与 `AmbientCredentialsKey` 一样由带 `IConfiguration` 的公开构造读取，不是布尔值时构造即抛出 `ArgumentException`（`ConfigurationValues.ReadBoolean`）；三参数的公开构造按关闭。
   - 不在实例设置的已知键里：实例设置写了它是未知的键，定义不合法。
   - 关闭时，读完设置（格式与成组都核对过）之后有 `ProxyHost` 即拒绝：`OBJECTSTORAGE_VALIDATION_003`，原因写明要打开哪个键，不带代理的主机、端口、用户名与口令。不建客户端，不发任何连接。
   - 打开之后照 ADR-0281 决策 6：代理的地址过出站地址策略。
   - 缺省实例（配置节 `XiHan:ObjectStorage:S3`）的代理不受它约束。
2. **配置报错不回显 `ServiceUrl`**：
   - 配置节与实例设置先判再赋值，报 `'<前缀>ServiceUrl' must be an absolute http or https URL.`；绑定的主值报 `The value of binding 'objectstorage' must be …`；直接构造时 `init` 报 `The service URL must be …`。都不带原值。
   - 规则写成：配置错误的消息带出的原值只限数值与布尔值，字符串键只报键名。
3. **两项密钥成对**：`RequireComplete` 第一条核对 `AccessKey` 与 `SecretKey` 同时给出或都不给，消息 `'<前缀>AccessKey' and '<前缀>SecretKey' must be set together.`。
   - 缺省实例在绑定的属性 `accessKey`、`secretKey` 覆盖之后核对（与 ADR-0281 的顺序一致），两项可以一项来自绑定、一项来自配置节；只给一项时装配失败（`ArgumentException`）。
   - 手工构造的选项在 `CreateClientConfig` / `CreateCredentials` 时核对。
   - 命名实例读设置时核对，仍是 `OBJECTSTORAGE_VALIDATION_003`。
4. **`xihan pack` 的绑定样板**：`bindings.example.yaml` 的 `blob` 段以注释列出 `accessKey`、`secretKey`、`sessionToken`，写法同其余凭据键。

## 理由

- 命名实例的两类风险——借宿主的身份、借内网的路——都由运营方决定，开关放在租户够不到的地方，缺省关闭。
- 只报键名不损失排查能力：键名指向配置里的那一行，值在配置里看得到；报错与日志的读者远比配置的读者多。
- 半套密钥与令牌、代理的半套是同一类错误，处置一致，文档只讲一遍。

## 影响

- **公开 API**（`PublicAPI.Unshipped.txt` 已同步，只有新增）：`S3BlobStoreProvider.AllowProxyKey`。`S3BlobStoreProvider` 是 `Preview`；内部构造多了 `allowProxy` 参数。
- **升级须知（行为收紧）**：
  - 命名实例的设置里配了代理（`ProxyHost` 等）的部署：升级后登记失败（`OBJECTSTORAGE_VALIDATION_003`）。确认由运营方负责后，在配置节写 `"XiHan:ObjectStorage:S3:NamedInstancesAllowProxy": true`。
  - 缺省实例只给了 `AccessKey` 或 `SecretKey` 其中一项的部署（含一项来自绑定、另一项哪里都没有）：升级后启动失败。要用默认凭据链就两项都删掉，要用静态密钥就两项都给。应用自己向容器注册了 `IAmazonS3` 的也一样：配置节照常读取与核对。
  - 只依赖消息文本的：`ServiceUrl` 不合法时的消息不再带原值；命名实例只给一项密钥时的消息由「Named S3 instances must set both …」变为「'AccessKey' and 'SecretKey' must be set together.」，错误码不变。
- **规范**（规范仓库已改，指针待更新）：RFC-0012「S3 Provider」新增「两项密钥成对」一条，「客户端的设置」的报错一条写明只带数值与布尔值、端点只报键名；「命名存储实例」写明代理开关；`packaging/app-manifest.md` 的样板凭据键补 `sessionToken`，RFC-0016 状态行跟上。前两处是 MAJOR（改已写明的行为，`v1.0.0` 之前允许），样板是 MINOR。
- **命令行**：`KustomizeGenerator` 的 `blob` 凭据键补 `sessionToken`，`PackagerTests` 的样板断言跟着改。`Knowledge/configuration.json` 没有改：配置节索引只收各 Options 类 `FromConfiguration` 读的键（`KnowledgeConfigurationTests` 对每个索引的键核对「读到了」），两个运营方开关由 Provider 的构造读取，收进去会被判为「indexed but never read」；ADR-0178 的 `NamedInstancesUseAmbientCredentials` 也因此一直不在索引里。见「待定」。
- **测试**（都不需要 S3 服务）：`S3ConfigurationHardeningTests`：开关关闭时带代理的定义被拒、不建客户端、原因与日志里没有代理的取值，打开后照常建出；不带代理的实例不需要开关；开关从运营方配置读、缺省与 `false` 都不许、不是布尔值时构造抛出；策略放行了回环时关闭的开关照样不让本进程连代理（假代理上连接数为 0）；实例设置打不开开关；缺省实例照常配代理；三种不合法的端点在配置节、实例设置、绑定主值、直接构造与命名实例的错误里都只报键名；只给一项密钥时缺省实例读取失败、手工构造的选项建客户端失败、装配失败；一项来自绑定时覆盖之后成对。`S3ClientSettingsWireTests` 的命名实例改为经带配置的构造、打开开关建出。
- **文档**：包 README 已补两项密钥成对、端点报错与两个运营方开关的表；文档站的 `packages/objectstorage-s3`、`object-storage/advanced`、`configuration/options`、`deployment/pack` 与更新日志待改。
- **待定**：
  - 运营方开关进不进配置节索引：要么给索引加「由 Provider 读取」的键类，并让 `KnowledgeConfigurationTests` 对这类键改为核对 Provider 的构造；要么维持只收 Options 类的键。两个开关（本 ADR 与 ADR-0178）一并处理。
  - 合法的 `ServiceUrl` 带用户信息时照样原样保存、在 `ToString()` 里明文打印（SDK 也不用这段用户信息）。要不要拒绝带用户信息的端点，或打印时遮蔽，没有在本 ADR 决定。
