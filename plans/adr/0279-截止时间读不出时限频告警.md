# ADR-0279 截止时间读不出时限频告警

## 状态

已采纳（内核新增 `UnreadableDeadlineLog` 并登记为单例；`Hosting.AspNetCore` 的 HTTP 入口与 `Plugins.Protocol` 的回调元数据在读不出截止时间时经它记一条限频的 Warning，调用的结果不变；`protocol/http.md`、`protocol/grpc.md`、`plugin/invocation.md` 已补）。

## 日期

2026-11-24

## 背景

- ADR-0276 / ADR-0278 把截止时间的文本收紧成一条文法（RFC-0003 规则 8）：HTTP 头 `xihan-deadline` 以前用通用的日期解析，空格代替 `T`、没有偏移、只有日期、HTTP 日期等写法都读得出，现在读不出。读不出当作没有给出截止时间，调用照常执行。
- 这个变化是静默的。ADR-0278「没有解决的」记着：宿主不记日志也不计数，调用方用了旧写法只能从「截止时间没有生效」反推；要不要记、记在哪一级、带不带原文没有定。
- 「调用方给的截止时间文本读不出就当没有」在 .NET 里一共三处，两个读取点：
  - `HttpInvocation.Create`（`Hosting.AspNetCore`）读 `xihan-deadline`，读不出或没有时再读 gRPC 的 `grpc-timeout`。HTTP、gRPC 元数据、MCP 的 Streamable HTTP 与认证方案 `XiHan` 都经这一个读取点。
  - `PluginMetadata.CreateContext`（`Plugins.Protocol`）读插件回调的 `InvocationMetadata.deadline`，进程外与 Wasm 两个宿主共用。
  - 命令行的 `--timeout` 与 MCP 的 stdio 传输不传文本，写错是用法错误（退出码 64），不属于这一类。
- 头的原值是调用方写的。原样进日志有两个风险：伪造日志行（不经 HTTP 解析器的入口可以带换行，按行解析日志的系统也可能被别的分隔符骗过）、把日志撑大（每个请求一条、每条带一段任意长度的文本）。

## 备选

1. **继续不记**：否决。读不出不报错是规范的决定，但宿主一点痕迹都不留，升级之后截止时间悄悄失效的调用方查不出来。
2. **读不出时答 400**：否决，ADR-0276 备选 3 与 ADR-0278 备选 7 已否决；规范写的是当作没有这个头。
3. **每次都记，不限频**：否决。日志量由调用方决定，一个坏掉的客户端或一次攻击就能刷满日志。
4. **带上原值，转义或截断之后再记**：否决。转义规则要跟着日志的落地格式走（文本、JSON、各家采集器），宿主不知道下游怎样解析；截断仍然让调用方往日志里写自己选的内容。长度已经够定位：旧写法的长度有限的几种（`2026-11-18` 是 10，没有偏移的是 19）。
5. **按调用方（远端地址、主体）或按原值分别限频**：否决。要一张按调用方或原值建的表，条目数由调用方决定，正是「不得无界增长」要防的；加上限与淘汰又是一套要测试的机制。固定的两个计数字段足够回答「有没有调用方在发读不出的截止时间、有多少」。
6. **用 `System.Threading.RateLimiting` 的 `FixedWindowRateLimiter`**：否决。它的窗口由真实的定时器或手工补充驱动，不认 `TimeProvider`，测试里推进不了；内部有锁；也不给出每个窗口被拒绝的条数。这里要的状态只有窗口起点与计数两个字段。
7. **限频的状态放静态字段**：否决。同一进程里的多个宿主（测试、多应用）会互相压掉对方的告警，测试之间也互相影响。状态挂在容器里的单例上，随宿主存亡。
8. **告警服务放在 `Hosting.AspNetCore`，插件一侧另写一份**：否决。两个包在不同的环（Ring 4 与 Ring 5），插件包不该为此引用 ASP.NET Core 宿主；各写一份限频门是重复建设。两个包都引用内核，内核已经有同类先例：`OutboundAddressPolicy` 是内核登记的单例，自己带 `LoggerMessage`。
9. **内核只给限频门，告警文案由各包自己写、各自登记单例**：否决。`Hosting.AspNetCore` 的登记点只有 `AddXiHan(WebApplicationBuilder)`，应用直接调内核的 `AddXiHan` 时就没有这个单例，告警悄悄消失；两个插件宿主还要各登记一次。内核在 `AppBuilder.Build` 里登记一次，凡是有 `App` 的容器里都有。
10. **三处共用一个限频门**：否决。请求头来自外部调用方，量可以很大；插件回调来自宿主自己装的插件，量小但更该被看到。共用一个门时，外部刷请求头会把插件一侧的告警一直压着。分成两类只多两个字段。`xihan-deadline` 与 `grpc-timeout` 同是请求头，算一类。
11. **值为空也记**：否决。空值是调用方没有要截止时间（有的客户端总写这个头、没有截止时间时留空），不是写错了；插件协议里空串本来就是「没有给」的写法。两处取同一条规则：不为空而读不出才记。
12. **同时加一个计数指标**：不在本 ADR。告警已经带着被压掉的条数；要不要进内核的 Meter、叫什么名字另行决定。
13. **窗口做成可配置**：不做。1 分钟一条对日志量没有压力，也足够及时；多一个配置键就多一处要进文档与工具知识库的东西。常量公开为 `UnreadableDeadlineLog.Window`。

## 决策

1. **内核新增 `UnreadableDeadlineLog`**（`XiHan.Framework.Kernel.Diagnostics`，`Preview`，自 5.0），`AppBuilder.Build` 以 `TryAddSingleton` 登记，日志与时钟取容器里的 `ILoggerFactory` 与 `TimeProvider`：
   - `ReportHeader(string header, int length, string? operationId)`：请求头里的截止时间读不出。
   - `ReportPluginMetadata(string pluginId, int length)`：插件回调的元数据里的截止时间读不出。
   - `Window`：限频的窗口，1 分钟。
2. **日志**：级别 Warning，`LoggerMessage` 源生成，类别是这个类型的全名。只带头名、原值的字符数、请求匹配到的操作 ID（没有匹配到操作时没有这一段）或插件的清单 ID，以及被压掉的条数；不带原值。
3. **限频**：请求头与插件回调各一个门，每个门在窗口里只放行一条，其余只计数；窗口过后的第一条放行，并带上上一次放行以来被压掉的条数。
   - 状态是每个门两个 `long`（窗口起点与计数），用 `Interlocked` 读写，没有锁，大小与调用的次数、调用方无关。
   - 窗口从放行的那一条算起，按 `TimeProvider.GetTimestamp` 的单调时间计，不受系统时间调整影响。
   - Warning 级别没开时不进门，计数不累加。
4. **HTTP 入口**（`HttpInvocation.Create`）：
   - `xihan-deadline` 不为空而读不出时报它，哪怕 `grpc-timeout` 接着生效。
   - 没有给 `xihan-deadline`、`grpc-timeout` 不为空而读不出时报 `grpc-timeout`。`xihan-deadline` 读得出时不看 `grpc-timeout`，它写成什么都不报。
   - 一个请求只报一次：同一个请求会建几次上下文（认证方案 `XiHan`、管道、MCP 的每个 `tools/call`），在 `HttpContext.Items` 里记一个标记。
   - 操作 ID 取端点元数据里的 `OperationDescriptor`（操作端点与 gRPC 方法都带）。
5. **插件回调**（`PluginMetadata.CreateContext`）：`deadline` 不为空而读不出时报，带插件的清单 ID。`PluginDeadlines.Effective` 多一个交出「写了却读不出」的重载，不再解析第二遍。
6. **调用的结果不变**：三处都仍按没有这个截止时间继续，不拒绝调用；插件回调仍不晚于 gRPC 调用自身的截止时间。容器里没有 `UnreadableDeadlineLog`（不是经 `AppBuilder` 装配的服务提供器）时不记，读法不变。
7. **规范**：`protocol/http.md`「上下文映射」写明宿主应当记一条不含原值的告警并限频，值为空不记；`protocol/grpc.md` 写明 `grpc-timeout` 同样；`plugin/invocation.md` §2 写明宿主读插件回调的 `deadline` 时同样，与请求头的告警分开计。都是「应当」，不记仍然符合规范；没有向量（日志不是对端观察得到的行为）。

## 理由

- 截止时间失效是会造成后果的静默变化：调用方以为请求最多跑 5 秒，实际没有上限。一条 Warning 让运维从宿主一侧就能发现，不必等调用方来报。
- 不带原值、限频、状态固定，三条合起来保证这条日志不会变成调用方手里的工具：写不进内容，刷不大日志，也撑不大内存。
- 放在内核、登记一次，三个读取处的行为由同一个类型保证一致，以后新的载体也到这里报。

## 影响

**公开 API（只增）**

- 新增 `XiHan.Framework.Kernel.Diagnostics.UnreadableDeadlineLog`：构造函数 `(ILoggerFactory, TimeProvider)`、`ReportHeader(string, int, string?)`、`ReportPluginMetadata(string, int)`、静态属性 `Window`。
- `HttpInvocation` 的签名与常量不变。`PluginDeadlines`、`PluginMetadata` 是 internal，不在公开面。没有新的配置键、错误码与消息键。

**行为变化**

- 以前不留痕迹的三种情况现在各记一条 Warning（类别 `XiHan.Framework.Kernel.Diagnostics.UnreadableDeadlineLog`）：
  - `The value of request header 'xihan-deadline' (19 characters) could not be read as a deadline and is ignored; the invocation of operation 'orders.create' continues without it. Similar warnings suppressed since the previous one: 0.`
  - 没有匹配到操作的端点没有 `of operation '…'` 这一段；`grpc-timeout` 读不出时头名是 `grpc-timeout`。
  - `The deadline in the callback metadata of plugin 'xihan.samples.echo' (19 characters) could not be read and is ignored; the callback continues without it. Similar warnings suppressed since the previous one: 0.`
- 请求头一类、插件回调一类，每类 1 分钟最多一条。按 Warning 告警的监控会在升级后第一次看到这一类日志；它说明有调用方在发读不出的截止时间，处理办法见 ADR-0278「迁移」。
- 响应、状态码、截止时间的读法与取值都不变。

**规范**

- `protocol/http.md`、`protocol/grpc.md`、`plugin/invocation.md` 各补一段，级别 MINOR（把以前不作规定的写成「应当」）。RFC-0003 规则 8 的读法不变，不改。
- 六个 SDK 是插件一侧，不读请求头，也不是宿主，这次没有要跟的。

**测试**

- 内核 `UnreadableDeadlineLogTests`：窗口内只记一条、窗口过后带被压掉的条数、两类分开计、并发下每个窗口只放行一条且计数不丢、参数核对、内核登记为单例。
- 宿主 `UnreadableDeadlineWarningTests`：读不出记一条且调用照常、窗口内不再记、窗口过后带条数、日志里没有原值、读得出 / 没有给 / 值为空不记、头出现两次、`grpc-timeout` 的两种情况、一个请求建几次上下文只算一次、没有告警服务时不记；最后一组走真实的宿主，核对操作 ID 与状态码。
- `PluginMetadataTests` 与 `GrpcProtocolTests` 各补一个用例。

**文档**

- 包 README：`Kernel`（主要类型加 `UnreadableDeadlineLog`）、`Hosting.AspNetCore`（`xihan-deadline` 读不出时的告警）。
- 文档站待改：`web/hosting.md` 的请求头表、`common/resilience.md`、`startup/invocation-context.md`、`protocols/grpc.md`、`packages/hosting-aspnetcore.md`、`packages/protocols-grpc.md`、`packages/kernel.md`、`plugins/out-of-process.md` 与 `plugins/wasm.md` 讲回调元数据的地方、更新日志。

**没有解决的**

- 没有计数指标（备选 12）。
- 并发下单条告警上的「被压掉的条数」可能在相邻两条之间挪动几个：换窗口起点与取走计数不是一个原子动作。合计不丢也不重；要逐条精确就得加锁，不值得。
- 同一个请求里 `xihan-deadline` 与 `grpc-timeout` 都读不出时只报前一个。
- 插件一侧（六个 SDK）读宿主写来的 `deadline` 读不出时记不记，规范没有要求：宿主写出的文本由 `DeadlineText.Format` 生成，读不出只可能是实现缺陷，由向量把关。
