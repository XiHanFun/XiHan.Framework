# ADR-0296 工作流表达式的格式化函数与工作量上限、关键字的小写、活动里的时间

## 状态

已采纳（四项各自在规范与本仓库实现，见各节的「影响」）。

## 日期

2026-11-25

## 背景

ADR-0287 把表达式小语言写进规范之后，「没有解决的」里留下了几件事，ADR-0277 的关键字向量也有一处两边不一致。所有者拍板了下面四项，本文逐项记下取舍与做法：

1. 数字的文本只看数值之后（`19.90` 写成 `19.9`），模板里「金额显示两位小数」无法表达——加内置函数 `format(x, n)`。
2. 一次求值没有时间或步数的上限，长度以内写得出秒级 CPU 的表达式——加一个与平台无关、确定的累计工作量上限。
3. 关键字折叠的 `İ`（U+0130）：Go 规则的 `unicode.ToLower` 折成 `i`，.NET 的不变文化不转换——定成一种写进正文。
4. `Delay.Until`、`UserTask.DueAt` 与 `WorkflowValues.TryConvert<DateTimeOffset>` 仍交给 `DateTimeOffset.TryParse`——改用表达式的时间文法。

四项各占一节，每节有自己的备选、决策与影响；提交也按项拆开，规范与本仓库各四个，次序同本文的节。

## 一、内置函数 `format(x, n)`

### 背景

ADR-0287 决策 3 规定数字的文本只有一种写法：不用指数、不带结尾的零。升级须知写明「要固定小数位数的展示（金额）在流程之外格式化，或把格式化好的字符串放进变量；语言里目前没有格式化函数」。审批单的标题、通知与 HTTP 请求体的模板里，金额要写成两位小数，这是表达式最常见的展示需求。

### 备选

1. **让数字记住小数位数**：否决，ADR-0287 备选 3 否决过——JSON 的读取器拿不到这个位数，存储会不会保留它也因库而异。
2. **格式串**（`format(x, 'N2')`、`'0.00'`）：否决。千分位与小数点随区域；`N2`、`F2`、`0.00`、`%.2f` 各语言的语法不同，写进规范等于再定义一个格式串小语言，而需求只是定长的小数位数。
3. **舍入一半取偶**：说明里写的是「舍入与 `round` 相同（一半取偶）」，而 `round` 在 RFC-0021 与 .NET 里都是**正好一半时远离零**（`Math.Round(…, MidpointRounding.AwayFromZero)`，`round(2.5)` 是 3、`round(1.005, 2)` 是 1.01）——两半句互相矛盾，「一半取偶」只是「放进数字」时的舍入。照「与 `round` 相同」做：`format(x, n)` 就是 `round(x, n)` 的定长写法，`toNumber(format(x, n)) == round(x, n)` 总成立；金额展示要的也是四舍五入。若取一半取偶，`format(0.125, 2)` 是 `0.12` 而 `round(0.125, 2)` 是 `0.13`，同一个语言里两种舍入更难解释。
4. **`n` 截去小数部分**（与 `round` 相同）：否决。2.5 位小数没有意义，截成 2 是静默兜底；`n` 的值必须是整数（`2.0` 与 `'2'` 可以）。
5. **小数位数不合法另设消息键**（如 `not_integer`）：否决。沿用 `number_out_of_range`（`operator` 是 `format`）：它已经用于 `round` 的位数越界，模板「运算符 'format' 收到或产生了超出范围的数字」照样说得通，不必另补 10 个区域文件。
6. **`x` 不是数字时报 `not_number`**：否决。`not_number` 是解析时数字字面量的错误；求值时操作数不能当数字的一律是 `operands_not_numeric`，`format` 与 `abs`、`round` 同一组。
7. **结果是数字**：做不到——数字没有结尾的零，定长的只能是字符串。
8. **`n` 可省**（`format(x)` 写 0 位）：不加。实参个数固定为 2，以后再加是兼容的。

### 决策

1. RFC-0021「内置函数」加一行：`format(x, n)` 是字符串，先照 `round(x, n)` 舍入，再写出——整数部分照数字的文本，负数以 `-` 开头、没有 `+`；`n` 大于 0 时接小数点 `.` 与 `n` 位小数（不足的补零），`n` 为 0 时不写小数点；没有千分位，不随区域。舍入之后是零的不写负号（数字没有负零）：`format(-0.001, 2)` 是 `0.00`，`format(-0.005, 2)` 是 `-0.01`。
2. `x` 与 `n` 都要能当数字（数字文本照「数字文本」先读成数字），否则 `operands_not_numeric`（`operator` 是 `format`）；`n` 的值不是 0 到 28 之间的整数 → `number_out_of_range`（`operator` 是 `format`）。两个实参先从左到右都求值，再先核对 `x`、后核对 `n`（与 ADR-0287 决策 7 的次序一致）。
3. 结果最长 59 个码元（符号、29 位整数、小数点、28 位小数：`format(-79228162514264337593543950335, 28)`），远在 4194304 的字符串上限以内；它是字符串，不受数字范围（96 位整数加 28 位小数）的约束；当数字用时读回的就是 `round(x, n)`。
4. .NET：`ExpressionCompiler` 加 `format` 分支；内部的 `WorkflowNumberText.Format(decimal, int)` 把舍入好的数字补零到 `n` 位（位数多于 `n`、`n` 越界是编程错误，抛 `ArgumentOutOfRangeException`，不悄悄截断）。
5. 向量：`expression-functions.json` 补 39 条成功与 15 条失败的用例——各种位数、正好一半的两侧（`2.5`、`3.5`、`0.125`、`0.135` 区分远离零与一半取偶）、负数与舍入成零、进位到整数部分、最大与最小的数、28 位小数、数字文本（带指数与首尾空白）、结果是字符串（`format(1, 2) + 1` 是 `1.001`）、错误与实参个数；期望值由 .NET 算出。Go 一致性模块的内置函数名单加上 `format`。

### 影响

- 公开 API：没有签名变化，没有新消息键与错误码；`WorkflowMessages.ExpressionNumberOutOfRange` 的说明加上 `format`。
- 行为：只新增。以前 `format(…)` 解析时就是 `unknown_function`，发布过的定义里不会有它；名为 `format` 的变量不受影响（变量与函数可以同名）。
- 规范：RFC-0021「内置函数」一行、`operands_not_numeric` 与 `number_out_of_range` 的 `operator` 取值、「一致性」的向量表；`expression-functions.json`；`rules/workflow.go` 的 `WorkflowExpressionFunctions`。MINOR。
- 测试：`ExpressionFunctionVectorTests` 回放新用例，并核对向量里有带结尾零的结果、零位小数不写小数点、`format` 的 `number_out_of_range`；`WorkflowNumberText.Format(decimal, int)` 的补零与拒收。
- 六个 SDK：不受影响（不认领 `workflow` 档）。

## 二、一次求值的工作量上限

### 背景

ADR-0287「没有解决的」最后一条：一次求值的时间没有单独的上限。它当时的理由是「没有循环与递归，运算次数不超过表达式的长度」，但每一步读写的数据量没有界——变量可以有 8 MiB，一个字符串可以有四百万个码元。在 Release 构建上实测（每次求值）：

| 写法 | 一次运算 | 长度以内重复到底 |
| --- | --- | --- |
| `len(k+k+k+k)+…`（`k` 是 1048576 个码元） | 复制九百多万个码元，约 4 毫秒 | 两百多组，约 1 秒 |
| `a == b && …`（两个各一百万个数字的数组） | 遍历两百万个值，约 200 毫秒 | 三百次，约 1 分钟 |
| `contains(a, 'x') \|\| …`（一百万个元素） | 约 140 毫秒 | 两百多次，约半分钟 |
| `toString(o)`（二十万个成员的对象） | 约 50 毫秒 | 两百多次，约 10 秒 |

后三行比拼接慢两个数量级：开销在「值」上（取类型、把 JSON 数字读成数字、比较、排序成员名），每个值 70～350 纳秒；拼接、扫描与把字符串读成数字的开销在「码元」上，每个码元 0.4～1.8 纳秒。表达式与模板由持流程定义权限的用户写，模板本身不限长。

### 备选

1. **墙上时间的截止**：否决。结果随机器的快慢与负载变，进不了向量，同一个流程在快的机器上成功、在慢的上失败。
2. **只数步**（每个节点一步）：否决。步数本来就不超过表达式的长度（四千上下），开销在每一步读写的数据量。
3. **步数加产生的文本**（说明里给的例子）：只算产生的文本漏掉了上表的后三行——比相等、`contains`、把长字符串当数字读都不产生文本。所以记的是「读」：运算读到的字符串按长度，读到的容器按它里面值的个数与字符串的长度。拼接读的两侧之和就是产生的文本，例子里的那一项包含在内。
4. **容器按它的文本长度记**：否决。要算出文本长度，就得把每个数字写成规范文本、把每个字符串转义一遍，与写出文本一样贵；而读容器的开销在每个值上，不在字符上。
5. **容器里的值各记 1**：否决。上限要放得下拼到上限的拼接（九百多万），值记 1 时上限之内能遍历一千六百万个值，按实测要好几秒。值与码元的开销之比是一两百，一个值记 64（一步的工作量，与节点相同）：上限之内最多遍历二十六万个值，一千个元素的数组读一次是 64064，正常的容器离上限很远。
6. **容器按比较实际走到的地方记**（提前结束就少记）：否决。对象成员的次序各语言不同（Go 的 `map`、JavaScript 把整数样的键排在前面），提前结束的位置随之不同，计数就不确定。按读到的整个容器记，与怎样比无关；实现可以量到超过上限即停（.NET 这样做），结果相同。
7. **在数组里 `contains` 只读一次要找的值**：否决。逐个元素与它比相等的直白实现每次都要读它（把它当数字读、取它的文本），一百万码元的数字文本与一千个元素比就是十亿个码元；按元素个数乘以它的读取量记，直白的实现也有界。
8. **读取量在求值之前按表达式里的变量估**：否决，与值无关，算不准。
9. **上限做成配置**：否决，与 4194304 同一个理由（ADR-0287 备选 13）：同一个定义在一处能跑、在另一处不能。
10. **模板的每个占位各自一份**：否决。模板不限长，几十万个占位各自在上限以内、合起来是秒级；整个模板一份。字面文本不记：渲染出的文本已经受 4194304 约束，扫描它的开销随之有界。
11. **超过时报 `string_too_long`、或另设错误码**：否决。新消息键 `workflow.expression.budget_exceeded`（参数 `max`），错误码仍是 `WORKFLOW_VALIDATION_003`。参数里不带累计的工作量：实现在使它超过的那一笔里量到哪里停下可以不同（.NET 量到超过即停），确定的只有「超没超」与在哪个运算上超。

### 决策

1. **规则**（RFC-0021「表达式」的「长度与上限」）：一次 `Evaluate` 或 `EvaluateCondition` 从 0 起累计工作量，一次 `Render` 的全部占位共用一份；单位是 UTF-16 码元。
   - **步**：每开始求值一个节点记 64——字面量、变量、成员访问、索引、函数调用、一元与二元运算；括号不是节点；短路没有求值的右操作数不记。
   - **读**：运算求值完全部操作数之后、核对它们之前，记它读的操作数的读取量。读取量：字符串是长度；数组与对象是 64 乘以它里面的值的个数（它自己也算），加上全部字符串与成员名的长度；`null`、布尔与数字是 0。哪些运算读哪些操作数是正文里的一张表：拼接读两侧；算术、比较、一元负、数字函数（含 `format`）与数组的下标只读字符串操作数；相等在两侧都是标量时读字符串、两侧都是容器时读两侧、其余不读；在数组里 `contains` 读数组再按元素个数读要找的值；别的字符串函数与 `toString`、`date` 读全部实参；对象的键读下标；模板的每个占位读结果；`!`、`&&`、`||`、`.name`、`len`、`isNullOrEmpty`、`now` 与加法不读。
   - 每记一笔就与上限比较，超过即停。步先于节点的操作数记，读先于运算自己的核对：`k + k + k + k + k` 在工作量以内，报的是 `string_too_long`。在模板里，求值占位里的表达式时超过的，`expression` 参数是那段表达式；记占位的结果时超过的，是模板。
2. **上限 16777216**（2^24，拼接上限的 4 倍）：把四个 1048576 的字符串拼到拼接的上限是 9437632，渲染出 4194304 个码元的模板是它加上占位的步，长度以内最长的表达式只计步是 256000 上下——都在以内。按实测，上限之内的任何一次求值在参考实现上都在一百毫秒以内（最慢的是在十三万个元素的数组里 `contains`，约 50 毫秒）。
3. **.NET**：内部新增 `ExpressionRun`（作用域加累计的工作量，`Step`、`Read`、`ReadIfString`、`ReadTimes`），`CompiledExpression` 改成在它上面求值；量容器时累计超过剩下的额度即停，几十万个值的容器不必走完；`WorkflowExpressionEvaluator` 内部的 `Evaluate` / `Render(…, out long work)` 交出累计的工作量（测试与向量回放用）。新增消息键常量 `WorkflowMessages.ExpressionBudgetExceeded`，10 个区域文件都补了。
4. **向量**：`expression-limits.json` 新增 `maxWork`（16777216）、`stepWork`（64）、很长的数组变量 `arrays`（1382 个 0）、一个 1044224 个码元的字符串变量与两个小变量，以及 33 条 `budgets`：22 条逐条核对计数规则的（成功，带累计的工作量），11 条上限两侧的——只计步（262144 个占位正好到上限、多一个就超过）、读字符串（正好到上限、多一个码元就超过）、读容器、拼接到上限一次与两次、模板读占位的结果到上限与超过（带模板）、占位里的表达式超过（带那段表达式）。期望值由 .NET 算出。Go 一致性模块：类型 `WorkflowExpressionArray`、`WorkflowExpressionBudget`，常量 `MaxWorkflowExpressionWork`、`WorkflowExpressionStepWork`，消息键名单加上 `budget_exceeded`（26 个），核对每条用例的写法与两侧都有，只计步的那一对按规则算出工作量。

### 影响

- 公开 API：新增常量 `WorkflowMessages.ExpressionBudgetExceeded`；`IWorkflowExpressionEvaluator` 的说明写明上限。没有签名变化与新的配置键、错误码。
- 行为（升级须知）：工作量超过 16777216 的表达式与模板以前能求值成功（只是慢），现在以 `WORKFLOW_VALIDATION_003`（`budget_exceeded`）失败。正常的表达式远在上限以内；撞上的是把几十万个值的变量整个渲染进模板、在几十万个元素的数组里 `contains`、比两个很大的容器、对百万码元的字符串反复做字符串运算这类写法——迁移是在活动里处理这样的数据，或只取需要的成员。
- 规范：RFC-0021「长度与上限」里「没有另设求值步数的上限」改成工作量的规则（改了已写明的行为，MAJOR，`v1.0.0` 之前允许），「错误」表加一行，「模板」与「错误」写明带出的文本；`expression-limits.json`；`rules/workflow.go`、`vectors_subsystems.go`。
- 测试：`ExpressionLimitVectorTests` 回放 `budgets`（成功的核对累计的工作量，失败的核对全部参数）并核对两侧都有；新增 `ExpressionBudgetTests`（两个百万元素的数组比相等、在数组里找百万码元的值、每次求值一份而渲染共用一份、超过 64 层的容器只算一个值）。五个表达式向量文件原有的用例全部照旧通过。
- 六个 SDK：不受影响。

## 三、关键字折叠的小写

### 背景

列表查询的关键字（RFC-0021「定义」的「关键字」，ADR-0096、ADR-0099）写的是「不变文化的小写」。.NET 的 `WorkflowKeyword.Fold` 逐个 UTF-16 码元取 `char.ToLowerInvariant`，Go 规则 `FoldWorkflowKeyword` 逐个码位取 `unicode.ToLower`。ADR-0277 的 `keyword-matching.json` 只收了两边相同的字符。把全部码位逐个对过（Go 1.27 带 Unicode 17.0；.NET 10 在 Windows 11 上走 ICU，数据是 Unicode 15.x，invariant 全球化模式下用自带的 Unicode 16.0 数据）：

| 映射 | Go `unicode.ToLower` | .NET `char.ToLowerInvariant`（以前） | .NET `Rune.ToLowerInvariant`（ICU） | 同（invariant 模式） |
| --- | --- | --- | --- | --- |
| 有小写映射的码位 | 1488 | 1172 | 1432 | 1459 |
| `İ`（U+0130） | `i` | 不变 | 不变 | 不变 |
| 基本多文种平面以外的大写字母（德塞莱特、欧塞奇、古匈牙利、瓦朗齐地、梅德法伊德林、阿德拉姆、维斯库奇等 260 个） | 折叠 | 不变（代理项逐个转换，原样留下） | 折叠 | 折叠 |
| Unicode 16.0 与 17.0 新收录的（U+1C89、U+A7CB、加莱字母等 55 个） | 折叠 | 不变 | 不变 | 16.0 的折叠，17.0 的 28 个不变 |
| `ẞ`、`Σ`、切罗基字母、开尔文符号、`ǅ` | 相同 | 相同 | 相同 | 相同 |

没有一个码位是 .NET 折叠而 Go 不折叠的；Go 的 `unicode.ToLower` 正是 UnicodeData.txt 的 Simple_Lowercase_Mapping。两边的差别只有三类：`İ`、平面以外的字母（.NET 逐码元的缺陷）、各自所带 Unicode 数据的版本。

### 备选

1. **把 .NET 的不变文化写进正文**：否决。「不变文化」是 .NET 的概念，它不转换 `İ`、不转换平面以外的字母，别的语言要复现只能抄 .NET 的表；平面以外的字母不折叠是逐码元转换的缺陷，不是有意的规则。
2. **完全映射**（SpecialCasing.txt，`İ` 折成 `i` 加 U+0307）：否决。折叠后的长度会变，查询列与关键字的长度不再对应；Go 的 `unicode.ToLower` 与 .NET 的 `Rune.ToLowerInvariant` 都是简单映射，完全映射要另写一份表。
3. **Unicode 的大小写折叠**（CaseFolding.txt 的 C 与 S，Unicode 推荐的不区分大小写比较）：否决。它把小写的切罗基字母折成**大写**、把 `ς` 折成 `σ`、把 `ſ` 折成 `s`，与「小写」的直觉不同；Go 与 .NET 都没有现成的简单折叠函数（Go 的 `unicode.SimpleFold` 是在等价类里转圈），各语言都得自带表。简单小写映射在 Go（`unicode.ToLower`）、.NET（`Rune.ToLowerInvariant` 加一处例外）、Java（`Character.toLowerCase(int)`）上都是现成的。
4. **Go 改成与 .NET 一样不转换 `İ`**：否决。那是让规则迁就一个平台的特例。
5. **钉一个 Unicode 版本，.NET 自带一份映射表**：否决。约一千五百个映射的表要随 Unicode 维护，换来的只是新近收录的几十个字符一致。Unicode 的映射只在收录新字符时增加（新字符本身，以及因此才有了成对字符的已有字符，如 Unicode 8.0 收录切罗基小写字母之后原有的大写字母），版本不同的实现只在这些字符上不同：标为实现自定，向量只收 Unicode 9.0 及更早就有、之后没有变过的映射。
6. **只认 ASCII 的大小写**：否决。西里尔、希腊、全角字母现在就折叠，收窄改变的已有结果比这次多得多。

### 决策

1. RFC-0021「定义」新增「关键字的小写」：逐个码位取 Unicode 的简单小写映射（Simple_Lowercase_Mapping，没有映射的码位不变），不做 SpecialCasing 的完全映射，也不做按上下文、按区域的映射——`İ` 折成 `i`，`ẞ` 折成 `ß`，`Σ` 总是折成 `σ`，开尔文符号折成 `k`，`ǅ` 与 `Ǆ` 折成 `ǆ`，切罗基大写字母折成小写字母，平面以外的字母同样折叠，`ı` 不变。映射不跨平面，折叠前后的 UTF-16 长度相同；含孤立代理项的文本不在规定之内。映射取自实现所带的 Unicode 数据，新近收录的字符怎样折叠实现自定。
2. .NET：`WorkflowKeyword.Fold` 对代理对取 `Rune.ToLowerInvariant`，对基本多文种平面的字符取 `char.ToLowerInvariant`，U+0130 由这里折成 `i`；分隔符照旧换成空格。映射万一跨了平面就抛出，不悄悄写坏（全码位的测试核对它不发生）。
3. Go：`FoldWorkflowKeyword` 的 `unicode.ToLower` 本来就是这条规则，只改注释；新增测试核对全部码位折叠前后的 UTF-16 长度相同。
4. 向量：`keyword-matching.json` 补 10 条规范化用例（`İ`、`ı`、`ẞ`、词尾的 `Σ`、开尔文与埃符号、`ǅ` 与 `Ǆ`、切罗基、德塞莱特、阿德拉姆、平面以外没有大小写的字符）与 5 条匹配用例（`İ` 在关键字与在字段里、`i` 加组合点匹配不到 `İ`、词尾的 `ς` 与 `Σ` 不同、平面以外的字母不区分大小写）；期望值由 .NET 算出，Go 回放同样通过。

### 影响

- 公开 API：没有签名变化；`WorkflowKeyword.Fold`、`Normalize`、`Join`、`Matches` 的结果只在含 `İ` 或平面以外的大写字母的文本上不同。
- 行为（升级须知）：数据库实现的查询列存的是写入时的折叠结果（定义行与实例行的 `SearchText`、书签行的 `SearchTitle` 与 `SearchInstanceText`）。含 `İ` 或平面以外大写字母的已有行要按新的 `WorkflowKeyword.Join` / `Fold` 重新算出回填，否则关键字里的这些字符匹配不到它们；不含这些字符的行（绝大多数）不受影响。内存实现每次现算，不用迁移。
- 表达式的 `upper` / `lower` 不在这次的范围：它们的 U+0130 与 U+0131 仍是实现自定（ADR-0287 决策 12），.NET 照旧逐码元转换。
- 规范：RFC-0021「关键字」「关键字的小写」与「一致性」（改了已写明的「不变文化的小写」，MAJOR，`v1.0.0` 之前允许）；`keyword-matching.json`；`rules/workflow.go` 的注释与 `rules/workflow_test.go`。
- 测试：`WorkflowKeywordVectorTests` 回放新用例，核对向量里有 `İ`、平面以外的字母与「完全映射才命中」的用例，并逐个码位核对折叠不改变长度、不抛出。
- 六个 SDK：不受影响。
