# ADR-0333 S3 的元数据值照 RFC 2047 编解码，批量删除逐项报告，其余几处不合规的应答与没读到末尾的释放

## 状态

已采纳（规范 RFC-0012「S3 Provider」「范围读取、分片上传与预签名」「一致性」与 `conventions/error-codes.md` 里 `OBJECTSTORAGE_UNAVAILABLE_001` 的说明已改；`ObjectStorage.S3` 新增内部类型 `S3MetadataHeader`，`S3BlobStore` 写入与发起分片上传时照 RFC 2047 编码元数据的值、读取与 `Head` 时解码，批量删除接住 `DeleteObjectsException` 逐项报告，写坏的 XML、放弃分片上传与建桶的解析失败、列出分片交出不比起点大的编号返回 `OBJECTSTORAGE_UNAVAILABLE_001`，发起分片上传时建桶失败不再抛出，`S3ObjectStream` 没读到末尾就释放时不抛出；公开签名、配置键、错误码与消息键不变）。

## 日期

2026-11-27

## 背景

ADR-0322「影响」的待定与第九轮对 RustFS 的实测留下六处 S3 Provider 的问题，仓库所有者已拍板全部修：

1. **写不出非 ASCII 的元数据值**：`SocketsHttpHandler` 缺省不发出含非 ASCII 字符的请求头，`x-amz-meta-*` 里有中文、成对的代理项等时写入以 `HttpRequestException` 失败，返回 `OBJECTSTORAGE_UNAVAILABLE_001`；规范与向量把 `2026 年度报告` 这类值算合法，文件系统存储照收。SDK 的 `AWSConfigsS3.EnableUnicodeEncodingForObjectMetadata` 是进程级的全局开关，又逐个 UTF-16 码元做百分号编码，拆坏成对的代理项。拍板：Provider 自己照 RFC 2047 编解码。
2. **批量删除的逐项报错在真实 SDK 上走不到**：`DeleteObjects` 的应答有错误项时 SDK 抛 `DeleteObjectsException`（静默模式也是），Provider 把整批报成存储故障；ADR-0313 按 `DeleteErrors` 逐项报告的分支只有内存替身走得到。
3. **写坏的 XML 原样抛出**：响应体不是良构的 XML 时 SDK 抛 `XmlException`。
4. **列出分片的编号不比起点大**：不重复时没有判定。
5. **两处成功应答没接解析失败**：`AbortMultipartUpload` 与 `PutBucket`。
6. **读够长度后释放也抛出**：调用方读够声明的长度、没读到末尾就释放时，SDK 在释放时才核对，`S3ObjectStream` 的释放抛出携带 `OBJECTSTORAGE_UNAVAILABLE_001` 的 `FrameworkException`（ADR-0322 决策 18）。拍板：没读到末尾就释放时不抛（核对没有意义，Dispose 不抛也是 .NET 的约定），读到末尾时核对失败照旧报错；先查清 SDK 在哪里核对，再定在哪一层判断。

## 查明的事实

以下是对 `AWSSDK.S3` 4.0.104.8、`AWSSDK.Core` 4.0.102.14 的反编译（ilspycmd）与线上实测（回环上的 `RecordingHttpListener`），以及对本机 RustFS 的实测。

- **SDK 在哪里核对整读的内容**：`HashStream.Read` / `ReadAsync` 在读到 0 个字节时调 `CalculateHash`；`Dispose` 也调 `CalculateHash`。`CalculateHash` 在 `ExpectedLength < 0` 或已读的字节数等于 `ExpectedLength`（应答的 `Content-Length`）时才算散列并核对，否则记一个空散列、不核对；散列一经记下（`FinishedHashing` 是 `CalculatedHash != null`，在抛出之前就记下）不再核对。所以：读到末尾的那次读核对、对不上即在那次读里抛出，之后的释放不再核对；只读了一部分就释放的不核对；读够了声明的长度、没读到返回 0 就释放的在释放时核对——第九轮遇到的就是这一种（`ReadExactly` 声明的长度再释放）。请求 0 个字节的读返回 0 同样触发 `CalculateHash`，这是 SDK 的行为，Provider 不另管。
- **`DeleteObjectsException`**：`AmazonS3ResponseHandler.ProcessResponseHandlers`（`PostInvoke`，解组之后）遇到 `DeleteErrors` 非空的 `DeleteObjectsResponse` 即 `throw new DeleteObjectsException(response)`，异常的 `Response` 就是解出的应答（`DeleteErrors` 与 `DeletedObjects`）。线上实测：尝试次数 3 时 SDK 不重发（HEAD、HEAD、一个 POST）。
- **SDK 写元数据**：`AmazonS3Util.SetMetadataHeaders` 把 `MetadataCollection` 的值原样写进请求头（开关打开时才逐个 UTF-16 码元百分号编码）；读回时 `GetObjectResponseUnmarshaller` 原样取头值（开关打开时 `Uri.UnescapeDataString`）。
- **RustFS 1.0.6**（本机镜像 `rustfs/rustfs:latest`，标签 `version=v1.0.6`，摘要 `sha256:ee717072…`，与 CI 钉的 `1.0.6` 相同）：经 SDK 原样写入的 `=?UTF-8?B?5Lit5paH?=`、`=?UTF-8?Q?=E4=B8=AD_x?=`、`=?UTF-8?B?5Lit?= =?UTF-8?B?5paH?=` 都原样存下、原样读回（不解码）；` lead` 读回 `lead`、`trail ` 读回 `trail`（首尾的空格被去掉）；`a  b`（中间两个空格）与空串原样往返；680 个「中」（2040 个字节）编码之后 3317 个字符的头照收、原样读回。
- **Amazon S3 的文档**（《Working with object metadata》，只读）：值里有非 US-ASCII 字符时按 RFC 2047 解码之后存下，返回时按 RFC 2047 编码，只有 US-ASCII 的值原样返回；用户元数据上限 2 KB，按各键与值的 UTF-8 字节数计。没有实测。

## 备选

### 元数据值的写入

1. **Provider 照 RFC 2047 编码**：采纳（拍板）。只用 B 编码、UTF-8 字符集，写成 `=?UTF-8?B?<base64>?=`。
2. **哪些值编码**：值里有 U+0020–U+007E 之外的字符（非 ASCII）；以空格开头或结尾（RustFS 实测会被去掉，HTTP 的字段值本来不含首尾空白）；以 `=?` 开头且以 `?=` 结尾（原样写出，读回时会被当作 encoded-word 解码）。采纳。中间的连续空格不编码：RustFS 实测原样往返，SigV4 只在签名时合并它们。空串不编码：RFC 2047 的 encoded-text 至少一个字符，空串写不成 encoded-word，RustFS 实测空串原样往返。只是含有 `=?` 的 ASCII（`=? 说明`、`结尾 ?=`）不编码：读回时不整个是 encoded-word，原样交出。
3. **拆分**：RFC 2047 §2 的 encoded-word 至多 75 个字符；`=?UTF-8?B?` 与 `?=` 占 12 个，base64 至多 63 个、取 4 的倍数是 60 个，即每个至多 45 个字节。按 Unicode 标量值累积，下一个字符放不进就先写出已有的，一个字符（平面以外的是 4 个字节）不拆在两个里；各个 encoded-word 以一个空格隔开（RFC 2047 §6.2 规定解码时忽略相邻 encoded-word 之间的空白）。采纳。按字节等分、不管字符边界：否决，RFC 2047 §5 要求每个 encoded-word 自己是完整的字符。
4. **孤立的代理项**：`BlobPutOptions.Metadata` 已拒收（ADR-0322）；编码时再遇到（核对被绕过）抛 `ArgumentException`，不换成 U+FFFD 照写。
5. **用 SDK 的 `EnableUnicodeEncodingForObjectMetadata`**：否决（拍板理由：进程级全局开关、拆坏代理项）；它的百分号编码也不是 S3 的约定。
6. **在规范里写明 S3 只收 ASCII 的值**：否决，契约与文件系统存储都收非 ASCII 的值。

### 元数据值的读回

7. **什么算 encoded-word**：值整个是以空格或制表符隔开的一个或多个 RFC 2047 §2 的 encoded-word（`=?charset?encoding?encoded-text?=`，charset 与 encoding 是不含空格、控制字符与 especials 的 token，encoded-text 是 `?` 与空格之外的可打印 ASCII、至少一个字符）才解码；只有一部分是的（`说明 =?UTF-8?B?5Lit?=`）、相邻的 encoded-word 之间没有空白的、首尾有空白的都原样交出。采纳：这正是 Provider 写出的形状，也是 Amazon S3 文档示例里返回的形状；不去解夹在普通文本中间的 encoded-word，免得把别的写入方原样写下的 ASCII 值当成编码。
8. **解码**：相邻 encoded-word 之间的空白忽略；各个解出的字节依次连起来再按 UTF-8 严格解码（一个字符被别的写入方拆在两个 encoded-word 里也照常解出）；charset 不区分大小写、只认 `UTF-8`，可带 RFC 2231 §5 的 `*语言` 后缀；encoding 认 `B` 与 `Q`（不区分大小写），`B` 用带补齐的标准 base64，`Q` 的 `_` 是空格、`=XX` 是一个字节（十六进制不区分大小写）、其余字符是它自己；单个 encoded-word 超过 75 个字符照常解码（别的写入方不一定拆）。采纳。
9. **解不了的怎么办**：按不合规的应答返回 `OBJECTSTORAGE_UNAVAILABLE_001`，原因 `HeadObject returned user metadata with an RFC 2047 encoded-word that does not decode to a valid value`（`GetObject` 同），不带应答里的值，记一条 Warning。采纳（倾向见拍板）。解不了包括：charset 不是 UTF-8、encoding 不是 B 或 Q、base64 坏了、Q 的 `=` 之后不是两位十六进制、字节不是合法的 UTF-8（含编成 UTF-8 的代理项 `ED A0 80`）、解出的值含控制字符（U+0000–U+001F、U+007F–U+009F，同 `BlobPutOptions.Metadata`：头里写不出的控制字符经编码就能带进来，交出去调用方原样写回即被拒绝；Amazon S3 的文档也说它不返回含不可打印字符的元数据）。否决的有：原样交出编码的文本（调用方拿到的不是存进去的值，又看不出来）；替换成 U+FFFD（静默乱码）；另认 `ISO-8859-1`、`US-ASCII` 等字符集（S3 的约定只有 UTF-8，别的字符集只会来自别的写入方原样写下的值，认了也认不全）。检查排在 `ETag`、修改时间与长度之后；只判存在与否的 `Head` 与起点越界时取总长的 `Head` 不读元数据，不受影响。
10. **两种服务都能往返**：Provider 写出的总是只有 US-ASCII 的值。RustFS 原样存取，读回的就是写出的 encoded-word；Amazon S3 若先解码、存下原值，返回时对非 ASCII 的值再编码，读回的是它自己的 encoded-word，同样照第 8 条解出。写进规范「S3 Provider」。
11. **Amazon S3 上没法实测的两处**：用户元数据上限若按请求头里编码之后的字节计，原值离 2048 字节上限不远、非 ASCII 的字节又多时（base64 是原来的 4/3，每 45 个字节另加 13 个字符），写入会被拒绝，按存储故障返回 `OBJECTSTORAGE_UNAVAILABLE_001`；以 `=?` 开头且以 `?=` 结尾的 ASCII 值，若它先解码 Provider 写出的 encoded-word、存下只有 ASCII 的原值并原样返回，读回时又被当作 encoded-word 解码。都作为已知的缺口写进规范，不为没实测的服务行为另加规则（例如预先按编码之后的字节数拒收：契约的上限按原值计，文件系统存储与 RustFS 都收得下）。

### 批量删除

12. **接住 `DeleteObjectsException`、从它的 `Response` 取 `DeleteErrors`**：采纳（拍板）。照 ADR-0313 的规则逐项报告（认得出键的只报那一项、`reason` 是 S3 的错误码），有认不出键的错误项就整批报告。`catch` 排在解析失败与存储故障之前（它是 `AmazonS3Exception`）；`Response` 为空时（SDK 的构造本来不允许）落到存储故障。成功应答里的 `DeleteErrors` 照样逐项报告：SDK 4.0 不会走到，以后的 SDK 若改成在应答里交出错误项，不当作全部删成。两处共用 `RecordDeleteErrors`。
13. **内存替身**：`FakeS3Client` 的批量删除改为同 SDK 抛出 `DeleteObjectsException`，原有的替身用例因此走的是真实 SDK 的路径；新增 `DeleteErrorsAnswered` 模拟在应答里交出错误项的 SDK。

### 写坏的 XML

14. **`IsUnparsableAnswer` 认 `XmlException`**：采纳（拍板）。与 `FormatException`、`OverflowException` 同一处置，每一步的 `catch` 不变；原因另写明是响应体：`<请求名> returned a body the SDK could not parse as XML`（仍含 `could not parse`）。SDK 解析出错的应答（4xx、5xx）时自己兜住、抛 `AmazonS3Exception`，不经这里。条件写入探测不改：没有归类的异常照旧按尚未确认记下并重试（ADR-0322 备选 10）。

### 列出分片的编号

15. **这一页交出的编号不比这一页请求的起点大即不合规**：采纳（拍板）。S3 的 `ListParts` 只交出编号大于 `PartNumberMarker` 的分片。原因 `ListParts returned a PartNumber not greater than the PartNumberMarker of the page`。检查排在重复之后：重复又不比起点大的按重复报告（ADR-0322 的用例「第二页重复第一页的编号」照旧报 `twice`）。第一页的起点是 0，编号又至少是 1，第一页不会触发。

### 放弃分片上传与建桶

16. **照其他调用的写法接解析失败**：采纳（拍板）。放弃分片上传加 `catch … when (IsUnparsableAnswer(exception))`，原因点名 `AbortMultipartUpload`。建桶抽成 `CreateBucketAsync`，返回 `Error?`，解析失败点名 `PutBucket`、服务端错误按存储故障。SDK 现在不会在这两步抛出解析异常，用例用内存替身按请求名注入。
17. **顺带修的缺陷**：写入与发起分片上传都在接住「桶不存在」的 `catch` 里建桶，而 `catch` 里抛出的异常同一个 `try` 的其余 `catch` 接不住。写入外面还有一层 `try`，所以建桶失败一向按存储故障返回（只是解析失败的原因点名了 `PutObject`）；发起分片上传外面没有，建桶失败时 SDK 的异常原样抛给了调用方。`CreateBucketAsync` 在建桶处就转成错误，两处一致。

### 没读到末尾的释放

18. **在哪一层判断「读到末尾」**：在 `S3ObjectStream`（Provider 交出的流）上判断：有一次请求了至少一个字节的读返回 0 即读到末尾。采纳。SDK 在返回 0 的那次读里核对（查明的事实），所以读到末尾的核对失败在那次读里抛出、已由读的转换换成 `FrameworkException`；释放时 SDK 不再核对。没读到末尾就释放时 SDK 抛出的 `AmazonClientException` 交给构造时给的回调、不抛出；回调记一条 Warning（`... the caller released the stream before reading to its end, so the release did not throw.`，只带桶名）：内容对不上而调用方读够了长度，这是唯一留下的痕迹。读到末尾之后的释放若 SDK 抛出（4.0 不会，以后的 SDK 若改成只在释放时核对），照旧换成异常抛出，「读到末尾时核对失败照旧报错」不依赖 SDK 的时机。
19. **按已读的字节数等于声明的长度算读到末尾**：否决。那正是拍板要不抛的情形（读够长度、没读到末尾）。
20. **释放时一律吞掉**：否决。读到末尾的规则就依赖 SDK 只在读里核对，SDK 一变就静默丢掉报告。
21. **流自己在读够声明的长度时主动多读一次、提早核对**：否决。多读会阻塞到连接关闭或超时（服务多给了字节时还会读进下一段），也改变了读的语义。
22. **`DisposeUndelivered`**：不变（没交出去的应答，释放时的核对照旧吞掉，ADR-0322 决策 18）。

## 决策

### 规范

1. RFC-0012「S3 Provider」（MINOR，写明以前不作规定的行为）：新增「自定义元数据的值」一条（写入、读回、解不了、两种服务的存法与 RustFS 的实测、Amazon S3 的两处已知缺口、不用 SDK 的开关）；批量删除写明 SDK 抛 `DeleteObjectsException` 时照样逐项报告；「SDK 解析不了的应答」补写坏的 XML、放弃分片上传与建桶，.NET 认的异常加 `XmlException`；「整读的内容对不上 `ETag`」写明只在读到末尾时报告；`EnsureBuckets` 写明建桶失败同其余服务端错误。
2. RFC-0012「范围读取、分片上传与预签名」（MINOR）：列出分片交出不比起点大的编号即不合规，重复的先按重复报告。
3. RFC-0012「一致性」（PATCH）：「向量不收的」补元数据值的编解码。状态行追加「同日再修订」，「对应 ADR」加本 ADR。
4. `conventions/error-codes.md` 的 `OBJECTSTORAGE_UNAVAILABLE_001`（PATCH，码不变）：补写坏的 XML、不比起点大的编号与解不了的 encoded-word，内容流在读到末尾时抛出。

### 实现（`ObjectStorage.S3`）

5. 新增 `internal static class S3MetadataHeader`：`Encode(string)` 与 `TryDecode(string, out string?)`，规则同备选 2–4、7–9。
6. `S3BlobStore`：
   - 写入与发起分片上传以 `S3MetadataHeader.Encode` 写元数据的值，写入结果里仍是原值；`ReadMetadata` 以 `TryDecode` 解码、解不了为 `null`，`DescribeObject` 据此返回不合规的应答；`ObjectAnswer` 加 `MetadataUndecodableReason`。
   - 批量删除接 `DeleteObjectsException`，与成功应答共用 `RecordDeleteErrors`。
   - `IsUnparsableAnswer` 认 `XmlException`；`UnparsableReason` 收异常，写坏的 XML 另写原因。
   - `ListPartsAsync` 判编号不比起点大（`ListedPartNumberBehindMarkerReason`）。
   - `AbortOneAsync` 接解析失败；新增 `CreateBucketAsync`，写入与发起分片上传经它建桶。
   - 整读与范围读取交出的流多给一个回调 `ContentDiscarded`，记 `LogContentDiscarded`。
7. `S3ObjectStream`：构造加 `discard` 回调与 `_ended`；四个读的重载经 `Track` 记下是否读到末尾；释放时没读到末尾的交给回调、不抛出，读到末尾的照旧换成异常抛出。
8. S3 包 README 写明元数据值的编解码、批量删除的逐项报告、写坏的 XML 与建桶，以及读到末尾才报告内容对不上。

## 理由

- RFC 2047 是 S3 自己对非 ASCII 用户元数据的约定（Amazon S3 的文档），兼容服务原样存取时也能往返；Provider 自己编解码，不依赖进程级开关，也不拆坏代理项。
- 读回只认「整个是 encoded-word」的值，解不了就报错：不把编码的文本或乱码当作存进去的值交给调用方，也不误解别的写入方原样写下的普通文本。
- SDK 把批量删除的逐项结果放进异常、把写坏的 XML 原样抛出，都是 SDK 的实现细节；Provider 接住它们，调用方拿到的仍是契约里的逐项结果与错误码。
- 读到末尾才算读完了内容：核对在那次读里发生、在那里报告；没读到末尾就释放的不抛出，守住 .NET 释放不抛的约定，又留下日志。

## 影响

- **公开 API**：无变化（`PublicAPI.Unshipped.txt` 不改）；配置键、错误码、消息键不变。
- **行为**（`ObjectStorage.S3`，`Stable`）：
  - 元数据值有非 ASCII 字符、首尾有空格或形如 encoded-word 时：以前写入与发起分片上传以 `OBJECTSTORAGE_UNAVAILABLE_001` 失败（非 ASCII）或读回少了首尾的空格；现在照 RFC 2047 编码写入、读回原值。读回时整个是 encoded-word 的值被解码（以前原样交出编码的文本）；解不了的读取与 `Head` 返回 `OBJECTSTORAGE_UNAVAILABLE_001`（升级须知：别的写入方以别的字符集写下 encoded-word 的对象，经本 Provider 读取与 `Head` 会失败，列举与删除不受影响）。
  - 批量删除：SDK 抛 `DeleteObjectsException` 时逐项报告，认得出键的只有那一项失败（以前这一批要删的项都以 `reason` 为异常类型的 `OBJECTSTORAGE_UNAVAILABLE_001` 失败）。
  - 写坏的 XML、放弃分片上传与建桶的解析失败、列出分片交出不比起点大的编号：返回 `OBJECTSTORAGE_UNAVAILABLE_001`（以前分别是抛 `XmlException`、抛解析异常、照收）。发起分片上传时建桶失败返回 `OBJECTSTORAGE_UNAVAILABLE_001`（以前抛 SDK 的异常）。
  - 整读的内容对不上 `ETag`：没读到末尾就释放流时不再抛 `FrameworkException`，改记一条 Warning；读到末尾的那次读照旧抛出。
- **规范**（规范仓库已改，指针待更新）：见「决策」第 1–4 条；不新增向量（编解码只有 .NET 的 S3 Provider 做，由它自己的测试与对 RustFS 的门控用例核对），SDK 不受影响。
- **测试**（`ObjectStorage.S3.Tests`）：
  - 新增 `S3MetadataWireTests`（线上的写法：要编码与不编码的值、45 字节的拆分与 4 字节字符的边界、发起分片上传；读法：B 与 Q、大小写、空白、跨词的字符、RFC 2231、长 encoded-word、原样交出的几种、解不了的 12 种、整读与范围读取、只判存在的 `Head` 不解码）、`S3MetadataHeaderTests`（编解码互逆、写出的 encoded-word 合长度与字符边界、孤立的代理项不被替换）、`S3ObjectStreamTests`（释放时读没读到末尾的两种处置，用释放时抛出的替身流）、`S3AbortAndBucketAnswerTests`（放弃与建桶的解析失败、发起分片上传时建桶失败）。
  - `S3DeleteResponseTests` 补两条线上用例（真实 SDK 抛 `DeleteObjectsException`：逐项与整批）与一条应答里交出错误项的替身用例；`S3UnparsableAnswerTests` 补写坏的 XML（列举 3 种、发起、列出分片、完成、批量删除），分类函数改为认 `XmlException`；`S3MultipartPartResponseTests` 补编号不比起点大（替身 3 条、线上 1 条）；`S3WholeReadETagTests` 把「读够长度之后的释放抛出」改为不抛、记 Warning，补只读一部分与读到末尾之后释放的两条。
  - 新增门控用例 `S3MetadataRoundTripTests`（4 条，`XIHAN_TEST_S3`）：写入、读取、范围读取与 `Head` 往返一组值（非 ASCII、平面以外的字符、首尾的空格、形如 encoded-word 的、连续空格、空串），接近 2048 字节上限的值，分片上传的发起与完成，别的写入方编好的 encoded-word；服务里存下的头值解得回原值。
  - 改实现之前（不含依赖新内部类型的三个类）这组用例里有 60 条失败。
  - 本机对 RustFS 1.0.6（本机镜像，摘要与 CI 钉的相同）跑全部 `ObjectStorage.S3.Tests`：420 条，0 失败，只跳过 `XIHAN_TEST_S3_UNCONDITIONAL` 那 1 条（门控用例 32 条全过）。
