# ADR-0322 S3 其余不合规的应答返回错误，元数据的值拒收孤立的代理项

## 状态

已采纳（规范 RFC-0012「标识」「契约」「S3 Provider」「S3 的条件写入探测」「范围读取、分片上传与预签名」「一致性」、`conventions/error-codes.md` 里 `OBJECTSTORAGE_UNAVAILABLE_001` 的说明与向量 `objectstorage/blob-metadata.json` 已改，Go 一致性模块的 `rules.IsBlobMetadata` 拒收不是合法 UTF-8 的值；`ObjectStorage.Abstractions` 的 `BlobPutOptions.Metadata` 拒收含孤立代理项的值，`ObjectStorage.S3` 的 `S3BlobStore` 在读取与 `Head` 缺长度、列举的对象缺长度、任一步的应答 SDK 解析不了、列出分片里同一编号出现两次时返回 `OBJECTSTORAGE_UNAVAILABLE_001`，整读交出的流把 SDK 的内容核对失败换成携带该码的 `FrameworkException`，`S3ConditionalWriteProbe` 在上传分片的应答缺 `ETag` 时以同一个码结束这次探测；公开签名、配置键、错误码与消息键不变）。

## 日期

2026-11-27

## 背景

ADR-0313 与 ADR-0317 的「待定」留下几处 S3 的不合规应答，另有元数据值里的孤立代理项。仓库所有者已拍板，按 ADR-0313 / ADR-0317 的「不合规的应答」路线处理：

- **读取与 `Head` 缺 `Content-Length`、列举的对象缺 `<Size>`**：长度取 SDK 给的值或 0。实测（`AWSSDK.S3` 4.0.104.8、`AWSSDK.Core` 4.0.102.14，回环上的 `RecordingHttpListener` 原样写出应答头）：应答没有 `Content-Length` 时，`AmazonWebServiceResponse.ContentLength`（HTTP 客户端解析出的值）是 0，`HeadersCollection.ContentLength`（SDK 解组时读到的原值）是 -1；`Content-Length: -5` 时 HTTP 客户端不认（当作没有，读到连接关闭），前者 0、后者 -5。以前 Provider 用前者，交出一个长度为 0 的非空对象。列举的条目缺 `<Size>` 时 SDK 给 `null`，Provider 按 0 交出。
- **SDK 解组时的解析失败**：`Last-Modified`、`Content-Length`、`x-amz-mp-parts-count` 等写错时，异步路径上的解组（`Amazon.Runtime.Internal.Unmarshaller.UnmarshallAsync`，同步路径包成 `AmazonUnmarshallingException`，异步路径不包）原样抛 `FormatException` / `OverflowException`。实测：`Last-Modified: not a date`、`Content-Length: abc`、`x-amz-mp-parts-count: abc`、`x-amz-server-side-encryption-bucket-key-enabled: maybe` 抛 `FormatException`，`Content-Length: 99999999999999999999`、`x-amz-mp-parts-count: 99999999999` 抛 `OverflowException`；`ListObjectsV2` 的 `<Size>abc</Size>` 抛 `FormatException`，超出 64 位抛 `OverflowException`。反编译各操作的应答解组：`GetObject`、`HeadObject`、`PutObject`、`UploadPart`、`InitiateMultipartUpload`、`CompleteMultipartUpload` 的应答头里都有按 `long` / `int` / `bool` / `DateTime` 读的值，`ListObjectsV2`、`ListParts`、`DeleteObjects` 的 XML 里有按数与布尔值读的元素；`AbortMultipartUpload` 与 `PutBucket` 的成功应答没有按类型读的值。
- **列出分片里同一编号出现两次**：ADR-0313 只在累计超过 10000 片时失败。10000 片之内重复的编号原样交出（按编号排序之后两片相邻），调用方拿列出的清单去完成，清单不是严格升序，得到 `OBJECTSTORAGE_VALIDATION_002`，像是自己给错了清单。
- **整读的内容对不上 `ETag`**：`ETag` 是十六进制而不是内容的 MD5（兼容服务对单次写入的对象给的不是 MD5，又没有 SSE 的应答头）时，SDK 把响应流包成 `MD5Stream`（ADR-0317），读到末尾才发现，抛 `AmazonClientException`（`Expected hash not equal to calculated hash`），调用方拿到的不是对象存储的错误。另查清：SDK 的 `HashStream` 在**释放**时也核对，读到的长度等于应答声明的长度就算——调用方读够了长度、没读到末尾就释放时，核对在释放时才发生；缺 `Content-Length` 时声明的长度是 0，一个字节没读的响应在释放时就核对、抛出。以前 Provider 在判了应答不可用之后释放响应，这个异常会从 `finally` 里盖过已经定下的结果（本 ADR 的用例先红时实测）。
- **`IsUndecodableETag` 认调用栈的文本**：ADR-0317 按 `Exception.StackTrace` 里 `AmazonS3ResponseHandler.ProcessResponseHandlers(` 那一帧识别「SDK 把 `ETag` 当 MD5 解码失败」。裁剪掉栈追踪的运行时（Native AOT 的 `StackTraceSupport = false`）里 `StackTrace` 不带方法名，识别失效。
- **条件写入探测里上传分片的应答缺 `ETag`**：探测照样以空的 `ETag` 发带条件的完成，结论取决于服务先判条件还是先判分片（先判分片的回 `InvalidPart`，报成完成那一步的服务端错误）。
- **元数据值里的孤立代理项**：值只拒控制字符，孤立的代理项照收。实测文件系统存储：写入结果里是原值，旁路的元数据文件（System.Text.Json 写成 UTF-8）里存成 U+FFFD：写入 `a\uD800b`，读回 `a�b`。S3 的 `x-amz-meta-*` 头要编成字节，按 UTF-8 写头的客户端同样换成 U+FFFD（.NET 的 `SocketsHttpHandler` 缺省只收 ASCII 的请求头，见「影响」的待定）。ADR-0316 已让键、查询前缀、保存的文件名与上传标识拒收孤立的代理项。
- **ADR-0313「背景」的一处错误**：它说整读与写入时 SDK 都拿 `ETag` 当 MD5 核对，ADR-0317 实测 SDK 4.0 写入不核对。

`BlobMetadata.LastModified`（`Stable` 的 `required DateTimeOffset`）在 S3 的写入结果里是本机时钟，仓库所有者定为维持，只写明。

## 备选

### 缺长度

1. **整读与 `Head` 的 `Content-Length` 缺失或为负即不合规**：采纳。照 Amazon S3 API Reference，`GetObject` 与 `HeadObject` 的应答带 `Content-Length`，它就是对象的长度；与缺 `ETag`、修改时间同一处置（ADR-0313），检查次序排在它们之后，固定原因 `GetObject returned no usable Content-Length` / `HeadObject returned no usable Content-Length`。
2. **长度取哪个值**：取 SDK 解组时读到的原值（`HeadersCollection.ContentLength`，缺失为 -1），不取 HTTP 客户端解析出的值（缺失与为负都是 0，分不出「0 字节的对象」）。采纳。
3. **范围读取（206）也要求 `Content-Length`**：否决。元数据的长度取 `Content-Range` 的总长（解析不了本来就是不合规的应答），`Content-Length` 只是这一段的长度，用不到它（同 ADR-0313 备选 23「判定放在用到它的地方」）。
4. **范围起点越界时为取总长而发的 `Head`**：要求 `Content-Length`。它只用长度，缺了以前以 0 写进 `OBJECTSTORAGE_VALIDATION_001` 的参数；现在返回 `OBJECTSTORAGE_UNAVAILABLE_001`。只判存在与否的 `Head` 仍不看长度。
5. **列举的对象缺 `<Size>` 或为负**：整页失败，同缺 `ETag`、修改时间（ADR-0313 备选 12），原因 `ListObjectsV2 returned an object without a usable Size`；跳过的对象缺什么照旧不影响这一页。列出分片的长度缺失照旧按 0（它只用于说明，ADR-0308），不在本条。

### SDK 解析不了的应答

6. **只接 `FormatException`（`UriFormatException` 除外）与 `OverflowException`**：采纳（拍板：只接这些解组异常，不吞别的）。`UriFormatException` 是 `FormatException` 的子类，来自端点而不是应答，除外；`ArgumentException`、`InvalidOperationException` 等照旧抛出。请求一侧不会因 Provider 的输入抛这两类：内容类型先过 `S3ContentTypeHeader`（ADR-0295），元数据名与值、键、桶名各有文法。
7. **哪几步**：读取（整读与范围读取）、`Head`（含只判存在的与起点越界时取总长的）、写入、批量删除、列举、发起分片上传、上传分片、列出分片与完成分片上传，各自返回 `OBJECTSTORAGE_UNAVAILABLE_001`，原因 `<请求名> returned a header or element the SDK could not parse`。放弃分片上传与建桶的成功应答没有按类型读的值，不加（加了是测不到的死代码）。写入、完成不重发（对象可能已经写进去或拼成，同 ADR-0313）；批量删除的 `DeleteObjects` 解析不了时这一批要删的项各报一个错误（同 ADR-0313 备选 8）；只判存在的 `Head` 解析不了时 SDK 没有交出应答，存在与否无从判定，那一项失败。
8. **把这两类并进 `IsStoreFailure`、原因写异常类型**：否决。`Unavailable(Exception)` 把完整异常记进日志，而 `FormatException` 的消息带着写错的值（`The input string 'abc' was not in a correct format.`）；不合规的应答一向只记请求名、桶名与固定原因（ADR-0302、ADR-0313）。
9. **写坏的 XML（SDK 抛 `XmlException`）**：不在拍板的范围，照旧抛出，见「影响」的待定。
10. **条件写入探测**：不改。探测没有归类的异常已由 `S3ConditionalWriteGate` 按尚未确认记下并后台重试（「探测没有归类的异常」一支），解析不了的应答落在这里。

### 整读的 `ETag` 识别不靠调用栈

11. **认 `ArgumentOutOfRangeException { ParamName: "hex" }`，`FormatException` 归入上一节**：采纳。ADR-0317 备选 2 否决只认参数名，理由是含十六进制数字之外字符的 `ETag` 抛的 `FormatException` 没有参数名、只修一半；本 ADR 把解组的 `FormatException` 也定为不合规的应答，两种来源落在同一个码上，不必再分。参数名是 SDK 源码里的字面量，不依赖栈追踪。`IsUndecodableETag` 只认这一种，`reason` 照旧 `GetObject returned an ETag that is not hexadecimal`。
12. **整读的 `FormatException` 的原因**：分不出来自 `ETag` 还是来自读头，原因同时点名两者：`GetObject returned an ETag that is not hexadecimal or a header the SDK could not parse`；`OverflowException` 只来自读头，用通用的原因。
13. **按异常消息区分**：否决。消息是运行时的资源文本，裁剪掉资源（`UseSystemResourceKeys`）之后换成资源键，也不是契约。
14. **按 `TargetSite` / `StackFrame.GetMethod()` 区分**：否决，同 ADR-0317 备选 5（反射，AOT 下同样拿不到）。
15. **整读之前先 `Head` 看 `ETag`**：否决。多一个请求，并发覆盖时两次应答可能不是同一版。

### 整读的内容对不上 `ETag`

16. **包一层流、读时把 SDK 的 `AmazonClientException` 换成对象存储的异常**：采纳（拍板）。`S3ObjectStream` 的 `Read`、`ReadAsync`（两个重载）与释放时接住 `AmazonClientException`，换成由 `S3BlobStore` 给的异常抛出；`CopyToAsync` 不再转发给内层，走基类经 `ReadAsync` 复制，只换读时的异常，目标流写入时的异常不受影响。读响应流时 SDK 只会因内容核对抛这一类（MD5 与应答里的校验和头），网络中断等是 `IOException`，照旧原样抛出。范围读取的流同样包：SDK 不核对范围读取的内容，实际遇不到，换法一致。
17. **换成什么异常（先找再定）**：仓库里对象存储没有自己的异常类型；把 `Error` 带进异常的现有做法是 `FrameworkException`（错误码 + `ToError()`），远程缓存遇到不合规的应答抛的就是携带 `CACHING_UNAVAILABLE_001` 的 `FrameworkException`（`RemoteCacheStore`），对象存储的命名实例建不出时也抛携带对象存储错误码的 `FrameworkException`（ADR-0093）。采纳 `FrameworkException`，`Code` 为 `OBJECTSTORAGE_UNAVAILABLE_001`，消息是固定的英文 `The content the S3 service returned does not match the ETag or checksum it answered with; discard the bytes already read.`，不带桶名、键与应答里的值（这个异常会交到调用方手里），内层是 SDK 的异常。同时记一条 Warning（共用 `The S3 service answered {Operation} for bucket '{Bucket}' without the content the blob store needs: {Reason}.`，原因 `GetObject returned content that does not match its ETag or checksum`）。否决的有：`IOException`（流的读错一般是它，但它带不了错误码，调用方要另找原因）；新建对象存储的异常类型（多一个公开类型，`FrameworkException` 已经够用）。
18. **释放时的核对**：读够长度、没读到末尾就释放的，`S3ObjectStream` 的释放同样换成 `FrameworkException` 抛出（`base.Dispose` 照常执行）。否决吞掉：调用方已经拿到了全部字节，吞掉就没有任何地方告诉它内容不对。`S3BlobStore` 自己在判了应答不可用之后释放没交出去的响应时，吞掉这次核对的 `AmazonClientException`：内容不交出去，核对的结论没有用处，不能盖过已经定下的结果。

### 列出分片里重复的编号

19. **同一编号出现两次即不合规**：采纳（拍板）。同一页里或跨页都算，原因 `ListParts returned the same PartNumber twice`；检查排在编号、`ETag`、长度之后（坏的那一片先报它自己的问题）。已列出的编号放进集合：编号都在 1–10000 之内且各不相同，集合与列表因此至多 10000 项，ADR-0313 的「累计超过 10000 片」再也到不了，删掉（`TooManyPartsReason`）。
20. **交出不比请求起点大、却没重复的编号**：不在拍板的范围，见「影响」的待定。

### 探测里上传分片的应答缺 `ETag`

21. **按尚未确认处理、不发完成、尽力放弃这个上传**：采纳（拍板：与发起缺上传标识一样按尚未确认处理）。判定同 `S3BlobStore` 的上传分片（`IsUsableETag(Unquote(…))`，由 `private` 改 `internal`），原因 `UploadPart of '.xihan/probe/conditional-write' returned no usable ETag`（常量 `PartETagMissingReason`）。这次有上传标识，放弃得了：与探测中途出错时同一个尽力放弃（抽成 `AbortQuietlyAsync`），放弃失败留给生命周期规则，不掩盖这个结论。
22. **像缺上传标识那样单独退避、计次数上限**：否决。那条退避是因为放弃不了的上传每次重试都留下一个（ADR-0317）；这里放弃得了，不留东西，照连不上的节奏（1 秒起加倍到 `HealthProbeIntervalSeconds`）重试，不计入缺上传标识的次数（发起的应答带着可用的上传标识，回调照旧报告「可用」）。

### 元数据值里的孤立代理项

23. **与键一样拒收**：采纳（拍板）。判定用 ADR-0316 的 `BlobKey.HasLoneSurrogate`（同一程序集，不重写），给 `BlobPutOptions.Metadata` 赋值时抛 `ArgumentException`（`Metadata '<名>' contains lone surrogates.`），同值里有控制字符。成对的代理项照常合法。不新增消息键：这是构造时的编程错误，消息是英文、不本地化（同其余元数据的核对）。
24. **向量**：`blob-metadata.json` 给值补上四种孤立的代理项（单独的高代理项、单独的低代理项、颠倒的一对、末尾的高代理项）、高代理项之后又是高代理项、只有一个低代理项、与合法的一项同在，以及成对的代理项（转义写出与按码元写出各一条）。JSON 字符串写不出孤立的代理项：照 ADR-0316 的 `utf16` 写法，在用例的 `utf16` 里按名列出码元，整组是 `metadata` 与 `utf16` 组出的各项合在一起，有孤立代理项的一组不标 `utf8Bytes`。Go 一致性模块的 `BlobMetadataCase` 加 `UTF16` 与 `Values()`，`rules.IsBlobMetadata` 先整串核对值是合法的 UTF-8；.NET 回放组出同一组值（`SpecVectors.FromCodeUnits`）。
25. **一致性套件**：`BlobStoreConformance` 用例 7 补「值里有孤立代理项的元数据在构造时拒绝」，文件系统与 S3 两边都跑。成对代理项的写入读回不进套件：.NET 的 S3 Provider 写不出任何非 ASCII 的元数据值（见「影响」的待定），进了套件 S3 一边必然失败；文件系统存储的写入读回由它自己的用例核对。

### 写入结果的修改时间

26. **维持本机时钟，写明「要服务端时间就 `Head`」**：采纳（拍板）。改成可空是 `Stable` 契约的破坏（ADR-0313 备选 20）。RFC-0012「契约」、`BlobMetadata.LastModified` 的 XML 文档、`S3BlobStore` 的说明与 S3 包 README 都写明。

## 决策

### 规范

1. RFC-0012「标识」（MAJOR，`v1.0.0` 之前允许：以前合法的值变得不合法）：自定义元数据的值不能含孤立的代理项，理由与处置写进「孤立的代理项」一条与元数据一条。
2. RFC-0012「契约」（PATCH，写明）：写入结果的修改时间要服务记下的时刻就再 `Head`。
3. RFC-0012「S3 Provider」（MINOR，写明以前不作规定的行为）：列举的对象缺长度；「读取、`Head` 与写入的应答里的 `ETag`、修改时间与长度」一条补上长度、SDK 解析不了的应答、整读的内容对不上 `ETag`，整读 `ETag` 不是十六进制的识别不靠调用栈；映射一句的括注补上这几处。
4. RFC-0012「S3 的条件写入探测」（MINOR）：上传分片的应答缺 `ETag` 同其余服务端错误，不发完成、尽力放弃、不另退避。
5. RFC-0012「范围读取、分片上传与预签名」（MAJOR，`v1.0.0` 之前允许：改的是 ADR-0313 写明的「累计超过 10000 片」）：同一编号出现两次即不合规。
6. RFC-0012「一致性」与向量 `blob-metadata.json`（MAJOR，同第 1 条）：补元数据值的孤立与成对代理项；`conventions/error-codes.md` 的 `OBJECTSTORAGE_UNAVAILABLE_001` 补这几处（PATCH，码不变）。

### 实现

7. `ObjectStorage.Abstractions`：`BlobPutOptions.Metadata` 拒收含孤立代理项的值；`BlobMetadata.LastModified` 补 XML 文档。
8. `ObjectStorage.S3` 的 `S3BlobStore`：
   - `DescribeObject` 加长度的判定，整读与 `Head` 传 `Headers.ContentLength`；`ObjectAnswer` 加 `ContentLengthMissingReason`；起点越界时的 `Head` 同判。
   - `ListAsync` 判 `<Size>`；`ListPartsAsync` 以编号集合判重复，删掉 `TooManyPartsReason`。
   - 新增内部的 `IsUnparsableAnswer` 与各步的 `catch … when (IsUnparsableAnswer(exception))`；`IsUndecodableETag` 改为只认参数名 `hex`，删掉 `_etagDecodingFrame`。
   - 整读与范围读取交出 `S3ObjectStream(response, translate)`，`ContentRejected` 记 Warning 并交出 `FrameworkException`；`DisposeUndelivered` 释放没交出去的响应时吞掉 SDK 的核对异常。
   - `Unquote` 与 `IsUsableETag` 由 `private` 改 `internal`，供探测使用。
9. `S3ObjectStream`：构造加转换；读与释放时换掉 `AmazonClientException`；不再转发 `CopyToAsync`。
10. `S3ConditionalWriteProbe`：新增 `PartETagMissingReason` 与 `AbortQuietlyAsync`，上传分片的应答缺 `ETag` 时放弃上传、返回 `OBJECTSTORAGE_UNAVAILABLE_001`。
11. `ObjectStorage.Conformance`：用例 7 补元数据值的孤立代理项。
12. S3 包 README 写明长度、解析不了的应答、内容对不上 `ETag` 时流抛出的异常与「要服务端时间就 `Head`」。

## 理由

- 规范与 SDK 写明了应答里有什么、什么格式：照写明的去判，缺了、写错了都是服务一侧的问题，调用方拿到与其余服务端错误同一个码，而不是一个看上去合法的 0、一个 SDK 的解析异常，或一个像是自己给错了清单的校验错误。
- 只接住能确认来自应答的那几类异常：解组的两类、`hex` 参数名的那一个、读响应流时的内容核对；编程错误、端点错误照旧抛出。判定都不靠调用栈与消息文本，AOT 与裁剪掉资源的部署里一样成立。
- 流只能以异常报告读取中的失败：用仓库已有的带错误码的异常，调用方按码处理，不必认识 SDK 的类型。
- 元数据的值与键同样要编成 UTF-8 才进得了存储：存进去读回来变了的值不该收下，拒收的规则与键相同。

## 影响

- **公开 API**：签名不变（`PublicAPI.Unshipped.txt` 无改动）；`BlobPutOptions.Metadata` 的前置条件收紧（含孤立代理项的值以前收下、现在抛出）。配置键、错误码、消息键不变。
- **行为**（除元数据外都是合规的服务不会遇到的应答）：
  - S3 的读取与 `Head` 缺 `Content-Length` 或为负、列举的对象缺 `<Size>` 或为负、任一步的应答 SDK 解析不了、列出分片里同一编号出现两次：返回 `OBJECTSTORAGE_UNAVAILABLE_001`。以前分别是长度 0、原样抛出 `FormatException` / `OverflowException`、交出重复的分片。
  - 整读的内容对不上 `ETag`（或应答里的校验和）：读内容的流（与读够长度之后的释放）抛携带 `OBJECTSTORAGE_UNAVAILABLE_001` 的 `FrameworkException`，以前抛 SDK 的 `AmazonClientException`。
  - 条件写入探测里上传分片的应答缺 `ETag`：尚未确认，后台按连不上的节奏重试，不发完成，放弃这个上传。
  - 元数据的值有孤立的代理项：构造 `BlobPutOptions` 时抛 `ArgumentException`（升级须知：以前文件系统存储收下、读回 U+FFFD）。
- **规范**（规范仓库已改，指针待更新）：见「决策」第 1–6 条；向量 `blob-metadata.json` 改内容、不改文件名，`.NET` 与 Go 的回放都已跟上，SDK 不认领 `objectstorage` 档，不受影响。
- **测试**（都不需要 S3 服务）：
  - `RecordingHttpListener` 加 `AnsweringVerbatim`（原样写出响应头、不另加 `Content-Length`、写完即关闭连接）与 `AnsweringInTurn`（按请求的次序回不同的应答）。
  - `S3ObjectResponseTests` 补：整读与 `Head` 缺 `Content-Length` 或为负；起点越界时取总长的 `Head` 缺 `Content-Length`（与带着它的对照）。`FakeS3Client` 的 `Head` 应答缺省带 `Content-Length: 0`。
  - 新增 `S3UnparsableAnswerTests`：`Head`、范围读取、整读各 6 种写错的头（修改时间、分片数两种、布尔值、长度两种），写入、列举、发起、上传分片、列出分片、完成、批量删除与只判存在的 `Head` 的解析不了的应答；分类函数只认两类、不认 `UriFormatException`、`ArgumentException`、`XmlException` 等。
  - `S3WholeReadETagTests`：解组的 `FormatException` 改为返回错误；SDK 的行为钉子改为钉参数名与异常类型；`IsUndecodableETag` 对没抛出过、没有调用栈的异常照样成立；内容对不上 `ETag` 时三种读法（`ReadAsync`、`CopyToAsync`、同步 `Read`）与读够长度之后的释放都抛 `FrameworkException`，对照的 MD5 相符时照常读完。
  - `S3MultipartPartResponseTests`：「每页 1000 片而编号重复到第 11 页才失败」改为第 2 页即失败；补同一页里重复、线上重复与 10000 片各一次照常列全。
  - `S3ConditionalWriteTests` 补：上传分片缺 `ETag`（缺失、空串、只有引号、空白）时不发完成、放弃上传、回调报告上传标识可用；放弃失败不掩盖结论。`S3ConditionalWriteRetryTests` 补：照常启动、健康项降级、第一次重试在 1 秒后、恢复后确认。
  - `BlobPutOptionsTests`、`FileSystemBlobStoreTests`、`BlobMetadataVectorTests` 补孤立与成对的代理项；一致性套件用例 7 补一条。
  - 改实现之前（只补上让用例编译的两个桩）这组用例里有 49 条失败。
  - 一致性套件与对真实服务的用例只在设了 `XIHAN_TEST_S3` 时执行，本机跳过；CI 加上 RustFS 服务之后由 CI 跑。
- **文档**：包 README（S3）已改；文档站的 `object-storage/advanced`、`packages/objectstorage-s3`、`appendix/spec` 与更新日志待改。
- **待定**：
  - .NET 的 S3 Provider 写不出非 ASCII 的元数据值：`SocketsHttpHandler` 缺省只收 ASCII 的请求头，`x-amz-meta-*` 里有中文、成对的代理项等时写入以 `HttpRequestException` 失败，按存储不可用返回 `OBJECTSTORAGE_UNAVAILABLE_001`（实测）。规范与向量把这样的值算作合法（`2026 年度报告`），文件系统存储照收。要不要在 S3 上编码（SDK 的 `AWSConfigsS3.EnableUnicodeEncodingForObjectMetadata` 是进程级的全局开关，且它逐个 UTF-16 码元做百分号编码，会把成对的代理项拆开），还是在规范里写明 S3 只收 ASCII 的值，留给仓库所有者定。
  - 写坏的 XML：`ListObjectsV2`、`ListParts`、`DeleteObjects` 等的响应体不是良构的 XML 时，SDK 的异步解组原样抛 `XmlException`（实测），Provider 不接，原样抛给调用方。
  - 批量删除的错误项：SDK 的 `AmazonS3ResponseHandler` 在 `DeleteObjects` 的应答有错误项时抛 `DeleteObjectsException`（实测，静默模式也是），Provider 按存储故障把这一批全部报错、`reason` 是 `Amazon.S3.DeleteObjectsException`；ADR-0313 按 `DeleteErrors` 逐项报告的分支只在内存替身上走得到，真实的 SDK 走不到。
  - 列出分片的应答交出不比请求起点大、却没重复的编号，仍未判。
  - 读到的字节已经交给调用方之后才发现内容对不上：调用方要自己丢弃已经读到的部分（规范已写明），Provider 撤不回。
