# ADR-0189 gRPC 解码的嵌套上限

## 状态

已采纳（`spec/protocol/grpc.md` 错误映射一条修订）。

## 日期

2026-11-12

## 背景

5.0 安全审查 S-28（`plans/5.0-安全审查.md`），低危。

- `ProtoDecoder.Decode` 遇到嵌套消息就递归，自己不计深度。
- 操作的请求类型含自引用的消息（树、链表、评论回复）时，调用方可以构造任意深的嵌套。
- 写到第 1000 层时 `Utf8JsonWriter` 抛出 `InvalidOperationException`，不是 `ProtoException`：调用方得到 `Internal`（500 类），宿主记一条非预期异常。匿名调用方能随意制造这类错误日志。
- HTTP 上同样的请求在 JSON 解析时就被深度上限 64 拒绝，两个协议的结果不一致。

复现：`ProtoNestingTests`。修正前，2000 层的嵌套以 `InvalidOperationException` 失败。

## 决策

- `ProtoDecoder.MaxDepth = 64`：根消息算第 1 层，与 JSON 请求体的深度上限相同。
- 解码每进入一层嵌套消息先判定，超过即抛出 `ProtoException`（消息带上限与消息名），映射为 `InvalidArgument` + `PROTOCOLS_VALIDATION_005`。判定在解析这一层之前，不为超深的部分做任何工作。
- 打包的标量与映射条目沿用所在消息的层数，映射的值是消息时在下一层。

## 影响

- 行为：超过 64 层的嵌套请求以 `InvalidArgument` 拒绝。以前 64 到 999 层之间的可以解码，这样的请求在 HTTP 上本来就进不来。
- 公开 API：`ProtoDecoder.MaxDepth`。`Protocols.Grpc` 是 `Preview`。
