# ADR-0274 缓存键长度按 UTF-8 字节计

## 状态

已采纳（`CacheKey` 与键前缀的上限由 512 个 UTF-16 码元改为 UTF-8 编码后 512 字节，常量 `CacheKey.MaxLength` 改名 `MaxBytes`；`GenerationCache<T>` 的区名与直接写出的段按字节留余量，`MaxRegionLength` 改名 `MaxRegionBytes`；一致性套件加一个恰好 512 字节的多字节键用例；RFC-0006 的键文法已在规范仓库改好，「代数缓存区」一句与远程 Provider 的文案待补，见「影响」）。

## 日期

2026-11-24

## 背景

- RFC-0006 的键文法原文是「非空、无空白与控制字符、不超过 512 字符、区分大小写」，前缀「与键同文法」，`provider/caching-distributed.md` 是同一句。「字符」没有说单位，各实现按自己语言里字符串的长度去数：
  - .NET：`CacheKey.IsValid` 判 `value.Length > MaxLength`，数的是 UTF-16 码元。
  - Go SDK（`framework-sdk-go` 的 `caching.IsKey`）：判 `len(key) > MaxKeyLength`，Go 字符串的长度是 UTF-8 字节数。
- 同一个键两边结论不同。200 个汉字的键是 200 个码元、600 字节：.NET 的 `CacheKey` 接受，交给 Go 写的远程 Provider 时插件以 `caching.remote.key_invalid` 拒绝；宿主认为合法的键在后端写不进去。
- 后端的限制都按字节：键在 Redis、在远程插件的线协议里、在别的 Provider 可能用的数据库列里都是字节串。512 个码元最长是 1536 字节，按码元数的上限对后端没有约束力。
- 规范已经定为「UTF-8 编码后不超过 512 字节」（规范仓库，随 submodule 指针进来）。本 ADR 把 .NET 改到与它一致。
- .NET 里依赖「键长度」的地方（全仓搜 `CacheKey.MaxLength`、`IsValid`、`IsValidPrefix` 与 `new CacheKey(` 的拼接）：
  - 直接判长度的：`CacheKey.IsValid`；`GenerationCache<T>` 的区名上限 `MaxRegionLength`（128）与段的直接写出上限（128），两者是为「区名 + 后缀 + 两个编码段不超过键的上限」留的余量，按码元算。
  - 经 `CacheKey` 间接受限的：键前缀（`IsValidPrefix`、`CacheKeyQuery.Validate` / `ValidateRemovalPrefix`、`CacheChange.ForPrefix`、内存表的按前缀删除）、锁条目的键（`lock:` 加资源名）、幂等的作用域键（`idem:<租户>:<主体>:<键>`）、`IDistributedCache` 适配、Redis 的 `SCAN` 结果与变更通知里的键。
  - 不受这个上限约束的：Redis 的 `KeyPrefix` 在 `CacheKey` 之外拼接，Redis 自己的键上限远大于此；远程 Provider 的宿主侧不另行校验，由插件按规范校验。
- `GenerationCache<T>` 的余量按码元算在字节口径下不成立：128 个汉字的范围与条目各 384 字节，直接写进键是 128 + 8 + 388 × 2 = 912 字节。

## 备选

1. **维持码元，让别的语言改成数 UTF-16 码元**：否决。码元是 UTF-16 才有的单位，Go、Rust、Python 要先转码才数得出；后端的限制是字节，按码元数的上限保证不了键写得进去。
2. **按 Unicode 码位数**：否决。同样每种语言都要解码才数得出，一个码位占 1 到 4 个字节，仍然对不上后端的限制。
3. **按 UTF-8 编码后的字节数**：采纳。键在线上与后端里就是这串字节，每种语言都能直接得到它的长度。
4. **常量名留作 `MaxLength`**：否决。值没变、含义变了：应用里 `text.Length <= CacheKey.MaxLength` 这样的预检会照常编译、结论却是错的。改名让这些地方编译失败，逼着看一眼。
5. **改名 `MaxUtf8Bytes` 或 `MaxByteCount`**：否决。仓库里字节上限一律叫 `…Bytes`（`MaxBlobBytes`、`MaxTotalBytes`）；编码写在文档注释里，缓存键没有第二种编码。采纳 `MaxBytes`，`GenerationCache<T>.MaxRegionLength` 同理改 `MaxRegionBytes`。
6. **在 `CacheKey` 上公开「数字节」的方法**：否决。`Encoding.UTF8.GetByteCount` 就是它，多一个公开成员只是换个名字。
7. **不成对的代理项（不是合法 Unicode 的字符串）一并判为不合法**：不在本 ADR。它们编不成 UTF-8，实际编码时被换成 U+FFFD，两个只差一个孤立代理项的键会落到同一个后端键上；这是原先就有的问题，规范也没有写。这次只定长度：这类字符按替换后的 3 个字节计，与实际编码的结果一致。是否拒绝另行决定。
8. **`GenerationCache<T>` 段的长度前缀（`<长度>.<文本>`）也改成字节数**：不在本 ADR。前缀只用来让 `a:b` + `c` 与 `a` + `b:c` 拼出不同的键，哪种单位都做得到；改了会让所有含非 ASCII 字符的段换键。规范里这个 `<长度>` 同样没有写单位，见「影响」。
9. **每次构造键都数一遍字节**：否决作为唯一路径。键的构造在每次缓存读写的路径上。码元数乘 3 不超过上限的（170 个码元以内）一定不超，不数；码元数已经超过上限的一定超，也不数；只有中间这一段才调 `GetByteCount`（它本身是向量化的）。

## 决策

1. `CacheKey` 的文法：非空、不含空白与控制字符、UTF-8 编码后不超过 512 字节、区分大小写。键前缀同文法，可以为空（空前缀表示全部，不变）。
2. `CacheKey.MaxLength` 改名 `MaxBytes`，值仍是 512。`Validate` 与构造函数的异常消息写「at most 512 bytes long in UTF-8」。
3. `GenerationCache<T>`：
   - `MaxRegionLength` 改名 `MaxRegionBytes`：区名 UTF-8 编码后不超过 128 字节，超过在构造时抛出 `ArgumentException`。
   - 范围与条目直接写进键的条件由「不超过 128 个码元」改为「UTF-8 编码后不超过 128 字节」，超过的与含空白、控制字符的一样写成 `#<SHA-256 十六进制>`。
   - 长度前缀仍是 `string.Length`（备选 8）。
   - 余量：区名 128，分隔与后缀 8（`:entry:` 与两段之间的 `:`），每段至多 132（长度前缀至多 3 位、点号、文本 128），最长的条目键 400 字节。
4. 其余经 `CacheKey` 受限的地方不改代码，随 `IsValid` 一起按字节：键前缀的校验、锁条目的键、幂等的作用域键、`IDistributedCache` 适配、Redis 的 `SCAN` 结果与变更通知里的键。
5. 消息 `caching.inspector.prefix_invalid` 的 10 个区域文案由「最长 {max} 个字符」改为「UTF-8 编码后最长 {max} 字节」；参数 `max` 仍是 512。
6. 一致性套件 `CacheStoreConformance` 新增用例 `Keys_AtMaxUtf8Bytes_RoundTrip`：两个含 3 字节字符、恰好 512 字节、只差最后一个字节的键是两个条目，读、批量读、不存在才写、比较删都认得它们；实现了 `ICacheStoreInspector` 的存储按含多字节字符的前缀列出并删除。夹具用加前缀的包装隔离用例时覆写新增的 `KeyPrefixBytes`，用例据此让出字节，使到达后端的键恰好 512 字节。

## 理由

- 「键写得进后端」是这个上限唯一的用处，后端按字节计。
- 与 Go SDK 已有的行为一致，规范的一句话在两种实现里不再有两个结论。
- 上限的值不动：纯 ASCII 的键（框架自己的键、绝大多数应用的键）没有任何变化。

## 影响

- **行为变化：含非 ASCII 字符的长键比原来更早被拒绝。** 纯 ASCII 的键不变。全是 3 字节字符（汉字）的键原先最多 512 个字，现在 170 个；全是 4 字节字符（表情，占 2 个码元）的原先 256 个，现在 128 个。被拒绝的方式不变：
  - `new CacheKey(text)`、显式转换与 `Validate` 抛出 `ArgumentException`；`IsValid` / `IsValidPrefix` 返回 `false`。
  - 幂等：作用域键超过上限返回 `CACHING_VALIDATION_001`（HTTP 400）。匿名、无租户时前缀 `idem:-:-:` 占 9 字节，幂等键最多 503 字节。
  - 键管理：前缀超过上限时 `ListKeysAsync` 与 `RemoveByPrefixAsync` 返回 `CACHING_VALIDATION_004`。
  - 锁：资源名本身是 `CacheKey`，但锁条目的键是 `lock:` 加资源名，资源名超过 507 字节时 `TryAcquireAsync` 抛出 `ArgumentException`（原先是超过 507 个码元，同一处抛出）。
  - `IDistributedCache` 适配：抛出 `ArgumentException`。
- **`GenerationCache<T>` 的键**：范围或条目含非 ASCII 字符、码元数不超过 128 而 UTF-8 超过 128 字节的，原先直接写进键，现在写成摘要，键变了。
  - 升级后这些位置各多查一次源。
  - 滚动升级期间新旧实例对这类范围拼出的代数键不同，一组实例的失效另一组看不到，最长持续一个条目存活时间。框架自己的范围（授予的主体标识、租户标识）通常是 ASCII，不受影响。
  - 原先拼出的键按码元不超过 400、按字节最长可以到 1168（区名、范围、条目都是 128 个汉字）；现在最长 400 字节。
- **后端里已有的超长键**（旧版本写入、UTF-8 超过 512 字节）：`CacheKey` 构造不出来，读不到也单删不了；`ListKeysAsync` 不列出它们（Redis 的 `SCAN` 结果经 `IsValid` 过滤），`RemoveByPrefixAsync` 仍能删掉（按后端的键删，不经 `CacheKey`），否则等它们过期。
- **源码迁移**：
  - `CacheKey.MaxLength` → `CacheKey.MaxBytes`；与它比较的 `text.Length` 换成 `Encoding.UTF8.GetByteCount(text)`。
  - `GenerationCache<T>.MaxRegionLength` → `MaxRegionBytes`，同上。
  - 自写的一致性夹具若给键加前缀，覆写 `CacheStoreConformance.KeyPrefixBytes`。
- **远程 Provider 的文案没有改**：`Caching.Remote` 的 `caching.remote.key_invalid`（10 个区域）仍写「不超过 512 个字符」。这份目录与插件自带的同名目录逐键核对模板，不一致时插件加载失败（`framework-sdk-go` 的缓存示例带着同一份文案），要两边同一批改。
- **规范**：
  - RFC-0006「存储契约」「键管理」与 `provider/caching-distributed.md` 的键文法已在规范仓库改好。
  - RFC-0006「代数缓存区」第 1 条「含空白、控制字符或超过 128 个字符的写成 `#<SHA-256 十六进制>`」待改为按字节；同一句里 `<长度>` 的单位、以及「幂等」里主体的 `<长度>.<主体 ID>` 的单位都没有写（.NET 是 UTF-16 码元数），待定。
  - 规范的新向量在工作区里还没有，更新 submodule 指针后回放。
- **文档站**（待补）：`docs/caching/basics.md` 与 `docs/packages/caching-abstractions.md` 里「不超过 512 个字符（`CacheKey.MaxLength`）」。
- **本机没有覆盖的**：Redis 上的 512 字节多字节键（`RedisCacheStoreConformanceTests` 要真实的 Redis，本机跳过，由 CI 跑）。内存实现与经 Go 插件的远程 Provider 本机跑过。
