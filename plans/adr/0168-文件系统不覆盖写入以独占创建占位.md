# ADR-0168 文件系统不覆盖写入以独占创建占位

## 状态

已采纳（RFC-0012「Provider」修订 `ObjectStorage.FileSystem` 一条；修正 ADR-0089「不覆盖写入并发原子」一节的理由）。

## 日期

2026-11-11

## 背景

CI（Linux 运行器）上一致性用例 `Put_WithoutOverwrite_IsAtomicUnderConcurrentWriters` 失败：8 个不覆盖的写入方同时写同一个新键，有两个成功（`[0, 7]`）。

- 这个用例从 11-05 就有，此前 CI 多次通过，在 Windows 上也一直通过。
- ADR-0089 让 `FileSystemBlobStore.CommitAsync` 以 `File.Move(temporary, dataPath, overwrite: false)` 原子占位，理由是 Unix 上 .NET 以硬链接 `link` 占位、目标存在即失败。
- 这个前提不成立。.NET 在 Unix 上的不替换移动先 `lstat` 目标，目标不存在就直接 `rename`，失败了才退回 `link` / `unlink`。`lstat` 与 `rename` 之间别的写入方可以抢先，后到的 `rename` 静默覆盖先到的。
- Windows 的 `MoveFileEx` 不带替换标志是一次原子操作，所以只在 Linux 上偶发。

## 决策

1. **不覆盖的提交先独占创建占位文件，再替换内容**：
   - 以 `FileMode.CreateNew` 在内容路径建一个空文件。它对应 `O_CREAT | O_EXCL`（Windows 上是 `CREATE_NEW`），在各平台的本地文件系统上都原子，目标已存在即失败，返回 `OBJECTSTORAGE_CONFLICT_001`，不写元数据、不计用量。
   - 占到位的写入方再以替换方式把临时内容文件改名到内容路径。读取方以元数据判断对象是否存在，元数据要等内容就位后才写，所以读取方要么看不到对象，要么看到完整内容。
   - 写入与分片上传的完成共用这段提交，一并修正。
2. **一致性用例跑多轮**：每轮 8 个写入方、一个新键，共 16 轮，让这类只在窄窗口里出现的覆盖在一次运行里就能暴露。
3. **RFC-0012 写明**：不覆盖写入不能用「先查目标再改名」的移动，并点名 .NET 在 Unix 上的 `File.Move(…, overwrite: false)` 就是这种实现。

## 影响

- 行为：Linux 与 macOS 上并发的不覆盖写入只有一个成功，以前偶发两个成功、后写的覆盖先写的。Windows 上行为不变。
- 进程在占位之后、替换之前退出，会留下空的内容文件、没有元数据。这与 ADR-0089 写明的残留相同：不覆盖写入返回 `OBJECTSTORAGE_CONFLICT_001`，覆盖写入照常修复它。
- 公开 API、错误码、配置键不变；`CommitAsync` 是内部方法。
