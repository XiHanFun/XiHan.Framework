# ADR-0286 AI、配置、调度、本地化与可观测的正文出入：写明或修正

## 状态

已采纳（规范 RFC-0022、RFC-0014、RFC-0013、RFC-0010、RFC-0023 的正文已写明，七个向量文件已补，Go 一致性模块的规则已改并回放通过；.NET 修正了 `FixedWindowChunkingStrategy`、`NacosDocumentParser`、`CronExpression` 与 `LinuxHostPlatform`，`Localization.Conformance` 新增一条用例，各向量的回放已更新）。

## 日期

2026-11-24

## 背景

ADR-0277 给十一个子系统档补向量时，口径是「向量只收正文已经写明的规则」，正文没有写而 .NET 有自己做法的地方逐条记在「影响 → 正文与 .NET 的出入」里，共 13 行。其中消息的 4 行由 ADR-0283 处理，对象存储的 2 行由 ADR-0282 处理，余下 7 行在这里了结。

口径已定：正文没写的，按 .NET 的现状写进正文并补向量；.NET 明显收得过宽、结果不确定或有缺陷的，修正 .NET，正文按修正后的写。逐行把 .NET 的实际行为读准（读源码，并用 Release 构建的真实实现跑）之后，各行的情况是：

1. **工具名超长时的前缀（RFC-0022「工具」）**。正文写「前 55 个字符 + `_` + 哈希」，`AIToolNameConvention.Shorten` 先去掉前缀结尾的 `_`。操作 ID 的文法保证换成下划线之后没有连着的两个 `_`，所以前缀结尾至多一个；去掉它，名字是 63 个字符，照正文的字面则出现 `__`。.NET 的做法合理。同一节里工具名本身的文法（`^[A-Za-z0-9_-]{1,64}$`）正文只说「不合法」而没有给出。
2. **固定窗口分块（RFC-0022「知识库」）**。正文写「空白块丢弃」，`FixedWindowChunkingStrategy` 对每个窗口还 `Trim()`。去空白在切分之后、只裁这一块的两端，窗口的位置仍按原文算；有重叠时相邻的块去掉空白之后可能相同，各算一块。这些是确定的，照写。
   - **缺陷**：窗口按 UTF-16 码元计。窗口的边界落在代理对中间时，前一块以半个字符结尾、后一块以另半个开头（`"a😀b😀c"` 按 2 个字符切得到 `a` 加高位代理项、低位代理项加 `b`……），这样的块送去嵌入或写进向量存储时是坏的文本。正文的「按字符」别的语言也无从照做：Go、Rust、Python 数的是码位。
3. **提示词模板（RFC-0022「聊天」）**。`AIPromptTemplate.Render` 从左到右扫描一遍，逐个边角核对过：
   - 缺少参数是 `AI_VALIDATION_001`，消息键 `ai.prompt.argument_missing`，报的是模板里第一个找不到的占位符名，不输出半截文本。
   - 占位符的名字是 `{` 到其后第一个 `}` 之间的文本去掉两侧空白，不作别的限制：可以为空（`{}` 取名字为空串的参数）、可以含空格与 `{`，`{amount:N2}` 的名字就是 `amount:N2`（没有格式说明符）。
   - 没有闭合的 `{` 连同其后直到结尾的文本原样写出，其中的 `{{` 也不再转义。这与 RFC-0010「模板」对消息模板的处理相同（「没有闭合的 `{` 及其后的全部文本原样输出」）。
   - 单独的 `}` 原样写出；多给的参数不用；同一个占位符出现几次取几次；值为 `null` 写成空串。
   - 都是确定的、与语言无关的。唯一依赖语言的是字符串与空值之外的参数怎样写成文本（.NET 是 `Convert.ToString(value, InvariantCulture)`，布尔是 `True`）。
4. **Nacos 的文档格式（RFC-0014「Nacos Provider」）**。把 `NacosDocumentParser` 与 .NET 自带的 `Microsoft.Extensions.Configuration.Json`（10.0.14）逐项对过：
   - 相同的：顶层必须是对象；照收注释与尾逗号；嵌套最多 64 层；字符串取值、数字取原文；布尔写成 `True` / `False`；`null` 保留为空值；成员名里的 `:` 不转义。
   - **不同、且是缺陷的**：重复的键。配置键不区分大小写，`NacosDocumentParser` 用不区分大小写的字典、后写的覆盖先写的，文档里一个键写两次（哪怕只差大小写）悄悄取最后一个；自带的提供程序抛出 `FormatException`（`A duplicate key 'a' was found.`），框架自己的 `ConfigurationDocument` 对只差大小写的键也是抛出（ADR-0161）。properties 同样悄悄取最后一个。
   - **不同、不改的**：空对象与空数组。自带的提供程序给这个键一个空值（`{}`）或空串（`[]`，.NET 10 的行为，以前的版本又不同），`NacosDocumentParser` 不产生键。前者随运行时版本变，不适合写进规范；照 `NacosDocumentParser` 的写。
   - **另外三处缺陷**，读代码时发现：
     - JSON 里落单的代理项转义（`{"a":"\ud800"}`）要到取文本时才被发现，抛的是 `InvalidOperationException` 而不是 `JsonException`，没有被转成 `FormatException`；它从 `NacosConfigurationClient.FetchAsync` 漏出去，配置适配器把它算成 `CONFIGURATION_UNAVAILABLE_001`（远端不可达），其实是文档不合法。
     - JSON 顶层的成员名是空串（`{"":"x"}`）时展平出空的键，`ConfigurationDocument` 的构造函数拒收空键、抛出 `ArgumentException`，同样从 `FetchAsync` 漏出去。
     - properties 的键为空时，异常消息带着整行（`The properties line '=hunter2' has an empty key.`），这一行分隔符之后是配置的值；消息会进错误详情的 `reason` 与 `OnError`。
   - properties 的其余做法（`:` 也是分隔符、行与键值两侧去空白、不认转义与续行、按 `\n` 分行）是确定的，照写。
5. **cron（RFC-0013）**。`CronExpression` 的写法逐条核对过：名字不区分 ASCII 字母的大小写、数字可带前导 0、单个值带步长取到段的最大值、星期的步长在 0–7 里数、年份 1970–2099（写 `*` 也只到 2099）、`L-n` 的 n 是 0–30、整段正好是 `*` 或 `?` 才算不限定。这些照写。另有三处要改：
   - **过宽**：分段用的是 `Split([' ', '\t'], RemoveEmptyEntries | TrimEntries)`。`TrimEntries` 裁掉的是任何 Unicode 空白，于是 `"0 0 * * *\n"`、`"0   0 * * *"`（空格之间夹着一个不换行空格，这一「段」被裁成空再丢掉）都能过，而 `"0\n0 * * *"` 不能过。照收的范围说不清，换一种实现就读不出同一个表达式。
   - **缺陷**：步长的上限是 `int.MaxValue`（`int.TryParse`）。`1/2147483647` 这样的写法在展开时起点加步长溢出成负数，再去写匹配表，`TryParse` 抛出 `IndexOutOfRangeException`——它的契约是不抛出。
   - **不确定**：搜索上限。正文写「搜索上限 5 年」，代码里是 1830 天（5 × 366），但只在按年、月、日跳之前核对游标：跳到的那一天越过上限也照样返回。起点 2026-01-01 的上限是 2031-01-05 00:00:01，而 2031-01-06、2031-01-31 的触发照样返回，2031-02-01 的才不返回——实际多收最多一个月，边界取决于跳的步子，写不成规则。
6. **取文案的次序（RFC-0010「解析」）**。正文写「同一键先注册的目录优先」，`InMemoryMessageLocalizer` 与 `DatabaseMessageLocalizer` 都是外层走回退链、内层走目录：先按区域、再按目录。后注册的目录有请求区域的模板时，优先于先注册的目录里回退区域的模板。这是对的——调用方的语言有模板就不该退到别的语言——只是正文读得出两种次序。
7. **平台读取路径（RFC-0023）**。正文只有一张表，给了读哪个文件的哪一项。`LinuxHostPlatform` 的取法逐项核对过，绝大多数是确定的；两处要改：
   - **过宽且会抛出**：`/proc/uptime` 用 `double.TryParse(NumberStyles.Float)` 读。带符号与指数的写法照收，`-1` 读成负的时长；`NaN` 与装不下的值在 `TimeSpan.FromSeconds` 里抛出 `ArgumentException` / `OverflowException`，前者不在「读不到」的异常之列，破了「读取不抛出」。按二进制浮点读还有精度问题：`350735.47` 读成 350735.4699999 秒。内核写的总是两位小数，这些输入实际不会出现，但写成规则时不能把它们写进去。
   - **不确定**：最后一级缓存同一级有几项时取 `Directory.EnumerateDirectories` 次序里的第一项，次序随文件系统而变。实际的硬件每一级只有一项数据或统一缓存，同样是写规则时才暴露的问题。

## 备选

1. **工具名照正文的字面改 .NET（出现 `__`）**：否决。两个连着的下划线没有任何好处，名字还正好顶到上限。
2. **分块维持 UTF-16 码元，只保证不切开代理对**：否决。别的语言要先转成 UTF-16 才数得出码元，规则写出来是「按码元计、但边界落在代理对中间时……」，比「按码位计」复杂而没有好处。
3. **分块按字素簇（用户看到的一个字符）计**：否决。字素簇的划分随 Unicode 版本变，各语言的库给出的结果不同；切开一个组合序列得到的仍是合法文本，不是坏数据。
4. **分块按 UTF-8 字节计**（与缓存键、对象键的长度一致）：否决。那几处的上限是为了「写得进后端」，后端按字节算；块的大小对应的是嵌入模型的输入，按字节计会让同样大小的窗口在中文里只装三分之一的内容。
5. **提示词模板里没有闭合的 `{` 当成模板错误**（Python 的 `str.format`、.NET 的 `string.Format` 都这样）：否决。框架自己的消息模板（RFC-0010）对同一种写法是原样输出，两套模板在同一件事上给出相反的处理更难解释；单独的 `}` 也是原样输出，放过 `{` 与之一致。记在「待定」。
6. **给占位符的名字加文法（如消息模板的 `^[A-Za-z][A-Za-z0-9_]*$`），不合的当字面量或当错误**：否决。提示词里常有 JSON 片段，`{"answer": 1}` 现在会因为找不到名字是 `"answer": 1` 的参数而失败，逼着作者写成 `{{…}}`；改成字面量则漏写转义的模板悄悄通过，改成错误则多一类错误码与消息键，而现在的失败已经指出了问题所在。
7. **Nacos 的重复键只改 JSON，properties 维持取最后一个**（Java 的 `Properties` 就是取最后一个）：否决。两种格式展平出的是同一种配置键，同一个键写两次在一种格式里不合法、在另一种里悄悄生效，说不通；.NET 自带的 INI 提供程序对重复键也是抛出。
8. **Nacos 的空对象与空数组照自带的提供程序给一个空值或空串**：否决，见背景第 4 条：那是随运行时版本变的行为。
9. **Nacos 的 JSON 不再收注释与尾逗号**（严格的 JSON）：否决。与 `appsettings.json` 的读法一致是使用者的预期，现有的文档可能带注释；别的语言实现这个 Provider 时要一个照收注释的读取器，Go 一致性模块里已经写了一个，两百行以内。
10. **cron 的步长上限定成段的最大值**（Quartz、cronie 这样做，`*/60` 写在分钟上不合法）：否决。`*/60`、`*/100` 现在合法（只取起点），收紧会让已有的表达式失效，而它们没有歧义。上限照现状写 2147483647；这个数来自 .NET 的 `int`，记在「待定」。
11. **cron 的步长不设上限**（任意多位数字）：否决。要给 .NET 写一个不溢出的大数解析，换来的只是 2147483648 以上的步长从不合法变成合法。
12. **cron 的搜索上限改成 5 个日历年**：否决。1830 天是现有的数，改成日历年又多一种算法（闰年、月末）；只把判定的位置改对。
13. **cron 结尾的换行照收**（配置文件里的块标量常带一个）：否决。规范里的文法都按整串匹配、结尾的换行不例外（RFC-0001「文法的匹配」）；要收就得写明收哪些空白、在哪些位置，现状恰恰是说不清的。读配置的一方自己去掉。
14. **取文案改成正文的另一种读法（先按目录、再按区域）**：否决，见背景第 6 条。
15. **`/proc/uptime` 维持浮点，只挡住负数与 `NaN`**：否决。按十进制读一步到位：写法只认数字与小数点，结果是精确的，别的语言照着做得出同一个数。
16. **平台读取路径里 Windows 的取法也做成向量**：否决。输入是系统调用与注册表，不由用例给出；写成向量只能是「三个数相加」这样的算术。正文写明取法。
17. **顺手做计划的文本形式**（`every 00:10:00 x5`，ADR-0277「没有做的」）：这次不做。间隔是 .NET `TimeSpan` 的 `c` 格式、时刻是 `DateTimeOffset` 的 `O` 格式，时区标识依赖系统的时区库，选项的次序、重复与 `TrimEntries` 的宽松各要判断一遍，不是随手能补的量。预签名的有效期属于对象存储、审计查询的每页条数属于审计，不在这 7 行的范围。

## 决策

### AI（RFC-0022）

1. **工具名**：正文写明文法 `^[A-Za-z0-9_-]{1,64}$`；由操作 ID 推出的名字超过 64 个字符时取前 55 个字符、去掉结尾的 `_`，再接 `_` 与全名 SHA-256 的前 8 位小写十六进制。.NET 不改。
2. **固定窗口分块**：字符按 Unicode 码位计，代理对算一个；窗口在统一换行之后的文本上按「窗口 − 重叠」滑动，取到文本结尾的窗口是最后一个；每个窗口切出来之后去掉首尾的空白（RFC-0001 的 25 个码位），去掉之后为空的不成块，去空白不改变后面窗口的位置。
   - `FixedWindowChunkingStrategy` 改按码位计：窗口的两端各是一个只往前走的下标，每次按码位数前移，成对的代理项整个跨过去；落单的代理项各算一个、原样留在块里。只含基本多文种平面字符的文本结果不变。
3. **提示词模板**：把背景第 3 条的扫描规则逐条写进正文；字符串与空值之外的参数怎样写成文本不作规定。.NET 不改。

### 配置（RFC-0014）

4. **两种文档格式**逐条写进正文（见 RFC-0014「Nacos Provider」的「文档格式」）。
5. **展平后重复的键不合法**：键不区分大小写，同一个键出现两次——含只差大小写的、嵌套的成员与带冒号的成员名展平出同一个键的——文档不合法（`CONFIGURATION_VALIDATION_001`），不取其中任何一个。重复按展平后的键判断，`{"a":"1","a":{"b":"2"}}` 展平成 `a` 与 `a:b`，不算。
6. **展平出的键为空不合法**（JSON 顶层的成员名是空串）；JSON 里落单的代理项转义不合法。两者以前都以别的异常从客户端漏出去，现在是 `CONFIGURATION_VALIDATION_001`。
7. **不合法的原因不带配置的值**：properties 的键为空时只报行号。

### 调度（RFC-0013）

8. **cron 的文法与推算**逐条写进正文（九条，见 RFC-0013「作业与触发器」）。
9. **只按空格与制表符分段**：去掉 `TrimEntries`。别的空白出现在表达式里就落在某一段中，那一段不合法。
10. **步长是 1 到 2147483647**：展开时剩下的不够一步就停，不让加法溢出。
11. **搜索上限按候选判定**：下一次的墙上时间与起点的墙上时间（去掉秒以下）相差不超过 1830 天，超过即没有下一次。

### 本地化（RFC-0010）

12. **查找先按区域、再按目录**写进正文；「语言文件」里目录的查找顺序一句随之写准（插件的目录不覆盖宿主在同一区域已有的模板）。.NET 不改；`Localization.Conformance` 的 `MessageLocalizerConformance` 新增用例 8（`LocaleOrder_ComesBeforeCatalogOrder`），内存与数据库两个本地化器都跑到。

### 可观测（RFC-0023）

13. **平台读取路径**新增「Linux 的取法」（十一条）与「Windows 的取法」（七条），写到另一种语言能照着读出相同数值的程度。
14. **`/proc/uptime` 按十进制小数读**：只有数字与至多一个小数点、至少一位数字；别的写法与时长类型装不下的值读成空。
15. **最后一级缓存同一级有几项时取目录名按序数排在最前的**。

### 向量与 Go 一致性模块

16. 七个向量文件补用例，期望值都由修正后的 .NET（Release 构建）算出：

    | 文件 | 新增 |
    | --- | --- |
    | `ai/tool-names.json` | 工具名文法的 `valid` / `invalid`；前 55 个字符以 `_` 结尾及其两侧的 4 条 |
    | `ai/knowledge-chunks.json` | 块首尾的空白、重叠时相同的块、各种空白字符、基本多文种平面以外的字符，共 12 条 |
    | `ai/prompt-templates.json` | 名字两侧的空白、没有闭合的 `{`、`}` 的各种写法、空名字、`null`，共 18 条；新增 `code`、`messageKey` 与 `missing`（缺少参数的 9 条） |
    | `configuration/remote-documents.json` | 两种格式收的 27 条、拒的 27 条 |
    | `scheduling/cron-expressions.json` | 推算的 57 条（含各上限与搜索上限的两侧）、必须拒绝的 53 条 |
    | `localization/catalog-resolution.json` | 能区分两种读法的 3 条 |
    | `observability/host-usage.json` | 新增 `linux` 一节：CPU 累计时间、内存、运行时长、挂载点、处理器、显卡，共 70 条 |

17. Go 一致性模块（`conformance/rules`）与 .NET 独立实现同一套规则并回放通过：新增 `IsAIToolName`，`RenderAIPrompt` 的参数值改为可空并返回缺少的占位符名；配置的 JSON 读取器改成照收注释与尾逗号、核对重复键的手写读取器；cron 的名字改按 ASCII 折叠（以前用 `strings.EqualFold`，会把长 s 认成 `S`）、步长设上限、搜索上限按候选判定；新增 `hostlinux.go`（`LinuxCPUTimes`、`LinuxMemory`、`LinuxUptime`、`LinuxBlockDeviceMounts`、`LinuxProcessor`、`LinuxGPUs`）。

## 理由

- 正文是事实源。出入留在那里，别的语言照正文实现出来的与 .NET 不一样，而没有向量盯住的规则迟早分歧（ADR-0276「理由」）。
- 写规则是一次核对：为了把 .NET 的行为写成另一种语言照着做得出的文字，要把每个边角跑一遍，过宽与不确定的地方就在这时暴露——cron 段两侧的空白、搜索上限的边界、运行时长的写法、缓存同级的取法都是这样找出来的。它们写不成规则，所以改实现。
- 取严不取宽：收紧的几处拒绝的都是本来就不该通过的输入（一个键写两次、夹着不换行空格的 cron、带负号的运行时长）；放宽的没有。
- Go 一致性模块独立实现后一次回放通过全部新用例，说明正文加向量已经足以让另一种语言写出一致的实现。

## 影响

- **公开 API**（`PublicAPI.Unshipped.txt` 已同步）：只新增 `MessageLocalizerConformance.LocaleOrder_ComesBeforeCatalogOrder()`（`Localization.Conformance`，`Preview`）。继承这个套件的本地化器测试多跑一条用例；先按目录、再按区域查找的实现会在这一条上失败。其余类型的签名不变。
- **行为变化与迁移**（原来 → 现在）：
  - `FixedWindowChunkingStrategy`（`Preview`）：窗口与重叠按 UTF-16 码元计 → 按码位计。含表情、扩展区汉字等基本多文种平面以外字符的文本，块的边界与块数会变（同样的 `MaxChunkSize` 每块可以多装），不再切出半个字符。已经摄入的文档不受影响；要让旧文档按新的边界切，重新摄入（先写后删，RFC-0022）。
  - `NacosConfigFormat` 的两种格式（`Preview`）：一个键写两次取最后一个 → 整份文档不合法，`FetchAsync` 返回 `CONFIGURATION_VALIDATION_001`，适配器照「加载与重读的失败语义」处理（首次加载按 `Optional` 决定是否启动失败，轮询中保留上一份）。升级前在 Nacos 里把重复的键（含只差大小写的）删到只剩一个。
  - `NacosConfigurationClient.FetchAsync`：JSON 里落单的代理项转义、顶层的成员名是空串 → 由抛出 `InvalidOperationException` / `ArgumentException`（适配器记成 `CONFIGURATION_UNAVAILABLE_001`）改为返回 `CONFIGURATION_VALIDATION_001`。
  - `CronExpression.Parse` / `TryParse`（`Stable`）：各段两侧的换行、不换行空格等空白裁掉照收 → 不合法。从配置或文件读表达式的地方自己去掉首尾的空白（`Trim()`）；`JobSchedule.ToString()` 写出的文本里各段以单个空格连接，存储里已有的计划不受影响。
  - `CronExpression.TryParse`：步长大到起点加步长溢出时抛出 `IndexOutOfRangeException` → 返回 `true`，只取起点。
  - `CronExpression.Next`（`Stable`）：下一次的墙上时间越过「起点 + 1830 天」而游标还没有核对时照样返回（多收最多一个月）→ 一律无值。只影响下一次触发在 1830 天开外的表达式（年份段、多年一遇的日期组合）。
  - Linux 上的系统运行时长（内部类型）：按浮点读 → 按十进制读，带符号、指数的写法读成空。
- **规范**（规范仓库已提交，指针待更新）：五个 RFC 的写明是 MINOR；其中 Nacos 重复的键不合法、cron 段两侧不再收别的空白与搜索上限的判定是改参考实现已有的行为，记 MAJOR（`v1.0.0` 之前允许）。向量只是补用例与新增成员，没有新文件；`prompt-templates.json` 的 `arguments` 的值现在可以是 `null`、新增 `code` / `messageKey` / `missing`，`tool-names.json` 新增 `valid` / `invalid`，`host-usage.json` 新增 `linux`，严格读取的回放要跟着改对象模型。
- **六个 SDK**：不受影响，都不认领这几个子系统档。Go 一致性模块的导出面有一处不兼容：`rules.RenderAIPrompt` 的参数与返回值变了，`conformance.AIPromptCase.Arguments` 由 `map[string]string` 改为 `map[string]*string`；Go SDK 升模块版本时没有用到它们就不用改。
- **测试**：
  - 回放：`AIToolNameVectorTests`（文法样例、前缀以 `_` 结尾）、`KnowledgeChunkVectorTests`（块两端没有空白、代理项成对、码位数不超过窗口）、`AIPromptTemplateVectorTests`（`missing` 的错误码、消息键与报出的名字）、`RemoteDocumentVectorTests`、`CronExpressionVectorTests`、`CatalogResolutionVectorTests`，新增 `LinuxHostReadingVectorTests`（把向量给的文本写进临时的根目录，交给 `LinuxHostPlatform` 去读，任何系统上都能跑）。每个回放都有「向量换了写法后某一类一条都没核对」的覆盖断言。
  - 复现：分块切开代理对、落单的代理项；Nacos 重复的键（五种写法）、落单的代理项转义、空的键经客户端返回校验错误、键为空的原因不带值；cron 别的空白、溢出的步长、搜索上限的六个边界与时区；运行时长的精确值与八种读不出的写法；缓存同级的取法。
- **文档**：文档站的 `ai`、`configuration`、`scheduling`、`localization`、`observability` 各页与 `appendix/spec`、更新日志待改。
- **待定**：
  - 提示词模板里没有闭合的 `{` 是原样写出还是算模板错误（备选 5）。现在照 .NET 与 RFC-0010 的一致做法写明了前者；它会放过「忘了写 `}`」的模板。
  - cron 步长的上限 2147483647 来自 .NET 的 `int`（备选 10、11）。要换成与类型无关的数（段的最大值，或不设上限）时，那是又一次修订。
  - 配置键「不区分大小写」对 ASCII 以外的字母怎么折叠随实现的配置系统（.NET 是 `OrdinalIgnoreCase`），正文没有写死，向量只用 ASCII 字母。
  - `JobSchedule.TryParse` 分词时同样带 `TrimEntries`（计划的文本形式，备选 17），做那一项时一并处理。
  - 最后一级缓存「同一级有几项」在实际硬件上不会出现；Windows 一侧是「取先出现的」，没有改。
