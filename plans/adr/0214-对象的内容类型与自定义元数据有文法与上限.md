# ADR-0214 对象的内容类型与自定义元数据有文法与上限

## 状态

已采纳（RFC-0012「标识」与「范围读取、分片上传与预签名」各一条修订，`conventions/error-codes.md` 登记 `OBJECTSTORAGE_VALIDATION_006`）。

## 日期

2026-11-13

## 背景

5.0 安全审查 S-41（`plans/5.0-安全审查.md`），低危，加固。

- `BlobPutOptions.ContentType` 只要求不空白，自定义元数据的值是任意字符串、不限大小。
- 两者都进 S3 的请求头与文件系统的元数据文件：
  - 换行能在请求头里拆出别的头。
  - 一个对象的元数据可以无限大。文件系统每次读元数据都整个读进内存，S3 超过 2 KB 时才由服务端拒绝。
- 宿主的直传端点在签名没有限定内容类型时，直接把请求的 `Content-Type` 写成对象的内容类型，长度与文法都由客户端决定。

复现：用旧 API 写的临时用例确认，带 CR/LF 的内容类型与 100 KB 的元数据值都能构造出写入选项，直传端点对 300 个字符的内容类型返回 200 并写入。回归用例：`BlobPutOptionsTests`、`HostedBlobUrlTests.Uploads_WithoutASignedContentType_RejectAnInvalidRequestContentType`。

## 备选

1. **各 Provider 自己判定**：否决。同一份写入选项在文件系统上能写、在 S3 上失败，应用换存储才发现。契约层一处判定，所有 Provider 一致。
2. **元数据按条数限制**：否决。条数限制不住单个值的大小；按名与值合计的字节数限制，同时限住两者。
3. **内容类型只禁换行**：否决。媒体类型有明确的文法，按文法判定连同长度一起限住，也排除了制表、非 ASCII 这类同样不该进请求头的字符。

## 决策

1. **内容类型**：媒体类型 `type/subtype`，两段都是 RFC 9110 的 token 字符，可跟 `;` 起头的参数（可打印 ASCII 与空格），整体 1 到 255 个字符。
   - `BlobPutOptions.IsValidContentType` 判定，`MaxContentTypeLength = 255`。
   - 不合法时 `ContentType` 的 `init` 抛出 `ArgumentException`，与标识不合法一样是编程错误。
2. **自定义元数据**：
   - 值不含控制字符（U+0000–U+001F、U+007F–U+009F）。
   - 名与值合计不超过 2048 个 UTF-8 字节（`MaxMetadataBytes`），与 S3 用户元数据的上限一致。非 ASCII 的值照常可写，按 UTF-8 字节计。
3. **直传端点**：签名没有限定内容类型时，请求的 `Content-Type` 不合文法即 `OBJECTSTORAGE_VALIDATION_006`（HTTP 400，消息键 `objectstorage.blob.content_type_invalid`，参数 `max`），不写入。

## 影响

- 破坏性变更：把客户端给的内容类型或元数据直接交给 `BlobPutOptions` 的代码，遇到不合法的输入从「写进存储」变为抛出 `ArgumentException`。先用 `IsValidContentType` 判断，不合法时拒绝请求。
- 公开 API：`BlobPutOptions.MaxContentTypeLength`、`MaxMetadataBytes`、`IsValidContentType`；`ObjectStorageErrors.ContentTypeInvalid`；`ObjectStorageMessages.ContentTypeInvalid`。
