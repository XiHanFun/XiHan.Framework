# ADR-0328 回调客户端已关闭排在载荷与 `data` 的编码之后

## 状态

已采纳（规范 `plugin/invocation.md` §5「插件一侧」与 RFC-0017 状态行已改；框架代码不改；六个 SDK 待跟，见「影响」）。

## 日期

2026-11-27

## 背景

- `plugin/invocation.md` §5 写了插件一侧回调客户端发出之前的核对与先后：可用的回调端点、权限、租户、截止时间与取消，最后是以字符串给出的 `Host.Invoke` 载荷与 `Host.Publish` 的 `data` 严格编码成 UTF-8（ADR-0312、ADR-0315）。没写「回调客户端已关闭」（插件停止、SDK 释放了回调连接之后的回调）排在哪里，也没写已关闭时编不成的那几项报什么。
- TypeScript SDK 改过一次：`Host.invoke` 把已关闭的核对挪到载荷编码之后；`Host.publish` 已关闭时编不成的那一项仍报编码错误，全部编不成时报编码错误、不发请求。
- 六个 SDK 现在的排法（只读核对）：

| SDK | 有没有本地的关闭状态 | `invoke` | `publish` | 关闭之后的结果 |
| --- | --- | --- | --- | --- |
| TypeScript | 有（`host.ts` 的 `#closed`） | 端点、权限、租户、截止与取消、载荷编码，最后才看关闭 | 整批核对之后逐项编码，编得成的才走到关闭的核对；全部编不成时不发请求、每项是编码错误 | `PLUGINS_UNAVAILABLE_001` + `plugins.host.unavailable`，`reason` 为 `Unavailable: the host client is closed` |
| Java | 有（`Host.java` 的 `closed`，在 `channel()` 里看） | 与 TypeScript 相同：`refuse()` 之后编码，再到 `call()` 看关闭 | 与 TypeScript 相同：`sent` 为空即返回，不到 `call()` | 同上，`reason` 为 `Unavailable: the plugin runtime has stopped` |
| Go | 没有，`Close()` 关掉 gRPC 连接 | 没有编码这一步（载荷是字节），本地核对之后发出时失败 | 同左（`data` 是字节） | gRPC 报 `Cancelled`（`grpc: the client connection is closing`），按 §5 的表是 `plugins.host.unavailable`（回调上下文已取消时 `KERNEL_CANCELLED_001`） |
| Python | 没有，`close()` 关掉 grpc.aio 通道 | 没有编码这一步，本地核对之后发出 | 同左 | 没处理：grpc.aio 在通道关闭之后多半抛 `UsageError`，`except grpc.aio.AioRpcError` 接不住，异常直接抛给作者（读代码推断，没跑） |
| PHP | 没有，`close()` 断开连接、置空 | 没有编码这一步（字符串按字节原样发） | 同左 | 进行中的回调以 `Cancelled`（`The client was closed.`）结束，按表是 `plugins.host.unavailable`；之后的回调**重新连接**，宿主还在听就照常发出 |
| Rust | 没有 `close`，客户端一直在 | 没有编码这一步 | 同左 | 不会出现 |

- 有编码这一步、又有本地关闭状态的只有 TypeScript 与 Java，两个都把关闭排在编码之后；其余四个的关闭都在发出时才表现出来，同样在全部本地核对之后。

## 备选

1. **关闭排在最后，与「连接失败」同一行**（采纳）：已关闭不是发出之前的核对，而是发出这一步本身失败，结果与 §5 的表「`Cancelled`，回调上下文的取消信号没有触发；`Unavailable`；连接失败」那一行相同。编不成的载荷与 `data` 不论客户端是否关闭都报编码错误。理由：
   - 六个 SDK 现在都是这个顺序：有本地关闭状态的两个这样排，其余的在发出时失败、本来就在全部本地核对之后。只有 Python 与 PHP 要改，而它们要改的是关闭之后的结果本身，与先后无关。
   - 对调用方最可预期：编不成是请求本身的属性，任何时候重试都不会成功；已关闭（插件在停止）是暂时的、可以留给重试与熔断的不可用。先报不可用，调用方按不可用重试，重试到客户端恢复时又换成编码错误，同一个请求在不同时刻得到两种错误；先报编码错误，结果只取决于请求本身。
   - 与宿主一侧对称：宿主在管道的 Validate 阶段才解码载荷，连得上才谈得上；本地编码不成相当于宿主读到不是 JSON 的载荷，它根本不需要宿主在线。
   - `Host.Publish` 逐项：编不成的那一项本来就不发出（ADR-0315），它的结果与发不发得出无关；其余各项才是一次请求，才会撞上已关闭。全部编不成时不发请求，也就不会撞上已关闭。
2. **关闭排在最前（先于端点与权限）**：否决。整批的权限、租户与截止时间错误是调用方的错误，排在不可用之后会被插件停止期间的不可用遮住；也与六个 SDK 现在的顺序都不同。
3. **关闭排在整批核对之后、编码之前**：否决。这正是 TypeScript 改掉之前的样子；编码错误被暂时的不可用遮住，理由见备选 1。
4. **关闭之后照常重新连接（PHP 现在的做法）**：否决。客户端释放了就不该再开新连接：插件已在停止，宿主可能已经把它的会话作废，重新连接要么被拒、要么在停止之后又发出了回调。
5. **关闭时的 `reason` 定一句固定的文本**：否决。§5 的表对这一行只规定 `<状态名>: <说明>`，各 SDK 的关闭有的是本地状态、有的是 gRPC 库报的 `Cancelled`，统一文本要多改四个 SDK 而调用方并不据它判断；码与键已经足够。
6. **只写明 TypeScript 的排法、不写「不重新连接」**：否决。规范要说清「已关闭」是什么状态，否则 PHP 那样关闭之后照发也算合规，排在哪里就没有意义。

## 决策

1. `plugin/invocation.md` §5「插件一侧」新增一条（MINOR，写明以前不作规定的）：SDK 释放了回调客户端（插件停止、运行时收尾）之后的回调不发请求、不重新连接，结果是「`Cancelled`，回调上下文的取消信号没有触发；`Unavailable`；连接失败」那一行（`PLUGINS_UNAVAILABLE_001` + `plugins.host.unavailable`，`reason` 写成 `<状态名>: <说明>`，用哪个状态名与说明不作规定）；它是发出这一步本身，排在本地各项核对与载荷、`data` 的编码之后；`Host.Invoke` 的载荷编不成即 `kernel.operation.invalid_payload`，与是否已关闭无关；`Host.Publish` 编不成的那一项是 `messaging.envelope.invalid`、其余各项是已关闭的错误，全部编不成时不发请求、每项是编码错误；整批的核对不合时每项仍是整批的错误；回调途中被释放同样是那一行（截止时间已到或调用方取消时照表的相应行）。规范没有要求 SDK 在停止时一定释放回调客户端。
2. RFC-0017 状态行追加同日再写明，对应 ADR 加 0328。
3. 没有新向量：运行器不提供 `Host` 服务，回调的本地核对由各 SDK 的单元测试覆盖（§7）。

## 影响

- 规范：MINOR。按本规范实现的宿主不受影响；SDK 的公开面不变。
- 六个 SDK（下一波，SDK 代理做）：
  - TypeScript：不用改，现在就是这样；补用例钉住已关闭时 `invoke` 的载荷编不成报 `invalid_payload`、`publish` 部分与全部编不成的两种结果（若还没有）。
  - Java：不用改，同 TypeScript 补用例。
  - Go：不用改。没有编码这一步；关闭之后 grpc-go 报 `Cancelled`，已按表映射成 `plugins.host.unavailable`。可补一条关闭之后回调的用例。
  - Python：要改。释放回调客户端之后的回调要在本地核对之后以 `plugins.host.unavailable` 结束（例如记一个关闭标记，发出前看它），不能让 grpc.aio 的 `UsageError` 抛给作者；补用例。
  - PHP：要改。`close()` 之后不再重新连接（`GrpcClient::connection()` 不再懒连），回调在本地核对之后以 `plugins.host.unavailable` 结束；补用例。
  - Rust：不用改。没有释放回调客户端的时机，这一条不适用；若以后在停止时释放，照决策 1 排。
- 文档站：`docs/sdks/` 下 Python 与 PHP 两页的回调一节写明关闭之后的行为（随 SDK 的改动）。
