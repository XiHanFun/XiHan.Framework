# ADR-0080 插件声明的权限码由宿主登记、审计按操作排除、按名引用的策略启动时核对

## 日期

本 ADR 记录第三批回灌里安全与审计分区的三项决定（`g-batch-backlog.md` 第 1–3 条，来由是 ADR-0071 之后留下的待定项），每项一节。

## 一、插件清单声明的权限码由宿主登记（第 1 条）

### 背景

ADR-0071 让操作契约引用的权限码必须已登记于 `PermissionRegistry`：装配完成时核对，插件握手之后登记的在登记时核对。权限码只能由宿主的特性经 `FeatureContext.AddPermission` 登记，插件清单的 `contributes.permissions` 只是声明，宿主不读它。结果是插件的操作只能引用宿主替它预先登记好的码：插件要带一个自己的权限码，宿主应用就得改代码、发版，与"插件按目录发现、独立交付"相悖；不改就整组被拒。

清单 Schema 里 `contributes.permissions` 的每一项只是字符串，没有文法约束；`PermissionDefinition` 构造时才校验文法，插件写错了只会在登记那一刻抛参数异常。

### 备选

1. 宿主在发现插件时替它登记清单声明的权限码，冲突即插件整体失败（采纳）。
2. 宿主登记，冲突时视为"引用已有的码"静默跳过：插件可以借声明抢占或改写宿主码的含义，宿主看不出冲突。
3. 维持现状，由宿主应用为每个插件手写登记：插件不能独立交付。

### 决策

- 进程外与 Wasm 宿主登记插件的代理操作时，把清单 `contributes.permissions` 声明的码一并登记进 `PermissionRegistry`，显示名取码本身（插件可以在握手的消息目录里给 `permissions.<码>.name` / `.description` 的译文）。只登记清单声明了的：操作的 `permission` 既不是宿主已登记的、也不在本插件清单里，仍按 ADR-0071 拒绝（`KERNEL_VALIDATION_005`）。
- 一个插件的贡献一次登记、全进或全不进：内核 `OperationRegistry.AddRange(operations, permissions)`（原 `AddRange(operations)` 改签名，`Add` 是只有一个操作、没有权限码的特例）先把权限码写进权限登记表（同组的操作可以引用它们），再核对、写入操作；任一项不过，已写进的权限码在同一个锁里撤回。为此登记表在构造时绑定它核对的权限登记表（`new OperationRegistry(permissions)`，原无参构造改签名），`PermissionRegistry` 新增 `AddRange`（一批全进或全不进），写入改在锁内进行（插件在运行期也会登记）。
- 冲突：声明的码与已登记的重复——宿主特性定义的，或另一个已登记插件声明的——是 `KERNEL_SECURITY_001`，插件整体登记失败；宿主特性在插件之后登记同一个码，同样以 `KERNEL_SECURITY_001` 失败。配置阶段发现的插件在配置阶段登记，冲突是启动失败，装配完成时的权限码核对（ADR-0071）已能看到插件声明的码；之后登记的（重试成功、运行期 `LoadAsync`）按发现时被拒处理。
- 清单读取器按 `manifest.schema.json` 新加的约束核对 `contributes.permissions`：每项合权限码文法、不重复，否则清单读不出（插件按 `PLUGINS_VALIDATION_001` 在发现时被拒），不再等到登记那一刻才抛参数异常。
- 进程内插件宿主不登记：进程内插件有自己的容器，不向应用的登记表贡献操作。
- 登记表只增不减：卸载不撤回插件的权限码与代理操作（代理操作此前就不撤回）。登记过的插件卸载后再加载，与自己留下的登记冲突而失败，换版本须重启宿主。

### 理由

- "清单是插件的唯一事实源"（RFC-0017）：插件定义的权限码写在清单里，由宿主登记，插件才能独立交付；只登记声明了的，宿主仍能从清单看清插件引入了哪些码。
- 冲突即失败，不做"重复就当引用"：权限码是授权的语义单位，两个定义方共用同一个码时谁也说不清它的含义，静默合并会让插件借声明影响宿主码的授予判定。要引用宿主或别的插件的码，只在操作契约里写，不在清单里声明。
- 权限码与操作同一组登记、全进或全不进，被拒的插件不留下孤立的权限码；否则改正后的同一插件再加载会与自己上次留下的码冲突。

### 影响

- 公开 API（Kernel，均在 `PublicAPI.Unshipped.txt`，直接改，不留旧签名）：`OperationRegistry(int capacity)` → `OperationRegistry(PermissionRegistry permissions, int capacity)`；`OperationRegistry.AddRange(IReadOnlyList<OperationDescriptor>)` → `AddRange(IReadOnlyList<OperationDescriptor>, IReadOnlyList<PermissionDefinition>)`；新增 `PermissionRegistry.AddRange`。应用通常不直接构造登记表（`AppBuilder` 构造），单独构造的测试要传权限登记表。
- 行为：插件清单声明了权限码时，宿主替它登记；声明的码与宿主或别的插件冲突时，配置阶段发现的插件让应用启动失败（`KERNEL_SECURITY_001`），运行期加载返回同一错误。`contributes.permissions` 不合文法或重复的插件清单读不出。
- 测试：内核登记表整组登记与撤回、权限登记表整批登记、清单读取器的文法与重复；Wasm 宿主运行期加载登记声明的码、只登记声明的、与宿主冲突、两个插件冲突、配置阶段通过与两种登记顺序的冲突、清单不合法；进程外宿主配置阶段登记声明的码与冲突启动失败。
- 遗留：卸载不撤回登记（代理操作原本如此），`lifecycle.md` 里"`UnloadAsync` + `LoadAsync` 恢复"对登记过的插件不成立，已在规范写明须重启宿主；要支持卸载后再加载，需要登记表按归属撤回，另行决定。

## 二、审计按操作排除（第 2 条）

### 背景

ADR-0071 第三节让 `AuditSelection.Protected` 记录只用策略保护的操作。BasicApp 约 74 个操作只声明了 `Policy`（多为 `authenticated`），其中约 24 个是前端每次加载都调的只读查询（当前用户权限、会话角色、我的登录日志……），审计表行数会明显增加。选择规则只有 `Protected` / `All` / `None` 三档，想留下需要授权的写操作、又不记这些高频查询，没有办法。

### 备选

1. 按操作排除：列操作 ID 或前缀（采纳）。
2. 排除只读操作：一刀切，敏感的只读查询（导出、查看密钥）也不记了，而只读与否和是否该留痕无关。
3. 让应用在处理器里清掉动作：审计中间件没有这样的入口，且要改每个操作。

### 决策

- 配置键 `XiHan:Auditing:Exclude`（`AuditingOptions.Exclude`），列表；每项是操作 ID（精确匹配），或以 `*` 结尾的前缀——`profile.*` 是资源 `profile` 的全部操作，`my-*` 是资源名以 `my-` 开头的全部操作；按序数比较。写法与清单激活事件 `onOperation:orders.*` 一致，用 `*` 而不是"以 `.` 结尾"表示前缀，资源名内的前缀（`my-*`）也写得出。
- 只作用于按 `Selection` 挑出的操作；显式 `SetAuditAction` 的调用照样记录——那是代码要求留痕的动作（登录、导出），排除配置不压掉它。
- 不配置或空列表与以前完全一样。
- 配置非法即启动失败：每项必须是合法的操作 ID，或 `*` 之前是非空的操作 ID 前缀（`^[a-z][a-z0-9-]*(\.[a-z0-9-]*)?$`）；空白、单独的 `*`、`*` 不在末尾、大写或其他字符，以及把 `Exclude` 写成单个值而不是列表（环境变量 `XiHan__Auditing__Exclude=…` 会这样），都在读取选项时抛出 `ArgumentException`，消息指出配置键与那一项。代码里 `new AuditingOptions { Exclude = … }` 同样校验。
- 不核对操作是否已登记：模块可以按配置开关、插件的操作可能在启动之后才登记，列了不存在的操作只是不命中。

### 理由

- 量的问题出在少数几个高频只读查询上，按操作点名最准确；前缀让按资源成组排除（`profile.*`）不必逐个列。
- 单独的 `*` 与 `Selection: None` 重复，拒绝它避免两种写法表达同一件事；写成单个值时 `GetChildren` 为空，静默当作没配会让排除悄悄失效，所以按配置错误处理。

### 影响

- 公开 API：`AuditingOptions.Exclude`（新增，init 校验）。缺省行为不变。
- CLI 知识库 `configuration.json` 增 `XiHan:Auditing:Exclude:{index}`。
- 测试：精确 ID、资源前缀、资源名前缀、不命中、显式动作不受影响、不配置与以前一样、十种非法项装配失败、单个值与代码构造的校验。

## 三、按名引用的策略与端点上的要求启动时核对（第 3 条）

### 背景

ADR-0071 让操作契约的权限码在装配完成时核对，`SECURITY_NOTFOUND_001`（策略不存在，404）只剩按名给出的策略：契约的 `Policy`、端点上的 `RequireXiHanPolicy` / `RequireXiHanPermission`、`RequireAuthorization` 显式写入的要求。它们都在调用时才查找，拼错的策略名或忘了登记的权限码要等到有人调用那个端点才暴露，暴露的方式还是一个看上去像"资源不存在"的 404。

### 备选

1. 启动时核对，与 ADR-0071 同理（采纳）。
2. 装配时核对：`IPolicy` 是容器里的服务，`AppBuilder.Build` 时容器还没建，拿不到策略名；端点在 `Build` 之后才映射。
3. 维持调用时 404：拼写错误在生产上才暴露。

### 决策

- 契约的 `Policy`：授权能力的 Provider 在启动时（`IHostedFeature.StartAsync`）调用 `PolicyCatalog.EnforceOn(OperationRegistry)`。它经内核新增的 `OperationRegistry.Enforce(check)` 在同一个锁里核对已登记的全部操作并把核对挂到登记表上：已登记的有不存在的策略（含 `permission:<code>` 的权限码未登记）即抛出 `SECURITY_VALIDATION_004`（新错误码，`FrameworkException`，一次列出全部），该特性启动失败——默认失败策略 `TerminateStartup` 下应用启动失败（外层 `KERNEL_HOSTING_002`，内层 `SECURITY_VALIDATION_004`）；此后登记的操作（插件握手之后）在登记时逐个核对，不存在即登记失败（同一错误码，消息键 `security.policy.operation_unregistered`，参数 `id`、`owner`、`policy`），插件整体被拒、同组声明的权限码撤回。`Security.InMemory` 与 `Security.Database` 改为 `IHostedFeature`，被选为授权能力时这样做；自己实现 `security.authorization@1` 的 Provider 也要这样做（写进 RFC-0008）。
- 端点上的要求：`UseXiHan()` 改为中间件工厂形式，在宿主建请求管道时（`Map*` 都已调用、`UseEndpoints` 已把数据源交给路由）核对全部端点元数据里的 `AuthorizationRequirement`，权限码未登记、策略不存在即抛出 `SECURITY_VALIDATION_004`（一次列出全部，带端点显示名），`app.StartAsync()` / `app.Run()` 失败。
- 次序：插件声明的权限码（第一节）在配置阶段登记，授权能力启动与建请求管道都在其后，`permission:<插件声明的码>` 能通过。
- 没有装配授权能力（容器里没有 `PolicyCatalog`）时两处都不核对：此时 Authorize 阶段本来就不判定任何要求。
- `SECURITY_NOTFOUND_001` 保留：调用时才看到的要求（应用代码以 `RequireAuthorization` 显式写入的、启动之后才加进来的端点）仍在调用时查找，找不到按策略不存在拒绝。

### 理由

- 与 ADR-0071 的权限码一致：引用了不存在的东西是编程错误，越早失败越好，且一次列出全部。
- 核对点放在"判定依据刚好齐全"的那一刻：策略要等容器建好，端点要等路由映射完；再晚就是调用时。
- 错误码新增一个 `VALIDATION`（而不是复用 `KERNEL_VALIDATION_005` 或 `SECURITY_NOTFOUND_001`）：核对属于安全子系统，策略名不是权限码；`NOTFOUND` 是调用时的结果，启动失败与它区分开，调用方看错误码就知道是哪一类问题。端点上未登记的权限码在策略目录里就是"策略不存在"，与命名策略同一个码。
- 插件晚登记的操作同样核对，否则插件可以绕开启动核对、把 404 留到调用时。

### 影响

- 启动期新增失败：操作契约的 `Policy` 不是已注册的 `IPolicy` 名、也不是已登记权限码的 `permission:<code>`；端点的 `RequireXiHanPolicy(name)` 不是已注册的策略、`RequireXiHanPermission(code)` 的权限码未登记——装配了授权能力时启动失败（`SECURITY_VALIDATION_004`）。
- 公开 API：新增 `OperationRegistry.Enforce`、`PolicyCatalog.EnforceOn`、`SecurityErrors.UnregisteredPolicy`、`SecurityMessages.OperationPolicyUnregistered`（十种语言）；`InMemorySecurityFeature`、`DatabaseSecurityFeature` 从 `IFeature` 改为 `IHostedFeature`（多出 `StartAsync` / `StopAsync`，经 `UseFeature` 装配的应用不用改）。`UseXiHan()` 签名不变。
- 测试：内核 `Enforce`；`PolicyCatalog.EnforceOn` 列出全部与之后的登记；内存与数据库授权特性启动失败、通过、未被选为授权能力时不核对；端点权限码与策略不存在启动失败、`UseXiHan` 之后映射的同样核对、已登记的通过并照常判定；Wasm 插件的 `permission:<自己声明的码>` 通过启动核对、策略不存在启动失败、启动之后加载被拒且撤回声明的码。

第一节「登记表只增不减：卸载不撤回插件的权限码与代理操作」由 ADR-0085 第三节修订：登记带归属，卸载按归属一次撤回，之后可直接再加载。第三节「授权能力的 Provider 在 `IHostedFeature.StartAsync` 里调用 `PolicyCatalog.EnforceOn`，默认失败策略下应用启动失败」由 ADR-0085 第四节修订：改为在 `Configure` 里登记启动核对，不论失败策略都拒绝启动，异常直接是 `SECURITY_VALIDATION_004`；`InMemorySecurityFeature`、`DatabaseSecurityFeature` 改回 `IFeature`。
