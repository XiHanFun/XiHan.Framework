# ADR-0343 S3 的元数据太大与会被改写的值返回校验错误，别的写入方原样写进头的 UTF-8 字节严格按 UTF-8 解出

## 状态

已采纳（规范 RFC-0012「契约」「S3 Provider」「一致性」与 `conventions/error-codes.md` 已改；`ObjectStorage.Abstractions` 新增错误码 `OBJECTSTORAGE_VALIDATION_008`、`OBJECTSTORAGE_VALIDATION_009` 与两个消息键；`ObjectStorage.S3` 的 `S3BlobStore` 与内部类型 `S3MetadataHeader` 已改）。

本 ADR 修订 ADR-0333 备选 2 里「以 `=?` 开头且以 `?=` 结尾就编码」的适用范围（整个是 encoded-word 形状的改为拒收，其余照旧编码）与备选 11 的两处「已知缺口」。按「状态只增不改」，ADR-0333 的正文不改，以本 ADR 为准；ADR-0333 的编码写法、拆分、读回的形状与解码规则不受影响。

## 日期

2026-11-27

## 背景

ADR-0333 让 S3 Provider 照 RFC 2047 编解码自定义元数据的值，留下三处问题，仓库所有者已拍板：

1. **Amazon S3 的 `MetadataTooLarge`**：Amazon S3 的文档说用户元数据 2 KB 上限按请求头里各键与值的 UTF-8 字节数计。RFC 2047 编码之后的值变长，原值离契约 2048 字节上限不远、非 ASCII 的字节又多时，服务以 400 `MetadataTooLarge` 拒收，Provider 按存储故障返回 `OBJECTSTORAGE_UNAVAILABLE_001`——调用方以为重试有用。拍板：认出这个 S3 错误码，转成校验错误；不预先按编码之后的长度拒收（RustFS 收得下约 3.3 KB，契约上限按原值计）。
2. **整个是 encoded-word 形状的纯 ASCII 值**：Provider 把它编码之后写出；按 Amazon S3 的文档，服务先解码再存、只有 ASCII 的值原样返回，读回时 Provider 再解一次，悄悄变成另一个值。拍板：写入时以校验错误拒收、不发请求（先例：内容类型的 `OBJECTSTORAGE_VALIDATION_007`，ADR-0295），宁可报错不悄悄改值；一致性套件不受影响，在规范里写成 Provider 可以拒收的一类。
3. **别的客户端原样写进的 UTF-8 字节**：不按 RFC 2047、直接把 UTF-8 字节写进 `x-amz-meta-*` 头时服务原样返回（ADR-0333「没有解决的」）。拍板：先实测 .NET 的 HTTP 客户端与 AWS SDK 把这样的响应头交成什么，读成 Latin-1 乱码就还原成字节严格按 UTF-8 解，解不出算不合规应答。

## 查明的事实

以下是对 `AWSSDK.S3` 4.0.104.8、`AWSSDK.Core` 4.0.102.14 经回环上的 `RecordingHttpListener` 的实测（它的响应头改为按 Latin-1 写出，经新增的 `RawHeader` 能写出任意字节），以及对本机 RustFS 的实测。

- **SDK 与 .NET 怎么交出原样的字节**：HEAD 的应答头 `x-amz-meta-title` 带 UTF-8 字节 `E4 B8 AD E6 96 87 20 63 61 66 C3 A9`（`中文 café`），SDK 交出的值是 `U+00E4 U+00B8 U+00AD U+00E6 U+0096 U+0087 U+0020 U+0063 U+0061 U+0066 U+00C3 U+00A9`：每个字节一个 U+0000–U+00FF 的字符（Latin-1）。不是合法 UTF-8 的字节（`FF 41`、截断的 `E4 B8`）同样逐字节交出，不替换成 U+FFFD、不抛出；`61 C2 85 62` 交出 `a`、`U+00C2`、`U+0085`、`b`。缺省实例的传输（SDK 自己建的客户端）与命名实例的传输（`S3OutboundHttpClientFactory` 的 `SocketsHttpHandler`）结果相同；同一应答里只有 ASCII 的头不受影响。
- **`MetadataTooLarge`**：对端回 `400 Bad Request` 与 S3 的 XML 错误体（`<Code>MetadataTooLarge</Code>`）时，`PutObject` 与 `InitiateMultipartUpload` 都抛 `AmazonS3Exception`，`ErrorCode` 为 `MetadataTooLarge`，`StatusCode` 为 `BadRequest`，`ErrorType` 为 `Sender`；尝试次数取 3 时 SDK 只发一个请求，不重发。
- **RustFS 1.0.6**（本机镜像 `rustfs/rustfs:latest`，摘要 `sha256:ee717072…`，与 CI 钉的相同；临时容器只绑 `127.0.0.1`，测完即删）：用请求头按 UTF-8 写出的传输（`SocketsHttpHandler.RequestHeaderEncodingSelector` 选 UTF-8，SDK 按同一串字符的 UTF-8 签名，验签通过）把原始 UTF-8 字节写进 `x-amz-meta-title`，读回（HEAD 与 GET 一样）时有非 ASCII 字符的值都被 RustFS 编成 RFC 2047 的 encoded-word：`中文 café` 读回 `=?UTF-8?B?5Lit5paHIGNhZsOp?=`；100 个「中」读回 7 个以一个空格隔开的 encoded-word，每个至多 45 个字节，与 Provider 写出的形状相同；`说明 =?UTF-8?B?5Lit?=` 读回整个编码的 `=?UTF-8?B?6K+05piOID0/VVRGLTg/Qj81TGl0Pz0=?=`；`a U+0085 b` 读回 `=?UTF-8?B?YcKFYg==?=`。只有 ASCII 的值原样返回（`=?UTF-8?B?5Lit?=` 照旧原样，不解码）；` lead` 读回 `lead`（首尾的空格在写入时已被去掉）。所以 RustFS 上别的写入方原样写进的字节读回时已经是 encoded-word，Provider 照 ADR-0333 解得开；原样返回字节的一条路只能靠回环假对端验证。
- **RustFS 1.0.6 对以 `=?` 开头且以 `?=` 结尾的 ASCII 值**（同一个临时容器，经 SDK 原样写出）：它解得了的 encoded-word（`=?UTF-8?B?YQ==?=`）原样存下、原样读回；解不了的以 `400 InvalidArgument`（`invalid header: x-amz-meta-title: "…"`）拒收：`=?x?=`、`=?=`、`=? ?=`、`=?a b?=`、`=?foo?=`、`=?UTF-8?B?5Lit?==?UTF-8?B?5paH?=`、`=?ISO-8859-1?Q?caf=E9?=`、`=?x?y?z?=`、`=?UTF-8?X?abc?=`、`=?UTF-8?B?5Li?=`。不以这两段开头结尾的（`=?abc`、`abc?=`、`=?UTF-8?B?5Lit?= note`、`note =?UTF-8?B?5Lit?=`）照收，`=?UTF-8?B??=`、`=?UTF.8?B?5Lit?=` 也照收。所以 ADR-0333 对这类值编码写出是 RustFS 上写得进去的前提，不能改成原样写。
- **Amazon S3 的文档**（同 ADR-0333，只读）：值里有非 US-ASCII 字符时按 RFC 2047 解码之后存下，返回时按 RFC 2047 编码，只有 US-ASCII 的值原样返回；用户元数据上限 2 KB，按各键与值的 UTF-8 字节数计。没有实测。

## 备选

### 元数据太大

1. **认出 `MetadataTooLarge`、返回校验错误**：采纳（拍板）。写入与发起分片上传两处接住 `ErrorCode` 为 `MetadataTooLarge` 的 `AmazonS3Exception`，排在 `IsStoreFailure` 之前。不记 Warning：是调用方能改的输入，不是存储故障。
2. **复用现有的码还是新码**：新登记 `OBJECTSTORAGE_VALIDATION_008`。对象存储没有「元数据过大」的校验码：契约的 2048 字节上限在给 `BlobPutOptions.Metadata` 赋值时以 `ArgumentException` 抛出（编程错误，不占码）。`OBJECTSTORAGE_UNAVAILABLE_002`（配额或单对象大小超限）是不可用一类，拍板要的是校验错误。也没有与下面的 `009` 合成一个码：一个是服务按它的计法收不下（发出请求之后才知道，调用方要缩小元数据），一个是 Provider 预先知道服务会改掉值（不发请求，调用方要换一个值），处置不同。
3. **参数**：没有。服务的错误不说是哪一项、上限按什么计；写成 `max`（2048）会误导，那是契约按原值计的上限，服务拒收的元数据并没有超过它。
4. **预先按编码之后的长度拒收**：否决（拍板），理由同 ADR-0333 备选 11：契约的上限按原值计，文件系统存储与 RustFS 都收得下。

### 整个是 encoded-word 形状的 ASCII 值

5. **写入时以校验错误拒收**：采纳（拍板）。判定与读回时解码的形状同一个函数（`S3MetadataHeader.IsEncodedWords`，ADR-0333 备选 7）：值整个是以空格或制表符隔开的一个或多个合 RFC 2047 §2 文法的 encoded-word，首尾没有空白；认不认得 charset 与 encoding 都算（`=?ISO-8859-1?Q?caf=E9?=`、`=?x?y?z?=` 读回时是解不了，同样不是原值）。encoded-word 只有 ASCII，所以这一类只有 ASCII。
6. **新登记 `OBJECTSTORAGE_VALIDATION_009`**：采纳。不复用 `007`：那是内容类型。参数照 `007` 的写法给出写不成原样的那一项，但只给元数据名 `name`、不带值：值至多约 2 KB，也可能是业务数据。多项都是这个形状时报按名的序数次序的第一个，同一份元数据每次报同一个名。
7. **次序**：排在内容类型的核对之后，不覆盖写入的放行与 `Head` 之前，一个请求都不发（同 `007`）。写入与发起分片上传两处都接；Provider 不用 `CopyObject`（ADR-0313），没有复制这一处。
8. **以 `=?` 开头且以 `?=` 结尾而不是这个形状的值**（`=?x?=`）：照旧编码写出（ADR-0333）。曾考虑改为原样写——读回时它不整个是 encoded-word、原样交出，写入的规则就与读回的规则一一对应——但 RustFS 1.0.6 实测拒收原样写出的这类值（见「查明的事实」），否决。编码写出时 RustFS 原样存取、读回解出原值；Amazon S3 若先解码，存下的是同一个只有 ASCII 的值、原样返回，读回时不整个是 encoded-word，同样是原值。
9. **首尾有空格而去掉之后是 encoded-word 形状的值**：照旧编码写出（首尾的空格要编码），不拒收。RustFS 上往返；Amazon S3 上见「影响」的缺口。
10. **Provider 的 `Encode` 收到这一类时**：抛 `ArgumentException`（核对被绕过，同孤立的代理项，ADR-0333 备选 4），不照写。
11. **改为在 `BlobPutOptions` 里拒收**：否决。这是 S3 特有的收窄，文件系统存储照收（拍板：一致性套件不受影响）。

### 原样写进头的 UTF-8 字节

12. **把字符还原成字节、严格按 UTF-8 解**：采纳（拍板，实测是 Latin-1）。读回时值里有 U+0080 及以上的字符（`S3MetadataHeader.IsRaw`）即是这一类：Provider 写出的总是只有 ASCII 的值，encoded-word 也只有 ASCII。按 Latin-1 还原（每个字符一个字节），以严格的 `UTF8Encoding` 解出，再过控制字符的核对（U+0000–U+001F、U+007F–U+009F，同 ADR-0333 备选 9）。只有 ASCII 的值照旧判 encoded-word，不变。
13. **有 U+00FF 之外的字符**：解不了。Provider 建的两种传输都不会这样交出；应用自己注册了按别的编码读头的客户端时，交来的已经不是一个字符一个字节，还原不出服务发来的字节，不猜。
14. **解不了**：按不合规的应答返回 `OBJECTSTORAGE_UNAVAILABLE_001`，与 ADR-0333 解不了的 encoded-word 同一处置（记 Warning，不带值），原因另写：`HeadObject returned user metadata with raw non-ASCII bytes that do not decode as UTF-8 to a valid value`（`GetObject` 同）。解不了包括：不是合法的 UTF-8（单独的 `FF`、截断的多字节字符、Latin-1 写的 `é`、编成 UTF-8 的代理项 `ED A0 80`），解出控制字符（`C2 85` 即 U+0085，制表符），有还原不了的字符。否决的有：原样交出 Latin-1 的乱码（以前的做法：调用方拿到的不是存进去的值，里面的 U+0080–U+009F 写回即被 `BlobPutOptions.Metadata` 拒收）；换成 U+FFFD（静默乱码）；试过 UTF-8 不行再按 Latin-1 交出（猜别的写入方的字符集）。
15. **解出的值再判 encoded-word**：否决。原样的字节解出的值有非 ASCII 字符，不可能整个是 encoded-word；夹着的 encoded-word（`说明 =?UTF-8?B?5Lit?=`）原样交出，同 ADR-0333 备选 7。

## 决策

### 规范

1. RFC-0012「契约」（MINOR，写明以前不作规定的）：新增「存储收不下或会改写的自定义元数据」一条——存储按它自己的计法拒收合上限的元数据时写入与分片上传的发起以 `OBJECTSTORAGE_VALIDATION_008` 失败（HTTP 400，没有参数），不当作存储故障，Provider 不预先按编码之后的长度拒收；所用的存储会把值存成另一个值时在发出任何请求之前以 `OBJECTSTORAGE_VALIDATION_009` 失败（HTTP 400，参数 `name`，不带值）；文件系统存储两类都不会遇到。
2. RFC-0012「S3 Provider」「自定义元数据的值」：写入一条里整个是 encoded-word 形状的只有 ASCII 的值改为以 `009` 拒收（MAJOR，`v1.0.0` 之前允许：以前写明的是编码之后写出），以 `=?` 开头且以 `?=` 结尾的其余值照旧编码并写明 RustFS 拒收原样写出的这类值；读回新增原样字节的一条，解不了的一条补上原样字节（MINOR）；「服务怎么存」补 RustFS 对原样字节的实测；「Amazon S3 没有实测，已知两处可能的缺口」改为照文档定的两条规则，另记一处仍没实测的缺口（见「影响」）；错误映射补 `MetadataTooLarge` → `008`。
3. RFC-0012「一致性」（PATCH）：「向量不收的」补写入时拒收的形状与原样的字节。状态行追加「同日第三次修订」，「对应 ADR」加本 ADR。
4. `conventions/error-codes.md` 登记 `OBJECTSTORAGE_VALIDATION_008`、`OBJECTSTORAGE_VALIDATION_009`（MINOR）；`OBJECTSTORAGE_UNAVAILABLE_001` 的说明补上解不成合法值的原样字节（PATCH，码不变）。

### 实现

5. `ObjectStorage.Abstractions`（`Stable`，只有新增）：`ObjectStorageErrors.MetadataTooLarge`（`OBJECTSTORAGE_VALIDATION_008`）、`ObjectStorageErrors.MetadataValueUnsupported`（`OBJECTSTORAGE_VALIDATION_009`）；`ObjectStorageMessages.MetadataTooLarge`（`objectstorage.blob.metadata_too_large`，没有参数）、`ObjectStorageMessages.MetadataValueUnsupported`（`objectstorage.blob.metadata_value_unsupported`，参数 `name`），10 个语言文件已补。
6. `S3MetadataHeader`：新增 `IsEncodedWords`（读回时解码与写入时拒收共用）与 `IsRaw`；`Encode` 收到整个是 encoded-word 形状的值抛 `ArgumentException`，以 `=?` 开头且以 `?=` 结尾的其余值照旧编码；`TryDecode` 对原样的字节按 Latin-1 还原、严格按 UTF-8 解、核对控制字符，有 U+00FF 之外的字符时解不了；严格解码与控制字符的核对抽成 `TryDecodeUtf8`，两条路共用。
7. `S3BlobStore`：写入与发起分片上传在内容类型的核对之后以 `FindAlteredMetadataName` 找出第一个整个是 encoded-word 形状的元数据名，返回 `009`；两处接住 `MetadataTooLarge`（`IsMetadataTooLarge`）返回 `008`；`ReadMetadata` 交出解不了的那个值，`DescribeObject` 据 `IsRaw` 选原因，`ObjectAnswer` 加 `MetadataBytesUndecodableReason`。
8. S3 包 README 写明这三项。

## 理由

- `MetadataTooLarge` 是服务对调用方输入的判定，换一份更小的元数据就能写进去：报成存储故障会让调用方重试、让健康与告警误报。
- 存不成原样的值在写入之前拒收，与内容类型同一条原则（ADR-0295）：同一份写入选项在不同 Provider 上要么得到同一个值，要么明确失败，不悄悄存成另一个值。
- 原样写进头的字节是合法的 UTF-8 时，它就是别的写入方存进去的值；.NET 交出的 Latin-1 字符一一对应字节，还原是无损的。解不出时报错，而不是交出看上去合法的乱码。

## 影响

- **公开 API**（`PublicAPI.Unshipped.txt` 已同步，只有新增）：见「决策」第 5 条。`BlobPutOptions` 与 S3 包的公开面不变，配置键不变。
- **行为**（`ObjectStorage.S3`，`Stable`）：
  - 写入与发起分片上传被服务以 `MetadataTooLarge` 拒收：以前 `OBJECTSTORAGE_UNAVAILABLE_001`（`reason` 是异常类型），现在 `OBJECTSTORAGE_VALIDATION_008`。
  - 整个是 encoded-word 形状的只有 ASCII 的元数据值：以前编码之后写出（RustFS 上往返，Amazon S3 上按文档推断读回会变），现在写入与发起分片上传返回 `OBJECTSTORAGE_VALIDATION_009`，不发请求。升级须知：把这类值（多半是别处读来的、已经编好的 encoded-word）交给 S3 Provider 的，先解开再写，或换一个值；文件系统存储不受影响。
  - 读回原样写进头的 UTF-8 字节：以前交出 Latin-1 的乱码，现在交出原值；不是合法 UTF-8 或解出控制字符的，读取与 `Head` 返回 `OBJECTSTORAGE_UNAVAILABLE_001`（以前交出乱码）。只判存在与否的 `Head` 不读元数据，不受影响。
- **规范**（规范仓库已改，指针待更新）：见「决策」第 1–4 条；不新增向量（只有 .NET 的 S3 Provider 做，由它自己的测试与对 RustFS 的门控用例核对），SDK 不受影响。
- **测试**（`ObjectStorage.S3.Tests`）：
  - `RecordingHttpListener` 的响应头改为按 Latin-1 写出（只有 ASCII 的头与以前相同），新增 `RawHeader` 写出任意字节。
  - `S3MetadataWireTests`：线上写法的用例去掉整个是 encoded-word 形状的那一条，补上首尾有空格的 encoded-word 形状（编码）与 `=?UTF-8?B?5Lit?==?UTF-8?B?5paH?=`（编码）、`=?UTF-8?B?5Lit?= note`（原样）；新增 encoded-word 形状的 6 种值在写入（覆盖与不覆盖）与发起分片上传时返回 `009` 且一条连接都不建、多项时报序数最小的名、内容类型先于元数据报告、服务回 `MetadataTooLarge` 时写入与发起返回 `008`（只发一个请求、不记 Warning）。
  - 新增 `S3MetadataRawBytesWireTests`：钉住 .NET 与 SDK 把原样的字节交成 Latin-1（两种传输），HEAD、整读与范围读取解出原样的 UTF-8，解不成合法值的 5 种字节返回 `001`（reason 固定、Warning 不带值）。
  - `S3MetadataHeaderTests`：拒收的形状与解码的形状是同一个（12 条），Latin-1 还原解出原值（4 条）、解不了的 6 种字节与 U+00FF 之外的字符。
  - 门控用例 `S3MetadataRoundTripTests`：往返的一组值里 `=?UTF-8?B?YQ==?=` 换成 `=?x?=`（编码写出，RustFS 上往返）；新增 encoded-word 形状的值被拒、什么都不写，别的写入方原样写进头的 UTF-8 字节读得回原值（`Utf8HeaderHttpClientFactory` 发出原始字节）。
  - 改实现之前（不含依赖新内部成员的 `S3MetadataHeaderTests`）新增与改过的线上用例里有 22 条失败。
  - 本机对 RustFS 1.0.6（本机镜像的临时容器，测完即删）跑全部 `ObjectStorage.S3.Tests`（含 ADR-0344 的改动）：483 条，0 失败，只跳过 `XIHAN_TEST_S3_UNCONDITIONAL` 那 1 条。写入的用例一度把 `=?x?=` 这类值改为原样写，正是这次门控运行发现 RustFS 拒收（备选 8）。
- **文档**：S3 包 README 已改；文档站的 `object-storage/advanced`、`packages/objectstorage-s3`、`packages/objectstorage-abstractions` 与更新日志待改。
- **没有解决的**：
  - Amazon S3 上没有实测；`MetadataTooLarge` 与 encoded-word 形状的两条规则照它的文档定。
  - 仍有一处可能的缺口（写进了规范）：以空格开头或结尾的只有 ASCII 的值，Provider 编码之后写出，Amazon S3 若先解码、存下原值并原样返回，HTTP 去掉首尾的空白，读回的少了它们；RustFS 不受影响。要不要同样拒收由仓库所有者定。
  - 只有 ASCII 的值里有制表符（别的写入方原样写下）时照旧原样交出，含控制字符；拍板是「纯 ASCII 的值不变」，没有改。
