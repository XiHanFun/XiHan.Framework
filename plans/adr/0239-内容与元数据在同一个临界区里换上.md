# ADR-0239 内容与元数据在同一个临界区里换上

## 状态

已采纳（修正 ADR-0183 的实现；RFC-0012「Provider」的条文不变：写入先落临时文件再原子替换，`ETag` 是内容的 SHA-256）。

## 日期

2026-11-18

## 背景

在负载下验证 ADR-0238 时，`FileSystemQuotaConcurrencyTests.ConcurrentOverwritesOfOneKey_CountTheBytesThatAreActuallyOnDisk` 偶发失败：并发覆盖同一个键的两个写入中有一个返回 `OBJECTSTORAGE_UNAVAILABLE_001`（`reason=System.UnauthorizedAccessException`），栈指向 `FileSystemBlobStore.CommitAsync` 换上元数据的 `File.Move(metaTemporary, metaPath, overwrite: true)`。

根因在实现：

- ADR-0183 把内容的改名与记账放进配额锁，写元数据留在锁外。`CommitAsync` 换上内容、出锁，再写元数据的临时文件并替换上去。
- 两个写入方的元数据改名因此能同时替换同一个目标。Windows 上同时替换同一个目标的改名，后到的以拒绝访问失败。这时内容已经换上、用量已经记上，调用方拿到的却是失败。
- 两次元数据改名的先后也不受内容替换次序的约束。先换上内容的写入方可能后换元数据，盘上留下另一个写入方的内容和它自己的长度、`ETag`。读取方拿到的长度与 `ETag` 对不上内容，条件请求和完整性校验都会出错。
- 删除也一样：内容在锁里删，元数据在锁外删。并发的覆盖能在两步之间换上内容与元数据，接着它的元数据被删除方删掉，留下没有元数据的新内容。读取时按文件信息补出内容类型与 `ETag`，自定义元数据丢失。
- 与配额无关：用例的总配额是 1 GiB。

复现：

- 本机实测：4 个线程对同一个目标反复替换改名，8000 次里 894 次拒绝访问。
- 原用例在后台 24 路持续写盘的负载下 60 次失败 4 次，都是拒绝访问；无负载时通过。
- 新增用例 `ConcurrentOverwritesOfOneKey_KeepTheMetadataOfTheContentOnDisk`：时钟让先放行的写入方停在提交途中取修改时间的那一下，等另一个写入方走完再让它继续。修之前每次都失败：盘上是后者 200 KiB 的内容，元数据记的是前者的 100 KiB。
- 删除的那一条没有确定的复现：删内容与删元数据之间没有能让删除方停住的位置。它与覆盖是同一个不变量，一并修正。

元数据紧跟内容换上之后，全量测试里 `BlobStoreConformance.Put_WithoutOverwrite_IsAtomicUnderConcurrentWriters` 偶发一次：8 个不覆盖的写入里有一个得到 `OBJECTSTORAGE_UNAVAILABLE_001`（`reason=System.IO.IOException`），不是 `OBJECTSTORAGE_CONFLICT_001`。原因是读元数据的另一个老问题，这次修正让它更容易碰上：

- 改名让新名字出现之后、关掉句柄之前，改名的句柄还带着删除权限。`ReadMetadata` 用 `File.ReadAllBytes` 打开，只容许读共享，这一刻打开就以共享冲突失败。
- 以前元数据比内容晚换上，后到的写入方先查是否存在时多半只看到内容、按文件信息补出元数据，不去打开元数据文件；现在两者紧挨着换上，后到的写入方正好在改名的那一刻打开它。
- 本机实测：改名的同时打开新名字，只容许读共享时 3000 次里 42 次共享冲突，容许读与删除共享时 0 次。
- 新增用例 `Head_WhileTheRenameThatPutTheMetadataInPlaceStillHoldsIt_ReadsIt`：以带删除权限、容许任何共享的句柄占着元数据文件，模拟改名还没关掉的句柄，再读元数据。修之前确定失败（`reason=System.IO.IOException`）；只在 Windows 上运行。

## 备选

1. **遇到拒绝访问有界重试**：否决。它只消掉写入方之间的拒绝访问，元数据与内容的次序仍然可能不一致。重试放在锁外照样乱序，放在锁里就要在锁里等待。
2. **按键加锁**：否决。内容替换必须和记账一起在配额锁里，按键的锁只能套在外层，还要一张有界的锁表或分段锁。收益只是不同键的写入少排两次改名的队，而改名本身是元数据操作，不值得多一层锁。
3. **元数据也进配额锁，紧跟内容换上，元数据的临时文件仍在锁外写**：采纳。

## 决策

1. `CommitAsync` 在锁外取修改时间，把元数据写到同目录的临时文件，然后进配额锁。锁里先换内容，不覆盖时由它原子判定谁占到位；接着换元数据。记账也在同一个临界区里。
2. 没占到位（`OBJECTSTORAGE_CONFLICT_001`）时不换元数据。换上内容之前的任何失败（含取消）原样释放预留；没换上去的元数据临时文件在 `finally` 里删掉。
3. 删除时元数据文件也在删内容的同一个临界区里删。
4. 锁里仍然只有改名、删文件与量长度这几个元数据操作，复制与写文件都在锁外。ADR-0183 第 4 条的范围因此多了元数据的改名与删除。
5. 读元数据时打开文件容许读与删除共享（`FileShare.Read | FileShare.Delete`），与读内容一致。替换照样替换不了正被打开的文件，容许删除共享不会让写入方更容易失败。

## 理由

内容与元数据在同一个临界区里成对变更，各写入方与删除方按进锁的次序依次生效，最后进锁的一方同时决定盘上的内容与元数据。同一个进程里也不会再有两个改名同时替换同一个元数据文件。读取方容许删除共享之后，改名留下的句柄不再让它失败，并发的不覆盖写入照旧只得到成功或冲突。

## 影响

- 行为：
  - 并发覆盖同一个键时都成功，留下的元数据属于盘上的内容。
  - 覆盖与删除同一个键时，结果要么是对象已删除，要么是覆盖写入的内容带着它自己的元数据。
- 配额锁里多了一次改名，删除多了一次删文件，持有时间约为原来的两倍，仍然只有元数据操作。
- 元数据的修改时间取自进锁之前，比换上的那一刻早一点，差的是写元数据临时文件与等锁的时间。
- 下列限制与以前相同，不在本次范围：
  - Windows 上替换不了正被打开的文件，打开时带 `FileShare.Delete` 也不行（本机实测）。读取方正打开着元数据（读元数据的一瞬）或内容（下载期间）时，覆盖的替换以拒绝访问失败。若内容已换上而元数据没换上，调用方拿到 `OBJECTSTORAGE_UNAVAILABLE_001`，元数据仍是旧的。
  - 读取先读元数据再打开内容，两步之间被覆盖时，读到的元数据与内容可能不是同一版。
  - 进程在写好元数据临时文件之后、换上之前崩溃，临时文件会留在 `meta` 目录里；启动扫描只清内容目录。
  - 多个进程共享目录时锁只在进程内，次序与配额一样只是近似。
- 公开 API 不变。
- 测试：两个新增用例修之后都确定通过；在同样的负载下，原用例 60 次全过，覆盖的新增用例 60 次全过，整个测试类 20 次全过。
