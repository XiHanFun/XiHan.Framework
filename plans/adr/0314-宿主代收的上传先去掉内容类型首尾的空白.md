# ADR-0314 宿主代收的上传先照 RFC 9110 去掉 Content-Type 首尾的空白

## 状态

已采纳（规范 RFC-0012「范围读取、分片上传与预签名」的宿主代收发一条与状态行已改；`Hosting.AspNetCore` 的 `BlobEndpointRouteBuilderExtensions` 上传端点先去掉 `Content-Type` 首尾的空格与制表符，再与签名比较、核对文法与写入；公开面、错误码、消息键与向量不变）。

## 日期

2026-11-26

## 背景

ADR-0308 实测：Kestrel 在把请求交给应用之前，已经照 RFC 9110 §5.5 去掉请求头首尾的空白；进程内的测试服务器（`Microsoft.AspNetCore.TestHost`）原样转交。所以签名没限定内容类型时，以空格结尾的 `Content-Type`（`text/plain; `）经 Kestrel 存成 `text/plain;`，经测试服务器回 400（`OBJECTSTORAGE_VALIDATION_006`）。ADR-0308 备选 7 当时没有改端点，留进「待定」；仓库所有者已拍板：代收上传的端点在核对之前自己去掉 `Content-Type` 的首尾空白，各宿主结果一致。

查清端点读了哪些请求头：

- 上传（`PUT`）：只读 `Content-Type`（`HttpRequest.ContentType`）。签名限定了内容类型时与它比较（不区分大小写），没限定时它是对象的内容类型，先经 `BlobPutOptions.IsValidContentType` 核对；为空白时取缺省的 `application/octet-stream`——判空用的是 `string.IsNullOrWhiteSpace`，即 .NET 的 Unicode 空白，不是 HTTP 的空白。请求体的长度由服务器按 `Content-Length` / 分块读，端点不读这两个头。
- 下载（`GET`）：只读 `Range`，经 `HttpRequest.GetTypedHeaders().Range`，ASP.NET Core 的头解析器跳过值首尾的空白（本 ADR 的用例实测：测试服务器原样转交的 ` bytes=2-4\t` 读成 `bytes=2-4`）。
- 签名的各项（过期时刻、限定的内容类型、文件名、分片、实例名、签名本身）都在地址的查询串里，不是请求头；`x-store` 也是查询参数。

## 备选

1. **端点先去掉 `Content-Type` 首尾的 OWS 再用**：采纳（拍板）。RFC 9110 §5.5 规定字段值不含首尾空白、收的一方在求值之前先去掉它；§5.6.3 的 OWS 是空格与制表符。去掉之后的值用于全部三处：与签名限定的值比较、核对文法、写进对象。
2. **只去结尾的空白**：否决。开头的空白同样不是字段值的一部分，Kestrel 也会去掉；只去一头，同一个请求在两种宿主上仍会不同。
3. **按 .NET 的 `Trim()` 去掉所有 Unicode 空白**：否决。不换行空格、控制字符不是 HTTP 的空白，是值里的字符：照文法它们不合法，应当回 400，不该被悄悄去掉之后照存。
4. **判空的口径跟着改成「去掉 OWS 之后为空」**：采纳。以前 `string.IsNullOrWhiteSpace` 把只有不换行空格等空白的值当作没给，存成缺省的内容类型；现在只有空格与制表符的值当作没给，别的空白留在值里、不合文法回 400。Kestrel 缺省只按 ASCII 读请求头的值，不换行空格这类非 ASCII 字节通常到不了端点（本 ADR 没有另行实测）。
5. **改在宿主层（中间件）统一去掉所有请求头的空白**：否决。端点只读这一个头，`Range` 的解析器已经照 HTTP 语义处理；在中间件里改写请求头会影响应用自己的端点，超出本端点的职责。
6. **签名比较之前不去空白（只在核对文法前去）**：否决。签名限定的内容类型不会以空白开头或结尾（`BlobUrlRequest.ForUpload` 拒收），客户端照签出的头原样发送；同一个值经 Kestrel 能比较通过、经测试服务器比较不通过，正是这次要消除的不一致。
7. **版本级别**：MINOR，写明。RFC-0012「标识」已经写明 HTTP 的字段值不含首尾空白、收的一方要先去掉；端点以前没有照做，宿主之间结果不一。变化只在不去空白的宿主上可见：以空格或制表符开头、结尾的 `Content-Type` 由 400 变为按去掉之后的值写入（更宽）；只有不换行空格等非 HTTP 空白的值由写入缺省类型变为 400（Kestrel 缺省不收这类非 ASCII 的值，见备选 4）。

## 决策

1. RFC-0012「范围读取、分片上传与预签名」的宿主代收发一条写明（MINOR）：端点照 RFC 9110 §5.5 先去掉 `Content-Type` 首尾的空格与制表符再用；签名限定了内容类型时以去掉之后的值与它比较；没限定时去掉之后为空即当作没给（取缺省的 `application/octet-stream`），否则以去掉之后的值核对文法、写入；别的空白留在值里；端点读的请求头只有上传的 `Content-Type` 与下载的 `Range`，`Range` 经宿主的头解析器本来就去掉首尾空白，签名各项在查询串里。
2. `BlobEndpointRouteBuilderExtensions.UploadAsync` 以私有的 `FieldValue` 取 `Content-Type`：`Trim(' ', '\t')`，没有这个头为空串；比较、核对与取用都用它，判空改为长度为 0。
3. 下载端点不改。

## 理由

- 字段值的首尾空白不属于值，这是 HTTP 的语义，与哪个服务器托管端点无关；端点自己照做，Kestrel、测试服务器与别的宿主收到同一个请求时结果相同。
- 只去 OWS，不扩大到 Unicode 空白：去掉的是协议规定不属于值的字符，其余照文法判，不把不合法的值变成合法的。

## 影响

- **公开 API**：无（`PublicAPI.Unshipped.txt` 无改动）。
- **行为**：
  - Kestrel 上没有变化：交给端点的值本来就去掉了首尾空白（ADR-0308 实测）；非 ASCII 的值见备选 4。
  - 不去空白的宿主（进程内的测试服务器等）上：`text/plain; `、`\ttext/plain;\t`、`  text/plain \t ` 存成 `text/plain;`、`text/plain;`、`text/plain`，不再回 400；签名限定 `text/markdown` 时 ` text/markdown\t` 通过验签；只有空格与制表符的 `Content-Type` 照旧存成缺省类型；只有不换行空格的 `Content-Type` 由写入缺省类型改为 400（`OBJECTSTORAGE_VALIDATION_006`）。
  - ADR-0308 决策 5 里「签名没限定内容类型、端点收到以空格结尾的 `Content-Type` 时回 400」由本 ADR 修订为按去掉之后的值写入；以空格结尾的内容类型仍不合文法（`BlobPutOptions`、`BlobUrlRequest.ForUpload` 照旧拒收），只是它到不了端点的核对。
- **规范**（规范仓库已改，指针待更新）：RFC-0012 一节（MINOR）。不加向量：只有 .NET 的 `Hosting.AspNetCore` 实现这个端点，去掉 OWS 是一行规则，由它自己的测试核对。
- **测试**（`ObjectStorage.FileSystem.Tests` 的 `HostedBlobUrlTests`，用测试服务器的 `SendAsync` 直接填请求，请求头原样到达端点；HttpClient 会改写解析得了的值、拒收首尾的空白与制表符，不用它）：
  - 原来的 `Uploads_WithoutASignedContentType_RejectATrailingSpaceThatReachesTheEndpoint`（ADR-0308）改为 `Uploads_WithoutASignedContentType_DropTheWhitespaceAroundTheRequestContentType`：四种首尾带空格、制表符的写法 200，存的是去掉之后的值。
  - 新增：签名限定内容类型时去掉空白之后比较（`text/markdown;` 仍 403）；只有空格与制表符存成缺省类型，不换行空格开头或结尾的回 400、不写入；下载的 `Range` 首尾带空白照常 206。
  - 改实现之前 6 条失败。
- **文档**：文档站的 `packages/hosting-aspnetcore`、`object-storage/advanced`、`appendix/spec` 与更新日志待改。
