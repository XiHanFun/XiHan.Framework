# ADR-0132 启动请求的子流程字段只由引擎设置

## 状态

已采纳（规范 `rfcs/0021-workflow.md` 的 `StartAsync` 一条补充）。

## 日期

2026-11-11

## 背景

P5-05 的 API 审查发现，`WorkflowStartRequest` 的 `InstanceId`、`ParentInstanceId`、`ParentNodeInstanceId` 与 `Depth` 是公开的 `init` 属性。注释写的是「子流程用」，但公开的 `IWorkflowEngine.StartAsync` 照样接收，引擎在 `CreateInstanceAsync` 里原样写进新实例。后果有两个：

- 同分区的调用方可以伪造父链接。子实例到达终态时，引擎经 `NotifyParentAsync` 以 `SubWorkflow` 书签恢复父节点；伪造的父链接让它去恢复别人的子流程书签。
- 引擎只校验 `Depth` 不超过 `MaxSubWorkflowDepth`，负值能绕过嵌套上限。

框架、BasicApp 与示例都没有在引擎之外给这四个字段赋值。子实例由 `WorkflowSession.ScheduleChildren` 用 `with` 填好这些字段后交给引擎的内部启动路径，自定义活动经 `ActivityOutcome.CompleteWithChildren` 只给定义名、变量与关联 ID。

## 备选

1. **保留公开字段，公开入口校验它们必须为空**：字段公开却永远不能用，契约自相矛盾；要拒绝还得再加一个错误码。否决。
2. **改成 `internal`**：采纳。

## 决策

- 四个属性改为 `internal init`，只由引擎（`WorkflowSession.ScheduleChildren`）为子流程设置。
- `Workflow.Abstractions` 的 PublicAPI 去掉这八行访问器。
- 测试 `WorkflowStartRequestTests` 核对四个属性的访问器都不公开；子流程的父子链接继续由一致性套件的 `SubWorkflow_AndForEach_RunChildren` 覆盖。

## 影响

- 破坏性：在引擎外给这四个字段赋值或读取它们的代码编不过；框架与 BasicApp 里没有这样的代码。`Workflow.Abstractions` 是 `Preview`，GA 前修改，不需要登记豁免（ADR-0131）。
- 指定实例 ID 的需求：应用要幂等启动，用 `CorrelationId` 与 `ReusePolicy`。
