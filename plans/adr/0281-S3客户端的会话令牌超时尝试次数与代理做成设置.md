# ADR-0281 S3 客户端的会话令牌、超时、尝试次数与代理做成设置

## 状态

已采纳（`ObjectStorage.S3` 的选项、命名实例的设置、建客户端的一步与过出站地址策略的传输已改；规范 RFC-0012、RFC-0014、RFC-0016 已补；命令行知识库的配置索引已补）。

## 日期

2026-11-24

## 背景

- ADR-0266 把 `S3BlobStore` 的公开构造收掉，公开面上不再有 AWS SDK 的类型。它的「影响」留了一条待定：选项表达不了的四样（临时凭据的会话令牌、请求超时、重试次数、HTTP 代理），缺省实例还能靠应用向容器注册自己的 `IAmazonS3` 解决，命名实例（`BlobStores` 按定义建的）没有任何途径——以前是经公开构造给第二个存储包一个配好的客户端。
- 这四样在 SDK 里的缺省（以当前引用的 SDK 实测）：
  - 凭据：两项密钥都给了是静态凭据，都没给走默认凭据链；没有令牌。
  - 超时：S3 的客户端配置把 `Timeout` 设成 SDK 允许的最大值（约 24.8 天），等于不设。
  - 重试：标准重试模式，首次之外再试 2 次。
  - 代理：SDK 自己的传输不设代理时用系统代理（环境变量）；命名实例用的是过出站地址策略的传输（ADR-0117），`OutboundAddressPolicy.Apply` 把代理关掉——经代理时连接回调看到的是代理的地址，查不到真正的目标。
- 核对超时的路径时发现一处对不上：RFC-0012 写「SDK 超时 → `OBJECTSTORAGE_UNAVAILABLE_001`」，`S3BlobStore` 判存储故障时认的是「调用方没取消的 `OperationCanceledException`」，而 SDK 在单次请求超时后抛出的是 `TimeoutException`（内层才是取消）。以前超时实际到不了（24.8 天），这个缺口没有暴露；超时一旦可配，它就会把异常直接抛给调用方。

## 备选

1. **公开一个收 SDK 配置的回调（`Action<AmazonS3Config>`）或工厂**：否决。这正是 ADR-0266 收掉的东西，SDK 的类型回到公开面。
2. **键名 `MaxRetries`（首次之外的重试次数，0 即不重试）**：否决，采纳 `MaxAttempts`（含首次的总次数，1 即不重试）。
   - 决定里要求「非正即失败」。按重试次数计，0 是合理的取值（外层自己有重试、或要快速失败），拒绝它就没法关掉重试；按总次数计，非正本来就没有意义，1 表达不重试。
   - AWS 自己的共享配置与环境变量用的也是总次数（`max_attempts`、`AWS_MAX_ATTEMPTS`），本仓库消息与发件箱的同类键也叫 `MaxAttempts`。
3. **超时与尝试次数给框架自己的缺省值（如 100 秒、3 次）**：否决。决定是「不配置时与今天一样」。给超时一个缺省值会让今天能传完的大对象在升级后被掐断；尝试次数的缺省还受 SDK 的环境变量与共享配置影响，写死一个数就盖掉了它们。
4. **超时与尝试次数不设上限**：否决。命名实例的设置可以由租户填写（ADR-0117、ADR-0178）；尝试次数乘上退避就是一次调用占住的时间。
5. **代理写成一个地址（`ProxyUrl = http://user:pass@host:port`）**：否决。口令混在地址里，打印与报错只能整串遮蔽，排查时连主机都看不到；分成四项后主机与端口照常打印。也因此 `ProxyHost` 不收带用户信息的写法，报错不回显原值。
6. **命名实例不许配代理，或要运营方另开一个开关（仿 `NamedInstancesUseAmbientCredentials`）**：没有采纳，见决策 6 与「待定」。决定是缺省实例与命名实例都要能配；代理的地址照样过策略，本进程建出的连接没有一条绕过它。
7. **命名实例配了代理就不再过策略**：否决。代理的主机与端口同样可能是租户填的，不过策略就等于给了一个指哪连哪的入口。
8. **经代理时先把端点解析一遍、按策略核对**：否决。真正去解析与连接的是代理，本进程查一遍挡不住 DNS 重绑定（策略自己的说明里就写了「只查 URL 或事先解析一次都会被绕过」），还会让人以为查过了。
9. **成组的设置只给一部分时照能用的用**（有令牌没密钥就退回凭据链，有主机没端口就不走代理）：否决，是静默兜底。配置的人以为生效了，实际用的是另一个身份、另一条路。
10. **绑定不加 `sessionToken` 属性**：否决。绑定给出的是一组凭据，两项密钥能由绑定覆盖而令牌不能，临时凭据就没法随绑定下发。
11. **代理的用户名照常打印**：否决。它与代理口令是一对登录凭据，RFC-0014 规则 2 对登录用户名的处理是一同遮蔽。
12. **配置错误抛 `FrameworkException`**：没有照做。全仓的配置错误都是 `ArgumentException`（ADR-0255 的 `ConfigurationValues`，本包的 `HealthBucket` 与布尔键也是），命名实例的 Provider 靠接住它把定义错误翻译成 `OBJECTSTORAGE_VALIDATION_003`；换一种异常这条翻译就断了，还要为配置错误另登记错误码。
13. **同时去掉「应用向容器注册自己的 `IAmazonS3` 时沿用」**：这次不做，见「待定」。
14. **连带把连接超时、重试模式、代理绕过名单、HTTPS 或 SOCKS 代理也做成键**：不做。决定只有四样；键进了 `Stable` 的选项就要守到下个大版本。

## 决策

1. **`S3ObjectStorageOptions` 新增七个成员**，配置节 `XiHan:ObjectStorage:S3` 与命名实例的设置用同名的键，都不写时建出的客户端与以前相同：

   | 成员 | 键 | 取值 | 不写时 |
   | --- | --- | --- | --- |
   | `SessionToken` | `SessionToken` | 字符串 | 没有令牌 |
   | `RequestTimeout` | `RequestTimeoutSeconds` | 正的秒数，可带小数，不超过 86400（`MaxRequestTimeout`） | 不另设时限 |
   | `MaxAttempts` | `MaxAttempts` | 1 到 10（`MaxAttemptsLimit`） | SDK 的缺省 |
   | `ProxyHost` | `ProxyHost` | 主机名或 IP 字面量 | 不设代理 |
   | `ProxyPort` | `ProxyPort` | 1 到 65535 | — |
   | `ProxyUserName` | `ProxyUserName` | 字符串 | 代理不带凭据 |
   | `ProxyPassword` | `ProxyPassword` | 字符串 | — |

   - 字符串键空白不算给出（同 `AccessKey`）；数值键写了就必须合法，空串也不行（同 `ConfigurationValues`）。
   - `RequestTimeout` 是单次 HTTP 请求的超时，每次尝试各算各的，交给 SDK 作底层 `HttpClient.Timeout`。
   - `MaxAttempts` 含首次；交给 SDK 时减一（它记的是重试次数）。
   - `ProxyHost` 不带协议、端口、路径与用户信息，也不收带区域标识的 IPv6 地址（SDK 拼地址时会把区域丢掉）；IPv6 字面量带不带方括号都收，交给 SDK 时补上。
2. **成组的设置必须给全**，读完选项（绑定覆盖之后）即核对，手工构造的选项在建客户端时核对：
   - `SessionToken` 要有 `AccessKey` 与 `SecretKey`。
   - `ProxyHost` 与 `ProxyPort` 成对；`ProxyUserName` 与 `ProxyPassword` 成对，且只能跟着代理给。
3. **配置错误的处置同 `HealthBucket`**：抛 `ArgumentException`，缺省实例装配失败，命名实例返回 `OBJECTSTORAGE_VALIDATION_003`。消息带完整的键名；数值键带原值，`SessionToken`、`ProxyHost`、`ProxyUserName`、`ProxyPassword` 的值从不进消息。
4. **绑定 `objectstorage` 新增属性 `sessionToken`**，与其余属性一样逐项覆盖配置节，空白不算给出。
5. **凭据的遮蔽**：`SessionToken`、`ProxyUserName`、`ProxyPassword` 在 `ToString()` 里打印为 `***`，其余新成员照常打印。RFC-0014「选项里的凭据」把 `ProxyUserName` 列入登录用户名，架构测试 `CredentialRedactionTests` 的用户名规则随之加上它。
6. **命名实例的代理过出站地址策略**：`S3OutboundHttpClientFactory` 在 `Apply` 之后，实例自己配了代理才重新打开代理。
   - 本进程建的每条连接仍经策略的连接回调，此时它看到并核对的是代理的地址；代理落在被拒绝的地址上与端点被拒绝同样处理（不建连接，读写返回 `OBJECTSTORAGE_UNAVAILABLE_001`）。
   - 端点由代理去解析、去连，本进程的策略管不到；要限制经代理能到的目标，在代理上做。
   - 没配代理的命名实例照旧不用系统代理；缺省实例的端点与代理都是运维配的，不过策略。
7. **建客户端的一步拆成可单独核对的两段**：`S3ObjectStorageFeature.CreateClientConfig`（选项 → SDK 的配置）与 `CreateCredentials`（选项 → 凭据），都是 internal；`CreateClient` 用它们。没给的设置一个字段都不碰。
8. **SDK 的请求超时归为存储故障**：`S3BlobStore` 与条件写入探测判存储故障时加上 `TimeoutException`。读写返回 `OBJECTSTORAGE_UNAVAILABLE_001`；探测撞上超时与连不上一样是尚未确认，照常启动或建出实例、后台重试。

## 理由

- 四样都是「连得上、连得稳」的前提，不该以依赖 SDK 的类型为代价；做成设置之后缺省实例与命名实例用同一套键，文档只讲一遍。
- 不写即不变：升级不改变任何现有部署的行为，新键只对写了它的人生效。
- 成对的键给不全就拒绝：这类错误在启动或登记时暴露，比运行中用错身份、走错路要便宜得多。
- 策略守的是「本进程向哪里建连接」。经代理时这个问题的答案就是代理，所以查代理；目标交给代理，是这类策略本来的边界，写明比假装查过要好。

## 影响

- **公开 API**（`PublicAPI.Unshipped.txt` 已同步，全部是新增）：`S3ObjectStorageOptions` 的 `SessionToken`、`RequestTimeout`、`MaxAttempts`、`ProxyHost`、`ProxyPort`、`ProxyUserName`、`ProxyPassword`，静态只读字段 `MaxRequestTimeout` 与常量 `MaxAttemptsLimit`。公开面仍没有 SDK 的类型（`S3PublicSurfaceTests` 照旧通过）。
- **行为变化**：
  - 不写新键的部署没有变化。
  - 单次请求超时（只有配了 `RequestTimeoutSeconds` 才会发生）返回 `OBJECTSTORAGE_UNAVAILABLE_001`，条件写入的探测撞上它与连不上一样是尚未确认、记 Warning。按原来的判定，前者会以 `TimeoutException` 抛给调用方，后者会落到「探测意外失败」（Error 日志）；超时以前到不了，所以不算对现有部署的变化。
  - 命名实例的定义里出现新键不再是「未知的设置键」；`ToString()` 多打印七个成员。
- **`RequestTimeoutSeconds` 管不到的**：它是 `HttpClient.Timeout`，下载的内容流交给调用方之后的读取不在其内；单次探测的超时仍是 `HealthProbeIntervalSeconds`，两者取先到的。
- **规范**（规范仓库已改，指针待更新）：
  - RFC-0012「S3 Provider」新增「客户端的设置」一条，配置键的清单补上新键；「命名存储实例」写明命名实例配了代理时过策略的是代理的地址。
  - RFC-0016 的 Provider 对照表：`ObjectStorage.S3` 的属性补 `sessionToken`。
  - RFC-0014「选项里的凭据」：登录用户名的属性名补 `ProxyUserName`，`S3ObjectStorageOptions` 的遮蔽成员补三项。
- **命令行知识库**：`Knowledge/configuration.json` 的 `XiHan:ObjectStorage:S3` 一节补七个键（区间由 `KnowledgeConfigurationTests` 逐键核对）；包与清单索引没有变化。`ConfigSecretScanner` 的凭据名规则已经认得 `SessionToken` 与 `ProxyPassword`，生成 ConfigMap 时带值的这两个键照样被拦下。
- **测试**（都不需要 S3 服务）：
  - 选项到客户端配置：两个来源（配置节、命名实例的设置）各走一遍；不写时与一份没动过的 SDK 配置逐项相同；四样落到 `Timeout`、`MaxErrorRetry`、代理地址与代理凭据、会话凭据上；上下限两侧、IPv6 主机、各键不合法的值、只给一部分的各种组合；绑定的 `sessionToken` 与覆盖之后的核对；临时凭据签出的预签名地址带令牌参数，静态凭据的不带（签名是本地计算）。
  - 凭据不外泄：`ToString()`、各种失败的异常消息、命名实例返回的错误与全部日志（消息加异常全文）里都没有令牌、代理用户名与口令。
  - 线上（真实的 SDK 与套接字，对端是本机回环上记录请求头的假对端）：经代理的每次尝试都是给代理的绝对地址请求、带令牌头、带对了的代理凭据恰好 `MaxAttempts` 次，不带凭据的代理同样承接请求；命名实例的代理落在策略拒绝的地址上时一条连接都不建；一次尝试即不重试；不应答的对端在 `RequestTimeoutSeconds` 之后以 `OBJECTSTORAGE_UNAVAILABLE_001` 结束（这条在改判定之前以 `TimeoutException` 失败）；探测撞上超时实例照常建出。缺省实例的传输与命名实例的传输各走一遍。
  - 对真实 S3 兼容服务的用例只在 CI 设了 `XIHAN_TEST_S3` 时执行，这次没有新增。
- **文档**：包 README 已补配置表；文档站的 `packages/objectstorage-s3`、`configuration/options`、`configuration/bindings`、`object-storage/advanced` 与更新日志待改。
- **待定**：
  - 命名实例的代理要不要另设运营方的开关（备选 6）。现在的边界是「代理的地址过策略、目标归代理管」：策略放行了一个内网代理的部署里，能填设置的人可以经它到达它能到的任何目标。
  - 是否去掉对容器里 `IAmazonS3` 的沿用（备选 13，ADR-0266 备选 11 的后半句）。四样做成键之后，它只剩「自定义凭据链」这类用处；去掉它才能把 SDK 的类型彻底挡在应用之外。
  - 缺省实例只给了 `AccessKey` 或 `SecretKey` 其中一项时仍是悄悄走默认凭据链（命名实例早已拒绝，ADR-0178）。这次新增的成组设置都拒绝半套，这一处是原有行为，没有动。
