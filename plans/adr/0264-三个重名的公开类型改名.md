# ADR-0264 三个重名的公开类型改名

## 状态

已采纳（内核 `PermissionGrant` 改名 `PluginPermissions`，`IAuthenticationHandler` 改名 `ICredentialHandler`、三个实现随之改名，`AuthorizationResult` 改名 `AuthorizationDecision`；纯重命名，成员与行为不变；都在 GA 前，不需要登记豁免；规范正文已补，见「影响」）。

## 日期

2026-11-24

## 背景

三个 `Stable` 的公开类型与别的类型同名，引用双方的文件要靠别名或全名才能编译：

- **`PermissionGrant` 有两个**：
  - `XiHan.Framework.Kernel.Plugins.PermissionGrant`（类）：宿主授予一个插件的权限集合，成员是 `Granted`、`IsGranted`、`Missing(manifest)`、`MissingConfigurationGrants(manifest)`、`Empty`。项是插件权限（`capability:kernel.pipeline`、`config:<配置节>`、`fs.read:<路径>`）。
  - `XiHan.Framework.Security.Abstractions.Permissions.PermissionGrant`（记录）：RBAC 的一条授予（主体、权限码、范围）。同一族的还有 `IPermissionGrantStore`、`IPermissionGrantAdministration`、`IPermissionGrantSource`、`PermissionGrantQuery`、`PermissionGrantPage`、`PermissionGrantRecord`、`PermissionGrantStoreConformance`。
  - 两者不是一回事：一个是集合，一个是一条；一个的项是插件权限，一个是权限码。同时管插件与授予的应用代码（如授予管理页里加载插件）两个都要用。
- **`XiHan.Framework.Security.Abstractions.Authentication.IAuthenticationHandler` 与 `Microsoft.AspNetCore.Authentication.IAuthenticationHandler` 同名**：前者把某一方案的凭据变成主体，后者是 ASP.NET Core 认证方案的处理器。`Hosting.AspNetCore` 的 `InvocationAuthenticationHandler` 两个都要用，只能写别名 `using CredentialHandler = …IAuthenticationHandler`。应用里凡是同时引用 `Microsoft.AspNetCore.Authentication` 与本包命名空间的文件都会遇到 CS0104。
- **`XiHan.Framework.Kernel.Security.AuthorizationResult` 与 `Microsoft.AspNetCore.Authorization.AuthorizationResult` 同名**：前者是 `IPolicy.EvaluateAsync` 的判定，后者是 `IAuthorizationService.AuthorizeAsync` 的结果。写了 `IPolicy` 又用到 ASP.NET Core 授权的文件同样 CS0104。
- 以 `System.Reflection.Metadata` 扫过 `Microsoft.NETCore.App` 与 `Microsoft.AspNetCore.App` 两个引用包的全部公开类型，与框架 1008 个公开类型比对，同名的列在「影响」；本 ADR 只处理上面三个。

## 备选

### 两个 `PermissionGrant` 改哪一个

1. **改安全的那个**（如 `Grant`、`PermissionAssignment`）：否决。它名副其实（一条权限授予），而且带着一族七八个同词的类型、RFC-0008 的术语、授予表的实体名与一致性套件，改它要么只改一个、破坏同词链，要么整族都改。
2. **改内核的那个**：采纳。它本来就名不副实（是集合不是一条），引用面只在三个插件宿主与 `PluginSource` / `PluginContext`。

### 内核的 `PermissionGrant` 叫什么

1. **`PluginPermissions`**：采纳。
2. **`PluginGrants`**：否决。与宿主选项的 `Grants` / `GrantsFor(manifestId)` 同词，但承载它的属性叫 `Permissions`（`PluginSource.Permissions`、`PluginContext.Permissions`），类型叫 `PluginGrants` 就得把这些属性一并改名，破坏面从一个类型名扩大到 `Preview` 的两个类型的成员。
3. **`GrantedPermissions`**：否决。与线协议 `Configure.granted_permissions` 同词，但不带领域词：它与 `PermissionGrant` 只是两个词换了顺序，放在一起仍然分不清哪个是插件的、哪个是 RBAC 的，正是这次要消除的问题。

### `IAuthenticationHandler` 叫什么

1. **`ICredentialHandler`**：采纳。
2. **`ICredentialAuthenticator` / `IAuthenticator`**：否决。`Authenticator` 在 WebAuthn 里是认证器（用户手里的设备），`Security.WebAuthn` 的文档与错误消息都在用这个词。
3. **`IAuthenticationSchemeHandler`**：否决。离 ASP.NET Core 的 `IAuthenticationHandler`、`IAuthenticationSchemeProvider` 更近了，不同名但更容易认错。
4. **`ICredentialValidator`**：否决。方法叫 `AuthenticateAsync`、产出是主体，不只是校验；`Validate` 在框架里指 Validate 阶段与请求校验。

### 实现类型要不要跟着改

1. **只改接口**：否决。`JwtAuthenticationHandler : ICredentialHandler` 留在那里，仓库里 `…AuthenticationHandler` 这个后缀就同时指两种东西：实现框架契约的（`Jwt…`、`ApiKey…`、`OpenIdConnect…`）与真正的 ASP.NET Core 处理器（`InvocationAuthenticationHandler`，继承 `AuthenticationHandler<TOptions>`）。
2. **三个实现一并改成 `…CredentialHandler`**：采纳。此后 `…CredentialHandler` 一律是框架契约的实现，`…AuthenticationHandler` 只剩 ASP.NET Core 的那一个。

### `AuthorizationResult` 叫什么

1. **`AuthorizationDecision`**：采纳。
2. **`PolicyDecision`**：否决。同样准确，但把名字绑在 `IPolicy` 上；它的输入叫 `AuthorizationRequest`，阶段叫 Authorize，要求叫 `AuthorizationRequirement`，换成 `Policy` 前缀就离开了这条同词链。
3. **`PolicyResult` / `PolicyOutcome`**：否决。`Result` 仍然与外层的 `Result<T>` 叠在一起（见「理由」）；`Outcome` 在框架里指调用的结果（`context.SetOutcome`）。

### 要不要留旧名

- **留 `[Obsolete]` 的旧名转发或 `global using` 别名**：否决。接口不能用类型转发改名，留一个继承新接口的旧接口会让同一个处理器可以按两个服务类型登记、其中一个不被管道认出；仓库的规矩也是破坏性变更写明迁移方式、不留兼容别名。

## 决策

1. `XiHan.Framework.Kernel.Plugins.PermissionGrant` 改名 `PluginPermissions`。`PluginSource.Permissions`、`PluginContext.Permissions`、两个宿主选项的 `Grants` / `GrantsFor` 不改名，只是类型换了。安全的 `PermissionGrant` 不动。
2. `XiHan.Framework.Security.Abstractions.Authentication.IAuthenticationHandler` 改名 `ICredentialHandler`。实现随之改名：
   - `Security.InMemory` 的 `ApiKeyAuthenticationHandler` → `ApiKeyCredentialHandler`
   - `Security.Jwt` 的 `JwtAuthenticationHandler` → `JwtCredentialHandler`
   - `Security.OpenIdConnect` 的 `OpenIdConnectAuthenticationHandler` → `OpenIdConnectCredentialHandler`
3. `XiHan.Framework.Kernel.Security.AuthorizationResult` 改名 `AuthorizationDecision`。
4. 都是纯重命名：命名空间、成员、级别、行为、错误码与消息键都不变；文件名随类型名改。不留旧名的别名或转发。
5. 不跟着改名的同组类型：`AuthenticationCredential`、`AuthenticationMiddleware`、`AuthenticationChallenge`、`AuthorizationRequest`、`AuthorizationRequirement`、`AuthorizationMiddleware`、`InvocationAuthenticationHandler`（它是 ASP.NET Core 的处理器，名字是对的）。消息键、错误码与配置节里没有带这三个旧名的。中文里仍称「认证处理器」「授权判定」。
6. `Hosting.AspNetCore` 里为避让重名而写的别名 `CredentialHandler` 删除，直接用 `ICredentialHandler`。

## 理由

- **`PluginPermissions`**：`Plugins` 是术语表的领域词，内核这个命名空间里的类型都以它起头（`IPlugin`、`PluginContext`、`PluginSource`、`PluginStatus`）；`Permissions` 是清单字段 `permissions`、线协议 `granted_permissions` 与承载它的属性用的同一个词。复数说明它是集合。它与清单里「声明的权限」的区别由成员（`Granted`、`IsGranted`、`Missing`）表达。
- **`ICredentialHandler`**：RFC-0008 的两个词——凭据与处理器。同组的名字已经在用「凭据」：`AuthenticationCredential`、`context.FindCredential()`、`SecurityErrors.InvalidCredential`；宿主里原先的别名也正是 `CredentialHandler`。
- **`AuthorizationDecision`**：与输入 `AuthorizationRequest` 成对（请求 → 判定），XML 文档与 RFC-0008 的中文本来就叫「判定」。`IPolicy.EvaluateAsync` 返回 `Result<AuthorizationDecision>` 之后两层各说各的：外层失败是判定不出（授予存储读不到，503），内层是允许或拒绝（ADR-0071）；原先的 `Result<AuthorizationResult>` 两层都叫结果。
- 三个新名字与两个引用包里的公开类型都不同名（同一次扫描核对过）。

## 影响

- 源码迁移（全是改名，查找替换即可）：
  - 插件：`PermissionGrant`（`XiHan.Framework.Kernel.Plugins`）→ `PluginPermissions`，如 `new PluginSource(dir, new PluginPermissions([...]))`、`PluginPermissions.Empty`。
  - 认证：`IAuthenticationHandler` → `ICredentialHandler`（实现类的基接口与 `AddSingleton<ICredentialHandler, …>()` 的登记）；直接引用内置处理器的地方 `ApiKeyAuthenticationHandler` / `JwtAuthenticationHandler` / `OpenIdConnectAuthenticationHandler` → `ApiKeyCredentialHandler` / `JwtCredentialHandler` / `OpenIdConnectCredentialHandler`（多为 `…SchemeName` 常量）。为避让重名写的 `using` 别名可以删掉。
  - 授权：`AuthorizationResult`（`XiHan.Framework.Kernel.Security`）→ `AuthorizationDecision`，如 `AuthorizationDecision.Allow()`、`ValueTask<Result<AuthorizationDecision>> EvaluateAsync(...)`。
- 行为：不变。三个内置处理器没有日志类别，改名不影响日志。
- ADR-0263 里的 `IAuthenticationHandler` 即这里的 `ICredentialHandler`。
- 规范（已补，规范指针 `c90faf8`）：RFC-0008 里的 `IAuthenticationHandler`（「认证」第 2 条、「绕过管道的端点」第 2 条）与 `AuthorizationResult`（「授权」第 7 条）改成新名字；内核的 `PermissionGrant` 在规范里没有出现，RFC-0008 里的 `PermissionGrant.AnyTenant` 指安全的那个，不改。
- 同一次扫描里还有这些同名，本 ADR 没有动，是否处理另行决定：
  - `Security.Abstractions` 的 `AuthenticationMiddleware`、`AuthorizationMiddleware`（`Stable`）与 ASP.NET Core 的同名中间件。两边的中间件类型应用代码都很少直接写出来，但它们与上面两个同属一组。
  - `Localization.Abstractions.LocalizationOptions`（`Stable`）与 `Microsoft.Extensions.Localization.LocalizationOptions`。
  - `Workflow.Abstractions.Activities.ActivityContext`（`Preview`）与 `System.Diagnostics.ActivityContext`。
  - `Hosting.CommandLine.Commands.ICommand`（`Preview`）与 `System.Windows.Input.ICommand`。
  - 框架内部：`PluginErrors`、`PluginMessages` 在 `Plugins.InProcess` 与 `Plugins.Protocol` 各有一个（都是 `Preview`）。
  - 只承载扩展方法的静态类（`ApplicationBuilderExtensions`、`LocalizationServiceCollectionExtensions`）同名无碍，没有人写它们的名字。
  - 扫描只覆盖两个引用包；`Security.OpenIdConnect` 的 `OpenIdConnectOptions` 与 NuGet 包 `Microsoft.AspNetCore.Authentication.OpenIdConnect` 里的同名类型不在范围内。
