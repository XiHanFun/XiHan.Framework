# ADR-0329 类型化请求与原始调用对称、写不出响应记日志与内核腾体积

## 状态

已采纳（规范 RFC-0011「校验」第 1 步、RFC-0001「写出与转交」里「为 Schema 校验把类型化的请求编成 JSON 的」一条与两个状态行已改；内核的 `ValidationMiddleware`、`OperationDescriptor` 写出用的序列化选项、`OperationInvoker` 的日志与 `ManifestReader` 的读取，`Caching.Abstractions` 的 `IdempotencyMiddleware` 的日志。公开 API、错误码、消息键、配置键与向量不变）；2026-11-27 由 ADR-0341、ADR-0342 修订：XGI 入口写不出响应时 Span 与指标记失败，写出先走快速路径、写不出再按元数据写（见文末「修订」）。

## 日期

2026-11-27

## 背景

仓库所有者拍板「先腾体积，两项都做」：

1. **体积**：性能门禁要求 `Primitives` 与 `Kernel` 两个 Release 程序集合计不超过 512000 字节（`framework/benchmarks/budgets.json`），主检出是 103424 + 408064 = 511488 字节，内核 `.text` 节几乎没有余量（主检出 0 字节，PE 文件按 512 字节一档），再加一点就越过一档。下面两项都要往内核里加代码。
2. **类型化请求与原始调用不对称**（ADR-0320 备选 13、15 留下的）：
   - 浮点成员是 NaN 或无穷时，类型化请求在 Validate 阶段为 Schema 校验编码，System.Text.Json 抛出 `ArgumentException`，按未处理的异常结束（`KERNEL_UNEXPECTED_001`，HTTP 500 一类）；原始调用里同样的内容（载荷里写 `NaN`）是 `KERNEL_VALIDATION_001`。
   - 嵌套 64 层、最里层有值的类型化请求同样按未处理的异常结束（System.Text.Json 写到上限那一层的值就失败）；原始调用里同样的 64 层读得进。
3. **写不出响应时没有日志**（ADR-0324 之后）：
   - 幂等记录写不出响应时，`IdempotencyMiddleware.Complete` 接住异常、换成 `KERNEL_UNEXPECTED_001`，Span 与指标记失败，但异常没有抛出管道，Observe 阶段不记日志。
   - XGI 入口（`OperationInvoker`）在管道结束之后编码，写不出时同样接住异常、不记日志。实测这时连 Span 与指标也是成功（`xihan.invoke` 的 `xihan.outcome` 为 `success`、状态 `Unset`）：编码在管道之后（RFC-0011 规则 10「编码」），Observe 阶段看到的是编码之前的结果。待办里写的「只在 Span 与指标里记失败」只对幂等那一处成立，XGI 入口一处什么记录都没有。
4. **实测发现响应一侧的同类缺陷**：`EncodeResponse` 照 ADR-0319 用深度上限放宽一层的选项副本写出，但序列化上下文的选项与生成时一致时（没有 `DictionaryKeyPolicy`、编码器、转换器等，多数应用的上下文都是这样），System.Text.Json 走源生成的快速路径：
   - 快速路径判断兼容时不比较 `MaxDepth`，副本照样走它；它对嵌套对象直接调生成的写法、不核对深度，遇到没有内联写法的成员（`int?` 这样的可空值等）再调 `JsonSerializer.Serialize`，用的是上下文自己的元数据与原选项的上限。
   - 结果：64 层、最里层是可空值的响应写不出（`JsonException`，包成 `ArgumentException`）；66 层以上由写出器抛出 `InvalidOperationException`，`EncodeResponse` 的「写不出只抛 `ArgumentException`」（ADR-0320）在这里不成立。
   - ADR-0319 的测试用的上下文带 `DictionaryKeyPolicy` 与扩展数据，走不到快速路径，所以没测出。照字面「参照 `EncodeResponse` 的做法」编码请求，同样的缺陷会带到请求一侧。

## 备选

体积（不改行为）：

1. **清单读取不再经源生成反序列化，形状核对之后按成员名直接从 `JsonElement` 取值**：采纳。
   - `ManifestShape.FindProblem` 已经按 Schema 核对过：没有未知成员、没有 `null`、类型与取值都对，成员名区分大小写，重复成员在更早的共同检查里拒绝。反序列化在这之后不会再失败，它做的只是把值搬进七个 internal 的 `*Document` 类型，再转成 `Manifest`。
   - 改成直接取值之后删掉 `ManifestJsonContext` 与七个 `*Document` 类型：源生成的上下文约 16.7 KB 的 IL 加上元数据，内核 `.text` 少 43736 字节。缺少的可选成员取 Schema 的缺省值，列表照旧是 `List<T>`，交出的 `Manifest` 与以前相同；清单向量与读取测试照过。
2. **把内核里的 Schema 校验、清单形状检查挪到更高的环**：否决。内核自己用（Validate 阶段、装配时读清单），照约定不为躲预算挪走内核需要的代码。
3. **再合并重复的私有辅助方法、改写生成的正则、压缩嵌入的语言文件**：不做。一处已经腾出四十多 KB，其余每处只有几百字节到两三 KB，改动面大；语言文件压缩还要加构建步骤。

类型化请求：

4. **浮点成员是 NaN 或无穷、超过序列化上下文的深度上限 → `KERNEL_VALIDATION_001` + `kernel.operation.invalid_payload`，`reason` 为 `$`**：采纳。
   - 实测原始调用：`{"ratio":NaN}`、`{"ratio":Infinity}`、`{"ratio":-Infinity}` 都是 `KERNEL_VALIDATION_001`、`reason` 为 `$`（JSON 没有这样的数，字面量是语法错误，共同检查报 `$`）；超过序列化上下文深度上限的载荷解码时同样报 `$`（ADR-0236）。
   - 与 ADR-0320 的孤立代理项同一个理由：请求是调用方的输入，报成服务端的缺陷（500）不对。
5. **`reason` 写成员的路径（如 `$.ratio`）**：否决。原始调用里同样的内容是 `$`；System.Text.Json 写不出 NaN 时抛的 `ArgumentException` 也不带路径。
6. **编不成的范围**：采纳「System.Text.Json 写出时抛出的 `ArgumentException`，以及包成 `ArgumentException` 的 `JsonException` 与被换成 U+FFFD 的字符」（`StrictJson.Serialize` 的口径，ADR-0320）。转换器自己抛出的 `ArgumentException` 一并算编不成；其余异常（`NotSupportedException`、`InvalidOperationException`、框架异常）是编程错误，照旧按未处理的异常结束。
7. **64 层：与写出响应同一份深度上限放宽一层的选项编码请求**：采纳。编出的文本不在编码处过共同检查，超过 64 层与重复成员照旧由 Schema 校验前的共同检查报出路径（ADR-0320 备选 13 的后半）。
8. **写出用的选项副本设缺省的编码器，绕开源生成的快速路径**：采纳，响应一侧一并修好。
   - 编码器不为空时 System.Text.Json 不走快速路径，按元数据写出，深度照副本的上限核对：64 层照写，65 层以上抛 `JsonException`（包成 `ArgumentException`），不再有 `InvalidOperationException`。
   - 原选项没有编码器时副本设成 `JavaScriptEncoder.Default`，与空编码器写出的字节相同（实测含 `<`、`>`、`&`、`'`、`"`、`+`、U+00E9、U+2028、U+0001、U+1F600 与 U+FFFD 的文本逐字节相同）；`StrictJson.HasReplacedCharacter` 把它当缺省编码器，不多写一遍。
   - 代价：按元数据写出比快速路径慢一些，XGI 入口本来就要对整段文本再过一遍共同检查。只生成快速路径的上下文（`GenerationMode = Serialization`）给不出元数据，响应与为 Schema 校验编码的请求都写不出、按未处理的异常结束（实测 `InvalidOperationException`）；以前照写。这样的上下文本来读不了原始调用的请求，幂等回放也读不回响应，记进 `EncodeResponse` 的 XML 文档。
9. **只在快速路径失败时换按元数据的写法再写一遍**：否决。多一条重试路径；接住的异常里分不清是深度还是转换器自己抛出的。
10. **只给请求一侧另建一份选项，响应一侧不动**：否决。同一个缺陷，ADR-0319 已定 64 层照写；两份选项还要各自缓存。

写不出响应的日志：

11. **XGI 入口与幂等记录写不出时各记一条 Error 日志**：采纳。级别与 Observe 阶段记未处理异常的那条相同；两处不会对同一次调用都记（幂等已把结果换成失败，XGI 入口不再编码）。
12. **模板只带操作 ID、调用的 Trace ID 与错误码，异常作为日志的异常参数**：采纳。不带响应的内容；异常的消息是 System.Text.Json 或 `StrictJson` 的说明（`JsonException` 带出错的路径，不带值），堆栈指出是哪个转换器写不出。
    - XGI 入口：`The response of operation '{Operation}' could not be written; invocation '{TraceId}' ends with '{Code}'.`，类别 `XiHan.Framework.Kernel.Operations.OperationInvoker`。
    - 幂等记录：`The response of operation '{Operation}' could not be written for the idempotency record; invocation '{TraceId}' ends with '{Code}', and retries replay it.`，类别 `IdempotencyMiddleware` 的全名。
13. **事件 ID**：照仓库现有的做法不显式指定（框架里的 `LoggerMessage` 都没有写 `EventId`），由生成器按方法名给出。
14. **幂等中间件的日志器在这条路径上从调用作用域取**（`context.Services.GetService<ILoggerFactory>()`）：采纳。
    - 不动 `Stable` 的 `IdempotencyMiddleware` 的构造（主构造函数，测试与应用直接 `new`）；它本来就从调用作用域取 `ISharedCache`。
    - 只在少见的写不出路径上取；手工装配、容器里没有日志工厂时不记（内核装配的应用总有，`AppBuilder` 补登记 `NullLoggerFactory`）。
15. **给 `IdempotencyMiddleware` 加一个带 `ILoggerFactory` 的公开构造**：否决。多一个公开构造，两个构造并存时容器按参数多的选，直接 `new` 的旧写法照样没有日志。
16. **XGI 入口改在管道里编码，让 Observe 阶段的 Span 与指标记下失败**：不做。RFC-0011 规则 10 定了编码在管道之后、中间件看到编码之前的结果；超出这次范围，记在「影响」的发现里。
17. **规范写日志**：不写。日志不是跨语言的契约，规范里也没有「只记 Span 与指标」这样要改的话。

## 决策

1. **规范**：
   - RFC-0011「校验」第 1 步：序列化器写不出的（浮点成员是 NaN 或无穷，超过序列化上下文的深度上限）同样以 `KERNEL_VALIDATION_001` 结束，`reason` 为 `$`，与原始调用里同样的内容相同；层数照原始调用的读取，64 层、最里层有值的请求编得出。
   - RFC-0001「写出与转交」的「为 Schema 校验把类型化的请求编成 JSON 的」一条同步；两个状态行各加一条，对应 ADR 加上本 ADR。
2. **内核**：
   - `ManifestReader` 在形状核对之后按成员名直接从 `JsonElement` 取值，删掉 `ManifestJsonContext` 与七个 `*Document` 类型。
   - `OperationDescriptor` 写出用的选项改名 `WriteOptions`（internal，以前是 `private protected` 的 `ResponseWriteOptions`），副本在原选项没有编码器时设 `JavaScriptEncoder.Default`。
   - `ValidationMiddleware` 用 `StrictJson.Serialize` 按 `WriteOptions` 的元数据编码类型化请求，接住 `ArgumentException` 即 `KERNEL_VALIDATION_001`、`reason` 为 `$`。
   - `OperationInvoker` 构造时取 `ILoggerFactory`，`ToResponse` 写不出时记 `LogUnwritableResponse`。
3. **`Caching.Abstractions`**：`IdempotencyMiddleware.Complete` 写不出时经调用作用域的 `ILoggerFactory` 记 `LogUnrecordableResponse`。

## 理由

- 类型化调用与原始调用是同一个请求的两种交法，同样的内容应当得到同样的结果；把调用方的输入报成 500，会让调用方以为是服务端的缺陷去重试。
- 写出用的选项是请求与响应共用的一份：缺陷在这份选项上，修在这里两边都对，不必留两份做法。
- 写不出的那一刻是唯一知道原因的地方；不留日志，排查只能从错误码倒推，而 XGI 入口一处连 Span 与指标都是成功。
- 体积在不改行为的前提下腾出：清单反序列化在形状核对之后只是搬值，换成直接取值是同一个结果，省下的余量足够这次与之后几轮在内核里加东西。

## 影响

- **公开 API**：不变。`OperationDescriptor.WriteOptions`（以前 `ResponseWriteOptions`）是 internal；`OperationInvoker` 是 internal，构造多一个 `ILoggerFactory`；`IdempotencyMiddleware` 改成 `partial`，签名不变。没有新的错误码、消息键与配置键，向量不变。
- **对已有部署与代码的行为变化（升级须知）**：
  - 带 Schema 的操作经类型化入口调用，请求里的浮点成员是 NaN 或无穷、或超过序列化上下文的深度上限时，结果是 `KERNEL_VALIDATION_001`（`reason` 为 `$`，HTTP 400 一类），不进 Handle；以前是 `KERNEL_UNEXPECTED_001`。64 层、最里层有值的请求照常执行；以前 `KERNEL_UNEXPECTED_001`。
  - 序列化上下文的选项与生成时一致（走源生成快速路径）时，64 层、最里层是可空值的响应照常写出，以前 XGI 入口以 `KERNEL_UNEXPECTED_001` 结束；66 层以上 `EncodeResponse` 抛 `ArgumentException`，以前抛 `InvalidOperationException`（经 XGI 入口的结果不变）。写出不再走快速路径，字节不变。
  - 只生成快速路径（`GenerationMode = Serialization`）的上下文用作响应或带 Schema 的请求时写不出，按未处理的异常结束；以前照写。迁移：去掉 `GenerationMode = Serialization`，用缺省的生成模式（同时生成元数据）。
  - XGI 入口与幂等记录写不出响应时各记一条 Error 日志（见备选 12）；以前没有。
- **规范**（规范工作区已提交）：RFC-0011「校验」第 1 步、RFC-0001「写出与转交」与两个状态行，MINOR（少了一种失败，不让任何互通失败；合规的对端照常读入）。
- **Go 一致性模块**：不变。
- **六个 SDK**：不受影响。Schema 校验是宿主能力，SDK 的类型化调用跳过 Validate 的解码、不编码请求（RFC-0011 规则 10）；日志各家自定。
- **测试**：
  - `ValidationMiddlewareTests`：带 Schema 的类型化调用，浮点成员是 NaN、正无穷、负无穷时与原始调用里的 `NaN`、`Infinity`、`-Infinity` 同为 `KERNEL_VALIDATION_001`、`reason` 为 `$`；64 层、最里层有值时两种调用都照常执行，65 层都是 `KERNEL_VALIDATION_001`、`reason` 为 `$`。夹具 `MeasureRequest` 的上下文走源生成快速路径。改之前 5 条失败。
  - `ResponseTextCheckTests`：原始调用读得进的 64 层经回声操作照常写出；`EncodeResponse` 写出的字节与按原选项写出的相同，65 层与 100 层只抛 `ArgumentException`。不设编码器时 3 条失败（含上一条的 64 层）。
  - `OperationTests`：XGI 入口写不出（NaN）时记一条 Error 日志，模板、类别与异常照上，Observe 阶段不记。
  - `IdempotentOperationReplayTests`：幂等记录写不出时首次调用记一条 Error 日志，重试回放、不再记。
- **体积**（工作区 Release 构建，按差值折成主检出口径）：
  - 工作区：Primitives 103424 → 103424 字节；Kernel 408576 → 364544 字节（`.text` 405528 → 361792 字节）。
  - 主检出口径：Kernel 408064 → 364544 字节（主检出的 `.text` 比工作区短 24 字节，基线正好压在一档上，现在同一档），合计 511488 → 467968 字节，距预算 44032 字节。
- **文档**：`Kernel` 与 `Caching.Abstractions` 的 README 已同步；文档站与更新日志由整合时补。
- **发现而没改的**（报告另列）：
  - XGI 入口写不出响应时，Observe 阶段的 Span 与指标记的是成功（编码在管道之后，RFC-0011 规则 10）；这次只加了日志（备选 16）。
  - 编码类型化请求时把转换器自己抛出的 `ArgumentException` 也当作编不成（备选 6）。

## 修订（2026-11-27）

1. **备选 16 与「发现而没改的」第一条由 ADR-0341 改定**：编码仍在其余中间件之后（RFC-0011 规则 10），但挪到 Observe 阶段的内置中间件里、定结果与结束 Span 之前；写不出时 `xihan.invoke` 状态 Error、说明 `KERNEL_UNEXPECTED_001`，`xihan.outcome` 与两个指标记 `failure`，与调用方拿到的一致。备选 11 的日志不变。
2. **决策 2 的「副本设 `JavaScriptEncoder.Default`、不走快速路径」与备选 8、9 由 ADR-0342 改定**：先照原选项的元数据写（能走快速路径就走），只在快速路径抛出的 `InvalidOperationException` 与包成 `ArgumentException` 的 `JsonException` 上按副本再写一遍；原选项的深度上限大于 64 时直接按副本写。写出的字节与写不出时的异常与本 ADR 相同；只生成快速路径（`GenerationMode = Serialization`）的上下文恢复能写，「影响」里对它的升级须知随之作废。
