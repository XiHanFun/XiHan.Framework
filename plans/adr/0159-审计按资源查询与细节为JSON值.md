# ADR-0159 审计按资源查询，细节统一为 JSON 值

## 状态

已采纳（RFC-0015）。

## 日期

2026-11-11

## 背景

API 审查第三节与第五节（`Auditing.Abstractions` 升 `Stable` 的前提）指出两处缺口：

- **查不到一个资源的历史**：`AuditQuery` 能按动作、主体、租户、trace-id 与成败过滤，没有资源。`SetAuditResource` 写进事件的 `xrn:` 资源名查不出来，而「这张订单被谁改过」正是审计最常见的问法。
- **细节的类型随存储不同**：
  - `AddAuditDetail(key, object?)` 收任意对象，事件的 `Details` 是 `IReadOnlyDictionary<string, object?>`。
  - 内存实现原样保留调用方的对象（`int`、`decimal`），数据库实现写成 JSON 后读回 `JsonElement`。
  - 同一段读细节的代码换个存储就要改，单元测试在内存上通过、上线到数据库就错。
  - 调用方之后改了传入的可变对象，已记下的细节也跟着变。

## 决策

1. **按资源过滤**：
   - `AuditQuery.Resource`（`xrn:` 文本，按序数精确匹配，`null` 不过滤）进入 `Matches`。
   - 数据库实现在 SQL 里过滤，`AuditRecord` 新增 `(Resource, Sequence)` 索引。
   - 一致性套件在用例 2 里核对资源过滤，前缀不算命中。
2. **细节是 JSON 值**：
   - `AuditEvent.Details` 改为 `IReadOnlyDictionary<string, JsonElement>?`。
   - `AddAuditDetail(key, JsonNode? value)`：字符串、数值、布尔、日期、`Guid` 都能隐式转成 `JsonNode`，调用处写法不变。
   - `null` 记为 JSON null。
   - 追加时就经 UTF-8 写出再解析成脱离文档的 `JsonElement`，不走反射序列化（AOT 可用）；之后改原节点不影响已记下的值。
   - `FindAuditDetails` 交出 `IReadOnlyDictionary<string, JsonElement>` 的只读副本。
   - 数据库映射按 `JsonElement` 原样读写细节；错误细节仍是原语层的对象字典，不变。
3. **一致性套件**：用例 1 写入字符串与数值细节，读回后断言各自的 `JsonValueKind`。所有接收器读回同一类型。

不另设细节的类型白名单：`JsonNode` 本身就只表达 JSON 能表示的值，无法表达的对象在调用处就编译不过。

## 影响

- 源码迁移：
  - 读细节的代码从 `Details["amount"]` 的装箱值改为 `Details["amount"].GetDecimal()`、`GetString()`、`GetInt32()` 等。
  - 原来传复杂对象的 `AddAuditDetail` 改传 `JsonObject` / `JsonArray`，或拆成几个简单值。
  - 自己实现 `IAuditSink` 并读 `Details` 的 Provider 改成按 `JsonElement` 处理。
- 数据库实现的细节 JSON 格式不变，已有记录照常读出。新索引随表结构管理（`InitTables` 只用于开发与测试）。
- `AuditEvent` 是 `Stable`，其余是 `Preview`；GA 前修改，不需要登记豁免（ADR-0131）。
