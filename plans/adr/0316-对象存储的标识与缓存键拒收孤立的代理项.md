# ADR-0316 对象存储的标识与缓存键拒收孤立的代理项

## 状态

已采纳（规范 RFC-0012「标识」新增「孤立的代理项」一条，「范围读取、分片上传与预签名」的保存文件名、宿主代签的规范串与 S3 发起应答一条里上传标识的写法、「一致性」的向量说明已改；RFC-0006「存储契约」的键与「键管理」的前缀、「代数缓存区」的散列、「一致性」已改；`provider/caching-distributed.md` §2 的 `key` 与适配器写出请求已改；RFC-0006、RFC-0012 的状态行已改；向量 `objectstorage/blob-keys.json`、`objectstorage/download-file-names.json`、`caching/cache-keys.json` 补了孤立的代理项与成对的代理项，含孤立代理项的用例以新字段 `utf16` 写出码元；Go 一致性模块新增 `conformance.CodeUnits`，`rules.IsBlobKeyPrefix`、`rules.IsBlobDownloadFileName`、`rules.IsCacheKeyPrefix` 拒收不是合法 UTF-8 的文本。`ObjectStorage.Abstractions` 的 `BlobKey`、`BlobQuery`、`BlobUrlRequest`、`BlobMultipartUpload` 与 `Caching.Abstractions` 的 `CacheKey` 拒收孤立的代理项；`Hosting.AspNetCore` 的 `HostedBlobUrlSigner` 与 `Caching.Remote` 的 `RemoteCacheStore` 在编码处改用严格的 UTF-8；`GenerationCache<T>` 散列范围与条目时按 WTF-8 取字节。公开面、错误码、消息键与配置键不变）。

## 日期

2026-11-26

## 背景

上一轮实测了一个安全问题：

1. 对象键 `BlobKey` 的文法允许孤立的代理项。`IsValidPrefix` 只拒空白、控制字符与反斜线。
2. 给键 `a\uD800` 用 `HostedBlobUrlSigner` 签出的地址，路径经 `Uri.EscapeDataString` 成了 `a%EF%BF%BD`，端点从路由读到的是 `a�`。
3. 签名的规范串经 `Encoding.UTF8.GetBytes` 宽松编码，`a\uD800` 与 `a�` 编出的字节相同，验签通过。
4. 结果是给一个键签的地址打开了另一个对象。本 ADR 的用例在改之前复现了它：地址打开对象 `a�`，状态 200，读到的是那个对象的内容。

远程缓存的键是同一类。RFC-0006 的键文法同样不排除代理项。`RemoteCacheStore` 经 System.Text.Json 写出请求，孤立的代理项被写成转义的 `�`，两个不同的键到了插件就是同一个条目。ADR-0315 的「影响」已把它列进同类而没改的一项。

仓库所有者已拍板：键的文法都拒收孤立的代理项，契约先进规范；编码处改用严格的 UTF-8 作第二道防线。

按任务查了 RFC-0012 里其余会编成 UTF-8 字节或 URL 的标识：

- 保存的文件名（`BlobUrlRequest` 的 `downloadFileName`）：进宿主签名的规范串、地址的 `x-filename`、`Content-Disposition` 头与 S3 的 `response-content-disposition`，文法只拒控制字符。
- 分片上传的上传标识（`BlobMultipartUpload` 的 `uploadId`）：进宿主签名的规范串与地址的 `x-upload`、S3 的 `uploadId` 查询参数，文法只拒空白与控制字符。
- 容器名、元数据名、实例名与内容类型的文法只有 ASCII，本来就排除了孤立的代理项。
- 元数据的值与分片的 `ETag` 不是标识，见「影响」的「同类而没改的」。

实测了几种宽松的编码，都把孤立的代理项换成 U+FFFD：

- `Uri.EscapeDataString("a\uD800")` 得 `a%EF%BF%BD`。
- `Encoding.UTF8.GetBytes` 得 `61 EF BF BD`。
- `JsonSerializer.Serialize("a\uD800")` 得 `"a�"`（ADR-0315 也实测过）。
- AWS SDK 的 `AWSSDKUtils.UrlEncode`（`AWSSDK.S3` 4.0.104.8）得 `a%EF%BF%BD`。
- StackExchange.Redis 3.4.31 的 `RedisKey` 线上字节得 `61 EF BF BD`。

改之前缓存键这一边，代数缓存区（`GenerationCache<T>`）另有一处同类问题，而且会被本次改动放大。范围与条目合缓存键文法的直接写进键，不合的写成 `#<SHA-256>`，散列的输入是宽松的 UTF-8：

- 以前 `a\uD800` 是合法的键文本，直接写进键。内存缓存里它与 `a\uDBFF` 是两个条目；Redis 与远程缓存上两个都编成 `61 EF BF BD`，撞成一个。
- 缓存键拒收孤立的代理项之后，这两个范围都改走散列，散列的输入又都是 `61 EF BF BD`，内存缓存上也撞成一个。本 ADR 的用例只改了 `CacheKey`、没改散列时实测：四个范围里前三个读回的都是第三个的值。
- 授予缓存以 `user:` / `role:` 加主体 ID 作范围（`DatabasePermissionGrantStore`），主体 ID 只拒空白，一个主体会读到另一个主体的授予。

## 备选

文法：

1. **对象键、查询前缀、保存的文件名、上传标识与缓存键都拒收孤立的代理项**：采纳，照所有者的决定。
   - 孤立的代理项指不在一对之中的 U+D800–U+DFFF 码元：单独的高代理项、单独的低代理项、颠倒的一对、末尾的高代理项。
   - 成对的代理项是平面以外的一个字符，照常合法。
   - 只拒孤立的代理项，不另限字符集：键里的非 ASCII 字符本来就合法，S3 与文件系统都存得住。
2. **对象存储只改键与前缀**：否决。任务要求查全，保存的文件名与上传标识也进签名的规范串与 URL；只改键，给文件名 `f\uD800` 签的地址仍会对上 `f�`。
3. **把宽松编码的结果当作合法，只在编码处统一换成 U+FFFD**：否决。不同的键撞成同一个对象、同一个条目，正是要消除的问题。
4. **以字节表示字符串的实现怎么写**：规范写明，Go、PHP 里这几种标识必须是合法的 UTF-8。孤立的代理项在那里只能以编成 UTF-8 的代理项（`ED A0 80`–`ED BF BF`）或别的非法字节出现；Go 的 `range` 把它们读成 `utf8.RuneError` 照收，以前 `rules.IsBlobKey` 照收这样的字节。Python 的 `str` 不能有 U+D800–U+DFFF 的码位。Rust 的 `&str` 总是合法的 UTF-8，不用核对。
5. **错误码与消息**：与各自现有的「不合文法」相同，不新登记。
   - 构造 `BlobKey`、`BlobQuery`、`BlobUrlRequest`、`BlobMultipartUpload`、`CacheKey` 时抛出 `ArgumentException`，`IsValid*` 为假。
   - 幂等键（`IdempotencyMiddleware`）照旧返回 `CACHING_VALIDATION_001` + `caching.idempotency.invalid_key`，键管理的前缀照旧返回 `CACHING_VALIDATION_004`。
   - 异常消息（英文，编程错误，不本地化）在描述文法的那一句里补上「lone surrogates」；本地化的模板不改，见「待定」。
6. **级别**：两处都是 MAJOR（`v1.0.0` 之前允许）。键、前缀、文件名与上传标识的文法以前已经写明，这是收窄已经写明的合法集合。

编码处：

7. **签名器的规范串严格编码，编不成按编程错误抛出**：采纳，照所有者的决定。
   - `HostedBlobUrlSigner.Sign` 用私有的严格 `UTF8Encoding`。`EncoderFallbackException` 包成 `ArgumentException`，消息说明有签进去的值带孤立的代理项。
   - 签进去的各项要么是合文法的标识，要么是宿主从 UTF-8 字节解码出的路径与查询串，所以编不成只会出在绕过文法核对的代码上。照算会签出打开另一个对象的地址，所以抛出，不返回 `Result`。
   - 验签走同一个 `Sign`。从请求到不了这一步：本 ADR 的用例把查询串的 `x-filename` 换成编成 UTF-8 的代理项与截断的序列，宿主解码出的不是孤立的代理项，结果是签名不符（403），不是 500。
8. **`RemoteCacheStore` 在写出请求之前核对键能严格编码**：采纳，照所有者的决定。
   - System.Text.Json 没有严格写字符串的开关，所以在组请求时逐个键用严格的 `UTF8Encoding` 数字节。
   - 编不成时抛出 `ArgumentException`（带 `EncoderFallbackException`），不发请求，也不当成后端不可用（`CACHING_UNAVAILABLE_001`）：合文法的键总编得成。
   - 九个操作都经同一个 `KeyText` 取键。
9. **签名器与适配器编码失败时返回 `Result` 失败**：否决。这里的失败只出在绕过文法核对的代码上，是编程错误；返回 `OBJECTSTORAGE_VALIDATION_*` 或 `CACHING_UNAVAILABLE_001` 会让调用方以为是输入或基础设施的问题。

代数缓存区：

10. **散列的输入按 WTF-8 取字节**：采纳。
    - 合法的文本的 WTF-8 就是它的 UTF-8，已有的散列键不变，不用迁移。
    - 孤立的代理项照 UTF-8 三字节的写法编成 `ED A0 80`–`ED BF BF`。这几个字节序列不出现在合法的 UTF-8 里，所以不同的文本散列的输入总不相同。
    - 它不是任务点名的一处。只改 `CacheKey` 会让内存缓存上原本不撞的范围撞起来，授予缓存就会把一个主体的授予交给另一个主体，所以必须与 `CacheKey` 同一次改。
11. **散列 UTF-16 的码元**：否决。所有已有的散列键都会变，升级之后整个代数缓存区冷启动一次；与 UTF-8 也不再是同一个输入，规范里要另写一种编码。
12. **范围与条目有孤立的代理项时抛出**：否决。RFC-0006 写明范围与条目是任意文本，授予缓存的范围来自主体 ID，抛出就让授权检查对这样的主体整个失败。

向量：

13. **向量里怎么写孤立的代理项**：用新字段 `utf16`，以四位十六进制列出 UTF-16 码元。这样的用例不写原文，也不标 `utf8Bytes`。
    - ADR-0301 备选 27 否决过把孤立的代理项写进 JSON 字符串：System.Text.Json 读到即抛出（本 ADR 实测：`Cannot transcode invalid UTF-16 string to UTF-8 JSON text.`），Go 换成 U+FFFD，Python 原样保留。
    - 码元各语言都能照原样组出：UTF-16 的语言直接组成；以字节表示字符串的语言按 WTF-8 编成字节（Go 的 `conformance.CodeUnits.Text`）；Python 把成对的代理项合成一个码位。
    - `blob-keys.json` 的合法键里另有一条以码元写出的成对代理项，与转义写出的那一条是同一个键，用来核对组字符串的写法：没把成对的代理项合成一个字符的实现，在这一条上判错。
14. **四种写法都有用例**：单独的高代理项、单独的低代理项、颠倒的一对、末尾的高代理项（就是 `a\uD800`），另有「高代理项之后又是高代理项」一条，`blob-keys.json` 还有一整段只有一个低代理项的键。合法的一侧补转义写出的成对代理项（`😀`）。Go 一致性模块的测试要求这几种都在。
15. **把孤立代理项的用例放进单独的一组，而不是 `invalid`**：否决，照任务的写法放进 `invalid`。按旧的结构读 `cache-keys.json` 的 Go SDK 测试读到的是空的 `text`，仍判为不合法，不会因为这次改动失败（见「影响」的「六个 SDK」）。

## 决策

1. **RFC-0012**（MAJOR）：
   - 「标识」新增「孤立的代理项」一条：对象键、查询前缀、保存的文件名与上传标识都不能含孤立的代理项。写明孤立代理项的定义、成对的代理项合法、各类语言的判定与理由。
   - 「范围读取、分片上传与预签名」：保存的文件名的文法加上这一项。宿主代签的规范串严格编码成 UTF-8，签名与验签编码不成都按编程错误抛出。
   - 同一节 S3 发起应答一条里上传标识的写法加上这一项。
   - 「一致性」写明向量的 `utf16` 写法与组字符串的方法，删掉「向量不收的」里的那一句。
2. **RFC-0006**（MAJOR）：
   - 「存储契约」的键与「键管理」的前缀加上这一项，写明理由。
   - 「代数缓存区」写明散列取 WTF-8。
   - `provider/caching-distributed.md` §2 的 `key` 加上这一项，并写明两点：适配器写出请求时严格编码键，编不成按编程错误抛出、不发请求；插件读到的键过 RFC-0001「JSON 文本」的检查，转义出的孤立代理项到不了键的核对。
3. **向量与 Go 一致性模块**：
   - 三个向量文件补用例。
   - Go 新增 `conformance.CodeUnits`（`Units`、`Text`），`BlobKeyCase`、`BlobKeyPrefixCase`、`DownloadFileNameCase`、`CacheKeyCase` 加 `UTF16` 字段与 `Input()`。
   - `rules.IsBlobKeyPrefix`（`IsBlobKey` 经它）、`rules.IsBlobDownloadFileName`、`rules.IsCacheKeyPrefix`（`IsCacheKey` 经它）先整串核对 UTF-8。
4. **.NET**：
   - `BlobKey.IsValidPrefix`（`IsValid` 经它）、`BlobUrlRequest.ForDownload`、`BlobMultipartUpload` 的构造经 internal 的 `BlobKey.HasLoneSurrogate` 拒收孤立的代理项；`CacheKey.IsValid` 经私有的同名方法。
   - `HostedBlobUrlSigner` 与 `RemoteCacheStore` 改用严格的 UTF-8。
   - `GenerationCache<T>` 散列时按 WTF-8 取字节。
   - 测试类库 `XiHan.Framework.Testing.Workspace` 新增 `SpecVectors.FromCodeUnits` 与 `SpecVectors.TextOf`，读向量里的 `utf16`。

## 理由

- 孤立的代理项编不成 UTF-8。宽松的编码把它换成 U+FFFD，得到的仍是合法的文本：收的一方看不出交来的东西被改过，不同的键落到同一个对象、同一个条目上，签名也对上另一个对象。与 ADR-0301、ADR-0312、ADR-0315 同一个理由，换到标识的文法上。
- 契约收在文法上：标识在构造时就拒收，进不了任何存储、签名或请求。编码处的严格 UTF-8 只是第二道防线，失败即说明有代码绕过了核对。
- 代数缓存区按 WTF-8 散列，已有的散列键不变，只给原来撞在一起的文本各自一个键。

## 影响

- **公开 API**：没有变化（`PublicAPI.Unshipped.txt` 无改动）。`BlobKey.HasLoneSurrogate` 是 internal；`IsValid*`、构造与 `Validate` 签名不变，只多一种不合法的情形。没有新的错误码、消息键与配置键。
- **对已有部署与代码的行为变化（升级须知）**：
  - 对象键、查询前缀、保存的文件名与上传标识有孤立的代理项时，构造抛出 `ArgumentException`，`BlobKey.IsValid` / `IsValidPrefix` 为假；以前照收。宿主代收发的端点对这样的路由值回 404（与其余不合文法的键相同），文件系统与 S3 的列举跳过这样的对象。
  - 缓存键与键前缀有孤立的代理项时，`CacheKey` 的构造抛出 `ArgumentException`；`IDistributedCache` 适配同样抛出。幂等键或主体 ID 有孤立的代理项时，幂等调用返回 `CACHING_VALIDATION_001`、不执行处理器；以前照常去重，在 Redis 上与 U+FFFD 的那个键共用一条记录。
  - `GenerationCache<T>` 的范围或条目有孤立的代理项时写成散列形式；以前直接写进键。合法文本的键不变。
  - 已存的数据：
    - 文件系统存储写不进这样的键：`BlobPathEncoding` 遇到孤立的代理项构造 `Rune` 即抛出，写入失败。
    - S3 与 Redis 经宽松编码，存下的是换成 U+FFFD 之后的键：AWS SDK 的 `UrlEncode` 与 `RedisKey` 都实测编成 `EF BF BD`。这些对象与条目改后照常能用 U+FFFD 的那个键读写，只是不能再用带孤立代理项的键去访问。
    - 远程缓存的键经 System.Text.Json 同样写成了 U+FFFD。内存缓存不持久化。
    - 所以按理没有以孤立代理项为键的真实数据；要找回这类数据的应用，把键里的孤立代理项换成 U+FFFD 去读。
  - 迁移：从用户输入构造键的代码先用 `BlobKey.IsValid` / `CacheKey.IsValid` 判断，或在拼键之前把来源文本按严格的 UTF-8 核对；文件名与上传标识同此。
- **规范**（规范工作区已提交）：RFC-0006、RFC-0012、`provider/caching-distributed.md`、三个向量文件、`conformance/README.md`。两处 MAJOR（`v1.0.0` 之前允许）。
- **Go 一致性模块**：
  - 新增 `CodeUnits` 类型与四个用例类型的 `UTF16` 字段、`Input()` 方法，都只增不改。
  - 三个规则函数拒收不是合法 UTF-8 的文本。Go SDK 的 `caching.IsKey` 直接调 `rules.IsCacheKey`，升了模块版本就跟着改。
  - 去掉这三处核对，`rules` 包的测试有 14 处断言失败。
- **六个 SDK**：
  - 对象存储档（`objectstorage`）没有 SDK 认领，SDK 里也没有对象键、文件名与上传标识的判定。
  - `caching/cache-keys.json` 属于 `provider:caching.distributed@1` 档，只有 Go SDK 认领：它的 `caching` 包是远程缓存 Provider 的插件一侧，`caching/adapter_test.go` 的 `TestKeysFollowTheVectors` 回放这个文件。Go SDK 升规范指针与 conformance 模块之后：
    - `IsKey` 经 `rules.IsCacheKey` 自动拒收非法的 UTF-8；
    - 测试改用 `c.Input()` 取文本，含孤立代理项的用例跳过 `len(c.Text) != c.UTF8Bytes` 的核对。
    - 不改测试也不会失败：旧的结构读到这几条的 `text` 为空，照旧判为不合法，只是没有真正回放它们。
  - 插件一侧读到的键来自 JSON 文本，转义出的孤立代理项过不了 RFC-0001 的检查，运行时没有行为变化。
  - 其余五个 SDK 没有认领这两个档，不用改。
- **同类而没改的**（报告第 8 条另列，按风险排序）：
  - CloudEvents HTTP 绑定的二进制模式（缺省的出站模式）：`CloudEventsHttpBinding.EncodeHeaderValue` 经 `EnumerateRunes` 把孤立的代理项编成 `%EF%BF%BD`，不经 ADR-0315 的 `CloudEventsFormat.Encode` 核对。不同的 `id`、扩展属性写出相同的 `ce-*` 头，接收方按 `id` 去重会丢掉另一个事件。
  - 知识库的文档 ID（`KnowledgeIngestor`）：只拒空白，经宽松 UTF-8 的 SHA-256 生成向量记录的键，只差在孤立代理项上的两个文档互相覆盖分块。
  - Baggage 的值（`BaggageKeys.IsAcceptableValue` 只拒控制字符；幂等键连这一项也不查）：`HttpInvocation.FormatBaggage` 经 `Uri.EscapeDataString` 写出，下游收到的两个不同的幂等键是同一个。
  - 工作流的关联 ID：没有文法，`ReuseLockKey` 经宽松 UTF-8 散列；事件的 `correlation` 扩展属性会让 `Encode` 抛出，这个实例的事件都发不出去。
  - `ResourceName` 的 ID 段（`^[^/\s]+`）、审计详情的键：进审计记录与 JSON，两个资源或两个键分不开。
  - 元数据的值（`BlobPutOptions` 只拒控制字符）：文件系统的旁路文件与 S3 的 `x-amz-meta-*` 存下的是换成 U+FFFD 的值，读回与写入不同。
  - 插件绑定的值与属性、Kubernetes Lease 的 `holderIdentity`、调度定义的指纹，以及运营方配置的前缀与后缀（Redis 消息的 `KeyPrefix`、死信后缀、Nacos 的 dataId 等）。
