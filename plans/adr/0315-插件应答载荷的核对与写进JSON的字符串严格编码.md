# ADR-0315 插件应答载荷的核对与写进 JSON 的字符串严格编码

## 状态

已采纳（规范 RFC-0001「JSON 文本」的「写出与转交」改第一条、新增两条、改末句，`plugin/invocation.md` §1、§5、§8，`plugin/lifecycle.md` §2，`protocol/commandline.md` 的字段选项，RFC-0009「信封」的写出，RFC-0001、RFC-0009、RFC-0017 的状态行已改，向量 `plugin/plugin-messages.json` 的 `reasons` 加两条；`Plugins.Protocol` 的 `ProxyOperationDescriptor` 核对插件交回的应答，`PluginJson.SerializeSection` 改为 `TrySerializeSection`，`PluginConfigureRequests` 遇孤立的代理项即配置失败；`Hosting.CommandLine` 的 `FieldOptionPayload` 与 `Messaging.Abstractions` 的 `CloudEventsFormat.Encode` 遇孤立的代理项即失败；TypeScript 与 Java SDK 的同类改动由 SDK 一侧跟进；错误码、消息键与配置键不变）。

## 日期

2026-11-26

## 背景

ADR-0312 把 RFC-0001「JSON 文本」扩到写出与转交，它的「影响」与「待定」里留下几处同类而没改的。仓库所有者已拍板，下面三件都做：

1. **SDK 一侧以字符串写出的另两处**：处理器以字符串交回的 `Invoke` 应答（TypeScript 的 `runtime.ts` 经 `TextEncoder` 编码调用器交回的文本；这段文本总是 `writeJson` 写出的，孤立的代理项已经写成 `\ud800` 这样的转义，换不出 U+FFFD，见文末「更正」），插件以字符串给出的发布信封 `data`（Java 的 `Envelope.Builder.data(String)` 用 `getBytes(UTF_8)`，TypeScript 的 `Host.publish` 经 `TextEncoder`）。孤立的代理项换成 U+FFFD 或 `?` 照发。ADR-0312 只写了 `Host.Invoke` 的载荷。
2. **宿主不核对插件交回的应答载荷**：`ProxyOperationDescriptor` 把插件的 `payload` 原样交回，调用经 `ExecuteAsync`，幂等回放经 `DecodeResponse`。之后各协议各自处置：
   - MCP 的 tool 结果与命令行 `invoke` 的 stdout 用 `Encoding.UTF8.GetString` 宽松解码。
   - gRPC 载体的 `ProtoEncoder` 把转义出的孤立代理项写进 protobuf 字符串。
   - HTTP 把重复成员的正文原样写出。
   - 语法不对的应答让 MCP 的 `structuredContent`、gRPC 载体、AI 工具与幂等记录在 `JsonDocument.Parse` 处抛出。
3. **System.Text.Json 写字符串时把孤立的代理项写成转义的 U+FFFD**：实测 `Utf8JsonWriter` 的 `WritePropertyName` 与 `WriteStringValue` 都这样写，不抛出。
   - 命令行的字段选项（`FieldOptionPayload`）照常调用，同一个命令行上的 `--json` 却是用法错误。
   - 插件的配置节（`PluginJson.SerializeSection`）照常下发。
   - RFC-0001 的末句把「值里的字符串经 JSON 写出器写出」整个排除在规则之外。

按任务在框架里搜了一遍 STJ 把应用或外部来的字符串写成 JSON 交给别处的地方，搜的是 `Utf8JsonWriter`、`WriteStringValue`、`WritePropertyName`、`JsonSerializer.Serialize*`、`ToJsonString` 与自定义转换器，结果列在「影响」。其中 `CloudEventsFormat.Encode` 与上面两处同一类：
- 信封的属性是应用给的字符串，文档交给代理与消费方，读取一侧过「JSON 文本」的检查。
- 写出一侧本来就有现成的失败：写不出读得回来的文档即抛 `MESSAGING_VALIDATION_002`。
- 孤立的代理项被写成合法的转义 U+FFFD，写出之后的检查拦不下。

## 备选

SDK 的应答与发布的 `data`：

1. **处理器的应答编不成时报 `KERNEL_UNEXPECTED_001` + `kernel.invocation.unhandled_exception`**：采纳。没有参数，`payload` 为空，作为 `Status.error` 报给宿主。
   - RFC-0011 规则 10 的「编码」早已写明，XGI 入口写不出响应（NaN、序列化不支持的值）时就是这个结果。以字符串交回却编不成 UTF-8 是同一件事：响应写不出。
   - 处理器的失败本来就经 `Status.error` 报给宿主，宿主照 `invocation.md` §3 读入，不需要新码。
2. **用 `PLUGINS_UNEXPECTED_001` + `plugins.process.failed`**：否决。那是协议层失败，或者对方写坏了内容。这里是插件自己的处理器写不出应答，应当与插件里的类型化响应写不出得到同一个结果。
3. **用 `KERNEL_VALIDATION_001` + `kernel.operation.invalid_payload`**：否决。这个错误说的是调用方给的载荷不合法，把错归给了调用方。KIND 是 `VALIDATION`，熔断也不计。
4. **发布的 `data` 编不成时，那一项在本地失败、不发出**：采纳。结果是 `MESSAGING_VALIDATION_002` + `messaging.envelope.invalid`，`reason` 为 `the data has a lone surrogate and cannot be encoded as UTF-8`；其余各项照常组成一次请求发出。
   - 照 `Host.Invoke` 那一条的写法：本地失败，不发出；错误取宿主对同一类坏输入给的码与键。宿主逐项核对的最后一步「信封能否转换」（`PluginEnvelopeMapper.FromProto`）不合时，就是这个码与键。
   - 先后排在整批的核对（端点、权限、租户、截止时间）之后，与 `Host.Invoke` 的载荷相同。不发出的那一项，宿主的逐项核对（发布器、主题、`xihantenant`）不再进行。
5. **发布的 `data` 编不成时整批不发**：否决。`Host.Publish` 是逐项给结果的批量，整批的错误只给整批的条件（权限、租户）。把别的合法信封一起拒掉，作者就得自己拆批重发。
6. **发布的 `data` 编不成时报 `KERNEL_VALIDATION_001`**：否决。没有操作 ID 可填，`data` 也不是操作载荷。

宿主核对插件的应答：

7. **核对放在代理那一处（`ProxyOperationDescriptor`），进程外与 Wasm 共用**：采纳。
   - 两种载体的运行时都把应答包成 `PluginPayload` 交给代理，放进运行时就要写两份。
   - 代理先把运行时包一层，再交给 `PluginTracing`。核对因此在 `xihan.plugin.invoke` Span 之内，失败时 Span 的状态是 Error，与插件报的失败一样。
8. **没过检查报 `PLUGINS_UNEXPECTED_001` + `plugins.process.failed`**：采纳。`phase` 为操作 ID，`reason` 为 `the response payload is not valid JSON text at '<路径>'`。
   - 以进程外宿主的现有处置为准：插件写来的内容不合规时都是这个码与键，例如错误码不合文法、`ok` 为假却没有错误。`phase` 与 `FromStatus` 在调用时的写法相同。
   - 路径照 RFC-0001：语法错误为 `$`，重复成员为第一处重复。这与宿主读请求载荷时 `reason` 带路径一致。
   - 固定文本登记进 `plugin-messages.json`。
9. **按崩溃处理（进程外终止进程，Wasm 重建实例）**：否决。
   - 进程外的现有处置里，内容不合规只让这次调用失败，进程照常服务。
   - Wasm 只有整条消息不是合法的 proto3 JSON 时才按崩溃处理，因为那时客体的状态不可信。`payload` 是消息里一个合法的 `bytes` 字段，与错误码不合文法是同一类。
   - 重启一个只写坏了一次应答的插件，会丢掉它所有在途的调用。
10. **熔断**：不另做处理，规范写明。错误码的 KIND 是 `UNEXPECTED`，内核的 `ResilienceMiddleware` 按 KIND 计数（RFC-0004）：这个操作开了熔断时，它与插件不可用、超时一样算失败；没开时不计。
11. **另登记错误码或消息键**：否决。处置与运营方的动作和 `plugins.process.failed` 的其他场合相同：插件写坏了内容，就修插件。
12. **空的载荷也按不是 JSON 拒绝**：这次不改，记为待定。
    - RFC-0001 说空文本不是 JSON。但 .NET 一直原样交回空载荷，各协议适配器（MCP、gRPC、AI 工具）与一致性套件都把它当作没有响应体。
    - 按 SDK 的调用器写的插件，成功时总有载荷（RFC-0011 规则 10）；只有手写的插件会交回空载荷，例如测试用的 WAT 插件。
    - 规范写明：空载荷不做这道检查，照旧原样交回。
13. **幂等回放（`DecodeResponse`）也核对**：采纳。
    - 记录可能来自另一个版本的宿主（共享的分布式存储），回放出的应答应当与调用时交回的过同一道检查。
    - 不合时返回 `KERNEL_VALIDATION_001`，这是 `DecodeResponse` 现有的失败，写法照基类。Idempotency 阶段再照 RFC-0006 报 `CACHING_CONFLICT_003`。
14. **进程内插件**：不适用。进程内插件宿主不向登记表贡献操作（`invocation.md` §1），没有经宿主转交的应答。

STJ 写出的字符串：

15. **命令行字段选项有孤立的代理项时，是与 `--json` 同一个用法错误**：采纳，照所有者的决定。错误码 `HOSTING_VALIDATION_001`，退出码 64，沿用消息键 `hosting.commandline.invoke_json_invalid`。
    - `reason` 为 `the value of option '--<名>' has a lone surrogate and cannot be encoded as UTF-8`。名字本身有孤立的代理项时为 `an option name has a lone surrogate and cannot be encoded as UTF-8`：坏的名字不写进原因，stderr 的 JSON 一样会把它换成 U+FFFD。
    - 写之前先核对全部字段：写出器写到一半不会报错。
16. **插件配置节有孤立的代理项时，配置这一步失败**：采纳。结果是 `PLUGINS_UNEXPECTED_001` + `plugins.process.failed`，`phase` 为 `configure`，`reason` 为 `the configuration has a lone surrogate and cannot be encoded as UTF-8`，不带键与值。
    - 插件进入 `Failed`，按重启策略重试；宿主照常启动，处于降级状态。
    - 这是配置节现有的失败路径：`PluginConfigureRequests.Build` 不合时（绑定读不出、超限）就是这样，两种载体的调用方都丢弃进程或实例、记为 `Failed`。
    - 配置节在绑定之前核对，请求里先组装的就是它。
17. **配置节有孤立的代理项时装配失败（启动失败）**：否决。别的配置问题（绑定）都只让这个插件失败；运营方改正配置之后，插件在下一次重试时自己起来。
18. **`reason` 带出出问题的键**：否决。与绑定的 `reason` 只带绑定名同一口径：配置节里常有密钥，键名本身也可能正是那个坏字符串。
19. **信封的属性有孤立的代理项时，`CloudEventsFormat.Encode` 抛出携带 `MESSAGING_VALIDATION_002` 的 `FrameworkException`**：采纳。消息带属性名。
    - 核对 `id`、`source`、`type`、`subject`、`dataschema`、`datacontenttype` 与扩展属性的值。扩展属性名合文法，是 ASCII，不必核对。
    - 在序列化之前核对：写出之后的检查看到的已经是合法的转义 U+FFFD。
    - 四个代理、发件箱与 CloudEvents HTTP 绑定都经它写出，发布时就拒绝，与 JSON 数据里有重复成员同一个处理。内存代理不经线上编码，照常投递，与重复成员的情形相同。
20. **把「字符串能否严格编码」写成公开的辅助（如放进内核的 `JsonText`）**：否决。三处各用一个私有的严格 `UTF8Encoding`，与 ADR-0301、ADR-0312 的写法相同；不为几行代码加公开面。
21. **一并改的范围**：只改与命令行字段选项、配置节同一类的。同一类指：写成 JSON 交给一个按「JSON 文本」读的对方，并且那一处已有现成的失败。其余列在「影响」：
    - 错误细节（`PluginJson.SerializeDetails`）：写出一侧没有失败，读入一侧把不合法的当作没有细节。
    - `ResultJson.Write`：只对编程错误抛出。
    - HTTP 的路由与查询串：经 Kestrel 解码，不会有孤立的代理项。
    - AI 工具的参数：可以是任意对象与 JSON 节点，嵌套的字符串由类型化序列化写出，改不全。
    - 类型化对象的序列化（操作的响应、领域事件、持久化与缓存）：这是 ADR-0312 备选 2 否决的那一大类。
22. **加向量**：只给 `plugin-messages.json` 加两条宿主一侧的固定 `reason`。孤立的代理项写进 JSON 向量，各语言读出来的输入不同（ADR-0301 备选 27），由各实现的单元测试核对。

## 决策

1. **RFC-0001「写出与转交」**：
   - 第一条加上 SDK 以字符串交回的应答载荷与以字符串给出的发布 `data`。
   - 新增「以字节收到、不解析就转交出去的」一条：宿主转交插件的应答载荷之前，过共同检查。
   - 新增「把字符串写进一份要交给别处读的 JSON 文本的」一条：命令行字段选项、插件配置节、信封的属性有孤立的代理项时，按那一处不合法的输入处理。
   - 末句改为：上面列出之外经 JSON 写出器写出的字符串值，不在这一条里。
2. **`plugin/invocation.md`**：
   - §1「宿主读插件交回的应答」：不为空时过共同检查，没过为 `PLUGINS_UNEXPECTED_001` + `plugins.process.failed`；不按崩溃处理，计入熔断，空载荷照旧，幂等回放做同一道检查，进程内插件不适用。
   - §1「插件一侧写出应答」：字符串严格编码，编不成为 `KERNEL_UNEXPECTED_001` + `kernel.invocation.unhandled_exception`。
   - §5：`Host.Publish` 以字符串给出的 `data` 逐项在本地失败，`MESSAGING_VALIDATION_002` + `messaging.envelope.invalid`。
   - §8：补上 `plugins.process.failed` 的两个场合。
3. **其余规范**：`plugin/lifecycle.md` §2、`protocol/commandline.md`、RFC-0009「信封」的写出各补一句；`plugin-messages.json` 加两条固定 `reason`。
4. **.NET**：
   - `ProxyOperationDescriptor`：调用与回放都核对。
   - `PluginJson.TrySerializeSection` 与 `PluginConfigureRequests.Build`：配置节有孤立的代理项即配置失败。
   - `FieldOptionPayload.Write`：返回 `Result`，有孤立的代理项即用法错误。
   - `CloudEventsFormat.Encode`：属性有孤立的代理项即抛出。

## 理由

- 与 ADR-0301、ADR-0312 同一个理由：换成 U+FFFD 得到的仍是合法的 JSON，收的一方看不出交来的东西被改过。宿主原样转交插件写坏的应答，坏在哪里要到各协议的下游才各自显形，或者被宽松地「修好」。
- 每一处都沿用那里已有的失败，不新登记错误码与消息键：运营方与调用方看到的错误，不因为坏在编码上而换一种。
- 应答只在代理一处核对，两种载体的结论相同；不按崩溃处理，一次写坏的应答只影响这一次调用。

## 影响

- **公开 API**：没有变化。`ProxyOperationDescriptor`、`PluginJson`、`PluginConfigureRequests`、`FieldOptionPayload` 都是 internal；`CloudEventsFormat.Encode` 签名不变，只多一种抛出的情形。没有新的错误码、消息键与配置键。
- **对已有部署与代码的行为变化（升级须知）**：
  - 进程外与 Wasm 插件交回的应答载荷不是合法的 JSON 文本时，调用失败（`PLUGINS_UNEXPECTED_001`，`reason` 带路径）；以前原样交给调用方。不合法指语法错误、超过 64 层、非法的 UTF-8、孤立的代理项或重复成员。按 SDK 写的插件写出的是合法的 JSON，不受影响；空的载荷照旧。
  - 命令行 `invoke` 的字段选项有孤立的代理项时是用法错误（退出码 64）；以前写成 U+FFFD 照常调用。只在 Windows 上能出现。
  - 插件配置节的键或值有孤立的代理项时，插件配置失败（`Failed`，按退避重试）；以前写成 U+FFFD 下发。
  - 信封的字符串属性有孤立的代理项时，`CloudEventsFormat.Encode` 抛出 `MESSAGING_VALIDATION_002`：RabbitMQ、Kafka、Redis 与发件箱的发布、CloudEvents HTTP 绑定因此拒绝这样的信封；以前写成 U+FFFD 照常发布。
- **规范**（规范工作区已提交）：都是写明（MINOR），以前不作规定。RFC-0001 的末句明说那一类不在规则里；应答载荷与配置节以前没有写。宿主拒绝的应答载荷本来就不合「`payload` 是响应类型的 JSON」，按较早 MINOR 实现的合规插件不受影响。
- **Go 一致性模块**：不变。`plugin-messages.json` 多了两条 `reason`；`rules/binding_test.go` 只认 `configure` 阶段带 `{binding}` 的那几条，不受影响。
- **六个 SDK**：
  - TypeScript：处理器以字符串交回的应答与 `Host.publish` 里字符串形式的 `data` 改用严格编码。
  - Java：`Envelope.Builder.data(String)` 改用严格编码。
  - Go 与 PHP 的字符串就是字节，Rust 的 `&str` 总是合法的 UTF-8，Python 的信封 `data` 是 `bytes`、应答由 SDK 自己的写出器写成转义文本：这四个 SDK 的行为不用改。
  - `plugin-messages.json` 多了两条宿主一侧的 `reason`。按「向量里的每一条都在 SDK 里有对应」核对的测试（如 Go SDK 的 `plugin/vectors_test.go`），要把它们列进宿主一侧的名单。
- **同类而没改的**（报告第 8 条另列）：
  - 写出一侧没有现成失败的：`PluginJson.SerializeDetails`（宿主写给插件的错误细节），`ResultJson.Write`（Result 与 Error 的线上编码）。
  - 到不了的：`OperationRequestBinder` 把 HTTP 的路由值与查询串写进载荷，经 Kestrel 按 UTF-8 解码之后不会有孤立的代理项。
  - 改不全的：`OperationAIFunction.SerializeArguments` 把模型给的参数写进载荷，参数可以是任意对象与 JSON 节点。
  - 类型化的序列化：`OperationDescriptorOfT.EncodeResponse`、`DomainEventRegistration`、`IdempotencyRecord`、`JsonCacheSerializer`、工作流的 `WorkflowJson`（定义、实例、变量与事件）、调度的 `RecordMapping`，以及审计、租户、对象存储的旁路文件与向量库的元数据。
  - 应答与诊断输出：HTTP 的 Problem Details（`ProblemResponse`）、健康详情、命令行的失败 JSON（`CommandLineFailure`）、MCP 的应答、OpenAPI 文档、AI 工具的错误对象。
  - 交给外部服务的：工作流 `Http` 活动的正文与头、Kubernetes Lease 的 `holderIdentity`、`RemoteCacheStore` 写进远程缓存操作载荷的键、`xihan migrate --report` 的文件。缓存键的文法（RFC-0006）不排除代理项，两个不同的键到了远端可能撞成同一个。
  - protobuf 的字符串字段（经 gRPC 下发的 `Binding.value` 与属性）：Google.Protobuf 宽松编码，与 ADR-0312 已列的那一条相同。
- **测试**：
  - `PluginResponsePayloadTests`（新增，进程外测试项目，两种载体共用的代理那一处）：
    - 九种不合法的应答（语法、注释、两个根、65 层、截断的序列、编码成 UTF-8 的代理项、转义出的孤立代理项、重复成员、嵌套的重复成员）都是 `PLUGINS_UNEXPECTED_001`，`reason` 带路径。
    - 合法的多字节文本、空载荷与插件报的失败照旧。
    - Span 的状态是 Error。
    - 回放（`DecodeResponse`）对同样的九种返回 `KERNEL_VALIDATION_001`。

## 更正

- 2026-11-26（ADR-0318）：「背景」第 1 条原写「处理器以字符串交回的 `Invoke` 应答（TypeScript 的 `runtime.ts` 经 `TextEncoder` 编码）」，与「孤立的代理项换成 U+FFFD 照发」连读，与实际不符。TypeScript 的处理器没有以字符串交回应答的接口，应答总由调用器的 `writeJson` 写出，孤立的代理项写成 `\ud800` 这样的转义，再由宿主按 `plugin/invocation.md` §1 以 `PLUGINS_UNEXPECTED_001` 拒绝；`runtime.ts` 改用的严格编码在公开 API 下触发不到。这里只改了那一处括注，决策与影响不变；规范 `plugin/invocation.md` §1 的同一句注记同日更正。类型化应答里的孤立代理项怎样处理，见 ADR-0318。
