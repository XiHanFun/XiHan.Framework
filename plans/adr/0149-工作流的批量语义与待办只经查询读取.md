# ADR-0149 工作流的批量语义与待办只经查询读取

## 状态

已采纳（规范 `rfcs/0021-workflow.md` 修订）。

## 日期

2026-11-11

## 背景

API 审查对工作流提了两组问题。

**2.6 批量契约没写进公开文档**：

- 批量操作整批一个事务，失败项不写入，这条语义只写在 internal 的 `WorkflowScope` 上。
- 中途取消直接抛出。
- 空集合、重复 ID、条数上限都没规定。

**2.5 读取没有上限**：

- `IWorkflowTaskService.PendingAsync(assigneeId)` / `PendingByInstanceAsync(instanceId)` 一次读出全部待办，与已经分页的 `QueryAsync(UserTaskQuery)` 重复。
- 存储接口 `IWorkflowBookmarkStore.ByKindAndKeyAsync` / `BySignalAsync` 与 `IWorkflowDefinitionStore.ListAsync` 没有 limit。
- `SignalAsync` 把匹配的书签全部读出，在一个事务里逐个恢复。

## 决策

- **批量语义写进 `IWorkflowEngine` 文档与 RFC-0021**，任务与外部任务服务相同：
  - 结果与入参等长、同序；重复 ID 按顺序逐项施加。
  - 自己开调用时整批一个事务：逐项失败不回滚其余项，失败的项没有写入；提交失败时每一项都报告提交的错误。在调用方的工作单元里时并入调用方的事务。
  - 取消在任何时刻都整批回滚并抛出。整批在一个事务里，回滚就不会留下半批，符合批量优先第 7 条。这与调度器的逐项取消（ADR-0148）不同：调度器的每一项各自落地，没有包住整批的事务。
  - 不强加批次上限（批量优先第 8 条）。
- **空集合不开事务**：`WorkflowScope.RunBatchAsync` 在数量为 0 时直接返回空结果，不开调用、不访问存储（批量优先第 5 条）。引擎、任务与外部任务服务的全部批量方法都经过这里。
- **删除 `PendingAsync` 与 `PendingByInstanceAsync`**：
  - 待办一律经 `QueryAsync` 分页读取，某人的给 `AssigneeId`，某实例的给 `InstanceId`。
  - 一致性套件的宿主辅助方法改为经 `QueryAsync` 读取。
- **存储读取的分页暂不改**：
  - 信号扇出要分页，就要回答三个问题：
    - 只投递给发信号那一刻已有的书签：恢复会建出同名的新书签，分页时会被重新读到。
    - 恢复失败留在原处的书签不能挡住后面的书签：只按 limit 重读，会一直读到同一批失败的书签。
    - 每页一个事务还是整批一个事务。
  - 正确的做法要配合快照上界的游标与逐页事务，牵动 `SignalAsync` 的事务语义与两个 Provider 的查询，不是加一个参数就能解决的。
  - 这三个存储接口仍是 `Preview`，5.x 里可以经豁免修改，放到单独的一项里设计；审查清单记为待办。

## 影响

- `PendingAsync(assigneeId)` → `QueryAsync(new UserTaskQuery { AssigneeId = assigneeId })`，读 `Items`，按需翻页。
- `PendingByInstanceAsync(instanceId)` → `QueryAsync(new UserTaskQuery { InstanceId = instanceId })`。
- 空集合的批量调用不再开一次调用，因此不再经过管道（审计、幂等）；结果仍是空列表。
- 这些类型都是 `Preview`，GA 前修改，不需要登记豁免（ADR-0131）。
