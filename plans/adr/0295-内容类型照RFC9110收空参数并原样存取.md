# ADR-0295 内容类型照 RFC 9110 收空参数，并原样存取

## 状态

已采纳（`ObjectStorage.Abstractions` 的 `BlobPutOptions` 已改，新增错误码 `OBJECTSTORAGE_VALIDATION_007` 与消息键 `objectstorage.blob.content_type_unsupported`；`ObjectStorage.S3` 写不出原值的内容类型在发请求之前拒绝；一致性套件新增用例 15；规范 RFC-0012「标识」「契约」「S3 Provider」「一致性」、`conventions/error-codes.md`、向量 `blob-content-types.json` 与 Go 规则已改）。

本 ADR 修订 ADR-0282 决策 4 中「每个 `;` 之后必须有参数」那一部分。按「状态只增不改」，ADR-0282 的正文不改，以本 ADR 为准；ADR-0282 关于对象键、查询前缀与保存的文件名的部分，以及 `;` 两侧只收空格、参数不解析引号，都不受影响。

## 日期

2026-11-25

## 背景

- ADR-0282 把内容类型收紧成「每个 `;` 之后必须有参数」：`text/plain;`、结尾多出的 `;`（`text/plain; charset=utf-8;`）与连续的 `;` 都拒，宿主代收的上传带这样的 `Content-Type` 回 400。
- 复核发现 RFC 9110 §5.6.6 的文法是 `parameters = *( OWS ";" OWS [ parameter ] )`，参数本来就可以为空；野外也确有客户端这样发。ADR-0282 备选 9 的理由（「`;` 之后为空的不合法」）建立在对 RFC 的误读上。
- 核对「读元数据、写回存储时原样保留」时实测了两个 Provider：
  - 文件系统：内容类型原样写进元数据文件、原样读回。
  - S3：AWS SDK for .NET（`AWSSDK.S3` 4.0）在 `HttpWebRequestMessage.WriteContentHeaders` 里以 `MediaTypeHeaderValue.Parse` 重新写出 `Content-Type`。在回环上记录请求头的假对端上实测：
    - 解析不了的（`text/plain;`、`text/plain; charset=utf-8;`、`text/plain;;charset=utf-8`）SDK 抛出 `FormatException`，这时请求行与请求头已经发出（带 `Expect: 100-continue`、没有 `Content-Type`），`S3BlobStore.PutAsync` 与分片上传的发起把这个异常直接抛给调用方。
    - 解析得了而写法不同的（`text/plain;charset=utf-8`、`text/plain ; charset=utf-8`）线上发的是 `text/plain; charset=utf-8`，而按收到的请求头复算 SigV4 签名可知，签名是按原值算的（`content-type` 在 `SignedHeaders` 里）：服务按收到的头验签必然对不上。这一类在 ADR-0282 之前就合文法、也在规范的合法向量里，所以这是原有的缺陷，只是单元测试用的假客户端看不出来；本机没有 S3 服务，没有对真实服务复现。
    - 读取一侧，SDK 对解析得了的响应头同样按 .NET 的写法交出（存储里的 `text/plain;charset=utf-8` 读出 `text/plain; charset=utf-8`），解析不了的原样交出。
    - .NET 的写法本身（`text/plain; charset=utf-8`、`Text/HTML`、`text/plain; boundary=";;"`、`text/plain; flowed`）写出与读回都不变。

## 备选

1. **维持 ADR-0282**：否决，见背景。
2. **`;` 两侧的 OWS 照 RFC 9110 把制表符也收下**：否决，理由同 ADR-0282 备选 8。整个内容类型不含控制字符是 ADR-0214 定下的：值进 S3 的请求头与文件系统的元数据文件，制表符在多数日志与界面里不可见，两个看上去一样的内容类型可以不是同一个值；现有向量 `text/plain;\tcharset=utf-8` 必须拒绝。收空参数不需要收制表符：RFC 9110 的 OWS 是 `*( SP / HTAB )`，只取 SP 仍是它的子集。
3. **解析参数、按 `name=value` 与引号核对**：否决，理由同 ADR-0282 备选 10，ADR-0214「参数部分不细分」。
4. **正则逐段写（`( *; *(非空参数)?)*`）**：没有采用，改用等价的 `( *;[\x20-\x7E]*)?`。逐段写法里参数结尾的空格与下一个 `;` 前的空格可以互相让，是嵌套的量词；放宽之后两者描述的是同一个集合（任意一串可打印 ASCII 与空格都能在每个 `;` 处切成可以为空的参数），简单的那个没有回溯的余地。规范两种都写出，实现取哪一种都可以。它与 ADR-0282 之前 .NET 用的正则相同：从行为看，这次放宽回到 ADR-0282 之前的集合，同时保留 ADR-0282 写明的两条（`;` 前可以有空格、只收空格）。
5. **S3 把写不出原值的内容类型改写成 .NET 的写法再写**（`text/plain;` 写成 `text/plain`，`text/plain;charset=utf-8` 写成 `text/plain; charset=utf-8`）：否决。决定是原样存取、不规范化掉空参数；改写之后照写是静默兜底，存进去的不是调用方给的值，同一份写入在文件系统与 S3 上得到不同的内容类型。代价见「影响」：浏览器常发的 `text/plain;charset=UTF-8` 在 S3 上写不进去。
6. **S3 绕过 SDK 的改写**（换掉 SDK 管道里的 `HttpHandler`，自己包一层 `IHttpRequest<HttpContent>` 以 `TryAddWithoutValidation` 原样写头，读取一侧另包 `IWebResponseData` 取原始响应头）：没有做。要依赖 `Amazon.Runtime.Internal` 命名空间里的管道类型，SDK 每次升级都可能断；读写两侧都要改。见「待定」。
7. **S3 把 SDK 的 `FormatException` 归为存储故障（`OBJECTSTORAGE_UNAVAILABLE_001`）**：否决。不是存储故障，调用方会以为重试有用；请求已经发出一半；写法不同的那一类照样签名对不上。
8. **写不出原值时复用 `OBJECTSTORAGE_VALIDATION_006`**：否决。它是「宿主直传端点的请求内容类型不合文法」，消息说的是长度与文法；这里的内容类型合文法，是存储写不出它。新登记 `OBJECTSTORAGE_VALIDATION_007`。
9. **写不出原值时抛 `ArgumentException`**：否决。合契约文法的输入在一个 Provider 上能写、在另一个上不能写，调用方事先判断不了，是可以处理的失败，按仓库约定返回 `Result`。

## 决策

1. **内容类型的文法**（RFC-0012「标识」）：参数照 RFC 9110 §5.6.6 的 `*( OWS ";" OWS [ parameter ] )`：
   - 每个 `;` 两侧可以有空格；OWS 只取空格，制表符在 `;` 的哪一侧都不收。
   - 参数可以为空：`text/plain;`、`text/plain; `、结尾多出的 `;`、连续的 `;`、引号里连续的 `;` 都合法。
   - 不为空的参数是不含 `;` 的可打印 ASCII 与空格；参数内部不细分，不解析引号。
   - 媒体类型之后只有空格、没有 `;` 的仍不合法（`text/plain `）。
   - 整串匹配 `^<token>/<token>( *;[\x20-\x7E]*)?$`；整体 1 到 255 个字符不变。
   - `BlobPutOptions.IsValidContentType` 的正则照此改；`ContentType` 的异常消息去掉「non-empty」。
2. **原样存取**（RFC-0012「契约」，以前不作规定）：
   - 写入（含分片上传的发起）把 `ContentType` 原样交给存储，读取把存储里的值原样放进 `BlobMetadata.ContentType`；Provider 自己不规范化：不去掉空参数，不改 `;` 两侧的空格，不改大小写。把读出的元数据原样写回得到同一个内容类型。
   - 所用的存储客户端写不出原值的，写入与分片上传的发起在发出任何请求之前以 `OBJECTSTORAGE_VALIDATION_007` 失败（HTTP 400，参数 `contentType`，消息键 `objectstorage.blob.content_type_unsupported`），不改写之后照写。
   - 预签名上传限定的内容类型由客户端自己发送，不经 Provider 的客户端，不受此限。
3. **S3**：`S3BlobStore` 的写入与分片上传的发起先判 `S3ContentTypeHeader.IsSentVerbatim`（照 SDK 的做法以 `MediaTypeHeaderValue` 解析再写出，与原值逐字符相同才算原样），不原样即返回 `OBJECTSTORAGE_VALIDATION_007`，先于条件写入与不覆盖写入的 `Head`，一个请求都不发。读取照旧交出 SDK 读到的值；解析得了而写法不同的读出 .NET 的写法，是已知的缺口，规范写明。
4. **一致性套件**：`BlobStoreConformance` 新增用例 15 `ContentTypes_AreKeptAsGiven_OrRefusedBeforeWriting`：八种写法（含空参数、`;` 两侧的空格、引号里的 `;`）写入、`Head`、`Get` 与写回都原样，或者返回 `OBJECTSTORAGE_VALIDATION_007` 且对象不存在；实现了分片上传的再走一遍发起与完成。
5. **规范与向量**：`blob-content-types.json` 把 ADR-0282 加的 9 条「`;` 之后为空」挪到 `valid`，另补 `text/plain;;`、`text/plain ; ; ;`；`invalid` 补 `text/plain;\t`、`text/plain; charset=utf-8;\t`、`text/plain;\t;charset=utf-8`，原有带制表符的保持拒绝；期望值由 .NET 回放核对。Go 规则 `IsBlobContentType` 的正则同步。

## 理由

- RFC 9110 是内容类型的事实源；照它收下的值，HTTP 两端本来就会收发。
- 取严不取宽（ADR-0276）在这里不成立：ADR-0282 拒绝的是合规的输入，代价由调用方承担（400）。放宽只让 ADR-0282 之后才被拒的那一类重新合法，制表符与引号的规则不变。
- 原样存取让「同一份写入选项在不同 Provider 上得到同一个内容类型」成立；做不到的 Provider 明确拒绝，而不是悄悄存一个别的值，或者把请求发出一半再抛异常。

## 影响

- **公开 API**（`PublicAPI.Unshipped.txt` 已同步，只有新增）：`ObjectStorageErrors.ContentTypeUnsupported`（`OBJECTSTORAGE_VALIDATION_007`）、`ObjectStorageMessages.ContentTypeUnsupported`（10 个语言文件已补）、`BlobStoreConformance.ContentTypes_AreKeptAsGiven_OrRefusedBeforeWriting`。`BlobPutOptions` 的签名不变。
- **放宽**：ADR-0282 之后被拒的写法重新合法——`BlobPutOptions.ContentType`、`BlobUrlRequest.ForUpload` 不再抛出，`IsValidContentType` 返回 `true`，宿主代收的上传（签名没限定内容类型）带 `Content-Type: text/plain;` 这类头照常写入，对象的内容类型就是请求发来的那一串。
- **升级须知（S3 的行为收紧）**：S3 Provider 的写入与分片上传的发起遇到 SDK 写不出原值的内容类型，返回 `OBJECTSTORAGE_VALIDATION_007`，不发请求：
  - 空参数的写法（`text/plain;` 等）：以前在 ADR-0282 之后构造 `BlobPutOptions` 即抛出，再往前 SDK 抛出 `FormatException`。
  - `;` 两侧的空格与 .NET 的写法不同的（`text/plain;charset=utf-8`、`text/plain ; charset=utf-8`，浏览器常发 `text/plain;charset=UTF-8`）：以前请求照发、按推断在服务端验签失败（`OBJECTSTORAGE_UNAVAILABLE_001`），单元测试的假客户端上看起来成功。
  - 迁移：把客户端给的内容类型交给 S3 的，遇到 `OBJECTSTORAGE_VALIDATION_007` 时由应用决定换成 .NET 的写法（`; ` 一个空格、去掉空参数）重写，或拒绝请求；文件系统存储不受影响。
- **读取**：两个存储包读元数据都不重新校验内容类型。S3 上经预签名地址由别的客户端写入的对象，解析得了而写法不同的内容类型读出 .NET 的写法；把它写回 S3 是原样的，写回文件系统存的就是改写后的值。
- **规范**（规范仓库已改，指针待更新）：RFC-0012「标识」的放宽是 MAJOR（改已写明的行为，`v1.0.0` 之前允许；读取一侧照收旧写法，只是多收）；「契约」的原样存取、`OBJECTSTORAGE_VALIDATION_007` 的登记、「S3 Provider」与「一致性」的增补是 MINOR；向量改的是内容（无新文件），认领 `objectstorage` 档的实现回放要跟着改，目前只有 .NET。
- **测试**：
  - 回放：`BlobContentTypeVectorTests` 核对向量里空参数的各种写法在合法一侧、带制表符的与 `text/plain ` 在不合法一侧（Go 一侧同样核对）。
  - `BlobPutOptionsTests`：空参数的七种写法合法且原样保存，制表符与 `text/plain ` 不合法。
  - 宿主代收：带制表符的 `Content-Type` 回 400（改用测试用 HttpClient 不会改写的 `text/plain;\t;charset=utf-8`：它会把解析得了的值改写后再发）；`text/plain; charset=utf-8;` 写入且 `Head` 原样读出。
  - 一致性用例 15：文件系统全部原样通过；S3 对真实服务的用例只在 CI 设了 `XIHAN_TEST_S3` 时执行，本机跳过。
  - S3 线上（真实的 SDK 与套接字，回环上的假对端）`S3ContentTypeWireTests`：向量里每一个合法的内容类型，要么线上请求头逐字符相同、返回的元数据也是它，要么返回 `OBJECTSTORAGE_VALIDATION_007` 且一个请求都没有，两种传输各走一遍；被拒的不覆盖写入与分片上传的发起连一条连接都不建；七种存储里的写法读出什么；绕过 Provider 直接用 SDK 时 `text/plain;` 抛 `FormatException`、`text/plain;charset=utf-8` 线上变成 `text/plain; charset=utf-8`（SDK 哪天改成原样写出，这条失败，拒绝就该撤掉）。
  - `RecordingHttpListener` 能带响应头应答，并按 `Content-Length` 读掉请求体（带 `Expect: 100-continue` 先回 100）。
- **文档**：文档站的 `object-storage/basics`、`object-storage/advanced`、`packages/objectstorage-abstractions`、`packages/objectstorage-s3`、`appendix/spec` 与更新日志待改。
- **待定**：
  - S3 要不要做到真正的原样存取（备选 6），还是改为写入前按 .NET 的写法改写（备选 5），或维持现在的拒绝。现在的拒绝让浏览器常发的 `text/plain;charset=UTF-8` 在 S3 上写不进去。
  - `S3BlobStore.StartAsync` 在服务应答成功却没有 `UploadId` 时会抛 `ArgumentNullException`（写回放测试时看到），没有在本 ADR 处理。
