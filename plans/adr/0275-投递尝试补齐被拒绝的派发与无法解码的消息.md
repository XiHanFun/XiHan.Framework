# ADR-0275 投递尝试补齐被拒绝的派发与无法解码的消息

## 状态

已采纳（`Messaging.Abstractions` 的 `MessageDeliveryAttempt.RunAsync` 不再把被管道拒绝的派发算作一次尝试，新增 `MessageDeliveryAttempt.Undecodable`，`Preview`；RabbitMQ、Kafka、Redis 三个代理改用 `Undecodable`，四个 Provider 包的公开面不变；`Messaging.Conformance` 的 `MessageBrokerConformance` 新增抽象方法 `ReadDeadLettersAsync` 与两条用例，`Preview`；RFC-0009 要补的文字见「影响」的最后一条）。

## 日期

2026-11-24

## 背景

ADR-0261 把四个代理「收到一条消息之后」的骨架收成 `MessageDeliveryAttempt`，留下三件没做（它的备选 8、备选 9 与「测试」一条）：

- **被管道拒绝的派发计一次尝试**：
  - `RunAsync` 先查看应用是否在服务状态，再把投递交给派发委托；派发器经 `App.InvokeAsync` 进管道，入口再查看一次，不在服务状态就抛出携带 `KERNEL_HOSTING_004` 的 `FrameworkException`。两次查看之间应用开始排空，这次派发就被拒绝，处理器没有执行。
  - 抛出的异常与别的异常一样归成一次失败的尝试（记一条「派发抛出」的警告，错误是 `MESSAGING_UNEXPECTED_001`）。下一次尝试等在服务状态上，直到停止信号到来被放弃，所以后果只落在被拒绝的那一次：
    - 没到上限：尝试号白白加一。内存代理以下一次尝试号入队尾，RabbitMQ 以下一次尝试号重新发布并确认原消息，Redis 认领一次让投递次数加一；Kafka 的原位计数不落盘，重启后从 1 起，没有留下痕迹。
    - 赶上最后一次尝试：竞争投递进死信（Kafka 还提交了位点），广播投递被丢弃，日志里是一条「已进死信」的警告。
  - 这与「被停止打断的投递不计尝试」（ADR-0261 决策 3）是同一种情形的两半：都是停机造成的，处理器要么没执行、要么没执行完。排空在前、停止信号在后，中间这一段漏了。
- **无法解码的消息各写一份**：RabbitMQ、Kafka、Redis 各有一段「竞争订阅进死信、广播订阅丢弃并记日志、不重试」。判定相同；广播的日志三家逐字相同，竞争的日志只差介质（`dead-letter queue` / `topic` / `stream`）；Redis 另有「条目没有 `envelope` 字段」的原因文字。内存代理不经线上编码，没有这条路径。
- **一致性套件看不到死信**：`MessageBrokerConformance` 只数处理器收到了几次，「进死信」只在各 Provider 自己的测试里核对（内存代理读死信列表，Redis 读死信流，RabbitMQ 与 Kafka 靠打桩）。ADR-0261 改掉的「停止打断的投递被送进死信」因此没有一条跨代理的用例守着。

## 备选

1. **被拒绝的派发按放弃（`Abandon`）了结**：否决。
   - `Abandon` 的约定是「停止信号已经发出」，四个代理照这个约定翻译：内存代理把投递放回队列后结束消费循环；Kafka 以取消异常抛出，令牌没有取消时消费循环把它当成投递没有完成，回退并等 `RedeliveryDelay` 再投；RabbitMQ 不确认，消息占着预取名额直到通道关闭；Redis 不确认，条目要空闲过 `ClaimIdleTime` 才被回收。
   - 应用开始排空到消息特性收到停止信号之间，令牌没有取消。这时给出 `Abandon`，内存代理的主题就没人消费了，另外三家各等各的超时。
   - 回到等服务状态，则与「查看时就已经不在服务状态」走的是同一条路径：等到停止信号，再按 `Abandon` 了结。
2. **被拒绝之后立即再派发**：否决。状态说在服务、管道却拒绝时就是忙等。
3. **一直等下去，不设出口**：否决。正常的应用状态只往前走，一次尝试里至多被拒绝一次；连续被拒绝说明状态与管道不一致（派发委托绑定的不是传进来的这个应用），这种不一致不会自己恢复。
4. **出口给 `Abandon` 或直接抛出**：否决。理由同备选 1；`RunAsync` 的约定是不抛出派发的异常。出口按一次失败的尝试处理，就是改动之前的行为。
5. **返回的失败结果里带 `KERNEL_HOSTING_004` 也不计**：否决。处理器已经执行过（它自己发起的嵌套调用被拒绝，再把这个错误返回）。与「取消只认令牌、不认错误码」同理，只认管道入口抛出的。
6. **让派发委托自己报告「没有执行」**（改 `MessageDispatch` 的返回类型或加一个重载）：否决。`MessageDispatch` 是 `Stable` 契约。
7. **无法解码的消息仍留在各代理**（ADR-0261 备选 9：没有信封、不是一次投递，日志按介质措辞不同，内存代理没有这条路径）：这次推翻。
   - 判定与 `Exhausted` 相同，而且是规范写明的规则（RFC-0009「订阅方式」第 3 条、「流」第 2 条），下一个带线上编码的代理会写出第四份。
   - 介质的名字不是日志里必须有的：日志记在各代理自己的类别下，类别已经说明是哪个代理。
   - 内存代理不调用它即可，不需要为它存在一条到不了的路径。
8. **`Undecodable` 收主题与订阅方式两个参数**：否决。三个代理手里都有 `MessageSubscription`，它在构造时已经校验过主题与方式。收 `MessageDelivery` 做不到，没有信封。
9. **`Undecodable` 返回另一种结论类型**：否决。返回与 `Exhausted` 相同的 `MessageDeliveryOutcome`，代理用同一段代码把 `DeadLetter` 与 `Discard` 翻译成动作。
10. **Redis 缺 `envelope` 字段的条目保留专门的原因文字**：否决。要么为一条日志新增消息键（十个语言文件），要么让共用的方法收自由文本。缺字段按空文档解码，同样解不开，错误说明文档不是合法的 CloudEvents JSON。
11. **套件的死信入口做成可选**（虚方法，不支持就跳过用例）：否决。竞争订阅用完尝试次数进死信是 `messaging.queue@1` 的规定行为，每个 Provider 都有死信可读。代价是已有的套件子类要补一个方法。
12. **套件读死信时取走它们**：否决。等死信出现要反复读，「不在死信里」的断言也要读；取走就得在夹具里另存一份。
13. **套件的死信入口返回原始字节，或带尝试号与错误码的记录**：否决。各介质带的元数据不一样（Redis 是条目字段，RabbitMQ 与 Kafka 是消息头，内存代理是投递对象），套件要核对的只是「哪条消息进了死信、信封还在不在」，返回能解码的信封就够。
14. **停止打断的用例停掉宿主、另起一个宿主**：否决。内存代理的队列在宿主里，换宿主就没了。在同一个宿主上停止再启动 `MessagingRuntime`，四个代理都支持。
15. **套件断言再到达时的尝试号**：不做。它由代理决定（RFC-0009「投递」第 3 条），套件只要求不超过上限。
16. **套件在最后一次尝试上打断**：不做。Redis 的回收让投递次数加一，最后一次尝试上被打断的条目回收后超过上限、不派发直接进死信（ADR-0261 决策 7）；这种情形四家不一致，留在各代理自己的测试里。

## 决策

1. `MessageDeliveryAttempt.RunAsync` 派发时遇到携带 `KERNEL_HOSTING_004` 的 `FrameworkException`：
   - 不算一次失败的尝试，不了结这条投递：等一个查看间隔（10 毫秒）后回到「等应用进入服务状态」，应用再进入服务状态时重新派发，尝试号不变。
   - 停止信号到来照旧 `Abandon`：等待期间令牌取消，或拒绝时令牌已经取消。
   - 只认派发抛出的这个错误码。处理器自己返回的同码失败结果照常是一次失败。
   - 记一条 Debug 日志，不记警告：应用开始排空的那一刻正在派发的投递都会遇到，是预期的状态。
2. 间隔与出口：
   - 间隔：每次被拒绝之后都先等一个查看间隔再看状态。状态已经翻成不在服务的，接着每 10 毫秒查看一次；状态仍说在服务的，两次派发之间至少隔这么久。
   - 出口：同一次尝试里第 10 次被拒绝不再等，按抛出的异常归成一次失败（记「派发抛出」的警告，错误是 `MESSAGING_UNEXPECTED_001`，`reason` 是 `KERNEL_HOSTING_004`，原错误作内部错误），之后照常重投或按用完尝试次数了结。
3. `MessageDeliveryAttempt` 新增 `Undecodable(subscription, error, logger)`（`Preview`），与 `Exhausted` 成套：
   - 竞争订阅是 `DeadLetter`，广播订阅是 `Discard`，结论带着解码给出的错误（`MESSAGING_VALIDATION_002`）；`error` 可以为空，日志里记 `?`。
   - 不派发、不重试，也不等应用进入服务状态：不执行处理器，与应用的状态无关。
   - 各记一条警告，记在调用方的 `logger` 上，原因写解码错误的文案（没有消息 ID 可记）：
     - `Topic {Topic} received an undecodable message; it was dead-lettered: {Reason}`
     - `Topic {Topic} delivered an undecodable broadcast message; it was dropped: {Reason}`
4. 三个代理只把 `Undecodable` 的结论翻译成自己的动作，与用完尝试次数时相同，死信里是收到的字节：

   | 结论 | RabbitMQ | Kafka | Redis |
   | --- | --- | --- | --- |
   | `DeadLetter` | 原样发布到死信队列，确认后 `basic.ack` | 原样（键、值与头）发布到死信主题，落盘后提交位点 | 原样 `XADD` 到死信流（带 `attempt` 与 `error`），应答后 `XACK` |
   | `Discard` | `basic.ack` | 没有动作，不提交 | `XACK` |

   Redis 没有 `envelope` 字段的条目按空文档解码。
5. `MessageBrokerConformance` 新增（`Preview`）：
   - 抽象方法 `ReadDeadLettersAsync(host, topic, cancellationToken)`：读出一个主题此刻的死信，返回竞争订阅的死信里能解码的信封，按进入顺序；不取走死信，可以反复调用；死信的队列、主题或流还不存在时返回空列表。由各 Provider 的测试实现：

     | 代理 | 读法 |
     | --- | --- |
     | 内存 | 宿主里代理的 `DeadLetters(topic)` |
     | RabbitMQ | 自己的连接：先被动声明死信队列（404 即没有死信），再逐条 `basic.get`、不自动确认，读完整批 `basic.nack` 退回 |
     | Kafka | 不提交位点的独立消费者，把死信主题从最早位点读到调用时的高水位；主题不存在即没有死信 |
     | Redis | `XRANGE` 死信流，取条目的 `envelope` 字段 |

   - 用例 15：竞争订阅的投递用完尝试次数后带原信封进死信、只进一次，处理成功的消息与别的主题的死信不受牵连。
   - 用例 16：处理器正在处理时停止消息运行时，这次投递不在原位重试、不进死信；重新启动后再到达并处理成功，尝试号不超过上限。
   - `DeliveryLog.BlockingIds`：这些 ID 的投递让处理器等到调用被取消；虚属性 `RedeliveryTimeout`（默认同 `DeliveryTimeout`）给没有确认的消息要等超时才重新可见的代理；辅助方法 `WaitForDeadLetterAsync`。
   - Redis 的套件把 `ClaimIdleTimeSeconds` 配成 5，`RedeliveryTimeout` 覆写成 30 秒。

## 理由

- 「被停止打断」与「被排空拒绝」是停机的先后两步，处理器在这两步里都没有把这条消息处理完。只修一半，剩下的一半照样把消息送进死信，只是窗口更窄、更难复现。
- 拒绝之后回到等待，四个代理不需要认识一种新的结论，也不需要各自决定「没有停止信号的放弃」该怎么办。
- 出口退回到改动之前的行为：最坏情况与现在一样，只是慢一点（每次尝试多出九个间隔），不会因为这次改动多出一种卡死的方式。
- 无法解码与用完尝试次数是同一条规则的两个入口（不再重试的投递怎么了结）。放在一处，第四个代理只写翻译。
- 套件能读死信之后，「进死信」与「不进死信」都成了可以跨代理断言的事实，不再依赖每个 Provider 的测试各自记得写。

## 影响

- **被管道拒绝的派发**（四个代理经 `RunAsync` 一起获得，各包没有改动）：
  - 原先计一次尝试并记一条带异常的警告；现在不计，记一条 Debug 日志，投递等在服务状态上，停止信号到来按 ADR-0261 的 `Abandon` 了结。
  - 赶上最后一次尝试：原先竞争投递进死信（内存代理进死信列表，RabbitMQ 发布到死信队列并确认，Kafka 发布到死信主题并提交位点，Redis 写死信流并 `XACK`）、广播投递被丢弃；现在都不发生，消息重新投递。
  - 没到上限：内存代理不再以下一次尝试号入队，RabbitMQ 不再重新发布，Redis 不再多认领一次。
  - 状态说在服务、管道却一直拒绝：原先每次尝试派发一次就失败，现在每次尝试派发 10 次（其间 9 个 10 毫秒的间隔）才按失败处理；最终去向不变。
- **无法解码的消息**：
  - 行为不变：竞争订阅原样进死信，广播订阅丢弃，都不重试。
  - 竞争订阅的日志由 `it was moved to the dead-letter queue`（RabbitMQ）、`… topic`（Kafka）、`… stream`（Redis）统一成 `it was dead-lettered`；广播订阅的日志不变。类别仍是各代理自己的。
  - Redis 没有 `envelope` 字段的条目：日志里的原因由 `The entry has no 'envelope' field.` 变成解码错误的文案（文档不是合法的 CloudEvents JSON）；死信条目的 `error` 字段仍是 `MESSAGING_VALIDATION_002`，`envelope` 字段仍是空串。
- **公开面**：
  - `Messaging.Abstractions`：新增 `MessageDeliveryAttempt.Undecodable`。
  - `Messaging.Conformance`：新增 `MessageBrokerConformance.ReadDeadLettersAsync`（抽象）、`RedeliveryTimeout`、`WaitForDeadLetterAsync`、两条用例与 `DeliveryLog.BlockingIds`。
- **自写 `IMessageBroker` 的 Provider**：
  - 用了 `MessageDeliveryAttempt.RunAsync` 的不用改。
  - 自己判定无法解码的消息的，换成 `Undecodable`，按 `Disposition` 翻译；不换也能通过套件，日志措辞自己对齐。
  - 继承 `MessageBrokerConformance` 或 `MessageStreamConformance` 的测试类要实现 `ReadDeadLettersAsync`，否则编译不过；没有确认的消息要等超时才重新可见的，覆写 `RedeliveryTimeout` 或把那个超时调小。
- **测试**：
  - `Messaging.Abstractions.Tests`：真实的应用开始排空时被拒绝的派发不计尝试、等到停止信号放弃；拒绝后再派发；一直被拒绝时的次数与间隔；返回的同码失败照常计入；`Undecodable` 的去向、错误与日志。
  - 内存代理：被拒绝的派发不进死信、停止后放回队列；套件的两条新用例。
  - RabbitMQ、Kafka、Redis：无法解码的消息的翻译与日志各有打桩上的用例。三家 `ReadDeadLettersAsync` 的实现与两条新用例只在有真实代理时运行。
- **规范**：RFC-0009 要补三处，在规范仓库落地后更新 submodule 指针。
  - 「投递」第 5 条：写明被管道以 `KERNEL_HOSTING_004` 拒绝的派发不计入尝试上限、回到等待，实现要在两次派发之间留间隔并在状态与管道持续不一致时有出口。
  - 「投递」第 3 条：把无法解码的消息「竞争订阅进死信、广播订阅丢弃，不派发、不重试，不等应用进入服务状态」写成全部代理的规则，与用完尝试次数并列。
  - 「一致性」：套件的 Provider 要提供读死信的入口，并通过「用完尝试次数进死信」与「停止打断的投递不进死信、重新启动后重新投递」两条用例。
