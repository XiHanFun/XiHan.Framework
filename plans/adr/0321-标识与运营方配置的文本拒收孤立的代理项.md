# ADR-0321 标识与运营方配置的文本拒收孤立的代理项

## 状态

已采纳。

- 规范：
  - RFC-0001 新增「孤立的代理项」一节（定义、各类语言的判定、用到它的地方）与原语 `UnicodeText`，`BaggageKeys.IsAcceptableValue` 的注释已改。
  - `conventions/baggage-keys.md` 的值的约束与幂等键的写出已改。
  - RFC-0008「资源名」的 ID 段与「一致性」、RFC-0015「事件的产生」的细节的键、RFC-0021「实例与执行」的关联 ID（启动、信号、实例查询）、RFC-0022「知识库」的文档 ID、RFC-0013「调度器 `IJobScheduler`」的作业定义已改。
  - RFC-0006「变更通知」的 Redis 键前缀、RFC-0009「信封」的死信后缀与各 Provider 的前缀与名字、RFC-0014「远程配置」的命名空间与「Nacos Provider」的 `Group`、`Tenant`、`plugin/lifecycle.md` §2 下发的绑定已改。
  - 十份 RFC 的状态行已改。
- 向量：`primitives/baggage-keys.json` 的 `values` 补了 `acceptableUtf16` 与 `unacceptableUtf16`；新增 `security/resource-names.json`，进 `security` 档。
- Go 一致性模块：新增 `BaggageValueCase`、`ResourceNameCase`、`ResourceNameVectors`、`conformance.ResourceNames()` 与 `rules.IsResourceName`；`rules.IsBaggageValueAcceptable` 拒收不是合法 UTF-8 的值。
- .NET：新增原语 `UnicodeText.HasLoneSurrogate` 与消息键 `workflow.instance.correlation_invalid`；三个键文法的模板与 `workflow.instance.query_correlations_invalid` 的 10 个区域已改。错误码与配置键不变。

## 日期

2026-11-27

## 背景

ADR-0316 定了对象存储的标识与缓存键拒收孤立的代理项，「影响」里列了同类而没改的一批。仓库所有者已拍板：全部拒收，规范先行。

这一批文本都会被编成 UTF-8 写到别处，宽松的编码把孤立的代理项换成 U+FFFD，只差在孤立代理项上的两段文本到了下游就是同一段：

1. **工作流的关联 ID**：没有文法。
   - 查重的锁键 `ReuseLockKey` 按宽松的 UTF-8 散列它，两个这样的关联 ID 撞成同一把锁。
   - 它又是事件的扩展属性 `correlation`，`CloudEventsFormat.Encode` 写不出（ADR-0315），这个实例的事件都发不出去。
2. **知识库的文档 ID**：只拒空白。
   - 向量键是记录 ID（`<文档 ID>#<块序号>`）的 UTF-8 的 SHA-256，两篇这样的文档写进同一组键，互相覆盖分块。
   - `RemoveAsync` 与文档过滤把文档 ID 编进存储的条件，落到另一篇文档上。
3. **Baggage 的值**：`BaggageKeys.IsAcceptableValue` 只拒控制字符，幂等键连这一项也不查。
   - `HttpInvocation.FormatBaggage` 经 `Uri.EscapeDataString` 写出，两个不同的幂等键都写成 `k%EF%BF%BD`。
   - 下游的 Idempotency 阶段把后一次调用当成前一次的重试，只回放前一次的结果。
4. **资源名的 ID 段**（`^[^/\s]+`）与审计细节的键：进审计记录、日志与 JSON，两个资源、两个键分不开；数据库 Provider 的细节 JSON 还会因此有重复的成员名。
5. **下发给插件的绑定**：主值与属性值只核对了字节数。
   - gRPC 载体的 protobuf 编码把孤立的代理项换成 U+FFFD，插件拿到的是另一个凭据。
   - Wasm 载体的 protobuf JSON 写出器抛出异常。
6. **调度定义的指纹**：代码作业的指纹散列说明、数据与触发器的宽松 UTF-8。
   - 数据先经 JSON 写出器写成文本，孤立的代理项已经换成 `�`。
   - 两份只差在孤立代理项上的代码定义指纹相同，运行时的修改在代码改了之后照样保留；持久化的定义读回来也已换成 U+FFFD。
7. **运营方配置的前缀与后缀**：Redis 缓存与 Redis 消息的 `KeyPrefix`、死信后缀、RabbitMQ 的队列前缀与交换机、Kafka 的主题前缀与消费组、Nacos 的 `dataId`（远程配置的命名空间）、`Group` 与 `Tenant` 都不核对。
   - 它们拼进键、队列名、主题名、流的键与请求的查询串，经各家客户端宽松编码。
   - 两套只差在孤立代理项上的配置落到同一个键空间、队列、主题或文档上，彼此读写、收走对方的消息。

这次实测了几处宽松的编码：

- `Uri.EscapeDataString("a\uD800")` 得 `a%EF%BF%BD`。
- `Uri.UnescapeDataString("a%ED%A0%80")` 原样留下百分号文本，不解出代理项：HTTP 入站读不出孤立的代理项。
- Google.Protobuf 3.36.2：`StringValue { Value = "a\uD800" }` 编成 `0A 04 61 EF BF BD`；`JsonFormatter` 抛出 `ArgumentException`。
- `JsonNode.ToJsonString` 把值与成员名里的孤立代理项都写成 `�`。

另外，原语层没有公开的孤立代理项判定：`MessageValueText` 是 internal 的转义写出，ADR-0316 的 `BlobKey.HasLoneSurrogate` 与 `CacheKey` 里的判定是各包私有的。

## 备选

判定放在哪里：

1. **原语层新增公开的判定 `UnicodeText.HasLoneSurrogate(ReadOnlySpan<char>)`**：采纳。
   - 这一轮有十几个包要判定，`BaggageKeys.IsAcceptableValue` 本来也要在原语层判定。放进原语，所有包都引用得到，只有一份。
   - 定义与 ADR-0316 相同：成对的跳过，其余的代理项不论高低、在哪里都是孤立的。
   - 体积：Primitives 的 `.text` 节原有 320 字节余量，加了之后余 88 字节，程序集仍是 103424 字节。
2. **每个包各写一份私有的判定**（照 ADR-0316）：否决。十几份一样的循环，不合「先找再用、不重写」。
3. **放进内核**：否决。原语层的 `BaggageKeys` 用不到内核；内核的余量也只有 184 字节。
4. **用 BCL 判定**：否决。
   - `Utf8.FromUtf16(…, replaceInvalidSequences: false)` 要一块目标缓冲区。
   - 严格的 `UTF8Encoding` 要靠捕获 `EncoderFallbackException`。
   - 都比一个循环重，判定处又多。

文法与失败语义：

5. **Baggage 的值**：`IsAcceptableValue` 加上这一项，失败语义同控制字符：外部输入丢弃这个成员，`WithBaggage` 抛出。采纳。
6. **幂等键**：
   - 照旧不按值的约束丢弃：丢了它重复的调用会执行两次（ADR-0204）。
   - 有孤立代理项的幂等键已由 Idempotency 阶段按缓存键的文法拒绝（ADR-0316）。
   - 写出的一侧不再换成 U+FFFD：`FormatBaggage` 遇到已登记键的值有孤立的代理项即抛出 `ArgumentException`。采纳。
   - 备选：`FormatBaggage` 丢掉这个成员。否决：下游就没有幂等，是静默兜底。
7. **关联 ID**：
   - `StartAsync` 与 `SignalAsync` 在入口返回 `WORKFLOW_VALIDATION_002` + 新消息键 `workflow.instance.correlation_invalid`，在找定义、开事务之前返回。没有参数：关联 ID 本身写不成合法的文本。采纳。
   - 实例查询的 `CorrelationIds` 并进已有的 `workflow.instance.query_correlations_invalid`，模板补上孤立的代理项。
   - 备选：启动与信号也用 `query_correlations_invalid`。否决：它带 `count` 与 `max`，讲的是查询的集合。
   - 备选：锁键改按 WTF-8 散列。否决：事件照样写不出，存储与查询也照样分不开。
8. **文档 ID**：采纳。
   - 摄入时逐篇返回 `AI_VALIDATION_001`，`reason` 是固定的英文，照已有的 `the document id is empty`。
   - `RemoveAsync` 有一个这样的 ID 即整批失败，不访问存储。
   - `RetrievalFilter.DocumentIds` 在构造时抛出 `ArgumentException`，与超过 1000 个时一样在构造时报。
   - 备选：向量键改按严格的 UTF-8 散列。否决：向量键的算法是存储格式（ADR-0111），改它要重建集合；别的知识库存储照样撞。
9. **资源名**：采纳。
   - `ResourceName` 构造时各段都判。其余各段只有 ASCII，判了没有代价。
   - `TryParse` 先判再构造，返回假而不是抛出。
   - 正则不改：源生成的正则写成能排除孤立代理项的形式会长出几百字节，内核只剩 184 字节。
10. **审计细节的键**：`AddAuditDetail` 抛出 `ArgumentException`，与只有空白时相同：键是程序给的，不合法是编程错误。采纳。细节的值是自由文本，不在这一条里。
11. **下发的绑定**：采纳。
    - 在组装 `Configure` 请求时核对，一个绑定里排在字节数之后。
    - `reason` 是固定的英文 `binding '<绑定名>' has a lone surrogate and cannot be encoded as UTF-8`，不带属性名与值。
    - 两种载体同一条。属性名的文法只有 ASCII，不用另判。
    - 备选：只在 gRPC 载体核对。否决：Wasm 载体靠 JSON 写出器抛异常失败，原因是异常的文本，不是固定的 `reason`。
12. **调度定义**：采纳。
    - 作业与触发器的说明与数据（逐层的成员名与字符串值）有孤立的代理项即 `SCHEDULING_VALIDATION_001`，`reason` 为 `the definition has a lone surrogate in a description or the data`。
    - 运行时与代码登记同一条；代码作业同步失败照已有的做法记日志、下一个周期重试。
    - 作业名与触发器名是作业名的文法，只有 ASCII。
    - 备选：指纹改按 WTF-8 散列。否决：数据先经 JSON 写出器，孤立的代理项在散列之前就已换成 `�`；持久化的定义照样换掉。
13. **运营方配置**：采纳。
    - 选项的初始化器抛出 `ArgumentException`，从配置读取也经它，所以启动失败，照仓库已有的选项校验做法。
    - 改了的：Redis 缓存与 Redis 消息的 `KeyPrefix`、`MessagingOptions.DeadLetterSuffix`、RabbitMQ 的 `QueuePrefix` 与 `Exchange`、Kafka 的 `TopicPrefix` 与 `ConsumerGroup`、`RemoteConfigurationOptions` 的命名空间（Nacos 的 `dataId`）、Nacos 的 `Group` 与 `Tenant`。
    - 本来就排除了的：Redis 消息的 `ConsumerGroup`、`MessagingOptions.InstanceId` 与 Kubernetes 的 `Lease` 的文法只有 ASCII。
    - 没改的见「影响」。
14. **模板**：采纳。
    - `caching.idempotency.invalid_key`、`caching.inspector.prefix_invalid`、`workflow.instance.query_correlations_invalid` 补上孤立的代理项，新增 `workflow.instance.correlation_invalid`，10 个区域都改。
    - 各区域的说法：zh-CN「孤立的代理项」、zh-TW「孤立的代理字元」、ja-JP「孤立したサロゲート」、ko-KR「짝이 없는 서로게이트」、de-DE「ungepaarte Surrogate」、es-ES「suplentes sin pareja」、fr-FR「substituts isolés」、pt-BR「substitutos isolados」、ru-RU「непарные суррогаты」。
    - `Caching.Remote` 的 `caching.remote.key_invalid` 单独一个提交：Go SDK `examples/cache` 的目录有同一个键（en-US、zh-CN）。两边模板不同时宿主启动失败：进程外插件特性登记插件的目录时报 `caching.remote.key_invalid` 在 en-US 的模板不一致（`LOCALIZATION_CONFLICT_001`，`kernel.feature.start_failed`）。`XiHan.Framework.Caching.Remote.Tests` 用本机的 go 构建这个示例（CI 也有 go），实测 32 个用例里 20 个失败。所以它要与 Go SDK 的目录、`framework/samples/CacheGoPlugin/go.mod` 升级同时合并。
15. **向量**：
    - `baggage-keys.json` 在 `values` 里加两个兄弟数组，以 `utf16` 写出码元。采纳。
    - 备选：把对象放进原有的字符串数组。否决：六个 SDK 都按字符串数组读它。
    - 新增 `security/resource-names.json`：资源名以前没有向量，文法完整地写在 RFC-0008 里。`security` 档只有 .NET 认领，新文件不会让 SDK 的覆盖测试失败。采纳。
    - 绑定属性的向量（`plugin/binding-properties.json`）不补：`delivery` 的属性值是字符串或 `{repeat, count}`。Go 一致性模块读对象写法时拒收未知成员，再加一种写法，钉着旧模块版本的 SDK 会读不出整份文件。
    - 文档 ID 与关联 ID 没有向量文件。
16. **级别**：MAJOR（`v1.0.0` 之前允许）。Baggage 的值、资源名的 ID 段与细节的键是收窄已经写明的合法集合；关联 ID、文档 ID、作业定义与配置项以前不作规定，现在拒收以前照收的输入。

## 决策

1. **规范**（MAJOR，`v1.0.0` 之前允许）：
   - RFC-0001 新增「孤立的代理项」：定义、各类语言的判定、理由、.NET 入口 `UnicodeText.HasLoneSurrogate`，以及用到它的地方的一张表。
   - 把这一项写进上面各处标识与配置的文法。
2. **向量与 Go 一致性模块**：
   - `baggage-keys.json` 补以码元写出的四种孤立代理项、「高代理项之后又是高代理项」、只有一个低代理项，以及以码元写出的成对代理项。
   - `resource-names.json` 覆盖各段的字符集、空的租户段、租户段 64 个字符的上限两侧、ID 段里的 `/`、空白与孤立的代理项、结尾的换行。
   - `rules.IsResourceName` 是独立的 Go 实现。去掉 `IsBaggageValueAcceptable` 与 `IsResourceName` 新加的 UTF-8 核对，`rules` 包有 12 处断言失败。
3. **.NET**：
   - 原语 `UnicodeText`。
   - `BaggageKeys.IsAcceptableValue`、`HttpInvocation.FormatBaggage`、`ResourceName`、`AddAuditDetail`。
   - 工作流引擎的启动、信号与实例查询，知识库的摄入、删除与 `RetrievalFilter`。
   - `PluginConfigureRequests`、`JobSchedulerEngine`。
   - 九个选项的成员（决策见备选 13）。

## 理由

- 与 ADR-0301、ADR-0312、ADR-0315、ADR-0316 同一个理由：孤立的代理项编不成 UTF-8，宽松的编码换成 U+FFFD 得到的仍是合法的文本，收的一方看不出来，不同的标识落到同一个条目、锁、文档或队列上。
- 契约收在文法上：标识与配置在进来的那一刻就拒收，进不了任何存储、请求与签名。
- 判定只有一份，放在所有包都引用得到的原语层，规范里也只有一处定义。

## 影响

- **公开 API**：
  - `XiHan.Framework.Primitives.UnicodeText`（`Stable`）与它的 `HasLoneSurrogate(ReadOnlySpan<char>)`。
  - `WorkflowMessages.InstanceCorrelationInvalid`。
  - 其余签名不变；九个选项成员从自动属性改成带校验的初始化器，`PublicAPI` 的写法不变。没有新的错误码与配置键。
- **程序集体积**：Primitives 103424 字节、Kernel 408064 字节，都没有变。`.text` 节的余量 Primitives 从 320 到 88 字节，Kernel 从 184 到 120 字节。
- **对已有部署与代码的行为变化（升级须知）**：
  - 已登记 Baggage 键的值有孤立的代理项时，载体入站、`App.CreateContext` 的选项、插件元数据与 Wasm 中间件丢弃这个成员，`WithBaggage` 抛出 `ArgumentException`；幂等键照旧留着，交给 Idempotency 阶段。
  - `HttpInvocation.FormatBaggage` 遇到这样的值抛出 `ArgumentException`；以前写成 `%EF%BF%BD`。
  - `ResourceName` 的 ID 段有孤立的代理项时构造抛出、`TryParse` 为假；`AddAuditDetail` 的键同样抛出。
  - 工作流：启动与信号的关联 ID 有孤立的代理项时返回 `WORKFLOW_VALIDATION_002`，实例查询的关联 ID 集合同样。
  - 知识库：摄入逐篇、删除整批返回 `AI_VALIDATION_001`，`RetrievalFilter` 构造抛出。
  - 插件的 `Configure` 不发、插件进入 `Failed` 并按退避重试，进程内插件不变。
  - 调度：`ScheduleAsync` 返回 `SCHEDULING_VALIDATION_001`，代码作业同步不过、每个周期重试并记日志。
  - 选项：Redis 缓存与 Redis 消息的键前缀、死信后缀、RabbitMQ、Kafka 与 Nacos 的那几项有孤立的代理项时，构造或从配置读取抛出 `ArgumentException`，宿主启动失败。
  - 已存的数据：这些文本以前经宽松编码存成 U+FFFD，改后照常能用 U+FFFD 的那一份读写，只是不能再用带孤立代理项的文本去访问。
  - 迁移：从外部输入拼这些标识的代码先用 `UnicodeText.HasLoneSurrogate` 判断，或在来源处按严格的 UTF-8 核对；配置里的这几项去掉孤立的代理项。
- **规范**（规范工作区已提交）：
  - 改了 RFC-0001、0006、0008、0009、0013、0014、0015、0021、0022，`conventions/baggage-keys.md`、`plugin/lifecycle.md`、`conformance/README.md`、`conformance/profiles.json`。
  - 两个向量文件，一个是新的。
- **Go 一致性模块**：新增的类型与函数只增不改；`IsBaggageValueAcceptable` 拒收不是合法 UTF-8 的值。
- **六个 SDK**：Baggage 的值的判定都要跟（PHP 的 `preg_match('//u')` 已经拒收不合法的 UTF-8，只差用例；Rust 的 `&str` 不用改），并回放新的两个数组。其余几类标识 SDK 里没有对应的判定。
- **同类而没改的**（报告另列）：
  - 插件元数据里的幂等键：宿主在 Handle 阶段把调用交给插件时经 protobuf 写出，有孤立代理项的幂等键写成 U+FFFD。没有 Idempotency 阶段的宿主不拒它。
  - 工作流的发起人 `StarterId`。
  - `Workflow.Database` 的 `HolderId`，以及 Kubernetes Lease 的 `holderIdentity`（所有者已定维持，写给外部服务的文本）。
  - OpenTelemetry 的 `ServiceName`。
  - 不在这一条里的：
    - `HttpProtocolOptions.RoutePrefix` 只在进程内匹配路由，入站的路径解码不出孤立的代理项。
    - `RemoteConfigurationOptions.Prefix` 是进程内的配置键。
    - 租户与名字的声明类型与令牌里的声明比较，令牌是 JSON，读不出孤立的代理项。
  - 审计的显式动作 `SetAuditAction` 只拒空白。
  - 资源名的 ID 段收控制字符（`[^/\s]` 放过 U+0000–U+0008 等），写进日志能断行。
  - ADR-0316 的 `BlobKey.HasLoneSurrogate` 与 `CacheKey` 的私有判定没有换成 `UnicodeText`：这一轮另有代理在改对象存储。
- **测试**：
  - `UnicodeTextTests`：四种孤立的代理项与合法的文本，与严格的 UTF-8 编码互相核对。
  - `BaggageValueVectorTests`：回放两个新数组；`WithBaggage` 对它们抛出，幂等键照留。
  - `InboundBaggageTests`：`App.CreateContext` 丢掉有孤立代理项的关联 ID，留下幂等键。
  - `WebHostTests`：两个只差在孤立代理项上的幂等键以前写成同一个头，改后 `FormatBaggage` 抛出；成对的代理项往返不变。
  - `ResourceNameVectorTests`：回放新的向量；以码元写出的 ID 段直接构造同样被拒。
