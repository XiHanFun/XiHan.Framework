# ADR-0177 插件读宿主配置与绑定要授予

## 状态

已采纳（`spec/plugin/lifecycle.md` §1 修订）。

## 日期

2026-11-12

## 背景

5.0 安全审查 S-02（`plans/5.0-安全审查.md`），高危。

- 进程外与 Wasm 宿主组装 `Configure` 请求时，把清单 `contributes.config.section` 指向的整节原样序列化给插件，清单 `bindings` 列出的每个绑定也照名交出。
- 配置节只受文法 `^XiHan:…` 约束，不要求属于插件，也不经授予。
- 后果：一个零权限的插件（Wasm 的 README 写明它适合不受信任的插件）在清单里写 `XiHan:Security:Jwt`，就能拿到 JWT 密钥并伪造任意主体的令牌；`XiHan:ObjectStorage:SignedUrls:Secret`、数据库连接串、AI 与 S3 的密钥同理，拿到后经插件自己的操作响应或日志带出去。
- 进程外插件的环境变量白名单也因此形同虚设：以 `XiHan__…` 环境变量注入的密钥照样经 `Configure` 交出。

复现：`ConfigurationSection_NotGranted_RejectsThePluginAtDiscovery`（进程外与 Wasm 各一个）。修正前，没有授予配置节的插件照常启动并拿到配置。

## 备选

1. **配置节限定在 `XiHan:Plugins:<清单 ID>` 之下**：否决。配置节文法是 PascalCase 段，清单 ID 是小写点分，放不进去；示例插件现有的 `XiHan:Echo`、`XiHan:Cache` 也都在这个范围之外。
2. **把 `config:` / `binding:` 加进清单 `permissions` 的文法**：否决。清单已经用 `contributes.config` 与 `bindings` 声明了要读什么，再在 `permissions` 里写一遍只是重复；改清单文法还要动 Schema 与已有插件。
3. **沿用运营方的授予**：采纳。清单照旧声明要读什么，运营方在宿主配置 `Grants:<清单 ID>` 里逐项授予。这与清单声明、宿主授予的权限模型一致，插件改不了。

## 决策

1. **`PermissionGrant`（`Kernel`，`Stable`）新增**：
   - 前缀常量 `ConfigurationPrefix = "config:"`、`BindingPrefix = "binding:"`。
   - `MissingConfigurationGrants(manifest)`：清单的配置节要求授予 `config:<配置节>`（与清单逐字相同），每个绑定要求授予 `binding:<绑定名>`，返回其中没有授予的。
   - 不改 `Missing(manifest)` 的语义：进程内插件是受信代码，本来就能读整个配置，不受此限。
2. **进程外与 Wasm 宿主的预检**：把没有授予的配置节与绑定并进「清单声明而未授予的权限」，在发现时（或运行期加载时）以 `PLUGINS_DENIED_001` 拒绝，不启动插件代码。错误消息列出缺的授予，运营方照着补。
3. **只做精确匹配**：授予 `config:XiHan:Echo` 不覆盖 `XiHan:Echo:Sub`，也不覆盖 `XiHan:Echoes`。插件要哪一节就授予哪一节。

## 影响

- 行为：声明了配置节或绑定的进程外、Wasm 插件，运营方不授予就不再加载。升级时按错误消息在 `XiHan:Plugins:<OutOfProcess|Wasm>:Grants:<清单 ID>` 里加 `config:<配置节>` 与 `binding:<绑定名>`；示例插件对应 `config:XiHan:Echo`、`config:XiHan:Cache`。
- 运行期 `LoadAsync` 由调用方给出授予，同样要带上这两类。
- 公开 API 只有新增；插件清单文法与插件协议都不变。
