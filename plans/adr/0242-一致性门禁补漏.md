# ADR-0242 一致性门禁补漏

## 状态

已采纳（`spec/manifest/manifest.schema.json`、`conventions/error-codes.md`、`rfcs/0002-manifest.md` 随之修订，规范新增 `tools/speccheck`；各实现的可观察行为不变）。

## 日期

2026-11-19

## 背景

两份外部评审指出规范与各实现的门禁会静默变绿。逐条按代码核对后，成立的有下面这些：

- **清单 Schema 与 RFC-0002 不一致**：Schema 给 `provides` / `requires` 加了 `uniqueItems`，而 RFC-0002 第 3 步按 Schema 查形状，重复要到第 4 步才报 `duplicate_provides` / `duplicate_requires`。向量「重复提供同一能力」的两项完全相同，照 Schema 实现会报成 `kernel.manifest.invalid`。Schema 的接口版本也不限上界，RFC 要求不超过 2147483647，两个超过 32 位的向量 Schema 照收。CI 从没拿 Schema 核对过向量。
- **登记表有缺口**：`KERNEL_CAPABILITY_006` 在 .NET 源码、RFC-0002 与 64 个清单向量里都在用，登记表只登记到 005。撤销过的 `LOCALIZATION_VALIDATION_001`、`MESSAGING_UNAVAILABLE_003` 只在 RFC 正文里提到，登记表没有撤销记录，「序号不复用」无从核对。
- **破坏性变更检查从没执行过**：`buf breaking` 只在 pull_request 上跑，而规范的提交都直接推到 main。规范、Go、TypeScript、Rust 的生成物检查用 `git diff`，看不到新生成的未跟踪文件。
- **向量回放没有全集约束**：22 个向量文件，没有任何地方要求每个文件都被回放或被豁免。.NET 回放 18 个，漏了 `wire-encoding`、`callback-status`、`wasm-exports`、`caching-distributed`；Go 回放 20 个；其余四个 SDK 各 19 个。Go 的 `conformance.Names()` 从没被调用。
- **缺 Go 时静默通过**：黑盒运行器的测试找不到 Go 时，Java、TypeScript、PHP 跳过，Rust 打印一句后返回、被记成通过。只有 Python 在 CI 里设了强制变量。Go 的 echo / cache 测试不核对运行器的用例全集。
- **SDK 的 CI 只在 main 上触发**：日常提交在 dev，推到 dev 的改动不过 CI。
- **.NET 构建作业没有超时**：它串着六个服务容器，默认上限是 6 小时。

评审的其他论断不成立，或属于另行决定的事，不在本 ADR：规范分层与向量受众、版本标签、`protocol_version` 的升级规则。

## 备选

1. **向量加受众字段，按受众判定 Stable**：这次不做。这属于规范分层，另行决定。在那之前由各实现的豁免表承担这件事，分层定下后用受众取代豁免表。
2. **登记表改成机读的 JSON**：现在不做。Markdown 表已经有两处解析（.NET 架构测试与 `tools/speccheck`），行的格式固定就能核对；改格式还会牵动文档站与命令行工具的知识库。
3. **在 conformance 模块的测试里做 Schema 校验**：否决。这要引入 JSON Schema 库，而 conformance 是 Go SDK 的运行时依赖，库会进入用户的模块图。所以另建独立模块 `tools/speccheck`。
4. **Schema 保留 `uniqueItems`，改 RFC 让重复在第 3 步报出**：否决。这会改变 .NET 与六个 SDK 的可观察行为，错误键会从 `duplicate_provides` 变成 `invalid`。而且 `uniqueItems` 按整项比较，查不出 ID 相同、版本不同的重复，`duplicate_*` 本来就得留着。
5. **缺 Go 时默认失败，另起一个变量名**：否决。沿用 Python 已有的 `XIHAN_CONFORMANCE_REQUIRED`，取值改为默认强制、恰好为 `0` 才跳过，六个 SDK 一个口径。

## 决策

1. **Schema**：`provides` / `requires` 去掉 `uniqueItems`。新增 `$defs/interfaceVersion`，pattern 精确到 1–2147483647，`primitives` 与 `provides[].version` 引用它。`requires[].version` 同样设上界，可带一个 `^`。RFC-0002 记一次修订。各实现的手写形状本来就是这样判的，行为不变。
2. **登记表**：
   - 登记 `KERNEL_CAPABILITY_006`。
   - 新增「已撤销的错误码」一节，记 `LOCALIZATION_VALIDATION_001`（ADR-0070）与 `MESSAGING_UNAVAILABLE_003`（ADR-0082）。
   - 新增规则 5：正文、向量与协议里出现的框架错误码（错误码域在术语表里）必须已登记或已撤销，撤销的码不再登记。
3. **`tools/speccheck`**：规范仓库新增的独立 Go 模块，只有测试，CI 加这一步。它核对四项：
   - 登记表自洽：不重复，错误码域在术语表里，撤销的码不再登记。
   - 正文、向量、协议与 Go 源码里出现的框架错误码都已登记或已撤销。
   - 两个 Schema 按 2020-12 编译通过。
   - 清单向量与 Schema 一致：`valid` 过得了 Schema，`kernel.manifest.invalid` 过不了，`primitives.manifest.*` 过得了。
4. **规范 CI**：推送时与推送前的那个提交比 `buf breaking`。生成物检查改用 `git status --porcelain`。
5. **.NET**：
   - 回放 `wasm-exports`：Plugins.Wasm.Tests 按向量现场生成 WAT 模块，交给 `WasmModule.Load` 判定。
   - 回放 `caching-distributed`：Caching.Remote.Tests 核对操作集；请求的写出与响应的读入经适配器自己的源生成上下文；非法键与非法选项在本地就构造不出来。
   - `wire-encoding` 与 `callback-status` 豁免并写明理由：原语层没有 Result / Error 的 JSON 编解码；回调失败的映射在插件一侧，而 .NET 是宿主。
   - 架构测试 `SpecVectorCoverageTests` 要求每个向量文件在测试源码里以字符串字面量出现，或被豁免。`NamingTests.ErrorCodes_InSourcesAreRegistered` 要求正式包里的框架错误码字面量都已登记。
   - 构建作业 `timeout-minutes: 30`。
6. **六个 SDK**：
   - 向量全集测试：回放与豁免的并集等于规范的全部向量文件，两者不相交，列出的文件都存在。Go 以 `conformance.Names()` 为准。
   - 运行器测试缺 Go 时默认失败，`XIHAN_CONFORMANCE_REQUIRED=0` 才真正跳过。Rust 没有运行期跳过，打印原因后返回。
   - Go 的 echo / cache 测试核对用例序列等于运行器的全集，不许名单外的跳过。cache 插件没有订阅，`event` 是名单内的跳过。
   - CI 在 main 与 dev 上触发。TypeScript、Go、Rust 的生成物检查改用 `git status --porcelain`。

## 理由

这几处缺口有一个共同点：规范或实现变了，而本该报出来的检查没有跑，或跑了也看不见。

- 全集测试让「规范新增向量」在七个实现里都变成失败，直到被回放或带理由豁免。
- 错误码检查让「用了没登记的码」在规范与 .NET 两边都失败。
- Schema 检查让 Schema 不再与 RFC 各说各话。

这些检查都只读规范文件与测试源码，不改任何公开 API。

## 影响

- 可观察行为不变：没有实现在运行时读 Schema，修改后的 Schema 与 RFC、各实现一致。
- 以后规范新增向量文件，七个实现的测试都会失败，直到回放或在豁免表里写明理由。这是有意的。
- Go SDK 的测试不能 import 运行器的包 `conformance/plugin`：运行器的 `internal/pluginv1` 与 SDK 的 `plugin/v1` 都注册 `plugin.proto`，初始化时 panic。用例全集改从同一版本运行器的 `help` 输出读取，格式一变测试即失败。根治要动 proto 的生成路径，留给 proto 多语言选项那一项。
- SDK 的 submodule 指针不动（仍是 `b66630a`），向量集合没有变化。
- 不在范围：规范分层与向量受众、版本标签、`protocol_version` 的升级规则；.NET 的 Result / Error JSON 编解码；PHP `ProcessTest` 在没有 pcntl 时的跳过。
- 测试：反证都做过。用原来的 Schema 与登记表跑 `tools/speccheck`，三处不一致与 `KERNEL_CAPABILITY_006` 都被报出；从各 SDK 的回放集合删掉一个文件，全集测试失败并报出它；PATH 里去掉 Go，运行器测试默认失败，设 `XIHAN_CONFORMANCE_REQUIRED=0` 时跳过。
