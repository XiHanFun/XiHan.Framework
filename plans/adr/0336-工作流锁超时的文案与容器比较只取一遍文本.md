# ADR-0336 工作流锁超时的文案与容器比较只取一遍文本

## 状态

已采纳（规范 `conventions/error-codes.md` 的 `WORKFLOW_TIMEOUT_001` 说明已改；本仓库 `Workflow.Abstractions` 实现；错误码、消息键、参数与配置键不变，RFC-0021 不变）。

## 日期

2026-11-27

## 背景

ADR-0326 留下的两条，仓库所有者已拍板：

1. **锁超时的文案写成实例**。`workflow.lock.timeout` 的模板是「等待工作流实例 '{id}' 的锁超时」，en-US 是 `Timed out waiting for the lock of workflow instance '{id}'.`。锁键早就不只是实例 ID：定时启动用定义 ID，重用策略查重用 `start.` 开头的派生键（RFC-0021「锁」），ADR-0326 之后目录改写已有的定义也取定义 ID 的锁。目录的批量操作里拿不到锁的那一项，调用方看到的是「工作流实例 '<定义 ID>'」。错误码登记表里 `WORKFLOW_TIMEOUT_001` 的说明同样写着「实例锁等待超时」。
2. **容器之间比较还取两遍文本**（ADR-0326 备选 7 留下的）。两个容器 `==` 深比较、`contains` 的元素与要找的值都是容器时，读的一方量规模（`ExpressionRun.Read`、`ReadItems`、`ReadTimes`）取一遍容器里每个字符串的文本，深比较（`SameScalar`）比到时再取一遍。从 JSON 文本读来的字符串每取一次都要解码全文、分配新的字符串；由别的 CLR 类型构造的每取一次都要经转换器写一遍 JSON。实测：两个各有一个 1048576 码元字符串、从 JSON 文本读来的数组 `left == right`，一次分配 8389032 字节，是解码一次（2097208 字节）的四倍。

## 备选

文案：

1. **10 个区域改成「工作流的锁」**：采纳。占位符名 `id` 不变（`LocalizationTests` 核对占位符一致），说法不限于实例：zh-CN「等待工作流的锁 '{id}' 超时。」，en-US `Timed out waiting for the workflow lock '{id}'.`，其余八个区域照同样的意思改。
2. **按锁键的种类各用一条消息**：否决。锁键是不透明字符串（RFC-0021「锁」：Provider 不得假设它是实例 ID），取锁的一方（`IWorkflowInstanceLock` 的实现）不知道它是哪一种；多几个键也要改 Provider 的契约。
3. **改参数名为 `key`**：否决。改参数名是改消息键的契约，已经翻译过的应用目录与按参数取值的调用方都要跟；`id` 也说得通。
4. **错误码登记表的说明一起改**：采纳，非规范性的措辞（PATCH），注记 ADR-0336。`WorkflowErrors.LockTimeout` 与 `WorkflowMessages.LockTimeout` 的 XML 文档随之改。

容器比较：

5. **量规模时把取出的文本记下，深比较按同一个值找回**：采纳。
   - 新增内部类型 `Expressions/ComparedTexts`：按引用记「值 → 已取出的文本」，只记取文本要解码或经转换器写出的值，进程内的字符串取出来就是同一个实例、不记；同一个值在两侧（`a == a`）也只取一次。
   - 两个容器 `==` 时 `ExpressionRun.ReadContainers(left, right)` 先左后右各记一笔（与以前的两次 `Read` 相同），交回这份文本；`contains` 每次调用建一份，`ReadItems` 量容器元素、`ReadTimes` 量容器的要找的值时记进去。
   - `DeepEqual` 与 `SameScalar` 多一个参数，字符串取这份文本；没记的（超过 64 层、量的时候只算一个值的容器里的）照常现取。
   - 结果与工作量都不变：只换了取文本的地方，读取量照旧按 RFC-0021「长度与上限」从同一段文本的长度算。
6. **深比较的同时量规模**：否决，ADR-0326 备选 7 的理由仍在：深比较按结构走、先比个数，可能半途分出不等；读取量要在比较之前把两个容器量完（向量里的工作量与比较的结果无关）。
7. **把容器复制一份、里面的字符串换成取出的文本**（照标量的 `Materialize`）：否决。`JsonNode` 只能有一个父节点，复制要为每个值新建节点，比记一张表重得多。
8. **表一直留在 `ExpressionRun` 里，跨运算复用**：否决。一次求值最多读一千六百多万个码元，留着就把这些文本都挂在求值的生命周期里；一次比较一份、比完即弃。
9. **基准**：仓库里没有表达式的基准（`benchmarks` 只有管道与启动），按当前线程分配的字节核对，见「影响」。

## 决策

1. **文案**（`Workflow.Abstractions`）：`workflow.lock.timeout` 的 10 个区域改成不限于实例的说法，占位符不变；`WorkflowErrors.LockTimeout`、`WorkflowMessages.LockTimeout` 的 XML 文档与包 README 写明锁键的三种来源。规范的错误码登记表同步。
2. **容器比较**（`Workflow.Abstractions`）：新增内部的 `ComparedTexts`；`ExpressionRun` 新增 `ReadContainers`，`ReadItems` 与 `ReadTimes` 多收一份文本；`ExpressionCompiler` 的相等与 `contains` 把它交给 `AreEqual` / `DeepEqual` / `SameScalar`。

## 理由

- 文案说的应当是调用方能对上的东西：锁键有三种来源，「工作流的锁」对三种都成立，参数照旧带着锁键本身。
- 取文本只发生在量规模的那一处，比较只查表，与 ADR-0326「写文本的地方只有一处、量的规则只有一处」同一个做法。

## 影响

- **公开 API**：没有变化。消息键、参数、错误码与配置键不变。
- **行为**：
  - `WORKFLOW_TIMEOUT_001` 的文案变了，应用按文案匹配的要改按错误码判断；应用自己的目录覆盖了这个键的不受影响。
  - 表达式的结果与工作量不变。实测从 JSON 文本读来、各有一个 1048576 码元字符串的两个数组 `left == right`，一次分配从 8389032 字节降到 4194856 字节（两侧各解码一次）；`contains` 在元素是对象的数组里找一个对象，从四次解码降到 4196584 字节。
- **规范**（规范工作区已提交）：`conventions/error-codes.md`，PATCH。
- **六个 SDK**：不受影响（没有工作流）。
- **测试**（`Workflow.Abstractions.Tests` 的 `ExpressionBudgetTests`）：
  - `ComparingContainers_TakesEachStringOnce_AndKeepsTheResults`：以自定义转换器构造、每取一次文本记一次数的值，`==`、`!=`、同一个值两侧、`contains` 的元素与要找的值都是容器，每个字符串最多取一次，结果钉住。
  - `ComparingContainersReadFromJson_DecodesEachStringOnce_AndGivesTheSameResultsAndWork`：上面的分配不超过两次解码加一半；从 JSON 读来与进程内构造的同一份值，结果与工作量相同。
  - 先红后绿：改之前前者有四个值取了两次，后者分配 8389032 字节。`expression-limits.json` 的读取量向量照旧通过。
- **文档**：`Workflow.Abstractions` 的 README 已同步；文档站与更新日志待改。
