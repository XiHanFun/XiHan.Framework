# ADR-0176 操作请求体在授权之后读取

## 状态

已采纳（RFC-0011「执行」第 4 条与 `protocol/http.md` 修订；新增错误码 `PROTOCOLS_VALIDATION_011`、`PROTOCOLS_VALIDATION_012`）。

## 日期

2026-11-12

## 背景

5.0 安全审查 S-07（`plans/5.0-安全审查.md`），中危。

- `UseXiHan()` 在进内核管道之前就调用 `OperationPayloadBinder`。绑定器把请求体整个复制进 `MemoryStream`，解析成 `JsonDocument`，再改写进 `ArrayBufferWriter`。
- 框架不设上限，只有 Kestrel 缺省的 30 MB；也不看 `Content-Type`。
- 这一切发生在 Resilience（限流、并发上限）、Authenticate 与 Authorize 之前：匿名调用方往需要权限的 POST 操作发近 30 MB 的 JSON，一个请求就占数百 MB 内存，并发几十个就能耗尽内存，限流与并发上限也看不到这些请求。
- `text/plain` 的 JSON 照样受理，浏览器跨站的简单请求（不触发预检）因此能调用操作。

复现：`OperationPayloadBindingTests`。匿名调用方发格式错误的 JSON，修正前回 400（先解析），修正后回 401；超限与 `text/plain` 的请求体修正前都被受理。

## 备选

1. **只加上限，仍在进管道前读**：否决。上限压低了单个请求的代价，但匿名与被限流的请求照样让宿主读请求体。
2. **宿主登记一个排在 Authorize 末尾的中间件读载荷**：否决。同阶段次序要靠显式的 Before/After，而授权中间件与校验中间件都可能没装配，约束的对象不存在时排序直接失败。
3. **内核提供延迟读取的载荷来源，Validate 阶段先读**：采纳。读载荷本来就属于 Validate 阶段，Validate 排在限流、认证、租户与授权之后。

## 决策

1. **内核（`Kernel.Operations`，`Stable`）**：
   - 新增委托 `OperationPayloadSource(CancellationToken)`。
   - 新增 `SetOperationPayloadSource(source)`，以及 `ResolveOperationPayloadAsync()`：已有载荷直接返回；没有而有来源时读一次、放进上下文；读取失败返回该失败；都没有时无值。
   - 内置的 `ValidationMiddleware` 开头先解析，失败即以它结束调用。
2. **宿主**：`UseXiHan()` 不再在进管道前调用绑定器，只把它包成载荷来源放进上下文。读取失败是调用的失败结果，与其他失败一样经管道（观测、审计）后写成 Problem Details。
3. **端点**：`MapXiHanOperations()` 的端点处理先解析载荷来源。关掉内置中间件、没有 Validate 阶段时，载荷在这里读；没有来源仍按 `UseXiHan()` 位置不对报错。
4. **绑定器（`OperationRequestBinder`）**：
   - 上限 `HttpProtocolOptions.MaxRequestBodyBytes`（`XiHan:Protocols:Http:MaxRequestBodyBytes`，缺省 4 MiB），超过返回 `PROTOCOLS_VALIDATION_011`。
     - `Content-Length` 超过时不读请求体。
     - 没有长度声明（分块、HTTP/2）时把服务器的请求体上限压到同一个值，自己按读到的字节数再判一次，读到上限即停。
   - 有请求体时 `Content-Type` 必须是 `application/json` 或 `+json` 结尾的类型（不分大小写、忽略参数），否则返回 `PROTOCOLS_VALIDATION_012`；有内容却没有声明类型同样拒绝。
   - 两者都是 `VALIDATION`，HTTP 400。框架的状态码按错误种类映射，不为单个错误码映射 413 与 415。
5. MCP 与 CloudEvents 的端点本来就在 Handle 阶段（授权之后）读请求体，不受第 1 条影响；它们的请求体与批量上限归入审查的资源上限一批（S-20）。

## 影响

- 行为：
  - 被限流、没有认证或没有权限的操作请求不再读请求体，错误码也随之变成限流、401 或 403，不再是载荷不合法。
  - 以 `text/plain`、表单或不带 `Content-Type` 发 JSON 的客户端会收到 `PROTOCOLS_VALIDATION_012`，要改成 `application/json`。
  - 超过 4 MiB 的操作请求体会被拒绝；需要更大请求体的应用调大 `MaxRequestBodyBytes`，文件走对象存储的上传端点。
- 公开 API 只有新增：`OperationPayloadSource`、`SetOperationPayloadSource`、`ResolveOperationPayloadAsync`、`HttpProtocolOptions.MaxRequestBodyBytes` 与 `DefaultMaxRequestBodyBytes`、`HttpErrors` 与 `HttpMessages` 的两项。
- 自己在 Validate 阶段实现校验（关掉内置中间件）的应用，要先调用 `ResolveOperationPayloadAsync()` 才能看到载荷。
