# ADR-0254 重复实现收拢第一批：分片清单、请求体限长读取、MCP 标准输入与几处漂移

## 状态

已采纳（新增公开成员 `BlobMultipart.ValidateParts`、`HttpInvocation.ReadBodyAsync`、`McpStdioTransport.OpenInput`、`PluginMessages.NotWasm`；规范不变）。

## 日期

2026-11-24

## 背景

对正式包做了一轮「同一件事写了几遍」的审计。重复的总量不大，问题在于副本各自演化，已经出现行为分叉。这一批收拢其中改动小、分叉已经造成缺陷的几处：

- **分片上传的完成清单**：文件系统与 S3 各校验一遍。S3 那份不查空项，清单里有 `null` 时抛 `NullReferenceException`，文件系统抛 `ArgumentException`。先后也不同：文件系统先看上传在不在、再看清单，S3 在本地只能先看清单；上传不存在且清单为空时，一个报 `OBJECTSTORAGE_NOTFOUND_002`，一个报 `OBJECTSTORAGE_VALIDATION_002`。
- **限长读取 HTTP 请求体**：`Protocols.Http`、`Protocols.Mcp`、`Protocols.CloudEvents` 各一份。后两份逐字相同，都比第一份少两步：不把服务器对这次请求的上限压到自己的上限，也不接服务器读到一半报的 413。上限配得比服务器的大时，超限的请求由服务器答复一个不带协议错误体的 413。
- **MCP 的标准输入读取器**：应用的 `mcp` 命令显式关掉按 BOM 探测编码；命令行工具的 `mcp` 命令另建读取器，用的重载缺省会按 BOM 改用别的编码，与前者注释里刻意避免的行为相反。
- **Wasm 宿主核对清单种类**：从进程外宿主复制来的代码沿用了消息键 `plugins.process.not_out_of_process`，清单不是 Wasm 插件时文案说的是「不是进程外插件」。
- **操作 ID 文法**：原语层的 `OperationId` 以 `\z` 收尾，源生成器的那份以 `$` 收尾，会放过结尾的一个换行；这样的 ID 编译通过、启动时才失败。架构测试 `RegexAnchorTests` 只扫 `[GeneratedRegex]`，生成器用 `new Regex`，没被拦到。
- **`HttpProtocolOptions` 的 `MaxRequestBodyBytes`**：解析时不判下界，`0` 落到属性里才被拒绝，消息不带配置键；MCP 的同名项在解析处就判。
- **gRPC 的认证失败判定**：`GrpcStatusMapping` 重新声明了 `SECURITY_DENIED_001` / `003` 两个字面量，宿主包已有公开的 `ProblemResponse.IsAuthenticationFailure`。

## 备选

1. **用链接文件或 `InternalsVisibleTo` 共享内部实现**：否决。`src` 下没有链接文件的先例（ADR-0134 否决过），新增友元要求确切版本引用。照已有做法，把共用的东西放成下层包的公开成员。
2. **分片清单：只让 S3 补上空项检查，两边各留一份**：否决。这正是漂移的来源。
3. **分片清单：文件系统保持「先看上传在不在」**：否决。S3 做不到同一个先后，两个 Provider 对同一份输入就给不出同一个错误。清单本身是否合法不依赖存储，先查它对两边都成立。
4. **请求体读取放进内核**：否决。它依赖 `HttpContext`，属于 HTTP 宿主；三个协议包本来就引用 `Hosting.AspNetCore`。
5. **Wasm 的清单种类复用进程外的键、只改文案**：否决。一个键一个意思，文案里的「进程外」是键的含义的一部分。
6. **一并收拢两个插件宿主之间约 650 行的重复**：这一批不做。那部分涉及登记与撤回的锁次序，要分步抽取并靠一致性套件兜底，另行处理。

## 决策

1. `ObjectStorage.Abstractions` 的 `BlobMultipart` 新增 `ValidateParts(parts)`（`Stable`）：
   - 只看清单本身：为空返回 `OBJECTSTORAGE_VALIDATION_002`（`objectstorage.parts.empty`），编号不是严格升序返回同一个码（`objectstorage.parts.unordered`，`part` 是第一个违规的编号）；清单里有 `null` 抛 `ArgumentException`。
   - 文件系统与 S3 的 `CompleteAsync` 第一步都调用它，然后才访问存储。分片是否上传、ETag 是否相符、非末片是否过小仍由各自判定。
2. `Hosting.AspNetCore` 的 `HttpInvocation` 新增 `ReadBodyAsync(httpContext, maxBytes, cancellationToken)`（`Stable`），返回 `Maybe<byte[]>`：
   - `Content-Length` 超过上限不读；没有声明长度的边读边计数，超过即停，读到的内容不留。
   - 读之前把服务器对这次请求的上限压到 `maxBytes`，只调低不调高。
   - 服务器读到一半报 413 按超过处理；别的 `BadHttpRequestException` 原样抛出。
   - 三个协议包都改用它，各自把「没有值」翻译成自己的错误。
3. `Protocols.Mcp` 的 `McpStdioTransport` 新增 `OpenInput(stream)`（`Preview`）：按 UTF-8 解码，跳过开头的 UTF-8 BOM，不按 BOM 改用别的编码。应用的 `mcp` 命令与命令行工具的 `mcp` 命令都用它。
4. `Plugins.Protocol` 的 `PluginMessages` 新增 `NotWasm`（`plugins.module.not_wasm`，参数 `id`、`kind`、`isolation`，10 种区域），Wasm 宿主核对清单种类时用它。
5. 源生成器的操作 ID 正则以 `\z` 收尾。
6. `HttpProtocolOptions.FromConfiguration` 在解析处拒绝小于 1 的 `MaxRequestBodyBytes`，消息带配置键。
7. `GrpcStatusMapping` 改调 `ProblemResponse.IsAuthenticationFailure`。

## 理由

- 这几处的共同点是「本该一致的两份代码已经不一致」。只修分叉的那一份，下次改动还会再分叉；收成一处，分叉无从发生。
- 新增的三个公开方法都放在消费方已经依赖的包里，不改变依赖方向，也不引入新的共享机制。

## 影响

- **行为变化**（都在同一个错误码之内，或原先是未处理异常）：
  - 文件系统存储：上传不存在且清单为空或乱序时，由 `OBJECTSTORAGE_NOTFOUND_002` 变为 `OBJECTSTORAGE_VALIDATION_002`；清单里同时有乱序与未上传的分片时，报乱序而不是未上传。
  - S3 存储：清单里有 `null` 时由 `NullReferenceException` 变为 `ArgumentException`。
  - MCP 与 CloudEvents 入口：请求体超过服务器自己的上限时，答复各自的错误（`PROTOCOLS_VALIDATION_*` 的请求体过大），不再是服务器的裸 413。
  - 命令行工具的 `mcp` 命令：标准输入以 UTF-16 BOM 开头时不再改按 UTF-16 解码。
  - Wasm 宿主：清单不是 Wasm 插件时消息键由 `plugins.process.not_out_of_process` 变为 `plugins.module.not_wasm`，错误码不变。
  - 操作 ID 结尾带换行的操作在编译时报 XHG003，原先到启动才失败。
- 自写 `IBlobMultipartStore` 的 Provider 应当在 `CompleteAsync` 开头调用 `BlobMultipart.ValidateParts`。
- 审计里其余的重复（两个插件宿主、各选项类的配置读取、数据库 Provider 的工作单元外壳与租约、消息代理的投递骨架）不在这一批。
