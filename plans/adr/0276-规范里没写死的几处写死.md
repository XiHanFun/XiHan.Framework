# ADR-0276 规范里没写死的几处写死

## 状态

已采纳（framework-spec 已修订：缓存键长度的单位、截止时间的文本、操作 ID 的上限、激活事件的主题、应用清单 Schema、规范用语、RFC-0018 并入 `plugin/wasm.md`、保留的能力 ID；本仓库的规范指针已更新到 `c90faf8`；.NET 与各 SDK 的跟进见「影响」）。

## 日期

2026-11-24

## 背景

ADR-0258 的那轮审计除了重复书写与过时段落，还列出一批规范性的问题：没有向量盯住的地方实现已经分歧，Schema 比正文宽，登记表里有只占了名字的 ID，正文用语没有定义。那些要改实现的行为，当时没有动。这次逐项核对代码后，成立的是下面八处：

1. **缓存键的长度没有单位**。RFC-0006 写「不超过 512 字符」。.NET 的 `CacheKey.IsValid` 按 UTF-16 码元计（`value.Length`），Go SDK 的 `caching.IsKey` 按 UTF-8 字节计（`len(key)`）。171 个汉字（171 个码元、513 字节）的键 .NET 收下，交给 Go 写的远程缓存插件就以 `CACHING_VALIDATION_001` 被拒。其余五个 SDK 没有缓存键的代码。
2. **`xihan-deadline` 没有文法**。插件协议的 `InvocationMetadata.deadline` 有严格的文法与向量（ADR-0237），HTTP 载体只写着「RFC 3339，UTC」。.NET 的 HTTP 入口（`HttpInvocation.Create`，HTTP、gRPC、MCP 的 Streamable HTTP 与认证方案 `XiHan` 共用）用 `DateTimeOffset.TryParse`：空格代替 `T`、没有偏移、没有秒、只有日期、偏移不带冒号、首尾空白、HTTP 日期、`11/18/2026` 都读得出，只有时间的补上系统当天的日期，比 100 纳秒细的小数四舍五入，`9999-12-31T23:59:59.999999999Z` 反而读不出。六个 SDK 不读这个头。
3. **操作 ID 的 128 上限只在 .NET**。`OperationId.MaxLength = 128`，清单读取、握手核对、契约与调用请求都经它；规范、清单 Schema 与六个 SDK 都没有上限，129 个字符的操作 ID 在 SDK 里合法、到了宿主被拒。
4. **`onEvent:` 写不了带下划线的主题**。主题文法（RFC-0009）允许 `_`，清单 `activation` 的 `onEvent:` 与 `onOperation:` 共用 `[a-z0-9.*-]`，`order_events` 能订阅却写不成激活事件。
5. **应用清单 Schema 比正文宽**。`packaging/app-manifest.md` 写 `name` 是 `^[a-z][a-z0-9-]{0,62}$` 且不以 `-` 结尾，Schema 只有前半句；`bindings.<name>.secret` 与 `leader.lease` 用同一个正则。`xihan pack` 一直按 DNS 标签核对（`^[a-z]([a-z0-9-]{0,61}[a-z0-9])?$`），Schema 放行的 `orders-` 到它那里才被拒。
6. **规范用语没有定义**。「必须」「不得」「应当」「可以」的约束力没有出处，正文又大多写成不带这些词的陈述句。
7. **RFC-0018 还有几条只在它那里的规则**。ADR-0258 把「设计」缩成概览时留下了「`wasm.md` 没有写的细节」，其中有规则：可贡献的范围、可用的 WebAssembly 提案、握手应答的核对、单条日志 16384 字节的上限、`net.outbound:` 声明即加载失败、再入计入嵌套深度、表的元素数上限、健康轮询、崩溃细节 `trap` 的写法。
8. **能力登记表里有没实现的 ID**。`domain.model`、`persistence.document`、`search.fulltext`、`actors.virtual`、`hosting.aspnetcore`、`hosting.commandline`、`testing` 七个，.NET 与六个 SDK 里都没有清单提供。

## 备选

1. **缓存键按 UTF-16 码元计**：否决。它是 .NET、Java 与 JavaScript 字符串的内部表示，Go、Rust、Python、PHP 没有这个概念；键最后落到 Redis 与线上的 JSON 里都是 UTF-8。按码位（字符）计同样要各语言各算一遍，且与存储的容量脱节。
2. **`xihan-deadline` 另定一条宽一些的文法**（比如照收任意 RFC 3339、允许没有偏移）：否决。两条文法就要两套向量、两个解析器；没有偏移的时间按哪个时区读各语言不一致。取已有的那一条，HTTP 与插件协议共用。
3. **`xihan-deadline` 读不出时返回 400**：否决。现状是读不出当作没有，`grpc-timeout` 照常生效；改成报错会让带着别的格式的老调用方整个请求失败，而截止时间是可选的。
4. **把操作 ID 的上限从 .NET 去掉**：否决。操作 ID 会进路由、gRPC 方法名、MCP tool 名、消息键（`<操作 ID>.title`，消息键自己也限 128）与持久化的列，要有上限；128 已经随 5.0 的 Stable API 发布。
5. **`onEvent:` 的模式收紧成「主题文法或带 `*` 的前缀」**：这次不做。宿主目前只看有没有 `onStartup`，不解释模式；通配的匹配规则另行规定时再一起收紧。这次只把字符集放宽到与主题一致。
6. **清单 Schema（`manifest.schema.json`）也加跨字段约束**（插件必须有 `isolation` 等）：否决，理由同 ADR-0242 备选 4：RFC-0002 第 3 步照 Schema 查形状、报 `kernel.manifest.invalid`，跨字段约束在第 4 步报各自的消息键，写进 Schema 会改变七个实现报出的错误。清单 Schema 与正文逐条对过，除了操作 ID 的上限与激活事件两处（本 ADR 第 3、4 条），没有正文禁止而 Schema 放行的写法。
7. **应用清单的跨字段约束硬写进 Schema**（`ports.grpc` 不等于缺省的 8080 之类只能表达一半）：否决。JSON Schema 不能比较两个成员，表达一半反而让人以为 Schema 查全了；正文新增一节把这几条列出来，交给读取核对。
8. **「应」按国标的用法定为要求**（GB/T 1.1 的「应」是 shall）：否决。正文里情态的「应」只有十几处，都是建议（「应提醒本人」「应优先用异步成员」「至少应含 `en-US`」），要求一律写「必须」或陈述句；照 RFC 2119 的通行译法，「应当」对 SHOULD。
9. **删掉没实现的能力 ID**：否决。「能力 ID 一经发布不改」，删了以后别人可以拿同一个名字指别的东西。标成保留。
10. **RFC-0018 独有的规则继续留在 RFC**（ADR-0258 当时的做法）：这次并过去。那些是规则，Wasm 的规范性文本应当自足。

## 决策

1. **缓存键与键前缀按 UTF-8 编码后的字节数计，不超过 512 字节**（RFC-0006「存储契约」「键管理」、`provider/caching-distributed.md` §2）。前缀与键同一条规则，只是可以为空。同时写明控制字符指 Unicode 的 Cc 类。代数缓存区直写范围与条目的上限、区名的上限随之改为 128 字节，否则三段各 128 个非 ASCII 字符拼出的键会超过 512 字节。
2. **截止时间的文本只有一条文法**，写进 RFC-0003 新增的规则 8：`^[0-9]{4}-[0-9]{2}-[0-9]{2}[Tt][0-9]{2}:[0-9]{2}:[0-9]{2}(\.[0-9]{1,9})?([Zz]|[+-][0-9]{2}:[0-9]{2})\z` 加各段的取值范围，读不出当作没有，比时钟精度细的小数截断；框架写出时用 UTC、七位小数、`+00:00`。HTTP 的 `xihan-deadline` 与插件的 `InvocationMetadata.deadline` 共用，文法的出处从 `plugin/invocation.md` §2 移到规则 8、内容不变。`protocol/http.md` 写明它是单值头、整串匹配、不再裁剪，读不出（含空值、出现多次）当作没有这个头；`protocol/grpc.md` 写明这时 `grpc-timeout` 照常生效，`grpc-timeout` 的数值是 1 到 8 位数字。
3. **操作 ID 不超过 128 个字符**写进 `conventions/operation-ids.md`、RFC-0011 与 RFC-0002 解析规则 2 第 3 步，清单 Schema 的 `contributes.operations[]` 补 `maxLength: 128`。
4. **`onEvent:` 的模式是 `[a-z0-9._*-]+`**，`onOperation:` 不变。清单 Schema、RFC-0002 与 `plugin/lifecycle.md` §3 随之修订。
5. **应用清单 Schema 收紧到与字段表一致**：`name`、`bindings.<name>.secret`、`leader.lease` 共用 `$defs/dnsLabel`。`packaging/app-manifest.md` 写明后两个是 DNS 标签，新增「Schema 之外的约束」列出 Schema 表达不了的五条。
6. **规范用语**：新增 `conventions/normative-language.md`，RFC-0024 新增一节引到它。「必须 / 须」「不得 / 不能 / 不可 / 禁止」「应当 / 应 / 应该」「不应当」「可以 / 可 / 可选」对应 RFC 2119 的五个关键词；规范性内容里的陈述句与「必须」同等约束；要求落在行为上，只约束认领了所属档的实现。只加定义，已有正文不改。
7. **RFC-0018 独有的规则并入 `plugin/wasm.md`**，RFC 改为引用，规则不变；参考实现的选项名与默认值留在 RFC。
8. **没实现的能力 ID 标成「保留，尚无实现」**并新增一节说明现状，不删。`configuration.secrets` 有契约、适配器与一致性套件（RFC-0014），只是没有内置的 Provider 包，不算保留。
9. **向量与规则**：
   - 新增 `caching/cache-keys.json`（档 `caching` 与 `provider:caching.distributed@1`，36 条）、`primitives/operation-ids.json`（档 `core`，34 条）、`context/http-deadline.json`（档 `host`，37 条）。
   - `manifest/manifests.json` 加 6 条（128 与 129 个字符的操作 ID、带下划线的 `onEvent:`、三种不合法的激活事件），`plugin/deadlines.json` 的 `invalid` 加 16 条宽松写法，`provider/caching-distributed.json` 的 `invalidKeys` 加一个多字节的超长键。
   - Go 规则包新增 `IsCacheKey`、`IsCacheKeyPrefix`、`IsActivationEvent`、`HTTPDeadline`、`ParseGRPCTimeout`，`IsOperationID` 加上限。
   - `tools/speccheck` 新增两个测试：应用清单字段表的每一行都有 Schema 必须拒绝的例子；能力登记表的保留标注与「保留」一节一一对应。

## 理由

- 八处有一个共同点：规范说得不够死，实现各按各的理解做了，或者只有参考实现做了。没有向量的地方迟早分歧，所以每一处能用向量表达的都补了向量，并让 Go 一致性模块回放。
- 取严不取宽：键长度取字节（码元数不超过字节数，按字节计只会更严）；截止时间取已有的严格文法；操作 ID 取 .NET 已经发布的上限。唯一放宽的是 `onEvent:`，因为原来的文法与主题文法自相矛盾。
- 期望值仍由 .NET 算出。例外是这次要改 .NET 的那几条（按字节计才超长的键、HTTP 入口照收的宽松写法、带下划线的 `onEvent:`），它们按规则给出，向量的 `$comment` 逐条标明。

## 影响

规范的级别（RFC-0024）：第 1、2、4 条是 MAJOR（`v1.0.0` 之前允许），第 3、5、6 条是 MINOR，第 7、8 条是 PATCH。

**.NET（XiHan.Framework）**

- `Caching.Abstractions`：`CacheKey.IsValid` 改按 `Encoding.UTF8.GetByteCount(value) <= 512`（`Stores/CacheKey.cs`），异常消息与 XML 文档写明单位；`GenerationCache<T>` 的 `MaxRegionLength` 与 `MaxLiteralLength` 改按 UTF-8 字节计（`Caches/GenerationCacheOfT.cs` 的构造与 `Encode`）。按码元计合法、按字节计超长的键从此被拒，这是行为变化。
- 文案：`caching.inspector.prefix_invalid`（`Caching.Abstractions`）与 `caching.remote.key_invalid`（`Caching.Remote`）各 10 个区域写着「512 个字符」，改成「512 字节（UTF-8）」。
- `Hosting.AspNetCore`：`HttpInvocation.Create` 读 `xihan-deadline` 改用规则 8 的严格解析。现有的 `PluginDeadlines.TryParse` 在 `Plugins.Protocol` 里是 internal，宿主引用不到，把解析与写出提成两处共用的一份（照 `TraceParent` 的先例放进原语层，或放进内核）。gRPC、MCP 与认证方案 `XiHan` 经同一个入口，不用另改。`grpc-timeout` 的读法不变。
- `Kernel` 与 `Primitives`：激活事件的正则两处（`Capabilities/ManifestShape.cs`、`Manifests/Manifest.cs`）的 `onEvent:` 加上 `_`。
- 操作 ID：不用改。
- 测试：回放三个新向量文件（架构测试 `SpecVectorCoverageTests` 按文件名核对）；`ManifestVectorTests` 在放宽激活事件之前会在「激活事件的主题带下划线」上失败；`RemoteCacheVectorTests.InvalidKeys_CannotBeBuilt` 在改 `CacheKey` 之前会在新加的多字节键上失败。
- 文档站：`docs/appendix/spec.md` 的目录说明（`conventions/` 加规范用语）、向量与 RFC 表；缓存与 HTTP 宿主两页写明键长度的单位与 `xihan-deadline` 的写法。

**六个 SDK**

- 全部：操作 ID 的判定加 128 个字符的上限（Go 随一致性模块升级自动带上）；读清单的激活事件文法给 `onEvent:` 加 `_`；回放新向量 `primitives/operation-ids.json`。`manifest/manifests.json` 与 `plugin/deadlines.json` 的新用例随已有的回放自动跑到。
- Go 另有：回放 `caching/cache-keys.json`（它认领 `provider:caching.distributed@1`）；`caching.IsKey` 本来就按字节计，不用改；示例 `examples/cache` 的文案「512 characters」改成字节。
- 截止时间：六个 SDK 只读插件元数据的 `deadline`，文法没变，不用改。

**不变**

- 线上协议（`plugin.proto`）没有改动，`buf breaking` 通过。
- Wasm 宿主、能力求解与 `xihan pack` 的行为不变。

**没有解决的**

- 不能编码成 UTF-8 的键（孤立的代理项）算不算合法，规范没说。
- 代数缓存区键里 `<长度>` 的单位规范没写（.NET 是 UTF-16 码元数）。
- 清单 `version` 的正则比 SemVer 宽（放行前导零与空的预发布标识），清单 `bindings[].type` 的正则比应用清单的六种类型宽；收紧要改七个实现的读取，没有动。
- `testing` 不合能力 ID 文法，只能作为保留项留着。
- 128 个字符的操作 ID 派生的消息键 `<操作 ID>.description` 会超过消息键自己的 128 上限。
