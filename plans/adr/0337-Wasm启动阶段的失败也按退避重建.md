# ADR-0337 Wasm 启动阶段的失败也按退避重建

## 状态

已采纳（规范 `plugin/wasm.md` §5 与 RFC-0018 的状态行已改；本仓库 `Plugins.Wasm` 实现：`WasmPluginRuntime` 新增 internal 的 `ScheduleRestart`，`WasmPluginHost` 的 `AttachAsync` 与 `LoadAsync` 在启动失败之后调用它；公开面、错误码、消息键与配置键不变；修订 ADR-0260 决策 4 与 ADR-0325 备选 10、11）。

## 日期

2026-11-27

## 背景

- ADR-0260 把两个宿主的退避重启收进共用的 `PluginLifecycle`，载体差异留在调用方：进程外宿主在启动阶段失败（握手、`Configure`、`Start`）之后也排退避重启（`ScheduleRestart`），Wasm 宿主只在运行期崩溃之后排，启动阶段的失败不在后台重试，留给下一次调用按需再试。ADR-0067 写过 Wasm 的握手失败不重试。
- ADR-0325 给 Wasm 补「绑定有孤立代理项」的用例时照实测写了两条路径：启动时配置失败是下一次调用按需再试（调用方拿到配置这一步的错误），崩溃之后的重建失败接着退避。要不要让启动阶段的失败也排退避重启（备选 11）提请所有者决定。
- 规范 `plugin/lifecycle.md` §6 写的是进程外的说法（「终止进程」），`plugin/wasm.md` §5 只写了陷阱后的重建，启动阶段的失败没有写。
- 仓库所有者拍板：启动阶段的失败也排退避重启，与进程外一致；发现阶段的握手失败仍不重试。

## 备选

1. **`WasmPluginRuntime` 加排退避重启的入口，宿主在 `AttachAsync` / `LoadAsync` 启动失败之后调用**：采纳。与进程外宿主同一个位置、同一个组件（`PluginLifecycle.ScheduleRestart`），重启做的事已经有了（`IPluginCarrier.RecoverAsync` 即 `EnsureRunningAsync`：重建实例、握手并核对声明、配置、启动），退避期间的调用沿用 `IsRestartPending` 按不可用失败。
2. **在 `EnsureRunningAsync` 里失败时直接排重启**：否决。懒激活插件的首次调用、重启次数用完之后的按需再试也走这里，`lifecycle.md` §6 规定懒激活的首次调用失败由下一次调用再试；按调用方区分要多传一个参数，宿主那一处本来就知道自己在启动。
3. **发现阶段（探测启动）的实例化与握手失败也重试**：否决（拍板）。进程外宿主会重新探测并补登记声明，Wasm 宿主没有这条补登记的路径，也没有为它的需要。
4. **只在 `AttachAsync` 排，运行期加载的失败照旧只返回给调用方**：否决。进程外宿主两处都排（`lifecycle.md` §6「运行期显式加载的同类失败同样返回给调用方，插件保持 `Failed` 并按策略重试」），一处不排又是一处载体差异。
5. **排重启时带不带调用方的异步流**：不带（`ExecutionContext.SuppressFlow`）。崩溃之后的重建已经这样启动（`Background`），回调流的标记与调用方的上下文不该漏进后台的重建；进程外宿主没有回调流的标记，照旧。

## 决策

1. **规范**（`plugin/wasm.md` §5，MINOR，写明以前不作规定的行为）：新增「启动阶段的失败」一条——宿主装配时启动 `onStartup` 的插件、运行期加载后启动插件，组装 `Configure` 请求、`xihan_configure` 或 `xihan_start` 失败：丢弃实例，插件 `Failed`，与进程外插件相同按 `lifecycle.md` §6 退避重启实例并重走握手、配置、启动，计入 `RestartLimit`；运行期加载的这类失败照样返回给调用方、插件按策略重试直到 `UnloadAsync`；重启时的实例化、握手与核对失败接着退避；退避期间的调用与投递以 `PLUGINS_UNAVAILABLE_001` 失败，不按需抢跑；发现阶段失败的不重试；懒激活插件首次调用时的失败由下一次调用再试。RFC-0018 状态行追加 2026-11-27 写明，对应 ADR 加 0337。
2. **实现**（`Plugins.Wasm`）：
   - `WasmPluginRuntime.ScheduleRestart()`（internal）：在 `ExecutionContext.SuppressFlow` 里调 `PluginLifecycle.ScheduleRestart`；发现时被拒、已显式停止或已有重建在退避中时什么都不做（组件本来的判断）。
   - `WasmPluginHost.AttachAsync`：启动失败记日志之后调它。`LoadAsync`：启动失败时调它，再把错误返回给调用方。
   - `WasmPluginStatus.Restarts` 的说明改成「崩溃或启动阶段失败后自动重建实例的累计次数」；运行时与宿主的 XML 文档、包 README 照改。
3. **测试**（`Plugins.Wasm.Tests` 的 `WasmPluginBindingTests`）：
   - `Binding_WithALoneSurrogate_FailsTheConfigureStep_AndTheNextCallTriesAgain` 改为 `…_AndIsRetriedWithBackoff`（主值、属性值两例）：宿主启动后插件 `Failed`、原因照 ADR-0321、重启 0 次、宿主 `Degraded`；退避期间的调用是 `PLUGINS_UNAVAILABLE_001`（以前是配置这一步的错误）；推过 1 秒的退避，重建失败、原因相同、重启 1 次、排上第二次退避（等日志里的第 2 次排期，见第 4 条），之后的调用仍是不可用；改正绑定、推过 2 秒的退避，插件 `Ready`、重启 2 次、宿主 `Ready`。
   - 新增 `Binding_FixedBeforeTheBackoffEnds_IsPickedUpByTheRebuild_NotByACall`：退避结束之前改正并调用，仍是不可用；推过退避后插件 `Ready`、重启 1 次。
   - 新增 `Binding_WithALoneSurrogate_InAPluginLoadedAtRuntime_ReturnsTheFailure_AndIsRetriedWithBackoff`：运行期加载的启动失败返回给调用方，之后的调用是不可用，改正后推过退避即 `Ready`、重启 1 次。
   - 崩溃之后的那条（`…FailsTheRebuildAfterACrash_AndIsRetriedWithBackoff`）照过，不改。
   - 另外三条启动时配置失败的用例（属性过多、必需的没给、类型不同）换上不推进的时钟：它们读的是启动之后的状态，真实时钟下 1 秒后的重建可能正好在读状态时进行（`Resolved`）。
   - 新增的三条在改之前都失败（退避期间的调用拿到的是配置错误或直接重建成功）。
4. **用例怎样知道一次重建已经结束**：重启计数在退避结束、重建之前递增，重建失败前后插件的状态与错误相同，看状态与计数分不出；等运行时记下下一次排期的日志（`… will be rebuilt in … (attempt N).`），记下时这次重建已经结束、插件又在退避里。用例经 `LogCapture` 收日志。

## 影响

- **行为**（`Plugins.Wasm`，Experimental）：启动 `onStartup` 的插件与运行期加载的插件启动失败之后，宿主在后台按退避重建（1、2、4 秒……上限 60 秒，计入 `RestartLimit`，与进程外相同）；以前留给下一次调用按需再试。退避期间的调用与投递由「按需再试一次（往往得到同一个启动错误）」变成 `PLUGINS_UNAVAILABLE_001`；改正配置之后，插件在下一次退避结束时恢复，不再由调用带起来。`WasmPluginStatus.Restarts` 把这些重建也计进去。
- 不变的：发现阶段（实例化与握手）失败的插件不重试；懒激活插件首次调用时的失败由下一次调用再试；重启次数用完之后插件保持 `Failed`，与进程外一样之后的调用可以按需再试一次（`PluginLifecycle` 原有的行为）。
- **公开面**：不变；没有新的错误码、消息键与配置键。
- **规范**：`plugin/wasm.md` §5 与 RFC-0018 状态行，MINOR。向量不变；Wasm 插件一侧（客体）的义务不变。
- **六个 SDK**：不受影响（宿主一侧的行为）。

## 理由

- 两种载体的插件在同一个宿主里并存，运营方看到的是同一个状态机：启动失败之后一个自己恢复、一个要等有人调用，诊断与告警都要分两套。
- 退避而不是按需：配置错了的插件每来一次调用就重建一次实例、组装一次请求、记一次失败，调用越多重试越密；退避把重试的节奏交给宿主，调用方立即得到不可用，与崩溃之后相同。
- 发现阶段不重试：没有握手成功过的插件没有声明，宿主登记不了它的操作，重试成功也没有入口；进程外宿主为此另有补登记的路径，Wasm 不为没有需求的场景加一条。
