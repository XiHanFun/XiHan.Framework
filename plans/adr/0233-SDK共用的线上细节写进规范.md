# ADR-0233 各语言 SDK 共用的线上细节写进规范

## 状态

已采纳（`spec/rfcs/0001-primitives.md`、`0002-manifest.md`、`0003-invocation-context.md`、`0004-pipeline-stages.md`、`0010-localization.md`、`0011-operations.md`、`conventions/baggage-keys.md`、`manifest/manifest.schema.json` 随之修订，新增向量 `conformance/vectors/primitives/wire-encoding.json`、`message-templates.json`、`kernel-messages.json`，`baggage-keys.json` 增加值的用例）。

## 日期

2026-11-16

## 背景

TypeScript、Rust、Java、Python、PHP 五个 SDK 按 Go SDK 的形状实现原语五包（primitives、manifest、invocation、pipeline、operation）时，发现有几处规范只写在 .NET 的文档注释或语言文件里，或者干脆没写。各 SDK 只好自己取舍，结果互相对不上：

- 无值成功的编码：RFC-0001 只给出 `{"ok":true,"value":…}`。.NET 的文档注释写的是 `{"ok":true}`，TypeScript 与 Rust 照它写；Go、Java、Python、PHP 写的是 `{"ok":true,"value":{}}`，PHP 还拒收 `{"ok":true}`。
- 内核消息键只在 .NET 的 `Localization/en-US.json` 里。Go 把载荷不合法写成了 `kernel.operation.payload_invalid`，宿主目录里没有这个键，翻译不出来；PHP 跟了 Go，另外四个 SDK 跟了 .NET 的 `kernel.operation.invalid_payload`。中间件以成功短路、处理器没有产出响应时，各家给出的结果也不一样：OK 加空载荷、`PRIMITIVES_VALIDATION_002`、`KERNEL_UNEXPECTED_001` 都有。
- 模板的 `:format` 是 .NET 的格式串。Go 用 printf 动词，插件把目录交给 .NET 宿主后会被误读。值的文本形式也不一致：布尔写 `True` 还是 `true`，`null` 写 `<nil>` 还是空串，浮点会不会写成 `2.0`。
- 根调用的 trace-flags：RFC-0003 说没有上游时"为空"，可是 `traceparent` 总要写标志位。
- 接口版本：RFC-0001 说 `^N` 与 `N` 等价，Schema 却只允许依赖里的版本带 `^`。清单 Schema 里操作 ID 的 pattern 也比操作 ID 文法宽。
- Baggage 值的 256 个字符，.NET 按 UTF-16 码元计，PHP 按码点计。
- RFC-0002、0003、0004 引用的 `vectors/manifest`、`context`、`pipeline` 目录不存在。

## 备选

1. 规范只写原则，细节留给各 SDK 的测试互相对照。
2. 以 .NET 参考实现的现有行为为准，把细节写成规范条文，配向量；.NET 只改确实不可移植的一处。
3. 另定一套语言中立的规则，.NET 跟着改。

## 决策

采用备选 2。

- **无值成功**编码为 `{"ok":true}`，不写 `value`。有值成功的 `value` 必填，只有值类型是 Maybe 时可以是 `null`。失败的 `error` 必填，不能带 `value`。`ok` 必填且是布尔。读取方拒绝这些组合之外的写法，未知成员忽略（v1 只增不改）。
- **Error** 写出时成员顺序是 `code`、`message`、`messageKey`、`details`、`inner`：`message` 总有、非空；`messageKey` 只在有键时写；`details` 为空时不写；没有 `inner` 时不写。可选成员缺失表示没有，写成 `null` 不合法。
- **消息键**最长 128 个字符，与 .NET 的 `MessageTemplate.MaxKeyLength` 一致。
- **模板**：
  - 占位符名、字面量花括号、转义、宽松与严格格式化的规则，按 .NET `MessageTemplate` 的现有行为写进 RFC-0010。
  - `:format` 规定一个各 SDK 必须支持的可移植子集 `D`、`X` / `x`、`F`、`N`，按不变文化解释。舍入按值的精确十进制展开，正好一半时取偶数：.NET 10 实测 0.125 写 `F2` 得 `0.12`、2.5 写 `F0` 得 `2`，起草时写成远离零，向量回放后按参考实现改正。其余说明符是 .NET 格式串，SDK 不支持时按无格式输出。
  - 值的文本形式：字符串原样，整数十进制，布尔 `true` / `false`，`null` 为空串，浮点在 [1e-4, 1e15) 内写最短往返的十进制、不用指数、整数值不带小数点。
  - `Describe` 的参数顺序与范围外的浮点不作规定。
- **内核错误**：SDK 与宿主共用的错误码、消息键与参数写进 RFC-0011，en-US 模板放进向量 `kernel-messages.json`。中间件以成功短路、处理器没有产出响应时为 `KERNEL_UNEXPECTED_001` + `kernel.operation.no_response`，与 .NET 一致。
- **追踪**：上下文里没有上游的标志仍为空；写出 `traceparent` 时写采样决定，没有采样器的实现写 `01`。是否采样只看最低位。
- **清单**：接口版本是十进制数字字符串，只有 `requires[].version` 可以带 `^`。成员名区分大小写，不收 `null`。Schema 里操作 ID 的 pattern 收到与操作 ID 文法一致。
- **Baggage 值**：长度按 UTF-16 码元计；控制字符指 U+0000–U+001F、U+007F–U+009F。不合的成员由构造调用上下文的入口丢弃：宿主是载体入站与 `App.CreateContext`，SDK 是上下文的构造函数。
- **SDK 范围**：管道的运行期改动（`UseOwned` / `RemoveOwnedBy`）、幂等回放与 Schema 校验是宿主能力，语言 SDK 可以不提供。RFC 里引用的、还不存在的向量目录改成"规划中"，现在由各实现移植的测试覆盖。
- **.NET 要改的一处**：`MessageTemplate.Format` / `TryFormat` / `Describe` 里的布尔改写为 `true` / `false`。原先用 `Convert.ToString` 写成 `True` / `False`，这是 .NET 独有的写法。.NET 的测试回放 `message-templates.json` 与 `kernel-messages.json`。

## 理由

- .NET 是参考实现，宿主翻译插件错误用的是它的目录与格式化。以它的现有行为为准，宿主与插件之间不会再出现一边写、另一边认不出的情况，代价只落在 SDK 上，而 SDK 还没有发布。
- 备选 1 正是这次分歧的来源：五个 SDK 各自对照 Go，Go 自己就和 .NET 不一致。
- 备选 3 要改 .NET 已经 `Stable` 的格式化，换来的规则并不比现有的更好。
- 布尔是唯一的例外：`True` 只是 `Convert.ToString` 的副产品，别的语言照做反而别扭；细节本来就要求是 JSON 值，按 JSON 的写法更自然。

## 影响

- Go SDK 与五个新 SDK 按本 ADR 改齐，Go SDK 的破坏性改动（无值成功的编码、`:format` 改用可移植子集、`payload_invalid` 改名、`Unexpected` 的参数顺序）写进它自己的 README 与提交说明。
- .NET：布尔参数在消息与 `Describe` 里由 `True` / `False` 变为 `true` / `false`。公开 API、错误码、消息键与配置键都不变。
- 一致性：新增三个向量文件，`baggage-keys.json` 增加 `values`；运行器的 `vectors` 子命令与 `rules` 增加对应的核对。
