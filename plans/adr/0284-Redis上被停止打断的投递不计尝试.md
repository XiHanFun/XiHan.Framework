# ADR-0284 Redis 上被停止打断的投递不计尝试

## 状态

已采纳（`Messaging.Redis` 的消费循环在放弃一条投递时把它的投递次数退回一次，包的公开面不变；`Messaging.Conformance` 的 `DeliveryLog` 新增 `BlockingAttempts`、`MessageBrokerConformance` 新增一条用例，`Preview`；RFC-0009「投递」第 3 条、Redis 一节与「一致性」已修订）。

## 日期

2026-11-24

## 背景

ADR-0261 定了「被停止打断的投递不是失败，不计入尝试上限」，ADR-0275 给一致性套件加了「处理器正在处理时停止消费，这次投递不进死信、重新开始消费后重新投递」的用例。四个代理都过了这条用例，但 Redis 是靠用例只在**第一次**尝试上打断才过的：

- `Messaging.Redis` 的尝试号就是消费组待确认列表里的投递次数：`XREADGROUP` 读到新条目时是 1，原位重试之前 `XCLAIM` 给自己加一，回收时 `XAUTOCLAIM` 再加一。
- 被停止打断的投递不确认、留给回收（ADR-0261 的 `Abandon`）。条目留在待确认列表里，投递次数是被打断的那一次的尝试号；重启后（或别的实例）回收它，次数又加一。被打断的那一次因此实际上计入了尝试上限。
- 没到上限时后果是少一次尝试。赶上**最后一次**尝试时，回收到的投递次数是上限加一，消费循环按「已经投过上限次」处理：不派发，直接写进死信流（ADR-0261 决策 7）。一次正常的停机就把一条还有机会处理成功的消息送进了死信。
- 内存代理与 RabbitMQ 的尝试号随消息走，放弃时不变；Kafka 的原位计数不落盘，重启后从 1 起。只有 Redis 这样。ADR-0275 的备选 15、16 因此没有让套件断言再到达时的尝试号，也没有在最后一次尝试上打断，把这种情形留在各代理自己的测试里。

同一个计数还有两处被白白加一，也是停机造成的：

- `XREADGROUP` 一次取一批（`BatchSize`，默认 10），依次派发。停止时这一批里还没轮到的条目留在待确认列表里，投递次数已经是 1，而它们一次也没有派发过；回收之后从第 2 次尝试起。`MaxAttempts` 配成 1 时，它们不经处理就进死信。
- `XAUTOCLAIM` 一次认领一批，认领即加一。停止时还没轮到的条目同样白加了一次；连着几次停机都赶上，条目会一路加到超过上限。

## 备选

1. **回收时扣掉被打断的次数**（把「被打断过几次」另存一处，回收判定时减去）：否决。要多一个键（或在条目上加字段，而流的条目不可改），还得保证它与待确认列表一起过期、一起被清理；写这个键与放弃这条投递之间同样有「来不及写」的窗口，并不比直接改计数更安全。
2. **回收时不再让计数加一**（`XAUTOCLAIM … JUSTID` 后再读条目）：否决。回收到的条目多数来自崩溃的实例，那一次算不算只能靠计数；不加一，让进程崩溃的消息每次都以同一个尝试号回来，永远进不了死信。
3. **放弃时立即确认并重新 `XADD`**（像 RabbitMQ 那样把尝试号放进条目）：否决。一条流上挂着全部消费组，重新写入会让每个组再收一遍；写入与确认之间崩溃还会丢消息或重复。
4. **回收到的超上限条目照样派发一次**：否决。这是「宁可多投」的最简单做法，但死信写入失败的条目（已经真实失败过上限次）回收时也在这条路径上，它们会被多处理一次；让进程崩溃的消息在上限之后还会再把进程打崩一次。
5. **放弃时把投递次数退回一次**：采纳。`XCLAIM … RETRYCOUNT <n> JUSTID` 可以直接设置计数（带 `RETRYCOUNT` 时不再自增）。停止是有序的，消费循环在放弃的那一刻知道条目的 ID 与尝试号，Redis 连接要到代理释放时才关闭。
6. **退回时不核对归属**（直接 `XCLAIM`）：否决。处理得比 `ClaimIdleTimeSeconds` 久的条目可能已经被别的实例认领并在处理，无条件 `XCLAIM` 会把它抢回来、把别人的计数改掉。在一段 Lua 里先 `XPENDING` 核对条目仍在本消费者名下、次数与本实例看到的相同，再改。
7. **退回的同时把空闲时间设成回收阈值，让别的实例立刻接手**：这次不做。被放弃的条目处理器已经返回，立刻被认领没有重复处理的风险，停机后的重新投递也会更快；但它改的是回收的时机，不是这次要修的计数，`IDLE` 照原样写回，什么时候轮到回收与改动之前相同。
8. **只退被打断的那一条，不管读到或认领到却没派发的**：否决。它们是同一个原因造成的同一种错（没有处理却计了次数），`MaxAttempts` 为 1 时每次停机都把一批没处理过的消息送进死信。
9. **退回失败时抛出或重试**：否决。它发生在停止途中，Redis 不可达时重试只会拖住停机；不退的后果与进程被强行终止相同，是已经接受的。记一条 Warning。
10. **套件用一个新的处理器类型来打断最后一次尝试**：否决。`RecordingHandler` 加一个按尝试号阻塞的开关就够，四个代理的套件子类不用改。
11. **套件断言再到达时的尝试号等于被打断的那一次**：不做。Kafka 重启后从 1 起，这是它的位点语义决定的；套件要求的是处理器再执行一次、不进死信、尝试号不超过上限。Redis 上「仍是原来的尝试号」由它自己的测试断言。

## 决策

1. `RedisStreamConsumer` 在三处把投递次数退回一次（条目 ID 与本实例看到的次数一起交给脚本）：
   - `MessageDeliveryAttempt.RunAsync` 给出 `Abandon` 时：被打断的这一条，次数是它的尝试号。
   - 停止时 `XREADGROUP` 读到的一批里还没派发的条目：次数是 1。
   - 停止时 `XAUTOCLAIM` 认领到的一批里还没派发的条目：次数是认领之后查到的投递次数。
2. 退回由一段 Lua（`RedisStreamScripts.RestoreDeliveryCounts`）原子完成，一次可以退多条：
   - 逐条 `XPENDING <流> <组> <id> <id> 1 <消费者>`：条目不在本消费者名下（已被别的实例认领、已确认或已被裁剪），或投递次数与交来的不同，就不碰。
   - 否则 `XCLAIM <流> <组> <消费者> 0 <id> IDLE <原来的空闲毫秒数> RETRYCOUNT <次数减一> JUSTID`：只改计数，归属与空闲时间都不变。
   - 返回退回的条数。
3. 退回不随停止信号取消。失败（Redis 不可达、超时、组已不存在）只记一条 Warning，不抛出：这些条目的那一次照旧计入。
4. 没有退回的情形都照旧计入，行为与改动之前相同：进程被强行终止、实例崩溃、退回失败。回收到的条目投递次数超过上限时仍然不派发、直接进死信。
5. 一致性套件（`Preview`）：
   - `DeliveryLog.BlockingAttempts`：事件 ID 到尝试号，这个 ID 的投递只在这一次尝试上等到调用被取消；`RecordingHandler` 认它。
   - 用例 17 `LastAttemptInterruptedByStop_IsNotDeadLettered_AndIsHandledAgainAfterRestart`：前几次尝试返回失败，第 `MaxAttempts` 次正在处理时停止消息运行时；这一次不进死信，重新启动后处理器再执行一次并成功，尝试号不超过上限，之后不再投递、不进死信。

## 理由

- 被停止打断的那一次有没有计入，四个代理应当给出同一个答案；规范写的是不计入，Redis 是唯一一个在计数上把它算进去的。
- 改计数比另记一笔简单：计数本来就是尝试号的唯一来源，退回之后回收、原位重试与「超上限直接进死信」三处都不用改。
- 强杀时保守：来不及退回的那一次计入，最坏是一条消息少处理一次就进死信，死信里有它，不丢；让进程崩溃的消息每崩一次用掉一次尝试，上限次之后进死信，不会无限地投。反过来（强杀也不计）就没有这个保证。
- 核对归属与次数让退回只在「这一次确实是本实例的、之后没人动过」时生效，其余情形什么都不做，不会把别的实例正在处理的条目的计数改坏。

## 影响

- **被停止打断的投递**（竞争订阅与广播订阅相同）：
  - 没到上限：回收之后是原来的尝试号，以前是下一个。第 1 次尝试上被打断的，再到达时仍是第 1 次（以前是第 2 次）。
  - 最后一次尝试上：回收之后以最后一次的尝试号再派发一次，以前不派发、竞争订阅直接进死信流（`attempt` 字段是上限加一，没有 `error` 字段），广播订阅确认掉。
- **停止时读到或认领到却没派发的条目**：回收之后的尝试号比以前少一。`MaxAttempts` 为 1 时它们以前不经处理就进死信，现在照常处理。
- **没有变的**：
  - 实例崩溃或被强行终止：那一次照旧计入，回收之后尝试号加一，超过上限的不派发直接进死信。
  - 真实失败到上限、死信写入失败的条目：回收之后直接进死信。
  - 什么时候回收：空闲超过 `ClaimIdleTimeSeconds` 之后的下一次维护。
- **停止多出的开销**：每个消费循环在停止时至多三次脚本调用（被打断的一条、认领到的一批里剩下的、读到的一批里剩下的），只在确有这样的条目时发出。Redis 不可达时各多等一次命令超时，并各记一条 Warning。
- **公开面**：
  - `Messaging.Redis` 不变。
  - `Messaging.Conformance`：新增 `DeliveryLog.BlockingAttempts` 与用例 17。继承 `MessageBrokerConformance` 或 `MessageStreamConformance` 的测试类不用改就多跑这一条。
- **自写 `IMessageBroker` 的 Provider**：尝试号随消息走（消息头、内存里的投递对象）或不落盘的不用改。靠代理一侧的计数（投递次数、重投次数）得出尝试号的，要在放弃时把这一次从计数里退掉，否则过不了用例 17。
- **测试**：
  - 打桩数据库（不需要 Redis）：被打断的投递退回的条目与次数（第 1 次、最后一次），读到却没派发的条目一并退回，处理成功与真实失败到上限的不退。
  - 真实 Redis（设置 `XIHAN_TEST_REDIS` 时）：第 1 次尝试上被打断后待确认条目的投递次数是 0、接手的实例以第 1 次尝试投递；最后一次尝试上被打断后次数是 1、接手的实例以第 2 次尝试处理、不进死信；在最后一次尝试上消失的消费者（没有退回）留下的条目直接进死信；读到却没派发的条目都从第 1 次尝试起。
  - 套件的用例 17 在内存代理上本机运行；Redis 用本机的临时容器跑过（Redis 8），CI 用 Redis 7；RabbitMQ 与 Kafka 只在 CI 上运行。
- **规范**（RFC-0009）：
  - 「投递」第 3 条：被放弃的投递再到达时的尝试号不得因为这次放弃而超过上限；靠代理一侧的计数得出尝试号的代理在放弃时把这一次退掉，来不及退的照旧计入。Redis 由「回收让投递次数加一」改为「仍是原来的尝试号」。
  - Redis 一节：放弃时退回投递次数的做法，停止时没派发的条目同样退回，回收到的超上限条目包含哪些情形。
  - 「一致性」：套件新增最后一次尝试上被停止打断的用例。

## 没有解决的

- 消费循环中途遇到 Redis 异常（确认失败、认领失败）时，这一批里剩下的条目留在本消费者的待确认列表里，要等空闲超过回收阈值被回收，次数加一。这是出错的路径，不是停机，没有退回。
- 被放弃的条目仍要等 `ClaimIdleTimeSeconds` 才被回收（备选 7）。
- 回收途中遇到停止信号时，消费循环退出之前还会再读一批新条目（ADR-0261「影响」记过）。它们现在会被退回投递次数，但仍挂在本消费者名下，要等回收阈值过后才被别的实例接手；停止时不再读新条目可以让它们留在流里立刻被别的实例读到，这次没有改。
