# ADR-0260 两个插件宿主共用的宿主层

## 状态

已采纳（`Plugins.Protocol` 新增功能区 `Hosting`，类型全部 internal；`Plugins.OutOfProcess` 与 `Plugins.Wasm` 改用它，公开面、可观察行为、错误码与消息键不变；规范不变）。

## 日期

2026-11-24

## 背景

- 进程外宿主与 Wasm 宿主各有一套宿主层，两份之间约 650 行逐段相同：
  - 宿主：读清单与核对种类、预检、发现时被拒的登记、目录与代理操作的登记与撤回、事件投递、健康条目、附着时的启动循环。
  - 运行时：重启退避循环、健康应答到状态的映射、`Configure` 请求的组装、状态转移与「不可用」错误。
  - 其余：特性 `Configure` 里的发现循环、回调时的插件身份上下文、认证方案常量 `Plugin` 各声明一次。
- 副本之间只差载体：隔离方式与不符时的消息键、权限怎样才算授予、入口怎样解析成文件、「重新起来」做什么、自报 Failed 之后怎么办、日志措辞。
- 两份一起改才不会分叉。ADR-0085、ADR-0088、ADR-0252 的登记与撤回每次都要在两个宿主里各落一遍，规则写在两处的注释里。
- 审计另外指出两处隐患：
  - 两个宿主的登记顺序 `_order`（`List<T>`）在事件投递与健康条目里不加锁枚举，加载与卸载同时在改它；撤回失败的那条路径又用另一把锁。
  - 两份 `BuildConfigure` 都只读 `XiHan:Bindings:<绑定名>`，进程外那份的注释却写「与内核的绑定解析同源」，内核的 `BindingResolver` 还读 `SERVICE_BINDING_ROOT` 目录。

## 备选

1. **两个宿主继承一个基类**：否决。公开的 sealed 宿主不能继承 internal 基类（CS0060），基类公开就多出一份要长期维护的公开面。
2. **另开一个包放共用的宿主层**：否决。两个宿主本来就以确切版本引用 `Plugins.Protocol`，它已对两个宿主开了友元；再加一个包只多一条依赖与一份包元数据。
3. **用链接文件共享源码**：否决。`src` 下没有这个机制（ADR-0134）。
4. **在 `Plugins.Protocol` 里加一个功能区，宿主以组合使用**：采纳。类型全部 internal，载体的差异留成参数或留在宿主里，不抹平。
5. **消息键作为参数传进种类核对**：否决。架构测试要求 `new Error(...)` 的消息参数是 `<领域>Messages` 的常量；改为传隔离方式，由共用的函数按它取常量。

## 决策

1. `XiHan.Framework.Plugins.Protocol.Hosting`（新功能区，全部 internal）按风险分三步落地，每步一个提交。
2. 第一步，纯函数：
   - `PluginManifests`：`Read(directory, isolation)`、`ReadFile(directory)`、`CheckKind(manifest, isolation)`。隔离方式不符时进程外用 `plugins.process.not_out_of_process`、Wasm 用 `plugins.module.not_wasm`，别的隔离方式抛 `ArgumentOutOfRangeException`。
   - `PluginPreflight`：`Check(source, manifest, isGranted)` 核对授予与入口，返回清单里的入口；`EntryMissing(path)` 给出入口文件不存在的错误。一项权限是否授予由载体判定（进程外只看宿主授予，Wasm 的 `fs.*` 看映射）；入口怎样解析成文件留在宿主里（进程外在 Windows 上补 `.exe`，写进错误的是没有规整过的路径；Wasm 写绝对路径）。进程外先拒绝贡献中间件的清单，这一条也留在进程外宿主里。
   - `PluginConfigureRequests.Build(manifest, configuration, workDirectory)`：工作目录由载体给出（进程外在组装时准备，Wasm 在实例化时已经准备好）。
   - `PluginHealth.Read(health, manifestId)`：健康应答要进入的状态与随它记下的错误，状态为空表示不改。自报 Failed 之后怎么办留在运行时里（进程外终止进程，Wasm 按崩溃重建）。
   - `PluginIdentity`：认证方案常量 `Scheme` 与 `CreateContext`（按回调元数据建上下文，主体是插件自己）。`OutOfProcessPluginHost.PluginScheme` 与 `WasmHostFunctions.PluginScheme` 改为引用它。
   - `PluginContributions.Configure<THandler>`（原有类型，`Proxies` 区）：两个特性的发现循环里「代理操作与权限码进登记表、目录按归属注册、订阅接进容器」这一段。Wasm 的中间件登记留在 Wasm 特性里。
3. `Configure` 请求里的绑定：行为不改，仍只读 `XiHan:Bindings:<绑定名>`；注释改成与实际一致。判断见「理由」。
4. 第二步，重启退避与状态转移：
   - `PluginLifecycle`（每个运行时持有一个）：当前状态与错误（`State`、`Error`、`Status`、`Enter`、`Fail`、`Unavailable`），以及退避重启（`MarkRestartPending`、`ScheduleRestart`、`RestartAsync`、`IsRestartPending`、`Restarts`）。节奏照旧：1 秒起翻倍、上限 60 秒，只数时间窗内的重启，窗内次数达到上限后停下、插件保持 Failed。
   - `IPluginCarrier`（两个运行时实现）：`RecoverAsync`（怎样重新起来）、`IsStopped`（不该再试）与四条日志通知。日志的模板与日志器留在各运行时里，措辞不变。
   - 载体的差异都留成注入的部分，不抹平：
     - 「重新起来」：进程外是重新探测启动（首次握手还没成功过时）、交宿主登记声明、再配置并启动；Wasm 是重建实例并重走握手、配置、启动。
     - 谁来排重启：进程外在启动阶段失败（握手、`Configure`、`Start`）后也排（`ScheduleRestart`），Wasm 只在运行期崩溃后排，启动阶段的失败不在后台重试、留给下一次调用按需再试。这条差异在调用方，组件里没有分支。
     - 载体自己的串行化（生命周期锁、Wasm 的调用锁、进行中的调用计数）不进组件。
   - 一处合并：重试失败后「载体已停止就不再试」原先只有进程外查（声明登记不进去、按发现时被拒处理时令牌并没有取消）。Wasm 那份靠取消令牌退出，结果相同；合并后两边都查，Wasm 少的只是停止与取消之间那一瞬可能多记的一条「将要重建」的警告。
5. 第三步（名册）随它的提交补在这里。

## 理由

- 组合而不是继承：载体的差异是参数（隔离方式、授予判定、工作目录）或留在宿主里的那几行，读代码时一眼看得出哪些是共用的规则、哪些是载体自己的。
- 纯函数先行：没有锁、没有状态，新旧对照就能确认等价，出错的面最小。
- 退避循环与状态放在一个组件里：重启记录与状态原先就共用一把锁，「有重启在退避中」又是调用路径判断可不可用的依据，拆开只会多出一层转手。载体的锁不进来，组件就不必知道进程与实例的区别。
- 日志经接口回到运行时：两边的模板措辞不同（重启与重建），事件名与日志器类别也各是各的，放进共用组件就得改模板。
- 绑定只读配置来源是遗漏，不是有意的信任边界：
  - 信任边界是授予。清单 `bindings` 的每一项都要运营方授予 `binding:<绑定名>`（ADR-0177），按名字授予、不分来源；授予了的绑定从哪个来源解析，对「插件能拿到什么」没有区别。
  - 规范不分来源。`lifecycle.md` §2 只说 `bindings` 只含清单声明的绑定，`plugin.proto` 称它是「已解析的资源绑定」；RFC-0016 把绑定定义为 `SERVICE_BINDING_ROOT` 目录或 `XiHan:Bindings:<名字>`、由内核 `BindingResolver` 解析。
  - 进程外那份的原注释写着「与内核的绑定解析同源」，写的时候就是想同源。
  - 后果是具体的：打包生成的 k8s 清单只经 `SERVICE_BINDING_ROOT` 挂载绑定（`app-manifest.md`「映射」），那里部署的插件拿到的 `bindings` 是空的。
  - 这次不改行为：改了就是插件开始收到以前收不到的绑定，属于行为变化，要单独的决定与用例；本 ADR 只把注释改准并记下这条。补法是把内核解析好的绑定（`FeatureContext.Bindings`）交给宿主。

## 影响

- `Plugins.Protocol`：新增功能区 `Hosting`（`PluginManifests`、`PluginPreflight`、`PluginConfigureRequests`、`PluginHealth`、`PluginIdentity`、`PluginLifecycle`、`IPluginCarrier`），`PluginContributions` 新增 `Configure<THandler>`。全部 internal，`PublicAPI.Unshipped.txt` 不变。
- `Plugins.OutOfProcess`、`Plugins.Wasm`：删掉各自的清单读取、种类核对、预检里相同的部分、`Configure` 请求的组装、健康应答的映射、回调上下文的构造与发现循环里相同的一段，运行时删掉退避循环、状态字段与状态转移的三个函数，改调共用的实现。公开面与 `PublicAPI.Unshipped.txt` 不变。
- 行为、错误码、消息键、日志模板都不变；现有测试不用改。
- 测试：`PluginLifecycleTests` 用假载体与假时钟核对退避的节奏（1、2、4 秒与 60 秒上限、时间窗外的重启不计、次数用完后停下、载体停止后不再试、退避中取消）与状态的记录；真实载体上的崩溃重启仍由两个宿主的端到端用例覆盖。
- `plans/architecture/03-代码规范.md` 的功能区表给 `Plugins.Protocol` 加上 `Hosting`。
