# ADR-0048 调用来源带端点身份

## 状态

已采纳（`spec/rfcs/0003-invocation-context.md` 规则 6 修订）。

## 日期

2026-10-29

## 背景

BasicApp 6.0 N2 第四批（Files）报告：`UseXiHan()` 只把端点元数据里的 `AuthorizationRequirement` 与 `OperationDescriptor` 带进调用上下文，普通端点（文件下载等非操作端点）在 Observe 阶段的访问日志里认不出是哪个端点。BasicApp 目前用 ASP.NET Core 端点过滤器在 Handle 阶段登记身份与实际状态码，授权阶段就被拒绝的普通端点调用因此进不了访问日志。

## 备选

1. 新增 HTTP 专用的扩展（如 `context.GetEndpointName()`）放在 `Hosting.AspNetCore`：Observe 阶段的访问日志是协议无关的中间件，不该为了一个字段依赖宿主包。
2. 把端点身份放进已有的调用来源 `InvocationOrigin`（ADR-0043）：建上下文时端点已经选定（`UseXiHan()` 在路由之后），与请求目标、远端地址同一时机、同一只读项。

## 决策

采用 2。

- `InvocationOrigin` 增加 `Route`（匹配到的端点的路由模板，`RouteEndpoint.RoutePattern.RawText`，如 `/api/files/{id}`）与 `EndpointName`（`IEndpointNameMetadata`，即 `WithName`）。
- `HttpInvocation.CreateContext` 从 `HttpContext.GetEndpoint()` 读取。没有匹配到端点（404）或终结点不是路由端点时 `Route` 为空，端点没有命名时 `EndpointName` 为空。
- gRPC 的来源沿用承载它的 HTTP/2 请求（路由模板即方法路径）；MCP 子调用沿用外层 HTTP 请求（`/mcp` 端点）；其他协议没有端点，两项为空。
- 状态码仍不进来源：失败按 `ProblemResponse.StatusCodeFor`、成功按 `HttpRouteConvention.SuccessStatusCode` 推导（ADR-0043）。普通端点的实际状态码只有 ASP.NET Core 管道写完响应后才知道，需要时由应用在 Handle 阶段补记。

## 理由

- 端点身份与请求目标是同一跳的事实，放在同一个只读项里，Observe 阶段的中间件不需要知道协议。
- 路由模板让访问日志按端点聚合而不受路径参数影响，端点名给出稳定的标识。

## 影响

- 公开 API：`InvocationOrigin.Route`、`InvocationOrigin.EndpointName`（Kernel PublicAPI +4）。
- 行为：HTTP 来源多两项，原有字段不变。
- 测试：`WebHostTests`（命名端点的模板与名字、未命名端点只有模板、404 两者为空、原有来源用例补上模板）。
