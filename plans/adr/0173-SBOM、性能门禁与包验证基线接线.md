# ADR-0173 SBOM、性能门禁与包验证基线接线

## 状态

已采纳（P5-06 的前三项；安全审查另行记录）。

## 日期

2026-11-12

## 背景

开发计划 P5-06 是「包验证基线、性能基准回归、安全审查、SBOM」。总体方案 11.2 的门禁表要求：性能「BenchmarkDotNet 基线，回退超过 5% 阻断」，依赖安全「`dotnet list package --vulnerable`、SBOM，高危阻断」，包验证以同一大版本最近发布的版本为基线（ADR-0131）。现状：

- `framework/benchmarks` 有管道与启动两组基准，只在本地跑，不进 CI。
- 高危与严重漏洞在还原时已经中断构建（NU1903、NU1904 视为错误），但没有 SBOM。
- 包验证没有基线。ADR-0131 定在 5.0.0 上架后设，设置方式与流程没有实际走过。
- 开发计划第九节的预算从没测过。实测（JIT，.NET 10.0.15）如下：

  | 预算项 | 目标 | 实测 |
  | --- | --- | --- |
  | 管道，单个中间件 | 0.1 ms | 约 25 ns，32 B/次 |
  | 管道，五个中间件 | 0.5 ms | 约 54 ns，32 B/次 |
  | Primitives + Kernel 程序集 | 500 KB | 434 KB |
  | 冷启动额外开销 | 50 ms | Linux 容器 80～85 ms，Windows 54 ms |
  | 空应用常驻内存 | 30 MB | Linux 约 40 MB（运行时自己约 27 MB），Windows 约 29 MB（运行时 21.5 MB） |

  - 冷启动：全新进程里装配空应用到启动完成。Linux 上装配（能力图谱解析）约 32 ms，建容器并解析 `App` 约 34 ms，几乎都是首次 JIT 与类型加载。
  - 常驻内存：两次完整回收之后读进程常驻内存，减去同一进程装配前的读数，就是框架额外的部分。

## 备选

1. **SBOM 用 CycloneDX 工具在 CI 里对整个解决方案生成一份，作为构建产物上传**：否决。使用方拿到的是包，SBOM 应该跟着包走。
2. **SBOM 用 GitHub 依赖图导出**：否决。它在仓库外，也不进包。
3. **性能与仓库里存的固定数字比较**：否决。GitHub 托管运行器之间的硬件差异远大于 5%，门禁会反复误报。
4. **性能只在 CI 报告、不阻断**：否决。总体方案要求阻断。
5. **基准放进主作业**：否决。主作业同时开着六个服务容器、跑全部测试，噪声大，还会拉长主作业。
6. **分配在仓库里记绝对字节数**：否决。启动路径里有随操作系统变化的分配，Windows 上量的数到 Linux 上对不上。

## 决策

1. **SBOM**
   - 正式包经 `Microsoft.Sbom.Targets`（只在构建期使用，`PrivateAssets="all"`）在打包时生成 SPDX 2.2 清单，放在包内 `_manifest/spdx_2.2/manifest.spdx.json`，附带 `.sha256`。
   - 供应方是 `$(Authors)`，文档命名空间在 `https://github.com/XiHanFun/XiHan.Framework/sbom` 之下。
   - 不联网查许可证（`SbomGenerationFetchLicenseInformation=false`），构建离线可重复。
   - CI 打包之后核对每个包都带清单。
2. **性能门禁**：CI 新增与主作业并行的「性能门禁」作业，由 `framework/scripts/Test-Benchmarks.ps1` 按 `framework/benchmarks/budgets.json` 检查。
   - 绝对预算（阻断）：
     - 列出的基准都要有结果。
     - 管道单个中间件小于 0.1 ms、五个小于 0.5 ms。
     - Primitives 与 Kernel 两个程序集合计不超过 500 KB（512 000 字节）。
   - 相对回退（阻断）：同一台运行器上先构建、测试对照提交，再测当前提交。对照提交：推送取推送前的远端提交，PR 取目标分支的提交，拿不到就取上一个提交。
     - 耗时：逐个基准比较每次操作耗时的中位数，慢了超过 5% 且单侧 Mann-Whitney 检验 p < 0.01 才算回退；两边各复测一次，仍然回退才失败。
     - 分配：每次操作分配的字节数增加超过 5% 即失败。同一台机器上分配是确定的，不复测。
     - 冷启动与框架额外常驻内存：基准程序加 `--resident-memory <文件>` 探针，在全新进程里测。各跑 7 次取中位数，增加超过 5% 时复测一次，仍然超过才失败。
   - 冷启动 50 ms 与常驻内存 30 MB 两个绝对目标只报告，不阻断：JIT 模式下实测都达不到，Linux 上光运行时自己就接近 30 MB。是按框架额外开销重定预算、按 AOT 发布测，还是先做启动优化，另行决定。
   - 有意的回退用显式标记放行：最后一个提交的说明带 `[perf-accepted]`，或 PR 带 `perf-accepted` 标签。放行的只有相对回退，绝对预算照常；对照提交每次前移，接受只管这一次。
   - 对照提交还没有基准项目、构建失败或没有探针时，跳过对应的相对比较并在摘要里写明。
3. **包验证基线接线**（落实 ADR-0131 决策 2）
   - `framework/Directory.Build.props` 新增 `XiHanPackageBaselineVersion`，空表示不比对。
   - `framework/src/Directory.Build.targets` 在它有值、且包启用了包验证时设 `PackageValidationBaselineVersion`。放在 targets 里，是为了让基线发布之后才新增的包能在项目里写 `<XiHanPackageBaselineVersion />` 清空；`Cli` 不启用包验证，不受影响。
   - 本地预演：把当前代码以 `5.0.0` 打包放进本地源，再故意破坏一个 `Stable` 成员（`DistributedLockExtensions.AcquireAsync`）和一个 `Preview` 成员（`WorkflowEngineExtensions.MigrateAsync`），各自报 CP0002。`Preview` 那处用 `-p:ApiCompatGenerateSuppressionFile=true` 生成 `CompatibilitySuppressions.xml` 后打包通过；豁免的 `Target` 是成员的文档 ID，以后的豁免门禁据此核对级别。
   - 5.0.0 上架后的步骤写进 `version-release` 技能。
   - 预演拉进本机 NuGet 全局缓存的假 `5.0.0` 包已删除，否则正式版发布后会被缓存顶替。
4. **漏洞报告**：仓库根新增 `SECURITY.md`，指向 GitHub 私密漏洞报告（仓库已开启），不留个人邮箱。

## 影响

- 每个包多了约 20 KB 的清单文件；打包时间每个包多几秒。
- CI 多一个并行作业：构建两次基准，跑两轮完整基准与 14 次探针，复测时更多，不拉长主作业。
- 有意的性能或分配回退要在提交说明或 PR 上显式标记。
- 冷启动与常驻内存两项预算待定；在定下来之前，门禁只保证它们不继续变差。
