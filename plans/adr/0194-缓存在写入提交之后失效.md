# ADR-0194 缓存在写入提交之后失效

## 状态

已采纳（RFC-0008「授权」数据库 Provider 一条修订；同一做法用于租户目录）。

## 日期

2026-11-12

## 背景

5.0 安全审查 S-14（`plans/5.0-安全审查.md`），中危，审查时未复现，这里复现确认。

- `PermissionGrantRecordStore` 在调用方的工作单元里删行或加行，写入后立即让 `DatabasePermissionGrantStore` 的缓存按主体失效。
- 写入要到调用方的事务提交之后才对别的调用可见。失效与提交之间，并发的权限判定未命中缓存就重新查库，读到提交之前的旧行，再写回缓存。
- 撤销：被撤销的人在撤销提交之前持续发起调用，就能把旧授予写回缓存，保留到存活时间结束；`CacheTimeToLiveSeconds` 为 0 时永久保留，撤销对本实例永不生效。授予：新授予同样被旧值盖住，直到存活时间结束。
- 数据库租户目录（`TenantRecordStore`）的写入有同一个窗口：停用租户之后，它可能被当作仍启用写回缓存。

复现：`GrantCacheCommitTests`。修正前，撤销之后、提交之前的一次判定让已撤销的授予在提交之后仍然有效，新授予在提交之后仍然看不到。

## 备选

1. **在 `IUnitOfWork` 上加提交后回调**：否决。每个持久化 Provider 与一致性套件都要改，只为让几个缓存在提交后失效。
2. **只靠代数计数**：否决。失效之后、提交之前开始的读取拿到的代数没变，读回的旧行照样写回缓存。
3. **失效两次并按代数丢弃读取**：采纳，不改接口。

## 决策

1. **代数**：缓存记一个代数，每次失效（`Invalidate`、`InvalidateAll`）在锁内加一。读取在查库之前记下代数，写回缓存时代数变了就丢弃这次结果。
2. **失效两次**：写入方（作用域服务）写入时失效一次，作用域释放时对本作用域写过的主体再失效一次。
   - 管道里的调用先提交、后释放作用域，第二次失效时写入已经可见。
   - 提交之前读回的旧行，要么在第二次失效时被清掉，要么因代数变了写不回去。
   - 回滚之后的第二次失效无害。
3. **存活时间为 0**：仍然允许，只适用于单实例部署。失效只作用于本实例，多实例部署里别的实例靠存活时间看到撤销。
4. **租户目录**：数据库租户目录的写入与缓存用同一做法，单独提交。

## 影响

- 行为：
  - 本实例上，撤销与授予在提交之后立即生效，不再等存活时间。
  - 并发写入期间缓存的命中率略降：代数变了的那几次读取不写回缓存。
- `PermissionGrantRecordStore` 实现 `IDisposable`（公开 API 新增），由容器在作用域结束时释放，重复释放无害。
- 管道外自己开作用域写授予的代码，要在提交之后再释放作用域，与管道里的次序相同。
