# ADR-0266 对象存储正式版前的四处契约调整

## 状态

已采纳（`ObjectStorage.Abstractions`、`ObjectStorage.FileSystem`、`ObjectStorage.S3`、`ObjectStorage.Conformance` 与 `Hosting.AspNetCore` 的一处构造已改；规范 RFC-0012 的正文与错误码登记表已补）。

## 日期

2026-11-24

## 背景

对象存储的抽象包与两个存储包大多是 `Stable`，5.0.0 之后同一大版本内不能再破坏（ADR-0131）。2026-11 的全库审计在这个子系统里留下四处要在正式版之前改掉的形状：

- **命名存储实例的登记表 `BlobStores` 没有上限，移除只有单条。**
  - `GetOrAddAsync(definition)` 的定义可以来自应用的库（按租户、按用途各登记一个，ADR-0050）。登记多少个没有限制，每个 S3 实例持有一个客户端、一个条件写入的后台探测和一条健康项，实例数随应用写进去的定义无界增长。
  - `RemoveAsync(name)` 只收一个名字。批量优先（`conventions/batch-first.md`）要求按标识执行的操作以集合为入参。
  - 持久化的 `DataSourceRegistry` 是同一种登记表（按定义建实例、按名缓存、定义变了替换），ADR-0078 已经给它定了登记数上限（`XiHan:Persistence:DataSources:MaxCount`，满了返回 `PERSISTENCE_UNAVAILABLE_007`，不淘汰、替换同名不占名额）与批量移除。两个登记表的行为没有理由不同。
- **`S3BlobStore` 的公开构造收 `IAmazonS3`。** 这是 S3 包公开面上唯一一处 AWS SDK 的类型。它在 `Stable` 类型的签名里，SDK 升大版本（类型换了程序集版本或改了形状）就是本包的破坏性变更，框架的版本承诺被一个第三方包的发版节奏绑住。架构测试「公开签名不泄漏第三方类型」只约束 Ring 0～2，管不到 Provider 包。
- **`IBlobMultipartStore.AbortAsync(upload)` 只有单条。** 清理一批过期或被用户取消的上传时，调用方只能循环调它。同一子系统里 `IBlobStore` 的写入与删除早就是「接口上只有批量，单条是扩展方法」。
- **`BlobSignedUrl` 是位置记录。** `BlobSignedUrl(Uri Url, BlobUrlMethod Method, DateTimeOffset ExpiresAt, IReadOnlyDictionary<string, string> Headers)`：以后给签出的地址加任何成员（比如必带的查询参数、可用的方法集合），构造与 `Deconstruct` 的签名都要变。ADR-0142 把会演进的数据类型改成初始化器形状时漏了它。

## 备选

登记表：

1. **上限的配置键放在 `XiHan:ObjectStorage:Stores:MaxCount`（与持久化的键同形）**：否决。`Stores` 一节的子键都是实例名，配置键不区分大小写，而 `maxcount` 本身是合法的实例名（`^[a-z0-9][a-z0-9-]{0,63}$`），两者会撞。已有的探测间隔 `XiHan:ObjectStorage:StoreHealthProbeIntervalSeconds` 就是因此放在节外的，上限照它取名 `XiHan:ObjectStorage:StoreMaxCount`。
2. **仿 `DataSourceOptions` 新建一个 `BlobStoreOptions` 选项类，构造收它**：否决。注册表本来就要 `IConfiguration`（配置定义的实例首次取用时从里面读），探测间隔也是在构造里直接读的；为两个标量再加一个 `Stable` 类型和一个构造重载，换不来行为。代价见「影响」的命令行知识库一条。
3. **满了淘汰最久没用的实例**：否决，理由同 ADR-0078：淘汰会释放一个可能正在被调用使用的实例，调用落到已释放的客户端上；调用方也无从知道它手里的实例已经换了。
4. **配置里定义的实例不占名额**：否决。它们的个数确实由配置封顶，但实例占的资源和运行时登记的一样；不占名额就要给每个实例记来源，而同名的实例可以被运行时登记的另一份定义替换，来源会翻转。统一成「已建的实例都算」，规则只有一句。
5. **不加新错误码，复用 `OBJECTSTORAGE_UNAVAILABLE_002`（配额超限）配一个新消息键**（文件系统「未完成的上传数已达上限」就是这么做的）：否决。登记表满了与存储空间的配额是两回事，调用方的处置也不同（移除闲置的实例或请运维调高上限，而不是清理对象）；持久化那边用的是专门的码。代价是新码要先登记进规范。
6. **保留单条的 `RemoveAsync(name)` 作为批量的转调**：否决。`DataSourceRegistry` 只有批量；`BlobStores` 是密封类不是接口，多留一个重载就是多一行要守到下个大版本的 `Stable` 签名，而调用方写 `[name]` 没有成本。
7. **移除的实例释放失败时抛出（或汇总成一个异常）**：否决。实例已经不在登记表里，逐项结果已定；抛出会让调用方拿不到结果，单个实例的释放失败还会挡住同批其余实例的释放。照 ADR-0259「释放失败只记日志、不改变已经确定的结果」。

S3 的构造：

8. **保留公开构造，把参数换成框架自己的客户端抽象**：否决。给 SDK 再包一层接口没有第二个实现，只是把 SDK 的形状抄一遍。
9. **构造改 internal，另给一个不收客户端的公开工厂 `S3BlobStore.Create(options, …)`**：否决。按选项建客户端并探测条件写入的入口已经有了，就是命名实例的 Provider（`S3BlobStoreProvider.CreateAsync`，不需要宿主）；再加一个不探测的工厂等于公开一条绕过 ADR-0089 的路。
10. **构造改 internal，不加任何新入口**：采纳。
11. **同时去掉「应用向容器注册自己的 `IAmazonS3` 时沿用」，改成给选项加会话令牌、代理、超时、重试等键**：这次不做。它能把 SDK 的类型彻底挡在应用之外，但要先定哪些键值得进 `Stable` 的选项与命名实例的设置，超出这次的范围。记为待定，见「影响」。

放弃分片上传：

12. **接口上保留单条，另加 `AbortManyAsync`**：否决。同一子系统的 `IBlobStore.PutAsync` / `DeleteAsync` 是同名的批量方法加扩展方法里的单条；自写 Provider 的人只需要实现一个方法。
13. **基础设施失败整批抛出（汇总异常）**：否决。S3 没有批量放弃的接口，每一项是一次独立的请求，如实报告每一项的结果才不是「伪装成部分成功」；`IBlobStore` 的批量删除也是逐项报告存储不可达。
14. **取消时不再检查、把整批做完**：否决。一批可以很大，S3 上每一项是一次网络往返。放弃是幂等的，半批之后取消没有需要回滚的东西，调用方整批重试即可。

签出的地址：

15. **`Url` 经构造给出，其余走初始化器**：否决。ADR-0142 留给构造的是「构成身份的一两个必需成员」，这四项里没有哪一项是身份；与同包的 `BlobMetadata` 一样全部走初始化器。

## 决策

1. **`BlobStores` 的登记数上限。**
   - 已建的实例数不超过 `MaxCount`：配置键 `XiHan:ObjectStorage:StoreMaxCount`，缺省 64，1 到 `MaxCountLimit`（1024），用 `ConfigurationValues.ReadInt32` 读，写了不合法的值在构造注册表时抛出带完整配置键的 `ArgumentException`。配置定义的实例建出之后与运行时登记的一样占名额，建出之前不占。
   - 满了再登记新名字（`GetOrAddAsync`，以及 `GetAsync` 首次取用配置定义的实例）返回 `OBJECTSTORAGE_UNAVAILABLE_005`（`ObjectStorageErrors.StoreCapacityExceeded`，消息键 `objectstorage.store.capacity_exceeded`，参数 `store`、`capacity`）。不建实例、不淘汰已有的；同名同定义照常返回，同名换定义照常替换（不占名额）；移除腾出名额。
   - 判容量与放进登记表都在串行化建、替换与移除的那把锁里，并发登记超不过上限，被拒的登记方不会建出没人释放的实例。
2. **`BlobStores` 的移除改批量。** `RemoveAsync(IReadOnlyList<string> names, CancellationToken)` 返回 `IReadOnlyList<bool>`，删除 `RemoveAsync(string, CancellationToken)`。
   - 逐项返回该名字的实例是否存在过，与入参等长同序；同一批里重复的名字第二次为 `false`；空集合返回空列表。
   - 名字为 `null` 是编程错误，在移除任何实例之前抛出 `ArgumentNullException`。
   - 进入前检查取消；整批在一次加锁里移除，不会只移一半；之后逐个释放，释放不响应取消。
   - 某个实例释放失败记一条 Warning（带实例名与异常），不改变返回值，不挡住其余实例的释放。
3. **`S3BlobStore` 的构造改 internal。** 缺省实例由 `S3ObjectStorageFeature` 建出，命名实例由 `S3BlobStoreProvider` 按定义建出；测试经 `InternalsVisibleTo` 照旧以打桩的客户端构造。S3 包新增一条测试，核对导出类型的基类、接口与公开或受保护成员的签名里没有 `AWSSDK.*` 程序集的类型。自定义客户端的途径不变：
   - 端点、区域、静态密钥与路径风格在 `S3ObjectStorageOptions`（配置节或连接绑定 `objectstorage`）；两项密钥都不给时走 SDK 的默认凭据链。
   - 选项表达不了的（临时凭据、代理、超时、重试策略），应用在装配前向容器注册自己的 `IAmazonS3`，缺省实例沿用它。这是应用自己选的对 SDK 的依赖，不在本包的公开签名里。
   - 更多的实例经 `BlobStores` 登记（设置同选项，各建各的客户端），或不经宿主直接调 `S3BlobStoreProvider.CreateAsync`。
4. **`IBlobMultipartStore` 的放弃改批量。** `AbortAsync(IReadOnlyList<BlobMultipartUpload> uploads, CancellationToken)` 返回 `IReadOnlyList<Result>`；接口上不再有单条方法，单条是扩展方法 `BlobMultipartStoreExtensions.AbortAsync(store, upload, cancellationToken)`（转调批量、取第一项）。
   - 按入参顺序逐项执行，返回与入参等长同序的逐项结果。
   - 上传不存在或已结束也成功，所以同一批里重复的上传每一项都成功；空集合不访问存储，返回空列表。
   - 存储不可达只记在该项上（`OBJECTSTORAGE_UNAVAILABLE_001`），其余项照常执行。
   - 每一项之前检查取消，已取消即抛出 `OperationCanceledException`；请求途中的取消同样抛出，不记成该项的存储故障。已放弃的不恢复。
   - 集合里有 `null` 是编程错误，在放弃任何上传之前抛出 `ArgumentException`。这道检查由新增的 `BlobMultipart.ValidateUploads` 给出，两个存储包与自写的 Provider 共用（做法同 ADR-0254 的 `ValidateParts`）。
   - 文件系统逐项放弃，让出暂存的字节与名额；S3 逐项请求 `AbortMultipartUpload`。
   - 一致性套件新增用例 14 `Multipart_AbortsInBatch_ReportingEachUpload`。
5. **`BlobSignedUrl` 改成初始化器形状。** `Url`、`Method`、`ExpiresAt`、`Headers` 都是 `required` 的 `init` 成员，没有位置构造与 `Deconstruct`；以后加成员只加可选的初始化成员。

## 理由

- 登记表是长生命周期的状态，键空间由应用的数据决定；没有上限就是把「会不会无界增长」交给每个应用自己记得。上限的缺省值与范围照持久化的登记表，运维只需要记一套数。
- 满了拒绝而不是淘汰：被拒是调用方看得见、处理得了的结果；被淘汰是别的调用在某个不相干的时刻失败。
- 公开面上有没有第三方类型，决定的是谁的发版节奏说了算。应用自己往容器里放一个 `IAmazonS3` 是应用的选择，升级 SDK 时改的是应用自己的那一行；写在框架 `Stable` 签名里的则是所有使用者被动跟着破坏。
- 批量方法与单条扩展同名、接口上只留批量，是这个子系统已经定下的形状；放弃照它做，使用者不必再学一种。
- 这四处都在 5.0.0 之前改，不需要豁免登记（ADR-0131）；拖到正式版之后，前三处只能等下一个大版本。

## 影响

- **公开 API 与迁移**（`PublicAPI.Unshipped.txt` 已同步；尚无基线，不需要 `CompatibilitySuppressions.xml`）：
  - `BlobStores.RemoveAsync(string, CancellationToken)` 删除，改用 `RemoveAsync(IReadOnlyList<string>, CancellationToken)`：`await stores.RemoveAsync(name, ct)` 改成 `(await stores.RemoveAsync([name], ct))[0]`。
  - `BlobStores` 新增 `MaxCount` 与常量 `MaxCountLimit`；`ObjectStorageErrors.StoreCapacityExceeded`、`ObjectStorageMessages.StoreCapacityExceeded` 新增。登记数超过 64 的应用要配 `XiHan:ObjectStorage:StoreMaxCount`，否则第 65 个新名字被拒。
  - `S3BlobStore` 的公开构造删除：直接 `new S3BlobStore(client, …)` 的代码改为装配 `S3ObjectStorageFeature`（要自定义客户端就向容器注册 `IAmazonS3`），或经 `BlobStores` / `S3BlobStoreProvider.CreateAsync` 按定义建。
  - `IBlobMultipartStore.AbortAsync(BlobMultipartUpload, CancellationToken)` 从接口删除，新增批量方法与 `BlobMultipartStoreExtensions.AbortAsync`、`BlobMultipart.ValidateUploads`：调用点 `multipart.AbortAsync(upload, ct)` 不用改（落到扩展方法上）；自写的 Provider 改实现批量方法，开头调 `BlobMultipart.ValidateUploads(uploads)`。`FileSystemBlobStore` 与 `S3BlobStore` 上的同名公开方法随之换成批量的。
  - `BlobSignedUrl` 的位置构造与 `Deconstruct` 删除：自写签名器把 `new BlobSignedUrl(url, method, expiresAt, headers)` 改成 `new BlobSignedUrl { Url = …, Method = …, ExpiresAt = …, Headers = … }`，位置解构改成读属性。
  - 一致性套件：`BlobStoreConformance` 新增用例 14，实现了 `IBlobMultipartStore` 的自写 Provider 要通过它；`BlobStoreProviderConformance` 的注册表用例改用批量移除，公开面不变。
- **行为变化**：
  - 登记表满了之后的新登记原先成功，现在失败（见上）。
  - 移除的实例释放时抛出，原先异常传给 `RemoveAsync` 的调用方，现在只记 Warning、返回值照常。
  - 其余不变：单条放弃的结果、S3 与宿主两个签名器签出的四项内容都与原先相同。
- **与 `DataSourceRegistry` 仍有的两处不同**（都在批量移除的边角上，这次没有动持久化）：它在遇到 `null` 名字之前已经移除的实例不会被释放；它在第一个实例释放失败时抛出，同批其余已移除的实例不再释放。建议照这里的做法补齐。
- **规范（已补，规范指针 `c90faf8`）**：
  - `conventions/error-codes.md` 登记 `OBJECTSTORAGE_UNAVAILABLE_005`。登记之前，架构测试 `NamingTests.ErrorCodes_InSourcesAreRegistered` 失败（源码里的错误码必须已登记），这是全量测试里唯一的失败。
  - RFC-0012：「范围读取、分片上传与预签名」里 `Abort(upload)` 一句改为批量放弃的语义；「命名存储实例」的注册表一条补容量，`Remove(name)` 改为批量；「S3 的条件写入探测」与「一致性」两处提到「经公开构造函数直接建的 `S3BlobStore`」的句子改掉；「一致性」补用例 14 与批量移除。`objectstorage` 一致性档是 `stable`，这些是规范性修订。
- **命令行知识库**：配置索引按「带 `ConfigurationSection` 与 `FromConfiguration` 的选项类」建，`BlobStores` 不是选项类，`XiHan:ObjectStorage:StoreMaxCount` 与已有的 `StoreHealthProbeIntervalSeconds` 一样进不了 `Knowledge/configuration.json`；包与清单索引没有变化。
- **待定**：是否把会话令牌、代理、超时、重试做成 `S3ObjectStorageOptions` 的键并去掉对容器里 `IAmazonS3` 的沿用（备选 11）。现在命名实例只能用选项里的那几项，原先经公开构造「给第二个存储配一个自定义客户端」的做法没有等价的替代。
- **测试**：
  - 登记表：批量移除的逐项结果、空集合、重复与没登记过的名字、`null` 与已取消时一个都不移除、释放失败只记日志；上限的拒绝与错误参数、同名同定义与替换不受限、不淘汰、移除腾出名额、32 个并发登记恰好成功 4 个且只建出 4 个实例、配置定义的实例建出后占名额、缺省值与不合法的配置值。
  - 批量放弃：文件系统上的逐项结果、让出字节与名额、空集合、单条即一项的批量、`null`、两项之间的取消与整批重试、一项删不掉时其余照常（只在 Windows 上能造出删不掉的文件）；S3 用打桩的客户端核对逐项请求、一项服务端失败其余照常、`NoSuchUpload` 与 `NoSuchBucket` 都算成功、两项之间与请求途中的取消。
  - S3 的公开面核对；不连服务的 S3 签名用例（签名是本地计算）。
  - S3 真实服务上的路径（一致性用例 14、分片与预签名的直连用例）只在 CI 设了 `XIHAN_TEST_S3` 时执行。
- **文档**：抽象包、S3 包与一致性套件的 README 已同步；文档站的 `packages/objectstorage-abstractions`、`packages/objectstorage-s3`、`packages/conformance`、`object-storage/advanced`、`configuration/options` 与更新日志待改。
