# ADR-0285 下发给插件的绑定带上属性

## 状态

已采纳（规范 `plugin/plugin.proto` 的 `Binding` 新增 `map<string, string> properties = 4`，`plugin/lifecycle.md` §2 与 §7.2、RFC-0016「资源绑定与配置节」第 7 条、RFC-0017 已补，新增向量 `plugin/binding-properties.json`；`Plugins.Protocol` 的 `PluginConfigureRequests` 把内核解析出的属性写进请求，新增 internal 的 `PluginBindingProperties` 核对文法与上限；内核 `BindingValue` 打印时属性只带名字。六个 SDK 的生成物与公开的绑定类型由后一波跟进）。

## 日期

2026-11-24

## 背景

- ADR-0268 让下发给隔离运行的插件（进程外、Wasm）的绑定与内核同源解析，但线协议的 `Binding` 消息只有 `name`、`type`、`value` 三个字段，于是定下「属性不下发，没有主值的绑定整个不下发」，并把「给 `Binding` 加属性字段」记为待定。
- 一个绑定除了主值还可以带属性（RFC-0016）：Service Binding 目录里每个文件是一个属性（`host`、`port`、`username`、`password` 各一个文件），只有 `uri` 一个文件算主值；配置来源里 `type`、`value` 之外的子键是属性。`xihan pack` 生成的 Kubernetes 清单只经 `SERVICE_BINDING_ROOT` 挂载绑定，运营方自备的 Secret 可以只有各项属性、没有 `uri`。
- 后果：**只挂属性文件、没有单一连接串的绑定对隔离运行的插件不可用**；带 `uri` 的绑定里另放的凭据（`password`、`accessKey`）也到不了插件。同一个应用里宿主进程的特性两样都读得到（`BindingValue.Properties`）。
- 属性里多是凭据。加字段之前要定：是否仍只凭 `binding:<绑定名>` 一项授予（ADR-0268 留下的问题）、属性名有没有文法、数量与大小有没有上限、超限怎么办、日志里能出现什么。
- 协议怎样演进已有规则（RFC-0024「版本」第 3、4 条）：协议版本（握手里的整数，现在是 `1`）只在线上不兼容时新增；同一协议版本里的新增字段走规范的 MINOR，不升协议版本、不在握手里协商，宿主必须容忍同一大版本里任一 MINOR 的插件。

## 备选

怎样把属性送过去：

1. **给 `Binding` 加 `map<string, string> properties = 4`，协议版本不变（规范 MINOR）**：采纳。protobuf 的未知字段规则保证两个方向都不坏：较早的插件跳过字段 4，较早的宿主不发它。Wasm 载体的 proto3 JSON 映射同样忽略未知字段（`wasm.md` §2）。
2. **新增协议版本 `2`**：否决。线上兼容，不满足新增协议版本的条件；六个 SDK 与宿主都要同时支持两个版本，只为一个可选字段。
3. **把属性并进 `value`（如拼成 JSON 或查询串）**：否决。`value` 的含义是连接串或地址，改了它较早的插件会拿一段 JSON 去连。
4. **握手里协商「对端认不认 `properties`」，不认就不发**：否决。RFC-0024 明确不在握手里协商 MINOR；发了被忽略与没发对较早的插件是一回事。
5. **属性另起一个 RPC 或按需回调宿主读取**：否决。多一次往返与一处权限判定，Wasm 载体还要多一个导入；`Configure` 本来就是下发绑定的地方。

只有属性的绑定：

6. **主值与属性都没有的才不下发；只有属性的照常下发、`value` 为空**：采纳。这正是要解决的情形。ADR-0268 否决「以空主值下发」的理由是插件分不出空与没给、会拿空地址去连——那时属性送不过去，空主值的绑定没有任何可用的内容；现在 `value` 为空而 `properties` 非空的含义是确定的。
7. **只有属性的绑定仍不下发**：否决。问题原样留着。
8. **宿主按属性拼出一个主值再下发**（`host` + `port` → 地址）：否决。拼法因资源类型而异，是 Provider 的知识，宿主猜不对；RFC-0016 的 Provider 对照表也是「属性覆盖配置节里的同类键」，不是拼主值。

权限：

9. **属性随绑定一起受 `binding:<绑定名>` 约束，不单独授权**：采纳。授予一个绑定就是把这个资源的连接信息交给插件，连接串里本来就有口令；把同一个 Secret 的 `password` 文件另设一道授予，运营方要为每个插件逐个属性地写授予，却挡不住任何实际的东西。
10. **按属性名授权（`binding:<绑定名>:<属性>`）**：否决，理由同上；权限码的文法也要跟着改。

文法与上限：

11. **属性名原样下发、不设文法**：否决。目录来源的文件名在 Linux 上可以是任意字节，配置来源的子键可以带空格与控制字符；`map` 的键必须是合法的 UTF-8，各语言拿到手的键也该是可以预期的字符集。
12. **属性名用 Kubernetes Secret 键的字符集与长度，另不许以 `.` 开头**：采纳。Service Binding 目录里的文件名就是 Secret 的键（`[-._a-zA-Z0-9]+`，最长 253）；以 `.` 开头的文件内核本来就不当属性（`..data` 之类的挂载元数据）。框架 Provider 现有的属性名（`username`、`sasl.username`、`accessKey`、`forcePathStyle`）都在这个文法里。区分大小写照 RFC-0016 第 4 条，宿主不折叠。
13. **不设数量与大小的上限**：否决。属性文件由 `File.ReadAllText` 整个读进内存再塞进一个请求，gRPC 的缺省消息上限是 4 MiB，超过时失败在传输层，运营方看到的是一个与绑定无关的状态码。
14. **一个绑定最多 64 个属性、属性名与属性值合计不超过 262144 个 UTF-8 字节（256 KiB），主值不计入**：采纳。常见的绑定是几个到十几个属性、合计几 KB，证书链与密钥也在几十 KB 之内；十来个顶到上限的绑定仍在 gRPC 的缺省消息上限之内。按字节而不是按字符计，与线上的大小一致。
15. **超限或属性名不合文法时少发（丢掉不合的属性、截断）并记警告**：否决。与 ADR-0268 否决「读失败时当成没有」同一个理由：插件带着缺的凭据启动，比启动失败更难查。
16. **超限或不合文法时让配置这一步失败**：采纳。沿用读失败的处理：`PLUGINS_UNEXPECTED_001` + `plugins.process.failed`，`phase` 为 `configure`，插件进入 Failed、有健康条目、按重启策略再试，运营方改了挂载或配置之后自己起来。`reason` 是固定的英文文本，只带绑定名与上限的数字。不为它另加错误码（ADR-0268 备选 12 的理由仍然成立）。
17. **在内核的 `BindingResolver` 里设文法与上限**：否决。那是 `Stable` 契约的行为变化：现在启动得了的应用（属性名带空格、挂了一个大文件）会启动失败，而宿主进程里的特性并不经过线协议。限制只管下发给插件的那一段。

日志：

18. **不合文法时在日志里写出那个属性名，方便定位**：否决。属性名来自部署环境，没有经过文法核对的名字正是要拒绝的那些（可能很长、带控制字符）；`reason` 与日志只带绑定名，运营方到那个绑定的目录或配置节里去看。
19. **内核 `BindingValue` 的打印照旧（`Properties = ` 后面接字典自己的 `ToString()`）**：否决。BCL 的字典打印的是类型名，泄露不了值，但那取决于调用方给的字典实现；绑定对象会整个进日志与异常消息。改为只打印属性名，与主值的遮蔽写在同一处。

三种运行方式：

20. **给进程内插件的 `PluginContext` 加绑定成员**：不做。进程内插件是受信代码，拿到的是整个宿主配置（`PluginContext.Configuration`），经公开的 `BindingResolver.Resolve(configuration)` 得到的 `BindingValue` 本来就带属性；这次没有要补的。它拿不到应用经 `UseServiceBindingRoot` 指定的根目录（进程内宿主没有特性入口，构造时只收配置），那是主值与属性共有的缺口，与属性无关，记为待定。

## 决策

1. **规范：`Binding` 消息新增 `map<string, string> properties = 4`。** 键是属性名、值是属性值，没有其余属性时为空；`name`、`type`、`value` 的含义不变。协议版本仍是 `1`，这是规范的一次 MINOR（规范没有版本文件，级别记在它的 `CHANGELOG.md`）；握手、`XIHAN_PLUGIN_PROTOCOL_VERSIONS` 与 `PluginProtocol.Version` 都不动。
2. **下发什么。** `properties` 是解析结果里这个绑定的全部属性，与宿主进程里的特性读到的 `BindingValue.Properties` 是同一份，原样下发：
   - 目录来源是绑定目录里 `type` 之外、不以 `.` 开头的每个文件（文件名是属性名，内容去掉首尾空白是值）；`uri` 文件既是主值也是属性 `uri`，两处都下发。配置来源是 `XiHan:Bindings:<名字>` 下 `type`、`value` 之外有值的子键。同名时配置整体覆盖目录，属性不逐个合并（不变）。
   - 属性名区分大小写，宿主不折叠、不改写；值为空的属性照发；各项的先后没有含义。
   - 来源只给了属性、没有主值的绑定照常下发，`value` 为空。主值与属性都没有的绑定不下发，记一条 Warning（绑定名与插件 ID）。
3. **属性名的文法与上限**（只管随 `Configure` 下发的绑定）：
   - 属性名 1 到 253 个字符，只含 ASCII 字母、数字、`.`、`_`、`-`，不以 `.` 开头。
   - 一个绑定最多 64 个属性；全部属性名与属性值按 UTF-8 编码后合计不超过 262144 字节，主值不计入。
   - 清单声明的绑定不合时，宿主不发 `Configure`，返回 `PLUGINS_UNEXPECTED_001`（`plugins.process.failed`，`phase` 为 `configure`），不少发、不截断。按清单的顺序逐个绑定核对，一个绑定里先数量、再属性名、最后字节数，报第一处：`binding '<绑定名>' has more than 64 properties`、`binding '<绑定名>' has a property name that is not valid`、`the properties of binding '<绑定名>' exceed 262144 bytes`。清单没有声明的绑定不读、不核对。
4. **权限不变。** 插件仍然只拿得到清单声明并以 `binding:<绑定名>` 获批的绑定，缺授予在发现时以 `PLUGINS_DENIED_001` 拒绝（ADR-0177）；属性随绑定一起受这一条管，不单独授权。
5. **属性值不进日志。** 宿主的 `reason`、Warning 与 Error 日志只带绑定名与插件的清单 ID，不带属性名与任何值；成功下发不记日志。插件一侧：SDK 不得把主值与属性值写进日志、错误与诊断输出，交给作者的绑定类型的调试输出应当只带绑定名、类型与属性名。
6. **对端按较早的规范实现时。** 宿主不看对端的 SDK 版本，照发 `properties`：较早的插件把它当未知字段跳过，`name`、`type`、`value` 读到的不变，只是会收到以前不下发的、`value` 为空的绑定。较早的宿主不发它，新的 SDK 读到的是空表。
7. **.NET。**
   - `Plugins.Protocol` 的消息类型由 `Grpc.Tools` 在构建期从规范的同一份 `.proto` 生成（internal），不用另行更新生成物。
   - `PluginConfigureRequests.Build`（进程外与 Wasm 两个宿主共用）把 `BindingValue.Properties` 写进 `Binding.properties`，没有主值时 `Value` 写空。
   - 新增 internal 的 `PluginBindingProperties`：`MaxCount`、`MaxNameLength`、`MaxBytes`、`IsValidName`、`FindViolation`。
   - 内核的解析不变（`BindingResolver`、`BindingValue` 的成员都不动，属性本来就在解析结果里）。`BindingValue` 打印时 `Properties` 只列属性名（按序数排序），不再接字典自己的 `ToString()`。
8. **规范的向量。** 新增 `plugin/binding-properties.json`（档 `plugin` 与 `host`）：上限、属性名文法的样例、宿主一侧由清单声明与解析出的绑定到下发的绑定 / 警告 / 失败的 `reason`、插件一侧由宿主写出的 `ConfigureRequest` 字节与 proto3 JSON 文本到交给作者的绑定。期望值由 .NET 算出。`plugin-messages.json` 的固定 `reason` 补上三条。

## 理由

- 协议只增不改：一个可选的 `map` 字段是 protobuf 里代价最小的演进，两个方向的旧实现都照常工作，用不着版本协商。
- 属性与主值是同一个资源的同一份连接信息，授予、来源、解析时机与日志规则都应当一样；这次没有为属性引入任何新的概念，只是把内核已经解析出来的那一半送过去。
- 送不过去的不装作送到了（ADR-0268 的原则）：不合文法或超限让插件配置失败，运营方从宿主一侧看得到原因与绑定名。
- 文法与上限只加在线协议这一段：内核怎样读绑定是 `Stable` 契约，也不经过线协议；给插件的那一份要过 gRPC 的消息上限、要进六种语言的映射类型，才需要可预期的键与大小。

## 影响

- **公开 API**：没有变化。`PluginBindingProperties` 与生成的协议类型都是 internal，`PublicAPI.Unshipped.txt` 不用动；没有新的配置键、错误码与消息键。
- **对已有部署的行为变化**：
  - 只挂属性文件、没有 `uri` 的绑定，原先插件收不到（ADR-0268 之后另有一条 Warning），现在收得到：`value` 为空、属性都在。带主值的绑定原先只到主值，现在属性一并到达。前提不变：清单声明、运营方授予 `binding:<绑定名>`。
  - 配置来源里大小写写错的保留键（`XiHan:Bindings:cache:VALUE`、全大写环境变量）原先解析成只有属性 `VALUE`、没有主值的绑定，不下发；现在作为属性 `VALUE` 下发、主值为空，与宿主进程里的特性看到的一致。仍应按 `XiHan__Bindings__<绑定名>__value` 书写。
  - 清单声明的绑定有属性名不在文法里（带空格、非 ASCII、以 `.` 开头的配置子键）、属性多于 64 个或合计超过 256 KiB 时，这个插件配置失败、进入 Failed 并按重启策略重试；原先属性不下发，没有这种失败。把不该给插件的文件从绑定目录里挪走，或把属性名改到文法之内。宿主进程里的特性不受影响。
  - 「没有主值、因此不下发」的 Warning 只在主值与属性都没有时才记。
  - 用较早的 SDK 构建的插件不用改、不用重新构建：它们照旧读到 `name`、`type`、`value`；原先收不到的只有属性的绑定现在会出现在 `bindings` 里、`value` 为空，要用属性得升级 SDK。
  - `BindingValue.ToString()` 的 `Properties` 一段由字典的类型名变成属性名的列表（`Properties = [password, username]`），值照旧不出现。
- **规范（已补，规范提交 `746169d`）**：`plugin/plugin.proto`、`plugin/lifecycle.md` §2 与 §7.2、`plugin/invocation.md` §8 的场合一栏、`conventions/error-codes.md` 里 `PLUGINS_UNEXPECTED_001` 的说明、RFC-0016 第 7 条、RFC-0017「生命周期」与 .NET 映射；Go 一致性模块的生成物 `conformance/internal/pluginv1` 重新生成，规则包新增 `IsBindingPropertyName`、`BindingPropertyViolation`、`DeliverBindings`。ADR-0268 当天写明的「其余属性不下发；没有主值的绑定不下发」由这次改写，那两句没有随任何规范标签发布过。
- **六个 SDK（后一波）**：各自从新的 `plugin.proto` 重新生成消息类型；公开的绑定类型加属性成员（没有属性时是空表）；调试输出不带主值与属性值；回放 `plugin/binding-properties.json` 的 `reading`，并把它加进各自的向量覆盖名单。协议版本常量不动。
- **待定**：
  - 进程内插件拿不到应用指定的 Service Binding 根目录（备选 20）。
  - 内核的 `BindingResolver` 读绑定目录时没有大小上限（一个很大的属性文件会被整个读进内存）；这次只限制了下发给插件的那一段。
  - ADR-0268 留下的两条仍然待定：来源声明的类型与清单不同时是否拒绝、必需绑定解析不出来时是否让插件配置失败。
  - 一致性套件（`PluginProtocolConformance`、`WasmPluginConformance` 与规范的黑盒运行器）的 `Configure` 请求不带绑定，这次没有加：被测插件不回报自己收到了什么，黑盒看不出它读没读到属性。
- **测试**：
  - `PluginConfigureRequestsTests`（两个宿主共用的那一处）：目录来源的属性随绑定下发（`type` 不是属性、`uri` 两处都在、内容去首尾空白）；只有属性的绑定下发且主值为空；主值与属性都没有的不下发并记警告；配置来源的属性区分大小写、空值照发、嵌套的节不是属性；配置整体覆盖目录、属性不合并；每次组装重新解析；三个上限各踩在线上能下发；数量、属性名（空格、点开头、非 ASCII、过长）、字节数（含按码元计不超而按字节计超过的）超限时返回 `PLUGINS_UNEXPECTED_001`，错误、`details` 与日志里没有属性名、属性值与主值；按清单的顺序、先数量再属性名再字节数；清单没声明的绑定不核对；大小写敏感的文件系统上只差大小写的两个属性都下发；只认字段 1 到 3 的读法（较早的插件）跳过 `properties` 后三项不变，Wasm 的 JSON 文本同理。
  - `ProtocolVectorTests`：回放 `binding-properties.json`——上限与常量一致，属性名的样例经 `IsValidName`，`delivery` 的每个用例经真实的 `PluginConfigureRequests.Build`（解析出的绑定以配置来源给出）核对下发的绑定、警告与错误，`reading` 的字节与 JSON 文本就是宿主写出的、读回来是同一个请求；`plugin-messages.json` 的三条固定 `reason` 是 `FindViolation` 写出的。
  - `WasmPluginBindingTests`（端到端，现场生成的 WAT 插件在 `xihan_configure` 里核对请求）：只挂属性文件的绑定连同属性到得了插件；主值旁边的属性与配置来源的属性到得了插件；属性多于 64 个时插件停在 Failed、错误只带绑定名。
  - `OutOfProcessPluginHostTests`（端到端，EchoPlugin 的副本改清单声明一个绑定）：带属性的 `Configure` 请求经 gRPC 到达插件进程、插件进入可服务状态；属性多于 64 个时宿主不发 `Configure`、插件停在 Failed。EchoPlugin 不回报收到的绑定，字段的取值由上面两组核对。
  - 内核：`BindingValue.ToString()` 只带属性名、不带属性值。
  - 规范的 Go 一致性模块：规则包回放 `binding-properties.json`；`reading` 由重新生成的协议代码解码（字节与 JSON 文本读出同一个请求），并以只认字段 1 到 3 的读法核对较早的插件读到的三项不变。
- **文档**：`Plugins.OutOfProcess` 与 `Plugins.Wasm` 的 README 已同步；文档站的 `configuration/bindings`（「下发给插件的绑定」一节）、`packages/plugins-outofprocess`、`packages/plugins-wasm`、`plugins/out-of-process`、`plugins/wasm`、`appendix/spec` 与更新日志待改。
