# ADR-0270 调度的查询方法补动词

## 状态

已采纳（`IJobScheduler` 的 `RunsAsync` → `ListRunsAsync`、`StatusesAsync` → `FindStatusesAsync`，扩展方法 `StatusAsync` → `FindStatusAsync`；`IJobStore` 的六个读取方法同样补上动词；纯重命名，签名、级别与行为不变，不留旧名；都在 GA 前，不需要登记豁免；规范正文待补，见「影响」。按名取状态原定叫 `GetStatusesAsync`，与 RFC-0001「查找的命名」冲突，改用 `Find`，见备选 3）。

## 日期

2026-11-24

## 背景

- `IJobScheduler`（`Stable`）十四个方法里十二个以动词起头，只有两个是名词：
  - `RunsAsync(JobRunQuery)`：运行历史。
  - `StatusesAsync(IReadOnlyList<JobName>)`：按名取作业的状态。
- 名词读不出是哪一种读取，而同一个接口上紧挨着的就是带动词的同类方法：
  - `StatusesAsync(names)` 与 `ListStatusesAsync(query)` 并排，一个按名批量取（与入参等长、同序，未登记为无值），一个按作业名分页列出。两种读取的区别正好在动词上，前者没有。
  - `RunsAsync(query)` 与 `CountRunsAsync(query)` 用同一组过滤项，一个列出、一个计数；`CancelRunsAsync(runIds)` 是对运行的写操作。三个名字里只有它看不出做什么。
- 来历：ADR-0148 把不分页的 `StatusesAsync()` 换成「按名批量」加「分页列出」两个方法，新加的 `ListStatusesAsync` 带了动词，留下的那个沿用旧名；`RunsAsync` 在 ADR-0053 给它配上 `CountRunsAsync` 之前就是这个名字。
- 按同一条标准核对了 `Scheduling.Abstractions` 的全部公开异步方法（`PublicAPI.Unshipped.txt` 里以 `Async` 结尾的成员）：
  - **扩展方法**（`JobSchedulerExtensions`，`Stable`）：`StatusAsync(name)` 是 `StatusesAsync([name])` 的单项写法，同样没有动词。其余单项写法（`TriggerAsync`、`ScheduleAsync`、`UnscheduleAsync`、`PauseAsync`、`ResumeAsync`、`EnqueueAsync`、`CancelRunAsync`）都有。
  - **存储契约**（`IJobStore`，`Preview`）：二十一个方法里六个读取没有动词，同一接口上的同类方法却有（`FindJobAsync`、`ListJobsAsync`、`CountRunsAsync`）：
    - `TriggersAsync(job?)`、`RunsAsync(query)`、`RunningAsync(job?)`、`LastRunsAsync(jobs)`、`NodesAsync()`
    - `CancelRequestedRunsAsync(nodeId)`：以 `Cancel` 起头，读成「取消被请求的运行」，实际是列出本节点上被请求取消的运行，什么也不取消；真正请求取消的是它旁边的 `RequestCancelAsync(runIds)`。
  - **`IJobStore.HeartbeatAsync(node)`**：写入节点心跳。`Heartbeat` 在这里当动词用，不是读取，见备选 7。
  - 其余都以动词起头：`ILeaderElection.TryAcquireAsync`，`LeaderLease.RenewAsync` / `ReleaseAsync`，`IJob.RunAsync`，`JobDispatcher.DispatchAsync`，`JobSchedulerEngine.StartAsync` / `StopAsync` / `PollOnceAsync`。
  - `Scheduling.Conformance` 的辅助方法 `JobSchedulerConformance.StatusAsync(host, name)` 是对扩展方法的包装（作业必须存在，否则抛出），同名同问题。
- 动词不能随手挑：RFC-0001「查找的命名」（ADR-0153）规定方法名决定「没有」怎么表示——`Find…` 返回 `Maybe<T>`，`Get…` 必定交出值，例外只有缓存条目的键值读取；架构测试 `LookupNamingTests` 守着这一条。

## 备选

1. **只改 `IJobScheduler` 的两个方法**：否决。
   - 扩展方法 `StatusAsync(name)` 是按名取状态的单项特例，批量的带动词、单项的不带，应用代码里两种写法会并排出现。
   - `JobSchedulerEngine.ListRunsAsync` 的实现是转调 `IJobStore.RunsAsync`，同一次读取在两层叫两个名字；写 Provider 的人照着 `ListJobsAsync` 找不到 `ListTriggersAsync`。
   - `IJobStore` 是 `Preview`，GA 之后还能经豁免再改，但那是第二次破坏、第二次迁移说明，现在一并做只有一次。
2. **留 `[Obsolete]` 的旧名转调新名**：否决。接口成员留旧名，每个实现都得多写一份；仓库的规矩也是破坏性变更写明迁移方式、不留兼容别名（ADR-0264 同）。
3. **按名取状态叫 `GetStatusesAsync` / `GetStatusAsync`**（最初的打算）：否决。
   - 这两个方法对未登记的作业返回无值（`Result<IReadOnlyList<Maybe<JobStatus>>>`、`Result<Maybe<JobStatus>>`）。RFC-0001 规定 `Get…` 必定交出值，返回 `Maybe` 的叫 `Find…`；`LookupNamingTests.GetMethods_AlwaysProduceAValue` 对这两个名字直接报错。
   - 那条规则的例外只给缓存条目（`ICache.GetAsync` / `GetManyAsync` 沿用键值存储的词汇）。给调度再开一个例外要改规范与门禁，而调度器的状态不是键值存储的条目。
   - 要保留 `Get` 就得改返回形状（未登记时返回 `SCHEDULING_NOTFOUND` 的失败结果）。那不是改名：批量读取里「有一个名字未登记」会让整批失败，或者变成逐项结果，调用方都要重写。
4. **按名取状态叫 `FindStatusesAsync` / `FindStatusAsync`**：采纳。返回形状不变，名字与规则一致；插件宿主按清单标识取状态的方法已经叫 `FindStatus(manifestId)`（ADR-0153），同一接口的存储侧是 `FindJobAsync`。
5. **`RunningAsync` 改名 `ListRunningAsync` 或 `ListActiveRunsAsync`**：否决。
   - `ListRunningAsync` 没有名词，同接口的其余列出方法都带（`ListJobsAsync`、`ListTriggersAsync`、`ListRunsAsync`、`ListNodesAsync`）。
   - `Active` 已经另有所指：`JobRecord.ActiveRunId` 是「占用这个作业的那一次运行」，只有不允许并发的作业才有；这个方法返回的是全部状态为 `JobRunState.Running` 的运行。
6. **`LastRunsAsync(jobs)` 改名 `FindLastRunsAsync`**：否决。它不返回 `Maybe`，结果也不与入参等长、同序（没有结束过运行的作业不在结果里），调用方按作业名自己对应；这是列出。
7. **`HeartbeatAsync(node)` 一并改名（`SaveNodeAsync`、`WriteHeartbeatAsync`）**：不在本 ADR。它不是同一类问题：是写入，`Heartbeat` 本身当动词读得通，分布式系统的接口里也惯用。与同接口的 `SaveJobsAsync` / `SaveTriggersAsync` 是否对齐另行决定。
8. **顺带把别的包里同类的名字一起改**（如 `IWorkflowBookmarkStore.ByKindAndKeyAsync` / `BySignalAsync`）：不在本 ADR。这次核对的范围是调度的契约包，别的子系统各自核对。

## 决策

1. `IJobScheduler`（`Stable`）与实现它的 `JobSchedulerEngine`：

   | 原名 | 新名 |
   | --- | --- |
   | `RunsAsync(JobRunQuery, CancellationToken)` | `ListRunsAsync` |
   | `StatusesAsync(IReadOnlyList<JobName>, CancellationToken)` | `FindStatusesAsync` |

2. `JobSchedulerExtensions`（`Stable`）：`StatusAsync(JobName, CancellationToken)` → `FindStatusAsync`。
3. `IJobStore`（`Preview`）与两个实现（`InMemoryJobStore`、`DatabaseJobStore`）：

   | 原名 | 新名 |
   | --- | --- |
   | `TriggersAsync(JobName?, CancellationToken)` | `ListTriggersAsync` |
   | `RunsAsync(JobRunQuery, CancellationToken)` | `ListRunsAsync` |
   | `RunningAsync(JobName?, CancellationToken)` | `ListRunningRunsAsync` |
   | `LastRunsAsync(IReadOnlyList<JobName>, CancellationToken)` | `ListLastRunsAsync` |
   | `CancelRequestedRunsAsync(string, CancellationToken)` | `ListCancelRequestedRunsAsync` |
   | `NodesAsync(CancellationToken)` | `ListNodesAsync` |

4. `Scheduling.Conformance` 的 `JobSchedulerConformance.StatusAsync(host, name)` → `GetStatusAsync`：它对不存在的作业抛出，必定交出值，按同一条规则是 `Get`。
5. 动词的用法（调度契约内，与 RFC-0001 一致）：
   - `Find`：按标识找，没有为无值；批量时结果与入参等长、同序，逐项是 `Maybe`。
   - `List`：按查询或过滤项列出，结果的条数与顺序由方法自己规定。
   - `Count` 照旧（`CountRunsAsync`）。
6. 都是纯重命名：参数、返回类型、级别、行为、错误码与消息键都不变。不留旧名的别名。
7. 不改名：`IJobStore.HeartbeatAsync`（备选 7）；`JobStatusQuery`、`JobStatusPage`、`JobRunQuery`、`JobRunView` 等类型名；`Kubernetes` 的领导选举（`ILeaderElection` 没有名词方法，这个包不实现 `IJobScheduler` 或 `IJobStore`）。

## 理由

- 方法名第一个词说出「做什么」，读调用点时不用翻文档：`FindStatusesAsync(names)` 与 `ListStatusesAsync(query)` 的区别、`ListRunsAsync` 与 `CountRunsAsync` 的区别都在动词上。
- `Find` 同时说出了「可能没有」：调用方看名字就知道每一项要判 `HasValue`，这正是 RFC-0001 那条规则要的效果。
- 调度器与存储对同一次读取用同一个名字（`ListRunsAsync`），实现 `IJobStore` 的人看到的是一组 `List…`，与 `ListJobsAsync` 排在一起。
- `ListCancelRequestedRunsAsync` 以 `List` 起头之后，`Cancel` 不再被读成这个方法的动作。
- 现在改的代价只是查找替换；`IJobScheduler` 是 `Stable`，5.0 正式版之后就不能改了。

## 影响

- 源码迁移（全是改名，查找替换即可）：
  - 应用代码：`scheduler.RunsAsync(query, ct)` → `ListRunsAsync`；`scheduler.StatusesAsync(names, ct)` → `FindStatusesAsync`；`scheduler.StatusAsync(name, ct)` → `FindStatusAsync`。
  - 自写的 `IJobStore`：六个方法照决策 3 的表改名，方法体不动。
  - 继承 `JobSchedulerConformance` 的测试里用到 `StatusAsync(host, name)` 的改成 `GetStatusAsync`。
- 行为：不变。日志模板、错误码、消息键、事件主题与线上形态里都没有这些方法名。
- 仓库里跟着改的：`JobSchedulerEngine`、两个存储、两套一致性套件（`JobSchedulerConformance`、`JobStoreConformance`）与内存、数据库两个测试项目。示例与各包 README 里没有出现这些名字。
- 较早的 ADR（0020、0053、0082、0148）与 `plans/5.0-API审查.md` 里的旧名是当时的名字，不回改；对应关系见决策的两张表。
- 规范（待补）：RFC-0013 与错误码登记表里写的是 .NET 参考实现的方法名，改成新名字：
  - RFC-0013「调度器 `IJobScheduler`」：`StatusesAsync(names[])`、扩展方法 `StatusAsync(name)`、`RunsAsync(query)`（两处）。
  - RFC-0013「存储 `IJobStore`」：`TriggersAsync(job?)`、`RunsAsync(query)`、`RunningAsync(job?)`、`LastRunsAsync(jobs[])`、`CancelRequestedRunsAsync(nodeId)`、`NodesAsync()`。
  - `conventions/error-codes.md` 的 `SCHEDULING_VALIDATION_002`：「`RunsAsync` 以结果返回」。
- 文档站（待补）：`docs/scheduling/cluster.md`、`docs/scheduling/jobs.md`、`docs/packages/scheduling-abstractions.md` 里的三个应用面方法名。
- 没有处理、另行决定的：`IJobStore.HeartbeatAsync`（备选 7）；别的子系统里同类的名词方法（备选 8）。
