# ADR-0211 发件箱投递覆盖租户分片库

## 状态

已采纳（RFC-0009「发件箱」一条修订）。

## 日期

2026-11-13

## 背景

5.0 安全审查 S-36（`plans/5.0-安全审查.md`），低危，可靠性。

- `OutboxPublisher` 在活动工作单元里把消息写进发件箱表，与业务写入同一个事务。
- EF Core Provider 一个 `DbContext` 一个连接：带分片的调用里整个上下文连到租户库，发件箱行也写进租户库。
- `OutboxDispatcher` 每轮只在默认库上开工作单元，从不连分片库。EF Core 下带分片的调用发的消息永远发不出去，也没有任何报错。
- SqlSugar Provider 把不实现 `IMultiTenant` 的发件箱行留在默认连接，不受影响。

复现：`EntityFrameworkCoreOutboxShardTests.Dispatcher_DeliversMessagesWrittenIntoTenantShards`。修正前，4 条消息只发出默认库里的 2 条。

## 备选

1. **发件箱行一律写默认库**：否决。EF Core 一个上下文一个连接，写默认库要另起上下文，发件箱行就不再与业务写入同一个事务，失去发件箱的意义。
2. **带分片的调用里发布直接报错**：否决。发布方不知道 Provider 把行写在哪里，SqlSugar 下这样会误伤；也让 EF Core 分库的应用用不了发件箱。
3. **按租户逐个投递**（与工作流的到期书签轮询一样）：否决。很多租户共用一个库，逐个租户轮询会把同一个库查很多遍。
4. **投递器覆盖分片库，按连接去重**：采纳。

## 决策

1. **一轮的范围**：装配了租户分片（容器里有 `ITenantStore`、`ITenantShardResolver` 与 `TenantShardScope`）且 `IncludeShards` 为真时，先投递默认库，再逐个投递分片库。
   - 每个库各自一个工作单元，各自最多 `BatchSize` 条，返回值是各库之和。
   - 投递分片库时新建作用域，先以 `TenantShardScope` 绑定分片，再取工作单元与仓储；工作单元的租户是这个分片的租户。
2. **分片清单**：
   - 从租户目录逐页读出全部租户，含停用的，停用之前写进发件箱的消息照常发出。
   - 经 `ITenantShardResolver` 解析，按连接串与数据库种类去重，每个分片库取它的第一个租户。
   - 每 `ShardRefreshInterval`（默认 1 分钟）重读一次。重读失败记 Warning 日志、沿用上一次的清单，下一轮再读。
3. **失败隔离**：
   - 一个库的存储失败不挡其他库，全部轮完之后再抛出：一个库失败抛出它的异常，多个库失败抛出 `AggregateException`。
   - 调用方取消立即抛出，余下的库不再投递。
4. **选项**：`XiHan:Messaging:Outbox:IncludeShards`（默认 `true`）、`ShardRefreshIntervalSeconds`（默认 60）。

## 影响

- SqlSugar 下分片轮次查到的仍是默认库，结果不变、只多出查询，可以把 `IncludeShards` 设为 `false`。
- EF Core 下带分片的调用要发消息，分片库就要建发件箱表；没有建的分片库每轮投递失败、记日志，不影响其他库。
- `Messaging.Abstractions` 新增对 `MultiTenancy.Abstractions` 的引用（同环的契约包）。
- 公开 API：`OutboxOptions.IncludeShards`、`OutboxOptions.ShardRefreshInterval`。
