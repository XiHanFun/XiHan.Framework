# ADR-0311 绑定根目录跳过以点开头的子目录与绑定核对改名

## 状态

已采纳（规范 RFC-0016「资源绑定与配置节」第 10 条改写、新增第 11 条，RFC-0017 的状态行与「与 .NET 的映射」已改；内核 `BindingResolver` 的两条读法都跳过根目录下以 `.` 开头的子目录，`Kernel.Plugins.PluginBindingRules` 改名 `Kernel.Hosting.BindingRules`，`AppBuilder`、`Plugins.Protocol` 的 `PluginConfigureRequests` 与 `Plugins.InProcess` 的 `InProcessPluginHost` 跟着改；向量、档表、错误码与 Go 一致性模块不变）。

## 日期

2026-11-26

## 背景

ADR-0301 留下的两件事，仓库所有者已拍板，契约先进规范：

1. **根目录下以 `.` 开头的子目录被当成绑定读**（ADR-0301 备选 12、待定）。绑定目录里的文件早就是「以 `.` 开头的不读、不计」（ADR-0292），根目录下的子目录没有同样的口径：`BindingResolver` 把根目录下的每个子目录都读成一个绑定（目录名就是绑定名），并计入 ADR-0301 的 128 个绑定的上限。Kubernetes 把 projected volume 直接挂到 `SERVICE_BINDING_ROOT` 时（一个卷里投影多个 Secret，每个绑定一个子路径），根目录下除了绑定还有 `..data`（指向带时间戳的目录的符号链接）与 `..2026_11_25_…` 这样的目录：解析全部绑定时它们成了两个名为 `..data`、`..<时间>` 的空绑定，出现在 `FeatureContext.Bindings` 与 `BindingResolver.Resolve` 的结果里，并各占一个名额，127 个真绑定的根目录就因「多于 128 个」启动失败。点了名的解析（插件宿主）不受影响：清单里的绑定名不以 `.` 开头（RFC-0002 的文法）。
2. **`PluginBindingRules` 的名字与位置**。ADR-0301 让内核装配特性也用这一处（备选 2 当时否决了改名：能复用就不挪），它的说明写着「名字里的 Plugin 是最初的使用方」。现在它有四个使用方：内核装配特性与三种插件宿主，名字与命名空间（`Kernel.Plugins`）都说它是插件的规则。它是 `Preview`、还没发布，改名不牵动已发布的契约。

另外，projected volume 里每个绑定名常常是指向 `..data/<名>` 的符号链接，Secret 卷挂到一个绑定目录时每个属性文件也是指向 `..data/<键>` 的符号链接：要确认按现在的读法这类链接读得出正确的内容。

## 备选

以 `.` 开头的子目录：

1. **只在解析全部绑定时跳过，点名时照读**：否决。点名时清单里的名字本来不以 `.` 开头，跳不跳结果一样；一条规则两种写法，迟早有人以为点名能读到 `..data`。两条读法都跳过，与绑定目录里以 `.` 开头的文件同一个口径。
2. **跳过、但照样计入 128 个**：否决。要解决的就是 projected volume 挂到根目录时的名额：计入的话，那两个目录照样让正好 128 个绑定的根目录启动失败。不读也不计，与 ADR-0292、ADR-0301 对以 `.` 开头的文件的处理相同。
3. **只跳过 `..data` 与 Kubernetes 带时间戳的目录（`..` 开头）**：否决。Kubernetes 的命名是实现细节，别的挂载工具也用以 `.` 开头的名字放元数据；文件的口径是「以 `.` 开头」，目录同一个口径，运营方只记一条。
4. **跳过的目录不限个数**：采纳。与以 `.` 开头的文件相同（ADR-0301 备选 11）：只枚举名字、不读内容，不占「上限再多一项」的那一项。
5. **跳过的目录记一条日志**：否决。它们是挂载工具正常放的东西，每次解析都记一条只是噪音。

符号链接：

6. **照现在的读法：指向目录的链接按目录、指向文件的按文件，名字取目录项自己的，内容与大小取链接最终指向的**：采纳。.NET 在 Windows 与其他系统上都这样列目录项（`Directory.EnumerateDirectories` 列出指向目录的链接，`Directory.EnumerateFiles` 列出指向文件的链接），读文件经 `FileStream` 跟随链接；ADR-0292 按读到的字节计数，不看文件系统报的长度（链接本身只有几个字节），超过上限照样失败。测试按 Kubernetes 的两种挂法搭出目录核对，代码不用改。
7. **不跟随符号链接**：否决。projected volume 挂到根目录时每个绑定都是链接，不跟随就一个绑定也读不出。
8. **名字取链接目标的名字**：否决。根目录下的 `db` 指向 `..data/db`，名字碰巧相同；`..data` 指向带时间戳的目录，取目标的名字就成了时间戳。名字是运营方在卷里写的那个。
9. **链接不得指出根目录**：这次不做。绑定根目录与里面的内容由运营方挂载，信任边界与配置相同（一个指向 `/etc` 的链接是运营方自己放的）；大小与条目数的上限照样按目标计，读不进无界的内容。记为待定。
10. **Windows 上建不了符号链接时改用目录联接（junction）**：否决。Kubernetes 放的是符号链接，联接只能指向目录、不能代替文件链接；拿不到权限（开发人员模式或提升的进程）时跳过那几条用例并写明原因，Linux 上的 CI 照跑。

改名：

11. **留在 `Kernel.Plugins`，只改类型名**：否决。它核对的是 `Kernel.Hosting` 里的 `BindingValue`（`BindingResolver` 的解析结果），两处使用方都在 `Kernel.Hosting` 一侧：`AppBuilder` 本身在 `Kernel.Hosting`，引用 `Kernel.Plugins` 只为这个类型；`PluginConfigureRequests` 与它的向量测试同样只为它引用 `Kernel.Plugins`，本来就引用 `Kernel.Hosting`（为了 `BindingResolver`、`BindingValue`）。`InProcessPluginHost` 两个都引用（它还要 `IPluginHost` 等）。名字去掉 Plugin、位置还在插件的命名空间，说的仍是插件的规则。
12. **挪进 `Kernel.Hosting`，与 `BindingResolver`、`BindingValue` 放在一起**：采纳。文件随之挪到 `Hosting/BindingRules.cs`，测试挪到 `Kernel.Tests/Hosting/BindingRulesTests.cs`。
13. **另起命名空间（如 `Kernel.Bindings`）把绑定的类型都挪过去**：否决。`BindingResolver`、`BindingValue` 是 `Stable`，不挪；只挪规则，绑定的类型反而分在两处。
14. **留一个标 `[Obsolete]` 的旧名转发**：否决。它是 `Preview`、没有发布过（`PublicAPI.Shipped.txt` 是空的），仓库的规则是不留推测性的兼容别名；引用它的只有框架自己的三个包。

## 决策

1. **根目录下以 `.` 开头的子目录不是绑定**（RFC-0016「资源绑定与配置节」第 11 条，第 10 条改写为「根目录下的每个绑定都计入」）：解析全部绑定时先跳过它们再数、再读，不读、不计入 `BindingResolver.MaxBindings`；只解析点了名的绑定时同样不读（`BindingResolver` 的私有判断 `IsBinding`，两条读法共用）。一个绑定目录里的子目录不是属性、不读（现状，写进规范）。配置来源不受约束。
2. **符号链接**（同一条）：目录项可以是符号链接，指向目录的按目录，指向文件的按文件，名字取目录项自己的名字，读的是链接最终指向的内容，大小与条目数也按它计。Kubernetes 的两种挂法因此都读得出卷里当前的内容：projected volume 直接挂到根目录（`..data`、带时间戳的目录与每个绑定名一个指向 `..data/<名>` 的链接），Secret 卷挂到一个绑定目录（目录里的 `..data` 与带时间戳的目录是子目录，每个属性文件指向 `..data/<键>`）。卷更新时 Kubernetes 换掉 `..data` 的指向，下一次解析读到的是新内容。
3. **`PluginBindingRules` 改名 `BindingRules`，挪到 `XiHan.Framework.Kernel.Hosting`**（`Preview`，成员不变：`HasContent`、`FindViolation`），不留旧名。RFC-0017 的 .NET 映射跟着改。

## 理由

- 以 `.` 开头的名字在 Service Binding 的目录里一直是挂载工具的元数据：文件早就照此处理，目录换成同一个口径，运营方不必知道 Kubernetes 怎样放它的原子写入目录，也不会因为它们多出两个空绑定、少两个名额。
- 符号链接按目标读是 projected volume 能用的前提，也是 .NET 文件系统 API 的缺省行为；把它写进规范并用按 Kubernetes 目录结构搭的用例核对，以后改读法（比如换成不跟随链接的枚举）的人会看到这些用例失败。
- 规则的名字与位置跟着它的使用方：四个使用方都在核对绑定，它与解析绑定的类型放在一起，读代码的人不必去插件的命名空间里找内核装配特性用的规则。

## 影响

- **公开 API**（`PublicAPI.Unshipped.txt` 已用 `Sync-PublicApi.ps1` 同步）：`Kernel`：`XiHan.Framework.Kernel.Plugins.PluginBindingRules` 改为 `XiHan.Framework.Kernel.Hosting.BindingRules`，成员与签名不变。`Plugins.Protocol`、`Plugins.InProcess`、`Plugins.OutOfProcess`、`Plugins.Wasm` 的公开面不变。没有新的错误码、消息键与配置键。
- **对已有部署与代码的行为变化（升级须知）**：
  - 绑定根目录下以 `.` 开头的子目录不再读成绑定，不再出现在 `BindingResolver.Resolve` 与 `FeatureContext.Bindings` 的结果里，也不计入 128 个绑定的上限；以前把绑定放在以 `.` 开头的目录里的，改个名字（清单里的绑定名本来不能以 `.` 开头，经清单声明的绑定不受影响）。
  - 引用 `PluginBindingRules` 的代码改成 `BindingRules`，`using XiHan.Framework.Kernel.Plugins` 换成（或加上）`using XiHan.Framework.Kernel.Hosting`。
- **规范（规范工作区已提交）**：RFC-0016 状态行、第 10 条（根目录下的每个绑定都计入，以 `.` 开头的子目录不计）与新增的第 11 条（目录项：以 `.` 开头的子目录不是绑定，子目录不是属性，符号链接的读法，Kubernetes 的两种挂法）；RFC-0017 状态行与「与 .NET 的映射」。第 11 条里以 `.` 开头的子目录是规范的 MAJOR（`v1.0.0` 之前允许）：改了 ADR-0301 写明的「根目录下的每个子目录都是一个绑定」；子目录与符号链接是写明（MINOR）；RFC-0017 的改名是 PATCH。向量不变：向量里没有目录结构，`binding-properties.json` 的 `limits` 与 `$comment` 说的「根目录下的绑定数」仍然准确。
- **Go 一致性模块与六个 SDK**：不变。目录来源只由宿主解析（.NET），插件一侧收到的是下发的绑定；Go 规则包只有上限的常量，没有读目录的实现。
- **测试**：
  - 内核 `BindingResolverDirectoryEntriesTests`（新增）：以 `.` 开头的子目录不进结果、不计入（128 个绑定加三个以 `.` 开头的目录照常读）、不读（里面有超限的文件与多于 128 个的文件也不失败）、点了名也不读；projected volume 挂到根目录时按链接读出两个绑定、名字取链接自己的；Kubernetes 换掉 `..data` 的指向之后读到新内容；Secret 卷挂到绑定目录时按链接读出属性、`..data` 不是属性；链接指向的文件超过大小上限照样失败。改之前八条里六条失败：四条以 `.` 开头的目录的用例，与两条 projected volume 的用例（链接读出的内容本来就对，失败在多出来的 `..data` 与带时间戳的绑定）；Secret 卷与链接文件大小的两条改之前也通过。建符号链接拿不到权限的 Windows 上跳过符号链接的用例，原因写在跳过信息里；本机（开发人员模式）全部运行。
  - `InProcessPluginHostTests`：根目录下 128 个绑定加 `..data` 与带时间戳的目录时插件照常加载（改之前以「多于 128 个绑定」加载失败）。`PluginConfigureRequestsTests`：projected volume 挂到根目录时，插件宿主按链接下发 `db` 的类型、主值与属性。
  - 改名：`BindingRulesTests`（原 `PluginBindingRulesTests`）、`FeatureBindingRulesTests`、`ProtocolVectorTests` 跟着改，断言不变。
- **文档**：内核 README 已同步（绑定目录的读法、`BindingRules`）；文档站的 `configuration/bindings`、`packages/kernel`、`packages/plugins-inprocess`、`appendix/spec` 与更新日志待改。历史 ADR（0292、0301）的正文是当时的记录，不改。
- **待定**：链接是否可以指出绑定根目录（备选 9）。
