# ADR-0292 绑定的大小上限与下发前的核对

## 状态

已采纳（规范 RFC-0016「资源绑定与配置节」第 8、9 条、`plugin/lifecycle.md` §2、RFC-0002 的字段表、RFC-0017、清单 Schema 的 `bindings[].required` 说明、`conventions/error-codes.md` 已补，向量 `plugin/binding-properties.json` 与 `plugin/plugin-messages.json` 已补；内核新增 `KernelErrors.BindingTooLarge`、`BindingResolver.MaxFileBytes` / `MaxBindingBytes` 与 `PluginBindingRules`，`Plugins.Protocol` 的 `PluginConfigureRequests` 与 `Plugins.InProcess` 的 `InProcessPluginHost` 已改；Go 一致性模块的 `rules.DeliverBindings` 等已同步）。

## 日期

2026-11-25

## 背景

ADR-0268 让下发给隔离运行的插件的绑定与内核同源解析，ADR-0285 让绑定带上属性并给下发的那一段加了文法与每个绑定的上限。两份 ADR 的「待定」里留下四件事：

1. **绑定目录的文件没有大小上限。** 内核的 `BindingResolver` 读 `SERVICE_BINDING_ROOT` 下的文件用 `File.ReadAllText`，一个文件整个读进内存。绑定目录里放错一个大文件（日志、备份、几百 MB 的证书归档），应用启动时就把它读进内存；ADR-0285 的下发上限只在读进来之后才判断。
2. **只限每个绑定，不限整个请求。** 每个绑定的属性最多 262144 字节，十几个顶到上限的绑定加起来超过 gRPC 缺省的 4 MiB 消息上限：进程外插件的 `Configure` 失败在传输层（插件一侧的 gRPC 服务端以 `ResourceExhausted` 拒收），运营方看到的是一个与绑定无关的状态码；Wasm 插件则是客体内存分配失败。
3. **来源声明的类型与清单不同时照样下发**（ADR-0268 备选 15）。插件声明要一个 `connection:relational`，运营方挂了一个 `type` 为 `connection:document` 的绑定，插件收到的类型是 `connection:document`，多数插件不看类型，拿着文档库的连接串去连关系库。内核装配特性时对必需绑定的同一种情形是启动失败（`KERNEL_HOSTING_001`）。
4. **必需的绑定解析不出时照常配置**（ADR-0268 备选 16）。清单的 `bindings[].required` 早已写在 Schema 里，缺省 `true`，原语层 `Binding` 的文档写着「缺失必需绑定在启动期失败」；内核对特性照此执行，插件宿主一直不看它：绑定不在请求里，插件自己决定怎么办，常见的结果是带着空连接启动、第一次调用才失败。

另外，进程内插件（`Plugins.InProcess`）拿的是整个宿主配置、宿主不下发绑定，对这两条也一样不做任何核对。

## 备选

绑定目录的文件大小：

1. **只限一个绑定的合计**：否决。任务要的是两道：一个文件就能占满合计，单个文件的上限让错放的大文件在它自己身上就停下，报出来的也是那个文件。
2. **单个文件 262144 字节（与下发的每个绑定上限相同）**：否决。宿主进程里的特性也读绑定（ADR-0285 备选 17：内核的读法是 `Stable` 契约），整份 CA 证书包在 200 KB 以上，再加上文件里的首尾空白要另占额度，正好卡在下发上限上会让「下发得了、读不进来」的情形出现。
3. **单个文件 524288 字节（512 KiB）、一个绑定合计 1048576 字节（1 MiB）**：采纳。都不小于下发上限的 262144 字节；合计与 Kubernetes 一个 Secret 的上限相同，绑定目录通常就是一个 Secret 挂进来的，正常的部署碰不到它。两个数都按文件的原始字节计（去首尾空白之前），与读进来的字节一致。
4. **先看文件系统报的长度（`FileInfo.Length`）再决定读不读**：否决。符号链接、虚拟文件系统里的文件报的长度不可信，判断与读之间文件还可能变；按读到的字节计，一块一块地读，到额度再多一个字节就停，不必知道文件到底多大。
5. **超限时截断或跳过这个文件**：否决。与 ADR-0285 备选 15 同一个理由：带着缺的凭据启动比启动失败更难查。超限是配置错误，装配时启动失败。
6. **配置来源也设上限**：否决。配置的值已经由配置系统读进内存，上限保护不了什么；`XiHan:Bindings` 的值来自环境变量与配置文件，本来就受它们自己的限制。
7. **沿用 `KERNEL_HOSTING_001`**：否决。它是「必需绑定缺失或类型不匹配」，处置是补上或改正绑定；文件太大的处置是把不该放的文件挪走，要分得出来。新登记 `KERNEL_HOSTING_005`。
8. **限制一个绑定目录里的文件数**：这次不做。合计的字节数已经限住了内存；一万个空文件的目录只是慢，记为待定。

插件宿主遇到超限的文件：

9. **与读失败一样，`reason` 写异常类型的全名**：否决。`FrameworkException` 这个类型名说明不了任何事，运营方要的是哪个绑定、超了哪个上限。
10. **固定的 `reason`，带绑定名与上限，不带文件名**：采纳。`a file of binding '<绑定名>' exceeds 524288 bytes`、`the files of binding '<绑定名>' exceed 1048576 bytes`。文件名就是属性名，这时还没有核对它的文法（ADR-0285 备选 18）。内核抛出的是 internal 的 `BindingTooLargeException`（对外就是携带 `KERNEL_HOSTING_005` 的 `FrameworkException`），`Plugins.Protocol` 认出它后取绑定名与超的是哪一个上限，与持久化抽象包的 `TakeExceededException` 同一个做法。
11. **点了名的绑定目录按文件系统枚举的顺序读**（现状）：否决。两个绑定都读不出或都超限时，报哪一个取决于文件系统；改为按点名的顺序（清单的顺序）读，与之后的核对报「清单顺序里的第一处」一致。不限名字的解析（内核装配时）照旧按枚举顺序。

整个请求的大小：

12. **按内容的字节数计**（配置节加各绑定的名、类型、主值、属性名与值）：否决。protobuf 每个字段另有标签与长度，属性多而小时开销可以是内容的几倍；按内容算对上限没有保证，失败照样落在传输层。
13. **按各载体实际写出的字节计**（进程外按 protobuf 二进制，Wasm 按 proto3 JSON 文本）：否决。同一份配置与绑定换一种载体可能一个下发得了、一个下发不了；JSON 的长度还取决于转义（控制字符写成 `\u00XX`），不好向运营方解释。
14. **一律按 protobuf 二进制编码的字节数计（`CalculateSize`，也就是 gRPC 发出的消息的长度），上限 2097152（2 MiB）**：采纳。它包括配置节、授予的权限、全部绑定与工作目录，没有声明绑定的插件同样核对（配置节本身也可能很大）。上限取 gRPC 缺省消息上限的一半：余量留给 Wasm 载体（JSON 文本比二进制长，最坏是六倍，参考实现的客体内存缺省 64 MiB 容得下），同一个数在两种载体上给出同一个结果。规范同时要求插件一侧 gRPC 服务端的接收上限不小于 4194304（各语言 gRPC 库的缺省值）。
15. **上限取 4 MiB 减一点**：否决。没有余量给 Wasm 的 JSON 文本，也挡不住插件一侧把接收上限调小的情形。
16. **核对放在逐个绑定的核对之前**：否决。一个绑定的属性名不合文法，同时请求又超限时，先报具体的绑定更有用；请求的大小是全部绑定都合格之后才有意义的数。

类型与清单不符：

17. **只核对必需的绑定**（与内核对特性一样）：否决。可选的绑定一旦下发，插件就会拿它去连，给错了类型与必需的绑定一样危险；把它当成没有（不下发、记警告）则是悄悄少给一个运营方明明给了的绑定。
18. **类型不符时不下发并记警告**：否决。理由同上，也与「送不过去的不装作送到了」（ADR-0268）相反。
19. **必需与可选都核对，不符即配置失败**：采纳。`reason` 是 `binding '<绑定名>' is of type '<来源的类型>' but the manifest declares '<清单的类型>'`：绑定的类型不是凭据，两个类型原样写进去，运营方一眼看出改哪一边；主值、属性名与属性值仍不出现。按序数比较，只差大小写也算不同（类型的文法本来就只有小写）。来源没有声明类型时取清单的，不算不同（ADR-0268、ADR-0285 的现行规则，不变）。

必需的绑定解析不出：

20. **给插件清单另加一个字段，缺省可选**：否决。不需要：清单 Schema 早有 `bindings[].required`，缺省 `true`；原语层 `Binding.Required` 缺省 `true`，文档写着缺失必需绑定在启动期失败；内核对特性照此执行。插件与特性用的是同一种清单，插件宿主不看这个字段才是缺口。
21. **插件宿主把 `required` 的缺省当成 `false`，保持现在的行为**：否决。同一份清单在特性与插件上含义不同，Schema 写的缺省值对插件不成立。任务的前提「缺省保持现在的行为」是对新加字段说的；这个字段已经在，缺省值已经写明。代价见「影响」：没写 `required`、又在部署里缺着那个绑定的插件，现在配置失败，迁移是在清单里写上 `"required": false`。
22. **「解析不出」照内核的判断：来源里有这个名字就算给出**：否决。只给了类型（一个只有 `type` 文件的目录）的绑定不会下发（ADR-0285），插件收不到它，对插件就是没有；按「有没有能下发的内容」（主值或至少一个属性）判断。内核装配特性时的判断不动（`Stable`，特性拿得到只有类型的 `BindingValue`），记为待定。
23. **可选的绑定解析不出时也记警告**：不改。来源里根本没有这个绑定是可选绑定的正常情形，不记；只给了类型的照旧记一条（ADR-0285）。

核对的先后：

24. **按清单的顺序逐个绑定核对，一个绑定里依次是有没有、类型、属性的数量、属性名、字节数；全部合格之后核对整个请求**：采纳。与 ADR-0285「按清单的顺序报第一处」一致，每个绑定的问题报在它自己身上；有没有与类型在属性之前，是因为没有内容的绑定谈不上属性，类型不对的绑定属性再合规也不该下发。读失败与文件超限在解析时就报，早于这些核对。

三种插件宿主：

25. **进程内宿主不核对，在 ADR 里写明为什么不同**：否决。进程内插件拿整个宿主配置是信任边界的事（ADR-0177），与「必需的绑定在不在、类型对不对」无关；不核对，同一份清单换成进程内运行就少一道运营方依赖的检查。
26. **进程内宿主在加载插件代码之前按同样的两条核对**：采纳。解析用公开的 `BindingResolver.Resolve(configuration)`，根目录取环境变量：进程内宿主没有特性入口、拿不到应用指定的根目录（ADR-0285 待定），插件自己经同一个方法读到的也是这一份，核对的与插件将要用的一致。不合即加载失败，错误码同为 `PLUGINS_UNEXPECTED_001`，消息键是进程内宿主自己的 `plugins.plugin.load_failed`，`reason` 与另两种宿主相同。属性的文法与上限、请求的总上限只管经协议下发的请求，进程内不核对。
27. **核对的代码放在哪里**：两个插件宿主包都要用（`Plugins.Protocol` 与 `Plugins.InProcess`，后者不引用前者，也不该为此引用 gRPC 依赖）。新增内核的友元否决（ADR-0254 备选 1）；照 ADR-0254 的做法放成下层包的公开成员：内核的 `PluginBindingRules`（`Preview`）。它只有两个方法，规则与 `reason` 的文本只在这一处。
28. **把内核按名字解析的 internal 重载公开，给进程内宿主用**：否决。那是 `Stable` 类型上的新成员，只为一个调用方；进程内宿主读全部绑定与插件自己读的一样，内核装配时也已经把同一个根下的全部绑定读过一遍（读不出或超限的话应用根本起不来）。

## 决策

1. **绑定目录的文件有大小上限**（RFC-0016「资源绑定与配置节」第 9 条）：
   - 一个文件最多 `BindingResolver.MaxFileBytes`（524288）字节，一个绑定目录里读的文件（`type`、`uri` 与其余属性文件，以 `.` 开头的不读、不计）合计最多 `BindingResolver.MaxBindingBytes`（1048576）字节，按原始字节计。
   - 文件按目录的枚举顺序读，每个文件的额度是单个文件的上限与剩余合计额度中较小的一个，每次读 4096 字节，到额度再多一个字节就停；超限时剩余的合计额度不少于单个文件的上限报单个文件，否则报合计。解码与 `File.ReadAllText` 相同（按字节顺序标记识别编码，缺省 UTF-8）。
   - 超限抛出携带 `KERNEL_HOSTING_005`（`KernelErrors.BindingTooLarge`）的 `FrameworkException`，消息只带绑定名、文件名与上限：`File '<文件>' of binding '<绑定>' is larger than 524288 bytes.`、`The files of binding '<绑定>' are larger than 1048576 bytes in total; the limit was reached while reading '<文件>'.`。装配时即启动失败。
   - 配置来源不受约束。按名字解析时（插件宿主）点了名的目录按点名的顺序读。
2. **下发之前核对**（`plugin/lifecycle.md` §2「`bindings` 的核对」）：按清单的顺序逐个绑定，有没有 → 类型 → 属性（数量、属性名、字节数），报第一处；不合即不发 `Configure`，`PLUGINS_UNEXPECTED_001` + `plugins.process.failed`（`phase` 为 `configure`），插件进入 Failed、按重启策略重试。
   - 必需（`required` 缺省 `true`）的绑定两种来源都没给，或只给了类型、没有主值也没有属性：`binding '<绑定名>' is required but not provided`。可选的照旧不下发。
   - 来源声明了类型而与清单的不同（必需与可选都核对，按序数比较）：`binding '<绑定名>' is of type '<来源的类型>' but the manifest declares '<清单的类型>'`。下发的 `type` 因此总是清单声明的类型。
   - 规则在内核的 `PluginBindingRules`：`HasContent(BindingValue)`、`FindViolation(Binding, BindingValue?)`。
3. **整个请求的总上限**：组装之后 `ConfigureRequest` 按 protobuf 二进制编码超过 2097152 字节（`PluginConfigureRequests.MaxBytes`）即不发，`reason` 为 `the configure request exceeds 2097152 bytes`；进程外与 Wasm 都按二进制编码的大小核对。插件一侧 gRPC 服务端的接收上限不得小于 4194304。
4. **文件超限在插件宿主里**：与读失败同样按配置这一步失败处理，`reason` 是固定文本 `a file of binding '<绑定名>' exceeds 524288 bytes` 或 `the files of binding '<绑定名>' exceed 1048576 bytes`，不带文件名；完整的异常只进日志。
5. **进程内宿主**：`InProcessPluginHost.LoadAsync` 在加载插件代码之前（清单、权限、入口与程序集文件都核对过之后）解析宿主配置与环境变量指定的绑定根，按清单的顺序用 `PluginBindingRules.FindViolation` 核对；不合返回 `PLUGINS_UNEXPECTED_001` + `plugins.plugin.load_failed`（`reason` 同上），读不出时 `reason` 为异常类型的全名，文件超限时为内核的消息。
6. **日志**：两个插件宿主把这些失败都记成一条 Error（`The configure request of plugin <ID> is not sent: <reason>; the plugin is not configured.`、`Plugin <ID> is not loaded: <reason>.`），只带插件 ID 与 `reason`。

## 理由

- 读的时候就按上限截断，是「上限」能保护内存的唯一写法：先读进来再判断，上限只是一条报错规则。
- 内核的上限比下发的宽：宿主进程里的特性读绑定是 `Stable` 契约，不该因为插件的线协议多了一道限制而读不进证书；两道上限之间的关系（目录的不小于下发的）写进规范，并由 Go 一致性模块核对。
- 整个请求按线上的二进制长度核对，是唯一与传输上限可比的量；同一个量用在两种载体上，配置的结果不随载体变。
- 类型与必需的核对补的是插件宿主对清单的理解：同一份清单、同一个字段，在特性与插件上含义一样。不合时让配置失败而不是少给，沿用 ADR-0268、ADR-0285 的原则：送不过去的不装作送到了，运营方从宿主一侧看得到原因与绑定名，改了部署之后插件在下一次重试时自己起来。
- 进程内宿主补上同样的两条，是因为这两条核对的是部署与清单是否相符，与插件在哪里运行无关。

## 影响

- **公开 API**（`PublicAPI.Unshipped.txt` 已同步）：
  - `Kernel`：`KernelErrors.BindingTooLarge`（`KERNEL_HOSTING_005`）；`BindingResolver.MaxFileBytes`、`BindingResolver.MaxBindingBytes`；新类型 `Kernel.Plugins.PluginBindingRules`（`Preview`：`HasContent`、`FindViolation`）。internal：`BindingTooLargeException`。
  - `Plugins.Protocol`：没有公开面的变化（`PluginConfigureRequests.MaxBytes` 是 internal 类型上的常量）。`Plugins.OutOfProcess`、`Plugins.Wasm`、`Plugins.InProcess` 的公开面不变。
  - 新错误码 `KERNEL_HOSTING_005` 已登记；没有新的消息键，五条新的固定 `reason` 进了 `plugin-messages.json`。
- **对已有部署的行为变化（升级须知）**：
  - 绑定目录里有文件超过 512 KiB、或一个绑定目录的文件合计超过 1 MiB（以 `.` 开头的不算）：应用启动失败（`KERNEL_HOSTING_005`）。把不属于绑定的文件挪出绑定目录。
  - 插件清单声明的绑定没写 `required`（缺省必需），部署里又没给（或只给了类型）：进程外与 Wasm 插件配置失败、进入 Failed 并按重启策略重试，进程内插件加载失败；以前照常配置，插件自己处理没有绑定的情形。补上绑定，或在清单里写 `"required": false`。
  - 来源声明的类型与插件清单声明的不同（`type` 文件或 `XiHan:Bindings:<名>:type`）：插件配置或加载失败；以前下发来源的类型。改正来源的类型，或去掉它（来源不声明类型时取清单的）。可选的绑定同样核对。
  - 进程外与 Wasm 插件的 `Configure` 请求按 protobuf 编码超过 2 MiB：配置失败，`reason` 说明是整个请求；以前照发，失败在 gRPC 或客体内存上。
  - 插件宿主的这几种失败与以前的属性超限共用一条 Error 日志，模板由 `The bindings of plugin … cannot be delivered: …` 改为 `The configure request of plugin … is not sent: …`。
  - 宿主进程里的特性：只多了文件大小的上限，必需与类型的核对不变（`KERNEL_HOSTING_001`）。
