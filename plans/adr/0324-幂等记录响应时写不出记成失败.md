# ADR-0324 幂等记录响应时写不出记成失败

## 状态

已采纳（规范 RFC-0006「幂等」第 2 条与状态行已改；本仓库 `Caching.Abstractions` 的 `IdempotencyMiddleware` 实现；ADR-0318「影响」与「待定」里留下的这一条由本 ADR 处置；公开 API、错误码、消息键与配置键不变）。

## 日期

2026-11-27

## 背景

ADR-0318 的「影响」里记下一个既有缺陷，「待定」里留下它的处置：

- 开了幂等的操作调用，处理器成功之后 `IdempotencyMiddleware.Complete` 用 `operation.EncodeResponse(response)` 把响应编成 XGI 的 JSON 记进存储。响应写不出时（浮点成员是 NaN 或无穷、字符串有孤立的代理项、超过 64 层、有重复成员，RFC-0011 规则 10 的「编码」；ADR-0320 之后 `EncodeResponse` 写不出只抛 `ArgumentException`）它抛出。
- 这个异常在清除标记的 `try` 之外：Observe 阶段把它翻译成 `KERNEL_UNEXPECTED_001`，操作却已经执行；「处理中」的标记留到 `InProgressTimeToLive`（默认 60 秒）过期，这段时间里的重试得 `CACHING_CONFLICT_002`，过期之后的重试再执行一次操作，再失败一次。
- 类型化入口（`InvokeAsync<TRequest, TResponse>`）自己不编码响应，但幂等要记下它，结果与 XGI 入口相同。
- HTTP 的操作端点在 Handle 阶段里经 `ExecuteAsync` 编码，写不出时已经把结果改成 `KERNEL_UNEXPECTED_001`，幂等照常记下这个失败、重试回放它；XGI 与类型化两个入口与它不一致。

仓库所有者定了处置：**用写不出的错误替换「处理中」标记并把这个错误返回给调用方，重试回放同一个错误，不再执行操作。**

## 备选

1. **记下写不出的错误、作为本次调用的结果**：采纳（所有者的决定）。操作只执行一次，首次调用与重试拿到同一个错误，与 HTTP 端点现在的结果一致。
2. **清除标记、允许重试**（与处理器抛出异常相同，RFC-0006 幂等第 3 条）：否决。操作已经执行，重试会再执行一次；写不出的原因在响应里，重试照样写不出，等于每次重试都多执行一次。
3. **记下成功、不记响应**：否决。回放时没有响应，按 RFC-0006 第 4 条返回 `CACHING_CONFLICT_003`，首次调用与重试的结果不同；首次调用的 XGI 入口照样写不出。
4. **用缓存子系统自己的错误码**（如新的 `CACHING_UNEXPECTED_001`）：否决。写不出的是响应，不是缓存；XGI 入口没开幂等时写不出就是 `KERNEL_UNEXPECTED_001` + `kernel.invocation.unhandled_exception`，开不开幂等不该让调用方看到两种错误。
5. **把异常重新抛出、由 Observe 阶段翻译**（先换掉标记再 `throw`）：否决。结果靠 Observe 阶段翻译出同一个错误，中间件之间多一层隐含的约定；没有 Observe 阶段的管道（只装配部分中间件的测试与宿主）会把异常抛给调用方，与记下的错误不一致。

错误的形状：

6. **与 XGI 入口写不出时完全相同**：采纳。`KERNEL_UNEXPECTED_001` + `kernel.invocation.unhandled_exception`，没有参数；异常是框架异常时它的错误放进 `inner`（`OperationInvoker` 的写法），`EncodeResponse` 写不出时抛出的是 `ArgumentException`，不带 `inner`。
7. **带上写不出的原因**（异常消息）作参数：否决。异常消息是英文的编程诊断，不是给调用方的文案；XGI 入口也不带。

记录的形状：

8. **`IdempotencyRecord.From(failure)` 加操作 ID**：采纳。与其他失败的操作调用的记录相同（错误码、已解析文案、消息键、字符串化的参数、操作 ID，不记响应），回放按 RFC-0006 第 4 条：同一个操作回放这个错误，另一个操作拿同一个键仍是 `CACHING_CONFLICT_003`。存储格式不变，以前写下的记录照旧读得出。

## 决策

1. **规范**：RFC-0006「幂等」第 2 条写明：响应编不出时用编不出的错误替换标记，保留 `TimeToLive`，作为本次调用的结果；错误与 XGI 入口写不出响应时相同；记录与其他失败的操作调用一样记下操作 ID、不记响应；两个入口的首次调用都拿到这个错误，重复调用按第 4 条回放、不再执行。状态行同日写明一条，对应 ADR 加上本 ADR。
2. **实现**（`IdempotencyMiddleware.Complete`）：
   - `EncodeResponse` 与把编出的文本解析成 `JsonElement` 两步放进同一个 `try`，接住 `OperationCanceledException` 之外的异常（与 `OperationInvoker.ToResponse` 相同）。编出的不是 JSON 文本（自定义的描述）同样当作写不出。
   - 接住时构造与 XGI 入口相同的错误，`context.SetOutcome` 设为本次调用的结果，记下 `IdempotencyRecord.From(failure) with { Operation = operation.Id }`；照旧用 `SetAsync` 替换标记、保留 `TimeToLive`。
   - XGI 入口在管道结束之后看到的是失败，不再编码；类型化入口交出这个错误。HTTP 端点不变（端点在 Handle 阶段已把结果改成同一个错误）。
3. **测试**（`Caching.InMemory.Tests` 的 `IdempotentOperationReplayTests`，取号操作的取号人为 `unencodable` 时成功、交回的名字是一个孤立的代理项）：
   - XGI 入口：两次调用都是 `KERNEL_UNEXPECTED_001` + `kernel.invocation.unhandled_exception`、没有参数、不带 `inner`、没有载荷；操作只执行一次；存储里的记录是 `completed`、错误码与消息键是这个错误、操作是 `tickets.create`、没有响应。
   - 类型化入口：两次类型化调用与随后一次 XGI 调用都拿到同一个错误，操作只执行一次，记录同上；另一个操作拿同一个键仍是 `CACHING_CONFLICT_003`、不执行。
   - 先红后绿：改之前两条都在第二次调用失败（`CACHING_CONFLICT_002`）。

## 影响

- **行为**：开了幂等的操作调用响应写不出时，首次调用的结果不变（`KERNEL_UNEXPECTED_001`），重试在 `TimeToLive`（默认 24 小时）内回放同一个错误、不再执行；以前 60 秒内的重试得 `CACHING_CONFLICT_002`，之后的重试再执行一次。Observe 阶段不再为这种情形记一条未处理异常的日志（异常没有抛出），Span 与指标照旧记失败与错误码，与 XGI 入口写不出时相同。
- **公开 API**：不变。`IdempotencyMiddleware`（`Stable`）的签名不变，XML 文档补上这一条；`IdempotencyRecord` 是 internal。没有新的错误码、消息键与配置键。
- **规范**（规范工作区已提交）：RFC-0006「幂等」第 2 条与状态行，MINOR（写明以前不作规定的处置；合规的对端写出的本来就是写得出的响应）。向量不变。
- **六个 SDK**：不受影响。SDK 只交出幂等键（`IdempotencyKey`），没有幂等中间件与幂等记录。
- **文档**：`Caching.Abstractions` 的 README 已同步。

## 理由

- 操作已经执行，记录就应当是「已完成」：写不出的是这次的响应，不是操作没做；让重试再执行一次，比让调用方拿到一个错误代价大得多。
- 首次调用与重试拿到同一个错误，才符合「回放首次调用的结果」；HTTP 端点一直如此，XGI 与类型化入口随之一致。
- 错误与不开幂等时相同，调用方不必区分是不是幂等的调用。
