# ADR-0253 CI 分作业并行与测试分片

## 状态

已采纳（只改 `.github/workflows/ci.yml`、新增 `.github/actions/test-shard`、`framework/test/shards.json`、`framework/scripts/New-TestShard.ps1` 与架构测试 `TestShardTests`；门禁内容不变）。

## 日期

2026-11-24

## 背景

- `ci.yml` 的主作业把还原、构建、测试、打包、SBOM、漏洞清单、AOT 冒烟串在一起，近三次用时 542、735、777 秒；CI 的总时长就是它。
- 各步骤（777 秒那次）：服务容器 40、还原 25、构建 153、测试 362、打包 70、漏洞清单 58、AOT 冒烟 47。打包、漏洞清单与 AOT 冒烟不依赖测试结果，却排在测试后面。
- 测试的 362 秒里，66 个测试程序集合计约 890 秒，按 4 核并行。其中 `Workflow.Database.Tests` 161 秒、`Persistence.SqlSugar.Tests` 153 秒、`Plugins.OutOfProcess.Tests` 67 秒，其余都在 32 秒以内。最慢的两个都是等数据库，不是等 CPU。
- 六个服务容器（Redis、PostgreSQL、SQL Server、MySQL、RabbitMQ、Qdrant）全起在主作业上，用到它们的只有 11 个测试项目。

## 备选

1. **只把打包、漏洞清单、AOT 冒烟挪到并行作业**：能省约 3 分钟，测试仍是 6 分钟加 2.5 分钟构建。不够。
2. **构建一次、把产物传给各测试作业**：否决。150 个项目的 `bin` 与 `obj` 有几个 GB，上传加下载的时间抵得上重新构建，还多一处「产物与源码不一致」的可能。
3. **在仓库里维护若干 `.slnf`**：否决。新测试项目忘了加进任何一个筛选器就不再运行，CI 照样是绿的。
4. **分片表只列要服务的项目、其余自动归一片，筛选器现场生成**：采纳。
5. **拆每个数据库一个作业（照现在 Oracle 的做法）**：现在不做。`database` 分片约 5 分钟，与构建作业相当，再拆只增加作业数。
6. **改 `Workflow.Database.Tests` 每个用例建删一个库的做法**：不在本 ADR。那是测试隔离的设计，要单独评估。

## 决策

1. `ci.yml` 拆成并行作业，总时长取最慢的一个：
   - `build`：还原、带全部分析器的整套构建、打包（包验证与 README 检查）、SBOM 核对、上传包。
   - `test-core`、`test-integration`、`test-database`、`test-oracle`：测试分片，见下。
   - `aot`：依赖漏洞清单与 Native AOT 发布冒烟。
   - `benchmarks`：性能门禁，不变。
2. 分片表 `framework/test/shards.json`：
   - 只列要外部服务或工具链的测试项目。每片写明作业设置的门控环境变量（`variables`）与安装的工具链（`tools`）。
   - 没列进任何分片的测试项目归 `core`，不带服务。新测试项目不用登记。
   - `integration`：Redis、RabbitMQ、Qdrant 与 Go；`database`：PostgreSQL、SQL Server、MySQL；`oracle`：Oracle。`Persistence.SqlSugar.Tests` 同时在 `database` 与 `oracle` 里，各跑各的门控用例。
3. `framework/scripts/New-TestShard.ps1 -Shard <名>` 生成 `framework/artifacts/shards/<名>.slnf`，只含这一片的测试项目；被引用的正式包与示例由项目引用带出。本机与 CI 用同一份。
4. 组合动作 `.github/actions/test-shard`：安装 SDK（要 Go 的分片另装 Go）、生成筛选器、还原、构建、测试并采集覆盖率、上传测试结果。服务容器与门控变量由调用它的作业声明。
5. 测试分片的构建带 `-p:RunAnalyzers=false`：分析器不影响生成的程序集，代码风格、PublicAPI 与 AOT 分析器的门禁由 `build` 作业对整套解决方案执行。编译器警告在分片里照旧按错误处理，源生成器不受影响。
6. 架构测试 `TestShardTests` 守住分片表：
   - 表里的测试项目都存在，分片名不重复、不叫 `core`。
   - 测试项目的源码里出现某个分片提供的门控变量（`XIHAN_TEST_*`）或按名字启动某个分片提供的工具（`ProcessStartInfo("go"`）时，它必须在提供它的分片里。
   - `ci.yml` 里每个分片（含 `core`）都有作业运行，分片的变量都有设置。
7. `ci.yml` 的触发路径加上 `.github/actions/**`。

## 理由

- 门控用例在变量没设时跳过而不是失败。分片之后，测试项目放错分片不会让 CI 变红，只会让用例不再运行；所以分片表必须由测试守住，而不是靠约定。
- `core` 取「其余全部」，新测试项目默认就在 CI 里，登记只在要服务时才需要，而那时架构测试会要求登记。
- 分析器在每个作业里都跑是重复劳动：同一份源码、同一套规则，结论相同。

## 影响

- CI 总时长预计由 9–13 分钟降到 5–6 分钟（最慢的是 `build` 与 `test-database`）；运行器总用时增加，因为每个作业各自还原与构建。
- 作业名变了。仓库的规则集不要求状态检查，没有要跟着改的地方。
- 产物名由 `ci-artifacts` 改为 `packages` 与 `test-results-<分片>`。
- 新增门控服务时要改三处：分片表的 `variables`、`ci.yml` 里那个作业的 `services` 与 `env`。漏了哪处架构测试都会失败。
- 本机的标准验证命令不变（`dotnet test --solution framework/XiHan.Framework.slnx`）。
