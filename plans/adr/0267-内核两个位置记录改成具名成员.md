# ADR-0267 内核两个位置记录改成具名成员

## 状态

已采纳（内核的 `BindingValue` 与 `MiddlewareDescriptor` 已改，框架内的构造处跟着改；规范不变，RFC-0001「数据类型的形状」已经是这条规则）。

## 日期

2026-11-24

## 背景

- ADR-0142 定下「会演进或跨 Provider 边界的数据类型不用位置记录」，规则写进 RFC-0001，并改了内核、消息与宿主里的一批 `Stable` 数据类型。内核里漏了两个，都是 `Stable`，5.0.0 之后同一大版本内不能再破坏（ADR-0131）：
  - `BindingValue(string Name, string Type, string? Value, IReadOnlyDictionary<string, string> Properties)`：宿主解析出的资源绑定，经 `FeatureContext.GetBinding` / `FindBinding` 交给每个要连外部资源的 Provider，EF Core 与 SqlSugar 的配置回调也收它（`Maybe<BindingValue>`）。它跨 Provider 边界，也是会演进的：来源（目录还是配置）、挂载的根、轮换时刻都是加得上去的成员。
  - `MiddlewareDescriptor(Type Middleware, PipelineStage Stage, Placement Placement, string Owner)`：`PipelineBuilder.Describe()` 给出的管道描述。它已经在位置参数之外追加了 `Name`、`Before`、`After` 三个 `init` 成员（ADR-0142 背景里说的「在位置参数之外再追加」正是这种形状），构造与解构只覆盖前四项。
- 位置记录每加一个位置参数，构造与 `Deconstruct` 的签名都要变；不加位置参数、只追加 `init` 成员，解构又看不到新成员。两种都不是正式版之后还能接着用的形状。
- ADR-0266 刚把对象存储的 `BlobSignedUrl` 照同样的理由改了。

## 备选

1. **留到下一个大版本再改**：否决。两个类型现在都没有基线（`PublicAPI.Shipped.txt` 是空的），5.0.0 之前改不需要豁免；正式版之后要等 6.0。
2. **`Name`（绑定名）与 `Middleware`（中间件类型）经构造给出，其余走初始化器**：否决。ADR-0142 留给构造的是「构成身份的一两个必需成员」；绑定的四项与描述的四项都是一条记录里并列的事实，没有哪一项是它的身份（同名的绑定在两个来源里各有一条，同类型的中间件可以按名字登记多个实例）。与 `BlobSignedUrl`、`AuditEvent`、`MessageDelivery` 一样全部走初始化器，调用点每个值都带着成员名。
3. **`BindingValue.Properties` 不标 `required`、缺省为空字典**：否决。位置构造时它就是必给的，改成缺省等于顺手改了契约；缺省的空字典还得选一个比较器。「没有其余属性时给空字典」写在成员的文档里。
4. **`BindingValue.Value` 不标 `required`、缺省 `null`**：否决。没有主值是合法状态（只给凭据属性的绑定），但要构造方明说，不能是忘了写。
5. **初始化器里加校验（名字不得为空白等）**：这次不做。两个类型原先都不校验，值都由内核自己建出（`BindingResolver`、`PipelineBuilder`）；加校验是行为变化，要另定哪些值不合法。
6. **保留 `Deconstruct`**：否决。它正是签名随成员数变的那一半；仓库里没有任何解构处。

## 决策

1. `BindingValue` 改成初始化器形状：`Name`、`Type`、`Value`、`Properties` 都是 `required` 的 `init` 成员，没有位置构造与 `Deconstruct`。`Type` 来源未声明时仍是空字符串，`Value` 没有主值时仍是 `null`，`Properties` 没有其余属性时是空字典。`Property(key)` 与遮蔽主值的 `PrintMembers` 不变。
2. `MiddlewareDescriptor` 改成初始化器形状：`Middleware`、`Stage`、`Placement`、`Owner` 是 `required` 的 `init` 成员，`Name`、`Before`、`After` 照旧是可选的 `init` 成员，没有位置构造与 `Deconstruct`。
3. 以后给这两个类型加成员只加可选的初始化成员。
4. 框架内的构造处机械改写：内核 3 处（`BindingResolver` 两处、`PipelineBuilder` 一处），`MultiTenancy.Abstractions` 的 `TenantShardBinding`、`Persistence.EntityFrameworkCore` 与 `Persistence.SqlSugar` 的 `NamedBinding` 各 1 处，测试 18 处。没有解构处。`with` 的用法（`binding with { Value = … }`）不受影响。

## 理由

- 绑定是每个连外部资源的 Provider 都要读的类型，也是应用自己写 Provider、写测试时最常手工构造的内核类型；它的构造签名一变，破坏面是全部 Provider。
- 管道描述是诊断用的只读快照，使用者几乎只读不建；它要改是因为形状已经是半位置半初始化器，解构出来的四项不是全部。
- 两个都在 5.0.0 之前改，不需要豁免登记（ADR-0131）。

## 影响

- **公开 API 与迁移**（`PublicAPI.Unshipped.txt` 已同步；尚无基线，不需要 `CompatibilitySuppressions.xml`）：
  - `BindingValue` 的位置构造与 `Deconstruct` 删除，新增无参构造：`new BindingValue(name, type, value, properties)` 改成 `new BindingValue { Name = name, Type = type, Value = value, Properties = properties }`；位置解构 `var (name, type, value, properties) = binding` 改成读属性。按大写参数名传参的（`Name: …`）同样改成初始化器。
  - `MiddlewareDescriptor` 的位置构造与 `Deconstruct` 删除，新增无参构造：`new MiddlewareDescriptor(middleware, stage, placement, owner) { … }` 改成 `new MiddlewareDescriptor { Middleware = middleware, Stage = stage, Placement = placement, Owner = owner, … }`；位置解构改成读属性。应用通常只读 `PipelineBuilder.Describe()` 的结果，不受影响。
  - 二进制不兼容：按旧签名编译的程序集要重新编译。
- **行为不变**：解析出的绑定、管道描述的内容、`ToString()` 的输出（`BindingValue` 仍遮蔽 `Value`）与相等比较都与原先相同。
- **规范**：不用改。RFC-0001「数据类型的形状」已经是这条规则；RFC-0004 只写了 `Describe()` 的返回类型，RFC-0014 只列了 `BindingValue.Value` 是凭据，都不涉及形状。
- **内核、原语层与抽象包里其余的 `Stable` 位置记录**（这次不改，改不改待定）：
  - 属于 RFC-0001 留给位置记录的「封闭的小值」，建议不动：
    - `Primitives`：`TypedId<TTag, TValue>(TValue Value)`（规范点名）。
    - `Kernel`：`ResourceName(string Partition, string Service, string? Tenant, string Type, string Id)`（规范点名，XRN 的五段是文法定死的）。
    - `Security.Abstractions`：`GrantSubject(string Kind, string Id)`（主体的种类与标识，两段式的键）。
    - `ObjectStorage.Abstractions`：`BlobContentRange(long Offset, long Length, long TotalLength)`（HTTP `Content-Range` 的三个数）。
    - `Localization.Abstractions`：`LocalizedText(string Text, string Locale)`（译文与命中的区域）。
    - `Persistence.Abstractions`：`Ordering<T>(Expression<Func<T, object?>> KeySelector, bool Descending)`（排序键与方向）。
  - 会演进、建议在正式版之前照这里的方式改：
    - `Kernel`：`SecurityContext(Principal Principal, TenantContext? Tenant)`。每次调用都带着它，认证方与测试都会构造；委托（代表谁）、认证强度这类成员加得上去。若保留构造，`Principal` 是身份、`Tenant` 应改走初始化器。
    - `Kernel`：`TenantContext(string Id)`。已经是「构造只收身份、`DisplayName` 走初始化器」，只多一个单参数的 `Deconstruct`；改成非位置的构造就与 ADR-0142 的形状完全一致，调用点 `new TenantContext(id)` 不用改。
    - `Security.Abstractions`：`PermissionGrant(GrantSubject Subject, string Permission, string? TenantId)`。跨授予存储的 Provider 边界；过期时刻、授予来源、条件都是加得上去的成员。
    - `Security.Abstractions`：`AuthorizationRequirement(string Policy, ResourceName? Resource)`。`Policy` 是身份、`Resource` 可选，照 `AuthorizationRequest` 的改法即可，两参构造的调用点不用改。
  - `Preview` 的位置记录另有 25 个（`Kernel` 的 `PluginStatus`，`Security.Abstractions` 的条件模型 10 个与 `IpRegion`，`Caching.Abstractions` 4 个，`Workflow.Abstractions` 7 个，`Persistence.Abstractions` 的 `TableSchema`，`AI.Abstractions` 的 `KnowledgeTrim`）。它们在 `Preview` 期间可以带豁免修改，不急在正式版之前；ADR-0151 已经按同一规则改过一轮 `Preview` 数据类型，这些是之后新增或当时判定为小值的。
- **测试**：`BindingValue` 以初始化器构造、`with` 只换主值、打印时遮蔽主值、没有主值的绑定合法；`PipelineBuilder.Describe()` 给出每个成员（含名字与约束）、`with` 与相等；两个类型只有无参构造、没有 `Deconstruct`。
- **文档**：`plans/architecture/03-代码规范.md` 里的示意代码改成初始化器；文档站 `configuration/bindings` 的类型表里 `BindingValue(Name, Type, Value, Properties)` 的写法与更新日志待改。
