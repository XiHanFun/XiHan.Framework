# ADR-0297 cron 步长的上限与计划的文本形式

## 状态

已采纳（规范 RFC-0013 的 cron 第 3～5 条已修订、新增「计划的文本形式」一节，`scheduling/cron-expressions.json` 已改、新增 `scheduling/schedule-texts.json`，Go 一致性模块的规则已改并回放通过；`CronExpression` 的步长收紧到这一段能写的最大值，`JobSchedule` 的读法收紧到与写法相同、`FromCron` 只收 IANA 的时区名，公开面不变）。

## 日期

2026-11-25

## 背景

### cron 的步长

ADR-0286 把 cron 的文法逐条写进 RFC-0013 时，步长照 .NET 的现状写成「1 到 2147483647」：比段的跨度大的步长只取起点，`*/60` 写在分钟上合法、等于 `0`。当时否决了「步长的上限定成段的最大值」（ADR-0286 备选 10），理由是收紧会让已有的表达式失效；同时把「2147483647 来自 .NET 的 `int`」记进了「待定」：这个数与规则无关，换一种语言要特意去找一个 32 位整数的上限，别的实现（Go 的 `strconv.Atoi` 是 64 位）不照着做就会分歧。

常见的两个实现都不收比段的上限大的步长：

- Quartz 的 `CronExpression` 在解析步长时核对：秒与分大于 59、时大于 23、日大于 31、月大于 12、星期大于 7 都报 `Increment > …`；年份段不核对。
- cronie 的 `get_range` 读到步长后核对它不大于这一段的 `high`（分 59、时 23、日 31、月 12、星期 7）。

`*/60` 这样的写法多半是把「每 60 分钟」误写在分钟段上，它的实际含义是「每小时的第 0 分」；照收只是让这个误解悄悄生效。仓库所有者已拍板：步长限到这一段的最大值，与 Quartz、cronie 一致。

要定的细节有两处：

1. **星期的上限是 6 还是 7**。RFC-0013 第 4 条写的是「范围与步长在 0–7 里数，数完把 7 归到 0」：`1/2` 是 1、3、5、7。数的时候这一段的最大值是 7，`*/7` 是 0 与 7（都是周日），`1/7` 只有周一。以归一之后的 0–6 为准把上限定成 6，就得在数法（0–7）与上限（0–6）之间换一次口径，而且会拒掉 Quartz 与 cronie 都收的 `*/7`。
2. **年份段**。Quartz 不核对年份的步长，没有可以照搬的做法。可选的有「段的最大值」2099、「段的跨度」129 与「段的取值个数」130。

### 计划的文本形式

存储以文本持久化计划（`Scheduling.Database` 的触发器行，`JobSchedule.ToString()` 写、`JobSchedule.Parse` 读），RFC-0013 只给了 `every 00:10:00 x5`、`cron 0 0 9 * * MON-FRI tz=Asia/Shanghai` 几个例子（ADR-0277「没有做的」、ADR-0286 备选 17）。逐项读 .NET 的写法与读法、并用 Release 构建的真实实现跑过之后：

- **写法是确定的**：种类与它的部分；cron 有时区时接 ` tz=<ID>`；再依次接有值的 ` start=`、` end=`、` calendar=`。间隔是 `TimeSpan` 的 `c` 格式（`00:10:00`、`1.02:03:04.0050000`，不足一秒的部分正好七位、为 0 时不写），次数不带前导 0，cron 是 `CronExpression.Expression`（各段以一个空格连接，保留书写时的大小写），时刻换算成 UTC 后的 `O` 格式（`2026-10-23T10:30:00.0000000+00:00`）。
- **读法比写法宽得多**：
  - 分词是 `Split(' ', RemoveEmptyEntries | TrimEntries)`：结尾的空格与换行、连着的空格都照收；制表符不是分隔符，但 cron 自己认它，`cron 0\t3 * * *` 也读得出。
  - 间隔交给 `TimeSpan.TryParseExact(…, "c")`：`00:10`（十分钟）、`5`（五天）、`0:10:00`、`00:10:00.5`、`0.00:10:00`、`01.00:00:00` 都读得出。别的语言要照着做，就得把 .NET `c` 格式的这些读法逐个仿出来。
  - 次数用 `int.TryParse`，`x05` 照收。
  - 时刻用 `DateTimeOffset.TryParseExact(…, "O", AssumeUniversal)`：不带偏移的 `2026-10-23T10:30:00.0000000` 当作 UTC 读；反过来 `2026-10-23T10:30:00Z`（没有七位小数）读不出。这与规范里已有的时间戳文法（RFC-0003 规则 8，截止时间与消息信封 `time` 共用）不是同一条。
  - 选项从尾部逐个剥下：不论次序；重复时取最前面的一个（`manual calendar=a calendar=b` 读成 `a`）；`tz=` 跟在 `every`、`once`、`manual` 后面照收、然后悄悄丢掉。
- **有写得出、读不回的**：`FromCron` 收 Windows 的时区 ID（`TimeZoneInfo.TryFindSystemTimeZoneById` 两种都认），`China Standard Time` 写出来是 `tz=China Standard Time`，分词时被空格拆开，这段文本再也读不出——存进数据库的这一行之后每次被读到都让那个存储操作失败。`UTC+12` 这类不带空格的 Windows ID 在 Windows 上读得回来，在别的系统与别的语言里读不出。日历名经 `with { Calendar = … }` 可以是任意文本，不合作业名文法的（带空格的）同样读不回；但日历按名登记时只收作业名文法（`AddJobCalendar`），调度器拒绝未登记的日历（`SCHEDULING_VALIDATION_001`），这样的计划进不了存储。
- **时区依赖本机的时区库**：读入时按 ID 查 `TimeZoneInfo`，查不到就读不出。

仓库所有者已拍板：文法写全进 RFC-0013，分隔只认确定的那一种（与 ADR-0286 对 cron 分段同一原则）、别的空白不合法，收紧 .NET 的分词；已经持久化在存储里、框架自己写出的文本必须仍然读得回来，读不回来的写法列出并给迁移办法；时区名写明照 IANA tz 数据库，并写明某个时区本机没有时的处置。

## 备选

### cron 的步长

1. **步长的上限是这一段的跨度（最大值减最小值）**：否决。日的跨度是 30、月是 11，会拒掉 Quartz 与 cronie 都收的 `*/31`、`*/12`。
2. **星期的上限是 6**：否决，见背景第 1 条。
3. **年份的上限是 129 或 130**（年份段的跨度或取值个数，使「上限」都落在「再大就只剩起点」的位置）：否决。别的六段用的是这一段能写的最大值，日与月的上限本来就比跨度大一（`*/31` 只有 1 日，`*/12` 只有 1 月），年份另用一个算法就要多写一条规则。130 到 2099 的步长只取起点，与 `*/31` 写在日上只有 1 日是同一种情形，不会读出歧义。
4. **年份段不设上限**（照 Quartz）：否决。那样年份段又回到一个与类型有关的数（.NET 的 `int`、Go 的 `int`），正是这次要去掉的。
5. **只拒绝明显的误写（`*/60` 之类），`a/n` 与 `a-b/n` 照旧**：否决。三种写法的步长是同一个东西，分开处理没有道理；Quartz 与 cronie 对三种写法一样核对。
6. **步长超过上限时按上限取**（`*/60` 当成 `*/59`）：否决。那是静默改写，`*/59` 是 0 与 59，与 `*/60` 以前的含义（只有 0）也不同。

### 计划的文本形式

7. **读法照收 .NET 现在收的全部写法，只把它们写进规范**：否决。`TimeSpan` 的 `c` 格式的读法、`TrimEntries` 裁掉的 Unicode 空白、从尾部剥选项时「重复取最前」都是 .NET 的实现细节，写成规则又长又容易漏，ADR-0286 在 cron 上已经否决过同样的做法。
8. **间隔的读法放宽一些**（小数一到七位、天数可带前导 0，像时刻那样）：否决。这段文本是存储格式，由框架写出、框架读回，不是给人手写的配置；读法与写法相同时一个值只有一种写法，规则一句话写得完。时刻另当别论，见备选 9。
9. **时刻的读法与写法相同**（只收 `O` 格式、`+00:00`、七位小数）：否决。规范里已经有一条时间戳的读法（RFC-0003 规则 8），截止时间与消息信封的 `time` 都用它，.NET 与 Go 各有一份实现（`TimestampText.TryParse`、`rules.ParseDeadline`）；再造一条只收七位小数的就有了两条时间戳文法。规则 8 收框架写出的全部时刻（`+00:00`、七位小数），读不出的只有不带偏移的写法，而框架从不写它。
10. **选项照旧不论次序**：否决。固定次序时文法是一个线性的序列，重复、次序不对与不认得的选项都落在同一条判定里（读完之后还有剩下的部分）；不论次序就要另写「重复时怎样」的规则。框架写出的次序本来就固定。
11. **`tz=` 跟在别的种类后面照收、丢掉**：否决。那是静默兜底，读出的计划与文本说的不一样。
12. **时区名照收 `TimeZoneInfo` 认的一切**（含 Windows 的时区 ID）：否决。带空格的 Windows ID 根本放不进按空格分的文本；不带空格的（`UTC+12`）只有 Windows 与带 ICU 的 .NET 认得，别的语言读不出。规范写明是 IANA 的名字，.NET 用 `TimeZoneInfo.HasIanaId` 核对。
13. **时区名在本机查不到时照样读出、到推算下一次时再报错**（触发器进 `Error`）：这次不做。读入时不查，存储读得出、触发器能列出来，比整段文本不合法友好；但推算、日历与引擎里取时区的几处都要改成可失败的，触发器的状态机也要多一条路径，不在这次的范围。现在写明为文本不合法，与改动之前 .NET 的行为相同，记在「没有解决的」。
14. **给日历名的 `init` 加核对**，让 `JobSchedule` 永远写不出读不回的日历名：否决。这样的计划进不了存储（背景），在构造时抛出反而把调度器给出的 `SCHEDULING_VALIDATION_001` 换成了异常，是又一处 `Stable` 的行为变化而没有收益。
15. **时区名的文法放宽到「不含空格的任意文本」**：否决。别的空白、`/` 开头结尾与连着的 `/` 都要另说；IANA 的名字只用 ASCII 字母、数字与 `_`、`+`、`-`，按它写文法最短。

## 决策

### cron 的步长（RFC-0013 cron 第 3～5 条）

1. **步长 n 是 1 到这一段能写的最大值**：秒、分 59，时 23，日 31，月 12，星期 7，年 2099。`*/n`、`a/n`、`a-b/n` 都核对；超过即表达式不合法，`CronExpression.TryParse` 返回 `false`、`Parse` 抛出 `ArgumentException`（与别的不合法一样）。
2. **星期的上限是 7**：数的时候这一段的最大值是 7（背景第 1 条），与 Quartz、cronie 一致。
3. **年份的上限是 2099**，与别的六段同一条规则（备选 3）。
4. **数字的写法不变**：ASCII 十进制数字，可以有前导 0（`*/059` 是 59，`*/060` 是 60、不合法）；比 2147483647 还大的数字串同样不合法。
5. `CronExpression` 解析失败的原因改为 `step '<文本>' in field '<段>' must be 1-<上限>`（以前是 `… must be a positive number`），步长为 0 与超过上限用同一句。展开时去掉了 ADR-0286 为防加法溢出加的提前退出：步长不超过 2099，起点加步长不会溢出。

### 计划的文本形式（RFC-0013「计划的文本形式」）

6. **分隔**：各部分之间正好一个空格，开头与结尾没有空格；连着的空格、制表符、换行、不换行空格等别的空白出现在任何位置都不合法。cron 的表达式在这里各段之间同样只是一个空格。
7. **种类与各自的部分**：`manual`；`every <间隔>`、`every <间隔> x<次数>`；`cron <表达式>`；`once <时刻>`。种类、选项名与 `x` 区分大小写。
8. **间隔与次数的读法与写法相同**：间隔 `[d.]hh:mm:ss[.fffffff]`（天数不带前导 0、不足一天不写，时 00–23、分秒 00–59 各两位，不足一秒的部分正好七位、为 0 时不写），大于 0、以 100 纳秒计不超过 9223372036854775807；次数 1 到 2147483647，不带前导 0。两个上限是 .NET `TimeSpan` 与 `int` 能写出的最大值，存储里可能已经有，所以照收（与 cron 步长的处境不同：这里没有「段」可以给出与类型无关的上限）。
9. **时刻按 RFC-0003 规则 8 读**，写出照旧（UTC、七位小数、`+00:00`）。
10. **选项**：`tz=`（只跟在 cron 的表达式后面）、`start=`、`end=`、`calendar=`，按这个次序，每个至多一次；不认得的、次序不对、重复与 `=` 之后为空的都不合法。日历名是作业名的文法。
11. **时区名是 IANA tz 数据库的名字**，文法 `^[A-Za-z0-9_+-]+(/[A-Za-z0-9_+-]+)*$`；读入时在本机的时区库里查，查不到（或查到的不是 IANA 的名字）整段文本不合法。`JobSchedule.FromCron` 做同样的核对，不合格时抛出 `ArgumentException`，不再写出读不回的文本。
12. **.NET 的实现**：`JobSchedule.TryParse` 改为按单个空格切分、逐部分按上面的文法读，间隔与次数手写解析，时刻交给原语 `TimestampText.TryParse`，日历名用 `JobName.IsValid`，时区先核文法、再 `TimeZoneInfo.TryFindSystemTimeZoneById` 并要求 `HasIanaId`。`ToString` 不变，所以已有的指纹（`CodeFingerprint` 含计划的文本）与「计划改了没有」的比较不受影响。

## 理由

- 上限由段自己的定义给出，不再依赖某种语言的整数宽度；规则一句话写得完，别的语言照着写不会分歧。
- 与最常见的两个实现一致：从 Quartz 或 crontab 搬过来的表达式，在这里合法与否与在原处相同。
- 比段的上限大的步长只可能是误写，拒绝它让写错的人在登记时就知道，而不是等到作业每小时才跑一次。
- 计划文本是框架写、框架读的存储格式，读法与写法相同最容易说清，也最容易让别的语言读出同样的结果；收紧的读法拒绝的都是框架从不写出的形状，存储里已有的文本不受影响（测试把 `JobSchedule` 能写出的每种形式乘上三个选项的全部组合逐一核对过）。
- 时间戳只留一条文法：规则 8 已经由向量盯住、两种语言各有实现，计划文本直接用它。
- Go 一致性模块按正文独立实现之后一次回放通过全部用例，说明正文加向量已经足以让另一种语言写出一致的实现。

## 影响

- **公开 API**：签名不变。行为收紧的都是 `Stable`：`CronExpression`（步长）；`JobSchedule.Parse` / `TryParse`（读法）、`FromCron`（时区名），`CronCalendar` 随 `CronExpression` 收紧。`JobSchedule.TimeZoneId` 与 `FromCron` 的 XML 文档改为「IANA tz 数据库的名字」。
- **升级须知**：
  - **cron 步长比这一段的最大值大的表达式不再合法**：`*/60`、`*/100` 写在秒或分上，`*/24` 写在时上，`*/32` 写在日上，`*/13` 写在月上，`*/8` 写在星期上，`*/2100` 写在年份上，以及同样步长的 `a/n`、`a-b/n`。
    - 改写方法：这样的步长以前只取起点，换成起点本身即可，含义不变——`*/n` 换成这一段的最小值（秒、分、时、星期是 `0`，日与月是 `1`，年份是 `1970`），`a/n` 与 `a-b/n` 换成 `a`。例：`*/60 * * * *` → `0 * * * *`，`0 0 5/100 * * *` → `0 0 5 * * *`。
    - 代码里登记的计划（`JobSchedule.FromCron`、`AddJob`、`CronCalendar`）：启动时抛出 `ArgumentException`，按上一条改写。
    - `Scheduling.Database` 里已经持久化的计划：触发器行的 `Schedule` 列读回时经 `JobSchedule.Parse`，表达式不合法会让读到这一行的存储操作失败（抢占、列出触发器都会读到它）。升级之前在旧版本上用 `IJobScheduler.ScheduleAsync` 把这些作业的计划按上一条改写，或直接改 `Schedule` 列里 `cron ` 之后的表达式；找出它们可以查 `Schedule` 以 `cron ` 开头且含 `/` 的行，逐条核对步长。内存存储不持久化，不受影响。
  - **`JobSchedule.FromCron` 只收 IANA 的时区名**：`China Standard Time` 这类 Windows 的时区 ID（含 `UTC+12` 这样不带空格的）、不合文法的名字抛出 `ArgumentException`。改用对应的 IANA 名（`Asia/Shanghai`、`Etc/GMT-12`；对照见 Unicode CLDR 的 `windowsZones.xml`，.NET 里可用 `TimeZoneInfo.TryConvertWindowsIdToIanaId`）。
  - **`JobSchedule.Parse` / `TryParse` 不再收框架从不写出的形状**：结尾或连着的空格、换行等别的空白、以制表符分隔的 cron；`00:10`、`5`、`0:10:00`、`00:10:00.5` 这类间隔；`x05` 这类次数；不带偏移的时刻；次序不对或重复的选项；跟在 cron 以外的种类后面的 `tz=`；不合作业名文法的日历名；Windows 的时区 ID。框架写出的文本都不是这些形状，存储里已有的不受影响；自己拼计划文本的地方改用 `JobSchedule` 的工厂方法加 `ToString()`，或照 RFC-0013「计划的文本形式」写。
  - **写得出、读不回的写法**（改动之前就读不回，现在列出）：
    - 带空格的 Windows 时区 ID（`tz=China Standard Time`）：以前 `FromCron` 收、`ToString` 写得出，存进数据库后这一行一直读不出。现在 `FromCron` 就拒绝。已经存进去的行要直接改 `Schedule` 列，把 `tz=` 之后的部分换成 IANA 名（这样的行在旧版本上也读不出，无法经 `ScheduleAsync` 改）；查 `Schedule` 以 `cron ` 开头、`tz=` 之后还有空格且下一部分不是 `start=`、`end=`、`calendar=` 的行。
    - 不带空格的 Windows 时区 ID（`tz=UTC+12`）：以前在 Windows 上读得回来，现在读不出。升级之前在旧版本上用 `ScheduleAsync` 把时区换成 IANA 名，或直接改 `Schedule` 列。
    - 不合作业名文法的日历名：只能经 `with { Calendar = … }` 写出，调度器拒绝未登记的日历，进不了存储，不需要迁移。
  - **时区依赖本机的时区库**（行为与以前相同，现在写进规范）：存储里的 `tz=Asia/Shanghai` 在缺这个时区的机器上读不出，读到这一行的存储操作失败。Linux 容器要装 `tzdata`（以及 .NET 识别 IANA 名所需的 ICU 或时区文件）。
- **规范**（规范仓库已提交，指针待更新）：
  - RFC-0013 cron 第 3 条步长的范围修订，第 4、5 条写明星期与年份的上限，是 MAJOR（`v1.0.0` 之前允许）。`cron-expressions.json`：原先合法的 4 条大步长（`*/100`、`*/60`、`0 0 */2147483647 * * *`、`5/2147483647 * * * *`）挪到 `invalid`，另补各段上限两侧的用例（合法 10 条、拒绝 12 条）；`*/2147483648` 那一条改名为「步长超出 32 位整数」。
  - RFC-0013 新增「计划的文本形式」：文法本身是写明（MINOR），读法比 .NET 以前收的窄、时区名只收 IANA 是改参考实现已有的行为，记 MAJOR（`v1.0.0` 之前允许）。「作业与触发器」里计划一条的时区改为 IANA 名、文本往返指向新的一节。新增向量 `scheduling/schedule-texts.json`（合法 30 条、拒绝 74 条，时区只用不依赖时区库的 `UTC`），进 `scheduling` 档。
- **Go 一致性模块**：`rules.ParseCron` 的步长上限由 `math.MaxInt32` 改为段的最大值；新增 `rules/jobschedule.go`（`JobSchedule`、`ParseJobSchedule`、`FormatJobSchedule`、`ParseJobInterval`、`FormatJobInterval`、`IsTimeZoneName`、`IsKnownTimeZone`）与 `conformance.JobScheduleTexts()`，导出面只增不改。
- **六个 SDK**：不受影响，都不认领 `scheduling` 档；Go SDK 升模块版本时多出的导出不用改。
- **测试**：
  - cron：`CronExpressionTests` 新增各段步长正好是上限的合法用例与比上限大一的拒绝用例，失败原因的用例跟着新的文本改；`CronExpressionVectorTests` 的覆盖断言改为「每一段都有步长正好是上限的合法用例与比上限多一的拒绝用例」。
  - 计划文本：新增 `JobScheduleTextVectorTests`（回放 `schedule-texts.json`，并核对写回的文本读回再写出不变、四种种类与各上限都有用例、写回有变化的只是时刻）；`JobScheduleTests` 新增「写法能写出的每种形式乘上三个选项的全部组合，按新的读法全部读回」、以前照收的 13 种形状被拒、`FromCron` 拒绝 Windows 的时区 ID 与不合文法的名字。
- **文档**：文档站 `scheduling/jobs` 与 `packages/scheduling-abstractions` 里「步长是 1 到 2147483647」一句、时区「IANA 或 Windows」的说法、计划文本的写法，更新日志待改。

## 没有解决的

- 存储里有一行计划读不出（表达式不合法、时区本机没有）时，读到它的存储操作整个失败：`AcquireDueAsync` 读到这一行时这个节点每个周期都抢占失败，别的到期触发器也跟着停下。这是改动之前就有的行为，这次的收紧让它更容易遇到（cron 步长的升级须知）；按行隔离（读不出的触发器记为 `Error`、跳过）要改存储与引擎，没有做（备选 13）。
