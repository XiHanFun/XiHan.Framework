# ADR-0250 时刻列的参数转换可以重复

## 状态

已采纳（只改 SqlSugar Provider 的实现；公开 API 与规范不变）。

## 日期

2026-11-21

## 背景

- `DateTimeOffsetConverter` 是约定登记到每个 `DateTimeOffset` 列上的参数转换器（ADR-0037）。写入时把时刻换成 UTC 的 `DateTime`，收到别的值一律写成数据库空值。
- 条件右边的变量是嵌套的成员访问时，SqlSugar 解析成员值的路径会先调用一次转换器，取出它写出的值；再按列追加参数时又调用一次。
  - 典型写法是方法参数与循环变量各在一层闭包：`foreach (var id in ids) query.Where(r => r.Id == id && r.At < cutoff)` 里的 `cutoff`。
  - 第二次收到的是第一次写出的 UTC `DateTime`，转换器不认，写成空值。条件变成与 NULL 比较，静默查不到任何行，也不报错。
  - 变量与表达式在同一层闭包时走另一条路径，不受影响，所以多数查询没有暴露。
- 一个应用的保留清理作业因此出过两个问题：按创建时间取过期的系统通知时一条都取不到；核对附件是否还被留存消息引用时以为没有，删掉了还在用的文件。

复现：新增的 `DateTimeOffsetCaptureTests` 与转换器的三个用例，修复之前都失败。

## 备选

1. **要求应用把变量先复制到同一层闭包**：否决。写法上看不出差别，出了错也只是静默查不到，靠约定守不住。
2. **在表达式访问器里把嵌套的成员访问预先求值成常量**：否决。要改写所有经过 `Filtered` 的表达式，SqlSugar 别的入口（`Updateable`、`Deleteable` 的条件）照样漏掉。
3. **转换器接受自己写出的值**：采纳。重复转换得到同一个时刻，与 SqlSugar 走哪条路径无关。

## 决策

1. 写入参数时，`DateTimeOffset` 换成 UTC 的 `DateTime`。`DateTime` 按 C# 隐式转换成 `DateTimeOffset` 的规则解释：Utc 原样，Local 与 Unspecified 按本地时间。所以第二次转换收到 Utc 的 `DateTime`，写出的还是同一个时刻。
2. `null` 与 `DBNull` 照旧写成数据库空值。
3. 别的类型抛 `NotSupportedException`，不再当成空值写入。
4. SQL Server 的转换器只改参数类型（ADR-0231），随之生效。

## 理由

- 漏洞的后果是静默的错误结果。让转换可以重复，修的是转换器自己的前提，不依赖 SqlSugar 内部调用几次。
- 未知类型改为抛出，同类问题会当场暴露，不会变成查不到。

## 影响

- 线上行为：嵌套闭包里的时刻变量照常作为参数写入，以前查不到、删不掉、核对落空的条件恢复正确。传 `DateTime` 给时刻列的条件按隐式转换的时刻比较。传别的类型以前静默写成 NULL，现在抛异常。
- 公开 API 不变，规范不变。
- 测试：新增 `DateTimeOffsetCaptureTests`（SQLite，两层闭包里比较非空与可空的时刻列）。`DateTimeOffsetConverterTests` 增加三个用例：重复转换、`DateTime` 的三种 Kind、未知类型抛出。
