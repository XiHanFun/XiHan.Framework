# ADR-0303 工作流表达式的大小写映射、Unicode 数据的依据与读数字的工作量

## 状态

已采纳（各项在规范与本仓库实现，见各节的「影响」）。

## 日期

2026-11-25

## 背景

ADR-0296 把关键字的折叠定成逐个码位的 Unicode 简单小写映射、给一次求值加了工作量上限之后，还剩三处没有收口，所有者拍板全部要做：

1. 表达式的 `upper` / `lower` 仍按 ADR-0287 决策 12 把 U+0130 与 U+0131 留作「实现自定」，.NET 照旧交给不变文化（它不转换这两个字符），与关键字的折叠不是同一条规则。
2. 关键字的折叠与 `upper` / `lower` 都说「映射取自实现所带的 Unicode 数据」，没有说这样写为什么站得住、向量该收哪些字符。
3. 工作量里数字的读取量是 0。变量里原文几百万位的 JSON 数字每读一次都要把原文重新扫描一遍（参考实现上约 7 毫秒），计量却是零，长度以内重复读几百次就是几秒的 CPU。

三项各占一节；提交按项拆开，规范与本仓库各两个（前两节同一个提交，第三节一个），次序同本文的节。

## 一、`upper` / `lower` 按简单大小写映射

### 背景

RFC-0021「内置函数」写的是「逐个码位按 Unicode 的简单大小写映射转换……U+0130 与 U+0131 怎样转换实现自定（.NET 的不变文化不转换它们）」。.NET 的实现是 `string.ToUpperInvariant()` / `ToLowerInvariant()`。把全部码位逐个对过（.NET 10 在 Windows 11 上走 ICU，Unicode 15.1；Go 1.27 的 `unicode` 带 17.0）：

| 映射 | 不变文化（以前的 `upper` / `lower`） | 简单映射（Go 的 `unicode.ToUpper` / `ToLower`） |
| --- | --- | --- |
| `İ`（U+0130）的小写 | 不变 | `i` |
| `ı`（U+0131）的大写 | 不变 | `I` |
| 基本多文种平面以外的字母 | 整串转换时按码位转换 | 按码位转换 |
| Unicode 16.0 与 17.0 新收录的字符，以及因此才有了映射的 `ɤ`（U+0264）、`ƛ`（U+019B） | 不变（ICU 的数据是 15.1） | 转换 |
| 其余码位 | 相同 | 相同 |

与 ADR-0296 对关键字的观察一样：两边只差这两个带点的 i 与各自 Unicode 数据的版本。整串的不变文化转换已经按码位处理平面以外的字母（`char.ToLowerInvariant` 逐个码元才会漏掉它们），这次不受影响。

### 备选

1. **维持实现自定**：否决。同一份流程定义里的 `upper(x)` 在不同语言的引擎上结果不同，正是 ADR-0287 要消除的那一类；关键字的折叠已经定成简单映射，表达式另留一个口子更难解释。
2. **照不变文化写进正文**（两个带点的 i 不转换）：否决，理由同 ADR-0296 第三节备选 1——那是 .NET 的特例，别的语言要复现只能抄 .NET 的表。
3. **完全映射**（`upper('ß')` 是 `SS`）：否决。结果的长度会变，`len(upper(x)) == len(x)` 不再成立；Go、Java、.NET 的现成简单映射都要换成自带的表。所有者的要求也是 `ß` 的大写保持 `ß`。
4. **`upper` 与 `lower` 各写一份**：否决。关键字的折叠就是 `lower` 再把字段分隔符换成空格，两处共用一份映射，以后改一处不会漏另一处。

### 决策

1. RFC-0021「内置函数」的 `upper(x)`、`lower(x)`：逐个码位取 UnicodeData.txt 的 Simple_Uppercase_Mapping / Simple_Lowercase_Mapping，没有映射的码位不变，不做 SpecialCasing 的完全映射，不随区域、不看上下文，与「关键字的小写」是同一份映射。正文写出例子：`lower('İ')` 是 `i`、`upper('ı')` 是 `I`、`upper('i')` 是 `I`，`ß`、`ŉ`、`ﬀ` 的大写不变，`lower('ẞ')` 是 `ß`，`upper('ſ')` 是 `S`，`ǅ` 的大写是 `Ǆ`，平面以外的字母按整个码位转换；转换前后长度相同。
2. .NET：新增内部的 `WorkflowCaseMapping`（`ToLower`、`ToUpper`）。整串先交给不变文化转换——成批转换比逐个字符快一个数量级，`upper` 读几百万个码元时这一点要紧——原文里没有两个带点的 i、也没有代理项时就是结果；否则逐个修正：U+0130 的小写写 `i`、U+0131 的大写写 `I`，代理对经 `Rune.ToUpperInvariant` / `ToLowerInvariant` 按整个码位转换（映射万一跨了平面就抛出，不悄悄写坏），孤立的代理项原样保留。`upper` / `lower` 与 `WorkflowKeyword.Fold` 都经它，`Fold` 只在它之后把分隔符换成空格。
3. Go 一致性模块：新增 `LowerWorkflowText`、`UpperWorkflowText`（`unicode.ToLower` / `ToUpper` 就是这两个字段），`FoldWorkflowKeyword` 改成在 `LowerWorkflowText` 之后换分隔符；新增测试按它们回放实参是字面量的 `upper` / `lower` 用例（Go 模块不另实现求值器，ADR-0287 备选 10，这一类不必求值也能核对），并逐个码位核对大写映射同样不改变 UTF-16 的长度。
4. 向量：`expression-functions.json` 补 16 条：`İ` 与 `ı` 两个方向、`upper('İi')` 与 `lower('ıI')`（不随土耳其语）、`ẞ`、`ſ`、`ǅ` 的两个方向、开尔文符号、没有简单映射的 `ŉ` 与 `ﬀ`、德塞莱特字母两个方向、切罗基字母两个方向、平面以外不变的字符与全角、汉字、阿拉伯-印度数字、`len(upper('𐐨'))` 是 2。期望值由 .NET 算出，Go 按自己的映射回放同样通过。

### 影响

- 公开 API：没有签名变化。`upper` / `lower` 的结果只在含 `İ`（`lower`）或 `ı`（`upper`）的文本上不同：以前原样留下，现在是 `i` / `I`。
- 行为（升级须知）：拿 `upper` / `lower` 的结果比较、拼进关键字或写进变量的流程，文本里有土耳其语的 `İ`、`ı` 时结果变了；要保留原样的在流程之外处理。
- 规范：RFC-0021「内置函数」一行、状态行与「一致性」（改了已写明的「实现自定」，MAJOR，`v1.0.0` 之前允许）；`expression-functions.json`；`rules/workflow.go`、`rules/workflow_test.go`；`conformance/README.md`。
- 测试：`ExpressionFunctionVectorTests` 回放新用例并核对向量里有两个带点的 i、平面以外的字母与没有简单映射的 `ß`；新增 `WorkflowCaseMappingTests`（逐个码位不改变长度、成批转换与逐个码位转换的结果相同、两个带点的 i、平面以外的字母、没有简单映射的字符、孤立的代理项、关键字的折叠就是小写映射再换分隔符）。`WorkflowKeywordVectorTests` 原有的用例照旧通过。
- 六个 SDK：不受影响（不认领 `workflow` 档）。

## 二、Unicode 数据的依据

### 背景

规范不钉 Unicode 的版本，关键字的折叠与 `upper` / `lower` 都以实现所带的数据为准：.NET 用平台的 ICU（Windows 11 上是 15.1），Go 用工具链自带的表（1.27 是 17.0），别的语言各有各的版本。这样写要讲清两件事：版本不同的实现在哪些字符上会不同，向量该收哪些字符才不会因为某个实现升级了 Unicode 数据而失败。

### 备选

1. **钉一个 Unicode 版本、实现自带映射表**：否决，ADR-0296 第三节备选 5 否决过：一千五百个映射的表要随 Unicode 维护，换来的只是新近收录的几十个字符一致。
2. **照所有者的原话写「稳定性政策保证已分配字符的大小写映射不变」**：收窄成准确的说法。Unicode 字符编码稳定性政策里与此相关的是 Case Pair Stability：两个已分配的字符一旦互为大小写就一直是，两个已分配而不成对的字符以后也不会成对。它并不保证已有字符不多出映射：新收录了与它成对的字符时，已有字符会多出映射——Unicode 8.0 收录切罗基小写字母之后原有的大写字母才有小写映射，16.0、17.0 收录 `Ɤ`（U+A7CB）、`Ƛ`（U+A7DC）之后原有的 `ɤ`、`ƛ` 才有大写映射（第一节的表里 Go 与 .NET 的出入正有这两个）。正文照准确的说法写，结论不变：已有的映射不随版本改变，差别只在新收录的字符与它们的配对。
3. **向量只收 Unicode 3.2 以前的字符**：否决，太窄。切罗基小写（8.0）与阿德拉姆字母（9.0）是 ADR-0296 有意收的平面以内、以外的例子；照 ADR-0296 的取法收 9.0 及更早就已分配、映射之后没有变过的字符。

### 决策

1. RFC-0021「关键字的小写」写明：结果以实现所带的 Unicode 数据为准，规范不钉版本；依据是 Case Pair Stability，版本之间的差别只在新收录的字符与因此才多出映射的已有字符，这些字符怎样转换实现自定；向量只用早已分配的字符——9.0 及更早就已分配、映射之后没有变过的。「内置函数」的 `upper` / `lower` 一行写明同一份映射、同一条依据。「一致性」的「向量不收的」改成「新近收录的字符与因此才有了映射的已有字符」，去掉已经定下的 U+0130 与 U+0131。
2. 核对：`keyword-matching.json` 与 `expression-functions.json` 里全部 65 个非 ASCII 字符逐个对过——Unicode 3.2 以后才分配的只有 `ẞ`（5.1）、切罗基小写字母（8.0）、阿德拉姆字母（9.0）与 `😀`（6.1，没有大小写）；Go 的 17.0 与 .NET 的 15.1 在这 65 个字符上的大小写映射全部相同；没有格鲁吉亚字母（11.0 才有大写映射）、`ɤ`、`ƛ` 这类后来才多出映射的已有字符。

### 影响

- 只改正文（把以前只说「映射取自实现所带的数据」的地方写明依据与向量的取字，MINOR），不改任何期望值；与第一节同一个提交。

## 理由

- 第一节把表达式里最后一处「实现自定」的大小写收成与关键字相同的规则：同一个平台上同一段文本经 `lower` 与经关键字的折叠得出同一个结果，别的语言用现成的简单映射就能复现。
- 第二节不靠钉版本取得一致：已有字符的映射本来就不变，规范只需说清差别会落在哪里，并让向量避开那里。
