# ADR-0251 协议适配器跟随操作登记表

## 状态

已采纳（规范 RFC-0011、`protocol/http.md`、`protocol/mcp.md`、`plugin/invocation.md` §1、`plugin/lifecycle.md` 同步修订）。

## 日期

2026-11-23

## 背景

- 插件宿主可以在运行期加载与卸载插件（ADR-0080、ADR-0085）：代理操作经 `OperationRegistry.AddRange` 登记、经 `RemoveOwnedBy` 撤回，内核调用器按操作 ID 查找，随即生效。
- 协议适配器却只在启动时读一次登记表：
  - `MapXiHanOperations()` 在映射时遍历登记表，逐个 `MapMethods`。此后登记的操作没有路由，只能经 `IOperationInvoker` 调用；撤回的操作路由还在，答复 `KERNEL_NOTFOUND_001`。
  - OpenAPI 文档第一次请求时生成，之后一直用缓存；分组只能写在 `OpenApiOptions.Groups` 里，每组的文档地址在映射时逐个发布。
  - MCP 服务端建立时就建好 tool 表，`tools/list` 与 `tools/call` 都查这份快照。
- 结果是运行期加载的插件对外不可用，应用要做「在管理界面装插件」只能重启宿主。重启又会把插件的登记冲突变成启动失败：配置阶段登记的冲突按规范是启动失败。
- 一个应用（BasicApp）准备做插件管理：平台在界面里上传、授权、启停插件，多实例各自对齐。它需要插件操作加载即可调用、卸载即消失，还要给每个插件单独一份接口文档。

## 备选

1. **启停要重启宿主**：否决。把运行期加载退化成配置阶段发现，插件冲突会让宿主起不来，管理界面的操作也要等一次重启。
2. **应用另开一个通用入口**（如 `POST /plugins/{id}/{operation}`）按操作 ID 转给调用器：否决。两套地址、两份文档，路由、Schema 与 OpenAPI 都要另做一遍，违背一份契约。
3. **协议适配器跟随登记表**：采纳。登记表给出变更通知，适配器据此重建发布的东西；冲突在登记时整组拒绝，和权限码、重名的处理一样。

## 决策

1. 内核登记表：
   1. `OperationRegistry.GetChangeToken()` 返回 `IChangeToken`。登记表的内容每变一次就触发一次：`AddRange` 写入了操作或权限码，`RemoveOwnedBy` 撤回了操作或权限码。登记失败、空组、没登记过的归属都不触发。
   2. 令牌在锁外触发，回调里可以读登记表，也可以再登记。触发之后再取得到的是新令牌。
   3. `OperationRegistry.EnforceAdditions(check)` 挂整组的核对，签名是 `check(已登记的, 新增的)`。挂上时以（空、已登记的全部）核对一次并返回结果；此后每次 `AddRange` 在写入之前，以（当时已登记的、这一组）核对。不通过即整组不登记、已写进的权限码撤回，返回核对给出的错误。逐项的 `Enforce` 看不到同一组里的其他项，路由与 tool 名的冲突不能用它。
2. HTTP 路由：
   1. `MapXiHanOperations()` 往路由表里加一个 `EndpointDataSource`。端点集合从登记表按需建出，变更令牌就是登记表的令牌，登记表一变，ASP.NET Core 的路由重新读端点。
   2. 返回值是这份数据源的约定构建器：加在上面的约定与收尾约定记下来，作用于每次建出的每个操作端点，此后出现的也一样（ADR-0144 的语义不变）。
   3. 映射时就建一次端点：已登记的操作推导出同一条路由，照旧在映射时抛出 `PROTOCOLS_CONFLICT_002`。
   4. 映射时同时挂上路由的整组核对：此后登记的操作与已登记的或同一组里的推导出同一条路由，整组被拒，返回同一错误码，已有的路由不变。
   5. 撤回的操作没有路由，请求按宿主对未匹配地址的处理答复，与从没有过这个操作一样。已经在执行的请求照常完成。
3. OpenAPI：
   1. 文档缓存在登记表或任一分组来源的令牌触发时整体换新，下一次请求重新生成。正在生成的那份写进旧缓存，随旧缓存丢掉。
   2. 新增 `IOpenApiGroupSource`（当前的分组与变更令牌），应用在容器里登记，给运行期才有的归属分组。
   3. 选项里的分组在前，各来源的按登记顺序在后，合在一起按原有规则核对：组名唯一且不是 `all`，一个归属只属于一个组。不合规则是应用的编程错误，生成时抛 `ArgumentException`。
   4. 分组文档的地址改为一条带参数的路由 `<pattern 去掉 .json>/{group}.json`，按请求时的分组答复，不是当时的组名为 404。
   5. `GetXiHanOpenApiDocuments` 仍是调用时的快照：此后来源新增的分组不会补进已经登记的文档界面，界面里的全量文档照样有它们。
4. MCP：
   1. tool 表在登记表的令牌触发后重建，`tools/list` 与 `tools/call` 用处理这条消息时的那一份。
   2. 服务端建立时，已登记的操作 tool 名不合法或重复照旧启动失败（`PROTOCOLS_VALIDATION_004` / `PROTOCOLS_CONFLICT_001`）。同时挂上 tool 名的整组核对：此后登记的不合法、与已有的或同一组里的同名，整组被拒，返回同一错误码。
   3. 不推送 `notifications/tools/list_changed`，`listChanged` 仍为 `false`。Streamable HTTP 传输不开 SSE 流、不建会话，没有推送的通道；客户端重新 `tools/list` 即可看到变化。
5. 不在范围：
   1. gRPC 方法表与 AI 工具目录照旧在启动时建成，此后登记的代理操作不是 gRPC 方法、也不是 AI 工具。gRPC 的服务描述（`.proto`）与反射服务都要跟着重建；AI 工具目录混有显式登记的工具，各有自己的名字规则。两者另行处理。
   2. 插件宿主的代码不用改：登记与撤回本来就经登记表，协议适配器跟随之后自然生效。

## 理由

- 一份契约、一个登记表：运行期加载与配置阶段发现走同一套发布，不另开入口、不另写文档。
- 冲突在登记时整组拒绝，与权限码重复、操作重名的处理一致（ADR-0080）。被拒的只是那个插件，宿主照常运行，已有的路由与 tool 不受影响。
- 变更令牌是 `Microsoft.Extensions.Primitives` 的标准形态，ASP.NET Core 的路由与配置都用它，内核允许依赖这个包。
- MCP 的推送要先有会话与 SSE 流，这是传输的改动，与登记表无关；不推送时客户端重新列出即可，规范照实写明。

## 影响

- 内核：`OperationRegistry` 新增 `GetChangeToken`、`EnforceAdditions`（公开 API 只增）。
- `Protocols.Http`：
  - 新增 `IOpenApiGroupSource`，`OpenApiDocumentSource.FromServices` 合并来源的分组。
  - `MapXiHanOperations` 的返回值从路由组换成数据源的约定构建器，类型仍是 `IEndpointConventionBuilder`。
  - 分组文档从每组一条路由换成一条带参数的路由。
  - 运行期路由冲突返回 `PROTOCOLS_CONFLICT_002` 的 `Error`，消息键 `protocols.http.route_duplicate`。
- `Protocols.Mcp`：tool 表跟随登记表；运行期 tool 名不合法、重名返回 `PROTOCOLS_VALIDATION_004` / `PROTOCOLS_CONFLICT_001` 的 `Error`，消息键 `protocols.mcp.tool_name_invalid` / `protocols.mcp.tool_name_duplicate`。
- 文档：插件总览与进程外插件页、`Plugins.OutOfProcess` / `Plugins.Wasm` 包页、OpenAPI 与 MCP 页去掉「运行期加载只对调用器可见」，写明跟随登记表与冲突处理。
- 应用：撤回之后的地址从答复 `KERNEL_NOTFOUND_001` 变成按未匹配地址处理（通常是 404）。按错误码判断「插件已卸载」的客户端要改看状态码，或改走内核调用器。
