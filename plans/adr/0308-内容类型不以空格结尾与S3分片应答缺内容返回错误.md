# ADR-0308 内容类型不以空格结尾，S3 的验签照实测写明，上传与列出分片的应答缺内容返回错误

## 状态

已采纳（规范 RFC-0012「标识」「S3 Provider」「范围读取、分片上传与预签名」「一致性」、向量 `blob-content-types.json` 与 Go 规则 `IsBlobContentType` 已改；`ObjectStorage.Abstractions` 的 `BlobPutOptions.IsValidContentType` 不收以空格结尾的内容类型，一致性套件用例 15 补两种写法；`ObjectStorage.S3` 的 `UploadPartAsync`、`ListPartsAsync` 对缺必需内容的应答返回 `OBJECTSTORAGE_UNAVAILABLE_001`）。

本 ADR 修订 ADR-0295 决策 1 里「`text/plain; ` 合法」与文法 `^<token>/<token>( *;[\x20-\x7E]*)?$` 那一部分，并补正 ADR-0295 背景里对 S3 验签的推断。按「状态只增不改」，ADR-0295 的正文不改，以本 ADR 为准；ADR-0295 关于空参数、`;` 两侧只收空格、参数不解析引号、原样存取与 `OBJECTSTORAGE_VALIDATION_007` 的部分都不受影响。

## 日期

2026-11-26

## 背景

- **S3 上的实测**（上一轮在本机 RustFS 1.0.6 上做，AWS SDK for .NET 为 `AWSSDK.S3` 4.0.104.8，经 http，客户端与服务之间放一个原样记下请求的中继）：11 种内容类型 × 7 条路——SDK 直接写入、SDK 发起分片上传、预签名 PUT（HttpClient 原样带头）、把 SDK 改写的值换回原值后的写入与分片发起、Provider 的写入与分片发起：
  - 只差空白的写法：`text/plain;  charset=UTF-8`（连续空格）、`text/plain; charset=UTF-8 `（结尾空格）。SDK 线上发的是 `text/plain; charset=UTF-8`，SigV4 验签照样通过，服务存下的是改写后的值，不报错。原因是 SigV4 的规范请求头把值去掉首尾空白、连续空格合并成一个：原值与改写后的值规范化之后相同。
  - `;` 两侧的空格与 .NET 的写法不同的：`text/plain;charset=UTF-8`、`text/plain ;charset=UTF-8`。规范化之后仍不同，403 `SignatureDoesNotMatch`。ADR-0295 对这一类的推断成立，但 RFC-0012「S3 Provider」写的是「解析得了而写法不同的……服务验签对不上」，把两类写成了一类。
  - 解析不了的：`text/plain;`、`text/plain;;`、`application/json;charset=utf-8;`、`text/plain; `。SDK 抛出 `FormatException`，之后仍发出一条不带 `Content-Type` 的请求，服务 403、没有存下。
  - 以空格结尾的写法换哪条路都存不住原样：预签名 PUT 原样发出的 `text/plain; ` 读回是 `text/plain;`，`text/plain; charset=UTF-8 ` 读回去掉了结尾的空格；换回原值的 SDK 写入同样如此。RFC 9110 §5.5 的字段值不含首尾空白，收发的一方要先去掉它。
  - Provider 现在的判定（`S3ContentTypeHeader.IsSentVerbatim`：照 SDK 的做法以 `MediaTypeHeaderValue` 解析再写出，与原值逐字符相同才算原样）与实测的 11 种逐一吻合：写得出原值的 3 种（`text/plain; charset="UTF-8"`、`text/plain; charset=UTF-8`、`application/octet-stream`）照常写入、原样读回，其余 8 种都在发请求之前以 `OBJECTSTORAGE_VALIDATION_007` 拒绝。
- **ADR-0295 把以空格结尾的写法列为合法**：`text/plain; `、`text/plain ; `、`text/plain; charset=utf-8 `、`text/plain; charset=utf-8; ` 在向量的 valid 里（`text/plain; charset=utf-8 ` 这一类从 ADR-0214 起就合法）。它们在 S3 上本来就以 `OBJECTSTORAGE_VALIDATION_007` 被拒；预签名直传、宿主代收发的上传与下载、换一个 S3 兼容服务，只要过 HTTP 头就保不住结尾的空格。
- **宿主代收的上传**：签名没限定内容类型时，对象的内容类型取请求的 `Content-Type`，经 `BlobPutOptions.IsValidContentType` 核对。本机实测 Kestrel 在交给应用之前已经去掉请求头首尾的空白：发 `text/plain; `、`text/plain;  `、`text/plain; charset=utf-8 `、`text/plain;\t`、`  text/plain;`，应用读到的是 `text/plain;`、`text/plain;`、`text/plain; charset=utf-8`、`text/plain;`、`text/plain;`。进程内的测试服务器（`Microsoft.AspNetCore.TestHost`）原样转交它解析不了的值。
- **ADR-0302 的待定**：S3 的另两处应答缺必需的内容时抛出。本 ADR 的用例先红后绿时实测：
  - `UploadPart`：回环上的假对端回 `200` 而不带 `ETag` 头，真实 SDK 照收、`ETag` 为空，`BlobPart` 的构造抛 `ArgumentException`；内存替身给出空串、只有引号、只有空白、引号里只有空白的 ETag 同样抛出（`Unquote` 去掉引号之后为空或只有空白）。
  - `ListParts`：假对端列出的 XML 里分片没有 `<PartNumber>`，真实 SDK 照收、编号为空，按 `0` 交给 `BlobMultipart.ValidatePartNumber`，抛 `ArgumentOutOfRangeException`；替身给出编号 0、-1、10001，缺 ETag 或 ETag 为空，长度为负时，同样抛出。

## 备选

### 结尾的空白

1. **维持 ADR-0295，只靠 S3 以 `OBJECTSTORAGE_VALIDATION_007` 拒绝**（现状）：否决（拍板）。`OBJECTSTORAGE_VALIDATION_007` 说的是「这个存储的客户端写不出原值」；结尾的空格是任何 HTTP 头都承载不了，不是某个 Provider 的局限。留在合法集合里，同一份写入选项在文件系统上原样，经预签名、宿主代收发或别的存储就变了。
2. **写入前去掉结尾的空白再存**：否决。原样存取（ADR-0295 决策 2）不许 Provider 改写，这是静默兜底。
3. **同时排除开头的空白**：不用另写。媒体类型以 token 字符开头，开头的空白本来就不合法（向量里的 ` text/plain`）。
4. **把 `;` 之后的空格一并收紧成「后面必须跟着参数」**：否决。`text/plain ;`（`;` 之前的空格）、`text/plain; charset=utf-8 ;`（参数之后、`;` 之前的空格）不在结尾，HTTP 头承载得住，没有理由拒；只排除结尾，规则一句话说得清。
5. **文法的写法**：取 `^<token>/<token>( *;([\x20-\x7E]*[\x21-\x7E])?)?$`，即旧集合去掉以空格结尾的。没有采用「旧正则再加一个 `EndsWith(' ')` 判定」：两个判定，Go 与 .NET 两处都要写对；单个正则仍然没有嵌套的量词，`[\x20-\x7E]*[\x21-\x7E]` 只在结尾回退。也不用后行断言 `(?<! )$`：Go 的 RE2 不支持。规范同时写明它与逐段的写法再加「最后一个字符不是空格」是同一个集合。
6. **空格之外的结尾空白**：不用另写。制表符、换行是控制字符（ADR-0214），U+00A0 等不是 ASCII，都已不合法。
7. **宿主代收的上传先照 RFC 9110 §5.5 去掉请求头首尾的空白再核对**：没有做。真实的服务器（Kestrel）已经这样做；不这样做的宿主（进程内的测试服务器）照文法回 400，是安全的一侧。改端点不在本次拍板的范围里，见「待定」。
8. **版本级别**：MAJOR（`v1.0.0` 之前允许），改的是已经写明的行为：以前合法的写法现在不合法。读取一侧不变，存储里已有的这类内容类型照旧原样交出。

### S3 验签的写法

9. **照实测写明，标出是对 RustFS 1.0.6 的实测、Amazon S3 按 SigV4 的规则推断**：采纳（拍板）。只改描述，`OBJECTSTORAGE_VALIDATION_007` 的判定不变，记 PATCH。
10. **把只差在连续空格的一类从 `OBJECTSTORAGE_VALIDATION_007` 里放出来**（反正验签通过）：否决。服务存下的是改写后的值，违背原样存取，比失败更糟：调用方以为存进去的就是给的。

### 上传与列出分片的应答缺内容

11. **错误码**：与 ADR-0302 相同，`OBJECTSTORAGE_UNAVAILABLE_001`，理由同 ADR-0302 备选 7：服务应答成功却缺了必需的内容是服务一侧的问题，调用方没有过错，处置与其余服务端错误相同。
12. **只判字面上的「缺」**（`ETag` 为空、`PartNumber` 为空）：否决，理由同 ADR-0302 备选 9。按 `BlobPart` 构造写明的公开前置条件先判，哪一种都不抛：编号 1 到 10000，ETag 去掉两端的引号之后不为空、不只有空白，长度不为负。长度缺失照旧当作 0：构造收 0，长度只用于说明、完成时不核对，它不是必需的内容。
13. **列出时跳过坏的那一片**：否决。续传按列出的结果跳过已传的分片，跳过之后会重传它；拿列出的结果拼完成清单会少一片，到完成时才失败，或拼出缺了一段的对象。整个列出失败，调用方明确知道这次列不出来。
14. **`reason`**：每种缺失一个固定文本，写明请求名与缺的字段，不带应答里的值（同 ADR-0302 备选 8）：`UploadPart returned no usable ETag`、`ListParts returned a part without a usable PartNumber`、`ListParts returned a part without a usable ETag`、`ListParts returned a part with a negative Size`。
15. **上传分片缺 ETag 时重发，或去列出分片里补 ETag**：否决。重发可能又缺一次；列出是另一个请求、另一个可能缺内容的应答，Provider 不替调用方做这一步。调用方可以重传同一编号（后一次覆盖），或自己列出分片。
16. **在 `ObjectStorage.Abstractions` 公开分片 ETag 的判定**：没有做，理由同 ADR-0302 备选 10：Stable 类型的公开面增项，S3 包按构造文档写明的前置条件判即可。
17. **用 `try`/`catch` 接住 `BlobPart` 构造的异常**：否决，理由同 ADR-0302 备选 11。

## 决策

### 内容类型不以空格结尾

1. RFC-0012「标识」写明整串不以空格结尾（MAJOR，`v1.0.0` 之前允许）：内容类型最终是 HTTP 的字段值，RFC 9110 §5.5 的字段值不含首尾空白，任何靠 HTTP 头存内容类型的存储都存不住结尾的空格；对所有存储都成立，不只是 S3。`;` 之后的空格只在后面还有字符时才合法：`text/plain ;`、`text/plain; charset=utf-8 ;`、`text/plain;  ;` 合法，`text/plain; `、`text/plain;  `、`text/plain ; ; ; `、`text/plain; charset=utf-8 ` 不合法。`;` 之前的 OWS 仍只收空格。文法改为 `^<token>/<token>( *;([\x20-\x7E]*[\x21-\x7E])?)?$`；整体 1 到 255 个字符不变。
2. 向量 `blob-content-types.json`：valid 里以空格结尾的 4 条挪到 invalid（`text/plain; `、`text/plain ; `、`text/plain; charset=utf-8 `、`text/plain; charset=utf-8; `）；valid 补 3 条边界（`text/plain; charset=utf-8 ;`、`text/plain;  ;`、`text/plain; charset="a "`），invalid 补 6 条（`text/plain;  `、`text/plain;; `、`text/plain ; ; ; `、`text/plain; charset=utf-8  `、`text/plain; charset="a" `，以及正好 255 个字符、去掉结尾的空格就合文法的一条）。期望值由 .NET 回放核对。Go 规则 `IsBlobContentType` 的正则同步，回放测试另盯住这几类与那条 255 个字符的。
3. `BlobPutOptions.IsValidContentType` 的正则照此改。`BlobPutOptions.ContentType` 与 `BlobUrlRequest.ForUpload` 的异常消息统一为 `The content type must be a media type 'type/subtype', optionally followed by ';' parameters of printable ASCII, not ending with a space and at most 255 characters long.`：`BlobUrlRequest` 的消息原来还带着 ADR-0282 的「non-empty」，ADR-0295 只改了 `BlobPutOptions` 的那一句。
4. 一致性套件 `BlobStoreConformance` 用例 15 补两种写法：`text/plain ;` 与 `text/plain; charset=utf-8 ;`（空格之后还有字符），同样要么原样存取，要么在写入之前以 `OBJECTSTORAGE_VALIDATION_007` 拒绝。文件系统存储不用改：它原样存取，不另做核对。
5. 宿主代收的上传与签名走同一个核对，不另改代码：签名没限定内容类型、端点收到以空格结尾的 `Content-Type` 时回 400（`OBJECTSTORAGE_VALIDATION_006`）、不写入；经 Kestrel 时首尾的空白在到达端点之前已被去掉，这样的请求按去掉之后的值写入。签名限定的内容类型不能再以空格结尾（`BlobUrlRequest.ForUpload` 抛出）。
6. S3 Provider 里没有专为结尾空白写的分支：拒绝来自 `IsSentVerbatim` 的逐字符比较（.NET 写出时本来就不带结尾的空格），没有死代码可删。

### S3 的验签

7. RFC-0012「S3 Provider」的内容类型一条照实测改写（PATCH）：解析得了而写法不同的，SDK 一律写成 `type/subtype; 参数`，签名按原值去掉首尾空白、合并连续空格之后计算——合并之后仍与改写后的值不同的（`;` 之后没有空格、`;` 之前有空格）验签对不上，只差在连续空格的验签通过、服务存下改写后的值；结尾的空格同样会被去掉，但它已不合文法。两类都在发请求之前以 `OBJECTSTORAGE_VALIDATION_007` 拒绝，不变。注明是对 RustFS 1.0.6 的实测（AWS SDK for .NET 4.0，经 http），Amazon S3 没有实测、按 SigV4 的规范请求头推断相同，其余兼容服务未知。
8. `S3ContentTypeHeader` 的文档、`S3BlobStore` 里写入一处的注释与包 README 同步；`S3ContentTypeWireTests` 补一条：绕过 Provider 直接用 SDK 写 `text/plain;  charset=utf-8`，线上同样是 `text/plain; charset=utf-8`。

### 上传与列出分片的应答缺内容

9. RFC-0012「范围读取、分片上传与预签名」的 S3 一条写明（MINOR，以前不作规定）：上传分片的应答没有可用的 `ETag`，或列出分片的应答里有一片没有可用的编号、没有可用的 `ETag`、长度为负，同发起缺上传标识一样是不合规的应答，返回 `OBJECTSTORAGE_UNAVAILABLE_001`，不抛出；`reason` 写明是哪一步的应答缺了什么，不带应答里的值；上传分片不重发，列出不跳过那一片，长度缺失照旧当作 0。「S3 Provider」映射里「服务应答成功却缺了必需的内容」那句的括注补上这两步。错误码登记表不改。
10. `S3BlobStore.UploadPartAsync` 拿到应答后先判 ETag（去掉引号之后不为空、不只有空白），不合即返回 `OBJECTSTORAGE_UNAVAILABLE_001`，`reason` 为 `UploadPart returned no usable ETag`。
11. `S3BlobStore.ListPartsAsync` 逐片判编号（1 到 `BlobMultipart.MaxPartNumber`）、ETag、长度，有一片不合即整个列出返回 `OBJECTSTORAGE_UNAVAILABLE_001`，`reason` 按缺的字段取备选 14 的固定文本。
12. 两处都记一条 Warning：`The S3 service answered {Operation} for bucket '{Bucket}' without the content the blob store needs: {Reason}.`，只带请求名、桶名与固定的原因，不带应答里的值。

## 理由

- 合法的内容类型应当在哪条路上都是同一个值。结尾的空格过不了 HTTP 头，这是协议决定的，不是哪个 Provider 做得不够；把它挪出合法集合，「原样存取」才在每个存储上都做得到。
- 实测把一类推断拆成了两类后果：一类是失败，一类是不报错地存了别的值。规范照实测写，才能说清 `OBJECTSTORAGE_VALIDATION_007` 为什么连「验签照样通过」的写法也要拒。
- 服务给的东西不合规是服务一侧的错误：调用方拿到的应当是与其余服务端错误同一个码，而不是一个看上去像自己传错了参数的异常（ADR-0302）。

## 影响

- **公开 API**：签名不变（`PublicAPI.Unshipped.txt` 无改动）。`BlobPutOptions.IsValidContentType` 对以空格结尾的内容类型返回 `false`；`BlobPutOptions.ContentType` 与 `BlobUrlRequest.ForUpload` 的异常消息改了措辞。
- **升级须知（行为收紧）**：
  - 以空格结尾的内容类型（`text/plain; `、`text/plain; charset=utf-8 `）构造 `BlobPutOptions` 或 `BlobUrlRequest.ForUpload` 时抛 `ArgumentException`。迁移：去掉结尾的空格（`text/plain; ` 写成 `text/plain;`）。
  - 存储里已有的这类内容类型（文件系统存储在 ADR-0295 之后写入的）照旧原样读出，但读出的值不能原样写回：复制对象之类的代码要先去掉结尾的空格。S3 上没有这类对象：Provider 一向以 `OBJECTSTORAGE_VALIDATION_007` 拒绝，经预签名写入的读回也已去掉了结尾的空格。
  - 宿主代收的上传：经 Kestrel 等会去掉首尾空白的服务器时没有变化（以前同样收到去掉之后的值）；不去掉的宿主上，以空格结尾的 `Content-Type` 由写入改为 400（`OBJECTSTORAGE_VALIDATION_006`）。
  - S3 的预签名上传以前能限定 `text/plain; `（直传之后存成 `text/plain;`），现在签不出。
- **行为**：S3 的 `UploadPartAsync`、`ListPartsAsync` 遇到缺必需内容的应答不再抛出，返回 `OBJECTSTORAGE_UNAVAILABLE_001`；合规的应答不受影响。
- **规范**（规范仓库已改，指针待更新）：RFC-0012「标识」的文法（MAJOR）、「S3 Provider」的验签（PATCH）、「范围读取、分片上传与预签名」的两步（MINOR）；向量改的是内容（无新文件），Go 一致性模块的 `IsBlobContentType` 跟着改，认领 `objectstorage` 档的实现目前只有 .NET。
- **测试**（都不需要 S3 服务）：
  - 回放：`BlobContentTypeVectorTests` 新增一条，盯住合法一侧没有以空格结尾的、四种以空格结尾的写法在不合法一侧、空格之后还有字符的照收、正好 255 个字符只因结尾空格而不合法的那条；原有一条改看 `text/plain ;`。Go 一侧同样核对。
  - `BlobPutOptionsTests`：七种以空格结尾的写法不合法、构造与 `BlobUrlRequest.ForUpload` 都抛出，消息写明不能以空格结尾；五种空格之后还有字符的写法合法且原样保存。
  - 宿主代收：测试服务器原样转交的 `text/plain; `、`text/plain; charset=utf-8; ` 回 400、不写入。测试用的 HttpClient 会把解析得了的 `text/plain; charset=utf-8 ` 改写成去掉结尾空格再发，所以只用它解析不了的值。
  - 一致性用例 15：文件系统通过；S3 对真实服务的用例只在设了 `XIHAN_TEST_S3` 时执行，本机与 CI 都跳过。
  - 新增 `S3MultipartPartResponseTests`：回环假对端回 `200` 不带 `ETag` 的上传分片、列出的 XML 里分片没有编号（真实 SDK），返回 `OBJECTSTORAGE_UNAVAILABLE_001`、只发一个请求、记一条带桶名与请求名的 Warning；替身给出 5 种当不了 ETag 的值、9 种当不了分片的列出项（排在两片好的中间，整个列出失败），`reason` 写明请求名与字段、不带应答里的值；带引号与不带引号的 ETag、编号 1 与 10000、长度缺失照常。改实现之前 16 条失败（`ArgumentException` / `ArgumentOutOfRangeException`）。
  - `FakeS3Client` 记下每个上传已传的分片，模拟 `ListParts`，加 `NextPartETag` 与 `ListedParts` 换掉应答；`RecordingHttpListener` 加 `AnsweringWithBody`，能带响应体应答。
