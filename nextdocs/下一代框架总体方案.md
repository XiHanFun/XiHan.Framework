# XiHan Framework — 下一代框架总体方案

> 状态：提案（待拍板） | 适用：`next` 分支，XiHan Framework 5 | 日期：2026-10-21
>
> 本文是下一代框架从零重写的总体方案，自成一体，不依赖 `next/` 目录里现有的代码与草案（它们将被清空重写）。核心范式是"微内核 + 能力图谱 + 管道执行"，并扩展到十年稳定、跨语言、三条扩展轴和云原生编排。

---

## 0. 一页结论

1. **十年不淘汰的不是代码，是边界。** 把框架分成三层承诺：不易（原语层，永不破坏）、简易（内核，大版本内稳定）、变易（子系统、Provider、宿主、插件，各自演进）。只冻结极小的一层，其余全部可替换。
2. **框架的本体是一份语言中立的规范，加一个 .NET 参考实现。** 其他语言按规范实现、通过同一套一致性测试，这才是"同一个名字各语言都能用"。没有规范和一致性测试，多语言就只是口号。
3. **扩展有三条轴，共享一份清单模型和一条执行管道。** 能力包（编译期、同进程、可信）、插件（运行期、隔离、可不可信）、协议（跨进程、跨语言、跨部署形态）。
4. **所有借鉴都要落成机器能检查的规则。** 分析器、API 兼容性门禁、架构测试、一致性套件；不落成隐喻，不落成类名。
5. **默认实现必须能用。** 任何抽象都配一个零外部依赖、有容量上限的默认实现；五分钟起一个应用不需要任何数据库或中间件。
6. **一个领域一个词，全链路同词。** 包名、命名空间、能力 ID、配置节、错误码域、文档目录共用一张术语表，名字可由"领域 + 角色"唯一推出。

## 2. 设计总纲：三易模型

《易》有"不易、简易、变易"。这是本方案唯一允许进入架构骨架的哲学表达，因为它可以直接落成三层承诺：

| 层 | 名称 | 内容 | 承诺 | 变更策略 |
| --- | --- | --- | --- | --- |
| 不易 | **原语层 Primitives（Ring 0）** | `Result<T>`、`Error`、`Maybe<T>`、`TypedId<T>`、执行上下文契约、错误码格式、清单模型、稳定性标记 | 永不破坏；跨语言语义一致 | 只增不改；若必须破坏，新包名并存，旧包永不删除 |
| 简易 | **内核 Kernel（Ring 1）** | 特性契约、能力图谱、执行管道、宿主、诊断抽象、安全原语、插件宿主抽象 | 大版本内不破坏；大版本间提供迁移工具 | 两阶段弃用；每个大版本对齐一个 .NET LTS |
| 变易 | **子系统、Provider、宿主、协议、插件、应用（Ring 2–6）** | 持久化、缓存、消息、安全、多租户、调度等抽象与实现 | 各包独立 SemVer；通过一致性测试即视为兼容 | 自由演进，实验包进孵化区 |

七条原则：

1. **内核克制。** 内核只定义稳定边界，不堆能力；依赖宿主、扫描、应用工厂的东西都不进内核。
2. **装配显式。** 显式注册优先，自动发现只是增强，且必须有退出机制。
3. **模块化不是信仰。** 能力包是组织方式之一，不强迫所有能力都写成包。
4. **边界刚、内部柔。** 项目边界、依赖方向、分层规则刚性约束；实现内部自由演化。
5. **宿主落地。** 内核不感知宿主形态，宿主决定系统如何运行。
6. **规范先于实现。** 公共契约先写进 Spec，再写代码；Spec 没有的语义不得进入原语层和内核。
7. **默认实现必须可用。** 每个抽象配一个默认实现：零外部基础设施、容量有界、可降级、通过一致性测试。

## 3. 借鉴矩阵

规则：每一项借鉴都写成"借什么 → 落到哪 → 怎么检查"。写不出第三列的，只能进文档，不能进代码。

### 3.1 操作系统

| 来源 | 借什么 | 落到哪 |
| --- | --- | --- |

### 3.5 诸子百家

硬性规则：思想只能变成**约束**，不能变成**类名或 API**。代码里不出现 `Dao`、`Wuwei` 这类标识符。

| 思想 | 工程约束 | 机器检查 |
| --- | --- | --- |
| 《易》不易 / 简易 / 变易 | 三层承诺（§2） | 包验证基线按层分级 |
| 道家 无为、大道至简 | 内核不自动注册、不扫描、不推断；默认实现零配置可用 | 内核公开类型预算、零反射分析器 |
| 道家 反者道之动 | 任何能力都可被移除，应用仍可编译；弃用必有回退路径 | 移除能力后的编译测试 |
| 道家 上善若水 | 内核不感知宿主形态：Web、命令行、Wasm 都能跑 | 架构测试：内核不引用任何宿主包 |
| 儒家 正名 | 能力 ID、错误码、Baggage 键、操作 ID 是规范化命名，一经发布不改；包名由术语表推出 | 命名注册表 + 分析器 + 包 ID 文法测试 |
| 儒家 礼 | 互操作标准（Spec）就是"礼"：跨语言、跨实现共同遵守 | 一致性测试 |
| 儒家 中庸 | 显式优先，约定可用，二者都有退出机制 | 约定行为必须有显式覆盖 API |
| 儒家 和而不同 | Provider 实现可以不同，契约语义必须一致 | 一致性套件 |
| 法家 以法治 | 规则由工具执行，不靠人审 | 分析器、架构测试、ApiCompat 作为 CI 必过项 |
| 墨家 节用、非攻 | 资源有界；不锁定供应商 | 容量测试；抽象包不暴露第三方类型 |
| 兵家 先胜后战、以正合以奇胜 | 发布前过全部门禁；稳定主线 + 孵化区 | 孵化包只能标 Experimental |

### 3.8 明确不借

- 不做 Reconcile Loop 内核。
- 不做 Sidecar。
- 不做 OSGi 式运行时服务总线。
- 不做低代码平台、不做 UI。
- 不把哲学词汇写进标识符。

## 4. 总体架构

### 4.1 环层

```text
┌───────────────────────────────────────────────────────────────────────┐
│ Ring 6  应用与模板      BasicApp、业务模块、行业模板                      │
├───────────────────────────────────────────────────────────────────────┤
│ Ring 5  协议与插件      Protocols.Http / .Grpc / .Mcp / .CloudEvents     │
│                        Plugins.InProcess / Plugins.Wasm / Plugins.OutOfProcess │
├───────────────────────────────────────────────────────────────────────┤
│ Ring 4  宿主           Hosting.AspNetCore / Hosting.CommandLine         │
├───────────────────────────────────────────────────────────────────────┤
│ Ring 3  Provider        Persistence.EntityFrameworkCore / Caching.Redis │
├───────────────────────────────────────────────────────────────────────┤
│ Ring 2  子系统          <领域>.Abstractions + <领域>.InMemory 等默认实现   │
│                        Domain / Persistence / Caching / Messaging       │
│                        Security / MultiTenancy / ObjectStorage / ...    │
├───────────────────────────────────────────────────────────────────────┤
│ Ring 1  内核            Kernel：Hosting / Capabilities / Pipeline /       │
│                        Diagnostics / Security / Plugins（命名空间）       │
├───────────────────────────────────────────────────────────────────────┤
│ Ring 0  原语层          Primitives：Result / Error / Maybe / TypedId /   │
│                        InvocationContext / 清单模型 / 错误码 / 稳定性标记 │
└───────────────────────────────────────────────────────────────────────┘
                 ▲ 依赖只能向下；同环之间只经抽象包往来
```

### 4.2 依赖规则

1. 只能依赖更低的环；同环之间只能引用对方的契约包（`.Abstractions`，以及纯契约的 `Domain`）。
2. Ring 0 与 Ring 1 的第三方依赖为零，只允许 `Microsoft.Extensions.*` 抽象包。
3. `.Abstractions` 包不暴露任何第三方类型；Provider 不被任何抽象包引用。
4. 宿主与协议包不包含业务规则；插件不被任何正式包引用。
5. 以上规则由架构测试执行，违反即 CI 失败。

### 4.3 一次调用的路径

```text
HTTP 请求 ─► Protocols.Http 适配器（翻译为 XGI 消息）
          ─► Pipeline：Ingress → Observe → Resilience → Authenticate → Tenant
                      → Authorize → Validate → Idempotency → Transaction → Handle → Egress
          ─► Handle 阶段调用操作（IOperation），操作通过子系统端口访问 Provider
          ─► Egress 阶段把 Result / Error 翻译回协议（HTTP 用 RFC 9457 Problem Details）
```

同一条管道同样服务 gRPC、MCP、消息消费、命令行与进程外插件回调；协议适配器只做翻译，不含业务逻辑。

## 5. Ring 0：原语层（Primitives）

### 5.1 内容清单

| 类型 | 说明 | 跨语言语义 |
| --- | --- | --- |
| `Result<T>` / `Result` | 成功或失败，失败携带 `Error` | JSON：`{"ok":true,"value":…}` 或 `{"ok":false,"error":{…}}` |
| `Error` | `Code`、`Message`、`Details`、`Inner`，不可变 | 错误码格式见附录 C |
| `Maybe<T>` | 类型层面的"可能没有" | JSON：值或 `null` |
| `TypedId<T>` | 强类型标识 | 线上为底层类型（string / uuid / int64） |
| `InvocationContext` 契约 | 取消、截止时间、Trace、Baggage、作用域服务 | 传播到 HTTP 头、gRPC 元数据、CloudEvents 扩展、插件协议元数据 |
| 清单模型 | `xihan.manifest.json` 的对象模型 | JSON Schema 发布在 Spec |
| `Stability` / `[ApiLevel]` | 稳定性分级 | 各语言用等价注解或文档标记 |
| `LifecycleState` | 特性与插件的统一状态 | 探针与健康端点的输出词汇 |
| `FrameworkException` | 框架异常基类，带错误码 | 仅 .NET 形态；语义等同 `Error` |
| `FrameworkInfo` | 框架身份与版本 | 各语言自描述 |

### 5.2 冻结规则

- 只允许新增类型与新增成员；不允许改签名、改默认值、改语义。
- 任何原语层变更必须附 Spec 修订与一致性测试向量。
- 若出现必须破坏的情况，发布新包 ID（`XiHan.Framework.Primitives.V2`）并存，旧包永不下架。
- 原语层的公开面以 `PublicAPI.Shipped.txt` 为准，CI 禁止修改该文件中的已发布行。

### 5.3 命名规则

命名是规范性条款，写进 Spec，由分析器与架构测试执行。

1. **一个领域一个词，全链路同词。** 术语表（§5.4）是唯一事实源：包名用 PascalCase，命名空间与包 ID 一一对应，能力 ID 用小写，配置节用 `XiHan:<领域>`，错误码域用大写，文档目录同名。
2. **领域用名词，不用隐喻。** 禁用 `Bus`、`Engine`、`Manager`、`Helper`、`Core`、`Common`、`Shared`、`Base`、`Impl`、`Default`、`Util`。
3. **容器用复数，能力领域用不可数名词。** `Diagnostics`、`Capabilities`、`Plugins`、`Protocols`、`Profiles`；`Caching`、`Messaging`、`Persistence`。
4. **后缀只表角色，领域永远在前。** `.Abstractions` 是契约；实现按机制或技术命名（`InMemory`、`FileSystem`、`Redis`、`EntityFrameworkCore`），"默认"是清单里的角色，不是包名；`.Conformance`、`.Generators`、`.Analyzers` 跟在所属领域后。
5. **技术名用官方拼写。** `EntityFrameworkCore`、`RabbitMQ`、`MongoDB`、`OpenTelemetry`；非品牌缩写按 .NET 规则，两字母全大写（`AI`），更长用 Pascal（`Jwt`、`Mcp`、`Oss`）。
6. **类型名不带 `XiHan`，版本不进包名。** 命名空间已经标识归属；接口版本在清单里，只有原语层破坏才出现 `.V2` 并存。
7. **可预测性是验收标准。** 给定"领域 + 角色"必须能唯一推出包名；架构测试校验所有包 ID 符合下面的文法。

包 ID 文法：

```text
PackageId  = "XiHan.Framework." Segment
Segment    = "Primitives" | "Kernel" [ "." KernelTool ] | "Domain" | "Testing" | "Cli"
           | Subsystem [ "." Role ]
           | "Hosting." Host | "Protocols." Protocol | "Plugins." Isolation | "Profiles." Profile
           | "Compat." Major
Subsystem  = 术语表中除结构词以外的领域词
Role       = "Abstractions" | "Conformance" | "Generators" | Mechanism | Technology
KernelTool = "Analyzers" | "Generators"
Mechanism  = "InMemory" | "FileSystem" | "Database" | "Embedded" | ...
Technology = 官方拼写的技术名
Host       = "AspNetCore" | "CommandLine"
Protocol   = "Http" | "Grpc" | "Mcp" | "CloudEvents"
Isolation  = "InProcess" | "OutOfProcess" | "Wasm"

```

结构词：`Primitives`、`Kernel`、`Domain`、`Hosting`、`Protocols`、`Plugins`、`Profiles`、`Testing`、`Cli`、`Compat`。规范性文本在 `next/spec/conventions/package-ids.md`，架构测试 `PackageIds_FollowGrammar` 执行本文法。

命名空间等于包 ID；包内子命名空间最多一层。原语层与内核的公开名字在首个预览版前定死：`Result<T>`、`Error`、`Maybe<T>`、`TypedId<T>`、`InvocationContext`、`FrameworkException`、`FrameworkInfo`、`Stability`、`ApiLevelAttribute`、`LifecycleState`；`IFeature`、`IHostedFeature`、`FeatureContext`、`AppBuilder`、`App`、`PipelineBuilder`、`PipelineStage`。

## 6. Ring 1：内核

### 6.1 能力包与清单

一个**能力包** = 一个 NuGet 包 + 一份 `xihan.manifest.json` + 一个或多个 `IFeature` 入口。清单是事实源；用 `[Capability]` 特性标注入口类型，源生成器产出清单并嵌入程序集，避免双份维护。

```csharp
[Capability("persistence.efcore", Provides = ["persistence.relational@1"], Requires = ["kernel.hosting@^1", "multitenancy.context@^1?"])]
public sealed class EntityFrameworkCoreFeature : IFeature, IHostedFeature
{
    public void Configure(FeatureContext context) { /* 显式注册 */ }
    public Task StartAsync(IServiceProvider services, CancellationToken ct) => Task.CompletedTask;
    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}
```

清单字段（完整草案见附录 A）：`id`、`version`、`primitives`、`stability`、`kind`、`role`、`provides`、`requires`（含 `optional`）、`bindings`、`contributes`（管道、操作、配置 Schema、权限、健康项）、`activation`、`entry`。

### 6.2 能力图谱与解析

- 依赖按**能力 ID** 声明，不按包名；同一能力可由多个 Provider 提供。
- 解析步骤：收集清单（引用的程序集、插件目录） → 校验 Schema 与原语层版本 → 按版本范围求解 → 拓扑排序 → 生成"已解析图"。
- 多个 Provider 同时提供一个能力时，由配置 `XiHan:Providers:<能力ID>` 指定；未指定时若恰有一个清单 `role` 为 `default` 的实现则选它，否则启动失败并列出候选。
- `optional` 依赖缺失不阻止启动，对应特性进入 Degraded 并在健康端点报告。
- 冲突报错必须可解释：`A 需要 persistence.relational@^1，C 提供的是 @2`。
- `xihan graph` 命令输出已解析图；启动日志打印同一份图。

### 6.3 执行管道与钩子点

管道定义固定阶段，特性在清单里声明中间件归属的阶段；显式 `Use<T>()` 仍可用。排序规则：阶段 → 阶段内 `Before/After` 约束 → 包 ID 字典序，结果确定且可打印。

| 阶段 | 职责 | 内核或子系统提供的默认中间件 |
| --- | --- | --- |
| Ingress | 协议消息归一化、大小限制 | 请求规范化 |
| Observe | Trace、日志、指标 | Activity 与 Meter 桥接 |
| Resilience | 超时、限流、自适应并发、熔断 | `System.Threading.RateLimiting`、自适应并发 |
| Authenticate | 主体解析 | 安全子系统 |
| Tenant | 租户解析与隔离上下文 | 多租户子系统 |
| Authorize | 策略判定 | 安全原语 + 安全子系统 |
| Validate | 契约校验 | 由操作 Schema 驱动 |
| Idempotency | 幂等键去重 | 缓存子系统 |
| Transaction | 工作单元 | 持久化子系统 |
| Handle | 调用操作 | 操作调度器 |
| Egress | 结果与错误翻译、响应信封 | 协议适配器 |

```csharp
pipeline.UseAt<TenantQuotaMiddleware>(PipelineStage.Tenant, Placement.After);
```

管道上下文即 `InvocationContext`（§6.4）；阶段内并行分支（计算图形态）列为 5.x 后期目标，不进 5.0。

### 6.4 执行上下文

| 字段 | 内容 | 传播载体 |
| --- | --- | --- |
| `CancellationToken` | 取消 | 宿主连接取消、插件协议取消 |
| `Deadline` | 截止时间（基于 `TimeProvider`） | `xihan-deadline` 头 / 元数据 |
| `TraceId` / `SpanId` | W3C Trace Context | `traceparent` |
| `Baggage` | `xihan.tenant`、`xihan.principal`、`xihan.correlation`、`xihan.idempotency-key`、`xihan.locale` | `baggage` 头；键名由 Spec 注册 |
| `Items` | 请求作用域对象袋 | 不传播 |
| `Services` | 作用域 `IServiceProvider` | 不传播 |

### 6.5 生命周期状态机

```text
Declared → Resolved → Configured → Started → Ready
                                      │          │
                                      │          ├─► Degraded（可选依赖或绑定失效）
                                      │          │
                                      └──────────┴─► Draining → Stopped
任一步失败 → Failed（宿主按策略：终止启动 / 隔离该特性）
```

- 启动按已解析图正序，停止按逆序；每一步带取消与超时。
- 探针映射：startup = 所有特性到达 Started；readiness = 所有必需绑定健康且无 Failed；liveness = 宿主循环存活。
- 插件状态与特性同构，由插件宿主上报。

### 6.6 资源绑定

清单 `bindings` 声明需要的资源类型（`connection:relational`、`cache:distributed`、`queue`、`blob`），宿主从配置、环境变量或 Service Binding 挂载目录中解析并注入。缺失必需绑定在启动期失败，不是在第一次请求时失败。

### 6.7 诊断

- 内核只依赖 `System.Diagnostics`（`ActivitySource`、`Meter`）和 `Microsoft.Extensions.Logging.Abstractions`，不自建日志体系。
- 诊断接口只是薄桥，默认直接落到 .NET 原生 API；OpenTelemetry 桥接包只配置导出器。
- 审计接收器接口保留在内核，审计事件格式进入 Spec。

### 6.8 安全原语

| 原语 | 内容 |
| --- | --- |
| `IPrincipal` | 主体、声明、认证方式 |
| 租户上下文 | 当前租户与隔离级别 |
| 资源名 | `xrn:<partition>:<service>:<tenant>:<type>/<id>`，用于策略与审计 |
| `IPolicy` / `AuthorizationResult` | ABAC 判定接口与结果 |
| 权限定义 | 权限码注册表，供安全子系统与插件权限复用 |
| 插件授权 | 插件清单声明权限，宿主配置授予，运行期强制 |

安全上下文是不可变记录，由 Authenticate 与 Tenant 阶段写入 `InvocationContext`。

### 6.9 内核预算

| 项目 | 预算 |
| --- | --- |
| 内核公开类型 | ≤ 120 |
| 第三方依赖 | 0 |
| 启动额外开销 | < 50 ms |
| 空应用常驻内存 | < 30 MB |
| 反射使用 | 0（分析器强制，`Plugins.InProcess` 除外且标注 `RequiresDynamicCode`） |

### 7.2 默认实现规则

1. 包名按机制命名（`InMemory`、`FileSystem`、`Embedded`）；"默认"是清单 `role: default` 声明的角色，不进包名。
2. 零外部基础设施，启动不需要配置。
3. 所有集合有界；容量、过期、并发语义有测试。
4. 明确标注用途：可上生产的（缓存、Channel 消息）与仅限开发的（内存仓储）在清单 `stability` 和文档中区分。
5. 通过与 Provider 相同的一致性测试。
6. 只在没有显式 Provider 时生效，并在启动日志中声明"正在使用默认实现"。

### 7.3 Provider 接口版本化

借 Android Treble：每个子系统的 Provider 接口单独编号（`persistence.relational@1`），内核小版本升级不改 Provider 接口；接口变更只加新版本并存，宿主按清单协商。目标是 5.0 时代写的 Provider 在 5.x 全程可用。

### 7.4 一致性测试套件

`XiHan.Framework.<领域>.Conformance`：针对抽象的行为测试（正确性、错误、取消、并发、容量、生命周期），Provider 项目引用后直接运行。规则：

- 未通过套件的 Provider 最高只能标 `Preview`。
- 套件本身版本随 Provider 接口版本。
- 远程 Provider（§8.3）跑同一套套件。

### 7.5 Profile

| Profile | 内容 | 目标 |
| --- | --- | --- |
| `Profiles.Minimal` | Primitives + Kernel + 一个宿主 | 边缘服务、工具、插件宿主 |
| `Profiles.Standard` | Minimal + Domain + Localization / Persistence / Caching / Messaging / Security / MultiTenancy 的抽象与默认实现 | 大多数业务服务 |
| `Profiles.Full` | Standard + ObjectStorage / Scheduling / Configuration / Auditing + OpenTelemetry 导出 + Http / Grpc / Mcp / CloudEvents 协议 | 中后台、SaaS |

Profile 是元包，只引用、不含代码；解决"包太多不知道装哪个"而不牺牲粒度。

## 8. 三条扩展轴

### 8.1 能力包

编译期引用、同进程、可信。就是 §6.1 的能力包。它是第一方与可信第三方扩展的默认形态。

### 8.2 插件

运行期加载、隔离、可不可信。三种隔离级别共用一份清单格式，只是 `isolation` 不同，包名按隔离边界命名：

| 包 | `isolation` | 机制 | 信任 | 语言 | 可贡献 | 卸载 |
| --- | --- | --- | --- | --- | --- | --- |
| `Plugins.InProcess` | `in-process` | 可收集 `AssemblyLoadContext` | 可信 / 半可信 | .NET | 操作、事件处理器、中间件 | 可（有限） |
| `Plugins.Wasm` | `wasm` | WASI 组件（wasmtime） | 不可信 | 能编译到 Wasm 的语言 | 操作、事件处理器、中间件（Envoy 过滤器模式） | 可 |
| `Plugins.OutOfProcess` | `out-of-process` | 子进程 + gRPC 插件协议 | 不可信 | 任意 | 操作、事件处理器 | 可 |

插件模型借 VS Code：

- `contributes` 声明贡献点（操作、处理器、中间件、配置 Schema、权限）。
- `activation` 声明激活事件（启动、首次调用某操作、某事件到达）。
- `permissions` 声明所需权限（出站网络域名、文件路径、能力访问），宿主配置授予，运行期强制。
- 失败隔离：插件崩溃把插件置为 Failed，宿主进入 Degraded，不崩；重启策略带退避；每插件独立健康项。
- 进程外插件的 gRPC 协议（`xihan.plugin.v1`）定义在 Spec：握手（原语层版本、能力声明）、配置、启动停止、健康、操作调用（含上下文元数据与流式）。

5.0 范围：`in-process` 与 `out-of-process`；`wasm` 标 Experimental。

### 8.3 协议

协议轴解决三件事：对外暴露、对内接入、跨语言互通。

**XGI（XiHan Gateway Interface）**：协议适配器与管道之间的消息契约，等价于 ASGI 之于 Python。

```csharp
public interface IOperationInvoker
{
    ValueTask<OperationResponse> InvokeAsync(InvocationContext context, OperationRequest request);
}
```

**操作契约**：业务以操作为单位声明，类型即 Schema。

```csharp
[Operation("orders.create", Stability.Stable, Expose = Expose.Http | Expose.Grpc | Expose.Mcp)]
public sealed class CreateOrder : IOperation<CreateOrderRequest, Result<OrderId>>
{
    public ValueTask<Result<OrderId>> HandleAsync(CreateOrderRequest request, InvocationContext context) { ... }
}
```

源生成器从契约产出 JSON Schema、OpenAPI、`.proto` 与 MCP tool 描述；一份契约，多协议暴露。这是旧框架"动态 API"的继承者，区别是契约先行、不依赖反射、不限于 HTTP。

**协议适配器**：

| 包 | 方向 | 规则 |
| --- | --- | --- |
| `Protocols.Http` | 入 / 出 | 操作 ID 推导路由（`orders.create` → `POST /orders`），可显式覆盖；错误用 RFC 9457 |
| `Protocols.Grpc` | 入 / 出 | 生成 `.proto`；上下文走元数据 |
| `Protocols.Mcp` | 入 | 标记为 `Expose.Mcp` 的操作成为 tool |
| `Protocols.CloudEvents` | 入 / 出 | 消息子系统的事件信封 |
| `Hosting.CommandLine` | 入 | `xihan orders create --json …` |

**远程能力**：`requires` 的某个能力可以由远程服务经协议提供。远程 Provider 只是一个实现了同一抽象的客户端，跑同一套一致性测试。这让 Go 写的缓存服务或 Python 写的 AI 服务可以作为能力接入，而应用代码不变。

## 10. 云原生与编排

### 10.1 应用清单

`xihan.app.json` 描述应用：名称、Profile、能力包、绑定、探针、资源限制、协议端口。`xihan pack` 从它生成：

| 产物 | 说明 |
| --- | --- |
| Dockerfile | chiseled 基础镜像；可选 Native AOT；非 root |
| Helm chart / Kustomize | Deployment、Service、ConfigMap、Secret 引用、探针、PDB、HPA 建议 |
| Compose | 本地联调 |
| Aspire AppHost 注册 | 本地编排与服务发现 |

### 10.2 映射规则

| 框架概念 | k8s 对应 |
| --- | --- |
| 特性状态机 | startup / readiness / liveness 探针 |
| Draining 超时 | `terminationGracePeriodSeconds` 对齐 |
| `bindings` | Service Binding 挂载、Secret、ConfigMap |
| 配置热更新 | 挂载文件监听 → `IOptionsMonitor` |
| 指标 | OTLP 导出 → HPA 自定义指标 |
| 单例特性（调度器） | 领导选举端口 → `Scheduling.Kubernetes`（Lease） |
| 日志 | JSON 到 stdout |

### 10.3 原则

- 无状态进程是默认；有状态走 Actors 或外部存储。
- 租户分片通过一致性哈希端口，Provider 决定物理布局。
- Operator 是后期可选项，调和逻辑只在编排层，内核不感知 k8s。

## 11. 十年稳定性治理

### 11.1 版本与发布列车

- 下一代所有包共享一条版本线，从 **5.0.0** 起（延续 NuGet 上的 4.7 序列，避免"1.0 低于 4.7"的误导）。首个预览版为 `5.0.0-preview.1`。
- 大版本每 3 年一次，对齐 .NET LTS；小版本约每 6 个月；补丁随时。
- LTS 大版本：3 年活跃支持 + 1 年安全修复。4.x 在 5.0 GA 后进入 24 个月维护期。
- TFM：当前 LTS，上一 LTS 保留 12 个月过渡期。

### 11.2 API 分级与门禁

| 门禁 | 工具 | 规则 |
| --- | --- | --- |
| 公开面文件化 | `Microsoft.CodeAnalysis.PublicApiAnalyzers` | 每包 `PublicAPI.Shipped.txt`；Primitives 包已发布行不可改 |
| 包验证 | SDK `EnablePackageValidation` + 基线版本 | 小版本禁止破坏；大版本列出破坏清单 |
| 稳定性标记 | 自研分析器 | 公开类型必须有 `[ApiLevel]`；`Internal` 被引用即报错 |
| 命名文法 | 架构测试 | 包 ID、命名空间、能力 ID、配置节、错误码域符合 §5.3 文法与 §5.4 术语表 |
| 架构边界 | 架构测试 | 依赖方向、抽象包不含第三方类型、内核零反射 |
| AOT | CI 发布冒烟 | 裁剪警告视为错误 |
| 性能 | BenchmarkDotNet 基线 | 回退超过 5% 阻断 |
| 一致性 | Conformance 套件 | Provider 标 Stable 的前提 |
| 依赖安全 | `dotnet list package --vulnerable`、SBOM | 高危阻断 |

### 11.3 弃用流程

1. 标 `[ApiLevel(Deprecated)]` + `[Obsolete]` 警告 + 迁移文档，至少跨 2 个小版本。
2. 下一个大版本前的最后一个小版本升级为错误。
3. 大版本移除，并提供 Roslyn 代码修复。

### 11.4 变更流程

公开契约变更：RFC（`spec/rfcs`）→ ADR → 实现 → 一致性向量 → 文档。没有 RFC 的公开 API 变更不合并。新增术语表条目同样走 RFC。

### 11.5 Edition

借 Rust：约定集合按 Edition 命名（`Edition2027`、`Edition2030`），应用通过 MSBuild 属性选入。换 Edition 只改约定（路由推导、默认中间件集合），不改原语层与内核 API。老应用不选入就保持原行为。

### 11.6 预算

| 项目 | 预算 |
| --- | --- |
| 大版本内破坏性变更 | 0 |
| 原语层破坏性变更 | 0（只能新包并存） |
| 内核公开类型 | ≤ 120 |
| 每个 Provider 包传递依赖 | 只含该 Provider 必需库 |

## 15. 风险与反模式

| 风险 | 缓解 |
| --- | --- |
| 抽象过度，只剩一堆接口 | 默认实现必须可用；每个阶段的退出条件都是"跑起来" |
| Spec 成为没人实现的文档 | 第二语言 SDK 是 P4 的退出条件，不是愿景 |
| 单人维护带宽不足 | 5.0 范围只含内核 + Standard 子系统；其余进孵化区 |
| 源生成器与 AOT 成本 | 5.0 允许手写替代；生成器只覆盖清单、契约 Schema、注册三处 |
| 社区分裂 | Compat 桥 + 4.x 两年维护 + 自动迁移工具 |
| 哲学蔓延进代码 | §3.5 的硬性规则进入代码审查清单 |
| 包数量回到 50+ | Profile 元包 + 共享版本线 + 孵化区隔离 |
| 命名漂移 | 术语表走 RFC；包 ID 文法由架构测试强制 |

反模式清单：上帝基类、隐式依赖、反射魔法、深层继承、包爆炸、用隐喻命名、没有默认实现的抽象、把策略写进包名。

## 16. 需要你拍板的决策

1. **版本号**：下一代所有包共享 `5.x` 版本线，还是沿用 `1.0.0` 重置。本文建议 5.x。
2. **原语层与内核分包**：`XiHan.Framework.Primitives` 与 `XiHan.Framework.Kernel` 分开发布，Primitives 单独冻结。本文建议分开。
3. **内核包形态**：单包还是按 Hosting / Capabilities / Pipeline 等拆子包。本文建议单包，Profile 元包负责收口。
4. **第二语言**：Go 先行还是 TypeScript 先行。本文建议 Go。
5. **数据 Provider 顺序**：EntityFrameworkCore 优先、SqlSugar 作为存量迁移。本文建议 EntityFrameworkCore 优先。
6. **进程外插件协议是否进 5.0**：本文建议进，Wasm 标 Experimental。
7. **Spec 仓库**：独立仓库还是留在 `next/spec/`。本文建议 P0 先留在仓内，P4 公开时拆出。
8. **4.x 维护期**：建议 24 个月安全修复。

已定事项：命名规则与术语表（§5.3、§5.4）、`Persistence` 代替 `Data`、`Security` 同域同词、默认实现按机制命名。

```json
{
  "$schema": "https://spec.xihanfun.com/manifest/v1.json",
  "id": "xihan.persistence.efcore",
  "package": "XiHan.Framework.Persistence.EntityFrameworkCore",
  "version": "5.0.0",

  "stability": "stable",
  "kind": "provider",
  "role": "provider",
  "provides": [ { "id": "persistence.relational", "version": "1" } ],
  "requires": [
    { "id": "kernel.hosting", "version": "^1" },
    { "id": "multitenancy.context", "version": "^1", "optional": true }
  ],
  "bindings": [ { "name": "db", "type": "connection:relational", "required": true } ],
  "contributes": {
    "pipeline": [ { "middleware": "XiHan.Framework.Persistence.UnitOfWorkMiddleware", "stage": "transaction" } ],
    "operations": [],
    "config": { "section": "XiHan:Persistence", "schema": "schemas/persistence.schema.json" },
    "permissions": [],
    "health": [ "persistence.relational.connectivity" ]
  },
  "activation": [ "onStartup" ],
  "entry": "XiHan.Framework.Persistence.EntityFrameworkCore.EntityFrameworkCoreFeature"
}
```

默认实现把 `role` 设为 `default`（例如 `XiHan.Framework.Caching.InMemory`）。插件在此基础上增加：

```json
{
  "kind": "plugin",
  "isolation": "out-of-process",
  "permissions": [ "net.outbound:api.example.com", "fs.read:./data", "capability:caching.distributed" ],
  "activation": [ "onOperation:orders.*", "onEvent:orders.created" ]
}
```

`kind` 取值：`capability`、`provider`、`plugin`、`host`、`protocol`；`role` 取值：`provider`、`default`；`isolation` 取值：`in-process`、`wasm`、`out-of-process`。

## 附录 B：管道阶段与内置中间件

阶段顺序固定：`ingress → observe → resilience → authenticate → tenant → authorize → validate → idempotency → transaction → handle → egress`。

| 中间件 | 阶段 | 来源 |
| --- | --- | --- |
| 请求归一化、大小限制 | ingress | 内核 |
| Activity / 日志 / 指标 | observe | 内核 |
| 超时、限流、自适应并发、熔断 | resilience | 内核（基于 .NET 原生） |
| 主体解析 | authenticate | Security |
| 租户解析 | tenant | MultiTenancy |
| 策略判定 | authorize | Security |
| Schema 校验 | validate | 内核（由契约驱动） |
| 幂等键 | idempotency | Caching |
| 工作单元 | transaction | Persistence |
| 操作调度 | handle | 内核 |
| 结果翻译、错误信封 | egress | 协议适配器 |

排序规则：阶段 → `Before/After` 约束 → 包 ID 字典序。违反约束（环）在启动期失败。`xihan pipeline dump` 输出最终顺序。

## 附录 C：命名与错误码约定

| 对象 | 格式 | 示例 |
| --- | --- | --- |
| 包 ID | §5.3 文法 | `XiHan.Framework.Persistence.EntityFrameworkCore` |
| 命名空间 | 等于包 ID，子命名空间最多一层 | `XiHan.Framework.Kernel.Pipeline` |
| 能力 ID | `<领域>.<能力>`，领域取自术语表小写 | `persistence.relational`、`caching.distributed` |
| 能力版本 | 整数接口版本 | `persistence.relational@1` |
| 操作 ID | `<resource>.<verb>` | `orders.create` |
| 错误码 | `<领域大写>_<KIND>_<NNN>` | `PERSISTENCE_CONFLICT_001`、`SECURITY_DENIED_003` |
| Baggage 键 | `xihan.<name>` | `xihan.tenant` |
| 资源名 | `xrn:<partition>:<service>:<tenant>:<type>/<id>` | `xrn:cn:orders:t-42:order/1001` |
| 清单 ID | `xihan.<领域>.<name>` | `xihan.persistence.efcore` |
| 配置节 | `XiHan:<领域>` | `XiHan:Caching` |

错误码注册表放在 `spec/conventions/error-codes.md`，术语表放在 `spec/conventions/vocabulary.md`；新增条目走 RFC 附件，不走代码审查临时加。
