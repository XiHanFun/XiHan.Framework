# ADR-0120 表达式的长度与嵌套上限

## 状态

已采纳（`spec/rfcs/0021-workflow.md` 随之修订）。

## 日期

2026-11-04

本 ADR 记录第三十一批回灌（`ak-batch-backlog.md`，N5 安全审查，用户定修）的第一项。

## 背景

工作流表达式由持流程定义权限的用户写，解析是递归下降，没有上限。发布一个带 3000 层括号条件的定义，线程栈溢出，进程直接退出。栈溢出在 .NET 里接不住，所以租户用户就能让整个宿主崩溃。修前用测试复现：`Stack overflow`，退出码 127。

## 决策

1. 长度上限 4000 个字符，空白也算，在解析之前就判。
2. 嵌套上限 64 层。递归只有这几条路径，都算进同一个计数：括号、函数实参、索引 `[]`、一元 `!` 与 `-`。层数出来就退回去，并列的括号不累加。
3. 超限是普通的表达式错误 `WORKFLOW_VALIDATION_003`，消息键 `workflow.expression.too_long`（`length`、`max`）与 `workflow.expression.too_deep`（`max`）。发布时进校验结果，模板和运行时求值时进失败结果。
4. 错误里的 `expression` 参数最多 200 个字符。错误会进校验结果、响应和实例故障，超长的表达式不能原样带出去。

链不算嵌套：`a + b + c`、`a.b.c`、`a || b || c` 解析时是循环，业务条件写几十上百项是正常的。求值时闭包一层套一层，长度上限把它压在两千层左右，测试实跑通过。

## 备选

1. **`RuntimeHelpers.EnsureSufficientExecutionStack`**：抛的是可以接住的异常，但阈值取决于调用时的栈深和平台，同一个定义可能这次过、下次不过。否决。
2. **改成不递归的解析器**：改动大，求值时的闭包树照样要限。否决。
3. **只限长度**：一元运算符一个字符一层，4000 个字符就是 4000 层，照样溢出。否决。
4. **把链也算进层数**：几十项的 `||` 就会被拒。否决。

## 影响

- 超过 4000 个字符或 64 层的表达式，发布与求值都会被拒。真实业务条件到不了这个规模。库里已有这样的已发布定义时，实例走到那个节点会故障，错误是上面的消息键。
- 公开 API 新增 `WorkflowMessages.ExpressionTooLong`、`WorkflowMessages.ExpressionTooDeep`。
