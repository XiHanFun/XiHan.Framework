# ADR-0077 工作流随业务事务、分区隔离与待办查询下推

## 状态

已采纳（`spec/rfcs/0021-workflow.md` 与 `spec/conventions/error-codes.md` 随之修订）。修订 ADR-0066 第 5、6 节（全局定义、无租户的调用看得到全部）与 ADR-0072 的工作流索引。

## 日期

2026-11-01

## 一、引擎写入随业务事务（F1）

### 背景

- `Workflow.Database` 的三个存储与锁共用 `StoreInvocation`：每个存储操作在根提供者的新作用域里以无租户的上下文经 `App.InvokeAsync` 走完整管道，自己开工作单元、返回即提交。业务在自己的调用里发起流程、办理任务时，引擎的写入不在业务的事务里：业务回滚后实例、节点实例与书签照样留在库里；一次波次的写回分成好几个各自提交的存储调用，中途失败就留下半截状态。
- 活动在每个节点各开一次经管道的调用（新作用域、新工作单元），结果处理器（结束节点调用的 `IWorkflowOutcomeHandler`）的写入先于实例完成单独提交。BasicApp 的两个用例做不到原子：授权申请"写申请并发起流程"，结论回写"授予并完成实例"。4.x 的存储用环境事务里的 SqlSugar 客户端，是随业务一起提交的。
- 事件在写回之后经 `IMessagePublisher` 发出，与状态不在同一事务里；实例锁在写回之后立即释放——若写回进了业务事务，锁会早于提交释放，别的节点读到提交之前的旧状态再改写。
- 上一轮新增的只读工作单元（ADR-0073）里调用引擎写入时会怎样，没有定义。

### 备选

事务边界：

1. 每个存储方法查环境里有没有工作单元（例如经 `AsyncLocal`），有就加入。存储是单例，拿不到调用方的作用域；环境态还会漏进嵌套的活动调用。
2. 存储改成作用域服务，在所在作用域的工作单元里读写；"有没有可加入的事务"由 Provider 回答，引擎每个操作先问它：能加入就在调用方事务里执行，不能就自己开一次经管道的调用、在那次调用的事务里执行。
3. 引擎自己管理事务（开事务、提交），不经持久化的工作单元。绕过 Transaction 阶段，领域事件派发、发件箱与只读规则都要重写一遍。

活动的执行位置：

1. 照旧每个节点一次独立调用。活动与结果处理器的写入仍不随业务提交，用例二做不到。
2. 活动在引擎这次操作所在的调用里执行（同一作用域、同一事务）。

锁与事务的先后：

1. 锁行写进调用方事务。别的节点要等插入同一主键时阻塞到事务结束；PostgreSQL 上撞主键后整个事务即中止，争用就会让业务事务失败。
2. 锁行照旧自己提交（独立的作用域与工作单元），但引擎把取得的锁持有到服务作用域结束（事务提交或回滚之后）才释放。

事件：

1. 在事务里经作用域的发布者发出——装配了发件箱时写进同一事务的发件箱表。
2. 攒到提交之后发出。框架没有提交钩子；作用域结束时发出的事件也绕过了发件箱，丢了持久性。

### 决策

- 取 2、2、2、1。
- 新契约 `IWorkflowTransaction`（作用域服务，Provider 实现）：`IsActive`（当前作用域在不在可加入的调用方事务里）与 `EnsureWritable()`。数据库实现：在调用里且 Transaction 阶段已开启工作单元；只读工作单元返回 `PERSISTENCE_DENIED_001`。内存实现：在调用里即可；没有事务、不看只读。
- 引擎、定义目录、任务服务、外部任务服务经内部的 `WorkflowScope` 执行每个操作：
  - 能加入：写入操作先 `EnsureWritable()`（只读调用在取锁、执行活动之前即被拒绝），然后在调用方事务里执行。
  - 不能加入：在新作用域里经完整管道开一次调用（来源协议 `workflow`、目标是操作名，租户写进 Baggage 并预先放进安全上下文），在那次调用里解析同一个服务、执行同一个操作。单个操作失败即回滚；批量操作整批一个事务，逐项失败不回滚其余项，提交失败时每一项都报告提交的错误。应用不在服务状态时 `WORKFLOW_UNAVAILABLE_001`；自己开的调用里仍不能加入是装配错误，同样 `WORKFLOW_UNAVAILABLE_001`，不再嵌套。
- 三个存储改为作用域服务，数据库实现在所在作用域的工作单元里经仓储读写，不再经管道；`StoreInvocation` 删除。
- 活动在这次操作的调用里执行：`ActivityContext.Services` 是同一作用域、`Invocation` 是同一调用，结果处理器与活动的写入随引擎写入一起提交或回滚。活动失败照旧按重试 / 继续 / 实例故障处理，它在失败之前做的写入留在同一事务里、不单独回滚（与 4.x 相同）：会写入的活动与结果处理器先校验、后写入。
- 锁：Provider 的锁行照旧自己提交（数据库实现每一步在根提供者的新作用域里开可写工作单元，不经管道，与应用是否在服务状态无关）。`WorkflowScope` 把取得的锁持有到作用域结束才释放；同一作用域里再取空闲的锁直接复用，正在使用中再取立即以 `WORKFLOW_TIMEOUT_001` 返回。
- 事件：在事务里经作用域的 `IMessagePublisher` 发出。装配了发件箱时随事务提交、回滚即丢弃；没有发件箱时直接发布，可能早于提交、回滚不撤回——要求一致的应用必须装配发件箱。
- 轮询器、定时器与后台恢复没有调用方事务，各自开调用：每恢复一个书签一次调用、一个事务。

### 理由

- 存储按作用域、事务按 Provider 回答，引擎只问一句"能不能加入"：数据库实现复用持久化现成的工作单元、只读规则与领域事件派发，内存实现照样可用。
- 自己开调用与活动执行原先就各走一次管道，现在合成每个操作一次，管道调用次数只少不多；Tenant 阶段照常解析、校验并绑定分片，后台的调用与业务调用走同一条路。
- 锁持有到作用域结束，事务提交之前别人拿不到锁，读到的一定是提交后的状态；回滚后作用域照样结束、照样释放。租约行自己提交，别的节点立刻看得见、不随业务回滚，也不会在 PostgreSQL 上因主键争用中止业务事务。
- 发件箱本来就是"随事务提交的事件"的机制，不再造一个提交钩子。

### 影响

- 公开 API：新增 `IWorkflowTransaction`、`InMemoryWorkflowTransaction`、`DatabaseWorkflowTransaction`；`WorkflowEngine`、`WorkflowTaskService`、`WorkflowExternalTaskService` 的构造不再接收 `IWorkflowInstanceLock`（引擎也不再接收 `App`）；`DueBookmarkPoller` 的构造不再接收书签存储，新增 `RunCycleAsync`；`DatabaseWorkflowInstanceLock`、`PollerLeadership` 的构造不再接收 `App`。
- 行为：业务回滚时引擎写入一起回滚；活动看到的主体、租户与追踪是这次调用的（原来是匿名的新调用、关联 ID = 实例 ID）；取消令牌是调用的令牌，取消即回滚；只读调用里的写入在执行活动之前返回 `PERSISTENCE_DENIED_001`；锁持有到调用的服务作用域结束。实例锁在应用停止后照常可用（原来经管道，停止后不可达）。
- SQLite 只有一个写者：调用方事务写过之后再写租约行要等自己，所以在 SQLite 上要把 `WorkflowLockRecord` 经 `IEntityConnectionSelector` 放到另一个库文件（数据库测试这样做）；PostgreSQL 等行级锁的数据库不需要。
- `Workflow.Database` 的轮询循环原来只轮询不清理，现在每个周期调用 `RunCycleAsync`，到了维护周期按保留期清理。
- 测试：一致性套件新增业务回滚丢弃引擎写入、办理任务随业务提交或回滚、锁持有到调用结束且回滚后立即释放、只读调用在执行活动之前拒绝写入，按 `JoinsCallerTransaction`（内存实现为否）断言；数据库测试新增"结果处理器写授予与实例完成一起提交或回滚"。

## 二、工作流数据按分区隔离、随租户分库（F2）

### 背景

- 存储不按租户过滤，数据库记录不实现 `IMultiTenant`：按 SqlSugar 的落点规则全部落默认连接（平台库），库隔离租户的工作流数据也在平台库里。
- ADR-0066 让无租户的调用（平台）看得到、操作得了全部租户的实例，`WorkflowInstanceQuery.TenantId` 为空即不过滤；平台建的定义是全局定义，租户按名字解析找不到本租户的就落到它。BasicApp 的平台侧要管理平台自己的流程定义与实例，查不出"只要平台自己的"；平台的定义会被租户的授权申请解析到。
- 全局定义的租户列是 NULL，唯一索引 `UX_WorkflowDefinitionRecord_Na_TeId_Ve` 在 PostgreSQL、SQLite、MySQL 上不约束这些行（ADR-0072 记下的缺口）。
- 到期书签的轮询只读默认连接：租户库里的书签永远不会被轮询。

### 备选

记录怎么落库：

1. 记录不实现 `IMultiTenant`，存储自己写租户条件。持久化的分片路由只认 `IMultiTenant`（EF Core 是整个上下文切换），租户的数据仍落平台库。
2. 租户与平台共用一张实现 `IMultiTenant` 的表，平台用哨兵租户值。`IMultiTenant` 的新增要求工作单元有租户、无租户的调用查不到任何行（RFC-0005），平台的调用写不进去；为平台另开带哨兵租户的工作单元就不在业务事务里了，与第一节冲突。
3. 两组表：租户分区的四张表实现 `IMultiTenant`（随租户分库、按租户过滤），平台分区的四张表不实现、落平台库。
4. 持久化新增"可为平台的租户行"协议。改 RFC-0005 与三个 Provider，超出本次范围。

存储契约怎么知道分区：

1. 隐式：取所在作用域的租户。内存实现得改成按作用域的外观，存储套件也看不出分区。
2. 显式：每个方法的第一个参数是分区。数据库实现核对它等于工作单元的租户。

轮询覆盖哪些分区：

1. 平台加租户目录（`ITenantStore`）里启用的租户，逐个分区开调用扫描；领导权全局一份。
2. 每个库一份领导权。实现复杂，节点数通常远少于租户数，收益小。
3. 平台库里另建一张跨租户的到期索引。要与各库的书签保持同步，EF Core 下平台表在分片调用里会落到分片库。

### 决策

- 记录取 3，契约取 2，轮询取 1。
- 分区：平台一个，每个租户一个。调用只在自己的分区里读写；平台与租户互相看不到。看不到的按不存在处理（定义 `WORKFLOW_NOTFOUND_001`、实例 `_002`、书签 `_003`）。没有全局定义：推翻 ADR-0066 第 5 节"租户看得到全局定义、按名字解析落到全局定义"与第 6 节"无租户的调用看得到、操作得了全部"。
- 契约：三个存储每个方法的第一个参数 `tenantId` 是分区，写入的记录的 `TenantId` 必须等于它（不等抛 `ArgumentException`）。`WorkflowStartRequest.TenantId`、`WorkflowInstanceQuery.TenantId` 删除：实例总是属于调用方的分区，查询只查调用方的分区——平台调用查到的就是平台的实例，"为空即不过滤"的语义取消。建定义时写了别的租户 → `WORKFLOW_NOTFOUND_001`。
- 数据库实现：租户分区的 `WorkflowDefinitionRecord`、`WorkflowInstanceRecord`、`WorkflowNodeInstanceRecord`（新增 `TenantId` 列）、`WorkflowBookmarkRecord` 实现 `IMultiTenant`；平台分区新增 `PlatformWorkflowDefinitionRecord`、`PlatformWorkflowInstanceRecord`、`PlatformWorkflowNodeInstanceRecord`、`PlatformWorkflowBookmarkRecord`；公共列在抽象基类 `Workflow*Row`。租约表 `WorkflowLockRecord` 只在平台库。存储核对分区等于工作单元的租户（不等抛 `InvalidOperationException`）。
- 平台定义的唯一性（用户拍板：平台定义改存哨兵值、使它受唯一索引约束）：目标照办——平台定义的每一行都受唯一索引约束；形态不用哨兵值，而是平台表。证据：授予表 `PermissionGrantRecord` 能用空字符串作全局租户，是因为它是平台级数据、不实现 `IMultiTenant`，租户列只是普通列；工作流的租户表要实现 `IMultiTenant` 才能随租户分库，而 RFC-0005 规定 `IMultiTenant` 的新增写入当前租户、无当前租户时返回 `PERSISTENCE_VALIDATION_001`、查询只返回当前租户的实体——平台的调用往这张表里写不进哨兵行、也读不到它；为平台另开带哨兵租户的工作单元又离开了业务事务（第一节）。平台表的唯一索引只有 `(Name, Version)`，与哨兵值的效果相同：PostgreSQL、SQLite、MySQL 上每一行都受约束。
- 索引（修订 ADR-0072）：租户定义 `UX_WorkflowDefinitionRecord_Na_TeId_Ve`（租户列由 `IMultiTenant` 写入当前租户，不再为空，每一行都受约束）；平台定义 `UX_PlatformWorkflowDefinitionRecord_Na_Ve`（名字、版本，没有可为空的列）。租户表的保留期清理、列表与到期轮询改为带租户前缀：`IX_WorkflowInstanceRecord_TeId_EnAt`、`IX_WorkflowInstanceRecord_TeId_CrAt`、`IX_WorkflowBookmarkRecord_TeId_DuAt`；平台表沿用单列。
- 轮询：`DueBookmarkPoller` 每个周期覆盖平台与 `ITenantStore` 里启用的租户，逐个分区开调用扫描到期书签（Tenant 阶段为租户调用绑定分片），合并后按到期时间取一批，逐条以书签的租户开调用恢复。停用的租户不轮询；新租户在进入租户目录后的下一个周期纳入；一个分区失败只记日志。领导权全局一份（平台库的 `workflow.poller` 租约），保留期清理同样逐个分区。`Workflow.Abstractions` 引用 `MultiTenancy.Abstractions`（同环契约包）；`DatabaseWorkflowFeature` 以可选依赖声明 `multitenancy.context@1`，装配了多租户时排在它之后启动。

### 理由

- 用户要的"与业务实体一样经持久化的多租户 / 分库路由落到租户库"只有 `IMultiTenant` 做得到；`IMultiTenant` 又装不下平台的行，平台与租户只能分表。分表之后平台的定义也有了不含可为空列的唯一键，ADR-0072 的缺口随之关闭。
- 分区写进每个存储方法的签名：存储套件能直接验证"写在 t1、t2 与平台都看不到"；内存实现保持单例；数据库实现多一道"分区等于工作单元租户"的核对，挡住把数据写进别的分区。
- 平台与租户对等是 BasicApp 第 9.5 节的口径：平台只管平台自己的流程，要管某个租户的流程以那个租户的身份进来。
- 轮询按租户目录逐个分区，每个分区一次轻量的只读扫描，租户上百时每秒上百次扫描仍可接受；轮询间隔可调。跨租户索引要额外维护一致性，按库领导权在节点少于租户时没有收益。

### 影响

- 公开 API：三个存储的方法签名全部加分区参数；`WorkflowStartRequest.TenantId`、`WorkflowInstanceQuery.TenantId` 删除；新增 `Platform*Record` 四个实体与 `Workflow*Row` 四个基类；`WorkflowNodeInstanceRecord` 新增 `TenantId`；一致性套件的 `WorkflowStoreHost` 改为持有宿主，用例在 `InPartitionAsync` 开的调用里使用存储（新增 `WorkflowStores`），`WorkflowEngineHost` 新增 `AsTenantAsync` 与按分区读的辅助方法。
- 行为：平台调用不再看得到、操作得了租户的实例与定义（列表、计数、控制、清理都只到平台自己的）；租户按名字解析不再落到平台的定义；信号只消费、只启动自己分区的。
- 表结构（应用迁移）：
  - 新增四张平台表，`WorkflowNodeInstanceRecord` 新增非空 `TenantId` 列，索引按上面改名、改列。
  - 已有数据：`TenantId` 为 NULL 的定义、实例、书签与这些实例的节点实例迁到对应的 `Platform*Record` 表（同列复制，删掉 `TenantId`；平台定义迁过去之前先查 `(Name, Version)` 重复——旧索引不约束 NULL 行，可能已有重复，保留一行、其余改名或删除）；租户的行补 `WorkflowNodeInstanceRecord.TenantId`（取所属实例的租户）。有独立库的租户，把它的行从平台库搬到它自己的库。
  - 删掉旧的单列索引 `IX_WorkflowInstanceRecord_EnAt`、`IX_WorkflowInstanceRecord_CrAt`、`IX_WorkflowBookmarkRecord_DuAt`（`InitTables` 只建不删）。
- 测试：存储套件新增分区互不可见、按分区的名字空间、写入别的分区的记录即抛出；引擎套件的定义与实例隔离改为分区语义（平台与租户对等），新增轮询覆盖平台与每个启用的租户、跳过停用的租户；数据库测试新增"独立库租户的记录落在它自己的库、轮询经 Tenant 阶段覆盖它"。
