# ADR-0036 审计事件的主体与租户取自安全上下文；数据库记录的字符串列显式声明长度

## 状态

已采纳（`spec/rfcs/0015-auditing.md`、`spec/rfcs/0005-persistence.md` 修订）。

## 日期

2026-10-28

## 背景

BasicApp 6.0 的 N1 第二批（Access 包）联调发现两处框架侧问题：

1. `AuditMiddleware` 只从 Baggage 的 `xihan.principal` / `xihan.tenant` 取主体与租户，而 HTTP + JWT 这条路上没有任何中间件写这两个 Baggage（全仓只有插件协议的 `PluginMetadata` 写主体，消息派发、命令行、工作流写租户），JWT 认证过的调用在审计里一律是 "by (null) in tenant (null)"。
2. `Auditing.Database` 的 `AuditRecord` 字符串列没有长度声明，SqlSugar 的 CodeFirst 在 PostgreSQL 建成 `varchar(255)`，一条带字段级错误的 `KERNEL_VALIDATION_003` 审计（错误文案、错误细节 JSON、细节 JSON）就 "22001: value too long"，整批审计被丢弃；SQLite 不校验长度，一致性套件发现不了。同一类问题不止审计：`Workflow.Database` 的 `Document`、`Scheduling.Database` 的 `Data` / `ErrorMessage`、`Localization.Database` 的 `Template`、`MultiTenancy.Database` 的 `PropertiesJson` 都是无长度的 JSON / 文本列。

## 备选

1. 主体：让认证中间件把主体与租户写进 Baggage；或审计中间件优先读安全上下文、Baggage 只作回退。
2. 列长的表达：各 `*.Database` 记录标 SqlSugar 的 `[SugarColumn(Length / ColumnDataType)]`（这些包只依赖 `Persistence.Abstractions`，不能引用 SqlSugar）；DataAnnotations 的 `[MaxLength(n)]` / 无参 `[MaxLength]`（构造函数带 `RequiresUnreferencedCode`，正式包的 AOT 分析器以 IL2026 拒绝）；`[StringLength(n)]`（没有 RUC，EF Core 原生识别）加一个框架自己的长文本标记；或在 SqlSugar 约定里给没有长度的字符串一个统一缺省（512 / 长文本）。
3. 覆盖面：只改 `AuditRecord`；或全部框架记录一起标注并以架构测试门禁。

## 决策

- 主体取安全上下文（备选 1 第二项）：`AuditMiddleware` 构造事件时先看 `context.GetSecurity()`——`Principal.IsAuthenticated` 时取 `Principal.Id`，`Tenant?.Id` 有则取；没有再回退到 Baggage。Observe 在 Authenticate 之外、事件在调用结束时构造，安全上下文此时已就绪；只带 Baggage 的调用（插件协议、消息派发、命令行）行为不变。Baggage 不由认证中间件回写：Baggage 是跨进程传播的载体，不是进程内状态的副本。
- 列长按 `[StringLength(n)]` + `[LongText]`（备选 2 第三项）：`Persistence.Abstractions` 新增 `LongTextAttribute`（属性级，无参数）标记长文本列；`SqlSugarConventions` 把 `[LongText]` 映射为 `StaticConfig.CodeFirst_BigString`（各数据库的长文本类型）、`[StringLength(n)]` 映射为列长，实体自己的 `[SugarColumn]` 已给长度或类型时不动；DataAnnotations 的 `[MaxLength(n)]` / 无参 `[MaxLength]` 也映射（应用实体可用），但框架记录不用它。EF Core 对 `[StringLength]` 原生识别，对没有上限的字符串本来就建长文本，`[LongText]` 不需要额外映射。没有注解的字符串列沿用 SqlSugar 默认，不另设统一缺省——缺省值仍是一次静默猜测，而且会把字符串主键也变成长文本（MySQL 不能做主键）。
- 全部框架记录标注（备选 3 第二项）：`Auditing` / `Localization` / `MultiTenancy` / `Scheduling` / `Security` / `Workflow` 六个 Database 包的 16 个记录、76 个字符串列全部显式声明：标识 128、名字 / 键 / 主体 / 权限码 256、错误码 64、trace-id 64、区域 16、状态与种类 32 / 64、资源 1024、描述 1024、类型名 512、并发戳 32（与约定一致），JSON 文档、模板、错误文案为 `[LongText]`。架构测试 `DatabaseRecordTests.DatabaseRecords_DeclareEveryStringColumnLength` 对 `*.Database` 包里实现 `IEntity<>` / `IAggregateRoot<>` 的类逐列检查。
- 测试：`AuditMiddlewareTests` 覆盖安全上下文优先、Baggage 回退、两边都没有为空；`SqlSugarPersistenceTests` 覆盖 `[LongText]`、`[MaxLength(n)]`、无参 `[MaxLength]`、`[StringLength(n)]` 与无注解的映射；`SqliteAuditTrailTests` 核对 `AuditRecord` 的列元数据。

## 理由

- 安全上下文是进程内唯一的主体真源；让每条协议再把主体复制进 Baggage，既重复又会在 Baggage 被外部伪造时失真。
- `[StringLength]` 是提供器中立且 AOT 安全的：同一记录给 SqlSugar 与 EF Core 用，长度只写一次；`[MaxLength]` 在正式包里被 IL2026 拒绝，所以长文本需要框架自己的标记，而不是绕开分析器。
- 门禁而不是缺省：没有长度的字符串在 PostgreSQL 上是静默的 255，把它变成编译期可见的要求，比在约定里再猜一个数更符合"不添加静默兜底"。

## 影响

- 审计行为变化：认证过的调用从 "by (null)" 变为记录主体与租户；只带 Baggage 的调用不变。
- 建表变化：框架记录在 PostgreSQL / SQL Server / MySQL 上的列类型从 `varchar(255)` 变为声明的长度或长文本；已经按旧 DDL 建好的开发库需要重建或手工改列（CodeFirst 的 `InitTables` 会同步列定义）。SQLite 不受影响。
- 公开 API：`Persistence.Abstractions` 新增 `LongTextAttribute`（PublicAPI +1）；`AuditMiddleware` 签名不变；记录类只多了特性。应用自己的实体不受门禁约束，但 README 建议同样标注。
