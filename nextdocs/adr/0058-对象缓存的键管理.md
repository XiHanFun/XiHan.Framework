# ADR-0058 对象缓存的键管理

## 状态

已采纳（`spec/rfcs/0006-caching.md` 键管理一节增加「对象条目」）。

## 日期

2026-10-30

## 背景

ADR-0055 给字节存储加了 `ICacheStoreInspector`。BasicApp 6.0 的缓存管理接上它之后报告：单节点内存模式下，应用经 `ISharedCache` 写的条目列不出来。

原因是 `InMemoryObjectCache` 把对象引用存在自己的有界 LRU 表里，与 `InMemoryCacheStore`（字节存储）各自独立；`ISharedCache.Store` 转成的检视接口只看得到字节存储。BasicApp 的 `access:`、`identity:` 等缓存都走对象接口，开发环境没有 Redis，缓存管理页因此总是空的。用 Redis 时对象序列化进存储，能看到。

## 决策

- 新增可选接口 `ICacheInspector`（`Caching.Abstractions.Caches`），管理类型化缓存里不经字节存储的对象条目：
  - `ListKeysAsync(CacheKeyQuery)`：按前缀分页列键，前缀、上限与续页同字节存储。
  - `InspectAsync(key)` 返回 `Maybe<CachedObjectInfo>`：对象的类型全名、剩余存活时间与滑动窗口。不读出值、不延长滑动过期。
  - `RemoveByPrefixAsync(prefix)`：删除前缀下的对象条目，返回删除数；前缀不能为空。
  - 删单个条目用 `ICache.RemoveAsync`，读值用 `ICache.GetAsync<object>`，不另设入口。
- `InMemoryObjectCache` 实现它；序列化缓存（Redis 等）的条目都在字节存储里，不实现。
- 管理界面把缓存转成 `ICacheInspector` 得到对象条目，再把 `Store` 转成 `ICacheStoreInspector` 得到字节条目，两份合起来是全部条目；条目来自哪一份即它所在的层，同一个键可以两层都有。
- 内存实现的分页、查看与按前缀删除收拢到 `BoundedLruTable`，字节存储与对象缓存共用一份逻辑。

## 理由

- 两层分开列：对象条目没有字节、只有类型，字节条目有大小没有类型，硬并成一种记录要让一半字段为空；分开后管理界面直接知道条目在哪一层，删除也落到对应的层。
- 不给值的文本：对象是任意类型，序列化可能失败或泄露敏感字段；要看值的界面可以自己用 `GetAsync<object>` 取出后按需展示。
- 不新增统一入口：类型化缓存本来就有 `Store`，两个可选接口各管一层，比再造一个合并接口少一层转发。

## 影响

- 公开 API：`Caching.Abstractions` 新增 `ICacheInspector`、`CachedObjectInfo`；`InMemoryObjectCache` 实现 `ICacheInspector`。
- 行为：不变；字节存储的检视结果与 ADR-0055 一致。
- 已知限制：两级缓存的 L1 只订阅 L2 存储的变更通知。L2 是进程内对象缓存时（单实例开发环境），经本接口删除的对象条目在 L1 里最长 `LocalTimeToLive` 后才消失。
- 测试：对象条目与字节条目分层列出，分页走完续页；类型与剩余存活、查看不延长滑动过期；按前缀删除只删对象条目、空前缀抛出。
