# ADR-0073 只读操作开只读工作单元；查询取出条数超限是校验错误

## 状态

已采纳（`spec/rfcs/0005-persistence.md`、`spec/rfcs/0011-operations.md` 与 `spec/conventions/error-codes.md` 随之修订）。

## 日期

2026-11-01

## 一、只读操作开只读工作单元

### 背景

- `UnitOfWorkMiddleware` 总是开可写工作单元。操作契约的 `OperationContract.IsReadOnly`（ADR-0041：动词 `get` / `list`，或 `[Operation(ReadOnly = true)]`）只用于协议推导（HTTP 方法、MCP 提示），只读操作里误写照常提交。
- `UnitOfWorkOptions.IsReadOnly` 与 Provider 的拒绝早已存在，但只有管道外的单例存储（租户目录、授予、审计查询、租约探测）用到：内存实现在提交时才拒绝，EF Core 与 SqlSugar 在写入时拒绝，错误码借用状态机错误 `PERSISTENCE_VALIDATION_002`（HTTP 400）。
- EF Core 与 SqlSugar 工作单元的 `EnsureTransactionAsync` 是直接写 `DbContext` / SqlSugar 客户端之前开事务的入口，应用里常见（`Updateable(...).SetColumns(...)` 之前先调用它）。它不检查只读，只读工作单元里照常开事务、提交时照常提交。
- 同一服务作用域里再经管道（把外层的 `context` 交给 `IOperationInvoker`）时，内层中间件对已经开始的工作单元再调 `BeginAsync`，抛出携带 `PERSISTENCE_VALIDATION_002` 的异常，被 Observe 阶段包成 `KERNEL_UNEXPECTED_001`（500）。规范没有写嵌套调用的语义。
- 用户决定（D 类第 2 条）：只读传给中间件；只读操作里的写入直接拒绝，返回新的错误码，不静默忽略、不以未处理异常变成 500；想清楚并写明嵌套调用的语义。

### 备选

错误码种类：

1. 沿用 `PERSISTENCE_VALIDATION_002`（400）。
2. 新码，VALIDATION（400，gRPC `InvalidArgument`）。
3. 新码，CONFLICT（409，gRPC `Aborted`）。
4. 新码，UNEXPECTED（500，计入熔断）。
5. 新码，DENIED（403，gRPC `PermissionDenied`，不计入熔断）。

处理器忽略了拒绝：只把失败交给处理器；或者同时把工作单元记为失败，提交返回同一错误。

同一服务作用域里的嵌套调用：加入外层的工作单元（不开始、不提交，由外层决定）；以结果拒绝内层；维持现状（异常变 500）。

### 决策

- `UnitOfWorkMiddleware` 按本次调用的操作描述开工作单元：契约只读开只读工作单元，写操作与不带操作描述的调用（消息处理器、作业、直接交给 `App.InvokeAsync` 的处理器）开可写工作单元。
- 新码 `PERSISTENCE_DENIED_001`（`PersistenceErrors.ReadOnly`，取 5），消息键沿用 `persistence.unit_of_work.read_only`，十种语言的文案改为说明只读操作不能写入。`PERSISTENCE_VALIDATION_002` 不再表示只读写入。
- 只读工作单元不开数据库事务。三个 Provider 的仓储都在写入时拒绝、不触后端（内存实现从提交时改为写入时，覆盖层始终为空）；批量逐项都是这个码，空集合不算写入、仍返回空列表。拒绝同时把工作单元记为失败（内存实现新增与 EF Core、SqlSugar 相同的失败槽），提交回滚并返回同一错误。
- EF Core 与 SqlSugar 的 `EnsureTransactionAsync` 在只读工作单元里记下失败并抛出携带 `PERSISTENCE_DENIED_001` 的 `FrameworkException`；`UnitOfWorkMiddleware` 只捕获这一个码，回滚并转为同码结果，其余异常照旧回滚后抛出。EF Core 提交时有未保存的跟踪变更仍然拒绝，码改为同一个。
- 嵌套调用：一次调用一个工作单元，各调用按自己的契约开自己的，嵌套调用须新建服务作用域（`CreateAsyncScope()` + `App.CreateContext`）；只读不向内、也不向外传播，只读操作里调用的写操作在自己的事务里提交，外层随后失败也不回滚它。同一服务作用域里再经管道时，中间件看到工作单元已经开始过，以 `PERSISTENCE_VALIDATION_002` 的结果结束内层（新消息键 `persistence.unit_of_work.nested`），不执行处理器、不动外层的工作单元。
- 一致性套件加三例：只读操作拒绝全部写入且忽略拒绝的调用仍以该码结束；只读操作在新作用域里调用写操作照常提交；同一作用域的嵌套调用以 `PERSISTENCE_VALIDATION_002` 结束。套件特性 `ConformanceFeature` 为此登记两个执行用例脚本的操作（只读的 `conformance-scripts.get`、可写的 `conformance-scripts.run`），用例经真实的操作契约走完整管道。

### 理由

- 种类取 DENIED：被拒的是"本次调用没有被允许写"，与插件回调用了清单没有声明的权限（`PLUGINS_DENIED_002`）同类。这是操作实现的缺陷，不是调用方的输入：VALIDATION 让客户端以为请求参数有错，CONFLICT 暗示刷新状态后重试，UNEXPECTED 正是要避免的 500 且会让熔断器把一个确定性的缺陷当成下游故障。DENIED 不计入熔断，403 告诉客户端这个请求不会被执行，错误码与文案让开发者直接定位到只读声明。沿用 `VALIDATION_002` 会把状态机错误与契约违规混在一个码里，客户端分不开。
- 写入时拒绝：不碰后端，同一工作单元里也读不到被拒的写入，三个 Provider 的可观察行为一致。
- 记为失败：只把失败交给处理器，处理器丢掉返回值就等于静默忽略。记为失败后调用无论如何以该码结束；这与并发新增撞上主键后的处理（ADR-0063）是同一个机制。
- `EnsureTransactionAsync` 抛异常而不是返回结果：它是直接写客户端之前的声明，随后的写入不在框架手里，只有异常能保证写入不执行；签名不变，现有调用点不用改。中间件只把这一个码转为结果，所以不会变成 500，也不吞掉别的异常。
- 嵌套不加入外层：加入时内层的写操作在只读外层里写不进去，在可写外层里又会把内层失败前已写的部分随外层提交（外层不知道内层失败过），要再引入"只能回滚"标记与传播策略，超出 5.0"一次调用一个工作单元"的模型。框架自己的嵌套调用（AI 工具、MCP 的每次 `tools/call`）一直按"新作用域"执行。同一作用域的嵌套原本就走不通（异常变 500），改为结果只是把失败说清楚。

### 影响

- 行为变化：只读操作里的写入从"照常提交"变为 403 `PERSISTENCE_DENIED_001`；只读工作单元写入的码从 `PERSISTENCE_VALIDATION_002`（400）变为 `PERSISTENCE_DENIED_001`（403）；内存实现的只读写入从提交时改为写入时拒绝；只读工作单元里调 `EnsureTransactionAsync` 从"照常开事务并提交"变为拒绝；同一作用域的嵌套调用从 500 `KERNEL_UNEXPECTED_001` 变为 400 `PERSISTENCE_VALIDATION_002`。
- 公开 API（都在 Unshipped）：新增 `PersistenceErrors.ReadOnly`、`PersistenceMessages.NestedInvocation`，一致性套件新增三个用例方法；`UnitOfWorkOptions.IsReadOnly` 签名不变，文档写明语义。
- 不受影响：管道外自己开工作单元的代码由 `UnitOfWorkOptions` 决定，与操作契约无关——发件箱投递、审计落库、调度与工作流存储用 `UnitOfWorkOptions.Default`（可写），租户目录与授予的读取、审计查询、租约探测本来就开只读工作单元。
- 应用要做的：只读操作里有写入（读时补建缺失的行、记访问次数）的，去掉只读（换非只读的动词，或不声明 `ReadOnly`），或把写入放进新服务作用域里的另一次调用；直接写客户端之前必须调用 `EnsureTransactionAsync`，不经它的写入不受守卫、也不在事务里；EF Core 的只读操作里不要把读出的实体当草稿修改。

## 二、查询取出条数超限是校验错误

### 背景

- 第二轮持久化分区（4ded20bb）把 `EntityQuery<T>.Take` 限为 1 到 `EntityQuery.DefaultMaxTake`（1000），越界在构造查询时抛 `ArgumentOutOfRangeException`。调用方传了大于 1000 的页大小时，异常从处理器抛出，Observe 阶段包成 `KERNEL_UNEXPECTED_001`，客户端得到 500。
- 用户决定：超过 1000 改为校验错误（400，带错误码与消息键，消息带上限），在正确的那一层产出失败结果，而不是到处 try/catch；编程错误与调用方输入分开考虑。

### Take 从哪里来

1. 协议层：页大小是应用请求契约里的字段（框架没有通用的分页请求类型），HTTP 从查询串或请求体绑定。字段上声明了 `[Range]` 时 Schema 带上 `minimum` / `maximum`，Validate 阶段以 `KERNEL_VALIDATION_003` 拒绝并指出字段，进不到 Handle。
2. 查询构造：处理器（或框架的作用域列表方法 `TenantRecordStore` / `MessageTranslationStore` / `PermissionGrantRecordStore.ListAsync(…, skip, take, …)`，它们把调用方的值原样传入）调 `Page(skip, take)`。框架内部的分页都有界：发件箱 `BatchSize` 在选项里限 1–1000，审计查询的页大小先由 `AuditQuery.Validate` 以 `AUDITING_VALIDATION_001` 校验、多取一条只在小于上限时发生，目录加载与授予、调度、工作流存储的分页取常量上限、`Math.Min(上限, 剩余)` 或已限 1–1000 的 `Limit`。
3. 仓储执行：`IRepository.ListAsync` 返回实体列表，不返回 `Result`；Provider 按 `Take` 取，不得多取。

### 备选

1. 只靠协议层：要求应用在请求契约上声明 `[Range]`。框架看不到应用的请求类型，没声明的仍是 500。
2. `IRepository.ListAsync` 改为返回 `Result<IReadOnlyList<TEntity>>`：仓储执行层直接给结果。框架内约五十处、应用里所有查询都要改，只为一种失败。
3. 再加一个返回 `Result<EntityQuery<T>>` 的分页方法给调用方输入用，`Page` 保持抛出：两条路并存，默认路径仍是 500。
4. 构造查询时抛出一个可识别的异常（携带新码），由持久化在管道里的那一层——Transaction 阶段的 `UnitOfWorkMiddleware`——回滚并转为同码的校验结果；Transaction 之外仍是异常。
5. 仓储执行时发现超限，把工作单元记为失败并返回空列表，提交返回错误：处理器会拿着假的空列表继续执行。

### 决策

取 4，协议层的 `[Range]` 作为推荐写法保留。

- 新码 `PERSISTENCE_VALIDATION_005`（`PersistenceErrors.TakeExceeded`），消息键 `persistence.query.take_exceeded`（`PersistenceMessages.TakeExceeded`，参数 `take` 为请求的条数、`max` 为上限，十种语言）。
- `EntityQuery<T>.Take` 大于上限时抛出包内的 `TakeExceededException`（`FrameworkException` 的子类，携带该码与请求的条数）；`Page(skip, take)` 与 `with { Take = … }` 同一规则。对外它就是带码的 `FrameworkException`。
- `UnitOfWorkMiddleware` 捕获它：回滚，把调用结果设为 `Error.Validation(PERSISTENCE_VALIDATION_005, persistence.query.take_exceeded, { take, max })`（HTTP 400、gRPC `InvalidArgument`）；其余异常照旧回滚后抛出。
- `Skip` 为负、`Take` 小于 1 仍抛 `ArgumentOutOfRangeException`，不转为结果。
- 三个 Provider 不改：超限的查询构造不出来，到不了 `ListAsync`。一致性套件的取出条数用例改断言新码，并加一段：调用里先写入、再用超限的条数构造查询，调用以该码结束、写入回滚。

### 理由

- 正确的层：上限是持久化的约束，结果由持久化在管道里的那一层产出，覆盖所有来源（应用处理器、框架的列表方法），不要求应用改代码；整个框架只有这一处捕获，不是到处 try/catch。这与雪花标识不可用时的做法（ADR-0063：`NewId()` 只能返回 `long`，异常在 Resilience 阶段转为结果）同理——`ListAsync` 的签名同样给不出 `Result`，而为一种失败改掉所有查询的返回类型代价过大。
- 在构造时而不是执行时拒绝：超限的查询对象根本不存在，每个 Provider（含应用自己的 Provider）都不必重复检查，失败点就是给出页大小的那一行。
- 编程错误与调用方输入：上限是存储一侧的约束，调用方事先不知道，传 5000 是能改正的输入，消息带上 `max` 告诉它怎么改；负的 `skip`、为 0 的 `take` 构不成查询，合法的调用方不会给出，应用应在请求契约上用 `[Range]` 拦住，没拦住是应用的缺陷，维持异常。转换只在 Transaction 阶段里发生：管道外的后台代码与 Transaction 之前的阶段里，取出条数由代码给出，超限是编程错误，仍以异常暴露。
- 放在 `UnitOfWorkMiddleware` 而不是另加一个中间件：只有持久化 Provider 装配时才有仓储可查，三个 Provider 都已登记它；它本来就捕获异常做回滚，已做的写入随之回滚。幂等阶段在它之外，同一幂等键的重试回放同一个校验结果，与处理器返回的校验失败一致。

### 影响

- 行为变化：调用里 `Take` 超过 1000 从 500 `KERNEL_UNEXPECTED_001` 变为 400 `PERSISTENCE_VALIDATION_005`；管道外与 Transaction 之前的阶段里，抛出的异常类型从 `ArgumentOutOfRangeException` 变为 `FrameworkException`（码 `PERSISTENCE_VALIDATION_005`），捕获 `ArgumentOutOfRangeException` 的代码要改。负的 `skip`、小于 1 的 `take` 不变。
- 公开 API（都在 Unshipped）：新增 `PersistenceErrors.TakeExceeded`、`PersistenceMessages.TakeExceeded`；`TakeExceededException` 是包内类型。
- 应用要做的：页大小来自调用方时，仍应在请求契约上声明 `[Range(1, EntityQuery.DefaultMaxTake)]`（或更小）与 `skip` 的下限，Validate 阶段给出字段级错误；页码换算成 `skip` 时注意溢出（页码 × 页大小超过 `int.MaxValue` 会变成负数，成为编程错误）。
- 同类而未改：`JobRunQuery.Limit`、`WorkflowInstanceQuery.Limit`、`UserTaskQuery.Limit`、`WorkflowPurgeRequest.Limit`、`BlobQuery.PageSize` 越界仍在构造时抛 `ArgumentOutOfRangeException`；审计查询用 `AuditQuery.Validate` 返回 `AUDITING_VALIDATION_001`。它们不经仓储，是否同样转为校验错误另行决定。

> 修订（2026-11-01）：第一节的错误码由 ADR-0081 第一节改为 `PERSISTENCE_UNEXPECTED_001`（操作实现的缺陷，HTTP 500、gRPC `Internal`、按操作计入熔断），`PERSISTENCE_DENIED_001` 撤销；只读工作单元的其余语义与嵌套调用不变。
