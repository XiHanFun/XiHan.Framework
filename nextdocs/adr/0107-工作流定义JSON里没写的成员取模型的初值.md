# ADR-0107 工作流定义 JSON 里没写的成员取模型的初值

## 状态

已采纳。`spec/rfcs/0021-workflow.md` 的「目录」（定义的 JSON 往返）与「故障原因的本地化 / 设计期诊断」里 `DeserializeDefinition` 一句随之修订。修订 ADR-0106 第十六批修订中「不在场的 `init` 属性被设成类型默认值、默认值过不了规则的报缺少成员」一条：这种情况不再出现。

## 日期

2026-11-03

本 ADR 记录第十七批回灌（`u-batch-backlog.md`，用户定「另立一批修」）的一项决定。

## 背景

第十六批发现，源生成的序列化器把定义 JSON 里没写的 `init` 成员设成类型的默认值，而不是模型的初值。

查看生成代码（`EmitCompilerGeneratedFiles`）可知：`WorkflowJsonContext` 把带 `init` 的成员当作「成员初始化器」，统一放进对象创建委托。没写的成员传类型默认值，于是盖掉了属性初值。例如：

```csharp
static args => new WorkflowRetryPolicy() { MaxAttempts = (int)args[0], FirstDelay = (TimeSpan)args[1], BackoffFactor = (double)args[2] }
```

可写成员（`set`）没写时不赋值，初值保留。

### 盘点

定义图里带初值的 `init` 成员，以及修改前读入没写时的结果：

| 成员 | 初值 | 修改前没写时 | 结果 |
| --- | --- | --- | --- |
| `WorkflowDefinition.Version` | 1 | 0 | 被模型拒绝（第十六批报 `member_missing`） |
| `WorkflowDefinition.Status` | `Draft` | `Draft`（枚举默认值就是 `Draft`） | 一致 |
| `WorkflowDefinition.Nodes` / `Transitions` / `Variables` | 空列表 | `null`，由 `init` 的 `value ?? []` 变回空列表 | 一致 |
| `WorkflowNode.Properties` | 空对象 | `null`，由 `value ?? []` 变回空对象 | 一致 |
| `WorkflowRetryPolicy.MaxAttempts` | 1 | 0 | 被模型拒绝 |
| `WorkflowRetryPolicy.FirstDelay` | 10 秒 | 0 | **静默读成 0** |
| `WorkflowRetryPolicy.BackoffFactor` | 2 | 0 | 被模型拒绝 |

`WorkflowTransition`、`WorkflowVariableDefinition` 没有带初值的成员。其余成员（`DisplayName`、`Timeout`、`Priority`、`IsDefault` 等）的初值就是类型默认值，不受影响。

实例、节点实例与书签的成员都是可写的（`set`），一直保留初值，不在本批范围。工作流以外用 `init` 加初值的查询类型（如 `WorkflowInstanceQuery.Limit = 100`）不经 `WorkflowJsonContext` 读入，同样不在本批范围。

## 备选

1. **在读入时显式补初值**：没写的成员按一张初值表插进 JSON 再反序列化。初值表是第二份，会与属性初值漂移；或者要先构造一个原型对象再取值，绕。
2. **为这些类型改用带默认值的构造参数**：初值要写两处——参数默认值与属性初值；`TimeSpan` 的 10 秒不能作参数默认常量，只能改成可空；公开构造签名也要变。
3. **改成可写成员（`set`）**：破坏模型的不可变性，公开 API 变化。
4. **只给初值不是类型默认值的四个成员各加一层可空的内部序列化成员（采纳）**：
   - 公开属性加 `[JsonIgnore]`，同名 JSON 成员改由一个 `internal` 的 `XxxJson` 属性承载（`[JsonInclude]`、`[JsonPropertyName("…")]`，类型为可空）。
   - 它的 `get` 返回公开属性。
   - 它的 `init` 在值不为 `null` 时赋给公开属性，因此照常经公开属性的校验；为 `null`（没写或写成 `null`）时什么也不赋，公开属性保留自己的初值。
   - 初值仍只在公开属性一处。

## 决策

### 四个成员的做法

取备选 4，作用于 `WorkflowDefinition.Version`、`WorkflowRetryPolicy.MaxAttempts`、`FirstDelay`、`BackoffFactor`：

- 公开 API 不变；新增的 `VersionJson` 等是内部成员。
- JSON 成员名不变：`version`、`maxAttempts`、`firstDelay`、`backoffFactor`。
- 生成代码里，创建委托改为传 `int?` / `TimeSpan?` / `double?`。

### 必填与可省略

- **必填成员**只有定义的 `id`、`name`，节点的 `id`、`activityType`，转移的 `id`、`sourceNodeId`、`targetNodeId`，变量的 `name`。它们就是模型的 `required`，没写时报 `workflow.definition.member_missing`（第十六批）。
- **可省略的成员**取模型的初值：`version` 1、`status` `Draft`、三个列表为空、节点 `properties` 为空对象、重试策略 `maxAttempts` 1、`firstDelay` 10 秒、`backoffFactor` 2；其余为空、`false` 或 0。写成 `null` 与不写相同。
- **读入核对**：只对在场的成员套规则。第十六批「不在场成员的默认值过不了规则时报缺少成员」的分支删除，因为不在场的成员现在取初值，初值本身合法。
- **写成类型默认值**：按规则处理。版本 0、最多尝试 0 次、退避因子 0 报对应的问题；首次延迟 0 合法，保留。

### 写出

- `WorkflowJson.Serialize` 写出全部非空成员，等于初值的也写出（选项仍是 `WhenWritingNull`）。
- 往返稳定：读入、写出、再读入，值与文档都不变。
- 写出的成员名与改动前相同。

### 一致性保证

`WorkflowDefinitionInitialValuesTests` 把「只写必填成员读出来的」与「直接构造的」逐个成员比较，按序列化器的成员元数据比。比较覆盖定义、节点、转移、变量、重试策略，以及实例。以后新增带初值的 `init` 成员而读入时丢了初值，这个用例就失败。

修改验证：把重试策略改回原样（不加序列化成员）时，三个用例失败。

## 理由

- **初值只在一处**：读入与直接构造得到同一个对象，没有第二份初值表。
- **校验路径不变**：给了值仍经公开属性的 `init` 校验，规则仍是 `WorkflowDefinitionRules`（ADR-0106 修订）。
- **范围最小**：只动初值不是类型默认值的四个成员，JSON 形状、公开 API、写出结果都不变。

## 影响

### 行为

| 情形 | 修改前 | 修改后 |
| --- | --- | --- |
| JSON 里没写 `version` | `member_missing` | 读成 1 |
| 重试策略没写 `maxAttempts` | `member_missing` | 读成 1 |
| 重试策略没写 `backoffFactor` | `member_missing` | 读成 2 |
| 重试策略没写 `firstDelay` | 0 | 10 秒 |
| 这四个成员写成 `null` | `json_malformed`（类型不符） | 取初值 |

### 已存的数据与正在运行的实例

- **数据库实现**：定义以 `WorkflowJson.Serialize` 写入 `Document` 列，四个成员一直以显式值写出。
- **内存实现**：存对象本身。
- 所以已存的定义读出来的值不变，正在运行的实例按定义 ID 取的仍是同一份定义，**不需要迁移**。
- **例外：已存的首次延迟 0**：以前由不写 `firstDelay` 的 JSON 建的草稿或已发布定义，存下的是显式的 `"firstDelay": "00:00:00"`，仍是 0。要 10 秒须重新保存，或给出新版本。

### 其他

- **公开 API**：没有变化。
- **序列化方式的约束**：
  - 用 `WorkflowJson`（框架的源生成上下文）读写，行为如上。
  - 用应用自己的 `JsonSerializerOptions` 直接序列化这些模型时，公开属性是 `[JsonIgnore]`，内部的序列化成员其他程序集的源生成上下文看不到，这四个成员会被漏掉。定义的 JSON 往返照 RFC-0021 走 `WorkflowJson`。
- **测试**：新增 `WorkflowDefinitionInitialValuesTests`，含逐成员与直接构造比较、四个成员的「不写 / 写了 / 写成类型默认值 / 写成 null」、写出与往返。第十六批「不在场成员报缺少成员」的用例删除。
- **不在本批**：转移的 `sourceNodeId` / `targetNodeId` 写成 `null` 时的待定项，没有随本批消失。这两个是必填成员，写成 `null` 不算缺少，模型也不拒绝。
