# ADR-0053 调度管理面

## 状态

已采纳（`spec/rfcs/0013-scheduling.md` 修订，`spec/conventions/error-codes.md` 登记一个错误码）。

## 日期

2026-10-30

## 背景

BasicApp 6.0 N2 第七批（Maintenance）做 4.x 的作业管理页时报告三处缺口：

- `IJobScheduler.RunsAsync` 不给总数，列表分页拿不到总条数；`JobRunQuery` 也不能按触发器、节点或有无错误筛选。
- `JobTypeRegistry` 不能枚举，运行时新建作业时无从列出可选类型。
- 代码登记的作业在运行时经 `ScheduleAsync` 改过计划，下次启动时首个周期又按代码写回（只有暂停状态保留），管理页改的 Cron 会被静默丢掉。

## 备选

针对代码作业的运行时修改：

1. 代码作业一律以代码为准：管理页不能改代码作业，只能暂停或手动触发。与 4.x 的作业管理页不符。
2. 运行时改过的一律保留：开发者改了代码里的计划，部署后不生效，问题更隐蔽。
3. 记下代码定义的指纹：代码没改就保留运行时的修改，代码改了以代码为准并记警告；另给「恢复为代码定义」的操作。

## 决策

采用 3。

- **运行历史**：
  - `JobRunQuery` 增加 `Trigger`（触发器名）、`Node`（执行节点）、`HasError`（有无错误码）。
  - `IJobStore` 与 `IJobScheduler` 增加 `CountRunsAsync(query)`：与 `RunsAsync` 同一组过滤项，不看分页。数据库实现用仓储的 `CountAsync`。
- **作业类型**：`JobTypeRegistry.Keys` 按序数列出已登记的类型键。
- **代码作业的运行时修改**：
  - `JobSource` 增加 `Overridden`；`JobRecord` 与数据库的作业表增加 `CodeFingerprint`（可空，64 位十六进制）。
  - 指纹覆盖代码定义的类型键、数据、标志、说明，以及各触发器的名字、计划文本、数据、优先级、misfire 策略与说明，算 SHA-256。
  - 按代码写入时记下指纹。运行时 `ScheduleAsync` 替换代码作业时，来源记为 `Overridden`，指纹沿用。
  - 启动同步时，存储里是 `Overridden` 且指纹与当前代码定义相同，就跳过不写；否则按代码写入，覆盖运行时修改时记一条警告。暂停状态一律保留。
  - `RestoreAsync(names[])` 照代码写回，来源回到 `Code`；没有代码定义 → `SCHEDULING_NOTFOUND_005`（十种区域）。

## 理由

- 指纹只在启动同步时比较，不改轮询路径，开销只发生在启动时。
- 保留了代码作为默认值的地位：开发者改代码一定生效，管理员的修改在代码不动时一直有效，两者冲突时有日志可查。
- 总数是独立的调用而不是改 `RunsAsync` 的返回值：已有调用不变，不需要总数的列表不多数一次。

## 影响

- 公开 API（`Scheduling.Abstractions`）：`JobRunQuery.Trigger` / `Node` / `HasError`、`JobTypeRegistry.Keys`、`IJobStore.CountRunsAsync`、`IJobScheduler.CountRunsAsync` / `RestoreAsync`、`JobSource.Overridden`、`JobRecord.CodeFingerprint`，错误码与消息键各一个。
- 存储实现：
  - 内存与数据库两种存储实现 `CountRunsAsync`。
  - 数据库实现：作业表加可空列 `CodeFingerprint`（建表即可补列），运行查询加触发器名、节点、有无错误三项过滤。
  - 5.0 尚未发布，接口增加成员不另开版本。
- 行为：已有代码作业的记录没有指纹，升级后首次启动按代码写入一次并记下指纹，之后按上面的规则处理。
- 测试：
  - 存储一致性：计数与三项新过滤、来源与指纹往返。
  - 数据库的跨重启用例：
    - 代码没改时，保留运行时的修改。
    - 代码改了，以代码为准。
    - 恢复为代码定义；没有代码定义的不能恢复。
    - 类型键可以列出。
