# ADR-0049 对象存储的范围读取、分片上传与预签名

## 状态

已采纳（`spec/rfcs/0012-objectstorage.md` 修订，`spec/conventions/error-codes.md` 登记四个错误码，`spec/conventions/capability-ids.md` 登记两个能力）。

## 日期

2026-10-29

## 背景

BasicApp 6.0 N2 第四批（Files）报告：`IBlobStore` 只有整对象的 Put / Get / Head / Delete / List，S3 单次 `PutObject`（不可寻址流先落临时文件），Get 的流不可寻址。大文件直传、断点续传与 S3 上的音视频拖动做不了。BasicApp 只好签发自己的下载端点（数据保护的限时令牌），S3 的内容经应用转发。4.x 的文件下载有预签名链接（缺省 30 分钟），也有发起 / 上传分片 / 完成 / 放弃的分片上传；本轮要求对齐 4.x 原有功能，并且由框架实现、BasicApp 不写替代。

## 备选

1. 全部加进 `IBlobStore`：预签名在没有原生签名的存储上要宿主的 HTTP 端点，契约包与存储包都碰不到 HTTP；而且每个 Provider 都得实现。
2. 三个都做成旁挂的可选能力：范围读取是任何存储都能直接做的基本读法，旁挂只会让调用方多一次判断。
3. 范围读取进 `IBlobStore`（`objectstorage.blob@1` 的一部分）；分片上传与预签名各成可选能力，存储能做就提供。

## 决策

采用 3。

- **范围读取**：`IBlobStore.GetAsync(container, key, BlobRange, ct)`。
  - `BlobRange` 是起点加可选长度；`BlobRange.Resolve(total)` 统一截断规则。
  - 结果的 `BlobContent.Range`（`BlobContentRange`）给出实际范围，元数据长度仍是总长。
  - 起点不在对象内（含空对象）→ `OBJECTSTORAGE_VALIDATION_001`。
- **分片上传**（`objectstorage.multipart@1`，`IBlobMultipartStore`）：Start / UploadPart / ListParts / Complete / Abort。
  - 限制与 S3 一致：编号 1–10000，非末片 ≥ 5 MiB。
  - 分片可乱序、可重传；完成时清单须编号严格升序、ETag 相符。
  - 清单不合法 → `OBJECTSTORAGE_VALIDATION_002`，上传保留；上传不存在或已结束 → `OBJECTSTORAGE_NOTFOUND_002`；放弃是幂等的。
  - `BlobMultipartUpload`（容器、键、上传标识、是否覆盖）可持久化，跨请求续传。
- **预签名**（`objectstorage.presign@1`，`IBlobUrlSigner`）：`BlobUrlRequest.ForDownload`（可带保存的文件名）、`ForUpload`（可限定内容类型）、`ForPart`（分片上传的一片）。
  - 有效期缺省 30 分钟，1 秒到 7 天。
  - `BlobSignedUrl` 带地址、方法、失效时刻与客户端必须发送的头；`BlobContentDisposition` 统一下载文件名的写法（RFC 6266 的 `filename*`）。
- **S3**：
  - 范围读取经 `Range`，解析 `Content-Range`；416 → 范围不可满足。
  - 分片直接映射 multipart；不覆盖的完成先 HEAD，再带 `If-None-Match: *`。
  - 预签名经 SDK，签名 V4；端点是 http 时显式按 http 签，否则签出的地址连不上。
- **文件系统**：
  - 范围读取打开文件后定位，用有界流只交出该段。
  - 分片暂存在 `<container>/uploads/<id>/`，分片文件名带内容的 SHA-256，所以重传后 ETag 与内容不会错位。
  - 完成时拼接成对象同目录的临时文件，经存储同一个提交路径原子替换并计入配额。暂存分片不计配额。
  - 过期（缺省 7 天）未完成的上传在启动扫描时清掉。
- **宿主代收发的预签名**（`Hosting.AspNetCore` 的 `HostedBlobUrlFeature` 与 `MapXiHanBlobs()`），给没有原生签名的存储用：
  - 签名：HMAC-SHA256，覆盖方法、容器、键、过期秒与各限定项，Base64Url 编码。无状态，同一密钥的多个实例互认。
  - 端点：`GET` 支持单个 `Range` 区间，回 206 / 416；`PUT` 写整个对象或一片，响应带 `ETag`。
  - 验签失败或过期 → `OBJECTSTORAGE_DENIED_001`（403）。端点经内核管道（Observe 照常记录），不要求凭据；上传解除请求体大小上限，单对象上限交给存储。
  - 与 S3 原生签名不要同时装。

## 理由

- 范围读取是读法，不是能力差异：两种存储都能直接实现，进契约以后调用方（下载端点、播放器）不必判断。
- 分片与预签名在不同存储上的实现差别很大（文件系统的预签名需要宿主端点），做成可选能力，按能力 ID 依赖与选择，与现有装配规则一致。
- 签名端点放在宿主包：只有它能映射 HTTP 端点，签名器与端点必须用同一把密钥、同一套规范串。
- 限制向 S3 看齐：同一套一致性用例在两种存储上都能通过，应用换存储不改代码。

## 影响

- 公开 API：
  - `ObjectStorage.Abstractions`：`BlobRange`、`BlobContentRange`、`BlobContent.Range`、`IBlobStore` 的范围读取，`Multipart.*`、`Signing.*`。错误码与消息键各四个、九个，十种区域。
  - `ObjectStorage.FileSystem`、`ObjectStorage.S3` 实现新增接口，文件系统选项 `MultipartExpiry`。
  - `Hosting.AspNetCore`：`Blobs.*`，并引用 `ObjectStorage.Abstractions`。
  - 5.0 尚未发布，`IBlobStore` 增加成员不另开接口版本。
- 行为：已有调用不变；文件系统与 S3 特性多提供两个 / 一个能力。
- 测试：
  - 一致性套件加范围读取与分片用例（文件系统通过；S3 对 MinIO 通过；不实现分片的 Provider 跳过）。
  - 文件系统：过期清理与伪造上传标识；宿主端点端到端（整读、206、后缀区间、416、保存文件名、篡改、方法不符、过期、限定内容类型的上传、分片直传后完成）。
  - S3：对 MinIO 的预签名直连（下载、Range、上传、分片）。
