# ADR-0121 网络入站不接受自报的租户与主体

## 状态

已采纳（`spec/rfcs/0003-invocation-context.md`、`0007-multitenancy.md`、`spec/conventions/baggage-keys.md`、`spec/protocol/http.md`、`grpc.md`、`mcp.md` 随之修订）。

## 日期

2026-11-04

本 ADR 记录第三十一批回灌（`ak-batch-backlog.md`，N5 安全审查，用户定修）的第二项。

## 背景

HTTP、gRPC、MCP 入站把 `baggage` 头里已登记的键都收进调用上下文，`xihan.tenant` 也在其中。租户解析顺序是声明、Baggage，而 `BaggageTenantResolver` 只取值、中间件只核对租户存在且启用，不核对调用方属不属于它。

结果是任何没有租户声明的令牌（平台账号）带上 `baggage: xihan.tenant=<id>` 就进入任意租户，匿名调用也一样。N5 用零权限的平台账号实测确认，BasicApp 目前靠 `TokenTenantMiddleware` 挡住自己签发的令牌，根因在框架。

`xihan.principal` 不参与认证，但审计把它当作没认证调用的主体（`AuditMiddleware`），调用方能伪造审计记录。

## 决策

1. `HttpInvocation.CreateContext` 丢弃 `xihan.tenant` 与 `xihan.principal`，不报错，与未登记的键同样处理。HTTP、gRPC（元数据就是 HTTP/2 头）、MCP 的 Streamable HTTP 传输、绕过管道的端点（SignalR Hub）都经它，一处改全部生效。
2. `xihan.correlation`、`xihan.idempotency-key`、`xihan.locale` 照收：它们不决定访问范围。
3. `BaggageTenantResolver` 留着。进程内建上下文时放进去的 Baggage 不受影响：消息派发、作业、工作流、发件箱、命令行宿主的 `--tenant`、MCP stdio 的 `--tenant`。这些值是框架自己或本机操作者给的。
4. 网络调用方的租户只来自认证：令牌或 ApiKey 的租户声明。要按主机名或请求头选租户的应用，登记自己的 `ITenantResolver`，由它决定信什么、核对什么。框架不提供通用的头映射，它正是这次要去掉的东西。
5. `ParseBaggage` 与 `FormatBaggage` 不变，它们只管格式。

## 备选

1. **保留入站，中间件核对成员关系**：框架不知道「成员」是什么，那是应用的模型。否决。
2. **加配置项允许信任内部网关转发的 Baggage**：现在没有使用者，配错就是越权。否决，有需要时应用用自己的解析器读网关的头。
3. **只丢 `xihan.tenant`**：`xihan.principal` 进审计同样不该由调用方决定。否决。
4. **带了这两个键就拒绝请求**：W3C `baggage` 头可能由链路上的代理传递，拒绝会误伤。丢弃与未登记的键一致。否决。

## 影响

这是对外行为变化。

- 靠 `baggage: xihan.tenant=<id>` 选租户的 HTTP、gRPC、MCP 调用方，租户变成解析不到：请求按没有租户处理，配了 `DefaultTenant` 用它，配了 `RequireTenant` 返回 `MULTITENANCY_VALIDATION_002`。迁移：令牌带租户声明，或应用登记自己的 `ITenantResolver`。
- 框架内没有转发路径依赖它：`FormatBaggage` 只有测试在用，插件通道走插件元数据（`PluginMetadata`），不经 `HttpInvocation`。
- 公开 API 不变。

### 没有动的

- **CloudEvents 入站的 `xihantenant`、`xihanprincipal`**：事件自身的上下文来自扩展属性，派发时进 Baggage。这是这个协议的设计，发送方是服务，由端点的权限把关。但它和这次的问题同类：能调入站端点的人能选租户。框架的端点缺省不要求权限，应用要自己给（BasicApp 要求 `runtime.cloud-events.deliver`）。写进文档，待用户定是否进一步收紧。
- **插件回调元数据里的租户**：主体被覆盖成插件自己的身份，租户沿用元数据。插件是装配时授予的，不是网络调用方。
