# ADR-0096 工作流列表查询下推：定义列表分页与摘要、实例只取顶层与一组关联 ID、标题关键字、按实例列书签

## 状态

已采纳（`spec/rfcs/0021-workflow.md`、`spec/conventions/error-codes.md` 随之修订；扩展 ADR-0077 第三节的待办查询下推）。

## 日期

2026-11-02

## 背景

BasicApp 第三批（N3）接入 5.0 工作流时，对照 4.x 的定义列表、实例列表、审批中心与实例详情，报了五处框架缺口（共享笔记 `n3-batch3-workflow-design.md` 第 9 节 G1–G5）。都是「4.x 有、5.0 没有」，用户拍板在框架补，做法照第二批 N2（ADR-0077 第三节）：过滤、排序、分页与计数下推到存储，内存实现与数据库实现都做，数据库实现在 SQL 里做，一致性套件补用例，分页越界返回 400。本 ADR 每项一节；G5 是文档与描述符的修正，只在第五节简述。

## 一、定义列表：分页、总数、关键字与分类过滤，返回摘要（G1）

### 背景

`IWorkflowDefinitionCatalog.ListAsync(name?, status?)` 没有分页、总数、关键字与分类过滤，返回整份定义（含全部节点、转移与扩展属性）。4.x 的定义列表按关键字（编码、名称）、状态、分类在库里分页（`WorkflowDefinitionQueryService.GetPageAsync`）。不下推，应用只能全取后在内存里筛选分页，每行还带着整份设计文档。

### 备选

1. 维持现状，应用在内存里分页：每次列表都把分区里的全部定义连文档读出来。
2. 只加分页，关键字由应用自己在内存里筛：分页与总数就不准。
3. 目录的列表改成查询对象加分页结果，过滤、排序、分页与计数下推到存储，只返回摘要。

### 决策

取备选 3。

- 目录：`ListAsync(name?, status?)` 改为 `QueryAsync(WorkflowDefinitionQuery) → Result<WorkflowDefinitionPage>`，不留旧方法。`WorkflowDefinitionPage(Items, Total)` 与 `UserTaskPage` 同形，`Items` 是 `WorkflowDefinitionSummary`：`Id`、`Name`、`Version`、`DisplayName`、`Description`、`Category`、`Status`、`TenantId`、`CreatedAt`、`PublishedAt`、`Title`（显示名或名字），不含节点、转移、变量与扩展属性；要整份定义按 ID 调 `FindAsync`。
- `WorkflowDefinitionQuery`：`Keyword`、`Name`、`Category`（精确匹配）、`Status`，同时给出的取交集；名字升序、版本降序；`Skip` ≥ 0、`Limit` 1～`MaxLimit`（1000），缺省 0 与 100。越界不在构造时抛出，`QueryAsync` 返回 `WORKFLOW_VALIDATION_002`（HTTP 400），新消息键 `workflow.definition.query_page_invalid`（参数 `skip`、`limit`、`max`，10 种语言），不进存储、不开事务——与实例查询、待办查询的越界一致（ADR-0082、ADR-0077）。
- 关键字匹配名字、显示名或说明。4.x 只匹配编码与名称；说明是用户拍板时点名要的字段，一并纳入。
- 关键字规则 `WorkflowKeyword`（定义、实例与待办查询共用）：去掉首尾空白，空白视同未给；关键字与被搜文本都先折叠——不变文化的小写，SQL `LIKE` 的 `%`、`_`、`[`、`\` 换成全角的 `％`、`＿`、`［`、`＼`，字段分隔符 U+001F 换成空格——再按序数判断包含，任一字段包含即匹配，不跨字段。
- 存储：`IWorkflowDefinitionStore` 新增 `ListSummariesAsync(tenantId, query)` 与 `CountAsync(tenantId, query)`；`ListAsync(tenantId, name?, status?)` 保留，只给引擎的信号启动找监听信号的已发布定义（整份定义、不分页）。
- 内存实现按 `WorkflowDefinitionQuery.Matches` 在锁内过滤、排序、分页与计数。数据库实现的定义行（平台表与租户表）加两列：`Category`（`varchar(128)`，精确过滤）与 `SearchText`（长文本，名字、显示名、说明各自折叠后以 U+001F 拼成，`WorkflowKeyword.Join`），SQL 里 `SearchText IS NOT NULL AND SearchText` 包含折叠后的关键字；摘要从读回的 `Document` 取，与 `FindAsync` 一致。
- `WorkflowDefinition.Category` 最多 `MaxCategoryLength`（128）个字符，与分类列同宽：超长构造即 `ArgumentException`，`WorkflowJson.DeserializeDefinition` 把它转成 `WORKFLOW_VALIDATION_001`。

### 理由

- 列表页只要摘要：整份定义动辄几十 KB（设计器布局在扩展属性里），分页查询返回整份文档没有用处。
- 关键字在 SQL 里匹配，分页与总数才准；`Contains` 由各 Provider 翻译：SqlSugar 翻译成不转义的 `LIKE '%…%'`（实测 SQLite 上 `t_2` 同时匹配 `budget_2026` 与 `budgetx2026`、`50%` 当通配，SQLite 的 `LIKE` 还不区分 ASCII 大小写），EF Core 翻译成 `instr` / `strpos`（区分大小写、按字面）。两边都存折叠后的文本、关键字也折叠，比较的两边都没有通配字符、都是小写，各 Provider 与内存实现结果一致；代价只是这四个 ASCII 字符与对应全角字符视为相同。不改 Persistence.SqlSugar 对 `Contains` 的翻译：那会改变所有应用实体的查询行为。
- 多字段拼一列：字段各自折叠、以 U+001F 分隔，折叠把 U+001F 换成空格，所以折叠后的关键字不会含分隔符，一次包含判断不会跨过字段边界，与内存实现逐字段判断等价，一列就够。
- 分类列有上限才能精确比较与按需建索引（Oracle 的长文本不能用 `=`）；上限放进模型，内存与数据库实现同一规则，不让超长写入在 PostgreSQL 上整批失败、在 SQLite 上悄悄写进去。

### 影响

- 公开 API（Workflow.Abstractions）：`IWorkflowDefinitionCatalog.ListAsync(WorkflowName?, WorkflowDefinitionStatus?, CancellationToken)` → `QueryAsync(WorkflowDefinitionQuery, CancellationToken)`，返回 `Result<WorkflowDefinitionPage>`；新增 `WorkflowDefinitionQuery`、`WorkflowDefinitionSummary`、`WorkflowDefinitionPage`、`WorkflowKeyword`、`WorkflowDefinition.MaxCategoryLength`、`WorkflowMessages.DefinitionQueryPageInvalid`；`IWorkflowDefinitionStore` 新增两个方法（自写 Provider 要实现）。
- 行为：分类超过 128 字符的定义建不出来（`WORKFLOW_VALIDATION_001`）；分页越界 400。
- 表结构：`WorkflowDefinitionRecord` 与 `PlatformWorkflowDefinitionRecord` 加 `Category varchar(128) NULL`、`SearchText`（长文本）`NULL`，没有新索引（一个分区的定义通常只有几百行，按分区的唯一索引已收窄）。可空列 `InitTables` 能给已有行的表加上（RFC-0005 只限制非空列）；升级前写入的行这两列为空，不被分类与关键字匹配，迁移时从 `Document` 回填：`Category` 取 `category`，`SearchText` = `WorkflowKeyword.Join(name, displayName, description)`。
- 测试：存储套件新增用例 11（关键字三字段、大小写、首尾空白、`%` 与 `_` 按字面、不跨字段、精确过滤、分页与计数、整体替换后按新内容匹配），引擎套件新增用例 33（目录分页越界、摘要与总数、关键字与状态、分类）。

## 二、实例查询：只取顶层、标题关键字、一组关联 ID（G2）

### 背景

`WorkflowInstanceQuery` 没有「只取顶层实例」，也没有标题关键字，`CorrelationId` 只能给一个。子流程继承父实例的 `StarterId` 与 `CorrelationId`（`SubWorkflowActivity.Start`），所以审批中心的「我发起的」会混进子流程，只能在内存里滤掉、分页因此不准；4.x 的实例列表与「我发起的」按名称关键字搜索；授权申请列表每行要显示审批进度，一页 N 个单据就要 N 次查询。

### 备选

1. 应用自己在内存里滤子流程、逐个单据查进度：分页不准，一页 500 行就是 500 次查询。
2. 保留单个 `CorrelationId`，另加 `CorrelationIds`（与 `Status` / `Statuses` 并存）：两个字段表达同一件事，违反「不做双轨」。
3. `CorrelationId` 换成集合 `CorrelationIds`（单个是集合的特例，批量优先），加 `TopLevelOnly` 与 `Keyword`，都下推到存储。

### 决策

取备选 3。

- `CorrelationIds`（`IReadOnlyList<string>?`）取代 `CorrelationId`：实例的关联 ID 是其中之一即匹配；`null` 不过滤；**空集合不匹配任何实例**（`ListInstancesAsync` 返回空列表、`CountInstancesAsync` 返回 0，不进存储；存储收到空集合同样不匹配）；重复的只算一个。最多 `WorkflowInstanceQuery.MaxCorrelationIds`（1000）个、不能有空白的 ID，否则两个方法都返回 `WORKFLOW_VALIDATION_002`（HTTP 400），新消息键 `workflow.instance.query_correlations_invalid`（参数 `count`、`max`，10 种语言），不进存储。
- `TopLevelOnly`（`bool`）：只取 `ParentInstanceId` 为空的实例；与 `ParentInstanceId` 同时给出时取交集（结果为空）。
- `Keyword`：匹配实例标题 `WorkflowInstance.Title`，规则同第一节的 `WorkflowKeyword`。实例标题本来就有：启动请求的 `DisplayName`，没给取定义的显示名（引擎 `StartAsync`），`Title` 在两者都没有时取定义名；4.x 的实例名称同样是发起时给出。不新增「由定义模板生成标题」的能力：4.x 也没有，发起方（BasicApp 的审批业务服务）自己拼标题。
- 内存实现按 `WorkflowInstanceQuery.Matches`。数据库实现的实例行加 `SearchTitle`（长文本，`WorkflowKeyword.Fold(instance.Title)`），关联 ID 集合是 `IN`，只取顶层是 `ParentInstanceId IS NULL`；实例表加索引 `(TenantId, StarterId, CreatedAt)`，平台表 `(StarterId, CreatedAt)`。
- 引擎内部按关联 ID 查重（`ReusePolicy`）改用单元素集合，行为不变。

### 理由

- 空集合不匹配：关联 ID 是要找的业务键，空集合就是一个都不找。`Statuses` 的「空集合视同未限定」是范围限定，照搬到业务键上，一页没有单据时会把分区里的全部实例当成进度查出来。
- 上限 1000 与一页的上限、仓储按 ID 批量查的批大小一致，数据库实现一个 `IN` 就够（Oracle 的 `IN` 列表上限也是 1000）。
- 「我发起的」按发起人倒序分页是审批中心的常用查询，现有的 `(TenantId, CreatedAt)` 要按租户扫完再按发起人过滤；4.x 有同样的 `(TenantId, StarterId, CreationTime)` 索引。

### 影响

- 公开 API：`WorkflowInstanceQuery.CorrelationId` 删除，新增 `CorrelationIds`、`TopLevelOnly`、`Keyword`、`MaxCorrelationIds`；`WorkflowMessages.InstanceQueryCorrelationsInvalid`。自写 Provider 的实例存储要实现三个新过滤项。
- 行为：`CountInstancesAsync` 原来不做任何校验，现在关联 ID 集合越界也返回 400（分页仍不看、不校验）。
- 表结构：`WorkflowInstanceRecord` 与 `PlatformWorkflowInstanceRecord` 加 `SearchTitle`（长文本）`NULL`；新索引 `IX_WorkflowInstanceRecord_TeId_StId_CrAt`、`IX_PlatformWorkflowInstanceRecord_StId_CrAt`（`InitTables` 只建不删，对已有表照常补建）。升级前写入的行 `SearchTitle` 为空、不被标题关键字匹配，迁移时回填 `WorkflowKeyword.Fold(title)`：`title` 取 `Document` 的 `displayName`，为空取 `definitionName`。
- 测试：存储套件用例 3 加关联 ID 集合（重复、不存在、空集合）、只取顶层、标题关键字（`%`、`_` 按字面）；引擎套件新增用例 34（真实子流程继承发起人与关联 ID、只取顶层、一组关联 ID、标题来自启动请求或定义、上限与空白的越界、恰好上限、空集合）。

## 三、待办查询的标题关键字（G3）

### 背景

`UserTaskQuery` 没有关键字。4.x 的待办在内存里按任务标题、实例名称、定义编码、关联 ID 筛选（`WorkflowTodoQueryService`）。BasicApp 的待办列表要搜索框，又不能退回全取后在内存里筛（分页与总数就不准，ADR-0077 第三节刚把待办分页下推）。

### 备选

1. 只匹配任务标题：任务标题缺省是节点名（「主管审批」），按流程名（「费用报销」）搜不到。
2. 匹配任务标题与实例标题：书签行要带所属实例的标题，存储维护。
3. 再加定义名与关联 ID：定义名已有精确过滤，关联 ID 是业务键、应按集合精确查（第二节），放进关键字只会让「标题关键字」变成什么都搜。

### 决策

取备选 2。

- `UserTaskQuery.Keyword`：任务标题或所属实例的标题任一包含即匹配，规则同第一节的 `WorkflowKeyword`。任务标题的来源：`UserTask` 活动渲染节点的 `Title` 模板（缺省节点显示名），写进每个用户任务书签的载荷 `title`，转办与加签新建的书签照抄（`UserTask.Title` 就从这里读）；实例标题同第二节。
- 内存实现：书签存储筛出候选后问实例存储运行中的实例（`RunningDefinitions` 带回定义名与标题），在那里匹配，两把锁仍不嵌套。
- 数据库实现：书签行加两列（平台表与租户表）：`SearchTitle`（载荷 `title` 折叠后的值，写书签时算出）与 `SearchInstanceTitle`（所属实例行的 `SearchTitle`）。后者与 ADR-0077 第三节的定义名、实例状态同一路径维护：写书签时按 ID 批量取回实例行填入；实例新增，或状态、定义名、标题查询列变了，实例存储把它同步到书签行，都在同一事务里。SQL 条件是两列各自判非空后做包含判断、取或。

### 理由

- 待办列表同时显示任务标题与流程标题，用户按任一处看到的字搜索都应命中；两列各自判断，与内存实现逐字段判断等价，不跨字段。
- 实例标题在启动后不变（引擎没有改显示名的操作），同步路径只在实例新增时真正写书签行；仍把它纳入比较，标题以后可改时不会悄悄失效。

### 影响

- 公开 API：`UserTaskQuery.Keyword`；数据库实现的 `WorkflowBookmarkRow.SearchTitle`、`SearchInstanceTitle`。自写 Provider 的书签存储要实现关键字条件。
- 表结构：`WorkflowBookmarkRecord` 与 `PlatformWorkflowBookmarkRecord` 加 `SearchTitle`、`SearchInstanceTitle`（长文本）`NULL`，没有新索引（待办查询已按受理人或实例收窄）。升级前写入的行要回填：`SearchTitle` = `WorkflowKeyword.Fold(Document.payload.title)`（没有标题为空），`SearchInstanceTitle` = 所属实例行回填后的 `SearchTitle`；没回填的行不被关键字匹配。
- 测试：存储套件用例 10 加任务标题与实例标题（显示名、定义名）的关键字、`%` 与 `_` 按字面、不跨字段、实例标题变了随之同步；任务套件用例 5 加引擎上的关键字（`Title` 模板渲染的任务标题、启动时给的显示名、没给时的定义名）。

## 六、一致性套件在代理一侧记录事件（G6，缺陷）

### 背景

BasicApp 在自己的完整宿主上跑 `WorkflowEngineConformance` / `WorkflowTaskConformance`（Full 画像 + SqlSugar + `DatabaseWorkflowFeature` + `OutboxFeature` + 全部能力包），SQLite 与 PostgreSQL 上都是 40 例里 13 例失败，全是「事件列表为空」（共享笔记 `n3-batch3-framework-findings.md`）。根因：套件在 `Register` 里把记录器 `ConformanceLog` 登记成 `IMessagePublisher`，`OutboxFeature.Configure` 以 `Replace` 把它换成 `OutboxPublisher`，引擎的事件进了发件箱，套件看不到。框架自己的测试宿主没装发件箱，所以一直没暴露；在框架宿主上加装内存持久化 / SQLite、内存消息与发件箱复现了同样的 13 例（内存实现另多 1 例，见下文）。

### 备选

1. 让宿主装配完成之后再换发布者：内核没有「全部特性配置之后」的登记钩子，`TestHost` 与应用宿主的回调都在特性之前。
2. 套件订阅工作流主题（`IMessageHandler`）：要求每个 Provider 的测试宿主装消息 Provider；投递是异步的，事件断言要轮询等待；发件箱的投递循环按 `TimeProvider` 计时，注入手动时钟的用例里它不醒。
3. 在代理一侧记录：记录器登记成 `IMessageBroker`，装了发件箱时由夹具在每次操作之后把已提交的事件投递给它。

### 决策

取备选 3。

- `ConformanceLog` 改为实现 `IMessageBroker`（原来实现 `IMessagePublisher`）：`PublishAsync` / `PublishManyAsync` 记录，同一信封按 ID 只记一次（发件箱至少一次投递，后台投递循环与夹具的主动投递可能送达两次）；`StartAsync` / `StopAsync` 什么也不做——只记录、不消费。
- 两个套件的 `Register` 改为 `AddSingleton<IMessageBroker>(log)` 加 `TryAddScoped<IMessagePublisher, DirectPublisher>()`：框架的消息 Provider（内存、RabbitMQ、Kafka）都以 `TryAdd` 登记代理与直接发布者，先登记的记录器不被顶替；没装消息 Provider 的宿主由套件补上直接发布者。
- `WorkflowEngineHost` 新增 `DrainOutboxAsync`：宿主装了发件箱（容器里有 `OutboxDispatcher`）时逐轮 `RunOnceAsync` 直到没有可投递的（至多 100 轮），没装时什么也不做；`InScopeAsync`、`AsTenantAsync` 在操作结束（提交或回滚）之后、`PollAsync` 在轮询之后都调它。
- 记录的时机就是「事件随事务提交」（ADR-0077）的语义：没装发件箱时引擎经直接发布者立即发出（可能早于提交，与真实宿主一样）；装了发件箱时只有提交的事件会被投递，回滚的从没进过发件箱。用例 27（业务回滚）在装了发件箱的宿主上加断言：回滚的调用的 `workflow.instance.started` 不送达，提交的送达。
- 用例 30（只读调用）改为自己开只读调用、看调用本身的结果：不加入事务的 Provider（内存实现）启动成功，宿主装了发件箱时它的事件写进只读工作单元被拒，调用以 `PERSISTENCE_UNEXPECTED_001` 结束（只读调用里写入是缺陷，ADR-0081）——这就是内存实现在发件箱宿主上多出的那 1 例，原用例经夹具断言调用成功，在这个组合上不成立。
- 框架补上回归：`Workflow.InMemory.Tests`（内存持久化 + 内存消息 + 发件箱）与 `Workflow.Database.Tests`（SQLite + 内存消息 + 发件箱）各加引擎与任务两个套件的「装了发件箱」版本。修改之前它们分别失败 14 例与 13 例，之后全过。

### 理由

- 代理一侧是事件真正离开事务的地方：观察点放在这里，记录的就是应用的订阅者会收到的，回滚语义自然成立，不依赖登记顺序之外的任何约定。
- 夹具主动投递让用例保持同步断言，不引入轮询等待，也不受手动时钟影响；发件箱自己的投递循环照常运行，重复送达由按 ID 去重吸收。
- 只记录、不消费：套件跑在应用宿主上时，应用别的消息订阅收不到消息，这对一致性测试无害，README 写明。

### 影响

- 公开 API（Workflow.Conformance）：`ConformanceLog` 不再实现 `IMessagePublisher`，改为实现 `IMessageBroker`（新增 `StartAsync`、`StopAsync`）；`WorkflowEngineHost` 新增 `DrainOutboxAsync(CancellationToken)`，`PollAsync` 之后会投递发件箱。
- 自写宿主跑套件（BasicApp 的 `BasicAppTestServer`）：不需要改装配，装着发件箱即可；要求消息 Provider 以 `TryAdd` 登记 `IMessageBroker`（框架的都是），并经夹具的 `InScopeAsync` / `AsTenantAsync` / `PollAsync` 操作。自己在夹具之外操作引擎后读事件，先调 `DrainOutboxAsync`。
- 测试：两个测试项目新增 4 个测试类（引擎 34 + 任务 8 例各跑一遍）；`Workflow.InMemory.Tests` 引用 `Messaging.InMemory` 与 `Persistence.InMemory`，`Workflow.Database.Tests` 引用 `Messaging.InMemory`。
