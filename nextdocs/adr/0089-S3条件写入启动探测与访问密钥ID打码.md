# ADR-0089 S3 条件写入启动探测、不覆盖写入并发原子与访问密钥 ID 打码

## 状态

已采纳（`spec/rfcs/0012-objectstorage.md`、`spec/rfcs/0016-packaging.md`、`spec/conventions/error-codes.md`、`spec/rfcs/0014-configuration.md` 随之修订；修订 ADR-0086 第二节，处理 ADR-0086 第一节记下的遗留）。

## 日期

2026-11-01

## 背景

第四批留下的两项待定由用户拍板（全按推荐）：不支持条件写入的 S3 兼容服务要在启动时探测、不支持就明确报错，不静默覆盖；S3 的 `AccessKey` 在选项打印时也打码。来由都是 ADR-0086：选型实测发现 Garage 与 Zenko CloudServer 不认 `If-None-Match: *`，S3 Provider 的"不覆盖写入"在这类服务上只剩先 HEAD 的检查，两个写入方同时写同一个键时后写的静默覆盖先写的；选项打印遮蔽凭据时把访问密钥 ID 当作与用户名同类、照常打印。本 ADR 每项一节，第二节是第一节的一致性用例在文件系统上发现的同类问题。

## S3 在用之前探测服务是否认条件写入

### 背景与实测

S3 Provider 的不覆盖写入（`Overwrite = false`，单次写入与分片上传的完成）先 HEAD、再带 `If-None-Match: *` 写入，原子性完全靠服务端拒绝第二个写入方（412）。服务端不认这个请求头时，请求照常成功，框架无从察觉。

本机 Docker 29.6.2，各服务单节点起在非默认端口，用两种方式核对：其一，curl 8.22 以 SigV4 直接发请求，记原始响应码（探测键 `.xihan/probe/conditional-write`，分片完成的 XML 带 S3 命名空间）；其二，以本 ADR 的实现启动只装 S3 的应用（文件式程序引用本分支的 `ObjectStorage.S3`），并把 `ObjectStorage.S3.Tests` 指向各服务。

Amazon S3 本身没有可用的账号核对，按 AWS 文档它自 2024 年 8 月起对 `PutObject` 与 `CompleteMultipartUpload` 都支持 `If-None-Match: *`，语义与 RustFS、MinIO 的实测一致。

把新加的一致性用例（下一节：8 个写入方同时以 `Overwrite = false` 写同一个新键）对直接构造的 `S3BlobStore`（不经探测）跑：RustFS 与 MinIO 恰好 1 个成功；**Zenko CloudServer 与 Garage 上 8 个全部"成功"**，即 7 次静默覆盖。这就是要拦下的情形。

### 备选

- **探测键怎么写**：
  - 每次用一个随机键写两次再删除：多实例并发互不干扰，但凭据要有删除权限；进程在写与删之间退出、或没有删除权限时，每次启动留下一个对象，无界累积。
  - 固定键写两次再删除：删除与另一个实例的探测交错时，后者的第二次写入会成功（键刚被删），误判为"不认"。
  - **固定键写入后不删除（选中）**：任何一次 412 都证明服务认条件写入；键已存在时第一次写入就被拒，所以并发启动、反复启动都得到同一结论，没有删除引起的竞态；凭据只需写这一个键；残留只有这一个空对象，有界。
- **探什么**：只探单次写入，或**连分片上传的完成一起探（选中，提供分片上传时）**。框架的分片不覆盖完成同样靠 `If-None-Match: *`，单次写入认、完成不认的服务会让分片上传静默覆盖；多出的 4 个请求（发起、上传一片、完成、放弃）只在启动或建实例时发生。
- **何时探**：
  - 第一次不覆盖写入时再探：不是用户定的"启动时"，失败推迟到运行中，且第一次写入多出几次往返。
  - 健康项周期探：每 15 秒写一次存储，不合适；服务的能力不会在运行中改变。
  - **缺省实例启动时、命名实例建出时各探一次（选中）**。
- **探测写在哪个桶**：新加一个 `ProbeBucket`，或**沿用 `HealthBucket`（选中）**——它本来就是"框架探测用的桶"，健康项对它 HEAD，应用通常配成自己写入的桶；一个键少一处配置。没配时：列桶挑一个（往不相干的桶里写，还要列桶权限）、跳过并记警告（就是静默兜底）都不可取，**条件写入开启时必须配置，没配是配置错误（选中）**。
- **连不上时**：降级运行、之后再探，或**启动失败（选中）**。没探过就无从确认，运行中的不覆盖写入可能落到不认条件写入的服务上；与 Redis 连不上即启动失败一致，编排器会重启。
- **显式关闭**：不提供，或**提供 `ConditionalWrites = false`（选中），只给明确不需要不覆盖写入的应用**（只做覆盖写入、凭据只读），关闭后 `Overwrite = false` 的写入一律失败，不退回"先查再写"。

### 决策

- `S3ObjectStorageOptions` 新增 `ConditionalWrites`（`bool`，缺省 `true`；配置节 `XiHan:ObjectStorage:S3:ConditionalWrites`，命名实例的设置键同名）。`HealthBucket` 的含义改为"框架探测用的桶"：健康项对它 HEAD；`ConditionalWrites` 开启时必须配置，没配时缺省实例装配失败（`ArgumentException`，消息给出两个键名），命名实例 → `OBJECTSTORAGE_VALIDATION_003`。
- 探测（内部 `S3ConditionalWriteProbe`）：在 `HealthBucket` 里对 `.xihan/probe/conditional-write`（空对象）带 `If-None-Match: *` 写入；成功则再写一次，第二次必须 412。提供分片上传时（缺省实例被选为 `objectstorage.multipart`；命名实例总是提供）再以同一个键发起分片上传、上传 1 字节的一片、带 `If-None-Match: *` 完成，必须 412，随即放弃该上传（服务已清掉时不算错；中途出错时尽力放弃，再报原来的错误）。探测键写入后不删除。`EnsureBuckets` 开启时探测桶不存在就建桶后重试一次。单次探测以 `HealthProbeInterval` 为超时（按注入的 `TimeProvider` 计时），调用方的取消原样抛出。
- 时机：`S3ObjectStorageFeature.StartAsync` 在健康探针启动之前探一次；`S3BlobStoreProvider.CreateAsync` 在建出命名实例之前探一次，不通过时释放客户端、抛出携带错误码的 `FrameworkException`。注册表 `BlobStores.GetOrAddAsync` 新增一条翻译：Provider 建实例时抛出的 `FrameworkException` 原样转成同码的失败结果（`ToError()`），不登记实例，下次取用重新探测。经公开构造函数直接建的 `S3BlobStore` 不探测，由调用方负责。
- 失败原因分开：服务不认（第二次写入或完成没被拒，或回 501）→ 新错误码 `OBJECTSTORAGE_UNAVAILABLE_003`（消息键 `objectstorage.conditional_write.unsupported`，参数 `bucket`、`operation`）；被拒绝（403：密钥错、凭据只读、无权写探测键、建桶或放弃上传）→ 新错误码 `OBJECTSTORAGE_DENIED_002`（`objectstorage.conditional_write.probe_denied`，参数 `bucket`、`key`、`operation`、`reason`）；探测桶不存在 → 复用 `OBJECTSTORAGE_NOTFOUND_001`（`objectstorage.conditional_write.probe_bucket_missing`，参数 `bucket`）；连不上、超时或其余服务端错误 → 复用 `OBJECTSTORAGE_UNAVAILABLE_001`（`reason` 带出是哪一步）。缺省实例以 `KERNEL_HOSTING_002` 启动失败，内层错误是上述之一。
- `ConditionalWrites = false`：不探测，`HealthBucket` 可以不配（健康项照旧列桶）；`S3BlobStore` 对 `Overwrite = false` 的写入、分片上传的发起与完成一律返回 `OBJECTSTORAGE_UNAVAILABLE_003`（消息键 `objectstorage.conditional_write.disabled`，参数 `container`、`key`），不访问存储；覆盖写入、读取、删除、列举、预签名不受影响。
- 新消息键 4 个，10 种语言都已补齐，挂在 `ObjectStorage.Abstractions` 的目录里（错误码属于对象存储领域，S3 包本身没有目录）。

### 理由

- 用户定的是"启动时探测、明确报错、不静默覆盖"：探测放在启动与建实例这两个"开始用之前"的点，失败即不开始用；关闭条件写入也不退回先查再写，所以任何配置下都不会出现没有保证的不覆盖写入。
- 固定键不删除是唯一既无竞态、又只要最小权限、残留又有界的写法（见备选）。代价是探测桶里多一个空对象，它符合键文法，按空前缀列举该桶会看到；放在框架专用前缀 `.xihan/` 下，可以单独授权，文档写明。
- 区分四种失败原因是因为处置完全不同：不认要换服务或关闭，被拒要改权限，缺桶要建桶，连不上要查网络。复用 `NOTFOUND_001` 与 `UNAVAILABLE_001` 是因为 S3 Provider 本来就把缺桶与连不上映射到它们；不认条件写入与"探测被拒绝"是新情形，各给一个码。
- 注册表翻译 `FrameworkException` 而不是新增异常类型：原语层已有携带错误码的异常与 `ToError()`，Provider 契约只是多写明一种失败；文件系统 Provider 不受影响。
- 一致性套件新增并发用例而不是只在 S3 包里测：原子性是 RFC-0012 契约的一部分，每个 Provider 都要满足；这条用例在 Garage、Zenko CloudServer 上失败，正是本探测要拦的情形（下一节它还发现了文件系统的同类问题）。

### 影响

- 启动期新增失败：装配 `S3ObjectStorageFeature` 且它提供缺省实例时，① 没配 `XiHan:ObjectStorage:S3:HealthBucket` 而 `ConditionalWrites` 没关 → 装配失败（`ArgumentException`）；② 服务不认条件写入 → `KERNEL_HOSTING_002` / `OBJECTSTORAGE_UNAVAILABLE_003`；③ 凭据无效、只读或无权写探测键（或无权放弃分片上传）→ `OBJECTSTORAGE_DENIED_002`；④ 探测桶不存在且没开 `EnsureBuckets` → `OBJECTSTORAGE_NOTFOUND_001`；⑤ 启动时连不上 S3 → `OBJECTSTORAGE_UNAVAILABLE_001`（以前照常启动、健康项 Degraded）。命名实例的建出同样会因这些原因失败（注册表返回对应错误码，配置定义的实例在首次取用时）。
- 行为：命名实例建出时会访问存储（以前不发请求），在注册表的串行门内，单次最长 `HealthProbeInterval`（缺省 15 秒）。启动多 2 到 6 个请求。探测桶里多一个空对象 `.xihan/probe/conditional-write`。失败策略设为 `IsolateFeature` 时探测失败按内核规则隔离 S3 特性（`Failed`，应用不就绪），不是降级放行。
- 公开 API（Unshipped）：`S3ObjectStorageOptions.ConditionalWrites`；`ObjectStorageErrors.ConditionalWriteUnavailable`、`ProbeDenied`；`ObjectStorageMessages.ConditionalWriteUnsupported`、`ConditionalWriteDisabled`、`ConditionalWriteProbeDenied`、`ConditionalWriteProbeBucketMissing`；一致性套件的 `BlobStoreConformance.Put_WithoutOverwrite_IsAtomicUnderConcurrentWriters`。`IBlobStoreProvider.CreateAsync` 的文档多一种失败（`FrameworkException`），签名不变。
- 配置键：新增 `XiHan:ObjectStorage:S3:ConditionalWrites`（CLI 知识库同步）；`HealthBucket` 在条件写入开启时变为必填。
- 迁移：用 S3 的应用加 `"HealthBucket": "<应用写入的桶>"`（`xihan pack` 起的 RustFS 不自动建桶，同时开 `EnsureBuckets` 或先建桶），给凭据开 `<桶>/.xihan/probe/*` 的写入与放弃分片上传权限；只读或只做覆盖写入的应用改设 `"ConditionalWrites": false`。
- 测试：`ObjectStorage.S3.Tests` 新增内存替身 `FakeS3Client`（`DispatchProxy` 实现 `IAmazonS3`）覆盖判定、四种失败、超时（`FakeTimeProvider`）、取消、并发、关闭条件写入与命名实例；对真实服务的门控用例在 `XIHAN_TEST_S3`（RustFS）上核对缺省与命名实例通过、4 个实例并发启动通过、密钥错即被拒，在新环境变量 `XIHAN_TEST_S3_UNCONDITIONAL`（如 Zenko CloudServer）上核对启动与命名实例都以 `OBJECTSTORAGE_UNAVAILABLE_003` 失败。

## 不覆盖写入并发原子：一致性用例与文件系统的原子占位

### 背景

上一节加的一致性用例（8 个写入方同时以 `Overwrite = false` 写同一个新键，恰好一个成功、其余 `OBJECTSTORAGE_CONFLICT_001`、内容是成功者写的）在默认实现 `ObjectStorage.FileSystem` 上也失败了：改动前一次运行有 2 个写入方成功（`[3, 4]`）。文件系统先读元数据判断是否存在，再把临时文件以替换方式移到内容路径，两步之间没有任何互斥，单进程里就会静默覆盖。

### 决策

- `FileSystemBlobStore.CommitAsync`（写入与分片上传的完成共用）按是否覆盖分开：覆盖时照旧以替换方式移动；不覆盖时以不替换的移动（`File.Move(..., overwrite: false)`）原子占位，目标已存在即返回 `OBJECTSTORAGE_CONFLICT_001`，不写元数据、不计用量。不覆盖的分片完成被抢先时上传保留（与先查到已存在时相同）。
- RFC-0012 契约写明：不覆盖写入必须原子，多个写入方同时写同一个新键恰好一个成功，不能先查再写；一致性套件新增上述用例。

### 理由

- 不替换的移动由文件系统原子判定（Windows 的 `MoveFileEx` 不带替换标志；Unix 上 .NET 以硬链接 `link` 占位，目标存在即失败——不支持硬链接的文件系统上 .NET 退回先查再改名，不保证原子），对共享目录的多个进程同样成立，不需要进程内的锁。
- 先查元数据的快速路径保留：已存在时不必复制内容；占位失败只发生在并发竞争的窗口里。

### 影响

- 行为：文件系统存储上并发的不覆盖写入只有一个成功，其余 `OBJECTSTORAGE_CONFLICT_001`（以前可能都成功、后写的覆盖先写的）。内容文件在、元数据缺失的残留（写入中途进程退出）上，不覆盖写入也返回 `OBJECTSTORAGE_CONFLICT_001`，覆盖写入照常修复它。
- 公开 API、错误码、配置键不变；`CommitAsync` 是内部方法。
- 改动后文件系统的测试连跑 5 次全部通过（33 / 33）。

## S3 的访问密钥 ID 也打码（修订 ADR-0086 第二节）

### 背景

ADR-0086 第二节给选项记录手写 `PrintMembers`，凭据打印为 `***`，但把 S3 的访问密钥 ID（`AccessKey`）判为非凭据、照常打印，理由是它与用户名同类、随每个请求明文发送。用户拍板改为也打码，与 `Redaction` 的做法一致。

### 同类字段的核对

逐个看了全部正式包里的公开记录（架构测试扫描的范围）与选项类：与 `AccessKey` 同性质、即"服务商发给调用方的一对访问密钥中的标识那一半"的字段，只有 `S3ObjectStorageOptions.AccessKey`。其余看似相近的都不是：`RedisCachingOptions.User`、`RabbitMQMessagingOptions.UserName`、`NacosOptions.Username` 是用户名；`PrincipalRecord.Id` 是主体标识（它的 `ApiKey` 早已遮蔽）；`JwtOptions` 与 `OpenIdConnectOptions` 的 `Issuer` / `Audience` 本来公开、令牌里明文携带；Kafka 的 `sasl.username` 在 `Properties` 字典里，记录只打印字典的类型名；命名实例的 `BlobStoreDefinition.Settings`（含 `AccessKey`）同样是字典，只打印类型名。CLI 的 `BindingKind.BlobAccessKey` 是内部常量（`xihan pack` 生成物里的本地联调凭据），不经 `ToString`。

### 决策

- `S3ObjectStorageOptions.PrintMembers` 把 `AccessKey` 经 `Redaction.Redact` 打印（`null` 仍为空），与 `SecretKey` 相同。
- 凭据的判定加入访问密钥 ID：RFC-0014「选项里的凭据」规则 1 的属性名后缀加入 `AccessKey`、`AccessKeyId`，规则 2 去掉 `AccessKey`；架构测试 `CredentialRedactionTests` 的属性名正则同步加入这两个后缀（只改测试不改记录时，它对 `S3ObjectStorageOptions` 报"明文打印凭据"与"必须打印 `AccessKey = ***`"两条失败）。
- 用户名、端点、令牌文件路径、分页游标仍照常打印，不扩大到它们。

### 理由

- 访问密钥 ID 不是公开的身份名：它由服务商签发、与密钥成对使用，单独泄漏也有代价——AWS 可以凭它查出所属账号（`sts:GetAccessKeyInfo`），密钥扫描工具把 `AKIA` 开头的 ID 当作泄漏上报；不少兼容服务的根凭据缺省两半相同（RustFS 的 `rustfsadmin` / `rustfsadmin`），打印 ID 就等于打印了密钥。
- 用户名不改：它是运维人员起的身份名，服务端自己的日志与认证错误里都会出现，排查"连的是哪个用户"最常用；口令本身已经遮蔽。
- 排查"用了哪把密钥"仍可做：遮蔽只影响 `ToString()`，选项对象的属性值不变，应用需要时可以自行输出 ID 的前几位。

### 影响

- 行为：`S3ObjectStorageOptions.ToString()` 里 `AccessKey = ***`（以前是明文，`null` 仍为空），其余不变；依赖这段文本的代码要更新（框架内没有）。
- 公开 API、错误码、消息键、配置键都不变；以后新加的带访问密钥 ID 的公开记录（属性名以 `AccessKey` / `AccessKeyId` 结尾）必须同样遮蔽，否则架构测试失败。
