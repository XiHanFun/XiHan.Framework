# ADR-0084 命名连接与工作流租约表、分页越界返回 400 与关系库实测

## 状态

已采纳（`spec/rfcs/0005-persistence.md`、`spec/rfcs/0021-workflow.md`、`spec/conventions/error-codes.md` 随之修订）。

## 日期

2026-11-01

## 背景

第二批与第三批收口时分区提出了几处待定（`f-round-summary.md` 第 5 节、`g-round-summary.md` 第 5、6 节），用户逐条拍板，全按推荐。本 ADR 记数据相关的几项，每项一节。

## 一、实体登记到命名连接、绑定连接的工作单元，工作流租约表可指定连接

### 背景

- 工作流的租约行不随业务事务（ADR-0077）：引擎在调用方事务里写过实例与书签之后，再在自己的作用域与工作单元里写租约行，立即提交、别的节点立刻看得见。
- SQLite 只有一个写者（库级写锁，Microsoft.Data.Sqlite 的事务是 `BEGIN IMMEDIATE`）。租约行与业务在同一个库文件时，租约步骤的事务要等调用方事务结束——等的正是自己，忙等超时后以 `WORKFLOW_TIMEOUT_001` 失败。
- 第二批的数据库测试靠手写绕过：自己注册客户端，调用里的作用域只连业务库、调用之外的作用域只连租约库，再自定义 `IEntityConnectionSelector` 把 `WorkflowLockRecord` 放到租约库。这套写法依赖「调用之外的作用域只有租约步骤」，换成真实应用（发件箱、调度、审计等后台组件同样在调用之外开作用域）就不成立；BasicApp 用方式一（特性按回调建客户端），也没法照抄。用户拍板：框架提供现成选项，给租约表指定连接名。
- 实测 SqlSugar 5.1.4.221 的多连接事务：`AsTenant().BeginTran()` 只在根连接与已经取用过的连接上开事务、之后首次取用的连接再补开；`GetConnection(name).Ado.BeginTran()` 只锁那一个库；`AsTenant().CommitTran()` 也提交单独开在子连接上的事务。所以只要租约步骤的事务不经 `AsTenant()`，业务调用又不碰租约库，两边就互不等待。

### 备选

1. 只在 Workflow.Database 里加一个「租约连接串」，由它自己建客户端。Workflow.Database 只依赖持久化契约、不认识 SqlSugar，做不到；而且绕开了仓储与工作单元。
2. 只做实体落点（登记时指定连接）。普通工作单元首次写入经 `AsTenant()` 开事务，根连接（业务库）总会被开事务——租约步骤照样去等业务库的写锁。
3. 只做绑定连接的工作单元。租约步骤不再锁业务库，但 `InitTables` 不知道租约表该建在哪个库，启动时也核对不了连接是否存在。
4. 改 SqlSugar 工作单元，事务一律只开在实际写入的连接上。能解决问题，但改变了所有多连接应用（默认 + 分片）的事务语义，不配置时行为也会变。
5. 2 与 3 都做：实体登记到命名连接（表在哪个库），工作单元可以绑定一个连接（事务只在哪个库）；Workflow.Database 的一个选项同时用上两者。

### 决策

取备选 5。

- `Persistence.Abstractions`：
  - `AddRepository<TEntity, TKey>(connection)`、`RepositoryRegistrations.Add<TEntity, TKey>(connection)`：把实体登记到命名连接（`null` 是 Provider 的缺省落点，非空不能是空白）。`RepositoryRegistrations.ConnectionOf(type)`、`RegisteredEntity.Connection` 取它。同一实体再次登记到另一个连接（含一次为空、一次非空）抛 `ArgumentException`。
  - `UnitOfWorkOptions(TenantId, IsReadOnly, Connection)`：`Connection` 非空时工作单元只在这个连接上读写——实体必须落在它上面，否则 `PERSISTENCE_VALIDATION_004`；事务只开在它上面。
- `Persistence.SqlSugar`：
  - 命名连接是客户端里同名 `ConfigId` 的连接。缺省落点规则改为 `[Tenant]` → 登记的连接 → `IMultiTenant` 且有 `shard` 时 `shard` → 默认连接；`SqlSugarConnectionSelector` 的构造收 `RepositoryRegistrations`。`[Tenant]` 与登记的连接不同、登记的连接不在客户端里，都是 `PERSISTENCE_VALIDATION_004`，缺省落点规则下启动时校验（`shard` 除外）。
  - 方式一在 `XiHan:Persistence:SqlSugar:Connections:<name>` 声明命名连接（值是连接串，名字合 `^[a-z0-9][a-z0-9-]{0,63}$`，不能是 `default` 或 `shard`）：每个作用域的客户端都带上它们，排在默认连接之后；回调对每个各调用一次，绑定的主值是该连接串、属性沿用 `db` 绑定，`config.ConfigId` 是连接名。不合法、或方式二也写了这一节，装配即抛 `ArgumentException`。
  - `SqlSugarUnitOfWork` 以 `Connection` 开启时取 `GetConnection(name)`，事务在它的 `Ado` 上开、提交、回滚，不经 `AsTenant()`；连接不在客户端里 `BeginAsync` 抛 `PERSISTENCE_VALIDATION_004`。
- EF Core 与内存实现不支持命名连接：登记到命名连接在装配时（`IRepositoryRegistrar.Register`）、绑定连接的工作单元在 `BeginAsync` 抛出携带 `PERSISTENCE_UNAVAILABLE_008` 的 `FrameworkException`。
- `Workflow.Database`：`XiHan:Workflow:Database:LockConnection`（`DatabaseWorkflowOptions.LockConnection`，空白视为未配置）。配置后特性以 `AddRepository<WorkflowLockRecord, string>(LockConnection)` 登记租约表，`LeaseTable` 的每一步与 `PollerLeaseProbe` 开 `UnitOfWorkOptions(Connection: LockConnection)` 的工作单元。不配置时与以前相同。
- 数据库测试的手写客户端与落点规则删掉，改为方式一 + `Connections:leases` + `LockConnection = leases`。

### 理由

- 「表在哪个库」与「这次事务碰哪个库」是两件事：前者是装配时的静态落点（建表、启动核对都要用），后者是一次工作单元的意图（只有租约步骤这类与业务互不等待的写入需要）。拆成两个小契约，各自的语义都简单，Provider 不支持时也各自明确拒绝。
- 不改普通工作单元的事务语义：不配置时所有应用的行为不变；配置后业务调用不碰命名连接，SqlSugar 现有的「只在取用过的连接上开事务」就保证业务事务不锁租约库。
- 方式一能声明命名连接，BasicApp 这类用 `db` 绑定的应用在 SQLite 集成测试里只加两个配置键，不必改成自己注册客户端。回调按 `ConfigId` 区分，库类型等属性沿用 `db` 绑定，与分片连接的做法一致。
- 绑定连接的工作单元遇到落在别处的实体直接报错，不让它悄悄去读不在事务里、也不该碰的库。

### 影响

- 公开 API：`AddRepository` / `RepositoryRegistrations.Add` 多了可选参数 `connection`；新增 `RepositoryRegistrations.ConnectionOf`、`RegisteredEntity.Connection`（构造多了可选参数）、`UnitOfWorkOptions.Connection`（位置参数第三个，`Deconstruct` 随之变化）、`SqlSugarPersistenceOptions.Connections`、`DatabaseWorkflowOptions.LockConnection`；`SqlSugarConnectionSelector()` → `SqlSugarConnectionSelector(RepositoryRegistrations)`。
- 启动期新增失败：`XiHan:Persistence:SqlSugar:Connections` 的名字或值不合法、方式二写了这一节（`ArgumentException`）；登记的命名连接不在 SqlSugar 客户端里、与 `[Tenant]` 不一致（`PERSISTENCE_VALIDATION_004`）；EF Core 或内存持久化上配了 `LockConnection` 或把实体登记到命名连接（`PERSISTENCE_UNAVAILABLE_008`）。都只在用到新选项时出现。
- 表结构：配了 `LockConnection` 时 `WorkflowLockRecord` 建在那个连接（`InitTables`）；生产库在 PostgreSQL 等行锁数据库上不需要配，租约表照旧在平台库。
- EF Core 在 SQLite 上跑数据库工作流仍会在调用方事务里取锁超时（做不到命名连接），文档写明改用 PostgreSQL 等或 SqlSugar。
- 测试：SqlSugar 在两个 SQLite 文件上验证命名连接的建表与读写、回调看到的 `ConfigId` 与绑定、业务事务占着默认库写锁时绑定连接的工作单元照样提交、落点错误与配置错误；EF Core 与内存实现验证明确拒绝；工作流数据库测试全部改用这个选项（含调用方事务里取锁、结果处理器与实例完成同进退的用例）。

## 二、到期书签轮询在应用不在服务状态时什么也不做（缺陷修复）

### 背景

ADR-0077 起 `DueBookmarkPoller` 每个分区开一次经管道的调用。内存与数据库工作流的特性在自己启动时就起轮询循环、停止时才停：应用启动中（别的特性还没启动完）与排空中（依赖它的特性先停）管道不接受调用，每个周期的扫描与清理都以 `WORKFLOW_UNAVAILABLE_001` 失败、逐个分区记告警。BasicApp 的真实宿主启动一次记 3 条，集成全量一次 476 条；第二批之前扫描不经管道，没有这些告警。

### 决策

`RunCycleAsync` 先看应用状态，不在服务状态（`LifecycleState.IsServing()` 为假）就返回 0：不轮询、不清理（维护时刻不推进，进入服务状态后的第一个周期照常清理）、不记日志，与调度引擎每个周期先看应用状态一致。循环照旧在特性启动时起、停止时停；数据库实现的领导权照旧每个周期先拿或续，不在服务状态时只是不轮询。手动调用的 `PollOnceAsync` 不变（调用方明确要轮询，失败照实告警）。

### 理由

- 应用不在服务状态时轮询本来就做不成，告警只是噪声；把判断放在周期入口，内存与数据库两条循环一处修好。
- 不改循环的启停时机：特性的生命周期钩子拿不到「应用已进入服务状态」的通知，在周期里判断最简单，也与调度引擎同形。
- 不在服务状态时仍续领导权：启动中的节点先拿到领导权、进入服务状态后立即轮询；排空中的节点停止时释放领导权，排空通常只有几秒。

### 影响

- 行为：应用启动与停机期间不再有 `Scanning due workflow bookmarks … failed with 'WORKFLOW_UNAVAILABLE_001'` 与 `Purging ended workflow instances failed …` 告警。公开 API、配置、表结构不变。
- 测试：内存与数据库工作流各一个用例，探针特性排在工作流之后启停，在启动中与排空中各跑一个周期，断言返回 0、没有工作流的告警；先写用例复现了告警，再改实现。
