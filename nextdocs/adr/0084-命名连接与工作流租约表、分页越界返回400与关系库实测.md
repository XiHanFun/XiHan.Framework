# ADR-0084 命名连接与工作流租约表、分页越界返回 400 与关系库实测

## 日期

## 背景

第二批与第三批收口时分区提出了几处待定（`f-round-summary.md` 第 5 节、`g-round-summary.md` 第 5、6 节），用户逐条拍板，全按推荐。本 ADR 记数据相关的几项，每项一节。

## 一、实体登记到命名连接、绑定连接的工作单元，工作流租约表可指定连接

### 背景

- 工作流的租约行不随业务事务（ADR-0077）：引擎在调用方事务里写过实例与书签之后，再在自己的作用域与工作单元里写租约行，立即提交、别的节点立刻看得见。
- SQLite 只有一个写者（库级写锁，Microsoft.Data.Sqlite 的事务是 `BEGIN IMMEDIATE`）。租约行与业务在同一个库文件时，租约步骤的事务要等调用方事务结束——等的正是自己，忙等超时后以 `WORKFLOW_TIMEOUT_001` 失败。
- 第二批的数据库测试靠手写绕过：自己注册客户端，调用里的作用域只连业务库、调用之外的作用域只连租约库，再自定义 `IEntityConnectionSelector` 把 `WorkflowLockRecord` 放到租约库。这套写法依赖「调用之外的作用域只有租约步骤」，换成真实应用（发件箱、调度、审计等后台组件同样在调用之外开作用域）就不成立；BasicApp 用方式一（特性按回调建客户端），也没法照抄。用户拍板：框架提供现成选项，给租约表指定连接名。
- 实测 SqlSugar 5.1.4.221 的多连接事务：`AsTenant().BeginTran()` 只在根连接与已经取用过的连接上开事务、之后首次取用的连接再补开；`GetConnection(name).Ado.BeginTran()` 只锁那一个库；`AsTenant().CommitTran()` 也提交单独开在子连接上的事务。所以只要租约步骤的事务不经 `AsTenant()`，业务调用又不碰租约库，两边就互不等待。

### 备选

1. 只在 Workflow.Database 里加一个「租约连接串」，由它自己建客户端。Workflow.Database 只依赖持久化契约、不认识 SqlSugar，做不到；而且绕开了仓储与工作单元。
2. 只做实体落点（登记时指定连接）。普通工作单元首次写入经 `AsTenant()` 开事务，根连接（业务库）总会被开事务——租约步骤照样去等业务库的写锁。
3. 只做绑定连接的工作单元。租约步骤不再锁业务库，但 `InitTables` 不知道租约表该建在哪个库，启动时也核对不了连接是否存在。
4. 改 SqlSugar 工作单元，事务一律只开在实际写入的连接上。能解决问题，但改变了所有多连接应用（默认 + 分片）的事务语义，不配置时行为也会变。
5. 2 与 3 都做：实体登记到命名连接（表在哪个库），工作单元可以绑定一个连接（事务只在哪个库）；Workflow.Database 的一个选项同时用上两者。

### 决策

取备选 5。

- `Persistence.Abstractions`：
  - `AddRepository<TEntity, TKey>(connection)`、`RepositoryRegistrations.Add<TEntity, TKey>(connection)`：把实体登记到命名连接（`null` 是 Provider 的缺省落点，非空不能是空白）。`RepositoryRegistrations.ConnectionOf(type)`、`RegisteredEntity.Connection` 取它。同一实体再次登记到另一个连接（含一次为空、一次非空）抛 `ArgumentException`。
  - `UnitOfWorkOptions(TenantId, IsReadOnly, Connection)`：`Connection` 非空时工作单元只在这个连接上读写——实体必须落在它上面，否则 `PERSISTENCE_VALIDATION_004`；事务只开在它上面。
- `Persistence.SqlSugar`：
  - 命名连接是客户端里同名 `ConfigId` 的连接。缺省落点规则改为 `[Tenant]` → 登记的连接 → `IMultiTenant` 且有 `shard` 时 `shard` → 默认连接；`SqlSugarConnectionSelector` 的构造收 `RepositoryRegistrations`。`[Tenant]` 与登记的连接不同、登记的连接不在客户端里，都是 `PERSISTENCE_VALIDATION_004`，缺省落点规则下启动时校验（`shard` 除外）。
  - 方式一在 `XiHan:Persistence:SqlSugar:Connections:<name>` 声明命名连接（值是连接串，名字合 `^[a-z0-9][a-z0-9-]{0,63}$`，不能是 `default` 或 `shard`）：每个作用域的客户端都带上它们，排在默认连接之后；回调对每个各调用一次，绑定的主值是该连接串、属性沿用 `db` 绑定，`config.ConfigId` 是连接名。不合法、或方式二也写了这一节，装配即抛 `ArgumentException`。
  - `SqlSugarUnitOfWork` 以 `Connection` 开启时取 `GetConnection(name)`，事务在它的 `Ado` 上开、提交、回滚，不经 `AsTenant()`；连接不在客户端里 `BeginAsync` 抛 `PERSISTENCE_VALIDATION_004`。
- EF Core 与内存实现不支持命名连接：登记到命名连接在装配时（`IRepositoryRegistrar.Register`）、绑定连接的工作单元在 `BeginAsync` 抛出携带 `PERSISTENCE_UNAVAILABLE_008` 的 `FrameworkException`。
- `Workflow.Database`：`XiHan:Workflow:Database:LockConnection`（`DatabaseWorkflowOptions.LockConnection`，空白视为未配置）。配置后特性以 `AddRepository<WorkflowLockRecord, string>(LockConnection)` 登记租约表，`LeaseTable` 的每一步与 `PollerLeaseProbe` 开 `UnitOfWorkOptions(Connection: LockConnection)` 的工作单元。不配置时与以前相同。
- 数据库测试的手写客户端与落点规则删掉，改为方式一 + `Connections:leases` + `LockConnection = leases`。

### 理由

- 「表在哪个库」与「这次事务碰哪个库」是两件事：前者是装配时的静态落点（建表、启动核对都要用），后者是一次工作单元的意图（只有租约步骤这类与业务互不等待的写入需要）。拆成两个小契约，各自的语义都简单，Provider 不支持时也各自明确拒绝。
- 不改普通工作单元的事务语义：不配置时所有应用的行为不变；配置后业务调用不碰命名连接，SqlSugar 现有的「只在取用过的连接上开事务」就保证业务事务不锁租约库。
- 方式一能声明命名连接，BasicApp 这类用 `db` 绑定的应用在 SQLite 集成测试里只加两个配置键，不必改成自己注册客户端。回调按 `ConfigId` 区分，库类型等属性沿用 `db` 绑定，与分片连接的做法一致。
- 绑定连接的工作单元遇到落在别处的实体直接报错，不让它悄悄去读不在事务里、也不该碰的库。

### 影响

- 公开 API：`AddRepository` / `RepositoryRegistrations.Add` 多了可选参数 `connection`；新增 `RepositoryRegistrations.ConnectionOf`、`RegisteredEntity.Connection`（构造多了可选参数）、`UnitOfWorkOptions.Connection`（位置参数第三个，`Deconstruct` 随之变化）、`SqlSugarPersistenceOptions.Connections`、`DatabaseWorkflowOptions.LockConnection`；`SqlSugarConnectionSelector()` → `SqlSugarConnectionSelector(RepositoryRegistrations)`。
- 启动期新增失败：`XiHan:Persistence:SqlSugar:Connections` 的名字或值不合法、方式二写了这一节（`ArgumentException`）；登记的命名连接不在 SqlSugar 客户端里、与 `[Tenant]` 不一致（`PERSISTENCE_VALIDATION_004`）；EF Core 或内存持久化上配了 `LockConnection` 或把实体登记到命名连接（`PERSISTENCE_UNAVAILABLE_008`）。都只在用到新选项时出现。
- 表结构：配了 `LockConnection` 时 `WorkflowLockRecord` 建在那个连接（`InitTables`）；生产库在 PostgreSQL 等行锁数据库上不需要配，租约表照旧在平台库。
- EF Core 在 SQLite 上跑数据库工作流仍会在调用方事务里取锁超时（做不到命名连接），文档写明改用 PostgreSQL 等或 SqlSugar。
- 测试：SqlSugar 在两个 SQLite 文件上验证命名连接的建表与读写、回调看到的 `ConfigId` 与绑定、业务事务占着默认库写锁时绑定连接的工作单元照样提交、落点错误与配置错误；EF Core 与内存实现验证明确拒绝；工作流数据库测试全部改用这个选项（含调用方事务里取锁、结果处理器与实例完成同进退的用例）。

## 二、到期书签轮询在应用不在服务状态时什么也不做（缺陷修复）

### 背景

ADR-0077 起 `DueBookmarkPoller` 每个分区开一次经管道的调用。内存与数据库工作流的特性在自己启动时就起轮询循环、停止时才停：应用启动中（别的特性还没启动完）与排空中（依赖它的特性先停）管道不接受调用，每个周期的扫描与清理都以 `WORKFLOW_UNAVAILABLE_001` 失败、逐个分区记告警。BasicApp 的真实宿主启动一次记 3 条，集成全量一次 476 条；第二批之前扫描不经管道，没有这些告警。

### 决策

`RunCycleAsync` 先看应用状态，不在服务状态（`LifecycleState.IsServing()` 为假）就返回 0：不轮询、不清理（维护时刻不推进，进入服务状态后的第一个周期照常清理）、不记日志，与调度引擎每个周期先看应用状态一致。循环照旧在特性启动时起、停止时停；数据库实现的领导权照旧每个周期先拿或续，不在服务状态时只是不轮询。手动调用的 `PollOnceAsync` 不变（调用方明确要轮询，失败照实告警）。

### 理由

- 应用不在服务状态时轮询本来就做不成，告警只是噪声；把判断放在周期入口，内存与数据库两条循环一处修好。
- 不改循环的启停时机：特性的生命周期钩子拿不到「应用已进入服务状态」的通知，在周期里判断最简单，也与调度引擎同形。
- 不在服务状态时仍续领导权：启动中的节点先拿到领导权、进入服务状态后立即轮询；排空中的节点停止时释放领导权，排空通常只有几秒。

### 影响

- 行为：应用启动与停机期间不再有 `Scanning due workflow bookmarks … failed with 'WORKFLOW_UNAVAILABLE_001'` 与 `Purging ended workflow instances failed …` 告警。公开 API、配置、表结构不变。
- 测试：内存与数据库工作流各一个用例，探针特性排在工作流之后启停，在启动中与排空中各跑一个周期，断言返回 0、没有工作流的告警；先写用例复现了告警，再改实现。

## 三、缓存键列表与库结构表列表的分页越界返回 400

### 背景

ADR-0082 把调度运行查询、工作流实例查询与清理、对象存储列举的分页越界改成由服务返回 400，同类的 `CacheKeyQuery.Limit`（缓存键管理）与 `TableListQuery.Skip`（库结构读取）不在当时点名范围：前者越界在 `init` 里抛 `ArgumentOutOfRangeException`，后者 `Skip` 为负、`Take` 小于 1 同样在 `init` 里抛出——查询经 HTTP 绑定构造时都是 500。用户拍板：照第三批第 10 条改成 400。

### 备选

1. 构造时抛包内异常，由 Transaction 阶段转为 400（`EntityQuery.Take` 的做法，ADR-0073）。缓存键管理不经工作单元，没有阶段可转；读结构在调用外也会用到。
2. 存储 / 读取器返回本领域的校验错误（ADR-0082 的形状）：查询类型给 `Validate()`，Provider 在入口调用。

### 决策

取备选 2。

- 缓存：`CacheKeyQuery.Limit` 不再在 `init` 里抛出；新增 `CacheKeyQuery.Validate()`。`ICacheStoreInspector.ListKeysAsync`、`ICacheInspector.ListKeysAsync` 的返回由 `ValueTask<CacheKeyPage>` 改为 `ValueTask<Result<CacheKeyPage>>`（越界要以结果返回，原签名表达不了）；内存存储、内存对象缓存与 Redis 存储先校验，`Limit` 不在 1～1000 返回新码 `CACHING_VALIDATION_003`（消息键 `caching.inspector.limit_invalid`，参数 `limit`、`max`），不访问后端；基础设施失败照旧抛 `CACHING_UNAVAILABLE_001`。前缀不合法仍在构造时抛 `ArgumentException`（与 `BlobQuery` 一致，前缀文法是键的文法，不是分页）。
- 库结构：`TableListQuery.Skip` / `Take` 都不再在 `init` 里抛出；新增 `TableListQuery.Validate()`。`Skip` 为负或 `Take` 小于 1 返回新码 `PERSISTENCE_VALIDATION_007`（`persistence.schema.list_page_invalid`，参数 `skip`、`take`），`Take` 超过 1000 仍是 `PERSISTENCE_VALIDATION_005`，但改由读取器以结果返回（不再构造时抛 `TakeExceededException` 等 Transaction 阶段转换）——同一个查询类型的三种越界都在一处、调用里外都是结果。SqlSugar 的读取器在入口校验，不连库、不登记运行时数据源；不读结构的 Provider（EF Core、内存实现）仍返回 `PERSISTENCE_UNAVAILABLE_008`。
- 一致性：缓存存储套件加一例（0、1001、-1 是校验结果，1 与 1000 照常分页）；库结构套件加一例（`Skip` = -1、`Take` = 0、1001 的码，经运行时数据源时不登记，`Skip` = 0、`Take` = 1 与 1000 照常）。

### 理由

- 与 ADR-0082 同形：越界是调用方能改正的输入，应是 400；校验在查询类型上，Provider 一行调用，不必每家各写一遍判断。
- 缓存的签名非改不可：返回裸 `CacheKeyPage` 只能抛异常，而异常在管道里是 500。
- 表列表的 `Take` 上限码不变（`PERSISTENCE_VALIDATION_005`），已按它判断的调用方不受影响；只是从「构造时抛出、调用里转换」变成「读取器返回」，调用外直接用读取器的代码也拿到结果而不是异常。

### 影响

- 公开 API：`ICacheStoreInspector.ListKeysAsync` / `ICacheInspector.ListKeysAsync` 返回 `ValueTask<Result<CacheKeyPage>>`（调用方加 `.ValueOrThrow()` 或按结果处理）；新增 `CacheKeyQuery.Validate()`、`CachingErrors.ListLimitInvalid`、`CachingMessages.ListLimitInvalid`、`TableListQuery.Validate()`、`PersistenceErrors.ListPageInvalid`、`PersistenceMessages.ListPageInvalid`。自写的缓存存储若实现了 `ICacheStoreInspector`，要改签名并在入口调 `query.Validate()`。
- 行为：缓存键列表 `Limit` 越界 500 → 400 `CACHING_VALIDATION_003`；表列表 `Skip` 为负、`Take` 小于 1 500 → 400 `PERSISTENCE_VALIDATION_007`；`Take` 超过 1000 仍 400 `PERSISTENCE_VALIDATION_005`。

## 四、库结构读取在 MySQL、Oracle、SQL Server 上实测

### 背景

ADR-0078 的库结构读取只在 SQLite 与 PostgreSQL 上跑过，SQL Server、MySQL、Oracle 的列长度与精度「只按 SqlSugar 报告的值映射」。SQL Server 在第三批验证过部分唯一索引，读结构没有用例。用户拍板：用 Docker 补测 MySQL 和 Oracle，测出问题照实修。

### 实测（本机 Docker：`mysql:latest` 9.7、`gvenzl/oracle-free:23-slim-faststart`、`mcr.microsoft.com/mssql/server:2022-latest`）

用运行时数据源读外部库，各建一张覆盖常见类型、带注释与缺省值、自增主键的表，一张加引号的大小写混合表，两张按月分表的物理表；另以它们作应用库跑 `SchemaConformance`。

- MySQL：注释、`AUTO_INCREMENT`、主键、可空、缺省值（`x`）、精度、分表折叠与分页总数都对。问题：`tinyint(1)` 的长度报 1（显示宽度）、`datetime(6)` 报 6（小数秒位数）。
- SQL Server：注释（扩展属性）、identity、主键、缺省值（`('x')`）、`money` 的精度都对。问题：`int` 报长度 10、`bigint` 19、`float` 53、`datetime2` 27、`bit` 1——都是精度或存储宽度，不是长度。
- Oracle：问题多。SqlSugar 的 `GetColumnInfosByTableName` 取 `GetSchemaTable`：类型名是 CLR 类型（`Decimal`、`String`、`Int64`）、identity 列报告不自增、缺省值错位（`'x' ` 读成 `x' `）、`CLOB` 长度 2147483647；加引号的大小写混合表 `"LegacyOrder"` 被转成大写，读列报 ORA-00942。

### 决策

- 长度只给字符与二进制类型（`char`、`nchar`、`varchar`、`nvarchar`、`varchar2`、`nvarchar2`、`character`、`character varying`、`bpchar`、`binary`、`varbinary`、`raw`）的声明长度，没有上限的（`nvarchar(max)`、`text`、`CLOB`）与其余类型都为 null；精度与小数位照旧只给定点数族。RFC-0005 原来写「其他数据库可能报告字节数或显示宽度」，实测之后收紧：代码生成按长度出 `MaxLength`，把整数的显示宽度当长度会生成错的校验。
- Oracle 的读列不走 SqlSugar，改由内部的 `OracleColumns` 查连接用户自己的数据字典：`USER_TAB_COLUMNS`（类型去掉括号里的位数，字符类型按 `CHAR_LENGTH` 即字符数，`NUMBER(p,s)` 给精度与小数位、不带精度的给 null，`IDENTITY_COLUMN` 判自增，`DATA_DEFAULT` 去掉末尾空格作原文）、`USER_COL_COMMENTS`、`USER_CONSTRAINTS` / `USER_CONS_COLUMNS`（主键）；表名按库里的原样绑定。`IDENTITY_COLUMN` 要 12c 及以上，更早的版本读列失败（`PERSISTENCE_UNAVAILABLE_006`），不做 11g 的分支。达梦、OceanBase Oracle 模式等兼容库仍走 SqlSugar 的读列，没有验证环境。
- 运行时数据源在 Oracle 上 `IsAutoToUpper = false`，与 PostgreSQL 不转小写一致：标识符按库里原样引用，零代码运行时 `Queryable<object>().AS(table)` 对大小写混合的表也查得到。
- 门控用例：`XIHAN_TEST_MYSQL`（服务器连接串，每个用例建删一个库）、`XIHAN_TEST_ORACLE`（能建用户的连接串，每个用例建删一个用户）、`XIHAN_TEST_SQLSERVER`（同第三批），与 PostgreSQL 同形：`SqlSugarSchemaReaderTests` 各一个读外部库的用例，`MySqlSchemaConformanceTests`、`SqlServerSchemaConformanceTests`、`OracleSchemaConformanceTests` 以它们作应用库跑库结构套件。

### 理由

- 长度的语义要跨数据库一致才对代码生成有用；各库报告的「长度位」含义不同，在映射层按类型族取舍最简单，也不需要逐库特判。
- Oracle 的问题出在 SqlSugar 的实现方式（`GetSchemaTable` 只有 ADO.NET 的类型信息），修 SqlSugar 不在本仓库；数据字典是 Oracle 读结构的标准做法，查询只读、不依赖 SqlSugar 的大小写转换。

### 影响

- 行为：MySQL、SQL Server（以及 SQLite、PostgreSQL 上整数、日期这类本来就为 null 的）非字符类型的 `Length` 变为 null；Oracle 的 `DataType` 从 CLR 类型名变为数据库类型名（`NUMBER`、`VARCHAR2`、`TIMESTAMP`），`IsIdentity`、`DefaultValue`、字符类型的 `Length`（字符数）、`Precision` / `Scale` 变为正确的值，大小写混合的表能读。按旧值推断控件类型的代码生成要按新值核对。
- 公开 API 不变。CI 是否起 MySQL 与 Oracle 的服务容器待定（见第五节）。

## 五、框架 CI 起 SQL Server 服务容器

### 背景

第三批起 `Persistence.SqlSugar.Tests` 有 SQL Server 的门控用例（筛选索引，`XIHAN_TEST_SQLSERVER`），本批又加了 SQL Server 的库结构读取与库结构一致性套件。`next-ci.yml` 只起 Redis、PostgreSQL、RabbitMQ，这些用例在 CI 里一直跳过。用户拍板：CI 加 SQL Server 服务容器，让它们真跑。

### 决策

- `next-ci.yml` 的 `services` 加 `sqlserver`：镜像 `mcr.microsoft.com/mssql/server:2022-latest`（与本机验证所用相同），`ACCEPT_EULA=Y`、`MSSQL_SA_PASSWORD`（只给 CI 一次性容器用的固定口令，满足复杂度且不含 shell 特殊字符），端口 `1433:1433`；健康检查 `/opt/mssql-tools18/bin/sqlcmd -C -S localhost -U sa -P … -Q 'SELECT 1' -b`，每 10 秒一次、最多 20 次（SQL Server 冷启动要十几秒，作业在服务健康之后才开始）。
- 测试步骤加 `XIHAN_TEST_SQLSERVER: Server=localhost,1433;User Id=sa;Password=…;TrustServerCertificate=True`。
- 本机按同样的镜像、环境变量、健康检查与连接串起容器验证：健康检查第一次就返回 0；`Persistence.SqlSugar.Tests` 在 PostgreSQL + SQL Server 下 176 例里 164 通过、12 跳过（MySQL 与 Oracle 的门控用例），SQL Server 的 7 例全部真跑通过。
- MySQL 与 Oracle 的门控用例不进 CI，是否加服务容器待用户定：MySQL 镜像小、起得快，适合加；Oracle Free 镜像约 1.5 GB、冷启动数十秒，每次 CI 都拉会明显拖慢作业。

### 影响

- CI 时长增加 SQL Server 镜像的拉取与启动（与其余服务容器并行）。用例在 CI 里失败就是真失败，不再被跳过掩盖。
- 修订 ADR-0081「SQL Server 的用例 CI 不提供、跳过」一句。

## 六、维持现状的几项改为已定

### 背景

第二批、第三批的汇报里有几处做法照实写了「需要用户再定」。用户拍板全部维持，规范与文档里的措辞改为已定。

### 决策

- 工作流平台定义用平台表、不用哨兵值（第二批第 1 条）：接受 ADR-0077 第二节的形态。平台定义存 `PlatformWorkflowDefinitionRecord`，唯一索引 `(Name, Version)` 不含可空列，每一行都受约束；租户表实现 `IMultiTenant` 装不下平台的行。ADR-0077 原文「目标照办、形态改成平台表」改注「用户已接受」。
- EF Core 不支持运行时数据源与读结构（第二批第 5 条）：维持返回 `PERSISTENCE_UNAVAILABLE_008`，不计划支持。EF Core 的数据库 Provider 由应用选、框架不引用，按类型建不出连接；跨库读结构在 EF Core 里是设计期脚手架服务。需要代码生成读结构、外部数据源或零代码运行时的应用用 SqlSugar Provider。
- 连接信息脱敏（第二批第 6 条）：维持现有范围——只遮整串连接串与口令类键（`password`、`pwd`、`secret`、`token`、`key`）的值；主机、端口、库名、用户名是排查连接问题要用的，不算机密。不改代码。
- PostgreSQL 衍生库（第三批第 9 条）：人大金仓、openGauss、GaussDB、瀚高、Vastbase、PolarDB、TDSQL PG 维持按不支持部分唯一索引处理（启动失败，不退化）；在真实库上验证过建出、约束与再次建表不重复建之后，才加进 `PartialUniqueIndexes` 的名单。

### 影响

无代码变化；`spec/rfcs/0005-persistence.md`、ADR-0077、docs-next 与包 README 的措辞改为已定。
