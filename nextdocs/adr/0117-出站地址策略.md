# ADR-0117 出站地址策略

## 状态

已采纳（`spec/rfcs/0008-security.md`、`0012-objectstorage.md`、`0021-workflow.md`、`0022-ai.md`、`spec/protocol/cloudevents.md` 随之修订）。

## 日期

2026-11-04

本 ADR 记录第二十九批回灌（`ai-batch-backlog.md`，N5 审查发现，用户定「缺省拒绝回环、私网、链路本地，经配置放行」）的决定。

## 背景

全仓库都没有私网防护。工作流 `Http` 活动只查 scheme，流程定义由租户管理员编辑，于是租户管理员能让服务器访问内网和云元数据地址。修前用真实端口复现：缺省配置下 `http://127.0.0.1:<端口>/` 的请求到达了监听端口，实例 `Completed`。

BasicApp 的机器人 Webhook、AI 提供商与第三方登录也会向用户给的地址发请求，要用同一个机制。

## 决策

1. 机制放在内核 `Kernel.Security`：`OutboundAddressPolicy`（宿主登记的单例）、`OutboundAddressOptions`（配置节 `XiHan:Security:Outbound`）、`OutboundAddressDeniedException`。放内核是因为工作流、协议、存储与应用都已经依赖它，放 `Security.Abstractions` 要让这些包多一条只为这个机制的引用。
2. 缺省只能连公网地址。除了用户点名的回环、私网、链路本地，其余不可公网路由的地址也拒绝：`0.0.0.0` 在 Linux 上连到本机，阿里云元数据 `100.100.100.200` 在运营商级 NAT 段，Oracle 元数据 `192.0.0.192` 在 IETF 协议段。IPv4 映射、NAT64、6to4、IPv4 兼容形式按内嵌的 IPv4 判定。判定顺序与全部网段见 RFC-0008。
3. 检查放在建立连接时（`SocketsHttpHandler.ConnectCallback`），按解析出的实际 IP 判，连接用的就是检查过的地址。只查 URL 或事先解析一次都会被 DNS 重绑定绕过。处理器的每条新连接都走这里，重定向自然覆盖。
4. 放行有四个配置：`AllowLoopback`（本地开发）、`AllowPrivateNetwork`、`AllowedNetworks`（CIDR）、`AllowedHosts`（整名相等）。链路本地没有单独的开关，它承载云元数据，要开只能按网段写明。`AllowPrivateNetwork` 也不开放 AWS 的 IPv6 元数据地址 `fd00:ec2::254`。
5. `AllowedNetworks` 要求主机位为零。`IPNetwork` 把 `10.0.0.1/8` 静默掩码成 `10.0.0.0/8`，在放行项里这多半是手误，悄悄开放整段比报错糟。
6. 解析结果里一部分被拒绝时只连其余的：连的都是检查过的地址，不会多返回一个内网地址就连不上。全部被拒绝才抛异常。
7. 异常与错误只带请求里的主机名，不带解析出的地址。解析结果是内网信息，只进日志（Warning）。
8. `Apply` 关掉代理：经代理时连接回调看到的是代理的地址，查不到真正的目标。
9. 用法是把策略 `Apply` 到 `SocketsHttpHandler`。命名客户端写 `UseSocketsHttpHandler`，手工建的客户端直接调，所以不需要给 `IHttpClientBuilder` 加扩展，内核也不必引用 `Microsoft.Extensions.Http`。

### 接了哪些

| 路径 | 为什么接 |
| --- | --- |
| 工作流 `Http` 活动的缺省客户端 | 地址来自流程定义，租户管理员可编辑 |
| CloudEvents Webhook | 地址是运维配的，但接收方是第三方，它的 3xx 能把请求引到内网 |
| S3 命名实例（`S3BlobStoreProvider`） | RFC-0012 明确定义可以来自应用的库，BasicApp 的存储配置就是租户填的端点 |

### 哪些不接

| 路径 | 为什么不接 |
| --- | --- |
| OpenID Connect 发现与 JWKS | `Authority` 只来自运维配置，签发者常在内网。它本身就是令牌的信任根，`jwks_uri` 跟它同一信任边界。`OpenIdConnectMetadataCache` 接受应用传入的 `HttpClient`，应用让租户配签发者时自己接 |
| OpenAI Provider | 框架的端点来自 `XiHan:AI:Providers` 配置，本地模型（Ollama 等）多在回环或内网。公开 `OpenAIFeature.HttpClientName`，应用的目录让用户填端点时自己接 |
| S3 缺省实例 | 端点来自运维配置 |
| Nacos、Kubernetes API Server、OTLP 导出 | 运维配置，都在内网，接了只会让正常部署都要放行 |
| 进程外插件通道、CLI 健康探测 | 本机地址，由框架自己决定 |
| 数据库、缓存、消息代理 | 不是 HTTP，策略管不到。连接串由运维或平台管理 |

## 备选

1. **只查 URL 的主机**：DNS 重绑定、指向内网的公网域名、重定向都绕得过去。用户否决。
2. **发请求前解析一次并检查**：检查和连接之间有窗口，两次解析可以得到不同结果。用户否决。
3. **`DelegatingHandler` 里检查**：拿不到连接时的实际 IP，重定向也可能在它下面发生。否决。
4. **一个解析结果里有内网地址就整体拒绝**：连接本来就只用检查过的地址，整体拒绝没有更安全，反而让双栈或多记录的正常域名连不上。否决。
5. **全局打开 `ConfigureHttpClientDefaults`**：会一并拦住 Nacos、Kubernetes 这些运维配置的内网地址。否决。
6. **放行项做成按客户端的多套策略**：现在只有一个部署级的需要，机器人和 AI 要不同放行范围时再说。不做推测性扩展。

## 影响

这是缺省行为变化。

- 工作流 `Http` 活动、CloudEvents Webhook 与 S3 命名实例连内网地址要先放行，否则分别得到节点故障 `workflow.http.address_denied`、`PROTOCOLS_UNAVAILABLE_002`、`OBJECTSTORAGE_UNAVAILABLE_001`。日志里有 Warning，带解析出的地址。
- 本地开发写 `"XiHan": { "Security": { "Outbound": { "AllowLoopback": true } } }`，放进 `appsettings.Development.json`。
- 公开签名：`WorkflowHttpClient()` 改成 `WorkflowHttpClient(OutboundAddressPolicy)`，`S3BlobStoreProvider(TimeProvider, ILoggerFactory)` 多一个 `OutboundAddressPolicy` 参数。经容器解析不受影响。新增 `OpenAIFeature.HttpClientName`。
- 替换主处理器或 `WorkflowHttpClient` 的应用不受影响，也不受保护，由替换后的处理器决定能连哪里。
- 经 `HttpClient` 用的应用接法：`services.AddHttpClient(name).UseSocketsHttpHandler(static (handler, sp) => sp.GetRequiredService<OutboundAddressPolicy>().Apply(handler))`。

### 已知限制

- HTTP/3 走 QUIC，不经过连接回调。请求缺省是 HTTP/1.1，框架接入的路径都不请求 HTTP/3；把 `Version` 设成 3.0 的请求不受保护。
- `AllowedHosts` 只看主机名，这个名字的 DNS 要是可信的。
- 代理软件的 fake-ip 模式把公网域名解析成 `198.18.0.0/15`，缺省全部被拒绝。开发机写 `AllowedNetworks: ["198.18.0.0/15"]`，这时策略只看得到假地址，真实目标由代理决定。开发这个策略的机器上就是这样：`api.nuget.org` 解析成 `198.18.0.149`，缺省被拒绝，放行这一段后 HTTPS 正常。
- ISATAP 这类把 IPv4 写进接口标识的形式没有单独判定，它们落在全球单播范围里时按公网放行，到达内网还需要路由配合。
