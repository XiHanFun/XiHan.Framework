# ADR-0090 S3 条件写入启动照常与后台重试、云厂商只走标准条件头、键的保留前缀与登录用户名打码

## 状态

已采纳（`spec/rfcs/0012-objectstorage.md`、`spec/conventions/error-codes.md`、`spec/rfcs/0016-packaging.md`、`spec/rfcs/0014-configuration.md` 随之修订；修订 ADR-0089 第一节与第三节）。

## 日期

2026-11-01

## 背景

第五批（ADR-0089）留下的待定项由用户拍板（全按推荐）：「启动时连不上 S3 也启动失败」不接受，恢复原来的照常启动、健康降级，条件写入的探测在后台或第一次使用时重试，探测通过之前写入返回不可用、不静默——用户之前定的只是「服务不认条件写入就明确报错」，这一条不变；阿里云 OSS、腾讯云 COS、Cloudflare R2 维持只做一个 S3 包，文档写明要实测；探测键换成业务列举时会跳过的键名；S3 的用户名打印时也打码。本 ADR 每项一节。

## S3 条件写入：启动照常、后台与首次使用时重试（修订 ADR-0089 第一节）

### 背景

ADR-0089 让 S3 Provider 在缺省实例启动时、命名实例建出时探测服务是否认 `If-None-Match: *`，四种失败——不认、被拒绝、探测桶不存在、连不上——都让启动失败或不建实例。其中只有"不认"是用户要的明确报错；后三种是 ADR-0089 的推论（"没探过就无从确认"），代价是启动依赖 S3 此刻的状态：编排里 S3 比应用晚就绪、桶由另一个任务稍后建出、IAM 策略刚改还在传播，应用都起不来。ADR-0089 之前，这些情况照常启动，健康项降级。

### 备选

- **什么时候再探**：
  - 只在健康项的周期里顺带探：恢复要等一整个健康间隔，而且健康项每 15 秒写一次存储（ADR-0089 已否决周期写入）。
  - 只在第一次不覆盖写入时探：没有写入时健康项一直停在降级；写入一来先多一次往返，恢复后的第一个写入才知道。
  - **启动时探一次，尚未确认就在后台按退避重试，写入时还可以就地探（选中）**。
- **退避**：固定间隔；指数倍增不设上限；**1 秒起倍增，上限是 `HealthProbeIntervalSeconds`（选中）**——不加新配置键，短暂中断（容器晚几秒就绪）几秒内恢复，长时间连不上时与健康项同一节奏，有界。
- **写入时就地探的频率**：每个写入都探（写入密集而 S3 不可达时把探测压成连发）；只等后台（恢复后的写入最多等一个上限间隔才放行）；**有探测在进行就共用它，没有而距上一次探测满 1 秒才就地再探（选中）**——每个实例同一时刻只有一个探测，写入密集时最多每秒一次。
- **探明之前不覆盖写入返回什么**：退回先查再写（就是 ADR-0089 要拦的静默覆盖）；复用 `OBJECTSTORAGE_UNAVAILABLE_001`（与"这次写入连不上"混为一谈）；复用 `OBJECTSTORAGE_UNAVAILABLE_003`（那是终态，调用方会以为要换服务）；**新码 `OBJECTSTORAGE_UNAVAILABLE_004`（选中）**：暂时不可用，稍后重试即可，参数 `reason` 带最近一次探测失败的错误码。
- **被拒绝（`DENIED_002`）与探测桶不存在（`NOTFOUND_001`）**：照 ADR-0089 启动失败；**与连不上一样记为"尚未确认"（选中）**。它们是配置问题，但修好它们（改 IAM 策略、建桶）不需要动应用；启动失败只会让编排器反复重启，而照常启动加后台重试能在修好后自动恢复，原因照样在健康项与日志里明确报告。
- **启动之后（后台重试或写入时）才探明不认**：让应用停止（运行中的服务被一个子系统拖垮）；健康项 Degraded（与"暂时连不上"看不出区别）；**健康项 Failed，不覆盖写入一律 `OBJECTSTORAGE_UNAVAILABLE_003`，记 Error 日志（选中）**——Failed 在内核里表示"要人处理"（与插件目录不可读同级），应用仍在服务。
- **命名实例**：建出时就要求探通（ADR-0089）；**与缺省实例同样处理（选中）**：只有探明不认才不建，尚未确认的照常建出、登记，各自在后台重试。

### 决策

- 内部类型 `S3ConditionalWriteGate` 持有一个存储实例的条件写入状态：关闭（`ConditionalWrites = false`）、尚未确认、已确认、不认；只从尚未确认迁出，已确认与不认是终态（服务的能力不会在运行中改变）。缺省实例的状态是容器单例，与 `S3BlobStore` 和健康项共用；命名实例的状态归实例所有；经公开构造函数直接建的 `S3BlobStore` 不探测（开启时视作已确认，由调用方负责，同 ADR-0089）。
- 启动 / 建实例：探一次（判定与失败归类同 ADR-0089，探测键、单次超时不变）。探明不认 → 缺省实例 `KERNEL_HOSTING_002`（内层 `OBJECTSTORAGE_UNAVAILABLE_003`）启动失败，命名实例抛出携带该码的 `FrameworkException`、注册表不登记（不变）。其余结论都是尚未确认：照常启动、照常建出并登记，起后台重试。
- 后台重试：第一次 1 秒后，之后间隔加倍，最长 `HealthProbeInterval`（它小于 1 秒时都取它），计时用容器里的 `TimeProvider`（`Task.Delay(delay, clock, token)`）；每次重试与写入共用"正在进行的探测"；有了终态即停；缺省实例在特性停止时、命名实例在被替换、移除或注册表停止时停止（`S3BlobStore` 新增 `IAsyncDisposable`，先等后台探测放下客户端再释放客户端）。
- 不覆盖写入（`S3BlobStore` 的 `Overwrite = false` 写入、分片上传的发起与完成）先问状态：已确认放行；关闭 → `UNAVAILABLE_003`（消息键 `objectstorage.conditional_write.disabled`，不变）；不认 → 探明时的 `UNAVAILABLE_003`（`objectstorage.conditional_write.unsupported`，参数 `bucket`、`operation`）；尚未确认 → 有探测在进行就等它（受调用方取消约束，共用的探测不因某个写入方取消而中止），没有而距上一次探测结束满 1 秒就地探一次，之后仍未确认 → 新码 `OBJECTSTORAGE_UNAVAILABLE_004`（新消息键 `objectstorage.conditional_write.unconfirmed`，参数 `container`、`key`、`reason`），不访问写入目标。
- 健康：缺省实例的健康项 `objectstorage.s3.connection` 由内部类型 `S3ConnectionHealth` 合成——连通性仍由 `PeriodicHealthContributor`（HEAD 健康桶或列桶）缓存，条件写入的状态每次读取时即时并入：数据 `conditionalWrites` 为 `confirmed` / `unconfirmed` / `unsupported` / `disabled`；尚未确认为 Degraded，错误是最近一次探测失败（`UNAVAILABLE_001` / `DENIED_002` / `NOTFOUND_001`，HEAD 成功也一样）；不认为 Failed，错误是 `UNAVAILABLE_003`。命名实例的健康探测（`S3BlobStoreProvider.ProbeAsync`）在 HEAD 成功后返回条件写入的状态，尚未确认或不认时失败，注册表记为 Degraded（注册表对 Provider 的探测失败一律记 Degraded，不改）。
- 日志：状态或失败原因变化时各记一条（尚未确认 Warning、重试后确认 Information、之后才探明不认 Error），稳定的失败不随每次重试刷屏。
- 公开 API（都在 Unshipped）：`ObjectStorageErrors.ConditionalWriteUnconfirmed`、`ObjectStorageMessages.ConditionalWriteUnconfirmed`；`S3BlobStore` 实现 `IAsyncDisposable`（`DisposeAsync()`）；`S3BlobStoreProvider` 的构造函数由 `(TimeProvider clock)` 改为 `(TimeProvider clock, ILoggerFactory loggerFactory)`（容器解析不受影响，手工构造要补日志工厂）。

### 理由

- 用户定的明确报错只针对"不认"：这一条在任何时机都成立——启动时探明即启动失败，之后探明即不覆盖写入一律报错、健康项 Failed；其余情况都不再让启动依赖 S3 此刻的状态。
- 任何时候都不放行没有保证的不覆盖写入：探明之前一律 `UNAVAILABLE_004`，不先查再写，所以去掉启动失败不会带回 ADR-0089 要拦的静默覆盖。
- 探测仍写同一个固定键、不删除（ADR-0089），所以后台重试、写入时就地探、多个实例并发探都得到同一结论；共用一个探测与 1 秒的最小间隔让写入密集时的额外请求有界。
- 新码区分"暂时"与"终态"：`UNAVAILABLE_004` 让调用方知道稍后重试即可，`UNAVAILABLE_003` 表示要换服务或改配置。

### 影响

- 启动期失败条件减少：装配 `S3ObjectStorageFeature` 且它提供缺省实例时，只剩 ① `ConditionalWrites` 没关且没配 `HealthBucket`（装配失败 `ArgumentException`，不变）② 启动时探明服务不认条件写入（`KERNEL_HOSTING_002` ← `OBJECTSTORAGE_UNAVAILABLE_003`，不变）。启动时连不上（`UNAVAILABLE_001`）、被拒绝（`DENIED_002`）、探测桶不存在（`NOTFOUND_001`）不再启动失败；命名实例同理，这三种情况下照常建出并登记（以前注册表返回对应错误码、不登记）。
- 行为：尚未确认期间 `Overwrite = false` 的写入与分片上传的发起、完成返回 `OBJECTSTORAGE_UNAVAILABLE_004`（HTTP 503），探测通过后自动恢复；健康项 `objectstorage.s3.connection` 多了数据 `conditionalWrites`，尚未确认时 Degraded（即便 HEAD 成功），之后才探明不认时 Failed（应用的聚合状态是 Degraded，仍就绪）。端点黑洞（不回 RST）时启动最长要等探测超时加首次健康探测超时，即 2 × `HealthProbeIntervalSeconds`（ADR-0089 是一次超时后失败，ADR-0089 之前是一次健康探测超时）。
- 错误码与消息键：新增 `OBJECTSTORAGE_UNAVAILABLE_004` 与 `objectstorage.conditional_write.unconfirmed`（10 种语言）；`DENIED_002`、`NOTFOUND_001`、`UNAVAILABLE_003` 的说明改写。配置键不变（CLI 知识库只改说明）。
- 测试：`ObjectStorage.S3.Tests` 新增 `S3ConditionalWriteRetryTests`（内存替身 `FakeS3Client` 加 `FakeTimeProvider`，推进假时钟前先等后台重试排定计时器，不靠真实等待）：启动时连不上照常启动、健康降级、写入 `UNAVAILABLE_004` 且不访问存储，后台第 1、2 秒重试、服务恢复后自动确认、健康即时恢复；写入时就地探测且三个写入方共用一个探测；被拒绝与缺桶照常启动、修好后自动恢复；之后才探明不认 → 健康 Failed、写入 `UNAVAILABLE_003`、不再重试；退避 1、2、4、8、10、10 秒（上限为健康间隔 10 秒）；停止与命名实例释放后不再探测；命名实例连不上照常建出并恢复、探明不认不建。替身新增 HEAD 对象、建桶与"拦住某个请求直到放行"。对真实服务的用例改为：密钥错照常启动、健康降级（`DENIED_002`）、写入 `UNAVAILABLE_004`；缺桶照常启动、健康降级（`NOTFOUND_001`）；命名实例缺探测桶照常建出。

## 云厂商的兼容服务只走标准条件头，接入前实测

### 背景

ADR-0089 的实测只覆盖了能在本机起容器的服务（RustFS、MinIO、Garage、Zenko CloudServer），阿里云 OSS、腾讯云 COS、Cloudflare R2 没有账号实测是否认 `If-None-Match: *`。OSS 与 COS 各有私有的禁止覆盖头（`x-oss-forbid-overwrite`、`x-cos-forbid-overwrite`），第五批问过要不要为它们适配；BasicApp 的文件模块有 AliyunOss / TencentCos 两种存储类型，迁 5.0 时会碰到。

### 备选

- 为 OSS、COS 加私有头适配：按端点识别服务商、换用私有头。与 ADR-0018"一个 S3 包、不为每家云做包"相抵；端点识别要维护一张表，私有头的原子语义也要逐家实测，同样没有账号验证。
- 拆出 `ObjectStorage.Aliyun` / `ObjectStorage.Tencent` 包：同上，且多出两个包的维护面。
- **维持只做一个 S3 包，只认标准条件头；文档写明这几家要实测，不认就关 `ConditionalWrites`（选中）**。

### 决策

- 不做私有头适配，不按端点识别服务商。RFC-0012「S3 Provider」、S3 包 README、docs-next 的 S3 包页（新节「云厂商的兼容服务」）与存储指南写明：这几家是否认 `If-None-Match: *` 没有实测，接入前要实测——缺省的条件写入探测就是实测（启动时探明不认即启动失败；通过时健康项数据 `conditionalWrites` 为 `confirmed`），也可以照探测的做法用 curl 对同一个键发两次带条件的 `PutObject`，第二次必须 412。
- 不认就设 `ConditionalWrites = false`（命名实例的设置同名，可以按实例关闭；BasicApp 会在自己的存储配置里加按条关闭的开关，框架不用管）。后果写明：这个存储上 `Overwrite = false` 的写入与分片上传的发起、完成一律 `OBJECTSTORAGE_UNAVAILABLE_003`，"只在不存在时写入"不再可用，需要它的业务改用不冲突的键（如带随机后缀）或覆盖写入；框架不退回先查再写。

### 理由

- 标准条件头是 Amazon S3 的语义（2024 年 8 月起 `PutObject` 与 `CompleteMultipartUpload` 都支持），兼容服务在跟进；为私有头适配是在没有验证的前提下增加分支，违背"一个 S3 包"。
- 探测本身就是可靠的实测手段：它写的就是框架真正依赖的语义，结论直接决定框架行为，不需要另一份兼容性表。

### 影响

- 代码、公开 API、错误码、配置键都不变，只改规范与文档。
- 接入这几家的应用要先实测；不认时关闭条件写入，并检查业务里有没有 `Overwrite = false` 的写入。

## 键的保留前缀 `.xihan`：框架对象不进业务列举

### 背景

ADR-0089 的探测键 `.xihan/probe/conditional-write` 写入后不删除，它符合键文法，按空前缀列举探测桶时会出现在业务的列举结果里（应用通常把 `HealthBucket` 配成自己写入的桶）。用户要求探测键换成业务列举时会跳过的键名。

### 备选

- **换成键文法之外的名字**（如含空格、以 `/` 结尾）：S3 与文件系统的列举本来就跳过不合文法的对象，改动最小；但键名怪异，以 `/` 结尾的对象在不少服务与控制台里被当作"目录"特殊处理，条件写入在它上面的行为也要逐家实测；IAM 策略按前缀授权（`.xihan/probe/*`）也要跟着改，ADR-0089 已在桶里留下的旧键还会继续混进列举，需要迁移。
- **保留一个框架前缀，列举时统一跳过、键文法里禁止业务写入（选中）**：首段 `.xihan` 的键不在键文法之内（`BlobKey` 构造时抛出、`IsValid` 为假），各 Provider 现有的"跳过不合文法的对象"自然把它们排除在列举之外。探测键名字不变，正好落在保留前缀下。
- 只在 S3 的列举里跳过探测键这一个名字：别的框架对象以后还要再加例外，文件系统与业务看到的键文法不一致。

### 决策

- `BlobKey` 新增 `ReservedSegment`（`.xihan`）与 `IsReserved(value)`：首段就是 `.xihan` 的键（`.xihan` 本身与 `.xihan/…`）保留给框架，只看首段、区分大小写（与键本身区分大小写一致，`.XiHan/a`、`.xihanx/a`、`a/.xihan/b` 都是普通键）。`IsValid` 对保留键为假，构造与 `Validate` 抛出 `ArgumentException`（消息指出保留段）。`BlobQuery.Prefix` 不受限（只是筛选），以 `.xihan` 开头的前缀列举总是空的。
- S3 与文件系统的列举都已经按 `BlobKey.IsValid` 跳过不合文法的对象，代码只补注释；S3 的探测键改为由 `BlobKey.ReservedSegment` 拼出，名字不变。5.0 只有这两个存储实现（没有内存实现），两者行为一致。
- RFC-0012「标识」写明保留前缀，`List` 写明跳过不合文法的对象时一页可能少于 `PageSize` 条、甚至为空而仍带续页标记，调用方取到续页标记为空为止。
- 一致性套件新增用例 13 `ReservedKeys_AreRejected_AndSkippedWhenListing` 与抽象钩子 `PlantOutsideContractAsync(container, key, content)`（Provider 的测试类绕过契约直接在底层存储里写一个对象）：保留键构造时拒绝、判定只看首段且区分大小写；放入 `.xihan/conformance/planted` 与业务键 `.xihanx/<随机>` 后，以 `.xihan/` 列举为空，以 `.xihan` 列举只有业务键。放入的键固定、业务键用完即删，反复运行不在共享存储里累积。

### 理由

- 用前缀而不是怪名：键名保持可读，IAM 可按前缀单独授权；判定复用键文法，所有 Provider 的列举一处规则就排除了框架对象，以后框架要在用户的桶里放别的对象也落在这里。
- 探测键名字不变，所以不需要迁移：ADR-0089 起在桶里留下的 `.xihan/probe/conditional-write` 自动成为保留对象，业务列举不再看到它；已有的 IAM 策略（`<桶>/.xihan/probe/*`）照旧有效。

### 影响

- 公开 API（Unshipped）：`BlobKey.ReservedSegment`、`BlobKey.IsReserved(string?)`；一致性套件的 `BlobStoreConformance.PlantOutsideContractAsync`（抽象，Provider 的一致性测试类必须实现）与用例 `ReservedKeys_AreRejected_AndSkippedWhenListing`。
- 行为：首段是 `.xihan` 的业务键从此构造即抛出（经 HTTP 宿主的代收发端点按键不合法处理，返回 `OBJECTSTORAGE_NOTFOUND_001`，HTTP 404）；存储里已有的这类对象经契约读不到、删不掉，也不出现在列举里。迁移：应用若曾把业务对象放在 `.xihan/` 下（5.0 预览期，可能性很小），升级前用存储自己的工具把它们改名到别的前缀；探测键不用动，也不必删除。
- 错误码、消息键、配置键都不变。

## 登录用户名在选项打印时也打码（修订 ADR-0089 第三节、ADR-0086 第二节）

### 背景

ADR-0086 第二节让选项记录手写 `PrintMembers`、凭据打印为 `***`，用户名照常打印；ADR-0089 第三节把 S3 的访问密钥 ID 改为也打码，用户名仍照常打印（理由是用户名是运维起的身份名、排查"连的是哪个用户"要用）。用户拍板"S3 的用户名打印时也打码"，并定"用户名也打码"。

### 同类字段的核对

- S3：`S3ObjectStorageOptions` 里属于"用户名"一类的只有访问密钥 ID `AccessKey`（S3 没有单独的用户名字段），ADR-0089 已遮蔽；命名实例的设置 `BlobStoreDefinition.Settings` 是字典，只打印类型名；绑定 `objectstorage` 的 `accessKey` 属性在 `BindingValue.Properties` 字典里，同样只打印类型名。S3 本身没有剩下要改的。
- 全框架逐个看了架构测试扫描的全部公开记录：属性名是用户名的有 `RedisCachingOptions.User`（Redis 6 的 ACL 用户）、`RabbitMQMessagingOptions.UserName`、`NacosOptions.Username`、`RuntimeInfo.UserName`（观测包，运行进程的系统账户）。Kafka 的 `sasl.username` 在 `Properties` 字典里，只打印类型名。持久化驱动消息里连接串的 `Username=` 键由 `ConnectionStrings.Redact` 脱敏，按 ADR-0084 保留（见"影响"）。

### 备选

- 只改 S3：S3 没有用户名字段，等于什么都不改，不符合用户"用户名也打码"的意图。
- 所有名字是用户名的属性一律打码：`RuntimeInfo.UserName` 是主机诊断数据（`IHostMonitor.ReadRuntime()` 交给应用展示的运行进程账户），不是任何服务的登录凭据，遮蔽它没有安全收益，还要给一个二十多个属性的诊断记录手写 `PrintMembers`。
- **与口令、密钥等凭据同在一个记录里的用户名打码（选中）**：它们是一对登录凭据的身份那一半（Redis、RabbitMQ、Nacos 都是"用户名 + 口令"登录），与访问密钥 ID 同理。

### 决策

- `RedisCachingOptions.User`、`RabbitMQMessagingOptions.UserName`、`NacosOptions.Username` 在 `PrintMembers` 里经 `Redaction.Redact` 打印（`null` 仍为空）。
- 凭据判定扩展（RFC-0014「选项里的凭据」规则 1、2、4）：属性名就是 `User`、`UserName`、`Username`，且所在记录另有凭据属性时，算作凭据。架构测试 `CredentialRedactionTests` 同步：新增用户名正则，记录有凭据时把这些属性一并写入哨兵并要求打印 `***`——只改测试时它对 Redis、RabbitMQ、Nacos 三个选项各报两条失败（明文打印、没有打印 `***`），`RuntimeInfo` 不受影响。
- 不改的：端点、令牌文件路径、分页游标；不带凭据的记录里的用户名。

### 理由

- 用户名与口令是一对：单独泄漏用户名就给了撞库与定向猜测的一半；多数服务的缺省账户（`guest`、`nacos`、`default`）一旦与口令同名，打印用户名就等于打印了口令——与 ADR-0089 遮蔽访问密钥 ID 的理由相同。
- "与凭据同在一个记录里"是可判定、可由架构测试强制的规则；以后新加的选项（如 SMTP 的 `UserName` + `Password`）自动纳入，诊断数据不被误伤。
- 排查"连的是哪个用户"仍可做：遮蔽只影响 `ToString()`，选项对象的属性值不变，应用要时可以自行输出。

### 影响

- 行为：三个选项记录的 `ToString()` 里用户名打印为 `***`（`null` 仍为空），依赖这段文本的代码要更新（框架内没有）。公开 API、错误码、消息键、配置键都不变。
- 以后新加的带凭据的公开记录，若有 `User` / `UserName` / `Username` 属性，必须同样遮蔽，否则架构测试失败。
- 范围之外、留待再定：持久化驱动消息里连接串的 `Username=` / `User Id=` 键，ADR-0084 定为保留（主机、端口、库名、用户名保留以便排查），它是驱动异常消息的脱敏，不是选项打印；`RuntimeInfo.UserName` 照常打印。若也要遮，前者改 `ConnectionStrings.Redact` 的键名单，后者给 `RuntimeInfo` 手写 `PrintMembers`。
