# ADR-0074 调度用例驱动轮询与启动前的手动触发、内存代理丢弃无人订阅的消息、AI 提示词启动期校验、Webhook 不外推与 AI 配置不热更新

已采纳（`spec/rfcs/0013-scheduling.md`、`spec/rfcs/0009-messaging.md`、`spec/rfcs/0022-ai.md`、`spec/protocol/cloudevents.md` 与 `spec/conventions/error-codes.md` 随之修订）。

## 日期

2026-11-01

## 背景

文档站与框架核对的第二轮留下几处待定（调度-2、AI-13、消息-10 语义部分、CloudEvents Webhook 外推、AI 配置热更新），以及数据库调度实现的一个一致性用例只在人为超载时超时。用户逐项拍板，本 ADR 记录每项的决定。

## 调度一致性套件由用例驱动轮询

### 背景

`JobSchedulerConformance` 的 15 个用例靠 Provider 的后台轮询循环（轮询周期 50 毫秒左右）推进，用真实时钟等待：`Task.Delay`、按墙钟轮询条件成立。机器繁忙时轮询与运行都会被拖慢，数据库实现的 `MultipleTriggers_HavePriorityData_AndCanBePausedIndividually` 在人为超载（全量测试 + 8 个并发测试进程）时超时；CI 与常规全量都通过，问题在用例，不在引擎。

### 决策

- 套件给每个用例的宿主登记一个只由用例推进的时钟（`FakeTimeProvider`，在 Provider 装配之前登记，内核只在没有时才补系统时钟）。引擎的到期判定、领导租约、`RecordingJob` 的停留（`RecordingJobLog.Delay`、`delayMilliseconds`）与执行时限都按它计时。
- `JobSchedulerHost` 增加轮询入口：构造为 `JobSchedulerHost(scheduler, poll, host)`，`PollAsync()` 执行一个周期。Provider 把轮询周期设得很长（3600 秒），后台循环不动作，传入 `JobSchedulerEngine.PollOnceAsync`。
- `JobSchedulerEngine.PollOnceAsync` 返回之前等本周期在本节点起的运行连同收尾结束（标为完成、间隔触发器推算下一次、失败的排好重试）：用例推进时钟、轮询一次即可断言。只在手动周期里收集起的运行，后台循环不收集；在轮询互斥之外等待。
- 用例全部改为「推进时钟 → 轮询 → 断言」，断言改为确切的时刻与次数（固定延迟的下一次、misfire 补运行的计划时刻、重试的到期时刻）。等作业开始用 `RecordingJobLog.WaitAsync`，改为由作业的记录唤醒，超时只防挂死。`RecordingJob` 先挂上停留的计时器再记录，用例看到记录就推进时钟不会错过。删除按墙钟轮询的 `WaitUntilAsync`。
- 选举套件也换成 `FakeTimeProvider`（只用到 `GetUtcNow`，行为不变），删掉包内只替换当前时刻的 `ManualClock`，一个包只用一种手动时钟。

### 理由

- 超时的根源是用例与墙钟、后台调度的竞争；把时间交给用例，结果只取决于引擎逻辑，与机器快慢、负载无关。
- 引擎本来就有给测试用的 `PollOnceAsync`；让它等本周期起的运行，是「轮询一次即可断言」的最小改动，不另加公开 API。
- 断言精确到时刻，比「条件最终成立」更能锁住语义（例如 RunOnce 补的那次按恢复时刻、RunAll 按原计划时刻）。

### 影响

- 公开 API（Unshipped）：`JobSchedulerHost` 构造多一个 `poll` 参数、新增 `PollAsync`；`RecordingJob` 构造多一个 `TimeProvider`；删除 `JobSchedulerConformance.WaitUntilAsync`。一致性包新增依赖 `Microsoft.Extensions.TimeProvider.Testing`。
- `PollOnceAsync` 的语义变为「一个周期并等本周期起的运行结束」，只有测试与套件调用它。
- 验证：数据库实现的测试项目在人为超载下（每轮 8 个、16 个进程同时跑整个项目）多轮全过，内存实现的套件从约 7 秒降到约 1.5 秒。

## 调度器启动之前的手动触发

### 背景

上一轮让本实例调度器开始停止之后的 `TriggerAsync` 返回 `SCHEDULING_UNAVAILABLE_001`：停止只等待已经开始的运行，之后起的运行无人等待。启动之前的手动触发仍照常执行，RFC-0013 也这样写。

### 决策

`JobSchedulerEngine` 用一个「是否接受手动触发」的标志代替「已开始停止」：`StartAsync` 置真，`StopAsync` 一开始置假，初始为假。启动之前与开始停止之后到达本实例的 `TriggerAsync` 都返回 `SCHEDULING_UNAVAILABLE_001`（KIND 为 `UNAVAILABLE`，HTTP 照现有映射为 503），不起新的运行；启动后照常，停止后再次启动亦然。`EnqueueAsync` 只写存储，不受影响。

### 理由

- 启动之前没有轮询：取消请求不被应用、维护与失联恢复不进行，起的运行同样无人照看；与停止之后是同一种「调度器不在」的状态，用同一个码。
- 引擎随 Provider 特性启动，宿主进入服务状态之前已经启动；正常的调用路径（HTTP、作业、消息）都在服务状态之后，不受影响。

### 影响

- 行为变化：在调度器所在特性启动之前（例如先于它启动的特性的 `StartAsync`、只构建了容器没有启动宿主的工具）手动触发作业，现在得到 `SCHEDULING_UNAVAILABLE_001`，以前会运行。
- 测试：`InMemorySchedulingTests.ManualTrigger_BeforeTheSchedulerStarts_IsUnavailable` 用注入的假时钟另建一个未启动的引擎验证。

## 内存代理发布到没人订阅的主题

### 背景

内存代理为发布到的每个主题建一条有界通道。没有处理器订阅的主题没有消费者，消息一直留在通道里，直到排满后发布返回 `MESSAGING_UNAVAILABLE_002`；上一轮为防止主题无界增长加了主题数上限，发布到新主题超出上限时逐项返回 `MESSAGING_UNAVAILABLE_003`。调度、工作流等框架事件照常发布到应用不一定订阅的主题，这些缓冲只占内存与主题名额，永远不会被投递。

### 决策

- 「订阅」以本进程的订阅表（`MessageSubscriptions`，`AddMessageHandler` 与插件在装配时登记）为准，交给 `StartAsync` 消费的主题也算。代理构造多一个 `MessageSubscriptions` 参数。
- 发布到没人订阅的主题：消息丢弃，发布照常成功（批量逐项成功），不建通道、不占主题名额；用 `LoggerMessage` 记一条 Debug 日志（条数与主题）。
- 被订阅的主题照旧：首次发布或消费时建通道，启动消费之前发布的消息留在通道里、启动后投递。`MaxTopics` 只约束被订阅的主题数，超出时启动失败（`MESSAGING_UNAVAILABLE_003`，`FrameworkException`）；发布不再返回这个码，只为它存在的消息键 `messaging.topic.limit` 删除（常量与十种语言的条目）。

### 理由

- 内存代理没有跨进程的消费者：没人订阅就不会有人消费，缓冲只是延后到通道排满才失败，还挤占别的主题的名额。丢弃与「交换器上没有绑定队列」的发布订阅语义一致。
- 日志用 Debug 而不是 Warning：框架事件发布到没人订阅的主题是常态，Warning 会让每次作业运行都刷日志；主题名写错时打开 `InMemoryMessageBroker` 类别的 Debug 日志即可排查。
- 订阅表在装配时就定好，以它判定可以在启动消费之前就区分「先发后消费」与「没人订阅」，启动期间发布到被订阅主题的消息不丢。

### 影响

- 行为变化：发布到没人订阅的主题以前先缓冲、排满后返回 `MESSAGING_UNAVAILABLE_002` 或超过主题上限返回 `MESSAGING_UNAVAILABLE_003`，现在总是成功并丢弃；之后再订阅也收不到这些消息。需要先发后订的留存语义用 RabbitMQ（持久队列）或 Kafka（按位点重放）。
- 公开 API（Unshipped）：`InMemoryMessageBroker` 构造多一个 `MessageSubscriptions`；删除 `MessagingMessages.TopicLimit`。`MESSAGING_UNAVAILABLE_003` 只在启动时出现。

## 知识库提示词启动时校验

### 背景

上一轮（AI-13）让 `IRagPromptAugmenter.Augment` 返回 `Result<string>`：配置了 `XiHan:AI:Knowledge:PromptName` 时每次调用才查提示词目录，模板不存在返回 `AI_NOTFOUND_002`、渲染失败返回 `AI_VALIDATION_001`。这两种都是配置错误，却要到第一次检索增强时才暴露，调用方每次都要处理一个由配置决定、与本次输入无关的失败。

### 决策

- `RagPromptAugmenter` 创建时就定下模板：没配置用内置模板；配置了就从提示词目录（配置与 `AddAIPrompt` 的合并）取它，并用代表性的 `{context}` / `{question}` 试渲染一次。模板不存在抛 `FrameworkException(AI_NOTFOUND_002)`，引用了这两个以外的占位符抛 `FrameworkException(AI_VALIDATION_001)`（消息里列出多出来的占位符），不退回内置模板。
- AI 的宿主特性在启动时解析增强器：`AIToolsFeature` 与 `VectorDataKnowledgeFeature` 的 `StartAsync`，配置错误即启动失败。只装了不带启动钩子的 AI 特性（如单独的 `OpenAIFeature`）时，在第一次解析增强器时抛出。
- `Augment` 改回返回 `string`：校验之后只用创建时取到的模板、只提供这两个参数，渲染唯一的失败原因（缺参数）不会发生，没有运行时失败的来源；不保留 `Result` 版本。

### 理由

- 模板引用是装配期就能确定的事实，配置错误应当让应用起不来，而不是在某次用户请求里才失败。
- 增强的参数固定为 `context` 与 `question`，试渲染一次就覆盖了运行时的全部情况，返回 `Result` 只会让调用方写永远走不到的分支。
- 创建时取定模板与「AI 配置不热更新」一致：之后目录里的变化不影响已经校验过的增强器。

### 影响

- 公开签名（Unshipped）：`IRagPromptAugmenter.Augment` 与 `RagPromptAugmenter.Augment` 从 `Result<string>` 改为 `string`，调用方去掉 `.ValueOrThrow()` / 错误分支。
- 启动期新增失败条件：`XiHan:AI:Knowledge:PromptName` 指向不存在的模板，或模板用了 `{context}`、`{question}` 以外的占位符，装配了 `AIToolsFeature` 或 `VectorDataKnowledgeFeature` 的应用启动失败。
- 错误码不增删：`AI_NOTFOUND_002` 仍是 `IAIChat` 请求的提示词不存在的运行时结果，`AI_VALIDATION_001` 仍用于提示词参数缺失等；知识库提示词的这两种情况变成启动失败。

## CloudEvents Webhook 出站不外推内部标识

### 背景

内部发布者（`DirectPublisher`、`OutboxPublisher`）在调用内发布时从当前调用补齐 `traceparent`、`xihantenant`、`xihanprincipal`、`xihancorrelation`、`xihanlocale` 扩展。`Protocols.CloudEvents` 的 `CloudEventsWebhookPublisher` 把信封推给外部 HTTP 端点，原样发出、不补扩展；上一轮把现状写进文档并用测试锁住，是否补齐留作待定。备选：维持现状；只补 `traceparent`；按 Webhook 配置决定；全部补齐。

### 决策

维持现状，定为规则：Webhook 发布者不外推任何内部标识，信封按调用方给出的原样发出，上述扩展都不由框架加上；要给接收方的扩展（包括 `traceparent`）由调用方显式写进信封。代码不变，现有用例 `Outbound_WebhookPublisher_SendsTheEnvelopeAsIs_WithoutTheInvocationsInternalExtensions` 锁住它。

### 理由

- Webhook 的接收方是第三方。租户 ID、主体 ID、关联 ID 是本系统的内部标识，推出去会暴露内部结构与身份信息，并让第三方依赖本该随时可变的内部 ID；全部补齐不可取。
- 追踪链要不要跨出组织边界，是每个集成自己的决定，不该由框架默认打开；只补 `traceparent` 或按配置决定都把这个决定从调用处挪走，而调用方显式写进信封已经足够。

### 影响

- 无代码与行为变化；`protocol/cloudevents.md`「出站」、RFC-0009「发布侧补齐」、包 README 与文档站写明这条规则与理由。
- HTTP 层另有一条与信封无关的传播：启用追踪时 .NET 的 HttpClient 按 W3C 在请求头里写当前 Activity 的 `traceparent`。文档写明可以在命名客户端 `xihan.protocols.cloudevents` 上以 `SocketsHttpHandler.ActivityHeadersPropagator = null` 关掉；框架没有默认关掉它。

## AI 配置不热更新

### 背景

`AIOptions` 在装配时从 `XiHan:AI` 读一次、登记为单例。RFC-0022 只就 Provider 写了「`Invalidate` 不拾取配置变化，改了要重启」，提示词、护栏、工具名、知识库是否随配置变化生效没有写明。

### 决策

不支持热更新：`XiHan:AI` 的全部配置在装配时读一次，改了要重启应用。框架不监听配置变化；`Invalidate` 只丢弃缓存的客户端、用同一份选项重建；提示词目录、工具目录、护栏、知识库选项与提示增强器都在创建时取定。不写代码，RFC-0022、AI 包 README 与文档站写明。

### 理由

- 这些配置在装配与启动时被校验（工具名、知识库提示词）并被多个单例取用。热更新要么只部分生效——换了嵌入模型而向量集合的维度没变、换了提示词而启动期校验没重做——要么要在运行中重做全部校验与重建，代价与风险都高。
- AI 配置的改动通常伴随部署，重启是可预期的生效点。

### 影响

无代码与行为变化；改 AI 配置要重启应用，这一点从「Provider 配置」扩大到全部 AI 配置并写进规范与文档。
