# ADR-0081 只读工作单元里的写入是 500 类缺陷；软删除实体的唯一索引改为部分唯一索引

## 状态

已采纳（`spec/rfcs/0005-persistence.md`、`spec/rfcs/0011-operations.md`、`spec/rfcs/0021-workflow.md` 与 `spec/conventions/error-codes.md` 随之修订）。修订 ADR-0073 第一节的错误码种类、ADR-0077 只读调用里的错误码。

## 日期

2026-11-01

## 一、只读工作单元里的写入是 500 类缺陷

### 背景

- ADR-0073 让只读操作（动词 `get` / `list`，或 `ReadOnly = true`）开只读工作单元，写入以新码 `PERSISTENCE_DENIED_001` 拒绝（HTTP 403、gRPC `PermissionDenied`，熔断不计数）。三处产生它：三个 Provider 的仓储写入（返回结果并把工作单元记为失败）、EF Core 与 SqlSugar 工作单元的 `EnsureTransactionAsync`（抛出、由 Transaction 阶段转为结果）、工作流加入只读事务时的 `IWorkflowTransaction.EnsureWritable`（ADR-0077，取锁、执行活动之前）。
- 403 让客户端与网关把它当作"已认证但没有权限"：前端走无权限提示，网关可能按越权统计，运维的 5xx 告警看不到它。可它与权限无关，换一个有权限的用户照样失败——是只读操作的实现写了数据，属于代码缺陷。
- 用户决定（第三批第 9 条）：改成 500 类错误；同一作用域的嵌套调用维持拒绝（`PERSISTENCE_VALIDATION_002`，行为不变）。

### 备选

错误码：

1. 保留 `PERSISTENCE_DENIED_001` 的编号、只改含义——不成立：错误码的 KIND 段就是 HTTP / gRPC 映射的依据（`conventions/error-codes.md`、`protocol/http.md`），`DENIED` 段的码不可能映射成 500。
2. 新码 `PERSISTENCE_UNEXPECTED_001`，撤销 `PERSISTENCE_DENIED_001`。
3. 不转结果，让异常与拒绝都落到 Observe 阶段的 `KERNEL_UNEXPECTED_001`。

撤销的旧码：保留登记标为"已撤销"（双轨），或直接删除登记。

### 决策

- 新码 `PERSISTENCE_UNEXPECTED_001`，常量仍是 `PersistenceErrors.ReadOnly`（名字说的是"只读拒绝写入"，没变），值从 `PERSISTENCE_DENIED_001` 改为它。仓储写入、`EnsureTransactionAsync`、`EnsureWritable` 三处都用 `Error.Unexpected` 构造；中间件仍只捕获这一个码、回滚并转为同码结果。
- `PERSISTENCE_DENIED_001` 从错误码表删除，不保留兼容：5.0 尚未发布，编号规则"一经发布不复用"约束的是已发布的码，没有发布过就没有要保护的客户端，留一个"已撤销"的码只会让人以为两个都会出现。
- 消息键沿用 `persistence.unit_of_work.read_only`，十种语言的文案补一句"这是操作实现的缺陷"。
- 映射：HTTP 500、gRPC `Internal`、命令行按 UNEXPECTED 的退出码；熔断按操作 ID 计数（RFC-0004 计 UNAVAILABLE / TIMEOUT / UNEXPECTED）。
- 不变：同一服务作用域里再经管道的嵌套调用仍以 `PERSISTENCE_VALIDATION_002` 结束内层；只读工作单元不开事务、写入时拒绝、拒绝即把工作单元记为失败、处理器忽略也以同一错误结束；嵌套调用各开自己的工作单元、只读不传播。

### 理由

- 500 才是缺陷的位置：告警、错误率与 SLO 按 5xx 统计，只读操作写数据这种上线后必须修的问题应当出现在那里，而不是混进 403 的越权统计；客户端也不会把它当成权限不足去提示用户换账号。
- 转为同码结果而不是交给 Observe 阶段：状态码同为 500，但 `PERSISTENCE_UNEXPECTED_001` 与本地化文案直接说明是只读写入，`KERNEL_UNEXPECTED_001` 只能说"发生未处理异常"；而且仓储写入本来就是结果，三处产生同一个码，排查只认一个码。
- 计入熔断可以接受：熔断按操作 ID 各一份，有缺陷的只读操作每次都会失败，熔断只挡住它自己；没有为它配置熔断的操作不受影响。ADR-0073 当时以"熔断会把确定性缺陷当成下游故障"否决 UNEXPECTED，这条在按操作隔离的熔断下代价有限，由用户的决定取舍。

### 影响

- 行为（BasicApp 升锁要改的）：只读操作里的仓储写入、`EnsureTransactionAsync`、工作流写入，从 403 `PERSISTENCE_DENIED_001` 变为 500 `PERSISTENCE_UNEXPECTED_001`；gRPC 从 `PermissionDenied` 变为 `Internal`；配置了熔断的只读操作，这类失败计入熔断。管道外以 `UnitOfWorkOptions(IsReadOnly: true)` 开的工作单元里写入，同样返回新码。
- 排查：日志与响应里的 `code` 是 `PERSISTENCE_UNEXPECTED_001`、`type` 是 `urn:xihan:error:PERSISTENCE_UNEXPECTED_001`；找到响应对应的操作 ID，它是只读的（动词 `get` / `list` 或声明了 `ReadOnly = true`），在它的处理器（及它在同一作用域里调用的服务）里找新增、更新、删除、`EnsureTransactionAsync` 或工作流的发起 / 办理。改法与 ADR-0073 相同：去掉只读、换非只读的动词，或把写入放进新服务作用域里的另一次调用。客户端或网关里按 `PERSISTENCE_DENIED_001` / 403 判断的代码要删掉。
- 公开 API（都在 Unshipped）：`PersistenceErrors.ReadOnly` 的值变化，签名不变。
