# ADR-0025 领域事件派发：工作单元登记写过的聚合，Transaction 阶段提交前经 `IDomainEventDispatcher` 发成 CloudEvents

## 状态

已采纳（RFC-0005 / RFC-0009 修订）。

## 日期

2026-10-27

## 背景

`Domain` 的 `IHasDomainEvents` / `DomainEventBuffer` 没有任何读取方：三个持久化 Provider 不取、不发、不清，`SimpleApp/Orders/Order.cs` 的注释（"工作单元提交后由持久化子系统取走并清空"）与实现不符，`CreateOrder` 手动把订单响应包成 CloudEvents 经 `IMessagePublisher` 发布。BasicApp 6.0 的聚合要靠领域事件驱动审计、通知与跨模块联动，用户于 2026-10-27 决定在框架里实现。约束：`Persistence.Abstractions` 不能引用 `Messaging.Abstractions`（后者已引用前者，发件箱用仓储）；事件对象的序列化不能反射（AOT）。

## 备选

1. 持久化 Provider 各自在提交后发布：三份实现，且 Provider 要引用 Messaging。
2. `Persistence.Abstractions` 定义派发端口 `IDomainEventDispatcher`，工作单元登记写过的聚合，`UnitOfWorkMiddleware` 在提交前调用端口；`Messaging.Abstractions` 实现端口，把事件映射成信封经 `IMessagePublisher` 发布。
3. 提交之后再发布（直接发布时不会发出已回滚数据的事件，但与发件箱"同事务"矛盾：提交后工作单元已结束，发件箱发布者会退化成直接发布）。
4. 提交之前发布（与现状 `CreateOrder` 在处理器里发布一致：发件箱时同事务、精确一次；直接发布时先于提交、至多一次，发布失败回滚）。
5. 事件到信封的映射靠反射读事件类型名与属性。
6. 应用显式登记每种事件：主题、CloudEvents `type`、源生成的 `JsonTypeInfo`、可选 `subject` 选择器；未登记即失败。
7. 没有注册派发器时静默忽略事件。
8. 没有注册派发器却有事件时以 `PERSISTENCE_VALIDATION_003` 结束调用。

## 决策

采用备选 2、4、6、8。

- `Persistence.Abstractions`：`IUnitOfWork.DomainEvents`（`DomainEventTracker`：按首次写入顺序登记实现 `IHasDomainEvents` 的实体，同一实例一次，`Drain()` 取出带有未派发事件的聚合）与端口 `IDomainEventDispatcher`（`DispatchAsync(aggregates, tenantId, ct) → Result`）。三个 Provider 的仓储在新增 / 更新 / 删除（单条与批量，通过校验的项）成功后 `Track`。`UnitOfWorkMiddleware`：处理器成功 → 若有聚合带事件：没有派发器 → `PERSISTENCE_VALIDATION_003` 并回滚；有 → 派发，失败回滚并以失败结果结束，成功清空缓冲 → 提交。
- `Messaging.Abstractions/DomainEvents`：`DomainEventRegistry`（事件类型 → `DomainEventRegistration`：主题、类型、`JsonTypeInfo`、`subject` 选择器；容量 10000，重复登记 / 超容抛 `MESSAGING_VALIDATION_004`）、`AddDomainEvent<TEvent>(services, topic, type, jsonTypeInfo, subject?)`（首次调用 `TryAddScoped<IDomainEventDispatcher, DomainEventDispatcher>`）、`DomainEventDispatcher`：信封 `id` = UUID v7、`source` = `/{topic}`、`type`、`subject`、`time` = `OccurredAt`、`data` = JSON、`xihantenant` 扩展；按主题分组一次 `PublishManyAsync`（批量优先），任一项失败即失败；未登记的事件类型 → `MESSAGING_VALIDATION_003`。
- `Persistence.Conformance` 加用例：事件在提交时派发且缓冲清空、失败的调用不派发、派发器失败回滚、没有派发器时 `PERSISTENCE_VALIDATION_003`。
- `SimpleApp`：`CreateOrder` 不再手动发布；`OrdersFeature` 登记 `OrderPlaced`（主题 `orders`、类型 `orders.placed`）；`OrderPlacedHandler` 照旧计数。

## 理由

- 端口放持久化抽象、实现放消息抽象，既不让持久化依赖消息，也不让三个 Provider 各写一份（备选 1）。
- 提交前派发（备选 4）是与发件箱同事务的唯一方式，也与现有处理器内发布的语义一致；直接发布的至多一次是没有发件箱时的固有代价，README 与 RFC 写明"要精确一次就装发件箱"。
- 显式登记（备选 6）零反射、可 AOT，主题与类型名由应用决定而不是从类型名猜；未登记即失败比猜一个主题诚实。
- 不静默忽略（备选 7 → 8）：聚合记了事件就是要发出去，没有派发器是装配错误，应在第一次调用时暴露；没有事件的调用不受影响，只用 `DomainEventBuffer` 做进程内处理的应用自己在提交前清空即可。

## 影响

- `IUnitOfWork` 新增 `DomainEvents` 成员（Stable 契约在 preview 期间的增补），三个 Provider 实现；仓储写入路径多一次登记。
- 新错误码 `PERSISTENCE_VALIDATION_003`、`MESSAGING_VALIDATION_003` / `_004` 与消息键 `persistence.unit_of_work.events_undispatched`、`messaging.domain_event.unregistered`（10 种区域）。
- `Messaging.Abstractions` 新功能区 `DomainEvents`（`03-代码规范` 分区表登记）。
- 行为变化：之前聚合里积累的事件被静默丢弃；现在没有派发器会让带事件的调用失败——装配 `Messaging.*` 并 `AddDomainEvent` 即可。
