# ADR-0051 绕过管道的端点认证

## 状态

已采纳（`spec/rfcs/0008-security.md` 增「绕过管道的端点」一节）。

## 日期

2026-10-29

## 背景

BasicApp 6.0 N2 第五批（Realtime）报告：SignalR Hub 不经内核管道（长连接不受截止时间约束，内核停止时不被 503 打断），内核管道的认证管不到它。

应用只好自己按 `JwtOptions` 手工配一个 JwtBearer 方案，照抄 `JwtAuthenticationHandler` 的校验项：密钥、签发者与受众、容差、名称与角色声明、不映射入站声明、按路径从查询串读令牌。它也没有办法从连接建调用上下文，会话门禁与审计都要自己补。4.x 的框架自带 Hub 认证与会话门禁过滤器。

## 备选

1. `Security.Jwt` 按 `JwtOptions` 登记 JwtBearer 方案，与处理器共用一份校验参数：
   - Ring 3 的 `Security.Jwt` 要引用 ASP.NET Core 共享框架与 JwtBearer 包，非 Web 宿主也得带上。
   - 只管 JWT，OIDC 与 ApiKey 照样没有。
2. `Hosting.AspNetCore` 提供一个 ASP.NET Core 认证方案，把凭据交给内核已装配的 `IAuthenticationHandler`。

## 决策

采用 2（重构设计会话确认）。

- **方案 `XiHan`**（`AddAuthentication().AddXiHan(o => o.QueryTokenPaths.Add("/hubs"))`）：
  - 可多次调用：方案只登记一次，各次的配置依次生效。
  - 不设为缺省方案；端点经 `RequireAuthorization` 的策略选用它。
  - 只认带 `PipelineBypassMetadata` 的端点。只登记这一个方案时 ASP.NET Core 会把它当作缺省方案，此时普通请求按未认证处理，由管道认证，不重复认证、不调用挂点。
- **凭据**（`HttpInvocation.CredentialOf`，方案与 `CreateContext` 共用）：
  - 先取 `Authorization` 头。
  - 没有时，只有请求路径（不含 PathBase）按路径段、不区分大小写落在登记的 `QueryTokenPaths` 下，且 `access_token` 只有一个非空值，才作为 `Bearer` 凭据。
  - 其他路径的查询串令牌一律忽略，请求按匿名处理。
  - 前缀不能为空或 `/`，在方案初始化时校验。
- **认证**：
  - 以请求建调用上下文（`HttpInvocation.CreateContext(httpContext, services)`，同一套载体映射，不记入 `HttpContext.Items`），交给方案匹配的内核处理器。
  - 方案不支持、凭据无效都是认证失败，失败原因只进日志。
  - 质询沿用 `AuthenticationChallenge`：无效凭据质询被拒的方案（Bearer 带 `invalid_token`）；不支持的方案与没有凭据一样，按已装配的方案逐个质询。
- **挂点 `IInvocationAuthenticationFilter`**：
  - 认证成功后按登记顺序调用，上下文已写入主体。
  - 任一返回失败即认证失败。
  - 会话门禁由应用实现（BasicApp 用 `ISessionStatus`）；框架不判定会话。
- **主体**：转成 `ClaimsPrincipal`，身份认证类型 `XiHan`。
  - 声明按原始类型名保留。
  - 另加 `ClaimTypes.NameIdentifier` 承载主体 ID 并作为名称声明，SignalR 的 `UserIdentifier` 随之可用。
  - 角色声明类型取 `SecurityOptions.RoleClaim`。
- **从连接建上下文**：`HttpInvocation.CreateContext(httpContext, services)` 按同一规则带凭据。Hub 以连接的 `HttpContext` 建上下文后 `App.InvokeAsync`，管道照常重新认证、过会话门禁、记审计。长连接上的令牌过期后，新的调用会被拒。

## 理由

- 校验只有一份：方案就是把凭据交给管道里同一个处理器，JWT、OpenID Connect、ApiKey 不用各接一遍，换认证 Provider 不用改宿主。
- 环层不变：ASP.NET Core 的类型留在 Ring 4 的宿主包，`Security.*` 仍不依赖 Web。
- 查询串令牌只在登记的路径下生效：查询串会进访问日志与代理日志，只给带不了请求头的客户端用；没登记的路径带令牌一律当匿名，不能拿它绕开头部要求。
- 只认绕过管道的端点：避免单一方案成为缺省方案后每个普通请求被认证两次、挂点被多调一次。

## 影响

- 公开 API：`Hosting.AspNetCore` 新增 `Authentication.*`：
  - `InvocationAuthenticationDefaults`（`XiHan`、`access_token`、`Bearer`）。
  - `InvocationAuthenticationOptions`（`QueryTokenPaths`、`AcceptsQueryToken`）。
  - `InvocationAuthenticationHandler`、`IInvocationAuthenticationFilter`、`AddXiHan`。
- 行为：`HttpInvocation.CreateContext` 在登记过查询串令牌路径时，也从这些路径的 `access_token` 取凭据；没登记时与原来相同。
- BasicApp：删掉 `RealtimeAuthentication`，Hub 的授权策略改指向 `XiHan` 方案，会话核对改为实现 `IInvocationAuthenticationFilter`。
- 测试（`Security.Jwt.Tests`）：
  - 头部与查询串令牌经内核 JWT 处理器认证：名称、认证类型、角色、原始声明。
  - 没登记的路径（含 `/hubsx` 这种前缀相似的）与多值查询串令牌被拒（401），同一路径带头放行。
  - 过期令牌与不支持的方案的质询。
  - 挂点拒绝。
  - 端点内建上下文经管道重新认证；普通端点不被重复认证、挂点不被调用。
  - ApiKey 走同一条路。
  - 选项校验与按路径段匹配。
