# ADR-0092 插件清单的中间件贡献在发现时被拒与超时归因两条路径统一

## 状态

已采纳（`spec/rfcs/0002-manifest.md`、`spec/rfcs/0003-invocation-context.md`、`spec/rfcs/0004-pipeline-stages.md`、`spec/rfcs/0017-plugin-protocol.md`、`spec/rfcs/0018-wasm-plugins.md`、`spec/conventions/error-codes.md`、`spec/manifest/manifest.schema.json` 与 `spec/plugin/` 的 `lifecycle.md`、`invocation.md`、`wasm.md` 随之修订）。修订 ADR-0088：第一节「截止令牌与外部令牌同时触发、下游写下取消结果时保持取消」改为报超时；第二节末段「进程外宿主不读清单的 `contributes.pipeline`，进程内宿主给插件的 `PluginContext.Pipeline` 恒为空，不改」改为清单写了即在发现或加载时拒绝。

## 日期

2026-11-01

本 ADR 记录第六批回灌里宿主分区的两项决定（`j-batch-backlog.md` 第 5、6 条，来由是 ADR-0088 留下的两项待定），每项一节。

## 一、进程外与进程内插件的清单写了 `contributes.pipeline` 在发现时被拒（第 5 条）

### 背景

RFC-0017 规定进程外插件不可贡献中间件，插件指南的清单表也写着 `contributes.pipeline`「只用于 Wasm」，但进程外宿主与握手核对都不读这个字段：清单写了照常加载，作者以为中间件生效了，实际一次也没执行。进程内宿主同样不读，给插件的 `PluginContext.Pipeline` 恒为空。安全相关阶段（认证、租户、授权）的中间件静默缺席最危险。ADR-0088 核对插件中间件撤回时记为待定。

### 备选

1. 在发现时拒绝，走现有的「发现时被拒」路径（采纳）。
2. 启动失败：与「插件失败不阻止宿主启动」的整体约定（`plugin/lifecycle.md` §4）相反；其他清单不合格的情形（隔离级别不符、缺 `entry`）都是发现时被拒，不该单独特殊。
3. 照常加载、记一条警告：仍是静默的一种，日志没人看时作者照样以为它生效。
4. 让进程外插件也能贡献中间件：RFC-0017 已经否决过（中间件在宿主进程内，跨进程调用的延迟与失败语义不适合管道阶段），不在本批范围。

### 决策

- 进程外：`OutOfProcessPluginHost` 在启动任何插件代码之前的检查里先核对清单 `contributes.pipeline`，非空即 `PLUGINS_VALIDATION_001`（`PluginErrors.InvalidSource`），先于权限、入口与可执行文件。配置阶段按目录发现的插件按发现时被拒处理：不启动进程、以 `Failed` 登记（带错误、可 `Describe`）、是健康条目 `plugins.<清单 ID>`、宿主附着到容器时记错误日志、不重试，宿主照常启动并进入 `Degraded`。运行期 `LoadAsync` 把同一错误直接返回给调用方、不登记。
- 进程内：`InProcessPluginHost.LoadAsync` 在核对种类与隔离级别之后、权限与程序集之前同样拒绝，不加载任何代码。进程内宿主只有运行期加载，失败一律返回给调用方。
- 错误码沿用 `PLUGINS_VALIDATION_001`：它的含义「插件清单、种类或隔离级别不合法」本就是清单与隔离级别不匹配的那一类，只扩充说明，不新增码。新消息键（10 种区域）：`plugins.process.pipeline_unsupported`（`Plugins.Protocol` 的 `PluginMessages.PipelineUnsupported`，进程外）、`plugins.manifest.pipeline_unsupported`（`Plugins.InProcess` 的 `PluginMessages.PipelineUnsupported`）；参数 `id`、`middleware`（声明的中间件名，逗号分隔）。
- 规范：RFC-0017「范围」写明只有 Wasm 插件能贡献中间件以及拒绝的方式，错误码表补 `PLUGINS_VALIDATION_001`；`plugin/lifecycle.md` §1 的发现时被拒条件加上这一条；`plugin/invocation.md` §1 与 §7；RFC-0002 `contributes` 一行与清单 Schema 的 `pipeline` 说明；`conventions/error-codes.md` 的 `PLUGINS_VALIDATION_001`。
- 一致性套件 `PluginProtocolConformance` 用例 1 另核对清单不写 `contributes.pipeline`，其他语言写的插件在自己的 CI 里就能发现。

### 理由

- 「不静默」是这一条的全部诉求：同类的清单不合格都按发现时被拒，这一条照同一条路径走，诊断方式不变（`Describe`、健康条目、错误日志），宿主仍不因插件而退出。
- 先于权限判定：清单本身不合格，与宿主授予了什么无关，与「不是进程外插件」同属一类。
- 不在清单 Schema 里加约束：`contributes.pipeline` 对能力包（`kind: capability`）是合法的，Schema 不按隔离级别分支；拒绝放在知道隔离级别的宿主里，Schema 只加说明。

### 影响

- 新的发现时被拒条件：进程外插件的清单写了非空 `contributes.pipeline`——插件 `Failed`、宿主 `Degraded`、照常启动；运行期 `LoadAsync` 返回 `PLUGINS_VALIDATION_001`。进程内插件的这类清单 `LoadAsync` 返回 `PLUGINS_VALIDATION_001`。以前两者都照常加载、中间件被忽略。
- 公开 API：新增常量 `XiHan.Framework.Plugins.Protocol.PluginMessages.PipelineUnsupported`、`XiHan.Framework.Plugins.InProcess.PluginMessages.PipelineUnsupported`。没有新错误码、配置键与表结构变化。
- Go SDK（framework-sdk-go）不改：它的清单模型对能力包与插件通用，拒绝在宿主；用一致性套件跑的 Go 插件会在用例 1 报出。
- 测试：清单带 `contributes.pipeline` 的进程外插件在发现时被拒（`Failed`、错误码、消息键与 `middleware` 细节、没有进程、代理操作未登记、健康条目 `Failed`、宿主 `Degraded` 照常启动、错误日志），卸载后运行期 `LoadAsync` 返回同一错误、不登记；进程内插件的完整副本只在清单里加一项中间件贡献，加载被拒、不登记。两例在去掉核对时都失败（进程外插件 `Ready`，进程内插件照常加载）。

## 二、截止时间与调用方取消同时触发时两条路径统一报超时（第 6 条）

### 背景

ADR-0088 第一节保留了 `DeadlineMiddleware` 的归因：下游写下的 `KERNEL_CANCELLED_001` 结果在截止令牌已触发、外部令牌没有触发时改写为超时。两个令牌同时触发时（客户端在截止时间到点前后断开），抛出的取消按「超时优先」报超时，写成结果的取消却保持取消——同一件事按下游的写法得到两种回答。第五批把它当作小的不一致写进了 RFC-0004，留作待定。

同时，第四批的文档要求「下游不要用 `IsExpired` 区分超时与取消，写下取消结果，交给 `DeadlineMiddleware` 归因」，框架自己的下游却还在按时钟判断：进程外插件运行时把 `context.IsExpired(clock.GetUtcNow())` 传给 `PluginErrorMapper.FromRpc`，gRPC 的 `Cancelled` 在时钟过了截止时间时改报超时；Wasm 运行时的 `Expired` 把插件写下的取消同样改报超时。定时器晚于时钟读数到达时（线程池繁忙、定时器合并），调用方的取消会被它们报成超时，而同一情形下抛出的取消是取消。Wasm 宿主函数交给插件的回调结果有两条路径：不再等待（`Abandoned`）按「回调计时器已触发或时钟已过截止时间」判断，回调已返回只看时钟，计时器已触发而时钟读数未到时报取消。

### 备选

1. 两条路径都按「截止令牌已触发即超时」，不论外部令牌；框架的插件运行时不再按时钟归因（采纳）。
2. 两条路径都按「外部令牌已触发即取消」（取消优先）：截止时间到了是调用方给定的事实，客户端同时断开时报取消就丢了这个事实；还要回退抛出路径既有的「超时优先」，变动更大。
3. 维持现状、只写进规范（第五批的做法）：同一情形两种状态码，按状态码决定重试或统计的一方无法据此行事。
4. `DeadlineMiddleware` 另看时钟（截止令牌已触发或时钟已过截止时间即超时）：能覆盖定时器晚到的情形，但把第四批去掉的时钟判断又带回内核，令牌之外多一个来源；用户定的规则是按截止令牌归因。

### 决策

- `DeadlineMiddleware`：下游正常返回、结果是 `KERNEL_CANCELLED_001`、截止令牌已触发时改写为 `KERNEL_TIMEOUT_001`，去掉「外部令牌没有触发」的条件；抛出路径不变。两条路径同一规则：截止令牌已触发即超时，不论外部令牌是否也已触发；截止令牌没有触发、外部令牌已触发即取消。
- 插件运行时随之统一，不再按时钟归因：
  - 进程外：内部类型 `PluginErrorMapper.FromRpc` 去掉 `deadlineExpired` 参数，gRPC `Cancelled` 一律 `KERNEL_CANCELLED_001`（`DeadlineExceeded` 仍是超时）；`PluginRuntime` 的操作调用与事件投递不再传 `context.IsExpired(clock)`。
  - Wasm 运行时：去掉 `Expired`，操作与事件的结果原样返回。
  - 两者都在管道里（操作经调用器、事件经派发器的 `App.InvokeAsync`），由外层的 `DeadlineMiddleware` 归因。
  - Wasm 宿主函数：回调交给插件的结果不再经过任何中间件归因，宿主保留判断，但不再等待与回调已返回两条路径改用同一判断 `DeadlineReached`——回调计时器已触发或时钟已过截止时间。计时器先看：它与外层的截止令牌按同一个时钟落下；时钟兜住外层令牌先于本地计时器触发的情形，那一刻宿主分不出外层是到了截止时间还是被调用方取消。
- 规范：RFC-0004 `DeadlineMiddleware` 一条与「行为变化」小节（改名为「截止时间到了一律报超时」，补本次统一的背景、旧行为、新行为、对调用方的影响，新增「下游的归因」一条）、RFC-0003 第 1 条、`conventions/error-codes.md` 的 `KERNEL_TIMEOUT_001` / `KERNEL_CANCELLED_001`、`plugin/invocation.md` §3 的 `Cancelled` 一行、`plugin/wasm.md` §4，RFC-0017 / RFC-0018 头部记修订。

### 理由

- 截止时间到了是确定的事实，回答不应取决于下游是抛出还是写成结果。
- 归因只在知道令牌来源的一个位置：下游按时钟判断，定时器早到会把超时报成取消，晚到又会在调用方取消时报成超时，两个方向都会与抛出路径不一致；框架自己的下游先照自己的文档做。
- 调用方已经取消时，回答通常已无人接收，影响落在审计、追踪、访问日志与指标里；统一之后同一类事件只有一个错误码，统计与告警不再按下游的写法分裂。

### 影响

- 行为：截止令牌与外部令牌都已触发、下游把取消写成结果的调用（进程外与 Wasm 插件、自己接住取消的操作或 Provider），由 `KERNEL_CANCELLED_001`（HTTP 408、gRPC `Cancelled`、命令行退出码 8）变为 `KERNEL_TIMEOUT_001`（504、`DeadlineExceeded`、7）。调用方通常已断开，主要影响 Observe 阶段的审计记录、追踪与访问日志；调用方的取消令牌由别的原因触发而连接仍在时，看到的是 504。
- 插件运行时：截止令牌没有触发、调用方已取消、而时钟已过截止时间（定时器晚到）时，进程外与 Wasm 运行时以前报超时，现在报取消，与抛出路径一致。关掉内置中间件（`XiHan:Kernel:UseBuiltInMiddleware=false`）时不再有按时钟的超时改写——那时内核本来就不把截止时间落成取消；进程外插件的 gRPC 截止时间仍报 `DeadlineExceeded` → 超时，Wasm 调用时限仍报超时。
- 熔断计数不变（`ResilienceMiddleware` 看下游写下的原结果）。
- 没有公开 API、错误码、消息键、配置键与表结构变化（`PluginErrorMapper` 是内部类型）。
- 测试：内核 `DeadlineAttributionTests`（注入时钟，下游等用例触发完令牌再观察）覆盖只有截止时间、只有调用方取消、截止时间先到再取消、取消后截止时间再到四种触发 × 下游抛出 / 写成结果，修前「两者都触发 × 写成结果」两例失败；进程外插件调用进行中（回调一直等待的宿主操作）时到截止时间、调用方取消、两者都发生的端到端用例；Wasm 回调等待期间调用方取消（取消）与截止时间先到再取消（超时）；`PluginErrorMapper` 的取消与超时在进程已退出时也保持内核错误码。

第二节备选 4「`DeadlineMiddleware` 另看时钟」由 ADR-0095 第一节定为不做，维持只按截止令牌归因。第一节「影响」里「Go SDK（framework-sdk-go）不改」由 ADR-0095 第三节修订：Go SDK 读清单时同样拒绝进程外与进程内插件的 `contributes.pipeline`。AI Provider 的超时与调用方取消同时发生时按同一原则报超时，见 ADR-0095 第二节。
