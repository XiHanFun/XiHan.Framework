# ADR-0064 发件箱死信与幂等响应回放

## 状态

已采纳（`spec/rfcs/0009-messaging.md`「发件箱」改写；`spec/rfcs/0006-caching.md`「幂等」第 2、4 条与 `spec/rfcs/0011-operations.md` 执行规则第 8 条）。

## 日期

2026-11-01

## 背景

### 发件箱

文档站写作时发现 `OutboxDispatcher` 有三个问题：

- 没有尝试上限，也没有死信。无法解码的行每一轮都失败，失败的行永远是「未投递」。
- 每轮按创建时间取 `BatchSize` 条未投递的消息。只要有不少于 `BatchSize` 条永久失败的消息排在前面，后面的消息就永远取不到，整个发件箱停摆。
- 投递成功的行只记 `DispatchedAt`、从不删除，表无界增长。

`OutboxMessage` 的 `Topic` 与 `LastError` 也没有声明长度。SqlSugar 在 PostgreSQL 上把没有长度的字符串建成 `varchar(255)`，失败原因（`[错误码] 文案`，文案里常带代理的异常信息）一超长，这一轮的批量更新就失败、整轮回滚，同一批消息下一轮再来一遍。

### 幂等回放

RFC-0006 写着「回放的是调用结果，不是响应体；操作契约（P3）在此之上回放响应」，但操作契约这一层一直没有做：

- `IdempotencyMiddleware` 回放时只设调用结果，Handle 不执行，上下文里没有响应对象。
- 调用器的 XGI 入口因此返回成功而载荷为空。类型化入口找不到响应，返回 `KERNEL_UNEXPECTED_001`（`OperationInvoker` 的 `ToTypedResult`）。
- HTTP 端点在 Handle 里执行，回放时端点不执行，`UseXiHan()` 只在失败时写 Problem Details，客户端拿到 200 加空正文；`create` 本该是 201。
- `WasReplayed` 全仓没有调用方。

此外，作用域键只有（租户、主体、键），不含操作。同一个键被另一个操作复用时，会把前一个操作的结果当成这一个的结果回放。

## 决策

### 发件箱

- 每轮只取到期的消息：未投递、未进死信，`NextAttemptAt` 为空或已到。仍按创建时间排序，最多 `BatchSize` 条。
- 每条计一次尝试：
  - 成功记 `DispatchedAt`。
  - 失败记 `LastError`，`NextAttemptAt` 推后 `RetryDelay × 2^(尝试次数 − 1)`，不超过 `MaxRetryDelay`。缺省 5 秒起、5 分钟封顶。
  - 尝试达到 `MaxAttempts`（缺省 10）记 `DeadLetteredAt`，进死信。载荷无法解码时不等次数用尽，直接进死信。
- 死信留在表里，循环不再取它。把 `DeadLetteredAt` 置空、`NextAttemptAt` 设为现在，就会重新投递。
- 代理整批抛出（不可达）时本轮照旧回滚，不计尝试。
- 投递成功的行保留 `DispatchedRetention`（缺省 1 天），过后由循环删除。每轮最多删 `BatchSize` 行，与投递同一个工作单元。保留期为 0 时，投递成功即在同一工作单元删除。死信行不自动删除。
- 表结构：
  - `Topic` 标 `[StringLength(128)]`，与主题文法的上限一致。
  - `LastError` 标 `[LongText]`。
  - 新列 `NextAttemptAt`、`DeadLetteredAt` 可空。列加在已有数据的表上时旧行为空，视为到期、未进死信。
- 新选项都在 `XiHan:Messaging:Outbox`：`MaxAttempts`、`RetryDelaySeconds`、`MaxRetryDelaySeconds`、`DispatchedRetentionSeconds`。

### 幂等回放

- 首次执行保存响应：处理器完成后，操作调用（上下文里有操作描述）的记录另带操作 ID；成功且上下文里有响应对象时，用 `OperationDescriptor.EncodeResponse` 编成 XGI 的 JSON，作为 JSON 值嵌进记录（`IdempotencyRecord.Operation`、`Response`）。
- 回放时还原：
  - 记录的操作 ID 必须与本次调用的一致，都不是操作调用时都为空。不一致返回 `CACHING_CONFLICT_003`（消息键 `caching.idempotency.key_reused`，参数 `operation`、`recorded`）。
  - 失败记录照旧回放为同一个错误。
  - 成功的操作调用用 `OperationDescriptor.DecodeResponse` 把记录的响应解码回对象，写进上下文。记录里没有响应或解码失败，返回 `CACHING_CONFLICT_003`（消息键 `caching.idempotency.response_unavailable`），不返回空载荷。
- `Kernel` 的 `OperationDescriptor` 增虚方法 `DecodeResponse`，是 `EncodeResponse` 的逆：缺省按 `ResponseInfo` 解码（源生成元数据，不经反射），插件代理覆写为原样包成载荷。
- 调用器不改：响应对象在上下文里，XGI 入口照常编码，类型化入口照常取出。
- HTTP：
  - `Hosting.AspNetCore` 增委托 `OperationResponseWriter`（写出成功响应：状态码、内容类型与正文），`Protocols.Http` 把它挂在每个操作端点的元数据上，端点执行时也用它写。
  - `UseXiHan()` 在管道成功结束、响应未开始、端点带写出方式、上下文里有操作与响应对象时，用它写出。端点执行过的请求响应已经开始，不会写第二次。
- 不比对请求内容：同一个键配不同的请求体，照样回放首次的响应。

## 理由

### 发件箱

- 退避而不是只加上限：只加上限时，失败的消息仍在每一轮排在最前面重试，直到次数用尽才让路。代理短暂拒收（磁盘告警、nack）时，所有消息会在几秒内耗尽次数、集体进死信。有了退避，退避中的消息不占批次，后面的消息照常投递；缺省参数下一条消息要连续失败约 20 分钟才进死信。
- 死信留在表里而不是发到代理的死信主题：进死信的原因往往就是代理不收或载荷坏了，再发一次多半同样失败；`IMessageBroker` 也只收信封，解不开的载荷没法发。行留在表里，原因（`LastError`）、次数与时间都在，便于排查与人工重投。
- 代理整批抛出不计尝试：那是基础设施故障，不是这条消息的问题。计入的话，一次几分钟的停机会把积压的消息全部送进死信。
- 保留期而不是立即删除：保留一段时间便于排查「这条消息发没发出去」；需要最小表的应用把保留期设为 0。清理每轮一批，与投递同节奏，吞吐与投递一致，不会出现一次删除大量行的长事务。
- 新列可空：给已有数据的表加列时，SqlSugar 只为数值、枚举、布尔与 Guid 列配缺省值回填旧行（ADR-0040），日期列要可空。空值有明确语义（到期、未进死信），升级时旧行照常投递。

### 幂等回放

- 回放在中间件里而不是调用器里：中间件拿着幂等记录，回放时 Handle 不执行，调用器根本没有机会补响应；内核也不能引用缓存子系统。中间件把响应放进上下文，调用器与宿主端点按已有的方式取用，四个入口与各协议一起生效。
- 存 XGI 的 JSON 而不是对象：存储是跨进程的字节存储。JSON 是 XGI 的规范编码，HTTP、gRPC、MCP 本来就按它编码，回放给出的载荷与首次调用逐字节一致；类型化入口拿到的是按同一份元数据解码出的等值对象。
- 嵌成 JSON 值而不是 Base64：记录可读，管理界面看缓存条目时能直接看到响应；大小与 Base64 相当或更小。
- 操作 ID 不一致即冲突：把一个操作的响应当成另一个操作的响应回放，类型对不上时解码失败，类型碰巧对上时更糟，调用方拿到错误的数据。冲突是 CONFLICT 种类（HTTP 409），提示调用方换一个键。
- 没有响应时报错而不是返回空载荷：空载荷在 XGI 上是「成功但没有数据」，在类型化入口上是意外错误，两者都把问题藏到了更远处。修复前写下的成功记录不带操作 ID，升级后 24 小时（`TimeToLive`）内同一个键重放会得到冲突，换键即可。
- 写出方式挂在端点元数据上：状态码约定（`create` 为 201）属于 `Protocols.Http`，`Hosting.AspNetCore` 不引用它。这与载荷绑定 `OperationPayloadBinder` 的做法一致，端点执行与回放写出的响应一致。
- 不比对请求内容：比对需要在记录里存请求摘要，并且要先定义「同一个请求」（字段顺序、缺省值、路由值与请求体的合并）。RFC-0006 的语义是「同一个键是同一次业务意图」，这里保持不变；需要防误用的应用可以在 Validate 阶段自己校验。

## 影响

### 发件箱

- 公开 API：`OutboxMessage` 增 `NextAttemptAt`、`DeadLetteredAt`；`OutboxOptions` 增 `MaxAttempts`、`RetryDelay`、`MaxRetryDelay`、`DispatchedRetention` 与 `RetryDelayAfter(attempts)`。
- 行为：
  - 失败的消息不再无限重试，用尽次数后进死信（日志 Error 级别）。
  - 投递成功的行缺省一天后被删除。依赖「投递过的行一直在」的应用要调大保留期。
  - `OutboxPublisher` 写入时 `NextAttemptAt` 等于创建时间。
- 表结构：已有的发件箱表要加两列（可空），`Topic` 长度改为 128，`LastError` 改为长文本。SqlSugar 开着 `InitTables` 时自动补列；EF Core 的应用随模型迁移。
- 已知限制：
  - 某一条消息让代理整批抛出（比如超过帧上限导致通道关闭）时，它所在的批次每轮回滚，依然会卡住；这种消息只能人工处理。
  - 到期判定的或条件写在最前面。SqlSugar 把 `A && B && (可空值 == null || …)` 译成丢了 `OR` 的 SQL（SQLite 上是语法错误），换成先写或条件的等价形式后译对。这是持久化包的翻译缺陷，另行修复。
- 测试：
  - `OutboxDispatcherTests`（内存持久化、可推进的时钟、脚本代理）覆盖：无法解码直接进死信，退避按倍数增长并受上限约束，次数用尽进死信，永久失败的消息不挡后面的消息，保留期过后删除已投递行、死信留着，保留期为 0 时当场删除并分批清理旧行，代理不可达时回滚且不计尝试，`NextAttemptAt` 为空的旧行照常取到。
  - `SqlSugarOutboxTests` 在 SQLite 上覆盖：列长与长文本，到期判定的可空比较，死信不再取到，保留期清理。

### 幂等回放

- 公开 API：
  - `Kernel`：`OperationDescriptor.DecodeResponse`（虚方法）。
  - `Caching.Abstractions`：`IdempotencyRecord` 增 `Operation`、`Response`；`CachingErrors.IdempotentMismatch`（`CACHING_CONFLICT_003`）；消息键 `caching.idempotency.key_reused` 与 `caching.idempotency.response_unavailable`，十种区域齐全。
  - `Hosting.AspNetCore`：`OperationResponseWriter`。
- 行为：
  - 带幂等键的操作调用重放时拿到首次的响应：XGI 载荷逐字节一致，类型化对象等值，HTTP 状态码与正文一致。
  - 同一个键跨操作复用，或在操作与非操作调用之间复用，由「回放别人的结果」改为 `CACHING_CONFLICT_003`。
  - 记录变大：操作调用成功的响应随记录保存 `TimeToLive`（缺省 24 小时）。响应很大的操作带幂等键时，要考虑存储的容量。
- 测试：
  - `IdempotentOperationReplayTests`（内存缓存与计数的取号操作）覆盖：XGI 回放首次的载荷且处理器只执行一次；类型化回放首次的对象，首次走 XGI 时也一样；失败两种入口都回放；跨操作、操作与非操作调用之间复用键都是冲突；修复前的旧记录与没有响应的记录明确失败、不返回空载荷。修复前的中间件下，5 例中 4 例失败。
  - `IdempotentReplayHttpTests`：回放写出 201 与同样的正文；跨操作复用键是 409 Problem Details。修复前回放得到 200 加空正文。
  - `OperationTests.DecodeResponse_RoundTripsEncodeResponse_AndRejectsNullOrInvalidJson`。
