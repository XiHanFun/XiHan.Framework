# ADR-0064 发件箱死信与幂等响应回放

## 状态

已采纳（`spec/rfcs/0009-messaging.md`「发件箱」改写）。

## 日期

2026-11-01

## 背景

### 发件箱

文档站写作时发现 `OutboxDispatcher` 有三个问题：

- 没有尝试上限，也没有死信。无法解码的行每一轮都失败，失败的行永远是「未投递」。
- 每轮按创建时间取 `BatchSize` 条未投递的消息。只要有不少于 `BatchSize` 条永久失败的消息排在前面，后面的消息就永远取不到，整个发件箱停摆。
- 投递成功的行只记 `DispatchedAt`、从不删除，表无界增长。

`OutboxMessage` 的 `Topic` 与 `LastError` 也没有声明长度。SqlSugar 在 PostgreSQL 上把没有长度的字符串建成 `varchar(255)`，失败原因（`[错误码] 文案`，文案里常带代理的异常信息）一超长，这一轮的批量更新就失败、整轮回滚，同一批消息下一轮再来一遍。

## 决策

### 发件箱

- 每轮只取到期的消息：未投递、未进死信，`NextAttemptAt` 为空或已到。仍按创建时间排序，最多 `BatchSize` 条。
- 每条计一次尝试：
  - 成功记 `DispatchedAt`。
  - 失败记 `LastError`，`NextAttemptAt` 推后 `RetryDelay × 2^(尝试次数 − 1)`，不超过 `MaxRetryDelay`。缺省 5 秒起、5 分钟封顶。
  - 尝试达到 `MaxAttempts`（缺省 10）记 `DeadLetteredAt`，进死信。载荷无法解码时不等次数用尽，直接进死信。
- 死信留在表里，循环不再取它。把 `DeadLetteredAt` 置空、`NextAttemptAt` 设为现在，就会重新投递。
- 代理整批抛出（不可达）时本轮照旧回滚，不计尝试。
- 投递成功的行保留 `DispatchedRetention`（缺省 1 天），过后由循环删除。每轮最多删 `BatchSize` 行，与投递同一个工作单元。保留期为 0 时，投递成功即在同一工作单元删除。死信行不自动删除。
- 表结构：
  - `Topic` 标 `[StringLength(128)]`，与主题文法的上限一致。
  - `LastError` 标 `[LongText]`。
  - 新列 `NextAttemptAt`、`DeadLetteredAt` 可空。列加在已有数据的表上时旧行为空，视为到期、未进死信。
- 新选项都在 `XiHan:Messaging:Outbox`：`MaxAttempts`、`RetryDelaySeconds`、`MaxRetryDelaySeconds`、`DispatchedRetentionSeconds`。

## 理由

### 发件箱

- 退避而不是只加上限：只加上限时，失败的消息仍在每一轮排在最前面重试，直到次数用尽才让路。代理短暂拒收（磁盘告警、nack）时，所有消息会在几秒内耗尽次数、集体进死信。有了退避，退避中的消息不占批次，后面的消息照常投递；缺省参数下一条消息要连续失败约 20 分钟才进死信。
- 死信留在表里而不是发到代理的死信主题：进死信的原因往往就是代理不收或载荷坏了，再发一次多半同样失败；`IMessageBroker` 也只收信封，解不开的载荷没法发。行留在表里，原因（`LastError`）、次数与时间都在，便于排查与人工重投。
- 代理整批抛出不计尝试：那是基础设施故障，不是这条消息的问题。计入的话，一次几分钟的停机会把积压的消息全部送进死信。
- 保留期而不是立即删除：保留一段时间便于排查「这条消息发没发出去」；需要最小表的应用把保留期设为 0。清理每轮一批，与投递同节奏，吞吐与投递一致，不会出现一次删除大量行的长事务。
- 新列可空：给已有数据的表加列时，SqlSugar 只为数值、枚举、布尔与 Guid 列配缺省值回填旧行（ADR-0040），日期列要可空。空值有明确语义（到期、未进死信），升级时旧行照常投递。

## 影响

### 发件箱

- 公开 API：`OutboxMessage` 增 `NextAttemptAt`、`DeadLetteredAt`；`OutboxOptions` 增 `MaxAttempts`、`RetryDelay`、`MaxRetryDelay`、`DispatchedRetention` 与 `RetryDelayAfter(attempts)`。
- 行为：
  - 失败的消息不再无限重试，用尽次数后进死信（日志 Error 级别）。
  - 投递成功的行缺省一天后被删除。依赖「投递过的行一直在」的应用要调大保留期。
  - `OutboxPublisher` 写入时 `NextAttemptAt` 等于创建时间。
- 表结构：已有的发件箱表要加两列（可空），`Topic` 长度改为 128，`LastError` 改为长文本。SqlSugar 开着 `InitTables` 时自动补列；EF Core 的应用随模型迁移。
- 已知限制：
  - 某一条消息让代理整批抛出（比如超过帧上限导致通道关闭）时，它所在的批次每轮回滚，依然会卡住；这种消息只能人工处理。
  - 到期判定的或条件写在最前面。SqlSugar 把 `A && B && (可空值 == null || …)` 译成丢了 `OR` 的 SQL（SQLite 上是语法错误），换成先写或条件的等价形式后译对。这是持久化包的翻译缺陷，另行修复。
- 测试：
  - `OutboxDispatcherTests`（内存持久化、可推进的时钟、脚本代理）覆盖：无法解码直接进死信，退避按倍数增长并受上限约束，次数用尽进死信，永久失败的消息不挡后面的消息，保留期过后删除已投递行、死信留着，保留期为 0 时当场删除并分批清理旧行，代理不可达时回滚且不计尝试，`NextAttemptAt` 为空的旧行照常取到。
  - `SqlSugarOutboxTests` 在 SQLite 上覆盖：列长与长文本，到期判定的可空比较，死信不再取到，保留期清理。
