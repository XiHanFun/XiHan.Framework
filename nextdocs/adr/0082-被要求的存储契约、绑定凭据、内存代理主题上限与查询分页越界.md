## 一、缺省存储的同一存储规则只约束被要求的契约

### 背景

ADR-0075 第二节规定缺省的 `IBlobStore`、`IBlobMultipartStore`、`IBlobUrlSigner` 必须落在同一存储：存储包被选为 `objectstorage.multipart` 或 `objectstorage.presign` 却没被选为 `objectstorage.blob` 时 `OBJECTSTORAGE_VALIDATION_004` 启动失败。内核对没人依赖的能力也按「显式 Provider 优先」选出提供者，于是以文件系统为缺省、另装 S3 只为用它的命名实例时，即使应用根本不用分片上传与预签名，S3 也被兜底选为这两项的提供者，应用必须把三个 `XiHan:Providers` 键都写上，还必须装 `HostedBlobUrlFeature` 来接走预签名。

### 备选

1. 维持现状：配置繁琐，而且逼着不用预签名的应用装一个宿主端点。
2. 内核改规则：没人依赖的能力不选提供者。会改变所有能力的装配（大量应用直接注入契约而不在清单里声明依赖），图谱与现有行为大面积变化。
3. 存储包自行改选：分片上传与预签名跟随缺省对象存储。图谱说 S3、容器里是文件系统，ADR-0075 已否决。
4. 区分「被要求的选中」与「兜底选出」，同一存储规则只约束被要求的；兜底选出的存储包按被顶替处理。

### 决策

取备选 4。

- 内核 `ResolvedNode.IsRequestedFor(capabilityId)`（Preview）：本节点被选中提供该能力，且这一选择是被要求的——有清单依赖这项能力（必需或可选，且解析到了提供者），或 `XiHan:Providers:<能力ID>` / `UseProvider` 指定了提供者。只按「没被依赖的能力也选出提供者」选出的是兜底选出，返回 `false`。兜底选出照样算选中，`SelectedCapabilities`、`IsSelectedFor`、`xihan graph` 不变（RFC-0002 解析规则 4）。
- `BlobStoreSelection.EnsureSameStore(node)` 改为 `ProvidesDefaultInstance(node) → bool`，存储包在 `Configure` 开头调用：
  - 被选为 `objectstorage.blob`：返回 `true`，它是缺省存储，照常为被选中的各项能力注册契约（兜底选出的也注册，单一存储的应用不受影响）。
  - 没被选为 `objectstorage.blob`，却被要求提供分片上传或预签名：仍然 `OBJECTSTORAGE_VALIDATION_004` 启动失败，消息列出被要求的能力。
  - 没被选为 `objectstorage.blob`，分片上传与预签名都只是兜底选出：返回 `false`，存储包与被顶替相同，只登记命名实例 Provider，不读配置节与连接绑定、不建缺省实例、不注册这两个契约、不启动（文件系统与 S3 两个特性都照此实现）。
- 仍然启动失败的情形：存储包没被选为对象存储，而（a）有特性在清单里依赖了 `objectstorage.multipart` / `objectstorage.presign` 并解析到它，或（b）`XiHan:Providers` / `UseProvider` 把这两项之一指定给它。另有内核本来的失败不变：装了 `HostedBlobUrlFeature` 又装 S3 而没指定 `objectstorage.presign`，两个显式 Provider 竞争，`KERNEL_CAPABILITY_004`。

### 理由

- 「实际被选中」以应用表达过的意图为准：依赖是特性说「我要用」，Provider 键是应用说「用这个」。两者都没有的选择没有人会经它取用，强制它与缺省存储一致只是在为不存在的使用者配置。
- 不改内核的选择规则，只多暴露一个事实：图谱照旧是选择的唯一事实源，兜底选出的存储包不注册契约，容器里只是少了没人要的服务，不会出现「图谱说 S3、容器是文件系统」。
- 应用若直接注入 `IBlobMultipartStore` / `IBlobUrlSigner` 而不在清单里声明依赖，混装时会在解析时缺服务；声明依赖后启动期就能核对，这正是清单的用途。

### 影响

- 公开 API：`Kernel` 新增 `ResolvedNode.IsRequestedFor`；`ObjectStorage.Abstractions` 的 `BlobStoreSelection.EnsureSameStore(ResolvedNode) → void` 改为 `ProvidesDefaultInstance(ResolvedNode) → bool`。
- 行为：以文件系统为缺省、另装 S3 只用命名实例时，只指定 `objectstorage.blob` 即可启动，不必装 `HostedBlobUrlFeature`；这时容器里没有缺省的 `IBlobMultipartStore` 与 `IBlobUrlSigner`。以前三项都指定的配置照样有效。
- 启动期失败变少，没有新增；`OBJECTSTORAGE_VALIDATION_004` 的消息改为列出被要求的能力。
- 测试：内核用例覆盖必需 / 可选依赖、配置与 `UseProvider` 指定、兜底选出；S3 测试项目的混装用例新增「只指定对象存储即可启动且 S3 只留命名实例」「依赖预签名而没指定时失败」「配置把分片上传指定给 S3 时失败」「依赖预签名并指定宿主签名器」。

## 二、资源绑定的凭据属性也覆盖配置节

### 背景

ADR-0075 第三节让绑定的主值覆盖 Redis、RabbitMQ、Kafka、Nacos 配置节里的连接键，凭据等其余键照读配置节；S3 的绑定属性（`accessKey`、`secretKey` 等）原本就覆盖同名键。部署环境的凭据（Kubernetes Secret、编排注入的环境变量）于是只能写进连接串，或者应用配置里另写一份，Nacos 的用户名密码、Kafka 的 SASL 凭据没有办法单独由绑定给出。`xihan pack` 生成的 Compose / Aspire 只给 MinIO 注入端点，应用拿不到它的访问密钥。

### 备选

1. 维持只覆盖主值：凭据只能拼进连接串，或留在应用配置里。
2. 绑定的全部属性都透传给 Provider：Kafka 会把绑定目录里的 `type`、`provider`、`host` 当成 librdkafka 配置项而拒绝启动，其余 Provider 也没有通用的透传口。
3. 每个 Provider 列出它认的凭据属性，逐项覆盖配置节里的同类键。

### 决策

取备选 3（RFC-0016「资源绑定与配置节」）。

- 逐项判定：绑定里有这一项就用绑定的，没有就读配置节的；空白的主值与属性不算给出。凭据属性与主值互不依赖，绑定只给凭据、连接来自配置节也照样覆盖凭据。属性名区分大小写。
- 各 Provider 认的属性：
  - `Caching.Redis`（`cache`）：`username`、`password` 覆盖连接字符串里的 `user`、`password`。`RedisCachingOptions` 新增 `User`、`Password`，连接时把连接字符串解析成 StackExchange.Redis 的选项再按属性设置，不改写字符串。
  - `Messaging.RabbitMQ`（`queue`）：`username`、`password` 覆盖 AMQP URI 里的用户名与密码。`RabbitMQMessagingOptions` 新增 `UserName`、`Password`，连接时在 `ConnectionFactory` 上先设 `Uri` 再设这两项，不改写 URI。
  - `Messaging.Kafka`（`stream`）：`security.protocol`、`sasl.mechanism`、`sasl.username`、`sasl.password` 覆盖 `Properties` 里的同名键，只认这四项。
  - `Configuration.Nacos`（`nacos`）：`username`、`password` 覆盖 `Username`、`Password`。
  - `ObjectStorage.S3`（`objectstorage`）：`region`、`accessKey`、`secretKey`、`forcePathStyle` 照旧覆盖同名键，补上「空白不算给出」。
- 凭据不进日志、错误与异常消息：报连接不合法时不带 URI 与凭据的值。
- `xihan pack`：Compose 与 Aspire 以固定的本地联调凭据（`BindingKind.MinioUser` / `MinioPassword`）启动 MinIO，并把同一对值作为 `blob` 绑定的属性 `accessKey` / `secretKey` 注入应用；Aspire 以前没给 MinIO 设根用户，应用拿不到可用的密钥，一并修正。其余类型的凭据已在主值里（PostgreSQL 连接串、AMQP URI，Aspire 集成资源的连接串）或依赖服务没开认证，不另注入。Kustomize 的 `bindings.example.yaml` 以注释列出各类型可单独给出的凭据键。CLI 知识库 `configuration.json` 的相关键说明同步。

### 理由

- 凭据与端点一样属于部署环境：Secret 轮换不应要求改应用配置，也不应要求把密码拼进连接串。
- 只认列出的属性：绑定目录按 Service Binding 规范还会有 `type`、`provider`、`host`、`port` 等文件，透传会把无关项交给客户端；列出来也让「哪个属性覆盖哪个键」可查。
- Redis 与 RabbitMQ 不改写连接串：StackExchange.Redis 的连接字符串没有转义规则，含逗号的密码一拼就拆错；AMQP URI 的用户信息要百分号转义。按客户端选项设置两者都避开了。
- 属性名沿用 Service Binding 规范的常用条目（`username`、`password`），Kafka 用 librdkafka 的原名，与它覆盖的 `Properties` 键一一对应。

### 影响

- 公开 API：`RedisCachingOptions` 新增 `User`、`Password`；`RabbitMQMessagingOptions` 新增 `UserName`、`Password`；`FromConfiguration` 签名不变。
- 行为：绑定里有凭据属性时覆盖配置节；没有的应用不受影响。S3 绑定里空白的属性以前会覆盖成空值，现在照读配置节。
- `xihan pack`：Compose 与 Aspire 的 `blob` 绑定多注入两个属性；Aspire 的 MinIO 容器多设根用户与密码；Kustomize 示例多出注释行。
- 测试：五个包的选项用例覆盖逐项覆盖、只给凭据、空白不算；Redis 与 RabbitMQ 断言连接选项里是绑定给的凭据（含逗号、`@`、`:` 的密码）且连接串不变；RabbitMQ 断言报错不带凭据；Redis 与 RabbitMQ 各加一个真实服务用例：配置节里的凭据是错的、正确的只由绑定属性给出，健康项照样 Ready（本机 Docker 上带密码的 Redis 与 RabbitMQ 实测通过）；CLI 打包用例断言注入与示例注释。

## 三、删除内存代理的主题数上限

### 背景

`Messaging.InMemory` 原来为发布到的每个主题建通道，主题数随发布增长，于是有 `MaxTopics`（缺省 1000）与 `MESSAGING_UNAVAILABLE_003`。ADR-0074 改成只为被订阅的主题建通道、发布到没人订阅的主题直接丢弃之后，`MaxTopics` 只剩下约束「代码与插件登记的订阅数」，超出时启动失败；d-sched 分区把它保留下来、留待再定。

### 决策

- 删除 `InMemoryMessagingOptions.MaxTopics` 与配置键 `XiHan:Messaging:InMemory:MaxTopics`，删除启动时的主题数判定。
- 错误码 `MESSAGING_UNAVAILABLE_003` 只为它存在，5.0 尚未发布，按编号规则撤销登记、序号不复用（同 ADR-0070 撤销 `LOCALIZATION_VALIDATION_001` 的做法）；常量 `MessagingErrors.TopicLimit` 删除。它的消息键 `messaging.topic.limit` 已在 ADR-0074 删除。
- CLI 知识库 `configuration.json` 删去该键。

### 理由

- 通道只为订阅表里的主题（或交给 `StartAsync` 消费的主题）创建，订阅表在装配时定好、之后只读，通道数不随运行时输入增长；资源上界由代码决定，与「默认实现容量有界」的要求一致，不需要再配一个上限。
- 剩下的唯一作用是让订阅了很多主题的应用启动失败，这不是资源保护，只是多一个要调的数字。
- 保留选项而不起作用是静默兜底；改成别的语义又没有使用场景，删掉最干净。

### 影响

- 公开 API：删除 `InMemoryMessagingOptions.MaxTopics`、`MessagingErrors.TopicLimit`。
- 配置：`XiHan:Messaging:InMemory:MaxTopics` 不再读取（写了也不报错，只是没有作用；CLI 知识库不再列出它）。
- 行为：订阅超过 1000 个主题的应用以前启动失败，现在照常启动。
- 测试：删掉主题数上限与配置解析的用例，新增「订阅 1001 个主题照常启动」。

## 四、调度、工作流与对象存储的查询分页越界返回 400

### 背景

ADR-0073 把查询取出条数超限改成 `PERSISTENCE_VALIDATION_005`（HTTP 400），ADR-0077 把待办查询的分页越界改成 `WORKFLOW_VALIDATION_002`。同类的 `JobRunQuery.Skip` / `Limit`、`WorkflowInstanceQuery.Skip` / `Limit`、`WorkflowPurgeRequest.Limit` 与 `BlobQuery.PageSize` 仍在 `init` 里抛 `ArgumentOutOfRangeException`：这些查询常由请求绑定而来，越界经 HTTP 是 500（`KERNEL_UNEXPECTED_001`），而它是调用方可以改正的输入。

### 决策

照待办查询（ADR-0077）的形状：属性不再在 `init` 里校验，由服务在执行前核对并返回本领域的校验错误，不进存储、不开事务。

- 调度：`IJobScheduler.RunsAsync` 在 `Skip` 为负或 `Limit` 不在 1～`JobRunQuery.MaxLimit`（1000）时返回新码 `SCHEDULING_VALIDATION_002`（`SchedulingErrors.RunQueryInvalid`，消息键 `scheduling.run.query_page_invalid`，参数 `skip`、`limit`、`max`）；`CountRunsAsync` 不看分页，不校验。存储收到的查询由调度器校验过。
- 工作流：`IWorkflowEngine.ListInstancesAsync` 的分页越界返回 `WORKFLOW_VALIDATION_002`（消息键 `workflow.instance.query_page_invalid`，参数同上）；`PurgeAsync` 的 `Limit` 不在 1～1000 返回同码（消息键 `workflow.purge.limit_invalid`，参数 `limit`、`max`）。清理请求不是查询，但它的条数与实例查询同一上限、同样来自请求，一并处理。
- 对象存储：`BlobQuery.Validate()` 核对页大小，不在 1～`BlobQuery.MaxPageSize`（1000）时返回新码 `OBJECTSTORAGE_VALIDATION_005`（`ObjectStorageErrors.PageSizeInvalid`，消息键 `objectstorage.list.page_size_invalid`，参数 `pageSize`、`max`）。契约在每个 Provider 上（没有共同的服务层），文件系统与 S3 在 `ListAsync` 开头调用它；第三方 Provider 由一致性套件的新用例核对。
- 新消息键都补齐 10 种区域；规范 RFC-0013、RFC-0021、RFC-0012 与 `error-codes.md` 同步。

### 理由

- 与 Take、待办查询保持同一条规则：调用方可以改正的输入是 400，编程错误才是异常；同一个应用里分页参数越界不该有的是 400、有的是 500。
- 在服务里校验而不是在 `init` 里：绑定框架构造请求对象时抛出的异常没有错误码，宿主只能当成未处理异常；服务返回的 `Result` 带码、带参数、可本地化。
- 对象存储没有像调度器、引擎那样的服务层，校验放在查询对象上，由各 Provider 调用，避免每个 Provider 各写一份上限与消息。

### 影响

- 公开 API：`JobRunQuery.Skip` / `Limit`、`WorkflowInstanceQuery.Skip` / `Limit`、`WorkflowPurgeRequest.Limit`、`BlobQuery.PageSize` 不再在构造时抛出（签名不变）；新增 `SchedulingErrors.RunQueryInvalid`、`SchedulingMessages.RunQueryPageInvalid`、`WorkflowMessages.InstanceQueryPageInvalid`、`WorkflowMessages.PurgeLimitInvalid`、`ObjectStorageErrors.PageSizeInvalid`、`ObjectStorageMessages.PageSizeInvalid`、`BlobQuery.Validate()`；三个一致性套件各新增一个公开用例方法。
- 行为：这几处越界以前在构造时抛 `ArgumentOutOfRangeException`（经 HTTP 是 500），现在构造成功、调用返回 400：调度 `SCHEDULING_VALIDATION_002`、工作流 `WORKFLOW_VALIDATION_002`、对象存储 `OBJECTSTORAGE_VALIDATION_005`。在管道外捕获 `ArgumentOutOfRangeException` 的代码要改成检查结果。
- 直接调用存储（`IJobStore.RunsAsync`、`IWorkflowInstanceStore.ListAsync`）而不经调度器或引擎的代码，越界的分页不再在构造时被拦下，要自己校验；数据库实现会在构造查询时以 `PERSISTENCE_VALIDATION_005` 或 `ArgumentOutOfRangeException` 失败。
- 测试：三个一致性套件各新增越界与边界用例（内存与数据库实现都跑）；工作流模型用例改为断言构造不再抛出。

> 修订（2026-11-01）：第二节里 `xihan pack` 为 `blob` 起的依赖服务由 ADR-0086 第一节从 MinIO（`minio/minio` 已拉取不到）改为 RustFS（`rustfs/rustfs:1.0.4`，`RUSTFS_ACCESS_KEY` / `RUSTFS_SECRET_KEY`）；注入应用的 `accessKey` / `secretKey` 属性与取值不变，常量 `BindingKind.MinioUser` / `MinioPassword` 改名 `BlobAccessKey` / `BlobSecretKey`。
