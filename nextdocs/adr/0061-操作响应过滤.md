# ADR-0061 操作响应过滤

## 状态

已采纳（`spec/rfcs/0011-operations.md` 执行规则增加第 7 条）。

## 日期

2026-10-31

## 背景

BasicApp 6.0 N2 收尾做字段级安全，要在响应发出去之前按调用者把某些字段掩码。

请求这一半够用：Handle 阶段的中间件能用 `GetOperationRequest` / `SetOperationRequest` 读写已解码的请求。响应这一半改不了：

- HTTP 端点在管道终点里调 `IOperationInvoker.ExecuteAsync`，它在执行之后立刻编码响应，gRPC、MCP 也一样。中间件在 `nextStep` 之后再写响应已经晚了。
- 应用也装饰不了调用器：`OperationInvoker` 是内部类型，由内核登记。

## 决策

- `Kernel.Operations` 新增 `IOperationResponseFilter`：`ValueTask<object> FilterAsync(InvocationContext context, OperationDescriptor operation, object response)`。
- 调用器在操作成功后、`SetOperationResponse` 之前，从 `context.Services`（调用的服务作用域，过滤器可以是任意生命周期）取出全部过滤器，按登记顺序调用，后一个拿到前一个的输出，最后的对象写进上下文。
- 四个入口都经过它：`InvokeAsync` / `ExecuteAsync` 的 XGI 与类型化形式。HTTP、gRPC、MCP 编码出去的，与类型化调用拿到的，都是过滤后的响应。
- 过滤器返回的对象必须是 `descriptor.ResponseType` 的实例（可以是新实例），否则抛出 `InvalidOperationException`。它与过滤器自己抛出的异常一样，由 Observe 阶段翻译为 `KERNEL_UNEXPECTED_001`。
- 失败的调用不过滤。
- 没有登记过滤器时零开销：调用器构造时经 `IServiceProviderIsService` 判定一次，没有就不解析、不分配。

## 理由

- 放在调用器里而不是中间件：响应的编码就在调用器里，这是所有协议与类型化调用的唯一汇合点；中间件在编码之后才拿到控制权。
- 对象进、对象出：过滤器面对的是类型化的响应，掩码可以直接改对象，也可以像 BasicApp 那样经 `EncodeResponse` 转成 JSON、按字段名处理后再反序列化；调用器不替它选。
- 类型检查是硬约束：后面的编码按响应类型的序列化元数据进行，类型不对会在更远处以更难懂的方式失败。
- 不让过滤器改失败语义：它的用途是裁剪成功的响应；要拒绝调用应在 Authorize 或 Handle 之前完成。

## 影响

- 公开 API：`Kernel` 新增 `IOperationResponseFilter`。`OperationInvoker` 是内部类型，构造参数多了根服务提供者。
- 行为：没有过滤器时不变。
- 测试：
  - 四个入口都过滤，按登记顺序串联，作用域与单例过滤器同时可用，作用域服务在调用的作用域里解析。
  - 失败的调用不过滤。
  - 返回别的类型是意外错误、没有载荷。
