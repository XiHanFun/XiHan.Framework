# ADR-0038 消息键文法的首段放开下划线

## 状态

已采纳（`spec/rfcs/0001-primitives.md`、`spec/rfcs/0010-localization.md` 修订）。

## 日期

2026-10-28

## 背景

OpenAPI 的操作摘要、MCP 的 tool 描述与 AI 工具描述都按同一约定取消息键：`<操作 ID>.description`，ID 里的 `-` 换成 `_`（`OpenApiDocumentSource.DescriptionOf`、`McpServer.MessageKeyOf`、`AIToolNameConvention.DescriptionKeyOf`）。操作 ID 的资源段允许连字符（`conventions/operation-ids.md`：`order-lines`、BasicApp 6.0 的 `tenant-members`、`role-grants`、`user-grants`、`data-scopes`），派生出的键是 `tenant_members.list.description`；但 `MessageTemplate.IsValidKey` 的文法 `^[a-z][a-z0-9]*(\.[a-z][a-z0-9_]*)+$` 不许首段带下划线。结果是这类键既进不了消息目录（`MessageCatalog.ParseLocaleFile` 直接抛 `FrameworkException`），三处约定也因 `IsValidKey` 为假而永远给不出说明——约定与文法互相矛盾。

## 备选

1. 首段放开成 `[a-z][a-z0-9_]*`，与后段同形。
2. 约定改成去掉连字符（`tenantmembers.list.description`），三处同步。
3. 约定改成连字符段落另起一段（`tenant.members.list.description`），三处同步。

## 决策

采用 1。`MessageTemplate.IsValidKey` 的文法改为 `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$`；`DomainOf` 仍取第一个 `.` 之前的段，不受影响。RFC-0010 的 `Domain` 定义改为"与 `Segment` 同形：术语表领域词的小写或应用自定义的小写标识，操作 ID 的资源段把连字符换成下划线后即是"。三处约定不动，`Localization.Database` 两处错误文案里的文法同步。

## 理由

- 约定已经被 OpenAPI、MCP、AI 三条协议与 BasicApp 的键共同依赖，改约定要动三处实现、全部已有的键与文档；改文法只动一处，而且后段本来就允许下划线，首段放开后文法整体更一致。
- 去掉连字符（备选 2）会让 `order-lines` 与 `orderlines` 两种资源撞键；另起一段（备选 3）让键的段数不再等于"领域 + 主题 + 名称"，读键时无法分辨资源名的边界。
- 框架自己的领域词都没有下划线，架构测试 `LocalizationTests` 仍按已知领域集合核对框架目录的首段，宽松的文法不会放过框架内部的错键。

## 影响

- `IsValidKey` 对首段含下划线的键从拒绝变为接受；原先被拒绝的键没有合法用途，不存在依赖旧行为的调用方。
- 公开 API 签名不变；`Primitives` 的 XML 文档与 `Localization.Database` 的错误文案同步。
- 测试：`MessageTemplateTests` 的文法用例（`kernel_core.empty`、`tenant_members.list.description` 合法，`_tenant.list`、`tenant-members.list.description` 不合法）；OpenAPI 测试里 `order-filters.list` 按 `order_filters.list.description` 取到摘要；MCP 与 AI 的说明键派生用例同样覆盖带连字符的资源。
