# ADR-0057 管道外作用域绑定租户分片

## 状态

已采纳（`spec/rfcs/0007-multitenancy.md` 分片一节增加「管道外的作用域」；`spec/rfcs/0015-auditing.md` 写明审计记录不按租户分片）。

## 日期

2026-10-30

## 背景

BasicApp 6.0 N2 第七批做库隔离时报告：作用域里的持久化客户端只从当前调用上下文取分片（`TenantShardBinding.Resolve` 读 `IInvocationAccessor.Current` 的 `GetTenantShard()`），而当前调用只有 `App.InvokeAsync` 进管道时才设置；`UnitOfWorkOptions` 的 `TenantId` 只管行过滤，不选连接。

后台写入（审计日志批量写、保留期清理作业、租户库初始化与升级）只能为此再走一遍整条管道，带来两个问题：

- 应用停止时只要有一个特性开始排空，`App` 就不再受理调用；`IHostedFeature.StopAsync` 里刷剩余队列时，独立库租户的数据写不进去。
- Tenant 阶段拒绝停用的租户，停用租户的独立库连日志都写不进。

## 决策

- 新增作用域服务 `TenantShardScope`（`MultiTenancy.Abstractions.Sharding`），给自己建的服务作用域显式绑定分片，不经管道：
  - `BindTenantAsync(tenantId)` 经 `ITenantShardResolver` 解析并绑定，返回解析结果。不看租户是否启用，不受应用是否在服务状态影响。共库租户、未知租户与没有装配分片能力时成功且不绑定；解析失败返回错误、不绑定。
  - `Bind(shard)` 直接绑定一个分片；`Shard` 与 `IsConnected` 可读。
- 绑定必须在作用域内首次创建持久化客户端之前：
  - `TenantShardBinding.Resolve` 在持久化 Provider 创建客户端时调用，同时记下「已取连接」。
  - 此后再绑定、或改绑另一个分片，抛出 `InvalidOperationException`；同一个分片重复绑定无副作用。
- 显式绑定优先于调用上下文里的分片。
- `MultiTenancy.InMemory` 与 `MultiTenancy.Database` 登记 `TenantShardScope`，与是否选中分片能力无关；自带分片 Provider 的应用同样登记它。
- 工作单元的 `TenantId` 仍由调用方在 `UnitOfWorkOptions` 里给出，应与绑定的租户一致；框架不在两者之间互相推导。
- 审计记录（`Auditing.Database`）核对后保持平台级：`AuditRecord` 不实现 `IMultiTenant`，落库与查询在根提供者的新作用域里进行、不绑定分片，独立库租户的记录也落默认连接、按租户列区分。RFC-0015 写明这一点。

## 理由

- 绑定挂在服务作用域而不是伪造一个调用上下文：后台工作本来就自己建作用域，不需要管道的认证、授权与租户校验，也不该受应用排空状态限制。
- 绑定时机有硬约束：持久化客户端在作用域里只建一次，建好之后改绑不会生效；抛出异常比静默沿用默认连接更安全，后者会把租户数据写进平台库。
- 按租户 ID 绑定复用 `ITenantShardResolver`（含缓存），与管道里 Tenant 阶段解析出的分片一致。
- 两个持久化 Provider（SqlSugar、EF Core）都经 `TenantShardBinding.Resolve` 取分片，一处改动同时生效。

## 影响

- 公开 API：`MultiTenancy.Abstractions` 新增 `TenantShardScope`（`Bind`、`BindTenantAsync`、`Shard`、`IsConnected`）；`TenantShardBinding.Resolve` 的签名不变，先看显式绑定。
- 行为：管道内的调用不受影响（没有显式绑定时照旧读当前调用的分片）。
- 测试：
  - 多租户：停用租户也能绑定，共库与未知租户不绑定，客户端建好后再绑定与改绑抛出，没有解析器与解析失败时不绑定，显式绑定优先于调用上下文。
  - SqlSugar：管道外的作用域绑定停用租户的分片后，租户行落分片库、平台行落默认库；没有绑定的作用域查不到分片库里的行。
