# ADR-0039 权限收窄过滤器 `IPermissionFilter`

## 状态

已采纳（`spec/rfcs/0008-security.md` 修订）。

## 日期

2026-10-28

## 背景

RFC-0008 的授权只有"用户与角色授予之并集、`*` 匹配任何权限"。操作声明 `Permission = X` 时，`PolicyCatalog` 动态建 `PermissionPolicy`，再经 `IPermissionChecker` 判定；应用登记的按名 `IPolicy` 拦不到 `permission:<码>`。BasicApp 6.0 N1 第八批的套餐门控要求"租户的有效权限与其套餐白名单求交，持 `*` 的租户管理员也被收窄"，之后的显式拒绝（Deny）、委托到期也是同一类需求：在授予命中之后再收窄。现状下唯一办法是在容器里替换 `IPermissionChecker`。

## 备选

1. 写明"扩展方式就是替换 `IPermissionChecker`"：应用要么重写一遍授予并集与通配（`PermissionChecker` 是 sealed），要么在自己的实现里 new 一个再包一层；还要抢在 Provider 的 `TryAddSingleton` 之前登记。几种收窄来源（套餐、Deny、委托）各自想包一层时互相覆盖，无法组合。
2. 让应用为每个权限码登记同名 `IPolicy` 覆盖动态权限策略：权限码成百上千，且策略目录的同名冲突是装配错误。
3. 在 `Security.Abstractions` 加收窄钩子 `IPermissionFilter`，`PermissionChecker` 在授予命中之后逐个调用（AND）。

## 决策

采用 3。

- `IPermissionFilter.AllowsAsync(SecurityContext security, string permission, CancellationToken cancellationToken)`：授予已命中 `permission` 之后判定是否仍放行。
- `PermissionChecker(IPermissionGrantStore, SecurityOptions, IEnumerable<IPermissionFilter>? filters = null)`：匿名主体直接不持有、不访问存储、不调过滤器；授予未命中直接不持有、不调过滤器；授予命中后按登记顺序逐个调用，任一返回 `false` 即不持有、后面的不再调用。`PermissionPolicy` 照旧给出 `SECURITY_DENIED_004`——调用方不需要区分"没授予"与"被收窄"。
- 过滤器按单例登记（与检查器同寿命）；抛出的异常照常传播，不当作放行或拒绝。通配命中时过滤器收到的是具体权限码，不是 `*`。
- 两个 Provider（`Security.InMemory`、`Security.Database`）登记的都是 `PermissionChecker`，由容器注入全部过滤器，应用只需 `services.AddSingleton<IPermissionFilter, T>()`。替换 `IPermissionChecker` 的实现必须同样在授予命中之后施加全部过滤器（RFC-0008 写明）。
- 稳定性 `Stable`：与 `IPermissionChecker` 同级，`PermissionChecker` 的构造函数引用它。

## 理由

- 收窄只能拿走权限、不能凭空给出：放在授予命中之后，过滤器出错或漏判时最坏是"多拒绝"，不会越权；授予并集与通配的语义仍只在一处。
- 组合靠 AND：套餐、Deny、委托到期各是一个过滤器，互不知道彼此。
- 不调用未命中的判定：过滤器多半要查库或缓存（套餐白名单），未命中时调用是纯开销。

## 影响

- 公开 API：新增 `IPermissionFilter`；`PermissionChecker` 构造函数多一个可选参数（5.0 尚未发布，属 Unshipped 内的调整，旧的两参调用源码兼容）。
- 行为：没有登记过滤器时与原来完全相同。
- 测试：`AuthorizationTests` 覆盖逐个 AND、`*` 被收窄、拒绝后短路、未命中与匿名不调用、空集合、集合含 null 报错，以及权限策略在收窄时给出 `SECURITY_DENIED_004`；`InMemorySecurityTests` 端到端验证 Provider 登记的检查器接上应用登记的过滤器。
