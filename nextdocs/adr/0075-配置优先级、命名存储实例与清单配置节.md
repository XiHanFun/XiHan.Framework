# ADR-0075 配置优先级、命名存储实例与清单配置节

## 状态

已采纳（`spec/rfcs/0014-configuration.md`、`spec/rfcs/0016-packaging.md`、`spec/packaging/app-manifest.md`、`spec/rfcs/0002-manifest.md`、`spec/rfcs/0012-objectstorage.md`、`spec/conventions/error-codes.md`、`spec/manifest/manifest.schema.json` 随之修订；修订 ADR-0050）。

## 日期

2026-11-01

## 背景

写 5.0 文档站时，配置、对象存储与插件分区报告了几处资源与配置的规则没有定下来或彼此不一致（`docs-next` 问题清单 D 类第 1、4、5、10 条与第二轮的清单配置节）。用户逐条拍板后，本 ADR 每项一节记录决定。

## 一、挂载配置目录的位置

### 背景

`Hosting.AspNetCore` 与 `Hosting.CommandLine` 的 `AddXiHan` 把 `XIHAN_CONFIG_PATH` 目录里的 JSON 文件追加在构建器全部配置源之后，于是 ConfigMap 里的键覆盖环境变量与命令行参数。XML 文档只提「晚于 appsettings」，RFC 没写位置。`xihan pack` 生成的 Dockerfile 与 Deployment 用环境变量写 `XiHan__Kernel__StopTimeoutSeconds`，ConfigMap 有同名键时停机宽限会被改掉，与 `terminationGracePeriodSeconds` 对不上。

### 决策

- 目录里的文件紧接构建器里最后一个 appsettings 文件源（`appsettings.json` 或 `appsettings.{环境}.json`，按文件名认、不区分大小写）插入。默认构建器的配置源从低到高：`appsettings.json` → `appsettings.{环境}.json` → 挂载目录 → 用户机密（仅开发环境）→ 环境变量 → 命令行参数 → 应用自己添加的配置源。
- 构建器里没有 appsettings 文件源（应用关掉了默认配置）时追加在末尾。
- 内核 `ConfigurationDirectory` 新增 `IsApplicationSettings(path, environmentName)`，两个宿主共用这条认文件的规则；插入在宿主里完成（需要 `Microsoft.Extensions.Configuration.Json`，内核只引用抽象包）。
- RFC-0016 增「挂载的配置目录」一节，RFC-0014 增「配置源顺序」一节。

### 理由

- 挂载目录是部署侧的文件配置，与 appsettings 同层；环境变量与命令行是更贴近单次运行的覆盖手段，按 .NET 的惯例应当更高。
- 停机宽限等由 `xihan pack` 用环境变量写死、与编排参数配套的键，不应被 ConfigMap 悄悄改掉。
- 只认 appsettings 的文件名、不认配置源类型：环境变量、命令行与用户机密的源类型在不同宿主里不一致，appsettings 的两个文件名是 .NET 默认构建器的固定约定。

### 影响

- 行为：同一个键同时出现在挂载文件与环境变量 / 命令行参数 / 应用自己添加的配置源里时，以前挂载文件生效，现在后者生效；挂载文件仍覆盖 `appsettings.json` 与 `appsettings.{环境}.json`。
- 公开 API：`Kernel` 新增 `ConfigurationDirectory.IsApplicationSettings`。
- 测试：两个宿主各有用例断言实际优先级（`appsettings.json` < `appsettings.Staging.json` < 挂载文件 < 环境变量 < 命令行 / 应用添加的源），改进程环境变量的用例归入不并行的集合。

## 二、命名存储实例的登记与缺省实例的一致性

### 背景

ADR-0050 说命名实例的 Provider「按包登记、与能力选择无关」，实际只在 `Configure` 里登记，而内核不调能力全部被顶替的节点的 `Configure`。混装文件系统与 S3 时，被顶替的那个包的命名实例建不出来；只把 `objectstorage.blob` 指定给文件系统时，分片上传与预签名仍归 S3，缺省 `IBlobUrlSigner` 签出 S3 的地址，而缺省 `IBlobStore` 是文件系统。细节见 ADR-0050 的修订一节。

### 决策

- 只要装配了存储包就登记它的命名实例 Provider，与选哪个当缺省无关。内核新增 `IShadowAwareFeature`：被顶替的特性改调 `ConfigureShadowed`，只登记与能力选择无关的服务；文件系统与 S3 两个特性实现它。
- 缺省的 `IBlobStore`、`IBlobMultipartStore`、`IBlobUrlSigner` 用同一个存储：被选为 `objectstorage.multipart` 或 `objectstorage.presign` 的存储包必须同时被选为 `objectstorage.blob`，否则 `OBJECTSTORAGE_VALIDATION_004` 启动失败（`BlobStoreSelection.EnsureSameStore`）。宿主代收发的签名器经缺省 `IBlobStore` 收发，总与缺省存储一致。

### 理由

- 被顶替只说明这个包不提供缺省实例，不说明应用不用它的命名实例；把「能力选择」与「命名实例」分开，混装才有意义。
- 内核层面的开关是一个可选接口而不是让被顶替的节点照常 `Configure`：多数特性在 `Configure` 里用 `TryAdd` 注册契约，被顶替的 default 若照常装配，按拓扑顺序可能抢先注册而压过选中的 Provider，这正是 shadowed 规则要避免的。
- 不一致时启动失败，而不是自动改选：能力图谱（`xihan graph`）是选择的唯一事实源，自动改选会让图谱与容器里的实现不一致；报错列出要设的键，修正只是配置。

### 影响

- 公开 API：`Kernel` 新增 `IShadowAwareFeature`；`ObjectStorage.Abstractions` 新增 `BlobStoreSelection` 与错误码常量 `ObjectStorageErrors.StoreSelectionInvalid`（`OBJECTSTORAGE_VALIDATION_004`）；`FileSystemObjectStorageFeature` 与 `S3ObjectStorageFeature` 实现 `IShadowAwareFeature`。
- 启动期新增失败：存储包被选为分片上传或预签名而没被选为对象存储。以文件系统为缺省实例、另装 S3 时，`objectstorage.blob` 与 `objectstorage.multipart` 指定 `xihan.objectstorage.filesystem`，`objectstorage.presign` 指定 `xihan.hosting.blob-urls`（装配 `HostedBlobUrlFeature`）。
- 行为：被顶替的存储包不再完全不装配，而是只登记命名实例 Provider；它的缺省实例、健康项与启动照旧不发生。
- 测试：内核的被顶替特性用例；S3 测试项目的混装用例（两种装配顺序、文件系统为缺省、选择不一致）。

## 三、资源绑定优先于配置节

### 背景

资源绑定与 Provider 配置节谁优先没有规范，各包不一致：S3 是绑定的主值与属性覆盖配置节；Redis、RabbitMQ、Kafka、Nacos 是配置节优先、绑定兜底。后者让 `xihan pack` 生成的 Compose / Kustomize 注入的绑定（`XiHan__Bindings__cache__value` 等）在应用的 appsettings 里写了本地连接时不起作用，部署环境给的连接被开发配置挡住。

### 决策

- RFC-0016 增「资源绑定与配置节」：绑定给出的连接信息覆盖配置节里的同类键，其余键照读配置节；绑定的主值为空或只有空白时不算给出了连接；两者都没有时装配失败。
- `RedisCachingOptions`、`RabbitMQMessagingOptions`、`KafkaMessagingOptions`、`NacosOptions` 的 `FromConfiguration(configuration, binding)` 改成与 `S3ObjectStorageOptions` 同向：绑定主值覆盖 `Configuration` / `BootstrapServers` / `ServerAddresses`，没有绑定才读配置节。签名不变。
- 持久化 Provider 照旧把绑定交给应用的配置委托；命名存储实例照旧不读绑定。

### 理由

- 绑定是部署环境（Service Binding Secret、编排注入的环境变量）对「这个实例连哪」的回答，配置节是应用自带的缺省；部署环境应当能覆盖应用缺省，与 .NET 配置源里环境变量覆盖 appsettings 同向（第一节）。
- 只覆盖连接信息、其余键照读配置节：前缀、超时、分组这些是应用行为，不该因为换了部署环境就丢掉。
- 统一成 S3 的方向改动最小：S3 已有属性级覆盖，另外四个包的绑定只有主值。

### 影响

- 行为：Redis、RabbitMQ、Kafka、Nacos 同时有绑定与配置节连接键时，以前用配置节，现在用绑定的主值。只配了其中一个的应用不受影响。
- 公开 API 不变；`FromConfiguration` 的 XML 文档与报错文字改为先提绑定。
- 测试：四个包的选项用例改为断言「两者都给时取绑定」，另断言只有配置节时取配置节、主值为空的绑定不覆盖（Redis）。

## 四、清单配置节可带子节

### 背景

清单 `contributes.config.section` 的文法只许领域节 `^XiHan:[A-Z][A-Za-z0-9]*$`，同一领域的各 Provider 都只能声明领域节，自己的子节「包含在内」。于是只读 `XiHan:Scheduling:Kubernetes` 的包与读整个调度领域的包写的是同一个 `XiHan:Scheduling`，清单说不清 Provider 真正读哪一节；插件声明配置节时也只能拿到整个领域。

### 决策

- 文法放开到领域节加任意层子节：`Section = "XiHan" ":" Domain *( ":" Segment )`，每段 PascalCase，正则 `^XiHan:[A-Z][A-Za-z0-9]*(:[A-Z][A-Za-z0-9]*)*$`。原语层 `ConfigContribution`、`spec/manifest/manifest.schema.json` 与 RFC-0002 同步；内核 `ManifestReader` 经 `ConfigContribution` 校验，随之放开。CLI 不校验这个文法，未改。
- 一份清单仍只有一个配置节，写特性在本领域里读取的配置的最近公共节：只读自己子节的写子节，同时读领域节下的公共选项或本领域几个子节的写领域节。别的领域的共享键与资源绑定不进清单，由包 README 写明。
- 逐个核对现有特性实际读取的节，18 个改写为子节：`Caching.Hybrid`（`XiHan:Caching:Hybrid`）、`Configuration.Nacos`（`XiHan:Configuration:Nacos`）、`Hosting.AspNetCore` 的 `HostedBlobUrlFeature`（`XiHan:ObjectStorage:SignedUrls`）、`Messaging.Abstractions` 的 `OutboxFeature`（`XiHan:Messaging:Outbox`）、`Observability.Host`、`Observability.OpenTelemetry`、`Persistence.Abstractions` 的 `SnowflakeIdFeature`（`XiHan:Persistence:Snowflake`）、`Persistence.EntityFrameworkCore`、`Persistence.InMemory`、`Persistence.SqlSugar`、`Plugins.OutOfProcess`、`Plugins.Wasm`、`Protocols.CloudEvents`、`Protocols.Grpc`、`Protocols.Http`、`Protocols.Mcp`、`Scheduling.Kubernetes`、`Security.Ip2Region`（各自 `XiHan:<领域>:<实现>`，取各选项类型的 `ConfigurationSection` 常量）。其余仍写领域节，因为它们同时读领域公共选项或几个子节：AI 四个特性（`XiHan:AI`）、`Auditing.*`（`XiHan:Auditing`）、`Caching.InMemory` / `Redis` / `Remote`（还读 `XiHan:Caching:Idempotency`）、`Localization.*`、`Messaging.InMemory` / `Kafka` / `RabbitMQ`（还读 `XiHan:Messaging`）、`MultiTenancy.*`、`ObjectStorage.FileSystem` / `S3`（还读 `XiHan:ObjectStorage:Stores` 与命名实例的探测间隔）、`Scheduling.Database` / `InMemory`、`Security.Database` / `InMemory` / `Jwt` / `OpenIdConnect`、`Workflow.*`。

### 理由

- 清单是装配的事实源：写最近公共节，既不夸大（不再把整个领域都算作某个 Provider 的配置），也不遗漏本领域里它读的键。
- 一份清单一个配置节不变：改成数组会动 Stable 的 `Contributions` 与插件协议的 `Configure`，收益只是把跨领域的少数共享键列出来，不值得。
- 只放开、不收紧：已有的领域节清单（含插件示例的 `XiHan:Echo`、`XiHan:Cache`）照样合法。

### 影响

- 公开 API 不变；`ConfigContribution` 接受的值变多（原语层 Stable 类型的校验放宽，不破坏已有调用）。
- 18 个特性清单的配置节变了。进程内特性的配置节只是声明，运行期不据此读取配置，行为不变；插件仍按各自清单下发配置。
- 测试：原语层接受子节、拒绝不合法的段；内核 `ManifestReader` 读出子节、拒绝不合法的节。

## 五、`[Capability]` 清单生成器顺延

### 背景

RFC-0002 与总体方案 §6.1 写「.NET 实现由源生成器从 `[Capability]` 生成清单并嵌入程序集」，但生成器一直没有实现：所有特性都在 `Manifest` 属性里手写清单，`CapabilityAttribute` 在仓库里没有使用者，`Kernel.Generators` 的 README 已写「`[Capability]` 清单生成顺延」，规范与总体方案却仍按已有来写。

### 决策

- 不实现生成器，把规范与文档改成「手写清单，生成器顺延」并写明现状：每个特性在 `IFeature.Manifest` 里手写清单对象，构建期 `Manifest.Validate()` 校验；插件的清单是插件目录里的 `xihan.manifest.json`，由 `ManifestReader` 读取。
- `CapabilityAttribute` 保留（Preview，运行期不读），XML 文档写明它是预留给生成器的。日后实现生成器时，手写的清单是一致性基准：生成结果必须与手写清单逐字段相同。
- 改动：RFC-0002 的摘要与「与 .NET 的映射」，总体方案 §6.1 与风险表，`architecture/04` 的 `Kernel.Capabilities` 与 `Kernel.Generators` 两行，内核与生成器 README，`IFeature.Manifest` 与 `CapabilityAttribute` 的 XML 文档，docs-next 的模块化与生成器包页。

### 理由

- 手写清单已经覆盖全部特性，且清单字段在构建期被校验、在架构测试里被核对（健康项、包名与能力 ID 文法），双份维护的风险比原先估计的小。
- 生成器要处理绑定、贡献点、健康项等全部字段，属性参数表达力有限（集合、嵌套对象），收益在 5.0 范围内不足以抵消工作量与 AOT 分析成本。
- 规范写已实现的事实，未实现的部分明确标为顺延，避免使用者照着 RFC 去找不存在的生成器。

### 影响

- 公开 API 与行为不变；只改规范、文档与两处 XML 注释。
- 第三方能力包照样手写清单；`spec/manifest/manifest.schema.json` 仍是清单的事实标准。

> 2026-11-01：第二节「缺省实例的一致性」由 ADR-0082 第一节修订为只约束被要求的契约（有依赖或经 `XiHan:Providers` / `UseProvider` 指定），兜底选出的存储包按被顶替处理。
