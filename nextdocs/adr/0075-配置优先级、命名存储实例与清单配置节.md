# ADR-0075 配置优先级、命名存储实例与清单配置节

## 状态

已采纳（`spec/rfcs/0014-configuration.md`、`spec/rfcs/0016-packaging.md`、`spec/packaging/app-manifest.md`、`spec/rfcs/0002-manifest.md`、`spec/rfcs/0012-objectstorage.md`、`spec/conventions/error-codes.md` 随之修订；修订 ADR-0050）。

## 日期

2026-11-01

## 背景

写 5.0 文档站时，配置、对象存储与插件分区报告了几处资源与配置的规则没有定下来或彼此不一致（`docs-next` 问题清单 D 类第 1、4、5、10 条与第二轮的清单配置节）。用户逐条拍板后，本 ADR 每项一节记录决定。

## 一、挂载配置目录的位置

### 背景

`Hosting.AspNetCore` 与 `Hosting.CommandLine` 的 `AddXiHan` 把 `XIHAN_CONFIG_PATH` 目录里的 JSON 文件追加在构建器全部配置源之后，于是 ConfigMap 里的键覆盖环境变量与命令行参数。XML 文档只提「晚于 appsettings」，RFC 没写位置。`xihan pack` 生成的 Dockerfile 与 Deployment 用环境变量写 `XiHan__Kernel__StopTimeoutSeconds`，ConfigMap 有同名键时停机宽限会被改掉，与 `terminationGracePeriodSeconds` 对不上。

### 决策

- 目录里的文件紧接构建器里最后一个 appsettings 文件源（`appsettings.json` 或 `appsettings.{环境}.json`，按文件名认、不区分大小写）插入。默认构建器的配置源从低到高：`appsettings.json` → `appsettings.{环境}.json` → 挂载目录 → 用户机密（仅开发环境）→ 环境变量 → 命令行参数 → 应用自己添加的配置源。
- 构建器里没有 appsettings 文件源（应用关掉了默认配置）时追加在末尾。
- 内核 `ConfigurationDirectory` 新增 `IsApplicationSettings(path, environmentName)`，两个宿主共用这条认文件的规则；插入在宿主里完成（需要 `Microsoft.Extensions.Configuration.Json`，内核只引用抽象包）。
- RFC-0016 增「挂载的配置目录」一节，RFC-0014 增「配置源顺序」一节。

### 理由

- 挂载目录是部署侧的文件配置，与 appsettings 同层；环境变量与命令行是更贴近单次运行的覆盖手段，按 .NET 的惯例应当更高。
- 停机宽限等由 `xihan pack` 用环境变量写死、与编排参数配套的键，不应被 ConfigMap 悄悄改掉。
- 只认 appsettings 的文件名、不认配置源类型：环境变量、命令行与用户机密的源类型在不同宿主里不一致，appsettings 的两个文件名是 .NET 默认构建器的固定约定。

### 影响

- 行为：同一个键同时出现在挂载文件与环境变量 / 命令行参数 / 应用自己添加的配置源里时，以前挂载文件生效，现在后者生效；挂载文件仍覆盖 `appsettings.json` 与 `appsettings.{环境}.json`。
- 公开 API：`Kernel` 新增 `ConfigurationDirectory.IsApplicationSettings`。
- 测试：两个宿主各有用例断言实际优先级（`appsettings.json` < `appsettings.Staging.json` < 挂载文件 < 环境变量 < 命令行 / 应用添加的源），改进程环境变量的用例归入不并行的集合。

## 二、命名存储实例的登记与缺省实例的一致性

### 背景

ADR-0050 说命名实例的 Provider「按包登记、与能力选择无关」，实际只在 `Configure` 里登记，而内核不调能力全部被顶替的节点的 `Configure`。混装文件系统与 S3 时，被顶替的那个包的命名实例建不出来；只把 `objectstorage.blob` 指定给文件系统时，分片上传与预签名仍归 S3，缺省 `IBlobUrlSigner` 签出 S3 的地址，而缺省 `IBlobStore` 是文件系统。细节见 ADR-0050 的修订一节。

### 决策

- 只要装配了存储包就登记它的命名实例 Provider，与选哪个当缺省无关。内核新增 `IShadowAwareFeature`：被顶替的特性改调 `ConfigureShadowed`，只登记与能力选择无关的服务；文件系统与 S3 两个特性实现它。
- 缺省的 `IBlobStore`、`IBlobMultipartStore`、`IBlobUrlSigner` 用同一个存储：被选为 `objectstorage.multipart` 或 `objectstorage.presign` 的存储包必须同时被选为 `objectstorage.blob`，否则 `OBJECTSTORAGE_VALIDATION_004` 启动失败（`BlobStoreSelection.EnsureSameStore`）。宿主代收发的签名器经缺省 `IBlobStore` 收发，总与缺省存储一致。

### 理由

- 被顶替只说明这个包不提供缺省实例，不说明应用不用它的命名实例；把「能力选择」与「命名实例」分开，混装才有意义。
- 内核层面的开关是一个可选接口而不是让被顶替的节点照常 `Configure`：多数特性在 `Configure` 里用 `TryAdd` 注册契约，被顶替的 default 若照常装配，按拓扑顺序可能抢先注册而压过选中的 Provider，这正是 shadowed 规则要避免的。
- 不一致时启动失败，而不是自动改选：能力图谱（`xihan graph`）是选择的唯一事实源，自动改选会让图谱与容器里的实现不一致；报错列出要设的键，修正只是配置。

### 影响

- 公开 API：`Kernel` 新增 `IShadowAwareFeature`；`ObjectStorage.Abstractions` 新增 `BlobStoreSelection` 与错误码常量 `ObjectStorageErrors.StoreSelectionInvalid`（`OBJECTSTORAGE_VALIDATION_004`）；`FileSystemObjectStorageFeature` 与 `S3ObjectStorageFeature` 实现 `IShadowAwareFeature`。
- 启动期新增失败：存储包被选为分片上传或预签名而没被选为对象存储。以文件系统为缺省实例、另装 S3 时，`objectstorage.blob` 与 `objectstorage.multipart` 指定 `xihan.objectstorage.filesystem`，`objectstorage.presign` 指定 `xihan.hosting.blob-urls`（装配 `HostedBlobUrlFeature`）。
- 行为：被顶替的存储包不再完全不装配，而是只登记命名实例 Provider；它的缺省实例、健康项与启动照旧不发生。
- 测试：内核的被顶替特性用例；S3 测试项目的混装用例（两种装配顺序、文件系统为缺省、选择不一致）。
