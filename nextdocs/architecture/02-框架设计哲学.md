# XiHan Framework — 框架设计哲学

> 版本：5.0.0-preview.1 | 状态：草案 | 最后更新：2026-10-21
>

## 一、三易模型与七条原则

框架按三层承诺组织：

| 层 | 名称 | 承诺 |
| --- | --- | --- |
| 不易 | 原语层 `Primitives`（Ring 0） | 永不破坏，只增不改 |
| 简易 | 内核 `Kernel`（Ring 1） | 大版本内不破坏 |
| 变易 | 子系统、Provider、宿主、协议、插件、应用（Ring 2–6） | 各自演进，通过一致性测试即视为兼容 |

七条原则派生所有具体设计决策：

```text
1. 内核克制     — 内核只定义稳定边界，不堆能力
2. 装配显式     — 显式注册优先，自动发现只是增强且可退出
3. 模块化不是信仰 — 能力包是组织方式之一，不强迫
4. 边界刚、内部柔 — 依赖方向与分层刚性，实现内部自由
5. 宿主落地     — 内核不感知宿主形态
6. 规范先于实现 — 公共契约先进 Spec，再写代码
7. 默认实现必须可用 — 每个抽象配零外部依赖、容量有界的默认实现
```

### 1.1 设计灵感来源

Unix 的"小工具组合"、Rust 的零成本抽象与 `core / std` 分层、Vue 的渐进式设计、Linux"不破坏用户态"的 ABI 承诺，共同塑造了框架的哲学基调：内核只定义抽象的秩序，扩展包提供可替换的实现，内核不替业务做决定。所有借鉴与落地规则见总体方案 §3。

## 二、核心设计决策

### 2.1 抽象与实现解耦

```text
抽象 → <领域>.Abstractions（XiHan.Framework.Persistence.Abstractions）
实现 → 按机制或技术命名（XiHan.Framework.Persistence.InMemory、XiHan.Framework.Persistence.EntityFrameworkCore）
```

内核不包含任何具体技术实现。`IRepository<T>` 是抽象，`EntityFrameworkCoreRepository<T>` 是实现。换 ORM 不需要改内核。"默认"是清单里 `role: default` 的角色，不是包名；今天默认是 `InMemory`，将来可以换，而包名不撒谎。

### 2.2 能力包为可选组织方式

模块化不是被抛弃，而是从强制机制降级为可选组织模式。任何实现 `IFeature` 的类都可以作为一个能力包入口，通过 `UseFeature<T>()` 显式加入；依赖写在 `xihan.manifest.json` 里按能力 ID 解析，不按类型。不扫描、不注入生命周期钩子，用户决定是否组织成能力包、如何组织。

### 2.3 内核不干预

内核做减法，不替业务做决定：

- 不自动注册服务（显式注册，生成器注册可选入）
- 不自动生成 Controller（操作契约 + 协议适配器是可选扩展包）
- 不自动推断约定（约定可覆写，非强制）
- 不隐藏执行细节（管道显式组装，`xihan pipeline dump` 可打印）

### 2.4 显式组合

```csharp
// 新框架 — 显式组合，启动期验证
var app = App.CreateBuilder(args)
    .UseFeature<SecurityFeature>()
    .UseFeature<MultiTenancyFeature>()
    .UsePipeline(pipeline => pipeline
        .UseAt<TenantResolutionMiddleware>(PipelineStage.Tenant)
        .UseAt<AuthorizationMiddleware>(PipelineStage.Authorize))
    .Build();

// 旧框架 — 隐式声明，运行时解析
[DependsOn(typeof(XiHanAuthorizationModule))]
[DependsOn(typeof(XiHanMultiTenancyModule))]
public class MyModule : XiHanModule { }
```

### 2.5 管道执行

每次调用通过一条固定阶段的管道执行：`Ingress → Observe → Resilience → Authenticate → Tenant → Authorize → Validate → Idempotency → Transaction → Handle → Egress`。特性按阶段插入中间件，不需要知道其他中间件；顺序确定、可打印、可测试，测试只需 mock 下一个委托。

### 2.6 协议而非 HTTP

管道不绑定 HTTP。协议适配器（`Protocols.Http` / `.Grpc` / `.Mcp` / `.CloudEvents`、`Hosting.CommandLine`）把线上消息翻译为 XGI 消息进入同一条管道。业务以操作契约声明，一份契约多协议暴露。

### 2.7 版本稳定

公共 API 是框架的"用户态 ABI"。原语层只增不改；内核大版本内不破坏；破坏性变更走三阶段弃用；大版本升级提供 Roslyn 代码修复。公开 API 标记 `Stability` 级别，公开面以 `PublicAPI.Shipped.txt` 为准。内部实现可随时重构。

### 2.8 扩展隔离

三类扩展，三种信任：

| 扩展 | 信任 | 隔离 |
| --- | --- | --- |
| 能力包 | 可信 | 编译期引用，同进程 |
| 进程内插件 `Plugins.InProcess` | 半可信 | 可收集 `AssemblyLoadContext` |
| Wasm 插件 `Plugins.Wasm` | 不可信 | WASI 组件 |
| 进程外插件 `Plugins.OutOfProcess` | 不可信，任意语言 | 子进程 + gRPC 插件协议 |

插件失败降级而不崩溃；权限在清单里声明、由宿主授予、运行期强制。

### 2.9 AOT 优先

- 原语层与内核零运行时反射；注册用源生成器，不用程序集扫描。
- 动态代理用编译期管道委托替代。
- 进程内插件是唯一允许反射的地方，标注 `RequiresDynamicCode`。
- CI 做 AOT 发布冒烟，裁剪警告视为错误。

### 2.10 规范先于实现

原语语义、清单 Schema、上下文传播、管道阶段、插件协议、协议映射、术语表先写进 XiHan Spec，再写 .NET 实现；其他语言按同一规范实现并通过同一套一致性测试。

### 2.11 渐进演进

5.0 只做正确的事，不做完美的事。内核与 Standard 子系统进主线，其余进孵化区且只能标 `Experimental`。每个子系统的 Provider 接口单独版本化，5.0 时代的 Provider 在 5.x 全程可用。

## 三、架构原则

### 3.1 单一职责 — 包级

| 原则 | 规则 |
| --- | --- |
| 每个 NuGet 包只提供一个领域的一个角色 | `XiHan.Framework.Caching.Redis` 只做 Redis 缓存 |
| 抽象包与实现包分离 | `Caching.Abstractions` 独立于 `Caching.Redis` |
| 原语层与内核零第三方依赖 | 仅 `Microsoft.Extensions.*` 抽象包（内核另加 BCL 扩展包 `System.Threading.RateLimiting`） |
| 实现包最小传递依赖 | 只引入该实现必需的库 |

### 3.2 开闭原则 — 管道级

对扩展开放：新中间件可插入任意阶段。对修改关闭：管道核心逻辑不因添加中间件而修改。

### 3.3 依赖倒置 — 端口级

```text
高层（操作、领域） → 定义端口（IRepository）
低层（Provider）   → 实现端口（EntityFrameworkCoreRepository）
```

编译依赖指向抽象，运行时依赖指向实现。

### 3.4 接口隔离 — 协议级

```csharp
// 按能力拆分的协议，而非大而全的基类
public interface IEntity<TKey> { TKey Id { get; } }
public interface ISoftDeletable { bool IsDeleted { get; } }
public interface IMultiTenant { TenantId TenantId { get; } }
public interface IAuditable { DateTimeOffset CreatedAt { get; } }

// 实体按需组合
public sealed class Order : IEntity<OrderId>, IMultiTenant, ISoftDeletable { }
```

### 3.5 最少知识 — 包间通信

包间只通过 `.Abstractions` 通信，不直接依赖具体类型；同环之间只经抽象包往来；依赖只能向更低的环。架构测试强制执行。

## 四、可见性控制

遵循 Rust 的可见性模型：默认 `internal`，显式 `public` 才对外承诺兼容。

```text
所有类型默认 internal
只有显式 public 的类型属于公开 API，并受 Stability 分级与 PublicAPI 文件约束
内部实现可随时重构
InternalsVisibleTo 仅对同名测试项目开放
```

## 五、设计模式选择

| 模式 | 使用场景 | 不用场景 |
| --- | --- | --- |
| **Builder** | `AppBuilder`、`PipelineBuilder` | 简单创建 |
| **Pipeline / Middleware** | 所有调用的执行链 | 纯计算 |
| **Ports & Adapters** | 持久化、缓存、消息等子系统 | 纯业务逻辑 |
| **Feature / Plugin** | 可选能力的装配 | 内核必备能力 |
| **Options** | 能力配置，`IOptionsMonitor` 热更新 | 请求级可变状态 |
| **Source Generator** | 清单、契约 Schema、注册 | 业务逻辑生成 |
| **State Machine** | 特性与插件生命周期 | 请求处理 |

## 六、反模式清单

| 反模式 | 旧框架表现 | 新框架避免方式 |
| --- | --- | --- |
| **上帝基类** | `XiHanModule` 含 7 个生命周期 + 配置方法 | 无基类，只实现 `IFeature`（可选 `IHostedFeature`） |
| **隐式依赖** | `[DependsOn]` 按类型 | 清单按能力 ID 声明，启动期求解并可打印 |
| **深层继承** | 7 层实体基类 | 接口组合，0 层继承 |
| **反射魔法** | 自动注册、动态 API、Castle 代理 | 源生成器 + 显式注册 |
| **包爆炸** | 66 个项目各自独立版本 | 抽象 + 实现分层、共享版本线、Profile 元包 |
| **隐喻命名** | — | 思想只能变成约束，标识符里不出现哲学词汇 |
| **策略进包名** | — | `Default` 不进包名，实现按机制或技术命名 |
| **没有默认实现的抽象** | — | 每个抽象必须有 `InMemory` 等默认实现并通过一致性测试 |

## 七、借鉴的边界

借鉴分三档：

1. **可落成机器检查的规则**：进代码、进分析器、进架构测试（例如 Linux ABI 承诺 → 包验证基线；netfilter 钩子 → 管道阶段）。
2. **可落成文档约束**：进规范与审查清单（例如"反者道之动" → 任何能力可移除）。
3. **只是启发**：留在设计说明里，不进代码。

写不出第一档或第二档的借鉴，一律按第三档处理。
