# 模块开发规范

## 开始方式

1. 阅读目标项目的 `.csproj`、Module 类、README 和直接依赖。
2. 使用 `rg` 搜索同类服务、选项、扩展方法、异常和测试。
3. 确认改动是否真的需要新增公开 API 或新模块。
4. 先定义契约与失败语义，再写默认实现和集成。

## 服务与注册

- 服务注册集中在模块或现有 `ServiceCollection` 扩展中，保持入口简短。
- 优先使用构造函数注入；不要在业务方法中临时解析依赖。
- 明确 Singleton、Scoped、Transient 的状态与线程安全含义。
- 多次调用注册扩展时不得产生重复后台任务、重复订阅或冲突配置。
- Options 应有清楚的默认值、验证和 XML 文档；非法配置快速失败。

## API 与实现

- 使用仓库现有基类、结果、异常和扩展方法，不创造近义类型。
- 异步方法以 `Async` 结尾，接受并传递 `CancellationToken`。
- 不使用 `.Result`、`.Wait()` 或同步阻塞包装异步 API。
- 不捕获宽泛异常后返回空集合、默认对象或 `false`；只在能恢复并保留语义时处理。
- 并发状态使用适合的数据结构并定义原子性，不依赖偶然执行顺序。
- 新依赖优先评估 BCL 是否已覆盖；引入包时同步检查许可证、传递依赖和包体积。

## 文档与兼容性

- 公开类型和成员必须有准确 XML 文档，说明线程安全、所有权、异常和默认行为。
- 改动配置键、序列化字段或扩展方法时，同步更新 README、示例和迁移说明。
- 不把旧 API 标记弃用后无限保留；弃用策略必须与发布计划一致。
- 不为未经证明的消费者设计兜底路径。

## 完成检查

- 所有项目引用和 `[DependsOn]` 一致。
- 新服务可被正确注册、解析和释放。
- 正常、非法、取消、并发和边界条件均有测试。
- 包元数据、XML 文档和示例与实现一致。
- 没有把应用专用行为带入框架默认路径。
