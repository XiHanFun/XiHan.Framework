# 架构与依赖规范

## 分层职责

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| Utils | 独立通用工具、基础扩展 | 领域、容器、Web 与外部服务 |
| Metadata | 类型、特性、描述与元数据模型 | 业务流程和基础设施 |
| Core | 模块系统、DI、配置、生命周期等核心原语 | 应用业务和具体存储 |
| Domain | 领域模型、规则、仓储契约、领域服务 | HTTP、UI 和数据库细节 |
| Application / Contracts | 用例编排、DTO、应用契约 | 具体数据库实现和传输宿主 |
| Infrastructure | 数据、缓存、消息等 Provider | 反向定义上层业务规则 |
| Web | ASP.NET Core、鉴权、接口与宿主集成 | 下沉为通用领域能力 |

任何新类型先回答“最低可成立层是哪一层”。只因上层调用方便，不足以把实现放进上层；只因多个模块需要，也不足以把业务能力塞进 Utils/Core。

## 依赖规则

- 用 `[DependsOn]` 表达模块依赖，用构造函数注入表达服务依赖。
- 下层声明抽象，上层提供实现；Provider 不把具体客户端类型泄漏进通用契约。
- 不通过 `IServiceProvider`、静态单例或反射查找规避显式依赖。
- 新增 ProjectReference 前检查完整依赖图；发现环时重新划分契约，不用延迟加载掩盖。
- `.Abstractions` 保持轻量，不引用具体 Provider、ASP.NET Core 或应用模块。

## 模块生命周期

- 沿用仓库现有生命周期接口和钩子，不自行创建第二套启动协议。
- 依赖模块先初始化、后关闭；新增行为必须验证顺序和失败传播。
- 初始化方法可重复进入时应明确幂等语义；不可重复时应快速失败。
- 长生命周期服务必须正确释放计时器、订阅、连接和后台任务，并响应取消。

## 命名和组织

- 正式项目使用 `XiHan.Framework.<Module>`。
- 纯契约使用 `.Abstractions`；技术实现使用能够说明 Provider 的后缀；Web 集成沿用 `.Web.<Module>` 形式。
- 新代码放入最接近职责的现有项目和命名空间，不为了少量类型新建模块。
- `next/` 是设计和实验区，未经明确决策不得被正式项目引用或当成当前 API。

## 公共 API 决策

公开前确认：

1. 是否必须跨程序集使用。
2. 是否能用内部实现与现有扩展点完成。
3. Nullable、线程安全、所有权、异常和取消语义是否明确。
4. XML 文档与测试是否覆盖默认值和失败路径。
5. 未来替换实现时，契约是否仍稳定。

删除、改名或改变默认行为属于破坏性变更。明确迁移路径和发布影响，不保留未经要求的旧别名。
