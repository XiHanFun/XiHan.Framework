# ADR-0078 运行时数据源与库结构读取

## 状态

已采纳（`spec/rfcs/0005-persistence.md`、`spec/conventions/error-codes.md`、`spec/conventions/vocabulary.md` 随之修订）。

## 日期

2026-11-01

## 背景

BasicApp 6.0 的代码生成（N3 第四批）要连外部库导入表、按最新库结构同步列配置、在零代码运行时里查外部表，并沿用已有的实体（BasicApp 方案 9.5 节 F3、F4，用户已批准回灌框架）。框架只有约定连接 `default` / `shard`，应用只能拿原生 `ISqlSugarClient` 自己 `new SqlSugarClient`、自己调 `DbMaintenance`、自己管缓存与失效；实体不写 `[SugarTable]`，也没有办法靠扫特性认出已有实体。本 ADR 每项一节。

## 一、运行时数据源（F4）

### 背景

应用记录里定义的外部库要在运行中连上：改了连接信息要能替换，不能漏了注销就一直用旧连接串直到重启；要有登记上限、健康检查与不登记的「测试连接」。

### 备选

1. 把外部库加进作用域客户端（`AddConnection`）。作用域客户端每个调用新建一个，连接集合还决定实体落点（`IEntityConnectionSelector`）与工作单元的事务范围（`AsTenant()` 在全部连接上开事务），外部库混进来会被卷进本地事务。
2. 只给工厂 `Create(definition)`：每次新建，缓存、替换、上限、健康都留给应用。
3. 照 ADR-0050 的命名存储实例：中立的注册表按定义建实例、按名缓存，Provider 经端口接入，注册表负责替换、释放、上限与逐实例健康项。

### 决策

采用 3，契约放在 `Persistence.Abstractions`（中立），SqlSugar 实现，EF Core 与内存实现明确不支持。

- 定义 `DataSourceDefinition(name, databaseType, connectionString)`：名字 `^[a-z0-9][a-z0-9-]{0,63}$`，`default` 保留给应用的缺省连接；数据库类型不区分大小写，`DatabaseTypes` 列出 `postgresql`、`mysql`、`sqlserver`、`sqlite`、`oracle`，Provider 认得哪些由 Provider 决定；`Describes` 比名字、类型与连接串。
- 注册表 `DataSourceRegistry`（单例，健康项贡献者）：
  - `GetOrAddAsync(definition)`：同名同定义复用；定义变了建新实例替换旧的并释放旧的；建实例不连库。
  - `RemoveAsync(names)`：批量（ADR-0012），逐项返回是否登记过。
  - `TestAsync(definition)`：建临时实例、打开一次连接再关闭、释放，不登记、不占名额。
  - `GetAsync(name)`：只取本进程已登记的，没有 → `PERSISTENCE_NOTFOUND_002`。
  - 容量 `XiHan:Persistence:DataSources:MaxCount`（缺省 64，1–1024），满了再登记新名字 → `PERSISTENCE_UNAVAILABLE_007`，不淘汰，替换同名的不占名额。
  - 健康：每个数据源一条 `persistence.datasource.<name>`（数据 `databaseType`、`provider`），按 `HealthProbeIntervalSeconds`（缺省 15）在后台打开连接再关闭，新登记的立即探一次；失败或超时 Degraded（`PERSISTENCE_UNAVAILABLE_006`）。
- 失效选显式 API 加定义比对，不用配置变化令牌：定义来自应用的库，不来自 `IConfiguration`，没有变化令牌可挂。应用在记录改了、停用或删了时调 `RemoveAsync`；每次使用都以记录里当前的定义调 `GetOrAddAsync`，定义变了即替换。注册表是进程内的，多实例时别的实例在下一次以新定义取用时替换——所以库结构读取等入口一律收定义而不收名字。
- Provider 端口 `IDataSourceProvider`（`Name`、`Supports(type)`、`CreateAsync`、`ProbeAsync`），由 `AddDataSourceProvider<T>(configuration)` 登记；注册表取第一个认得该类型的。没有 Provider 时（EF Core、内存实现经 `AddDataSourceRegistry()` 只登记注册表）取用与测试连接返回 `PERSISTENCE_UNAVAILABLE_008`。
- 机密：`DataSourceDefinition.ToString()` 不含连接串；错误与健康详情的 `reason` 取驱动异常的消息链，经 `ConnectionStrings.Redact` / `Describe` 把整串连接串与口令类键（键名含 `password`、`pwd`、`secret`、`token`、`key`）的值换成 `***`；日志只记名字与数据库类型。
- SqlSugar：数据库类型是 `DbType` 的名字（`Custom` 与数字不认）；`SqlSugarDataSource.Client` 是每个数据源一个的 `SqlSugarScope`（线程安全、`IsAutoCloseConnection`），不施加实体约定、不挂过滤器与 AOP、不进工作单元，PostgreSQL 上 `PgSqlIsAutoToLower = false`；登记时由驱动解析连接串（只构造连接对象），格式错 → `PERSISTENCE_VALIDATION_006`；探测与测试连接另建客户端、打开原生 `DbConnection` 再关闭。运行时数据源不加进作用域客户端，`default` / `shard`、`IEntityConnectionSelector` 与租户分片照旧。
- 错误码：`PERSISTENCE_NOTFOUND_002`、`PERSISTENCE_VALIDATION_006`、`PERSISTENCE_UNAVAILABLE_006`、`_007`、`_008`；消息键 `persistence.datasource.{not_found, database_type_unknown, definition_invalid, unavailable, capacity_exceeded, not_supported}`，十种区域。

### 理由

- 外部库不该进作用域客户端：作用域客户端的连接集合同时是实体落点与事务范围，加进去会把别人的库卷进本地事务。独立的注册表让两套连接互不相干。
- 按定义比对替换，应用不必判断「改没改」，也不会因为漏了注销就一直用旧连接串。显式 `RemoveAsync` 仍然需要：停用与删除没有新定义可比。
- 登记满了拒绝而不淘汰：淘汰会让正在用某个数据源的调用悄悄换连接，拒绝至少是明确的错误。
- 测试连接不登记：保存前的测试不该占名额、不该触发健康项，也不该替换已登记的同名实例。
- 打开原生连接而不用 SqlSugar 的 `IsValidConnection`：后者吞掉异常只返回 `false`，「测试连接」要告诉用户为什么连不上。
- PostgreSQL 不自动转小写：外部库的标识符可能是加了引号的大小写混合名（EF Core 建的库就是），转小写就查不到；本应用的表由 SqlSugar 建、本来就是小写，按原样引用同样能查。
- 脱敏只遮口令、不遮主机与用户名：连接问题多半要靠主机、端口、库名、用户名排查，它们不是机密；口令与整串连接串不进任何对外的地方。
- EF Core 不支持：数据库 Provider（`UseNpgsql` 等）由应用选、本包不引用，按「数据库类型 + 连接串」建连接要对应的 Provider 包；明确报错而不是建一个用不了的空壳。BasicApp 用 SqlSugar。

### 影响

- 公开 API：`Persistence.Abstractions` 新增 `DataSources.*`（`DataSourceDefinition`、`DatabaseTypes`、`IDataSource`、`IDataSourceProvider`、`DataSourceRegistry`、`DataSourceOptions`、`DataSourceServiceCollectionExtensions`、`ConnectionStrings`），`PersistenceErrors` 五个常量、`PersistenceMessages` 六个常量；`Persistence.SqlSugar` 新增 `SqlSugarDataSource`、`SqlSugarDataSourceExtensions.GetSqlSugarClient`；`Persistence.Conformance` 新增 `DataSourceConformance`。
- 配置：新增 `XiHan:Persistence:DataSources:MaxCount`、`HealthProbeIntervalSeconds`，值不合法时 SqlSugar 特性装配即失败（`ArgumentException`）。SqlSugar 清单的配置节改为 `XiHan:Persistence`（同时读 `XiHan:Persistence:SqlSugar` 与 `XiHan:Persistence:DataSources`，按 ADR-0075 写最近公共节）。
- 行为：三个持久化 Provider 都登记 `DataSourceRegistry`（EF Core 与内存实现没有 Provider）；SqlSugar 应用的健康报告多出每个已登记数据源一条（Degraded 不影响 readiness）。
- 测试：抽象层用替身 Provider 覆盖复用 / 替换 / 释放、批量移除、容量、测试连接不登记、健康项、不支持与脱敏；SqlSugar 在 SQLite（外部文件、只读打开不存在的文件、连接串关键字错误）与 PostgreSQL（错误口令带 `28P01` 而不带口令、大小写混合的表名）上验证；`DataSourceConformance` 由 SqlSugar（SQLite、PostgreSQL）、EF Core、内存实现四个测试类继承。

## 二、库结构读取与实体目录（F3）

### 背景

SqlSugar 的 `DbMaintenance` 能读表与列，但全量返回、不分页，分表不折叠；用当前租户的客户端读会落进当前事务。BasicApp 的实体不写 `[SugarTable]`，扫不出「已有实体」。

### 备选

1. 只给 SqlSugar 包的帮助方法：EF Core 应用拿不到中立契约，代码生成要绑死 SqlSugar 类型。
2. 中立契约 + Provider 实现，读不了的 Provider 明确报错。
3. 中立层用 ADO.NET 的 `DbConnection.GetSchema` 自己实现：各驱动返回的集合与列不同（`Microsoft.Data.Sqlite` 不实现），等于每种数据库各写一遍，SqlSugar 已经做了。

### 决策

采用 2，契约在 `Persistence.Abstractions` 的 `Schema` 命名空间。

- `ISchemaReader`：
  - `ListTablesAsync(dataSource, TableListQuery)`：表（不含列），按名字排序，`Keyword` 包含匹配，`Skip` / `Take` 分页（`Take` 最多 1000，超过构造时以 `PERSISTENCE_VALIDATION_005` 拒绝），返回过滤后的总数。
  - `GetTablesAsync(dataSource, tables)`：批量读结构，一次最多 `SchemaLimits.MaxTablesPerRead`（100）张，超过整批 `PERSISTENCE_VALIDATION_005`（新消息键 `persistence.schema.too_many_tables`）；逐项结果，找不到的表 `PERSISTENCE_NOTFOUND_003`；连接或读取失败整批 `PERSISTENCE_UNAVAILABLE_006`（新消息键 `persistence.schema.read_failed`）；空集合不连库。`GetTableAsync` 是单项特例。
  - 数据源 `null` 是应用的缺省连接（另开不在事务里的连接）；否则收 `DataSourceDefinition`，先 `GetOrAddAsync` 再读，不收名字。
- 列 `ColumnInfo`：名字、类型名、序号、主键（一律不可空）、自增、可空、长度、精度与小数位（定点数族）、注释、缺省值原文。表 `TableInfo`：名字、注释、物理表、是否分表。
- 分表：按已登记的分表实体的表名模板（`{year}` 四位、`{month}` / `{day}` 两位，不区分大小写）折叠成逻辑表（去掉占位符与首尾 `_`），物理表新到旧，列取最新的物理表；物理表名不能单独读。
- `IEntityCatalog.ListAsync()`：每个 `AddRepository` 登记的实体一条 `EntityMapping`（按登记顺序、去重）：实体与标识类型、表名（映射声明的写法，分表是逻辑名）、`IsSplit`、`EntityProtocols`、列映射（属性、列名、CLR 类型、主键、可空）、`[EntityIndex]` 推出的索引。为此 `RepositoryRegistrations` 新增 `Entities`（`RegisteredEntity`），`AddRepository` 的 `TEntity` 标注保留公开属性。
- Provider：SqlSugar 两者都实现（`DbMaintenance`、`EntityMaintenance.GetEntityInfo`）；EF Core 实体目录取 DbContext 模型、读结构不支持；内存实现实体目录取类型名与属性名、读结构不支持。不支持的经 `AddUnsupportedSchemaReader()` 登记，返回 `PERSISTENCE_UNAVAILABLE_008`（新消息键 `persistence.schema.not_supported`）。

### 理由

- 收定义而不收名字：读结构前按记录里当前的定义登记，多实例下也不会拿旧连接串读（见第一节）。
- 缺省连接另开连接：PostgreSQL 系语句失败会中止所在事务，读结构失败不能连累调用的业务写入。
- 列表一次读出再在内存里分页：各数据库的系统目录查询不统一分页，SqlSugar 只给全量；表的数量是有界的。读列是每张表一次查询，所以批量读设上限而列表不设。
- 分表按登记的模板折叠，不按「表名末尾是日期」猜：猜会把 `Report_2026` 这类普通表误折；外部库里的分表没有登记的实体就照物理表列出。
- 主键归一为不可空、长度与精度分开：代码生成按这些推断 C# 类型与校验，SQLite 的报告与其他库不一致时由读取层统一，而不是让每个使用方处理。
- EF Core 不读结构：跨数据库的读法在 EF Core 里是设计期脚手架服务（`Microsoft.EntityFrameworkCore.Design` 的 `IDatabaseModelFactory`，按数据库 Provider 程序集反射发现），不是运行时组件；`GetSchema` 各驱动不一致。实体目录能从模型取，照做。
- 内存实现的实体目录照它的存储形态（类型名、属性名）给出，不是空结果：枚举实体在测试里同样有用；读结构没有数据库可读，明确报错。

### 影响

- 公开 API：`Persistence.Abstractions` 新增 `Schema.*`（`ISchemaReader`、`SchemaReaderExtensions`、`SchemaLimits`、`TableListQuery`、`TablePage`、`TableInfo`、`TableSchema`、`ColumnInfo`、`IEntityCatalog`、`EntityMapping`、`EntityColumnMapping`、`EntityProtocols`、`SchemaServiceCollectionExtensions`）、`Repositories.RegisteredEntity`、`RepositoryRegistrations.Entities`、`PersistenceErrors.TableNotFound`、`PersistenceMessages` 四个常量；`AddRepository` / `RepositoryRegistrations.Add` 的 `TEntity` 加 `[DynamicallyAccessedMembers(PublicProperties)]`（不改签名）；`Persistence.Conformance` 新增 `SchemaConformance`。SqlSugar、EF Core、内存实现的实现类型都是 internal。
- 错误码：新增 `PERSISTENCE_NOTFOUND_003`；`PERSISTENCE_VALIDATION_005`、`PERSISTENCE_UNAVAILABLE_006`、`PERSISTENCE_UNAVAILABLE_008` 的含义扩展到库结构读取。
- 行为：三个持久化 Provider 都登记 `ISchemaReader` 与 `IEntityCatalog`；EF Core 的实体目录遇到登记了却不在模型里的实体抛 `InvalidOperationException`。
- 测试：SQLite 上列属性与限制、分表折叠（两个月的物理表折成 `split_records`）、实体目录的表名与索引、运行时数据源读外部库与读取失败的脱敏；PostgreSQL 上注释、identity、serial 缺省值、`numeric` 精度与加引号的大小写混合表名；`SchemaConformance` 由 SqlSugar（SQLite、PostgreSQL）、EF Core、内存实现四个测试类继承。

## 不在范围

视图、索引、外键、存储过程的读取不在本次范围：代码生成没有用到，SqlSugar 的 `GetIndexList` 只给名字、跨库不一致。

> 修订（2026-11-01）：库结构读取在 MySQL、Oracle、SQL Server 上实测，列的长度只给字符与二进制类型、Oracle 的读列改查数据字典、运行时数据源在 Oracle 上不自动转大写（ADR-0084 第四节）；表列表的分页越界（含 `Take` 超过上限）改由读取器以结果返回，`Skip` 为负或 `Take` 小于 1 是新码 `PERSISTENCE_VALIDATION_007`（ADR-0084 第三节）。
