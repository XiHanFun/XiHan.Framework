# ADR-0066 AI 与工作流的身份、原子性与租户隔离

## 状态

已采纳（`spec/rfcs/0022-ai.md`、`spec/rfcs/0021-workflow.md` 随之修订）。

## 日期

2026-11-01

## 背景

写 5.0 文档站时，对照代码发现 AI 与工作流两个子系统里有几处行为与 ADR、RFC 的意图相悖，或者在失败、并发、多租户下丢数据、串数据。本 ADR 记录修正时做出的设计决定，按条目分节。

### 1. 操作工具丢失调用方身份

ADR-0017 的要点之一是"操作即工具，工具不会绕过授权"。实现与 RFC-0022 却只把调用方的 trace-id、截止时间与 Baggage 复制进工具调用的新上下文，安全上下文与凭据都不带：

- 工具调用在 Authenticate 阶段是匿名的。
- 契约声明了 `Permission` 的操作，经模型调用一律被拒绝（`SECURITY_DENIED_001`），不管发起聊天的用户有没有这个权限。
- 原有测试只覆盖了没有权限要求的操作，看不出问题。

### 2. 重新摄入先删后写

`KnowledgeIngestor` 重新摄入一篇文档时，先按文档删掉旧块，再嵌入、校验维度、写入新块。嵌入端点不可达、维度不一致或写入失败，任何一步出错，这篇文档就从知识库里消失，直到重试成功。`IKnowledgeStore` 只有按文档整篇删除，没有别的办法在写入新块之后只删多出来的旧块。

### 3. 外部任务领取读回整个主题

`WorkflowExternalTaskService.FetchAsync` 的 `maxTasks` 只校验不小于 1，没有上限；领取先用 `ByKindAndKeyAsync` 读回该主题的全部书签（所有租户、已锁定的也在内），再在内存里筛租户、可领取时刻并截取前 `maxTasks` 条。积压的主题每次领取都把全部书签反序列化一遍，调用方还能一次锁住任意多条任务。

### 4. 重用策略的查重与创建不原子

`WorkflowEngine.StartAsync` 的 `ReusePolicy` 先 `ListAsync` 查同名定义、同一关联 ID 下未结束的实例，没有再 `SaveAsync` 写新实例，两步之间没有锁，存储也没有唯一约束。两个并发的 `RejectActive` 启动都查不到对方、各建一个实例。用探针把两个启动卡在"查重之后、写入之前"，内存实现与数据库实现都复现出两个实例。

### 5. 定义的名字与版本号跨租户共用

定义带 `TenantId`，但名字与版本号是全体租户共用的：

- `MaxVersionAsync(name)`、`FindLatestPublishedAsync(name)`、`FindAsync(name, version)` 都不看租户。租户 B 新建与租户 A 同名的定义，版本号接在 A 的后面。
- 引擎按名字启动不核对租户，租户 B 按名字启动会拿到租户 A 的已发布定义，跑出一个属于 B 的实例；按 ID 启动别的租户的定义也照样成功。
- 目录的查找、列表、按 ID 的发布 / 停用 / 删除与 `NewVersionAsync`（以全体租户里的最新版本为底）都不看租户。
- 重用策略按定义名与关联 ID 查重也不看租户：别的租户同一关联 ID 的实例会挡住启动，`ReturnActive` 还会把它返回。

RFC-0021 只写了"存储不按租户过滤（调用方负责）"与信号启动看"调用方租户或无租户的定义"，没有写定义的名字空间与可见性。新用例修正前在第一步就失败：租户 B 的同名定义得到版本 2；跳过这一步，租户 B 按名字启动成功、跑的是 A 的定义。

### 6. 引擎按实例 ID 的控制不核对租户

用户任务、外部任务与信号按书签租户与调用方租户相等匹配，引擎的入口却不核对租户：

- 按实例 ID 的挂起、恢复、取消（含补偿）、终止、重试、改变量、跳转、迁移，有租户的调用方能操作别的租户的实例。
- 按书签 ID 的 `ResumeAsync` 能消费别的租户的书签。
- `PurgeAsync` 能清掉所有租户的实例。
- 启动请求的 `TenantId` 可以写成别的租户。
- 实例查询只有存储契约 `IWorkflowInstanceStore`，它按约定不过滤租户，应用必须自己记得写上租户。

新用例在修正前第一处断言就失败：租户 t2 挂起 t1 的实例成功。

## 备选

### 1. 工具调用的身份

1. 复制凭据，让 Authenticate 阶段在新上下文里重新认证。与 MCP 的 `tools/call` 一样，但 `AI.Abstractions` 要引用 `Security.Abstractions` 才拿得到凭据；调用方不经凭据认证（插件回调、测试、应用自己写入主体）时仍然是匿名；每次工具调用都多一次认证。
2. 复制调用方的安全上下文（主体与租户），不复制凭据。
3. 保持匿名，文档里要求工具只用于没有权限要求的操作。

### 2. 重新摄入的替换方式

1. 存储契约加"整篇原子替换"方法，由 Provider 实现。向量库普遍没有跨记录事务，Provider 也只能先写后删，等于把同一段逻辑复制到每个 Provider。
2. 新块写在新的记录 ID 下（如带版本号），写成功后删旧版本。记录 ID `<documentId>#<chunkIndex>` 是 RFC 里的契约，改它会让检索结果的 ID 变化。
3. 存储契约加 `TrimAsync(collection, documentId, chunkCount)`：删除该文档块序号不小于 `chunkCount` 的记录。摄入先写新块（同 ID 覆盖），写成功后再裁掉多余的旧块。

### 3. 领取的条数

1. 给 `ByKindAndKeyAsync` 加一个 `limit` 参数。租户与可领取时刻仍在内存里筛，截取发生在筛选之前，别的租户或已锁定的书签会占满名额，领取可能一条也拿不到。
2. 书签存储加 `AvailableAsync(kind, key, tenantId?, now, limit)`：租户（相等，空只匹配无租户）、到期时刻（为空或不晚于此刻）与条数都在存储查询里完成。

### 4. 查重与创建的原子性

1. 存储层唯一约束：未结束实例上的（定义名、关联 ID）唯一。"未结束"是状态条件，要部分唯一索引或额外的标记列，SqlSugar 建表不支持部分索引；内存实现要另写一套；实例结束、迁移、改关联 ID 都要维护它。
2. 按（定义名、关联 ID）加锁，查重与写入都在锁里。复用已有的 `IWorkflowInstanceLock`：内存实现是进程内信号量，数据库实现是跨节点的租约行，Provider 不用新增任何东西。

### 5. 定义的租户隔离

1. 只在引擎与目录里事后过滤：存储按名字的查询仍跨租户。版本号照样跨租户递增，"最新已发布"可能是别的租户的版本、过滤掉之后就找不到本租户真正的最新版本。
2. 名字空间下推到存储：按名字的三个查询带上租户，按相等比较（空只匹配全局定义）；可见与可改的规则在目录与引擎里统一判定。
3. 全局定义只给平台用，租户一律看不到。各租户共用的流程模板就得在每个租户里复制一份，与信号启动已有的"调用方租户或无租户的定义"也不一致。

### 6. 实例的租户隔离

1. 在每个公开方法里逐个核对。入口多，漏一个就是越权；内部接续（轮询、子流程回调、级联）也要分清是不是"调用方"。
2. 在加载会话处统一核对：按实例 ID 的控制都经 `RunLockedAsync` → `LoadAsync`，在那里判定一次；按书签 ID 的恢复在取书签之后判定；清理与查询各自限定租户。
3. 对无租户的实例也开放给租户调用方（像全局定义那样）。实例是一次执行，没有"共用"的意义，无租户的实例属于平台。

## 决策

### 1. 工具以调用方身份执行

- 取 2。`OperationAIFunction` 在工具被调用时读取调用方的 `SecurityContext`（`Kernel` 的原语），写进新上下文。
- 凭据不复制：Authenticate 阶段没有凭据可认证，保留复制来的主体；`RequireAuthentication` 照常检查它。
- Authorize 阶段以调用方主体按契约判定：有权限放行；已认证没有权限是 `SECURITY_DENIED_004`；匿名是 `SECURITY_DENIED_001`。失败照旧以 `{"error","message"}` 交给模型。
- Tenant 阶段照常解析：主体与 Baggage 都与调用方相同，解析结果一致；没有解析器给出结果时保留复制来的租户。

### 2. 重新摄入先写后删

- 取 3。顺序改为：切块 → 嵌入 → 校验维度 → `UpsertAsync` 写新块 → `TrimAsync(documentId, 新块数)`。
- 写入之前任何一步失败都不碰旧块。写入中途失败最多留下新旧混合的块，文档仍可检索，重试摄入即恢复一致。
- 裁剪失败如实返回错误：新块已在库里，多余的旧块留待下次摄入删除。
- 新文本切不出块时整篇删除，返回 0，与原来一致。
- `AI.VectorData` 的集合定义把 `ChunkIndex` 也标为可过滤字段，裁剪以 `DocumentId == id && ChunkIndex >= n` 分页取键再按键删。

### 3. 外部任务领取限量下推

- 取 2。`maxTasks` 取 1 到 `IWorkflowExternalTaskService.MaxTasksPerFetch`（100），越界是 `WORKFLOW_VALIDATION_002`。
- 领取以 `AvailableAsync(External, topic, 当前租户, now, maxTasks)` 取候选，候选照旧在实例锁内重读确认：锁与 `notBefore` 的精确判定、实例是否运行中。被别的工作者抢先或实例已不在运行的跳过，结果可能少于 `maxTasks`。
- 书签的 `DueAt` 已经是"何时可以再领"：锁定时是锁到期时刻，带 `RetryAfter` 失败时是 `notBefore`，新挂起时为空。所以"可领取"在存储里就是 `DueAt` 为空或不晚于此刻。

### 4. 重用策略在锁里查重与写入

- 取 2。要查重时（有关联 ID、策略不是 `AllowDuplicate`），先以键 `start.` + SHA-256(定义名 + 换行 + 关联 ID) 的十六进制获取实例锁，在锁里查重、补全变量、写入新实例，写入完成才释放；之后照旧在实例锁里执行第一个波次。
- 两把锁不嵌套：查重锁在写入后即释放，再取实例 ID 的锁，不会与别的启动形成环。
- `AllowDuplicate` 与没有关联 ID 的启动不加这把锁，开销不变。
- 锁键是不透明字符串，RFC 写明它可以是实例 ID、定义 ID 或 `start.` 开头的派生键，长度不超过 128。

### 5. 定义按租户的名字空间

- 取 2。定义属于一个租户或是全局定义；(`TenantId`, `Name`, `Version`) 唯一，各名字空间各自从版本 1 编号。
- 看得到：有租户的调用是本租户与全局定义，无租户的调用（平台）是全部。改得动：有租户的调用只有本租户的定义，无租户的调用是全部。看不到、改不动都按不存在处理（`WORKFLOW_NOTFOUND_001`）。
- 按名字解析（启动、`FindPublishedAsync`、子流程与 ForEach）先找调用方租户的名字空间，没有已发布的匹配版本再找全局定义。
- `CreateAsync` 在定义所属租户的名字空间里编号；`NewVersionAsync` 只以当前租户名字空间里的最新版本为底。
- 引擎按 ID 启动别的租户的定义按不存在处理；实例租户仍是请求的、缺省当前调用的，都没有时取定义的（平台按 ID 启动租户的定义）。
- 迁移只迁到同一名字空间里的同名版本。重用策略只在同一租户里查重，锁键加上租户。
- 名字解析与可见性规则集中在内部的 `WorkflowDefinitionNamespace`，目录与引擎共用。

### 6. 实例按租户隔离

- 取 2。有租户的调用只看得到、操作得了 `TenantId` 与本租户相等的实例与书签（无租户的也看不到）；无租户的调用（平台、轮询器）看得到全部，照旧。
- `LoadAsync` 里看不到的实例按不存在（`WORKFLOW_NOTFOUND_002`），覆盖全部按实例 ID 的控制；`ResumeAsync` 先核对书签（含定义级定时书签），看不到按 `WORKFLOW_NOTFOUND_003`。
- `PurgeAsync` 把查询的租户限定为调用方租户。
- 有租户的调用在请求里写了别的租户 → `WORKFLOW_NOTFOUND_001`，不暴露那个租户有什么定义。
- 引擎新增 `FindInstanceAsync`、`ListInstancesAsync`、`CountInstancesAsync`、`NodeInstancesAsync`：存储查询加上调用方租户，点名别的租户得空结果。存储契约仍不过滤，留给 Provider 与平台。
- 用户任务、外部任务与信号原有的"租户相等"规则不变（无租户的调用只匹配无租户的书签）。

## 理由

### 1. 工具调用的身份

- 工具调用发生在调用方自己的调用之内（`IAIChat` 绑定的是当前调用），调用方已经在自己的管道里认证过，主体是进程内可信的对象，再认证一次没有增加安全性。
- 安全上下文是 `Kernel` 的原语，AI 包不必依赖安全包；无论调用方怎样得到主体，工具都继承它。
- "模型能做的事不超过发起聊天的用户本人能做的事"是唯一既不越权、又不让权限声明失效的语义。

### 2. 重新摄入的替换方式

- 记录 ID 由文档 ID 与块序号决定，新旧版本同序号的块天然同 ID，写入就是覆盖；只有旧版本多出来的尾部需要删除，裁剪正好描述这件事。
- 先写后删把"失败时丢文档"变成"失败时最多新旧混合"。对检索来说，过时的块比整篇消失好得多，而且重试就能恢复。
- 逻辑留在流水线里，Provider 只实现一个按条件删除，与已有的按文档删除同构。

### 3. 领取的条数

- 条数限制只有和全部筛选条件一起下推才有意义；租户在这里是查询键而不是事后过滤，与"存储不按租户过滤、由调用方负责"不冲突。
- 上限 100 与每条领取都要获取一次实例锁、写一次书签的成本相称；要更多就多领几次。

### 4. 查重与创建的原子性

- 锁已经是 Provider 必须提供、一致性套件验证过互斥的契约，数据库实现跨节点生效；唯一约束要改表结构、两套实现各写一遍，还要处理状态变化。
- 键取哈希：定义名与关联 ID 的长度加起来可能超过锁表主键的 128 个字符，哈希后定长，前缀 `start.` 让它不会与 32 位十六进制的实例 ID、定义 ID 撞上。

### 5. 定义的租户隔离

- 版本号与"最新已发布"只有在存储查询里按名字空间算才对，事后过滤修不了编号。
- 全局定义对租户可见，与信号启动的现有规则一致，也让平台能下发共用的流程模板；租户发布同名定义即可覆盖。
- 无租户的调用看得到全部，与 `WorkflowInstanceQuery.TenantId` 为空时不限定租户的约定一致，平台管理面不必逐个租户切换。
- 看不到按不存在处理而不是拒绝，不向别的租户暴露定义是否存在。

### 6. 实例的租户隔离

- 加载会话是按实例 ID 的控制的唯一汇合点，在那里判定，新加的控制方法自动受约束。
- 引擎内部的接续沿用发起它的调用的租户：轮询器没有租户，子流程与父实例同租户，判定在这些路径上都成立，不需要为内部调用开后门。
- 查询放进引擎，应用的列表、详情与状态不用再自己拼租户条件；存储契约保持 Provider 简单。

## 影响

### 1. 工具调用的身份

- 行为：经模型调用声明了权限的操作，调用方有权限即放行。没有权限要求的操作不变。
- RFC-0022「工具」一节改写调用规则；文档站 AI 指南把原来的警告改为说明。
- 测试：调用方经管道认证后绑定并调用带权限的工具，有权限放行且工具看到调用方主体、租户与 trace-id；没有权限与匿名分别被拒。去掉修正后有权限的用例失败、没有权限的用例得到 `SECURITY_DENIED_001`。

### 2. 重新摄入的替换方式

- 公开 API：`IKnowledgeStore` 新增 `TrimAsync`，`VectorDataKnowledgeStore` 实现它；`KnowledgeStoreConformance` 新增裁剪用例。自己实现 `IKnowledgeStore` 的应用要补这个方法。
- `KnowledgeVectorRecord.Definition` 把 `ChunkIndex` 标为可过滤。要求在建集合时声明过滤字段的向量库上，旧集合要重建才能裁剪，否则裁剪以 `AI_UNAVAILABLE_002` 失败。
- RFC-0022「知识库」一节写明先写后删与裁剪的契约。
- 测试：重新摄入时嵌入失败、维度不一致、写入失败，旧块原样保留、照常可检索；裁剪失败如实报错，重试后只剩新块。按旧的先删后写逻辑复跑，嵌入失败一步之后旧块即为空。

### 3. 领取的条数

- 公开 API：`IWorkflowBookmarkStore.AvailableAsync`（内存与数据库实现）、`IWorkflowExternalTaskService.MaxTasksPerFetch`。自己实现书签存储的 Provider 要补这个方法。
- 数据库实现的到期条件写成 `DueAt <= now || DueAt == null`：反过来写会被 SqlSugar 翻译失败（`KERNEL_UNEXPECTED_001`）。
- 测试：存储套件新增可领取书签的过滤、排序与上限（含恰好到期与跨租户）；任务套件新增按创建先后限量领取、别的租户领不到，原外部任务用例补上限越界。

### 4. 查重与创建的原子性

- 行为：并发的同键 `RejectActive` 启动只有一个成功，其余得到 `WORKFLOW_CONFLICT_005`；`ReturnActive` 都拿到同一个实例。等锁超过 `LockTimeout` 得到 `WORKFLOW_TIMEOUT_001`。
- 没有新的公开 API；引擎套件新增并发启动用例。套件以装饰器接入 Provider 的实例存储与锁（按 Provider 登记的具体类型），所以 Provider 要以具体类型登记它们、再以 `TryAdd` 转发接口——两个内置 Provider 本来就这样写。
- 测试：探针让第一个启动停在查重处，等第二个启动也走到查重处（不原子）或在锁上等待（原子）再放行，不睡眠、不赛跑。修正前内存与数据库实现都建出两个实例，修正后各连跑 5 轮、并发 8 份负载下 2 轮都通过。

### 5. 定义的租户隔离

- 公开 API：`IWorkflowDefinitionStore` 的 `FindAsync(name, version, tenantId)`、`FindLatestPublishedAsync(name, tenantId)`、`MaxVersionAsync(name, tenantId)` 多了租户参数，内存与数据库实现随之修改；自己实现定义存储的 Provider 要跟着改。目录的方法签名不变，行为按上面的规则收紧。
- 行为：不同租户的同名定义版本号各自编号；已有数据里跨租户交错的版本号不重排，新建的版本按本名字空间的最大版本递增。
- RFC-0021 新增「定义的租户」一节，目录、启动、重用策略、迁移、存储契约与一致性随之修订；error-codes 的 `WORKFLOW_NOTFOUND_001` 补上"看不到 / 改不动"。
- 测试：存储套件新增按名字的查询以租户为名字空间；引擎套件新增定义按租户隔离（两个租户同名定义各自编号，按名字、请求租户与 ID 启动都启动不到别的租户的定义，目录的查找、列表、停用、归档、更新看不到别的租户的定义，新版本以本租户为底，全局定义可用且本租户同名定义优先，迁移不跨名字空间，重用策略只在同租户查重，无租户的调用看得到全部），内存与数据库实现都通过。

### 6. 实例的租户隔离

- 公开 API：`IWorkflowEngine` 新增四个查询方法。行为：有租户的调用操作别的租户的实例与书签得到 `WORKFLOW_NOTFOUND_002` / `003`，清理只清本租户，不能为别的租户启动实例；无租户的调用不变。
- RFC-0021「实例与执行」新增「实例的租户」与「查询」两条；error-codes 的 `WORKFLOW_NOTFOUND_001`–`003` 补上租户语义；文档站的实例查询改用引擎的查询方法。
- 测试：引擎套件新增实例按租户隔离（t2 对 t1 的实例逐个调用八种控制、按书签恢复、完成 / 转办 / 加签用户任务、完成 / 失败外部任务、查实例与节点轨迹、写成 t1 的启动、清理，都按不存在或得空；t1 照常挂起、终止自己的实例；无租户的调用看得到、操作得了全部），内存与数据库实现都通过。测试辅助方法把管道内的断言失败原样抛出，不再被翻译成意外错误。
