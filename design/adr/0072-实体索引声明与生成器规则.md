# ADR-0072 中立的实体索引声明、唯一键重复；值类型实体由警告改为错误

## 状态

已采纳（`spec/rfcs/0005-persistence.md` 新增「索引声明」一节并修订仓储与批量的失败语义，`spec/conventions/error-codes.md` 登记 `PERSISTENCE_CONFLICT_003`）。

## 日期

2026-11-01

## 一、框架表的索引与中立的索引声明

### 背景

发件箱、审计、授予、翻译、调度、工作流的数据库记录（`*.Database` 包与 `Messaging.Abstractions` 的 `OutboxMessage`）一个索引都没有：

- 轮询与清理都是全表扫描：发件箱按「未投递、未进死信、到期」取批次，调度按「等待中、到期」抢占触发器、每个节点按「运行中、请求了取消、本节点」轮询运行记录，工作流按到期时间取书签，各自的保留期清理按时间删旧行。
- 业务上唯一的键没有约束：授予的（主体种类、主体 ID、权限码、租户）、翻译的（键、区域）、触发器的（作业、名字）、工作流定义的（名字、租户、版本）。BasicApp 宿主实测 `message_translation` 表里同一键、同一区域出现了重复的行。
- 各包 README 只给 EF Core 应用写了"建议索引"，要应用自己 `HasIndex`；SqlSugar 的 `InitTables` 什么都不建，而 BasicApp 正是 SqlSugar + PostgreSQL。

这些包只引用 `Persistence.Abstractions`，实体是 Provider 中立的（DataAnnotations 与 `[LongText]`），同时由 SqlSugar 与 EF Core 两个 Provider 映射。

核对 `message_translation` 的重复行时还发现了写入路径的缺陷：`MessageTranslationStore.UpsertAsync` 先按（键、区域）查已有的行，查询只读第一页（1000 条），键与区域两个 `IN` 的笛卡尔积超过一页时，超出的已有行被当成新行再插一遍——150 个键 × 10 种区域写两次就多出 500 行。

### 备选

#### 声明方式

1. 在实体上直接标 SqlSugar 的 `[SugarIndex]`。中立的 `*.Database` 包与 Ring 2 的 `Messaging.Abstractions` 因此依赖 `SqlSugarCore`，换 EF Core 的应用被迫带上它；EF Core 不读这个特性，EF 侧仍要手写 `HasIndex`。
2. 标 EF Core 的 `[Index]`（`Microsoft.EntityFrameworkCore.Abstractions`）。同样把第三方依赖带进中立包，SqlSugar 不读它。
3. 维持现状，只在 README 写建议索引。SqlSugar 应用实际没有索引，EF 应用各写各的名字。
4. 在 `Persistence.Abstractions` 定义中立的 `[EntityIndex]`，与 `[LongText]` 同一套路，由共用的解析推出名字与列，两个 Provider 各自映射。

#### 命名

1. EF Core 的缺省写法 `IX_表_列1_列2`（全列名）。授予表的唯一索引是 `UX_PermissionGrantRecord_SubjectKind_SubjectId_Permission_TenantId`，66 个字符，超过 PostgreSQL 的 63；PostgreSQL 会静默截断，SqlSugar 下一次 `InitTables` 按全名查不到已有索引，再建即撞名。
2. 由声明方给名字。名字随人走，两个 Provider、两个包之间难以一致。
3. BasicApp 的写法：`IX_` / `UX_` + 表名 + 每列缩写。BasicApp 是手写缩写，不完全一致；框架按固定规则推出。

#### SqlSugar 怎样接收非特性来源的索引（SqlSugarCore 5.1.4.221）

1. `InitTables` 之后由特性自己调 `DbMaintenance.CreateIndex`。要重写一遍"按名字查是否已有"的逻辑，而且只在特性的 `InitTables` 里生效，应用自己调 `CodeFirst.InitTables` 时没有索引。
2. 在表服务回调 `ConfigureExternalServices.EntityNameService` 里把 `SugarIndexAttribute` 加进 `EntityInfo.Indexs`。`EntityMaintenance.GetEntityInfoNoCache` 读完 `[SugarIndex]` 之后调用这个回调，`CodeFirstProvider.CreateIndex` 对 `Indexs` 里的每一项按名字 `IsAnyIndex` 查不到才 `CREATE [UNIQUE] INDEX`，任何 `InitTables` 调用都生效。

#### 软删除实体的唯一索引

1. 把删除标记列纳入唯一索引（BasicApp 现行写法 `UX_{table}_…` 含 `IsDeleted`）。
2. 部分索引 `WHERE IsDeleted = false`。MySQL 不支持，SqlSugar 的 `CreateIndex` 不能带条件。
3. 不处理，软删除的行一直占着业务键。

#### 撞上唯一索引时

1. 维持原样：Provider 核对不到标识重复，数据库异常原样抛出，调用以 `KERNEL_UNEXPECTED_001` 结束。
2. 由各个存储（如 `MessageTranslationStore`）自己捕获。存储不认识各数据库驱动的异常；PostgreSQL 语句失败后事务已中止，存储也没法把工作单元标为只能回滚，处理器忽略失败返回成功时，对已中止事务的 `COMMIT` 会被静默回滚，调用方看到的成功是假的。
3. 在 Provider 里与"写入阶段才发现的标识重复"同样处理：写入失败后核对唯一索引，撞上即返回新的错误码，工作单元标为失败。

### 决策

声明取 4，命名取 3，SqlSugar 取 2，软删除取 1，撞上唯一索引取 3。

- `Persistence.Abstractions` 新增 `EntityIndexAttribute`（类上可多个；`params string[] properties`，`IsUnique`）、`EntityIndexes.Resolve(entityType, table)`（`MaxNameLength` = 63）与结果类型 `EntityIndex`。不叫 `IndexAttribute`：EF Core 有同名特性，两个命名空间同时引入时冲突。
- 名字：`IX_`（唯一 `UX_`）+ 表名 + 每列一段缩写（属性名每个词的前两个字符），下划线连接；表名里字母、数字、下划线以外的字符换成下划线；超过 63 个字符不截断，抛 `InvalidOperationException`。同一实体两个索引同名（不区分大小写，PostgreSQL 把不加引号的名字折成小写）或同列也是声明错误。
- 软删除：实体实现 `ISoftDeletable` 时，唯一索引末尾自动加 `IsDeleted`，名字仍按声明的列。`next/` 里此前没有约定，取 BasicApp 的写法。
- SqlSugar：`SqlSugarConventions.Apply` 在 `EntityNameService` 上挂 `ConfigureIndexes`（已有回调先执行，表名以它们改过的为准），全部升序。分表实体声明 `[EntityIndex]` 抛 `NotSupportedException`：SqlSugar 按分表改写索引名时就地改动缓存里的特性，名字随建表次数变化，分表实体用 `[SugarIndex]` 与 `{split_table}`。
- EF Core：`ApplyPersistenceConventions()` 映射为 `HasIndex(列).IsUnique(…).HasDatabaseName(名字)`，表名取调用时的 `GetTableName()`；Provider 因此引用 `Microsoft.EntityFrameworkCore.Relational`。从属类型与共享类型实体跳过。
- 内存实现不建索引、不校验唯一性。
- 唯一键重复 `PERSISTENCE_CONFLICT_003`（`PersistenceErrors.UniqueKeyConflict`，消息键 `persistence.entity.unique_key_conflict`，参数 `entity`、`index`）：关系型 Provider 的新增、更新与删除写入失败、又不是标识重复时，核对实体的唯一索引——这次写入里两项同键，或库里另一行（标识不同）同键；撞上就对这次写入的项统一报告，工作单元标为失败，提交回滚并返回同一错误。SqlSugar 另开不在事务里的连接（`CopyNew`）查已提交的行，EF Core 在 SaveChanges 回到的保存点之后于同一事务里查。核对不到的（大小写不敏感排序规则下只差大小写、键含空值、SqlSugar 上与本工作单元先前未提交的行冲突）异常照旧抛出。
- `MessageTranslationStore.UpsertAsync` 查已有的行改为键每 1000 个一批、每批按标识分页读完；同一键与区域再写一次是更新。

### 理由

- 中立声明让实体只依赖契约包：`[LongText]` 已经证明这条路可行，索引是同一类建表声明。两个 Provider 经同一个 `Resolve` 推出名字与列，不会各写各的。
- 63 个字符是三种主流库里最紧的上限；截断会让 SqlSugar 的"按名字查是否已有"失效，所以报错而不是截断。缩写规则固定、可推导，与 BasicApp 已有的名字风格一致。
- `EntityNameService` 这条路让 SqlSugar 自己的建索引流程（含按名字幂等）照常工作，应用自己调 `InitTables` 也生效；另调 `CreateIndex` 要重写这部分，还覆盖不全。
- 删除标记纳入唯一索引是 BasicApp 的现行做法，所有数据库都支持；部分索引更精确，但 MySQL 与 SqlSugar 的建索引入口都不支持。代价写进了规范：同一业务键最多一行已删除，第二次删除返回 `PERSISTENCE_CONFLICT_003`，而不是异常。
- 唯一索引兜住的是并发与疏漏，撞上时调用方需要能编程处理的结果。放在 Provider 里，才能在 PostgreSQL 的已中止事务上把工作单元标为只能回滚——与标识重复的处理同一套机制；存储层做不到这一点。
- 不加的索引同样有理由：审计 `Sequence` 不唯一——不同节点的序号只按时钟大致有序、可能相同，唯一索引会让撞号的整批审计写入失败、整批丢失；工作流全局定义的租户列是 NULL，PostgreSQL、SQLite、MySQL 的唯一索引不约束这些行，全局定义的版本号仍只靠目录按最大版本加一分配（改成非空哨兵要迁移存储格式，不在本次范围）；按主体查审计、按定义与状态列实例这类组合由应用按查询习惯自己加，触发器的 `AcquiredBy` 只在恢复时用，走 `State` 前缀即可。

### 影响

- 表结构：上表的索引在 SqlSugar `InitTables` 时建出（已有表补建，已有索引不动）；EF Core 应用在 `modelBuilder.Entity<T>()` 之后调用 `ApplyPersistenceConventions()` 即得到它们，不用再手写 `HasIndex`（原先按 README 手写的、名字不同的索引在迁移里会表现为重命名）。表里已有重复数据时唯一索引建不出来，`InitTables` 失败、启动失败——补建前先去重（翻译表每个键与区域留一行，授予表每个四元组留一行）。
- 行为：关系型 Provider 写入撞上唯一索引返回 `PERSISTENCE_CONFLICT_003`（HTTP 409），之前是异常（`KERNEL_UNEXPECTED_001`，HTTP 500）。`MessageTranslationStore` 与 `PermissionGrantRecordStore` 的并发写入同一业务键从"写出第二行"变为"后到的一批冲突、重试即更新或已存在"。
- 公开 API（均在 `PublicAPI.Unshipped.txt`）：`Persistence.Abstractions` 新增 `EntityIndexAttribute`、`EntityIndexes`、`EntityIndex`、`PersistenceErrors.UniqueKeyConflict`、`PersistenceMessages.UniqueKeyConflict`（10 种区域的译文）；`Persistence.SqlSugar` 新增 `SqlSugarConventions.ConfigureIndexes`。`SqlSugarConventions.Apply` 额外挂表服务回调：应用在 `Apply` 之后再整个替换 `EntityNameService` 会丢掉索引，要么先设回调再 `Apply`，要么在自己的回调里调用 `ConfigureIndexes`。
- 依赖：`Persistence.EntityFrameworkCore` 增加 `Microsoft.EntityFrameworkCore.Relational`。
- 测试：`EntityIndexesTests`（命名、缩写、软删除、声明错误、长度上限）；`SqlSugarIndexTests`（映射、SQLite 与 PostgreSQL 建出且再次建表不重复、唯一拒绝重复、软删除的唯一、分表不支持）；`SqlSugarUniqueKeyConflictTests`（同批同键、已有行同键——SQLite 与 PostgreSQL、改键、软删除第二次）；`EntityFrameworkCoreIndexTests` 与 `EntityFrameworkCoreUniqueKeyConflictTests`（模型、`EnsureCreated`、同样四种冲突）；各 `*.Database` 测试项目的索引清单测试；`MessageTranslationUpsertTests`（超过一页的已有行仍按更新——修正前 Expected 1500 / Actual 2000；并发新增同一键与区域返回 `PERSISTENCE_CONFLICT_003`、重试按更新）。

## 二、值类型实体 XHP004 由警告改为错误

### 背景

`Persistence.Generators` 扫描实现 `IEntity<TKey>` 的类型生成仓储登记。值类型（`struct`、`record struct`）实现 `IEntity<TKey>` 时报 `XHP004`，级别是警告，不生成登记。仓储与工作单元按引用跟踪实体（`IRepository<TEntity, TKey> where TEntity : class`），值类型永远进不了仓储：警告只是让项目照常编译通过，运行时那个"实体"一直没有登记，直到第一次解析仓储才发现。

### 备选

1. 维持警告。项目开了 `TreatWarningsAsErrors` 才会失败，否则问题延后到运行时。
2. 改为错误。

### 决策

取 2。`GeneratorRules.ValueTypeEntity` 的级别改为 `DiagnosticSeverity.Error`，标题改为 "Entity must be a class, not a value type"，消息不再说"不生成登记"；`AnalyzerReleases.Unshipped.md` 同步（规则尚未发布，直接改该行，不记 Changed Rules）。仍不为值类型生成登记。

### 理由

- 这不是风格问题：值类型实体在任何 Provider 下都不能用，没有"知道风险仍然继续"的合理场景，应当在编译期拦下，与同为"无法生成"的 `XHP001`、`XHP002` 一致。
- 只有 `XHP003`（过滤规约类与已有类型同名、仓储登记照常生成）仍是警告：那是可以接受的降级。

### 影响

- 行为：引用生成器的项目里有值类型实现 `IEntity<TKey>` 时编译失败（之前是警告）。框架与示例里没有这样的类型，全量构建不受影响。
- 测试：`EntityGeneratorTests.Records_AreRegistered_AndValueTypeEntities_AreReported` 断言 `XHP004` 逐个报告、级别为 Error，值类型不登记。
- 文档：生成器 README 与 docs-next「Persistence.Generators」页的诊断表。

> 修订（2026-11-01）：软删除实体的唯一索引由 ADR-0081 第二节改为只约束未删除行的部分唯一索引（`WHERE IsDeleted = false`，PostgreSQL / SQLite / SQL Server，其余数据库启动失败），不再把 `IsDeleted` 追加进列；同一业务键可以反复删除。EF Core 的入口改为 `ApplyPersistenceConventions(Database)`。
