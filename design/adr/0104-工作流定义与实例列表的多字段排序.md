# ADR-0104 工作流定义与实例列表的多字段排序

## 状态

已采纳（`spec/rfcs/0021-workflow.md`「列表排序」、两个存储契约与一致性一节、`spec/conventions/error-codes.md` 的 `WORKFLOW_VALIDATION_002` 一行随之修订）。修订 ADR-0102：单个排序字段 `SortBy` / `Descending` 换成有序的排序项列表 `Sorts`；ADR-0103 的状态生命周期顺序不变。

## 日期

2026-11-03

本 ADR 记录第十三批回灌（`q-batch-backlog.md`，用户定，经 BasicApp 设计会话转来）的一项决定：工作流定义查询与实例查询支持多字段排序。

## 背景

ADR-0102 给两个查询加了单个排序字段与方向，固定的次序键补成全序；BasicApp 的列表要能按住 Shift 点列追加次级排序。

## 备选

1. 保留 `SortBy` / `Descending` 作主排序，另加一个次级排序列表：两套写法表达同一件事，是双轨。
2. 有序的排序项列表取代单个字段（采纳）：列表的顺序就是优先级，不另设 `Priority`。
3. 一个用分隔符拼的字符串（如 `"status,-createdAt"`）：要自己解析，类型不安全，与白名单枚举不搭。

非法输入的处理另有选择：忽略不认识的字段与重复（静默兜底，调用方以为排了其实没排，不采用）；报校验错误（采纳）。

## 决策

取备选 2，直接改签名（还没发版，不留旧属性）。

- 新类型 `WorkflowDefinitionSort(WorkflowDefinitionSortField Field, bool Descending = false)`、`WorkflowInstanceSort(WorkflowInstanceSortField Field, bool Descending = false)`；`WorkflowDefinitionQuery.Sorts` / `WorkflowInstanceQuery.Sorts`（`IReadOnlyList<…>?`）取代 `SortBy` / `Descending`。第一项是主排序字段，后面依次是次级排序字段；字段白名单不变（ADR-0102），状态按生命周期（ADR-0103）。
- 空或没给：定义名字升序（次序键版本降序），实例创建时间降序——与原来的缺省相同。每项的方向缺省升序；原来实例查询的 `Descending` 缺省为真，现在要最新的在前写 `new(WorkflowInstanceSortField.CreatedAt, Descending: true)`。
- 次序键接在全部排序项之后，排序项里已有的字段跳过（SQL Server 不许同一列在 `ORDER BY` 里出现两次）：定义名字升序、版本降序、ID 升序；实例创建时间降序、写入先后降序、ID 降序，排序项里有创建时间时它不再作次序键、写入先后与 ID 随它的方向。
- 上限 `MaxSorts` 等于可排序字段数（定义 6、实例 5）：每个字段最多一次，界面上的排序链也不会超过可排序列数。
- 校验在 `IWorkflowDefinitionCatalog.QueryAsync` / `IWorkflowEngine.ListInstancesAsync` 里、进存储之前，按顺序报第一个：项数超过上限（新消息键 `workflow.definition.query_sorts_too_many` / `workflow.instance.query_sorts_too_many`，参数 `count`、`max`）；某项为空或字段不在白名单（`…query_sort_invalid`，参数 `sort`，沿用 ADR-0102 的键）；同一字段出现两次、不论方向（新消息键 `workflow.definition.query_sort_duplicate` / `workflow.instance.query_sort_duplicate`，参数 `sort`）。都是 `WORKFLOW_VALIDATION_002`（HTTP 400），10 种语言。`CountInstancesAsync` 不看排序、不校验。
- 存储（内存与数据库实现）按排序项依次排序；收到空项抛 `ArgumentException`、白名单以外的字段抛 `ArgumentOutOfRangeException`，重复的字段只按第一次出现的排（调用方已校验，这里不让一条坏查询打到库上），两个实现同一结果。
- 待办查询 `UserTaskQuery` 不动：它只按创建时间排、只有一个可排序的字段，已有的 `Descending` 足够表达；为形状统一把它改成单元素的列表没有收益，还要 BasicApp 白改一次。

## 理由

- 用户拍板；BasicApp 把表头的排序链逐项映射成枚举即可。
- 直接换签名而不保留 `SortBy` / `Descending`：两套写法并存时谁优先、能否混用都要额外约定，还没发版，正是去掉的时候。
- 非法输入报错而不是忽略：字段与重复都是调用方能改正的输入，忽略会让排序结果和调用方以为的不同而没有任何提示。

## 影响

- 公开 API（Workflow.Abstractions，Unshipped）：删除 `WorkflowDefinitionQuery.SortBy` / `Descending`、`WorkflowInstanceQuery.SortBy` / `Descending`；新增 `WorkflowDefinitionQuery.Sorts`、`MaxSorts`（6），`WorkflowInstanceQuery.Sorts`、`MaxSorts`（5），类型 `WorkflowDefinitionSort`、`WorkflowInstanceSort`，消息键常量 `WorkflowMessages.DefinitionQuerySortDuplicate`、`DefinitionQuerySortsTooMany`、`InstanceQuerySortDuplicate`、`InstanceQuerySortsTooMany`。Workflow.Conformance 新增用例方法两个。没有表结构、配置键、启动失败条件的变化。
- 行为：缺省排序不变；单字段的调用照「旧 → 新」改写后结果不变（实例查询原来只给 `SortBy` 时是降序，要写出 `Descending: true`）。
- 测试：存储用例 14（定义：状态 + 创建时间升降两种、标题 + 版本、三项升降混合、标题 + 名字、显式名字 + 版本、空列表、分页、与过滤同时）、15（实例：状态 + 创建时间、定义名 + 标题、三项升降混合、定义名 + 创建时间、同刻创建由第二项决定、空列表、分页、计数不看排序）；引擎用例 36 加上越界、空项、重复、检查顺序、全部字段各一次、空列表；原有单字段用例改用排序项。修改验证：内存实现只按第一项排时存储用例 14 失败；数据库实现写入先后不随创建时间的方向时存储用例 13、15 失败。
