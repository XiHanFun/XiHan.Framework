# ADR-0088 截止时间超时归因的行为变化与插件中间件随卸载撤回

## 状态

已采纳（`spec/rfcs/0004-pipeline-stages.md`、`spec/rfcs/0003-invocation-context.md`、`spec/rfcs/0018-wasm-plugins.md`、`spec/conventions/error-codes.md` 与 `spec/plugin/` 的 `wasm.md`、`invocation.md`、`lifecycle.md` 随之修订）。修订 ADR-0085：第三节「Wasm 插件贡献的中间件不随卸载撤回、卸载后失败即关闭、运行期不能加载这类插件」改为随卸载按归属撤回、可在运行期加载；第五节的 `DeadlineMiddleware` 归因保留，补写为行为变化。

## 日期

2026-11-01

本 ADR 记录第五批回灌里宿主分区的两项决定（`i-batch-backlog.md` 第 1、4 条，来由是 ADR-0085 留下的待定项），每项一节。

## 一、截止时间到了而调用方没有取消，一律报超时（第 1 条）

### 背景

ADR-0085 第五节在修插件截止时间用例时顺带改了内核：截止令牌由 `DeadlineMiddleware` 按宿主 `TimeProvider` 落成的定时取消触发；下游把取消写成结果的路径——进程外插件运行时接住 gRPC 的 `Cancelled`、Wasm 宿主函数与运行时、自己接住取消的操作或 Provider——各自按 `context.IsExpired(clock.GetUtcNow())` 判断是超时还是取消。定时器按系统节拍触发，可能早于时钟读数到达截止时间，几毫秒的差让下游判断为「没过期」，写下 `KERNEL_CANCELLED_001`；中间件原来只翻译抛出的取消，写成结果的原样留下，同一个超时偶发报成取消（改动期间复现两次）。修法是 `DeadlineMiddleware` 在下游正常返回、结果是 `KERNEL_CANCELLED_001`、截止令牌已触发而外部令牌没有时改写为 `KERNEL_TIMEOUT_001`。这一改动当时只在 RFC-0004 里顺带一句，没有作为行为变化写清，是否保留留作待定。

### 备选

1. 保留，写成行为变化（采纳）。
2. 回退内核改动，只保留用例改写：生产路径照旧偶发把超时报成取消，调用方拿到的状态码取决于定时器与时钟谁先到，不可预测。
3. 让每个下游自己归因（比如给 `IsExpired` 加容差）：容差多大都只是缩小窗口；下游拿到的只是一个链接令牌，分不清是哪个源触发的，只有落下定时取消的中间件知道。

### 决策

- 保留 `DeadlineMiddleware` 的归因：截止令牌已触发、调用方的取消令牌没有触发时，下游写下的 `KERNEL_CANCELLED_001` 结果改写为 `KERNEL_TIMEOUT_001`。下游抛出的取消照旧：截止令牌已触发即超时（与外部取消同时触发时超时优先）。
- RFC-0004 在「Resilience 阶段」末尾新增「行为变化」小节（背景、旧行为、新行为、对调用方的影响、不变的部分），RFC-0003 第 1 条与 `conventions/error-codes.md` 的 `KERNEL_TIMEOUT_001` / `KERNEL_CANCELLED_001` 说明同步。ADR-0085 文末加一行指向本节。
- docs 韧性指南「截止时间」一节加行为变化提示与新旧对照表，错误码页、插件指南的映射表与 Kernel 包页、Kernel README 同步。

### 理由

- 「截止时间到了」是调用方给定的事实，应当得到确定的回答；以前同样的超时有时 504、有时 408，按状态码决定重试的客户端无法据此行事。
- 归因放在知道令牌来源的唯一位置；下游不再需要、也不应该自己用时钟判断。

### 影响

- 状态码与错误码：截止时间到了、调用方没有取消、下游把取消写成结果的调用，由偶发的 `KERNEL_CANCELLED_001`（HTTP 408、gRPC `Cancelled`、命令行退出码 8）一律变为 `KERNEL_TIMEOUT_001`（HTTP 504、gRPC `DeadlineExceeded`、命令行退出码 7）；Problem Details 的 `type` 随之变化。Observe 阶段的审计记录、追踪与访问日志看到的是改写后的超时。
- 重试判断：调用方按超时处理——截止时间已用尽，被调方可能已经完成副作用，非幂等操作重试前带幂等键（Baggage `xihan.idempotency-key`）；以前按 408 判断「调用方放弃」的重试策略要改看 504。调用方自己取消（连接断开、取消令牌）仍是 `KERNEL_CANCELLED_001`。
- 不变：熔断计数（`ResilienceMiddleware` 在 `DeadlineMiddleware` 之内，看到的是下游写下的原结果）；截止令牌与外部令牌同时触发、下游写下取消结果时保持取消（调用方已经取消，回答给谁都不重要），与抛出路径的「超时优先」不同，写进 RFC-0004。
- 没有新错误码、消息键与公开 API；内核代码与用例在 ADR-0085 第五节的提交里，本节只补规范与文档。

## 二、插件贡献的中间件随卸载按归属撤回，再加载后回来（第 4 条）

### 背景

ADR-0085 第三节让插件卸载按归属撤回代理操作与权限码，但 Wasm 插件贡献的中间件不在其中：中间件在配置阶段插进管道，管道委托第一次调用时构建一次、之后不再变；卸载后中间件仍在管道里，取不到插件实例，经过它所在阶段的全部调用都以 `PLUGINS_UNAVAILABLE_001` 失败（失败即关闭）；运行期又拒绝加载贡献中间件的插件（`PLUGINS_VALIDATION_005`），整条管道只能靠重启宿主恢复。用例 `Unload_OfAPluginContributingMiddleware_LeavesTheMiddlewareFailingClosed` 把这一状态锁住了。用户定：卸载时一并把中间件撤出管道，补用例锁住「卸载后经过管道的调用不失败、再加载后中间件回来」。

### 备选

1. 内核管道支持按归属成组登记与撤回、按版本构建委托；插件宿主在加载与卸载时调用（采纳）。
2. 中间件留在管道里，插件卸载后改为直接放行：管道打印里仍有它，换版本时新清单的中间件名、阶段、约束可能都不同，旧的占位对不上；运行期仍然不能加载新的贡献中间件的插件。
3. 卸载贡献中间件的插件直接拒绝：不再关掉整条管道，但插件换不了版本，与「再加载后中间件回来」的要求相反。

### 决策

内核（`PipelineBuilder`，Stable，都在 Unshipped，新增成员）：

- `UseOwned(string owner, Action<PipelineBuilder> configure)`：在构建器的锁里执行回调，一次登记同一归属的一组中间件与它们的次序约束；回调返回后立即排一次整条管道，约束目标未登记、有歧义、跨阶段（`KERNEL_PIPELINE_003`）或成环（`KERNEL_PIPELINE_001`）时整组撤掉、抛出，管道不变。组内的登记归属都必须是 `owner`，约束只能挂在组内的中间件上（目标可以在组外），否则 `KERNEL_PIPELINE_003`——这样撤回的恰好是这一组。不能嵌套，组内不能撤回。
- `RemoveOwnedBy(string owner) -> int`：一次撤回该归属的全部中间件（连同挂在上面的约束），立即核对剩下的管道；别的归属的中间件以约束引用了被撤回的中间件时什么都不撤、抛出 `KERNEL_PIPELINE_003`。没有该归属的登记时返回 0。
- 应用构建之后（`AppBuilder.Build` 把按类型登记的中间件补登记进容器之后）只能经这两个入口改动管道：单项的 `Use*`、`Before` / `After` 不立即核对，构建之后这样改会让下一次调用在构建管道时才失败，一律 `KERNEL_PIPELINE_003`；组内也只能按实例登记，按类型登记的进不了已建好的容器，同样 `KERNEL_PIPELINE_003`。配置阶段的行为不变（目标仍在构建或打印管道时解析）。
- 管道按版本构建：构建器每次改动版本前进；`App.Pipeline` 在版本没变时复用委托（无锁读），改动后的第一次访问在锁里重建，并发访问只重建一次。每次调用进入管道时取一次委托：已经取到委托的调用按取到时的管道走完，改动返回之后开始的调用一定经过改动后的管道。注册序号改为单调递增，撤回后再登记的中间件按排序规则回到原来的位置。构建器全部成员线程安全。

Wasm 插件宿主：

- 运行期 `LoadAsync` 不再拒绝贡献中间件的插件。登记顺序：先代理操作与权限码（`OperationRegistry.AddRange`），再中间件（`UseOwned`，归属是清单 ID）；中间件进不去时撤回刚登记的操作与权限码（撤回不会失败，回滚总能完成），返回内核的错误。两步与「运行时仍是宿主当前运行时」的核对在同一把登记锁里，与卸载互斥。
- `UnloadAsync`：在加载卸载锁与登记锁里先撤中间件（`RemoveOwnedBy`，可能因被引用而失败，这时什么都不改、插件照常服务、返回 `KERNEL_PIPELINE_003`），再把运行时移出宿主、撤回代理操作与权限码；然后停止插件，等撤回之前进入的调用离开运行时，再释放。
- 配置阶段发现的插件仍直接登记（不经 `UseOwned`），约束目标可以是之后才发现的插件的中间件，在构建管道时解析；卸载时同样按归属撤回。
- 在途调用：撤回之前已经进入管道的调用仍经过插件的中间件——插件停止之前照常执行钩子，停止之后钩子以 `PLUGINS_UNAVAILABLE_001` 失败即关闭（before 不进入下游；after 在下游成功时把结果改为失败）。撤回之后开始的调用不再经过它，经过它原来所在阶段的调用照常进入下游。
- 运行时补了两处在途调用与卸载交错的竞态（并发卸载用例以约五千次调用里一次 `KERNEL_UNEXPECTED_001` 暴露）：取实例改为只读一次（先判在服务再读第二次可能拿到空，而调用锁里核对「仍是同一个实例」时空对空会被当成同一个）；运行时记进行中的调用数，停止之后新进来的调用直接按不可用返回，释放前等已进来的调用离开（`DrainAsync`），不再让它们撞上已释放的锁。代理操作的在途调用同样受益。
- `PLUGINS_VALIDATION_005` 不再包括「运行期加载含中间件贡献的插件」。

进程外与进程内插件：核对过，都不能贡献中间件——RFC-0017 规定进程外插件不可贡献中间件，进程外宿主不读清单的 `contributes.pipeline`；进程内宿主给插件的 `PluginContext.Pipeline` 恒为空。没有要撤回的中间件，不改。

### 理由

- 与 ADR-0085 同一思路：中间件早就按清单 ID 记归属，按归属撤回是一次按键的批量删除；把它做成内核的通用能力，插件宿主只是调用方。
- 立即核对而不是留到构建时：运行期没有「之后构建管道时再报」的机会——留到下一次调用才失败，就是把整条管道关掉。
- 一组一个归属、约束只挂在组内：保证撤回与登记互为逆操作，撤回不会漏掉挂在组外的约束，也不会误撤别人的。
- 撤回被引用的中间件时拒绝而不是连带放宽约束：放宽等于静默改变别的中间件声明过的次序；拒绝让运维先处理引用方。
- 按版本构建、每次调用取一次委托：热路径只多一次版本比较；在途调用的语义与代理操作的撤回一致（已经查到的照常走完或以不可用结束），不需要为了撤回去追踪、等待正在执行的管道。
- 构建之后封住单项改动：否则一次不经核对的改动就会让下一次调用在构建管道时抛出，比原来的失败即关闭更糟。

### 影响

- 公开 API：新增 `PipelineBuilder.UseOwned`、`PipelineBuilder.RemoveOwnedBy`；`App.Pipeline` 的含义从「首次访问构建、之后不变」变为「当前版本的委托」（签名不变）。没有改签名、删成员。
- 新的失败条件（运行期，不是启动期）：应用构建之后直接调用 `PipelineBuilder` 的 `Use*` / `Before` / `After`，以前在第一次调用之前生效、之后静默无效，现在抛出 `KERNEL_PIPELINE_003`；仓库与 BasicApp 都没有这样用的。
- 行为：贡献中间件的 Wasm 插件卸载后，经过它原来所在阶段的调用由 `PLUGINS_UNAVAILABLE_001` 失败变为照常进入下游；运行期 `LoadAsync` 这类插件由 `PLUGINS_VALIDATION_005` 变为正常加载（次序约束不成立时 `KERNEL_PIPELINE_003` / `KERNEL_PIPELINE_001`）；卸载被别的中间件以次序约束引用了的插件返回 `KERNEL_PIPELINE_003`。
- 没有新错误码与消息键（`KERNEL_PIPELINE_003` 的说明扩充）。没有配置键与表结构变化。
- 测试：内核按归属撤回并成组再登记回到原位、成组登记约束不成立（目标缺失、成环）时整组还原且名字可再用、混归属与组外约束与嵌套被拒、撤回会留下悬空约束时被拒且不变、撤回之后开始的调用不经过中间件而在途调用经过它走完、构建之后只接受成组的按实例改动；Wasm 卸载后经过 observe 阶段的调用不失败、插件操作未登记、再加载后中间件回到原位并拦截，八个调用方经过插件中间件时并发卸载（卸载完成之前开始的调用只以成功或 `PLUGINS_UNAVAILABLE_001` 结束、之后开始的全部成功，之后再加载中间件回来），宿主中间件以次序约束引用插件中间件时卸载被拒且什么都不变，运行期加载贡献中间件的插件（约束目标缺失时 `KERNEL_PIPELINE_003`、操作与中间件都不留下；正常时中间件生效）。原用例 `Unload_OfAPluginContributingMiddleware_LeavesTheMiddlewareFailingClosed` 与 `LoadAsync_AtRuntime_RejectsMiddlewareContributions` 改写。

第一节「截止令牌与外部令牌同时触发、下游写下取消结果时保持取消」由 ADR-0092 第二节修订：两条路径同一规则，截止令牌已触发即超时，不论外部令牌是否也已触发；进程外与 Wasm 插件运行时不再按时钟改报超时。第二节末段「进程外宿主不读清单的 `contributes.pipeline`、进程内宿主给插件的 `PluginContext.Pipeline` 恒为空，不改」由 ADR-0092 第一节修订：清单写了 `contributes.pipeline` 的进程外插件在发现时被拒、进程内插件加载被拒（`PLUGINS_VALIDATION_001`），不再静默忽略。
