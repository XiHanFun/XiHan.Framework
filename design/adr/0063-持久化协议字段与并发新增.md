# ADR-0063 持久化协议字段、并发新增与雪花标识的不可用结果

## 状态

已采纳（`spec/rfcs/0005-persistence.md` 2026-11-01 修订，`spec/conventions/error-codes.md` 补充说明，不新增错误码）。

## 日期

2026-11-01

## 背景

docs-next 文档站按代码核对持久化时发现五处与 RFC-0005 / ADR-0033 不符的行为：

1. 更新传入游离实例会覆盖 `TenantId` 与 `CreatedAt`，行可以借更新改到别的租户。`PersistenceConventions.ApplyOnUpdate` 只写修改时间与并发戳；EF Core 用 `SetValues` 把游离实例的全部标量复制到跟踪实例；SqlSugar 把调用方实例整行写入；内存实现直接存调用方实例。读出后改了 `TenantId` 再更新也一样。RFC 只写了「新增时写入」，没写更新时怎么办。
2. 两个工作单元先后新增同一标识（检查时对方尚未提交），RFC 与 `IUnitOfWork` 注释承诺返回 `PERSISTENCE_CONFLICT_002`。实际 EF Core 与 SqlSugar 让数据库的主键冲突异常逃出，调用以 `KERNEL_UNEXPECTED_001` 结束；内存实现提交时同键覆盖，后提交的静默盖掉先提交的。
3. 内存实现查询返回表里的对象本身。在读出的实例上的修改，包括仓储写入的修改时间、并发戳与软删除标记，立即对其他工作单元可见，回滚也撤销不了，违反「提交前对其他工作单元不可见」。
4. 雪花标识没有机器位或时钟回拨超过阈值时，ADR-0033 与包 README 说协议适配器映射为 503。实际异常由 Observe 阶段包成 `KERNEL_UNEXPECTED_001`，HTTP 是 500。
5. `SnowflakeIdFeature` 没有声明依赖 `caching.distributed`，启停顺序只取决于 `UseFeature` 的先后。缓存 Provider 写在后面时先于雪花特性停止，释放机器位租约失败；Redis 这类启动后才连得上的 Provider 写在后面时，雪花特性启动就取不到租约。

## 备选

1. 更新时调用方给的租户与存储不同：（a）沿用存储值、调用方的值不生效；（b）返回校验错误拒绝更新。
2. 关系型 Provider 怎样把主键冲突识别成标识重复：（a）按驱动的错误码（PostgreSQL `23505`、SQLite 19 / 1555、MySQL 1062……）；（b）数据库报错后核对这些标识的行是否已存在。
3. 核对放在哪里：（a）同一事务；（b）另开连接。
4. 写入阶段才发现的标识重复之后，工作单元能否继续：（a）能，处理器自己决定；（b）只能回滚。
5. 内存实现的隔离：（a）浅复制（字段逐一复制）；（b）深复制（序列化往返，或按属性新建实例）；（c）保持存引用，只在文档里写明。
6. 内存实现提交时校验什么：（a）只校验新增的标识；（b）每个写过的标识都按首次读到的已提交状态校验，跨表原子。
7. 雪花标识不可用怎样变成 503：（a）内核 Observe 阶段把 KIND 为 UNAVAILABLE 的 `FrameworkException` 一律转为同码结果；（b）协议适配器看 `KERNEL_UNEXPECTED_001` 的内层错误决定状态码；（c）`SnowflakeIdFeature` 自己登记中间件，只转本特性的两个错误码。
8. 中间件放在哪个阶段：（a）Transaction；（b）Resilience 末尾；（c）Observe 末尾。
9. 启停顺序怎样保证：（a）清单声明必需依赖 `caching.distributed@1`；（b）声明可选依赖；（c）文档要求应用按顺序 `UseFeature`。

## 决策

采用 1a、2b、3 按 Provider 区分（EF Core 3a、SqlSugar 3b）、4b、5a、6b、7c、8b、9b。

- `PersistenceConventions` 新增 `ApplyOnUpdate(entity, stored, now)`：把存储行的创建时间、租户与删除标记写回调用方实例，再写修改时间、刷新并发戳。内存实现与 SqlSugar 的更新改用它。软删除在存储行（或其副本）上打标，删除标记再同步回调用方实例。
- EF Core 跟踪实例可能就是调用方改过的那个，所以不用存储行重载，而是：
  - 更新与删除把创建时间、租户与删除标记恢复为原值（`OriginalValues`）。
  - 写入路径的可见性按原值判定，否则读出后改了租户的实例会被判成不存在。
  - 保存成功后把创建时间与租户也复制回游离实例。
  - 提交时保存的残余变更（绕过仓储直接改跟踪实体）同样恢复创建时间与租户。
- EF Core 新增：`SaveChanges` 抛出 `DbUpdateException`（非并发）时，它已回到自动建的保存点，事务可用。把这次新增的实体移出跟踪，在同一事务里不跟踪地查这些标识；有已存在的就返回标识重复（`id` 是按入参顺序第一个撞上的），否则原样抛出。
- SqlSugar 新增：插入抛出 `DbException` 时，另开一个不在事务里的连接（`CopyNew`，同一份连接配置）查这些标识，规则同上。PostgreSQL 系语句失败后整个事务进入中止状态，不能在原事务里再查。
- 两个关系型工作单元各加内部的 `Fail(Error)`：写入阶段发现标识重复后记下错误，提交时只回滚并返回它。PostgreSQL 对已中止的事务执行 `COMMIT` 会静默回滚，不拦住的话处理器忽略失败、返回成功时，调用方看到的是假的成功。
- 批量新增写入阶段撞上同一标识时，这次写入的项统一返回标识重复，与「写入阶段的失败对这些项统一报告」一致。
- 内存实现：
  - 新增内部的 `EntityCopy`，经 `UnsafeAccessor` 调 `object.MemberwiseClone`。表与覆盖层只存副本，查找、`FindManyAsync`、查询只交出副本；过滤、排序、分页在表自己的对象上做，只复制最终交出的那一页。
  - `InMemoryTable.Find` / `Snapshot` 也交出副本。
- 内存实现的提交：
  - 覆盖层记下每个写过的标识首次读到的已提交状态（当时有没有行、行上的并发戳）。
  - 提交按建表先后给涉及的表依次加锁，在全部锁内逐表校验：新增的标识已有行 → `PERSISTENCE_CONFLICT_002`；更新或删除的行已不在 → `PERSISTENCE_CONFLICT_001`；带戳的行戳已变 → `PERSISTENCE_CONFLICT_001`；之后才是容量。全部通过才逐表应用，跨表原子。
  - `PendingChanges`、`IPendingChanges`、`InMemoryUnitOfWork.Changes`、`InMemoryTable.Apply` 改为内部类型 / 成员，只为仓储与工作单元服务。
- 雪花标识：
  - `SnowflakeIdFeature` 登记内部的 `SnowflakeUnavailableMiddleware`，在 Resilience 阶段末尾。
  - 它只捕获携带 `PERSISTENCE_UNAVAILABLE_004` / `005` 的 `FrameworkException`，记一条警告，把结果设为同码的 `Error.Unavailable`，消息键为新增的 `persistence.snowflake.clock_moved_backwards` 与已有的 `persistence.snowflake.worker_unavailable`，十种区域。
  - 清单的 `contributes.pipeline` 登记它。
- 清单 `requires` 增加 `caching.distributed@1?`。能力图谱据此把缓存 Provider 排在前面：先启动、后停止，与 `UseFeature` 的先后无关。启动失败时提示改为「装配一个 `caching.distributed` Provider」，不再要求写在前面。

## 理由

- 沿用存储值（1a）：新增时调用方的 `TenantId` 本来就被当前租户覆盖，更新沿用存储值与之一致。修改时间与并发戳也一直由 Provider 写，协议字段整组只由 Provider 写，规则最简单。拒绝（1b）会让「按 DTO 构造实例再更新」这类常见写法因为没填 `TenantId` / `CreatedAt` 而失败，却不带来额外的安全性。
- 核对而不是看错误码（2b）：
  - 错误码各驱动不同，Provider 不引用驱动包就拿不到。
  - 同一个 `23505` 也可能是别的唯一索引冲突，BasicApp 的软删除唯一索引就是例子。按标识重复报告会误导调用方。
  - 核对这些标识是否已有行，只把真正的主键冲突转成标识重复，别的约束冲突照旧是异常。
- 两个 Provider 的核对位置不同（3）：
  - EF Core 在已有事务里 `SaveChanges` 会自动建保存点，失败后事务仍可用，同一事务的读已提交能看到对方已提交的行。
  - SqlSugar 没有保存点，PostgreSQL 的事务已中止，只能另开连接。对方的插入只有在提交之后才会让本方失败，所以另开连接一定看得到它。
- 只能回滚（4b）：PostgreSQL 系的事务已中止，继续写入只会再抛异常。三个 Provider 取同一语义：内存实现本来就在提交时失败。
- 浅复制（5a）：
  - 深复制要么走反射序列化，正式包开着 AOT 分析，会有裁剪警告；要么按属性新建实例，`TEntity` 要加 `DynamicallyAccessedMembers`，会一路传到 Stable 的 `IRepositoryRegistrar` 与 `AddRepository`。
  - 私有 setter、构造函数参数也会丢数据。
  - `MemberwiseClone` 原样复制全部字段，经 `UnsafeAccessor` 调用不用反射。缺陷报告里的修改时间、并发戳、删除标记与业务标量都是值字段，浅复制已经隔离。
  - 集合与领域事件缓冲仍共享，写进 RFC 与文档；内存实现只用于开发与测试。
- 提交时全面校验（6b）：同键覆盖是并发新增与丢失更新的同一个根因，只补新增会留下「后提交的更新盖掉先提交的更新或删除」。关系型 Provider 靠行锁与并发令牌已经不会这样。校验既然能失败，就必须跨表原子，否则多表的工作单元会只提交一半。
- 特性自己转换（7c）：
  - 7a 改变内核对所有异常的约定（RFC-0004 / 0011 / 0015 都写着异常记 `KERNEL_UNEXPECTED_001`）。`PERSISTENCE_UNAVAILABLE_001` 这类装配错误会变成 503，审计记录的错误码也会与响应不一致。
  - 7b 让响应体的 `code` 是 UNEXPECTED、状态码却是 503。
  - 「`NewId()` 只能抛异常」是雪花特性自己的约束，由它把异常转回结果最贴切。
- Resilience 末尾（8b）：
  - 幂等中间件缓存所有结果、只在异常时清除标记。转换放在 Transaction 阶段，可重试的 503 会被幂等记录下来，同一幂等键重试只能回放失败。
  - 放在幂等之外，异常经过时标记已清除、工作单元已回滚。
  - Observe 末尾与审计中间件同阶段，先后只能靠清单 ID 的字典序，RFC-0004 第 8 条不允许依赖它；Resilience 末尾与内核的截止时间、熔断中间件（阶段开头）次序确定。
- 可选依赖（9b）：
  - 必需依赖会让「固定机器位、不装缓存」的应用启动失败。
  - 可选依赖只在提供者存在时建边，排序正确。
  - 代价是固定机器位又没有任何 `caching.distributed` Provider 时，按 RFC-0002 特性进入 Degraded。SqlSugar、EF Core 对 `multitenancy.sharding@1?` 的可选依赖已是同样的先例。Standard / Full Profile 都带内存缓存，不受影响。

## 影响

- 公开 API：
  - `Persistence.Abstractions` 新增 `PersistenceConventions.ApplyOnUpdate(entity, stored, now)` 与 `PersistenceMessages.ClockMovedBackwards`。
  - `Persistence.InMemory` 移除 `InMemoryTable.Apply`、`InMemoryUnitOfWork.Changes`、`PendingChanges`、`IPendingChanges` 共 13 个未发布符号。
  - `Persistence.Conformance` 新增 4 个用例方法。
- 行为：
  - 更新再也改不了创建时间、租户与删除标记。依赖「更新时顺手改 `TenantId`」的代码会发现改动不生效，要搬租户只能删除后重建。
  - 内存实现读出的是副本：读出后改了却不调用 `UpdateAsync` 的写法，在内存实现上不再落库。这与 SqlSugar 一致；EF Core 的残余变更在提交时仍会保存。
  - 内存实现并发提交同一标识或同一行时，后提交者失败。
  - 雪花标识不可用时，管道里的调用得到 503。
  - 固定机器位又没有缓存 Provider 的应用里，雪花特性是 Degraded。
- 测试：
  - 一致性套件新增 4 个用例，三个 Provider 继承：更新与删除沿用存储的创建时间与删除标记；更新沿用存储的租户；两个工作单元先后新增同一标识；回滚不留痕迹。修复前内存实现 4 个、EF Core 与 SqlSugar（SQLite）各 2 个失败。并发新增在 SQLite 上本来就通过（单写者，后到者等先到者提交后再核对），PostgreSQL 上的写入阶段冲突只在 CI 的 `XIHAN_TEST_POSTGRES` 下验证。
  - EF Core 用 `SaveChangesInterceptor` 在同一事务里抢先插入同一标识，SqlSugar 用 `OnExecutingChangeSql` 让新增前的核对查不到已提交的行，在 SQLite 上走通写入阶段的标识重复与「提交只回滚」。
  - EF Core 另测残余变更不改创建时间。
  - 内存实现另测：读写都复制、提交时的标识重复、并发戳变化与行被删时的冲突、跨表原子。
  - 雪花特性另测：缓存 Provider 写在后面也先启后停、没有机器位与时钟回拨在调用里是 UNAVAILABLE 结果、别的框架异常仍是 `KERNEL_UNEXPECTED_001`、固定机器位无缓存时 Degraded。
