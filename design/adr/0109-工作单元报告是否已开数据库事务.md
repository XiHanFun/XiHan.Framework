# ADR-0109 工作单元报告是否已开数据库事务

## 状态

已采纳。`spec/rfcs/0005-persistence.md`「工作单元」新增「是否已开数据库事务」一节，「一致性」随之修订。

## 日期

2026-11-04

本 ADR 记录第二十三批回灌（`ab-batch-backlog.md` 第 1 条 D10-A，用户定）的决定。

## 背景

BasicApp N4（AI）第三批的回复操作要先把助手的增量流式推送给客户端，最后再把整条回复写库。推送走 Realtime 的 `IRealtimePush.SendNowAsync`：立即发出、不随回滚撤回，所以只能在事务之外调用。

它现在的守卫是「工作单元 `State == Active` 即抛」：

```csharp
if (services.GetService<IUnitOfWork>() is { State: UnitOfWorkState.Active })
{
    throw new InvalidOperationException(...);
}
```

回复操作是写操作，Transaction 阶段给它开的是可写工作单元，调用一开始就是 `Active`，于是一推送就抛，做不到「先推送、后写库」。

但这时其实还没有数据库事务。三个 Provider 都延迟开启事务（RFC-0005「工作单元」，只读过数据的调用不开事务，好让 SQLite 这类单写者数据库上读写调用并存）：

| Provider | 事务何时开启 | 何时结束 | 修改前怎样记 |
| --- | --- | --- | --- |
| SqlSugar | 第一次 `EnsureTransactionAsync`（仓储每次写入前都调用它，直接用客户端写入前应用也要调用）：未绑定连接时经 `AsTenant().BeginTranAsync()` 在默认连接与已取用的连接上开，此后首次取用的连接由 SqlSugar 补开；绑定命名连接时只在那个连接上 `Ado.BeginTranAsync()` | 提交逐连接提交、回滚逐连接回滚、作用域释放时回滚 | 私有字段 `_transactionOpen`，提交 / 回滚 / 释放时复位 |
| EF Core | 第一次 `EnsureTransactionAsync`（仓储每次写入前、提交时保存残余跟踪变更前）：`Database.BeginTransactionAsync` | 提交、回滚、作用域释放 | 私有字段 `_transaction`，提交与回滚后不复位，作用域释放时才释放并置空 |
| 内存 | 没有数据库事务；写入进覆盖层 | 提交时校验后应用，回滚丢弃覆盖层 | 没有记 |

只读工作单元三个都不开事务：仓储写入在开事务之前就拒绝，`EnsureTransactionAsync` 抛出携带 `PERSISTENCE_UNEXPECTED_001` 的异常。

所以「开没开事务」只有 Provider 自己知道，契约上没有，BasicApp 只能退而用 `State`。

## 备选

1. **维持现状，BasicApp 用 `State`**：回复操作做不到先推送后写库，要拆成两个调用（推送一个、写库一个），回复的流式与落库不在一次调用里，失败时的补偿要 BasicApp 自己做。否决。
2. **BasicApp 按 Provider 类型转换后读实现的状态**：`IUnitOfWork` 是抽象，BasicApp 要认 SqlSugar 的具体类型、还要读私有字段；内存实现无从判断。否决。
3. **只在关系型 Provider 的实现类上加属性**：应用要按 Provider 分支；只装内存实现的测试拿不到它。否决。
4. **暴露事务对象或连接**：把 Provider 的细节（`IDbContextTransaction`、SqlSugar 的 `ITenant`）带进抽象，应用只需要一个是非。否决。
5. **「曾经开过事务」**（提交后仍为真）：管道外的代码提交之后再推送是正确用法，提交后仍为真会误拦；名字说的也是此刻。否决。
6. **「已有成功的写入」**（结果失败的写入不算）：关系型 Provider 在核对之前就开了事务，失败的写入发生时事务已经开着（PostgreSQL 上撞了主键的事务已中止），而且同一工作单元里可能已有别的写入；按写入调用算，三个实现在同一个时机变真，可以用一致性用例核对。否决。
7. **内存实现恒为假**：它没有数据库事务，字面上说得通。但守卫要判断的是「本工作单元有没有尚未提交、可能随回滚消失的写入」：内存实现写入之后覆盖层里正是这种变更。恒为假会让只装内存实现的测试放过「写过之后立即推送」的误用，到真实库上才抛。否决。
8. **`IUnitOfWork.HasTransaction`，三个实现按同一时机报告**：采纳。

## 决策

1. **契约**：`IUnitOfWork` 新增只读属性 `bool HasTransaction`，报告本工作单元此刻是否开着数据库事务。
2. **开启时机**：可写工作单元里第一次写入。
   - 仓储的 `AddAsync` / `UpdateAsync` / `RemoveAsync`，或集合非空的 `AddRangeAsync` / `UpdateRangeAsync` / `RemoveRangeAsync`，一经调用即开启，不论这次写入的结果（标识重复、不存在、并发冲突、租户不符都已开启）。
   - EF Core 与 SqlSugar 的直接写入入口 `EnsureTransactionAsync` 同样开启；EF Core 提交时保存残余跟踪变更之前也经它开启。
   - 查找、按标识集合查找、查询、计数、空集合的批量方法不开启；不经仓储、也不经 `EnsureTransactionAsync` 直接对客户端执行的写入不在事务里（各自自动提交），也不让它变真。
3. **取值**：
   - `NotStarted` 为假；`Active` 里开启前为假，开启后为真，再写入不重开、仍为真。
   - 提交（成功或返回失败）与回滚之后为假，`Committed` / `RolledBack` 恒为假。
   - 提交或回滚本身抛出异常时工作单元停在 `Active`，此时的值不作规定；作用域释放时 Provider 回滚未结束的事务。
4. **只读工作单元恒为假**：被拒绝的写入与抛出的 `EnsureTransactionAsync` 都不开事务。
5. **多连接**：一个工作单元一个值。SqlSugar 首次写入落在哪个连接都经同一个入口开事务，任一连接上开着即为真；EF Core 一个 `DbContext` 一个连接。
6. **绑定连接的工作单元**：只报告绑定的那个连接（RFC-0005「命名连接」）。不同服务作用域的工作单元各报各的：业务调用里另开作用域、绑定命名连接的工作单元写入并提交，不让业务调用的工作单元变真；业务调用开着事务，另开的工作单元开始时仍为假。
7. **内存实现**：可写工作单元里第一次写入调用（时机同 2）起为真，直到提交（含提交时校验失败、写入阶段记下的失败）或回滚。
8. **实现**：
   - SqlSugar：私有的 `_transactionOpen` 改为公开只读的 `HasTransaction`，还是同一个值。
   - EF Core：`HasTransaction => _transaction is not null`；提交成功、回滚成功之后立即释放并摘下事务对象（此前留到作用域释放时）。
   - 内存：仓储的写入关口（原 `RejectReadOnly`，改名 `PrepareWrite`）在可写工作单元里调用内部的 `InMemoryUnitOfWork.EnsureTransaction()`，与关系型仓储写入前的 `EnsureTransactionAsync` 同一位置；提交与回滚复位。
9. **一致性**：`RepositoryConformance` 新增 4 例。
   - 用例 29：开始前、刚开始、读与空批量之后为假；第一次写入（含结果失败的批量更新）之后为真、再写入仍为真；提交、失败结果、未处理异常、管道外的提交与回滚之后为假。管道外的值在作用域释放之前核对，释放时的回滚会掩盖没有复位的实现。
   - 用例 30：只读操作里读、被拒绝的单条与批量写入、空批量、抛出的直接写入入口之后都为假；管道外的只读工作单元同样。
   - 用例 31：直接写入入口开启事务，重复调用与随后的仓储写入仍为真，提交与回滚后为假，没有活动工作单元时抛出 `PERSISTENCE_UNAVAILABLE_001`。子类以 `EnsureTransaction` 给出入口，内存实现没有，跳过。
   - 用例 32：绑定命名连接的工作单元开始与读取后为假、写入后为真、提交与回滚后为假，只读时为假；业务调用里另开的绑定连接工作单元与业务调用各报各的。子类以 `NamedConnection` 给出连接名并在配置里声明，套件把新的套件实体 `ConformanceLease` 登记到那个连接；内存实现不支持命名连接，跳过。
   - SqlSugar 在 SQLite（命名连接另一个库文件）与 PostgreSQL（命名连接指向同一个临时库）上跑，EF Core 在 SQLite 上跑（`ConformanceDbContext` 的模型加上 `ConformanceLease`）。

## 理由

- 守卫要回答的是「现在对外发出不可撤回的东西，会不会描述随后可能回滚的数据」。事务开着就是「会」；还没开说明本工作单元还没有写入，先推送、后写库正是回复操作要的顺序。`State` 回答的是「工作单元开没开始」，不是这个问题。
- 按写入调用而不是按写入结果算，三个实现在同一时机变真，一致性用例能逐步核对；失败的写入也算，是因为那时关系型事务已经开着，偏保守的一侧不会放过误用。
- 提交与回滚后复位，名字说的是此刻；管道外提交之后再推送是正确用法，不该被拦。
- 内存实现与关系型同义，测试与真实库的行为一致，误用在单元测试里就暴露。

## 影响

- **公开 API**：
  - `IUnitOfWork.HasTransaction`（新接口成员）；自己实现 `IUnitOfWork` 的替身要补上。框架里只有 `UnitOfWorkMiddlewareTests` 的替身，BasicApp 没有实现它。
  - `InMemoryUnitOfWork`、`SqlSugarUnitOfWork`、`EntityFrameworkCoreUnitOfWork` 各新增 `HasTransaction`。
  - `RepositoryConformance` 新增虚属性 `EnsureTransaction`、`NamedConnection` 与 4 个用例；新增套件实体 `Fixtures.ConformanceLease`（Preview）。EF Core 的 Provider 子类要让自己的 `DbContext` 模型包含它，才能给出 `NamedConnection`。
- **行为**：EF Core 工作单元在提交、回滚成功后立即释放事务对象，此前在作用域释放时；此后工作单元不再接受写入，对外不可观察。其余行为不变。
- **没有**新错误码、消息键、配置键，也没有表结构变化。
- **BasicApp**：`RealtimeOutbox.SendNowAsync` 的守卫改为看 `HasTransaction`：

  ```csharp
  // 本工作单元写过数据（事务开着）时立即推送会描述可能回滚的数据；还没写入的调用（只读操作、先推送后写库的回复）照常立即发出
  if (services.GetService<IUnitOfWork>() is { HasTransaction: true })
  {
      throw new InvalidOperationException($"Realtime push '{method}' is sent immediately and cannot be used after the call has written data; use SendAsync so it follows the commit.");
  }
  ```

  `HasTransaction` 只在 `Active` 时为真，不必再判 `State`。回复操作要先推送完、再经仓储写库；写库之后还要推送的，用 `SendAsync`。
- **限制**：
  - 不经仓储、也不经 `EnsureTransactionAsync` 直接对客户端执行的写入不在事务里，也不计入。
  - 守卫只看本作用域的工作单元：在另开的服务作用域里写入并提交的数据已经落库，不影响外层。
  - 提交或回滚抛出异常时的值不作规定。
