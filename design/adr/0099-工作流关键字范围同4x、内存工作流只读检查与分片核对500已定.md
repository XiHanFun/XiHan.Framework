## 一、工作流关键字的匹配范围同 4.x（第 1 条）

### 背景

第八批（ADR-0096）给定义列表、实例列表、待办加了关键字，范围比 4.x 窄：实例只匹配标题，待办只匹配任务标题与实例标题。ADR-0096 第三节当时的理由是「定义名已有精确过滤，关联 ID 是业务键、应按集合精确查」。用户拍板：按 4.x 各自匹配的字段对齐。

4.x 的匹配字段（BasicApp 5.9.1，`backend/src/modules/XiHan.BasicApp.Workflow/Application/QueryServices/`；框架 4.x 的 `framework/src/XiHan.Framework.Workflow` 本身没有关键字查询，关键字都在应用的查询服务里）：

| 查询 | 4.x 匹配的字段 | 4.x 的做法 |
| --- | --- | --- |
| 定义列表 `WorkflowDefinitionQueryService` | 编码 `Code`、名称 `Name` | 库里 `SetKeyword`（SqlSugar 的 `LIKE`） |
| 实例列表 `WorkflowInstanceQueryService`、「我发起的」`WorkflowApprovalQueryService.GetStartedPageAsync` | 名称 `Name`、关联 ID `CorrelationId` | 同上 |
| 待办 `WorkflowTodoQueryService` | 任务标题、实例名称、定义编码、关联 ID | 全取后在内存里按 `OrdinalIgnoreCase` 包含 |
| 我已审批 / 抄送我的（`WorkflowApprovalQueryService`） | 任务标题、实例名称、关联 ID | 在 BasicApp 自己的办理记录表上，不归框架 |

### 备选

1. 维持第八批的范围：搜索框里输单据号查不到实例与待办，按流程编码搜不到有显示名的待办，与 4.x 的用户习惯不符。
2. 三处按 4.x 对齐（采纳）。
3. 再扩：实例也匹配定义名、待办也匹配节点名等。4.x 没有，不做推测性扩展。

### 决策

取备选 2。

- 定义列表不变：名字、显示名、说明。4.x 的编码与名称就是 5.0 的名字（`WorkflowName`）与显示名；说明是第八批拍板时另加的，保留（比 4.x 宽）。
- 实例列表 `WorkflowInstanceQuery.Keyword`：实例标题 `Title` 或关联 ID `CorrelationId`。「我发起的」用同一个查询，随之同 4.x。
- 待办 `UserTaskQuery.Keyword`：任务标题、实例标题、定义名或关联 ID。关联 ID 取所属实例的：用户任务书签的关联 ID 由 `UserTask` 活动从实例抄来，转办与加签照抄，实例的关联 ID 启动后不变，所以与任务视图的 `UserTask.CorrelationId`（书签的，没有取实例的）相同。
- 规则不变（`WorkflowKeyword`）：去首尾空白、折叠后按序数包含、任一字段命中即可、不跨字段。关联 ID 也按包含匹配（4.x 同），输单据号的一段就能找到；按一组单据号精确查进度仍用 `CorrelationIds`。
- 内存实现：实例按 `WorkflowInstanceQuery.Matches`；待办在实例存储的 `RunningDefinitions` 里多带回关联 ID，按四个字段匹配。
- 数据库实现（照第八批在 SQL 里下推）：
  - 实例行 `SearchTitle` 改名 `SearchText` = `WorkflowKeyword.Join(title, correlationId)`，与定义行的 `SearchText` 同名同构。
  - 书签行 `SearchInstanceTitle` 改名 `SearchInstanceText` = 实例行的 `SearchText` 再以 U+001F 接上折叠后的定义名，与 `Join(title, correlationId, definitionName)` 相同；写书签时从实例行算出，实例新增或状态、定义名、`SearchText` 变了由实例存储同步（ADR-0077 第三节与 ADR-0096 第三节的同一路径）。
  - 书签行 `SearchTitle`（任务标题）不变；SQL 条件仍是两列各自判非空后包含、取或。

### 理由

- 用户拍板按 4.x；关键字是给人搜的入口，人记得的往往是单据号或流程编码，精确过滤（`CorrelationIds`、`DefinitionName`）是给程序用的，两者不冲突。
- 数据库实现只在已有的查询列里多拼字段：列数不变、同步路径不变；实例一侧的列由实例行的 `SearchText` 加定义名算出，不必从文档取回标题，同步时也不用反序列化书签。
- 改名而不是沿用旧名：`SearchTitle` / `SearchInstanceTitle` 里已经不只是标题，留着旧名会误导回填与排查。5.0 还在预览、BasicApp 的 6.0.0 基线还没发布，改名的代价是重新生成基线。

### 影响

- 公开 API（`Workflow.Database`，Unshipped）：`WorkflowInstanceRow.SearchTitle` → `SearchText`，`WorkflowBookmarkRow.SearchInstanceTitle` → `SearchInstanceText`。`WorkflowInstanceQuery.Keyword`、`UserTaskQuery.Keyword` 签名不变，匹配范围变宽。自写 Provider 的实例存储与书签存储要按新范围匹配。没有新错误码、消息键、配置键。
- 行为：实例列表与待办的关键字结果变多（命中关联 ID 或定义名的也出来）；例如待办按定义名搜，原来只命中没给显示名的实例，现在有显示名的也命中。
- 表结构：实例表（`WorkflowInstanceRecord` / `PlatformWorkflowInstanceRecord`）新列 `SearchText`，书签表（`WorkflowBookmarkRecord` / `PlatformWorkflowBookmarkRecord`）新列 `SearchInstanceText`，都是长文本、可空；`InitTables` 只加列不删列，旧列 `SearchTitle`（实例表）、`SearchInstanceTitle`（书签表）留在库里、框架不再读写，可以手工删掉。没有新索引。
- 回填（升级前写入的行；没回填的不被关键字匹配）：实例行 `SearchText = WorkflowKeyword.Join(title, correlationId)`（`title` 取 `Document` 的 `displayName`，为空取 `definitionName`）；书签行 `SearchInstanceText` = 所属实例行的 `SearchText` + U+001F + `WorkflowKeyword.Fold(definitionName)`。用应用代码回填（SQLite 的 `lower()` 只管 ASCII）。
- 测试：存储套件用例 3、10，引擎套件用例 34，任务套件用例 5 加关联 ID 与定义名的断言（含不跨字段、`_` 与 `%` 按字面、实例的标题与关联 ID 变了书签随之同步）；任务用例 5 原来「`CONF-QUERY` 只匹配没给显示名的两个实例」改为三个都匹配。
- 差异（4.x 有、5.0 不做）：4.x 的「我已审批」「抄送我的」按办理记录的任务标题、实例名称、关联 ID 搜索，办理记录是 BasicApp 自己的表，由 BasicApp 照做；4.x 的待办关键字在内存里筛、分页不准，5.0 在存储里下推。

## 二、内存工作流在只读调用里拒绝写入（第 3 条）

### 背景

ADR-0077 起，只读调用（操作契约只读：动词 `get` / `list` 或声明了只读）里的工作流写入在取锁、执行活动之前拒绝（`IWorkflowTransaction.EnsureWritable`），ADR-0081 把它定为 500 类缺陷 `PERSISTENCE_UNEXPECTED_001`。数据库实现看加入的工作单元是否只读；内存实现总是放行：写入立即生效、活动的副作用已经发生；装了发件箱时事件写进只读工作单元被拒，调用才以 500 结束。第八批（ADR-0096 第六节）的一致性用例 30 照实按两种行为断言，留作待定。

### 备选

1. 维持：内存实现不检查。开发与测试用内存实现时发现不了只读操作里发起流程的缺陷，换数据库实现上线才暴露。
2. 内存实现看工作单元：没装持久化的宿主没有工作单元，检查形同虚设；且内存实现不加入工作单元，问它是否只读语义上不对。
3. 内存实现看调用的操作契约（采纳）。

### 决策

取备选 3。

- `InMemoryWorkflowTransaction.EnsureWritable`：调用带操作描述且 `OperationContract.IsReadOnly` 时返回 `Error.Unexpected(PERSISTENCE_UNEXPECTED_001, persistence.unit_of_work.read_only)`，否则成功。这正是 Transaction 阶段决定开只读工作单元的依据，两种实现因此在同一类调用里拒绝；`WorkflowScope` 在取锁、执行活动之前调用它，引擎、任务服务、定义目录、外部任务服务的写入都提前拒绝。没装持久化时同样拒绝。
- `Workflow.InMemory` 显式引用 `Persistence.Abstractions`（原来经 `Workflow.Abstractions` → `Messaging.Abstractions` 间接可见），`InMemoryWorkflowFeature` 另登记 `PersistenceMessages.Catalog`（同名目录合并），没装持久化的宿主也能翻译拒绝的消息。
- 一致性用例 30 去掉按 `JoinsCallerTransaction` 的分支：两种实现都是写入被拒、调用本身成功、活动没有执行、只有原来那一个实例。

### 理由

- 只读操作里写数据是代码缺陷（RFC-0005），默认实现应当和生产实现一样早暴露它；错误码、消息键、拒绝时机都与数据库实现相同，换实现不改变可观察行为。
- 判定看操作契约而不看工作单元：内存实现本来就不加入工作单元，契约是两者共同的上游。

### 影响

- 行为：用内存工作流的应用，若在 `get` / `list` 或声明了只读的操作里发起或推进流程，原来写入成功（装了发件箱时调用以 500 结束），现在写入返回 `PERSISTENCE_UNEXPECTED_001`（HTTP 500）、什么也不写；调用本身是否失败取决于操作怎么处理这个结果。没有公开签名、配置键、启动失败条件的变化。
- 依赖：`XiHan.Framework.Workflow.InMemory` 的包依赖多一个 `XiHan.Framework.Persistence.Abstractions`（本来就在依赖闭包里）；CLI 知识库 `catalog.json` 随之重新生成。
- 测试：内存测试项目新增 `ReadOnlyInvocationTests`（2 例，不装持久化的宿主）；用例 30 在两个内存宿主（有无发件箱）与数据库实现上同一断言。

## 三、租户分片时间列核对不通过时经管道报 500，定为已定（第 4 条）

### 背景

ADR-0097 第五节把 EF Core 在 SQLite 上的时间列核对扩到租户分片库：工作单元开始时核对，不符抛出携带 `PERSISTENCE_VALIDATION_008` 的异常，经管道由 Observe 阶段转为 `KERNEL_UNEXPECTED_001`（HTTP 500，原因是 008）。第八批收口时把「为什么不是 008 本身、为什么不是 400」列为待定。

### 备选

1. 维持 500 `KERNEL_UNEXPECTED_001`、原因码 008（采纳）。
2. 在 Transaction 阶段把它转成同码结果：008 是 VALIDATION 类，会按 400 回给调用方，而这是服务端库里的数据问题，调用方改不了。
3. 另立 UNEXPECTED / UNAVAILABLE 类的码：多一个只为这条路径存在的码；`BeginAsync` 里其余装配类错误（`PERSISTENCE_VALIDATION_002` 工作单元状态不对、`004` 连接未声明）也是以异常抛出、经管道是 500，要改就该一起改。

### 决策

取备选 1，不改代码。RFC-0005「租户分片」结果一条、`error-codes.md` 的 008 一行、docs-next（持久化与多租户指南、EF Core 包页）与 EF Core README 写明已定。

### 理由

- 状态码表达「谁能改正」：分片库的数据形式不对，只有运维能修，按 500 归入服务端错误、计入熔断与告警；原因码 008 留在 `Inner` 里，排查时看得到。
- 与启动时的核对、`BeginAsync` 的其余装配类错误一条路径，不为一个场景另开分支。

### 影响

无行为变化。行为已由 `EntityFrameworkCoreShardTimestampCheckTests` 钉住（`Error.Code` 是 `KERNEL_UNEXPECTED_001`，`Inner.Code` 是 008）。

## 四、撤销关键字的全角替换，只留小写折叠（第 2 条的后半）

### 背景

第八批（ADR-0096 第一节）的 `WorkflowKeyword.Fold` 除了不变文化的小写，还把 `%`、`_`、`[`、`\` 换成全角的 `％`、`＿`、`［`、`＼`，查询列与关键字两边都换：当时 SqlSugar 把 `Contains` 译成不转义的 `LIKE`，换掉之后 SQL 里比较的两边都没有通配字符，SqlSugar、EF Core 与内存实现的结果才一致；代价是这四个字符与全角字符视为相同。用户拍板（第九批第 2 条）在框架侧修好 SqlSugar，折叠值能撤就撤。ADR-0098（框架 `4af233a7`）让 SqlSugar 的 `Contains` / `StartsWith` / `EndsWith` 在 SQLite、PostgreSQL、MySQL、SQL Server、Oracle 上译成 `LIKE … ESCAPE '!'`，RFC-0005「规约里的字符串匹配」把字面匹配定为持久化契约；兼容库（达梦、人大金仓、openGauss、TiDB 等）与运行时数据源仍沿用不转义的翻译（ADR-0098 待定）。

逐项评估折叠里的三件事：

| 处理 | 为什么有 | 现在还要不要 |
| --- | --- | --- |
| `%`、`_`、`[`、`\` 换成全角 | 绕开 SqlSugar 不转义的 `LIKE` | 不要：五种主库上持久化已按字面匹配，EF Core 与内存实现本来就按字面 |
| 不变文化小写 | 各实现大小写规则不同：EF Core 的 `Contains`（SQLite `instr`、PostgreSQL `strpos`）、PostgreSQL 与 Oracle 的 `LIKE`、内存的序数比较区分大小写，SQLite 的 `LIKE` 只对 ASCII 不区分，MySQL 与 SQL Server 按排序规则 | 要：不折叠，同一个关键字在各实现上结果不同（RFC-0005 也写明「要跨库一致的不区分大小写匹配，存一列折叠后的值」） |
| U+001F 换成空格 | 多个字段拼进一列，关键字里不能有分隔符，否则会跨字段 | 要：与 SqlSugar 无关 |

### 备选

1. 维持全角替换：兼容库上照样按字面，但工作流为一个已经修好的持久化缺陷继续带着自己的绕法，四个字符与全角字符视为相同的怪处也留着。
2. 撤销全角替换，只留小写与分隔符（采纳）。
3. 只在持久化还没按字面的库上替换：工作流要知道底层是哪个 Provider、哪种库，是双轨实现；查询列的内容还要随换库而变。
4. 连小写也撤：EF Core 与 PostgreSQL 上变成区分大小写，与内存实现、SQLite 上的 SqlSugar 不一致。

### 决策

取备选 2。

- `WorkflowKeyword.Fold` 只做不变文化的小写（`char.ToLowerInvariant`），并把 U+001F 换成空格；其余字符原样保留。`Normalize`、`Join`、`Matches` 的签名与用法不变。关键字里的 `%`、`_`、`[`、`\` 按字面匹配，与全角的 `％`、`＿`、`［`、`＼` 是不同的字符。
- 数据库实现的查询与写入代码不变（仍是对查询列 `Contains`），按字面由持久化保证；查询列的构成随 `Fold` 变化。
- 持久化还没保证字面匹配的库上（SqlSugar 的兼容库与其余数据库），关键字里的 `%`、`_` 照那个库的 `LIKE` 当通配，PostgreSQL 系兼容库上以 `\` 结尾的关键字可能报错——这与应用自己实体的 `Contains` 查询一样，随持久化把这些库验证后加进名单一并解决，工作流不另做绕法。运行时数据源不涉及（工作流的表经仓储读写、施加了约定）。
- 一致性套件：存储用例 11 加 `[` 与反斜杠的字面匹配（含以反斜杠结尾的关键字、两个反斜杠不当一个）、全角与半角互不匹配；存储用例 3、10，引擎用例 34，任务用例 5 加全角关键字不匹配半角内容的断言；原有的 `%`、`_` 按字面的断言不变。

### 理由

- 绕法的唯一理由已经不在：字面匹配是持久化的契约（RFC-0005），在五种主库上有实现与真实库的验证（ADR-0098），工作流照契约用 `Contains` 即可；兼容库的缺口属于持久化，在那里补，所有实体一起受益。
- 小写折叠不是绕法，是跨库一致的大小写语义本身需要的；RFC-0005 也推荐这种做法。
- 全角与半角是不同的字符，不再把用户输入的 `50％` 与 `50%` 混为一谈。

### 影响

- 公开 API：`WorkflowKeyword.Fold` 的行为变化（签名不变），`Normalize` / `Join` / `Matches` 随之；没有新类型、错误码、消息键、配置键。
- 行为：关键字里含 `%`、`_`、`[`、`\` 的，只匹配含同样半角字符的内容；含全角 `％`、`＿`、`［`、`＼` 的只匹配含全角的内容（原来两者互通）。不含这八个字符的关键字结果不变。
- 已存的查询列：升级前写入的行里这四个字符存的是全角，按半角关键字搜不到；不含这四个字符的行不受影响。旧值不能反推（原文里的全角字符与替换出来的分不开），要从 `Document` 重算：定义行 `SearchText = WorkflowKeyword.Join(name, displayName, description)`；实例行 `SearchText = WorkflowKeyword.Join(title, correlationId)`；书签行 `SearchTitle = WorkflowKeyword.Fold(payload.title)`（没有标题为空）、`SearchInstanceText` = 所属实例行的 `SearchText` + U+001F + `WorkflowKeyword.Fold(definitionName)`。实例行与书签行的实例一侧列第一节已改名、本来就要全量回填，同一次回填用现在的 `Fold` 即可；额外要重算的是定义行的 `SearchText` 与书签行的 `SearchTitle`（只有含这四个字符的行会变，全量重算最简单）。存储整体替换一行时按新折叠重写，没回填的行在下一次被保存时自愈。没有表结构变化。
- 测试：内存实现与数据库实现（SQLite 的 SqlSugar、EF Core、装了发件箱的宿主；PostgreSQL 18 上 54 例）全过；修改验证：把 `%`、`_` 的全角替换加回 `Fold`，内存实现上 7 例失败（存储用例 3、10、11 各一例，引擎用例 34 与任务用例 5 在有无发件箱两种宿主上各两例）。

> 修订（2026-11-02）：第一节的列改名由 ADR-0101 第一节定为已定；第四节留给兼容库的工作流关键字由 ADR-0101 第二节定为已定（随持久化在真实库上验证后加进名单，工作流不另做绕法）；第四节小写折叠的理由里 EF Core 在 SQLite 上的 `instr` 已由 ADR-0101 第三节换成 `LIKE`，折叠照旧要保留。
