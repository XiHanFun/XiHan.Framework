# ADR-0102 工作流定义与实例列表的排序字段与定义的创建时间区间

## 状态

已采纳（`spec/rfcs/0021-workflow.md`「定义」一节新增「列表排序」，`spec/conventions/error-codes.md` 的 `WORKFLOW_VALIDATION_002` 一行随之修订）。扩展 ADR-0096 第一、二节（定义列表与实例查询）：缺省排序不变。

## 日期

2026-11-02

本 ADR 记录第十一批回灌（`o-batch-backlog.md`，BasicApp Workflow 会话报回、用户定交给框架补）的一项决定。

## 背景

定义查询 `WorkflowDefinitionQuery` 固定按名字升序、版本降序，没有创建时间区间；实例查询 `WorkflowInstanceQuery` 固定按创建时间降序（创建时间区间已有）。BasicApp 的两个列表都要能按列排序，定义列表还要能按创建时间过滤。

## 备选

1. **收一组通用排序（字段名字符串 + 方向，可多列）**：调用方能按任意列排，等于把存储的列名变成公开契约；内存实现要按名字反射取值（Ring 2 的抽象包里不该有），数据库实现要防注入、要逐一映射。
2. **白名单枚举的单个排序字段 + 方向，接固定的次序键（采纳）**。
3. **白名单枚举的多列排序（一组字段与方向）**：界面一次只按一列排，多列的组合要逐一处理次序键与重复列（SQL Server 不许同一列在 `ORDER BY` 里出现两次），没有实际的需求。

状态的排序另有两个选择：按状态名比较（列里存的就是状态名，采纳），或另加一列状态序号按生命周期排——多两列、多一次回填，换来的只是分组的先后；按标题排序要一列定长的排序键：给显示名加长度上限（新的启动失败条件、新的消息键），或存标题的前 256 个字符（采纳）；可空时间的空值位置：统一要持久化的排序支持 `NULLS FIRST / LAST`（各库写法不同，SqlSugar 与 EF Core 都没有通用的表达），本批照数据库。

## 决策

取备选 2。

- `WorkflowDefinitionQuery`：
  - 新增 `CreatedFrom` / `CreatedTo`（创建时间，下界含、上界不含，与实例查询同义），内存实现在 `Matches` 里、数据库实现在 SQL 里过滤。
  - 新增 `SortBy`（`WorkflowDefinitionSortField`：`Name`、`Title`、`Version`、`Status`、`CreatedAt`、`PublishedAt`，缺省 `Name`）与 `Descending`（缺省 `false`）。排序字段之后接次序键名字升序、版本降序（数据库实现最后再按 ID 升序；与排序字段相同的跳过）。缺省就是原来的名字升序、版本降序。
- `WorkflowInstanceQuery`：新增 `SortBy`（`WorkflowInstanceSortField`：`CreatedAt`、`EndedAt`、`Status`、`DefinitionName`、`Title`，缺省 `CreatedAt`）与 `Descending`（缺省 **`true`**，实例列表缺省最新的在前，与原来相同）。排序字段之后接次序键创建时间降序、写入先后降序、ID 降序；排序字段是创建时间时，写入先后与 ID 随它的方向。
- 两个枚举带 `JsonStringEnumConverter`（与工作流其余枚举一样），请求里写名字；不认识的名字在反序列化时被拒绝，越界的数字由 `IWorkflowDefinitionCatalog.QueryAsync` / `IWorkflowEngine.ListInstancesAsync` 校验：返回 `WORKFLOW_VALIDATION_002`（HTTP 400），新消息键 `workflow.definition.query_sort_invalid` / `workflow.instance.query_sort_invalid`（参数 `sort`，10 种语言），不进存储。`CountInstancesAsync` 不看排序、不校验（与分页一样）。存储收到白名单以外的值抛出 `ArgumentOutOfRangeException`（调用方已校验，是编程错误）。
- 比较规则（写进 RFC 与 XML 文档，照实）：文本（名字、标题、定义名）按数据库列的排序规则，内存实现按序数；状态按状态名（序数），是按名字的分组；可空时间的空值位置照数据库（PostgreSQL、Oracle 当作最大，SQLite、MySQL、SQL Server 当作最小），内存实现当作最小；标题按前 256 个字符。
- 新类型 `WorkflowSortKeys`：`MaxTitleLength = 256`、`Title(string)`（截到 256 个字符，截在代理对中间时少取一个）。数据库实现的定义行与实例行新增排序用的 `Title` 列（`varchar(256)`，可空），写入时存 `WorkflowSortKeys.Title(标题)`；内存实现按同一个键比较。
- 不加新索引：定义每个分区的行数少（几十到几百），创建时间区间与任何排序都是对过滤后的少量行排序；实例按创建时间排序仍走 `(TenantId, CreatedAt)`，按结束时间走已有的 `(TenantId, EndedAt)`，按标题、状态、定义名排序是对过滤后的行排序——要常用再由应用按自己的查询习惯加索引。
- 待办查询 `UserTaskQuery` 不动：它只按创建时间排序，已有的 `Descending` 与本批的同名同义（是否按排序字段降序）；只有一个排序字段，加 `SortBy` 没有可选的值。三个查询的形状因此一致：排序字段（待办隐含为创建时间）加 `Descending`，各自的缺省方向沿用各自列表原来的习惯（定义升序、实例降序、待办升序即先到先办）。

## 理由

- 白名单把「能按什么排」定成契约：内存实现与各数据库实现逐个字段对得上，一致性套件能逐个验证；BasicApp 列表能排的列都在里面，照列名映射即可。
- 单列加固定次序键是界面上「点列头排序」的语义，同值的行有确定的先后，分页不重不漏；次序键跳过排序字段，SQL Server 上也成立。
- 缺省值保持原来的顺序，已有调用不受影响；实例查询的 `Descending` 缺省为真是为了这一点。
- 标题存截断的排序键而不是给显示名加上限：不新增启动失败条件，256 个字符之后才不同的标题极少，由次序键决定先后。

## 影响

- 公开 API（Workflow.Abstractions，Unshipped）：`WorkflowDefinitionQuery.CreatedFrom` / `CreatedTo` / `SortBy` / `Descending`，`WorkflowInstanceQuery.SortBy` / `Descending`，新类型 `WorkflowDefinitionSortField`、`WorkflowInstanceSortField`、`WorkflowSortKeys`，新消息键常量 `WorkflowMessages.DefinitionQuerySortInvalid`、`InstanceQuerySortInvalid`。Workflow.Database：`WorkflowDefinitionRow.Title`、`WorkflowInstanceRow.Title`。Workflow.Conformance：新用例方法三个。自写 Provider 的定义存储与实例存储要实现排序与次序键、定义的创建时间区间。
- 行为：缺省排序不变；新错误只在给了越界的排序字段时出现（400）。没有新的启动失败条件、配置键。
- 表结构：`WorkflowDefinitionRecord` / `PlatformWorkflowDefinitionRecord` 与 `WorkflowInstanceRecord` / `PlatformWorkflowInstanceRecord` 新增可空列 `Title varchar(256)`，`InitTables` 照常给已有行的表加上；没有新索引。升级前写入的行要回填（定义 `Title = WorkflowSortKeys.Title(displayName 为空取 name)`，实例 `Title = WorkflowSortKeys.Title(displayName 为空取 definitionName)`，都从 `Document` 取）；没回填的行按标题排序时位置照空值规则，存储整体替换一行时写上。独立库的租户库同样要加。
- 测试：存储套件新增用例 12（定义按每个排序字段升降序、次序键、长标题按前 256 个字符、发布时间只比较有值的行、分页稳定、创建时间区间）与 13（实例按每个排序字段升降序、同刻按写入先后、超长显示名写得进定长列、结束时间只比较有值的行、分页稳定、计数不看排序），引擎套件新增用例 36（越界的排序字段经目录与引擎返回 400、计数不校验、定义与实例按标题经引擎升降序、实例的缺省方向）；Abstractions.Tests 加排序键与缺省值。

### 不做的

- 任意字段排序与过滤：只做白名单里的字段与定义的创建时间区间。
- 多列排序：一次一个排序字段，其余由固定的次序键决定。
- 状态按生命周期先后排序：状态列存的是名字，按名字排，是分组而不是先后；要按生命周期排需要另加序号列（待定，见汇报）。
- 实例列表按版本、关联 ID、发起人排序：界面没有开放这几列。

> 修订（2026-11-02）：「状态按状态名比较、是按名字的分组」由 ADR-0103 修订为按生命周期的先后（定义 Draft → Published → Disabled → Archived，实例 Running → Suspended → Completed → Canceled → Faulted → Terminated），定义表与实例表新增可空列 `StatusOrder`；「不做的」第 3 条随之作废。

> 修订（2026-11-03）：单个排序字段 `SortBy` / `Descending` 由 ADR-0104 换成有序的排序项列表 `Sorts`（多字段），白名单、次序键与缺省排序不变；「不做的」第 2 条（多列排序）随之作废。
