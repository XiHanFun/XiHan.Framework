# ADR-0122 授予与租户目录读主库

## 状态

已采纳（`spec/rfcs/0005-persistence.md` 随之修订）。

## 日期

2026-11-04

本 ADR 记录第三十一批回灌（`ak-batch-backlog.md`，N5 安全审查，用户定修）的第三项。

## 背景

ADR-0118 让只读工作单元读从库，框架自己的单例存储也一样，文档写明了这一点。授予读取（`GrantInvocation`）和租户目录（`CatalogInvocation`）是单例存储里决定放不放行的两个。

配了从库之后，撤销授予、停用租户的生效时间变成复制延迟加缓存时长：缓存过期时从落后的从库读回旧值，再缓存一整个存活时间。这段时间里被撤销的权限和被停用的租户照常放行。

## 决策

1. `UnitOfWorkOptions` 加非位置属性 `ReadsPrimary`，缺省假。为真时只读工作单元读主库，其余仍是只读的语义：不开事务，写入照样拒绝。
2. 授予读取和租户目录读取设它。撤销、停用的生效时间回到缓存时长。
3. Provider 无关：没有从库的 Provider（EF Core、内存）上没有作用，工作单元的状态与拒绝写入都不变。一致性套件覆盖这一点。
4. 管道里的只读操作不变，仍读从库：它不是单例存储，读到落后的数据不决定放行。

## 备选

1. **这两处开可写工作单元**：事务延迟到第一次写入才开，路由效果相同，也不用加 API。但丢了只读保护，读代码看不出为什么可写，EF Core 上还多出变更跟踪。否决。
2. **这两处绑定命名连接**：只有 SqlSugar 支持，这两个存储是 Provider 无关的，应用也不一定给主库单独命名。否决。
3. **所有只读工作单元都读主库**：那从库就没有用了。否决。
4. **加配置开关，允许这两处读从库**：现在没有使用者，这是安全判定的依据，不该配成读落后的数据。否决。读压力由缓存挡住，每个（主体，租户）或租户每个存活时间读一次。

## 影响

这是对外行为变化，只影响配了从库的部署：授予与租户目录的读取回到主库。没配从库的部署没有变化。

公开 API 新增 `UnitOfWorkOptions.ReadsPrimary`，是增量。`UnitOfWorkOptions` 的位置参数不变，解构不变。

### 没有动的

- **审计查询**：可以落后，继续读从库。
- **调度与工作流的租约探测**（`LeaseProbe`、`PollerLeaseProbe`）：读一行探连通，配了从库时探到的是从库，主库宕了它可能仍报可达。它不决定放行，也不在这一批的范围里，记进待办。
