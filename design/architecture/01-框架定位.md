>
> 本文从属于 [下一代框架总体方案](../下一代框架总体方案.md)，冲突处以总体方案为准。

## 一、框架定义

### 1.1 一句话定位

**XiHan Framework 是一套语言中立的应用框架规范及其 .NET 参考实现，以"微内核 + 能力图谱 + 管道执行"为核心范式，通过能力包、插件、协议三条扩展轴组合能力，适用于 B2B SaaS、企业后台、微服务、边缘服务等多种场景。**

### 1.2 三层定位

| 层 | 定位 | 对标参照 |
| --- | --- | --- |
| **原语与内核** | 十年不变的原语层 + 大版本内稳定的微内核 | Linux 系统调用 ABI、Rust `core`、XNU 微内核 |
| **子系统能力** | 通用企业能力标准化：持久化、缓存、消息、安全、多租户、调度等，抽象 + 默认实现 + Provider | Dapr Building Blocks、Android Treble |
| **协议与工具链** | 一份操作契约多协议暴露（HTTP / gRPC / MCP / 命令行）、打包与编排、迁移工具 | FastAPI、ASGI、OCI、Service Binding |

### 1.3 主要适用场景

| 场景 | 特征 |
| --- | --- |
| **多租户 SaaS 平台** | 租户隔离、数据分片、订阅计划 |
| **企业后台管理系统** | 复杂权限、审批流、组织架构 |
| **行业垂直应用** | CRM / ERP / WMS / HRM 等行业定制 |
| **微服务后端** | 每个服务只装所需能力包，远程能力经协议接入 |
| **开放 API 与 AI 工具平台** | 操作契约同时暴露为 REST、gRPC 与 MCP tool |
| **边缘 / 轻量服务** | `Profiles.Minimal`：原语 + 内核 + 一个宿主 |
| **插件化平台** | 三级隔离的插件宿主，第三方插件可用任意语言编写 |

### 1.4 不是

| 不是 | 原因 |
| --- | --- |
| 不是 ABP 的替代品或分支 | 架构哲学不同：特性组合与管道阶段，而非强制模块基类与生命周期钩子 |
| 不是 Spring Boot 的 .NET 移植 | .NET 有自己的最佳实践：Generic Host、源生成器、Native AOT |
| 不是微服务框架 | 不绑部署形态，单体 / 模块化单体 / 微服务均可 |
| 不是 Sidecar 平台 | 能力在进程内组合，远程能力是可选 Provider |
| 不是低代码平台 | 面向开发者，不面向拖拽配置 |
| 不是 ORM | 持久化走端口与 Provider，`EntityFrameworkCore` / `SqlSugar` / `MongoDB` 各有适配包 |
| 不是 UI 组件库 | 前后端分离，前端由 XiHan.UI 独立演进 |

### 1.5 是

| 是 | 具体含义 |
| --- | --- |
| 规范与参考实现 | XiHan Spec 定义原语、清单、上下文、管道、插件协议；.NET 是参考实现，其他语言按规范实现 |
| 开发效率基础设施 | 企业级通用能力开箱即用，默认实现零外部依赖 |
| 架构共识载体 | 统一的环层、依赖方向、术语表、命名文法、代码规范 |
| 能力集成平台 | 能力图谱协调多技术栈，而非基类继承绑定 |
| 质量保障体系 | 内置可观测、审计、错误模型、API 稳定性分级、一致性测试 |
| 可扩展宿主 | 微内核 + 能力包 + 插件 + 协议，按需组合，渐进增长 |

## 二、与主流 .NET 框架对比

### 2.1 ABP Framework

| 维度 | ABP | XiHan 5 |
| --- | --- | --- |
| 模块化 | 强制模块系统，`[DependsOn]` + 生命周期钩子 | 能力包为可选组织方式，`IFeature` + `UseFeature<T>()` 显式组合，依赖写在清单里按能力 ID 解析 |
| 实体基类 | 强制继承 `Entity<TKey>` 等 | `Domain` 只提供接口协议（`IEntity<TKey>`、`ISoftDeletable`、`IMultiTenant`），按需组合 |
| 扩展机制 | 拦截器 + 虚方法重写 | 固定阶段的管道中间件 + 源生成器 |
| 动态代理 | Castle 运行时代理 | 零反射；编译期生成 |
| 包数量 | 50+ | 内核 2 包（`Primitives`、`Kernel`）+ 按领域的子系统包 + 3 个 Profile 元包 |
| DI | 包装 MS DI + 自动注册 | 原生 MS DI + 显式注册，生成器注册可选入 |
| 对外暴露 | 动态 API（HTTP） | 操作契约，一份契约暴露为 HTTP / gRPC / MCP / 命令行 |
| 跨语言 | 无 | 规范 + 一致性测试 + 各语言 SDK |

### 2.2 Furion

| 维度 | Furion | XiHan 5 |
| --- | --- | --- |
| 设计理念 | 大而全的全家桶，开箱即用 | 微内核 + 可选能力包，按需加载；默认实现保证开箱即用 |
| 依赖注入 | 属性扫描自动注册 | 显式注册 + 可选源生成器注册 |
| 动态 API | 内置核心功能 | 操作契约 + `Protocols.Http` 适配器 |
| 配置方式 | 约定为主，配置为辅 | 显式为主，约定可覆写，二者都有退出机制 |
| 包结构 | 单一主包 + 少量扩展 | 抽象包 + 机制或技术命名的实现包 |
| 目标场景 | 中小型项目快速开发 | 中大型、长期维护、需要跨团队共识的项目 |

### 2.3 MASA Framework

| 维度 | MASA Framework | XiHan 5 |
| --- | --- | --- |
| 设计理念 | 云原生、微服务优先 | 部署形态中立，应用清单一键产出容器与 k8s 产物 |
| 模块化 | Building Blocks | 能力图谱 + 管道阶段 |
| 数据访问 | 多 ORM | `Persistence.Abstractions` + `EntityFrameworkCore` / `SqlSugar` / `MongoDB` |
| 可观测性 | 集成 OpenTelemetry | 内核直接基于 `System.Diagnostics`，`Observability.OpenTelemetry` 只配导出器 |
| 多租户 | 内置 | `MultiTenancy.*` 子系统，管道 Tenant 阶段 |

### 2.4 跨语言参照

| 参照 | 借鉴什么 | 不学什么 |
| --- | --- | --- |
| **Dapr** | Building Blocks 能力抽象、可插拔组件走 gRPC | Sidecar 架构 |
| **OpenTelemetry / MCP** | 规范 + 多语言 SDK + 一致性测试 | 无 |
| **FastAPI** | 类型即契约，Schema 自动生成 | Python 运行时反射 |
| **NestJS** | 装饰器声明能力、模块化组织 | TypeScript 特有的装饰器元编程 |
| **Vue 3** | 渐进式、组合式 | 仅后端框架，不涉及 UI |
| **Rust** | 零成本抽象、编译期保证、Edition | 语言层面的所有权机制 |

完整借鉴矩阵见总体方案 §3。

## 三、版本与兼容策略

### 3.1 版本线

- 下一代所有包共享一条版本线，从 `5.0.0` 起，首个预览版 `5.0.0-preview.1`。
- 大版本每 3 年一次，对齐 .NET LTS；小版本约每 6 个月；补丁随时。
- LTS 大版本：3 年活跃支持 + 1 年安全修复。4.x 在 5.0 GA 后进入 24 个月维护期。

### 3.2 TFM 滚动策略

```text
.NET 10（LTS）  ← 当前主力
.NET 8 （LTS）  ← 过渡期 12 个月后移除
```

原则：当前 LTS，上一 LTS 保留 12 个月过渡期；不在单一 TFM 上锁定超过两年。

### 3.3 API 稳定性分级

| 级别 | 标记 | 含义 | 示例 |
| --- | --- | --- | --- |
| **Stable** | `[ApiLevel(Stability.Stable, "5.0")]` | 大版本内不破坏 | `IFeature`、`PipelineBuilder` |
| **Preview** | `[ApiLevel(Stability.Preview, "5.0")]` | 可能变更，不建议生产使用 | 新子系统的首个抽象版本 |
| **Experimental** | `[ApiLevel(Stability.Experimental, "5.0")]` | 可能移除，需反馈 | `Plugins.Wasm`、孵化区包 |
| **Internal** | `[ApiLevel(Stability.Internal, "5.0")]` | 不对外暴露，分析器阻止引用 | 内核内部类型 |
| **Deprecated** | `[ApiLevel(Stability.Deprecated, "5.2")]` | 将在下一个大版本移除 | 旧版 API |

原语层（`XiHan.Framework.Primitives`）在 Stable 之上再加一条**冻结**承诺：只增不改，跨大版本不破坏。

### 3.4 弃用流程

```text
5.x：标记 Deprecated + [Obsolete] 警告 + 迁移文档，至少跨 2 个小版本
5.y：下一个大版本前的最后一个小版本升级为编译错误
6.0：移除，并提供 Roslyn 代码修复
```

### 3.5 版本号策略（SemVer 2.0）

```text
MAJOR.MINOR.PATCH[-preview.N]

MAJOR：破坏性 API 变更（原语层除外，原语层只能新包并存）
MINOR：新增向后兼容功能
PATCH：向后兼容的缺陷修复
-preview.N：预览版
```

## 四、旧框架诊断（新框架需求的来源）

### 4.1 旧框架概览

旧框架（`framework/`，v4.7）包含 **66 个源码项目**，按七层组织：

```text
1. Common          Analyzers, Utils
2. Metadata        Metadata
3. Core            Core（模块系统、DI、动态代理、AOP）
4. Domain          Domain.Shared, Domain
5. Application     Application.Contracts, Application, MultiTenancy(.Abstractions), Settings, Validation(.Abstractions)
6. Infrastructure  AI(.Abstractions), Auditing, Authentication, Authorization, Bot + 6 个 Bot.*, Caching, Castle,
                   Data, DevTools, DistributedIds, EventBus(.Abstractions/.Kafka/.RabbitMQ/.Redis), Http,
                   Localization(.Abstractions), Logging, Messaging, ObjectMapping, ObjectStorage, Observability,
                   Script, SearchEngines(.Abstractions/.Elasticsearch), Security, Serialization, Tasks, Templating,
                   Threading, Timing, Traffic, Uow, Upgrade, VirtualFileSystem, Workflow(.Abstractions)
7. Web             Web.Api, Web.Core, Web.Docs, Web.Gateway, Web.Grpc, Web.Mcp, Web.RealTime
```

### 4.2 旧框架的具体问题

| # | 问题 | 表现 | 影响 |
| --- | --- | --- | --- |
| 1 | 模块生命周期过度设计 | `XiHanModule` 有 7 个生命周期钩子 | 作者困惑于"该在哪个钩子写代码"，调用栈深 |
| 2 | `[DependsOn]` 隐式依赖图 | 依赖写在特性上，按类型而非能力 | IDE 无法静态分析，循环依赖运行时才报错，测试要加载完整模块树 |
| 3 | 基类继承链过深 | 实体基类 7 层 | 组合能力受限，无法按需选择 |
| 4 | ORM 硬绑定 | `Data` 直接依赖 SqlSugar | 无法切换到 EF Core 或其他 ORM |
| 5 | 包粒度不一致 | 66 个项目，粒度从工具类到 Web 全栈不等 | 选择困难，版本必须精确同步 |
| 6 | 反射依赖过重 | 自动注册、动态 API、模块发现、Castle 代理 | AOT 不可用，冷启动慢 |
| 7 | 没有稳定性分级与兼容门禁 | 公开 API 无 Stable / Preview 之分，无 ApiCompat | 破坏性变更靠人审 |
| 8 | 边界外的基础设施模块 | Bot、Script、Templating、Upgrade 等 | 应用层需求进了框架层 |
| 9 | 命名没有统一词表 | `Data` / `Uow` / `Tasks` / `Traffic` 等词义重叠或含糊 | 名字无法从领域推出 |

## 五、新框架设计目标

| 维度 | 旧框架 | 新框架目标 |
| --- | --- | --- |
| 内核包数 | 1 个大 `Core` | `Primitives` + `Kernel` 两包，内核公开类型 ≤ 120 |
| 模块系统 | `[DependsOn]` + 7 个钩子 | 清单声明能力依赖，`UseFeature<T>()` 显式组合，`Configure` + `Start/Stop` |
| 扩展机制 | Castle 动态代理 | 固定阶段管道 + 源生成器 |
| 实体模型 | 7 层基类 | 接口协议组合 |
| 数据访问 | SqlSugar 绑定 | `Persistence.Abstractions` + 多 Provider |
| 对外暴露 | 动态 API | 操作契约，多协议暴露 |
| 插件 | 仅文件夹加载程序集 | 进程内 / Wasm / 进程外三级隔离 |
| 跨语言 | 无 | XiHan Spec + 一致性测试 |
| API 稳定性 | 无分级 | Stable / Preview / Experimental / Internal / Deprecated + 原语层冻结 |
| 可观测性 | 独立日志模块 | 内核直接基于 `System.Diagnostics` |
| 命名 | 无统一词表 | 术语表 + 包 ID 文法，由架构测试强制 |
| 测试基础设施 | 基本无 | `Testing` 包 + 每领域 `Conformance` 套件 |
| AOT 兼容 | 不支持 | 内核零反射，CI 做 AOT 发布冒烟 |

## 六、5.0 不做清单

| 功能 | 5.0 状态 | 说明 |
| --- | --- | --- |
| Bot / Script / Templating / Upgrade / DevTools | 移除 | 应用层需求，可进孵化区 |
| 后台管理 UI | 永不做 | 前后端分离 |
| Workflow / Search / AI / Actors | 5.x 后续 | 子系统抽象在后续小版本孵化 |
| 实时通信 / 网关 | 5.x 后续 | 协议适配器或独立包 |
| Wasm 插件 | Experimental | 5.0 带实验实现，GA 在后续版本 |
| Castle 动态代理 | 移除 | 管道中间件 + 源生成器替代 |
| 管道阶段内并行分支 | 5.x 后期 | 计算图形态 |
| Kubernetes Operator | 5.x 后期 | 调和逻辑只在编排层 |

## 七、与 BasicApp 的关系

`XiHan.BasicApp` 是基于旧框架构建的参考应用。新框架的 GA 门槛之一是 BasicApp 全量跑在 5.0 上：

- 先把模块骨架改成特性，再逐模块改为原生写法（BasicApp 当时借助 `xihan migrate v4` 完成；该规则集已按 ADR-0021 删除）。
- 保留 Saas 管理、组织架构、权限管理等业务场景，用能力包与操作契约重写。
- 重建后的 BasicApp 作为官方参考实现与新用户起点模板。
